EggDB v0.4.0 builds on v0.3.0's SQL dialects, listeners and desktop client. It is one batch of
work (D314 to D334): partitions that move rows and index on expressions, a transaction that goes on
after a failing statement in four of the five dialects, read-only transactions, generated columns
and `CREATE TABLE ... AS` in every dialect that has them, PostgreSQL's privilege questions,
subqueries in `EXPLAIN`, Redis bitmaps, HyperLogLog and geo commands, Elasticsearch's multi and
by-query APIs, more of Cypher and PromQL, syslog, HTTP/1.1 keep-alive on every HTTP listener, key
writes for AI agents, and a desktop client that browses a Redis-compatible server's keys and has
an editor menu. It is not faster than v0.3.0, and it is slower than v0.3.0's notes said: point
selects, bulk inserts and `GROUP BY` through SQL are slower than SQLite's on Linux and macOS, and
"Limits" gives the numbers and corrects what the v0.3.0 notes said about the point select. What
v0.3.0's notes said it did not do yet and is now done: `CREATE TABLE ... AS` in PostgreSQL, MySQL,
SQLite and Oracle, `RESET ALL` and `SET eggdb.dialect` inside routines, a way to limit the MCP
sessions of `eggdb serve` to some tables (`--mcp-tables`), browsing the keys of a Redis-compatible
server in the desktop client, the client's comment and format actions, and generated columns, which the
roadmap no longer lists among SQLAlchemy's dialect-suite failures. What it can't do yet is in one place, "Limits", and
what was tested on which platform in "What was tested".

## What v0.4.0 brings
- **Partitions** (D316). Partition keys can be expressions (`PARTITION BY RANGE (lower(name))`,
  from an allow-list of built-in functions, since user routines are refused in keys). An `UPDATE`
  through the partitioned table that changes the key moves the row to the partition that now owns
  it, in every dialect. `CREATE INDEX` on the parent makes an index that reaches every partition,
  including ones attached later.
  **Files:** partition record version 2, written only when a key has an expression or a partition
  has attached indexes (see "Compatibility from here on").
- **A transaction goes on after a failing statement** (D317). In MySQL, SQLite, Oracle and SQL
  Server only the failing statement is undone and the transaction stays open; PostgreSQL keeps
  `25P02` until `ROLLBACK`. SQLite's `INSERT OR FAIL` keeps the rows before the conflict, SQL
  Server's `XACT_ABORT ON` still rolls back, and a MySQL `CALL` that ends in an error undoes the
  whole call. The undo is bounded by the statement's 1 GiB work memory (`53200`).
- **Read-only transactions** (D318). `SET TRANSACTION READ ONLY`, `START TRANSACTION READ ONLY`,
  `BEGIN READ ONLY`, `default_transaction_read_only` and `transaction_read_only`, each with its
  dialect's error for a write (PostgreSQL's, MySQL's and Oracle's dialects). Routines gain `RESET
  ALL`, `SET eggdb.dialect` and `ALTER FUNCTION ... SET | RESET`, and `current_setting` sees what a
  routine set earlier in the same statement (before, these were `0A000`).
- **`ROLLBACK TO SAVEPOINT` undoes key-value writes in `eggdb shell`** (D319). `put`, `del`,
  `incr`, `decr`, `expire`, `persist` and `cas`, times to live and collection entries included,
  are undone together with the SQL writes since the savepoint.
- **Collections with counts** (D320). `eggdb collection list` and `stats --collections` show each
  collection's entries, key bytes and value bytes at once, from a count the file keeps up to date
  on every write (`stats` stays instant from a cold open and on a read-only file, and `eggdb
  check` compares every kept count with a scan). `eggdb shell` runs `collection list | add |
  delete | move | rename`, `eggdb ui`'s picker renames (`e`), and a long `collection delete` shows
  its progress. Keys with a time to live that has run out count until the expiry sweep removes
  them, as Redis's `DBSIZE` does. **Files:** a count record and the `COLLECTION_COUNTS`
  read-only-compatible feature bit ([cli.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/cli.md),
  [format.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/format.md)).
- **More aggregates** (D321). `stddev`, `variance` and their `_samp` and `_pop` forms in every
  dialect's spelling (`STD`, `STDEV`, `STDEVP`, `VAR`, `VARP`), and the hypothetical-set
  aggregates `rank`, `dense_rank`, `percent_rank` and `cume_dist` with `WITHIN GROUP`. MySQL sorts
  NULLs as MySQL does (see "Limits" for what that costs), and PostgreSQL gives `2201W` for a NULL
  `WITH TIES` count.
- **Generated columns** (D322). PostgreSQL's `GENERATED ALWAYS AS (...) STORED | VIRTUAL`, MySQL's
  and SQLite's `VIRTUAL | STORED`, SQL Server's computed columns and Oracle's virtual columns.
  Writes to them are refused with each dialect's error and the catalogs show them. A virtual
  column is stored, not computed on read; a SQL Server computed column that is not `PERSISTED` and
  reads a function that changes between reads (`GETDATE()`) is refused with `0A000`. **Files:**
  table definition version 14.
- **More query syntax** (D323, D324). `CREATE TABLE ... AS` in PostgreSQL, MySQL, SQLite and
  Oracle; `VALUES` as a query in MySQL and SQLite; row constructors compared with rows and with
  subqueries (`(a, b) < (1, 2)`, `(a, b) IN (SELECT ...)`), with PostgreSQL's NULL rules; recursive
  `WITH` with `SEARCH` and `CYCLE`; `ON CONFLICT ON CONSTRAINT name` and `ON CONFLICT (...) WHERE
  predicate`; and `COPY ... (ON_ERROR ignore, REJECT_LIMIT n)`, whose limit error is `22P02`.
- **PostgreSQL's privilege questions** (D326). `has_table_privilege` and the other `has_*_privilege`
  functions, `relacl` text, `information_schema.table_privileges`, `column_privileges` and
  `role_table_grants`, `FORCE ROW LEVEL SECURITY` (stored and shown; it takes effect once tables
  have owners), `pg_policy` and `pg_policies`. Every answer comes from the grant model the engine
  enforces. **Files:** `FORCE` is a new bit in the existing row-security record.
- **Subqueries in `EXPLAIN`** (D327). PostgreSQL's `InitPlan` and `SubPlan` nodes, with `loops`
  under `ANALYZE`, and MySQL 8's iterator tree from `EXPLAIN FORMAT=TREE` and `EXPLAIN ANALYZE`
  (a `SELECT` only, as in MySQL 8).
- **Oracle's analytic functions and regular expressions** (D332). The shared window code takes
  `IGNORE NULLS` and `FROM LAST`, and `RATIO_TO_REPORT` and `KEEP` work; Oracle's `REGEXP_*` take
  the first match the pattern finds, as Oracle does, not POSIX's longest.
- **HTTP/1.1 on every HTTP listener** (D325). Connections stay open, requests can be pipelined,
  chunked request bodies are accepted and large responses stream as chunked, under the memory
  budget and with request smuggling refused (an unknown transfer coding alone is `400`, and
  duplicate `Content-Length` values are refused).
- **Syslog** (D315). `eggdb serve --syslog-listen` receives RFC 5424 and RFC 3164 messages over UDP
  and TCP into a `syslog` table you can query (loopback only, 16 KiB per message).
- **Redis bitmaps, HyperLogLog and geo commands** (D330). `SETBIT`, `GETBIT`, `BITCOUNT`,
  `BITPOS`, `BITOP`, `BITFIELD`; `PFADD`, `PFCOUNT`, `PFMERGE`; `GEOADD`, `GEODIST`, `GEOHASH`,
  `GEOPOS`, `GEOSEARCH`, `GEOSEARCHSTORE` and the `GEORADIUS` family, in Redis's own value formats
  and under the memory budget.
- **Elasticsearch-compatible multi and by-query APIs** (D331). `_mget`, `_msearch`,
  `_update_by_query` and `_delete_by_query`, with update scripts in a small Painless subset that
  `_update` and bulk `update` take too. A by-query run is a snapshot processed in `scroll_size`
  batches, and a failed script batch is rolled back whole.
- **More of Cypher** (D333). Named paths, `shortestPath()` and `allShortestPaths()`, `MERGE ... ON
  CREATE SET / ON MATCH SET`, `FOREACH`, `UNION [ALL]` and list and pattern comprehensions; Bolt
  sends paths as PackStream paths.
- **The rest of PromQL's common surface** (D334). Every aggregation (`topk`, `bottomk`,
  `quantile` and the rest), `histogram_quantile`, `label_replace`, `label_join`, `bool`, vector
  matching (`on`, `ignoring`, `group_left`, `group_right`), subqueries, and selectors without a
  metric name. A query is bounded by a samples limit and the memory budget.
- **Agents can store and delete keys** (D328). MCP's new `put` and `del` tools work on the default
  key space and the collections with `eggdb mcp --allow-write`: read-only by default, audited,
  `put` without a confirmation and `del` with one every time. `eggdb serve --mcp-tables` limits
  every session of the MCP endpoint to the listed tables, as `eggdb mcp --tables` does, and
  withdraws the key-value tools there ([mcp.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/mcp.md)).
- **A simulated network that loses connections** (D314). For people testing a server built on the
  platform layer: a connection can be cut one way, gives up after Linux's retransmission timeout,
  and each host has its own latency and bandwidth.
- **The desktop client** (D329; built from source, not in this release's downloads; design in
  [docs/ux/workspace.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/ux/workspace.md) 10.9
  and 10.10):
  - *Editor menu.* A right-click menu with Cut, Copy, Paste, Select all, Run selection, Explain,
    Toggle comment and Format statement. `Format statement` reads the editor's lexer, so it
    formats every dialect and changes no token's bytes except a keyword's case.
  - *Keys of a Redis-compatible server.* A `redis://` connection browses keys with a prefix
    filter, 100 keys a page (`Back` and `Next 100`) and a count; `Show DDL` focuses the DDL box.
    A `redis://` connection with `Use TLS` checked is refused, never sent in the clear.
- **Everything from v0.3.0 still works.** The single crash-safe file and its transactions, the
  ordered key-value store, the Rust API, the `eggdb` command and `eggdb ui`, SQL in the
  PostgreSQL, MySQL, SQL Server, SQLite and Oracle dialects and the PostgreSQL, MySQL and SQL
  Server listeners, restores and `eggdb follow`, export and import, and the MCP server are as the
  [v0.3.0 notes](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/releases/v0.3.0.md) describe
  them; this release adds to them.

## Migrating
Moving to EggDB starts from the dump or script your database already makes (D13); the guide is
[migrate.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/migrate.md).

```sh
pg_dump --dbname=app > app.sql                                # PostgreSQL, plain SQL format
eggdb restore --create app.db app.sql                         # or: pg_dump --dbname=app | eggdb restore --create app.db
mysqldump shop > shop.sql                                     # MySQL or MariaDB
eggdb restore --dialect mysql --create shop.db shop.sql
eggdb restore --dialect sqlserver --create shop.db shop.sql   # an SSMS Generate Scripts or sqlpackage script
eggdb restore --dialect oracle --create hr.db hr_export.sql   # SQL Developer, SQLcl or impdp SQLFILE= output
```

- Every restore ends with a report: what was restored, the known differences, and what was
  skipped and why. A dump that loads its data with `COPY` restores, each table's data in one
  transaction; `pg_dumpall` output restores too, and so do Redis AOF files and `mongodump`
  directories.
- `eggdb follow <file> <source-url>` copies a running PostgreSQL 10 or newer (through logical
  replication) or SQL Server (through change data capture, or change tracking for tables
  without it) into the file and keeps it in step, so you can switch over without downtime. It
  saves its position in the file with each change it applies, so a stopped follow resumes where
  it was, reconnects after a lost connection (`--reconnect-for`), and applies PostgreSQL's
  column changes (D261, D263).
- A SQLite file opens as it is: `eggdb sql app.sqlite` reads it into memory and says that
  changes are not written back.
- Formats without a public specification are refused with the command that turns them into a
  script: `pg_dump`'s custom, directory and tar formats (`pg_restore -f dump.sql`), compressed
  dumps, SQL Server `.bak` and `.trn` backups, BACPAC and DACPAC files, Oracle Data Pump `.dmp`
  and RMAN files, and a database's data directory.
- Upgrading from v0.3.0 needs no conversion: v0.4.0 opens v0.3.0's files as they are, and counts
  each collection's keys once the first time it needs the count. Going back is the one-way part,
  and it is wider than before (see "Compatibility from here on"): a file in which v0.4.0 created
  a collection, or in which `eggdb collection list` or `stats` kept a count for an existing
  one, opens read-only in v0.3.0 and earlier; a table with a generated column is refused by name
  by them, and so is a partitioned table whose key is an expression or whose partitions have
  attached indexes. A tested downgrade path to the previous minor version is still on the
  roadmap.

## Limits
Everything v0.4.0 doesn't do yet, in one list. Each follows the roadmap
([roadmap.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/roadmap.md), "What is left, per
milestone"). What v0.3.0's notes said it did not do yet and is now done: `CREATE TABLE ... AS` in
PostgreSQL, MySQL, SQLite and Oracle, `RESET ALL` and `SET eggdb.dialect` in routines,
`--tables` not filtering the MCP sessions of `eggdb serve` (`--mcp-tables`), the desktop client's
comment and format actions, and browsing the keys of a Redis-compatible server, and generated
columns in SQLAlchemy's failure list (the roadmap drops them from it; the suite's failure count was not re-split).
- **One writer at a time.** Readers run side by side; writers take turns.
- **Speed against SQLite, and a correction.** D7 asks that point `SELECT`s, bulk `INSERT`s and
  joins be at least as fast as SQLite's. D99 and D100 set the condition that they are at most 1.0
  on macOS and Linux, or that a research records why the rest is unavoidable; the decision log
  records no such research, so the condition is still open and has moved to v0.5.0 (D100's note
  of 2026-11-05). It is not a waiver. CI's `compare` job on `main` after this batch measured, as a
  ratio to SQLite's time on Linux and then macOS (committed baseline in parentheses): SQL point
  `SELECT` 1.665 and 2.342 (0.91 and 1.226), bulk `INSERT` 1.237 and 1.313 (0.833 and 0.885), key
  join 1.494 and 1.549 (1.396 and 0.99), `GROUP BY` 1.353 and 1.365 (0.9 and 0.939). These levels
  were already on `main`'s runs of 2026-11-03 and 2026-11-04, before and at v0.3.0, so this batch
  did not cause them; **the v0.3.0 notes understated the point select** (they said 0.91 on Linux
  and about 1.2 on a Mac) and said bulk `INSERT`s and `GROUP BY` were faster than SQLite's, which
  held only for the committed baselines. The baseline lines have not been lowered, and no weekly
  performance pass has run since: it first finds which change moved the point select and bulk
  insert, then takes the join's Linux profiles. The same run has other SQL shapes slower on both
  platforms, for example a correlated `EXISTS` 5.9 and 6.5 times, a view point select 4.4 and 4.7
  times, a `UNION` 3.4 and 3.8 times and an `IN` subquery 1.9 and 1.8 times
  ([benchmarks.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/benchmarks.md), D99, D100).
  MySQL's `ORDER BY ... LIMIT` on a nullable indexed column no longer uses the index: MySQL's NULL
  ordering (D321) means the index's order is not the query's, so the query sorts every row, until
  the weekly pass reads the index's NULL entries first for `ASC` and last for `DESC` (the
  `sql_mysql.order_by_nullable_index_limit` benchmark measures it).
- **Network.** Without TLS, the PostgreSQL, MySQL and SQL Server listeners bind to loopback
  addresses only (`127.0.0.1`, `::1`); other machines connect only over TLS. Every other
  listener of `eggdb serve` (Redis, MongoDB, Elasticsearch, syslog, MCP over HTTP and the rest) is
  loopback only, except the metrics endpoint (`--metrics-listen`). HTTP is HTTP/1.1 only: no
  HTTP/2 or HTTP/3, no `gzip` or `deflate` request bodies, a request without a `Host` header is
  accepted, and only the REST API's rows are streamed (Elasticsearch hits, S3 `GetObject` and
  Prometheus results are built whole). Syslog has no TLS (RFC 5425), no idle limit on TCP
  connections and records no sender address.
- **Memory budget.** Replies that are built whole before they are measured (RESP's `EXEC`, a
  single large value, a Bolt record, an HTTP response body other than a streamed one) still cost
  their size for a moment when refused, and a Bolt result's rows waiting for `PULL` and the
  queues' stored messages are not counted. AMQP 0-9-1 can't tell its own framing from a raw
  binary body that happens to parse as it, so such a body published through STOMP, SQS or AMQP 1.0
  can reach an AMQP 0-9-1 consumer cut or misframed (D307).
- **Users and privileges.** Over PostgreSQL, `CREATE ROLE`, `CREATE USER`, `GRANT` and `REVOKE`
  on tables and their columns work, and the privilege functions and views answer from them; MySQL
  and SQL Server clients log in as the one server user (`--user`). There are no schema, sequence
  or routine privileges, owners, `SET ROLE`, `WITH GRANT OPTION` kept in the grant, `BYPASSRLS` or
  `aclexplode` yet, and so `FORCE ROW LEVEL SECURITY` is stored and shown but changes nothing.
- **PostgreSQL's dialect.** PostgreSQL's `MERGE` (version 15's) is not accepted (Oracle's and SQL
  Server's are). `CREATE TABLE ... AS` takes no options before `AS` (`USING`, `WITH (...)`,
  `WITHOUT OIDS`, `TABLESPACE`), and `TABLE t` and `CREATE TABLE ... LIKE` are not accepted. `SET
  LOCAL` and a routine's `SET` clause are PostgreSQL's dialect only, `set_config` with a PL/pgSQL
  variable as an argument is `0A000` (constants and `$n` parameters work), and a routine's own
  later statements cannot switch `eggdb.dialect`. `ON CONFLICT` cannot infer a partial or
  expression unique index, and there are no exclusion constraints, `DO UPDATE ... WHERE` or
  column-level constraint names there. Read-only transactions take no exported snapshots,
  `FOR UPDATE`, `LOCK TABLE` or `DEFERRABLE`. `IS JSON` on a document nested deeper than 256
  levels gives false. Table columns of types `refcursor` and `refcursor[]` are stored as `text`
  and `text[]`. `regr_*`, `covar_*` and `corr` are not built.
- **Partitions.** There is no `DISABLE ROW MOVEMENT` (rows always move), a moved row fires no
  separate delete and insert triggers, user `IMMUTABLE` functions are refused in keys, MySQL's
  partition-function rules are not applied, and `ALTER COLUMN TYPE` and `ADD COLUMN` on a
  partitioned table change only the table named, not its partitions.
- **Generated columns.** A virtual column is stored, not computed on read. Not built: `ALTER
  COLUMN ... SET EXPRESSION` and `DROP EXPRESSION`, MySQL's `MODIFY` of a generated column,
  generated columns in partition keys and partitioned tables, user-defined functions and
  PostgreSQL's stable casts (such as `timestamptz` to `text`) in a generation expression, SQL
  Server's `sys.computed_columns` rows (the view is empty), and the generation clause in SQLite's
  and Oracle's `CREATE TABLE` text, MySQL's `SHOW CREATE TABLE` and `eggdb dump` in those
  dialects, so a dump written in them does not carry it.
- **Failing statements and savepoints.** A failing statement trigger that runs after its
  statement, SQL Server's doomed transactions and SQLite's constraint-level conflict clauses are
  not handled as the manuals describe, and a MySQL `CALL` undoes the whole call instead of keeping
  its earlier statements. `ROLLBACK TO SAVEPOINT` undoes key-value writes made in `eggdb shell`,
  not those from other front ends inside a SQL transaction.
- **Aggregates and Oracle.** SQLite's and SQL Server's NULL ordering are not reconsidered as
  MySQL's was; Oracle's 38-digit results and `STATS_*` are not built. Oracle's window functions
  have no `DISTINCT` in aggregates and `KEEP` on `LISTAGG`, and `REGEXP_*` knows fewer character
  classes than Oracle. `QUALIFY` is not built: none of the five dialects has it, and each reads
  `FROM t qualify` as a table alias.
- **Joined `UPDATE` and `DELETE`.** The refusals listed in the
  [v0.3.0 notes](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/releases/v0.3.0.md), and SQL
  Server's `OUTPUT deleted.` of a joined `UPDATE` (Msg 40517).
- **Oracle.** There is no Oracle wire protocol, so Oracle's own clients and drivers cannot
  connect; Oracle's SQL runs through `eggdb sql`, `eggdb shell`, `eggdb restore` and the
  embedded API. `CONNECT BY` over a join, `PRIOR` beside a subquery and `ORDER SIBLINGS BY` a
  pseudo-column are `0A000`; `EXPLAIN PLAN` takes a `SELECT`, `UPDATE` or `DELETE` only and gives
  no costs, cardinalities or predicates, and `DBMS_XPLAN.DISPLAY` always uses the `BASIC` shape;
  an `INSERT ALL` advances a sequence for each use, not once per source row.
- **SQL Server.** `SELECT ... INTO` keeps neither the source columns' `NOT NULL` nor their
  identity, and its computed columns get EggDB's types rather than SQL Server's; `OUTPUT ... INTO`
  a target with triggers, checks or foreign keys fires and checks them where SQL Server refuses;
  `SET STATISTICS PROFILE` counts rows for the statement, not each operator; `SHOWPLAN_XML` is
  `not_supported`; a procedure's `#temporary` tables outlive it. SQL Server clients: no MARS and
  no client certificates; a cancel (TDS attention) stops a running batch at once. `sqlcmd` here
  means go-sqlcmd, the one CI runs.
- **SQLite.** `INTEGER` columns are still plain 64-bit integers, not dynamic (SQLite keeps text
  or a real stored in one as it is); a few comparisons that mix a `TEXT` column with a number
  don't convert as SQLite does yet, and `CAST(x AS NUMERIC)` doesn't give integers (D305). Writing
  SQLite's own file format comes later: `eggdb sql app.sqlite` reads a file into memory. SQLite's
  `.scanstats` is not built.
- **Plans.** `EXPLAIN` shows subqueries only in the positions D327 built and only for PostgreSQL
  and MySQL; `EXPLAIN ANALYZE` of MySQL's `UPDATE` and `DELETE` is refused, as in MySQL 8, and
  MySQL's cost estimates and `FORMAT=JSON` are not built.
- **Servers.** Redis: coordinates are bulk strings in RESP3 too, and there is no geohash-range
  search, `SETRANGE` or benchmark against Redis. Elasticsearch: no `wait_for_completion=false`
  tasks, `_rethrottle`, slices or by-query over several indices, and only the Painless subset.
  Cypher: no `CALL {}`, no GQL `SHORTEST k`, no path predicates inside the shortest-path search
  and no byte budget per query. PromQL: no native histograms, `@` or negative offsets, and no
  query timeout. Collection counts are not in the C API or the drivers, and not on the picker's
  rows.
- **SQLAlchemy.** 272 tests of its dialect suite fail (1,180 passed, 99 skipped and 10 errored on
  CI's run after this batch; CI fails below 1,160 passes), among them two identity columns in one
  table, identity `MAXVALUE`/`MINVALUE`/`CYCLE`, zero-column tables, psycopg's named cursors,
  `nextval` of a `SERIAL` column's sequence and materialized views in `pg_class` (D308).
- **GUI tools.** pgAdmin, DBeaver, DataGrip, MySQL Workbench, SQL Server Management Studio and
  Azure Data Studio send catalog queries beyond psql's `\d` family that are not all answered
  yet; they are not tested and may not browse a database. psql's `\d` family, `\d+`, `\dt+`
  and `\df+` included, works.
- **The desktop client.** It is built from source and has no download and no `eggdb gui`
  command. A familiar layout places the regions and sets the labels and shortcuts, but does not
  yet draw each product's own contents (pgAdmin's Query Tool toolbar, DBeaver's run column,
  Compass's filter bar, SSMS's `F4` properties and the rest), and some keys the platform layer
  can't deliver yet (`F7`) are not mapped. Keys of a key space can be browsed on a
  Redis-compatible server but not yet on other servers; there is no `rediss://` (TLS over RESP),
  the full-value view in the keys tab shows a value's first 64 bytes and, for a hash, list, set,
  sorted set or stream, only the cell's text, data can't be edited in the grid, a second tab's
  write while another tab holds the write transaction fails at once with `55P03`, and more than
  400 tabs are refused. The editor's menu is built from groups and buttons, so it has no menu
  roles for screen readers yet. There is no native Wayland window and no IME input. The hand check
  with each screen reader (VoiceOver, Narrator, Orca) is still to come (issue #29).
- **Restore.** The formats in "Migrating" that have no public specification are refused, never
  read. Procedures written in C, Python or Perl, user-defined aggregates and event triggers are
  listed in the report as skipped.
- **AI agents.** `eggdb mcp --allow-write` without `--tables` grants the whole file, and an
  agent's `confirm: true` is its own word, not yours. A `put` asks for no confirmation: with
  `--allow-write` an agent can overwrite any key it can name in the default key space and the
  collections (limit it with `--tables`, or `--mcp-tables` on `eggdb serve`, which withdraw the
  key-value tools). Agents with a stored role have no key writes, `eggdb serve`'s MCP endpoint
  takes no writes, and there is no key allow-list per session. With `--tables`, a foreign key from
  a listed table to an unlisted one lets an agent learn whether a value exists in the unlisted
  table by trying it.
- **Files.** A damaged file is reported, not repaired. A file written by v0.4.0 can't be written
  by v0.3.0 or earlier once it holds a collection with a kept count.
- **Downloads.** The binaries are not code-signed (each archive has a checksum and a signed build
  provenance attestation), and there are no packages on crates.io or other registries yet.
- **Platforms.** `x86_64-apple-darwin` and `aarch64-pc-windows-msvc` are built and packaged but
  not run by CI, and on Windows the smoke test does not run the network clients (see "What was
  tested").

## Correctness
Every commit is atomic, and durable when it returns under `Full`. Damage is detected by
checksums and reported, never served as data, and hostile files, exports and arguments produce
errors, never a crash or a hang. The tests behind each promise run on every change: a crash
sweep that fails every I/O operation of a workload in each durability mode and ends it in a
reopen or a simulated power loss, injected faults in every layer, a model test against Rust's
`BTreeMap`, a fuzzer for hostile files and one for hostile exports, the v0.2.0 sample files that
every later release must keep reading, and a smoke test of every release binary that its build
machine can run (see "What was tested"). This release changes the file format in four places,
each with its own tests (D35). **Partition record version 2** (D316) is written only when a key
has an expression or a partition has attached indexes, so other files keep version 1's bytes:
pinned version 1 and 2 bytes, refusal of a newer version, hostile and mutated bytes, an upgrade
test, and links left stale by an older writer or a dropped index ignored and their ids never
reused. **The count record and the `COLLECTION_COUNTS` feature bit** (D320): a test vector, damaged
and newer records, the format bit's test, the v0.2.0 sample file taking a count and its bit, and
`eggdb check` verifying every kept count. **Table definition version 14** (D322): a pinned version
14 record, a pinned record without generated columns (older bytes unchanged), every truncation, a
byte-flip loop, and older readers refusing it by name. **The `FORCE` bit** in the row-security
record (D326) is a new bit in the existing record, not a new version, so an older release keeps
applying row security. The committed sample files are untouched. The SQL dialects are checked
against their manuals' examples: over 1,000 cases for PostgreSQL, over 480 for SQL Server, over
290 for MySQL, over 290 for SQLite and 773 for Oracle
([correctness.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/correctness.md)). What is
**not** tested is stated as plainly: no real power loss on hardware, no external audit, one writer
only, and the platforms CI doesn't run. The full statement is in the same page.

## Compatibility from here on
- **Files:** every later release reads the files this one writes (D20). The file format is still
  version 1. This release adds four things, each written only when it is needed; every other
  table, view and record keeps the version and bytes it had.
  - *Partition record version 2* (D316), for a partitioned table whose key has an expression or
    whose partitions have indexes attached to the parent's: a release that doesn't know it
    reports it as written by a newer format instead of misreading it (v0.3.0 and v0.2.0 do).
  - *The count record and the read-only-compatible feature bit `COLLECTION_COUNTS`* (D320), set
    by the first commit that writes a collection's count, which every new collection has, and by
    `eggdb collection list` or `stats` on an older file that has collections. A release before
    D320 opens such a file for reading only and refuses to write to it, because it would change
    keys without their count. The bit stays set.
  - *Table definition version 14* (D322), for tables with generated columns: a release that
    doesn't know it, v0.3.0 included, refuses the table by name with `0A000` and says the table
    definition was written in format version 14, which that EggDB cannot read.
  - *The `FORCE` flag* (D326), bit 2 of the row-security record: older releases keep applying
    row security from bit 1.

  The two files written by v0.2.0 and the v0.2.0 export stay in the repository, and CI opens,
  reads, checks, replays and writes to them on every change (D96); no sample file is added for
  v0.4.0.
- **Exports:** eggdb-jsonl version 1 stays importable.
- **The command's output:** the JSON fields and the exit codes in [cli.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/cli.md) are stable.
  `eggdb collection list` gains a `counts` field in its JSON (`collections` is unchanged) and
  prints each collection's entry count in its text form; `eggdb check` exits 4 for a kept count
  that is damaged or differs from the collection's keys.
- **The Rust API** is pre-1.0: it may change between minor releases, and each change is listed
  in the release notes.

**API changes since v0.3.0:** additions only; no existing item was removed or changed.
- `eggdb::DropProgress` and `Database::drop_collection_with_progress`, which reports the entries
  removed after each commit of a long drop; `Database::has_uncounted_collections`.
- `eggdb::sql::SharedWriteStore::with_open_transaction_undoable`, which records a key-value write
  in a SQL session's savepoint undo log, so `ROLLBACK TO SAVEPOINT` undoes it.
- `eggdb_sql::regex_captures`, next to `regex_matches_with_flags`.
- `Database::check` also compares every collection's kept count with its keys, and
  `CollectionStats` comes from the kept count.

## Size and speed
CI measures the stripped release `eggdb` binary on every change (D6, `scripts/footprint.sh`
against `benchmarks/footprint.txt`), here from the run on `main` after this batch (commit
8ddfe99):

| | macOS (Apple silicon) | Linux (x86-64) |
|-|-----------------------|----------------|
| `eggdb` binary, v0.4.0 | 13,545,848 bytes | 17,629,736 bytes |
| `eggdb` binary, v0.3.0 | 12,652,424 bytes | 16,450,960 bytes |
| Growth | 893,424 bytes (7.1%) | 1,178,776 bytes (7.2%) |
| C API library, v0.4.0 | 8,333,552 bytes | 10,626,456 bytes |
| C API library, v0.3.0 | 7,837,312 bytes | 9,989,904 bytes |
| C API library growth | 496,240 bytes (6.3%) | 636,552 bytes (6.4%) |

The growth is the batch's features (partitions, generated columns, statement-level rollback,
read-only transactions, the privilege functions, subplans in `EXPLAIN`, the new Redis,
Elasticsearch, Cypher and PromQL surfaces, syslog, HTTP keep-alive and collection counts), each
with its reason recorded when the budgets were raised to these sizes plus about 1% (D6,
[benchmarks.md](https://github.com/eggspot/EggDB/blob/v0.4.0/docs/benchmarks.md)). The window code
of the desktop client is linked only into `eggdb-gui`, not into `eggdb` or the C API library. The
exact size of every download is in the release's "Sizes" table. Start time and the peak memory of
`eggdb --version` and `eggdb get` are measured by CI's `bench` job against
`benchmarks/baseline.txt` on every change; the figures in benchmarks.md were last measured on
2026-10-27, so this release gives none of its own. Speed against SQLite is in "Limits", with the
correction to v0.3.0's notes. The same CI run measured the key-value paths against SQLite's time
on Linux and macOS: point gets 0.91 and 0.90, scans 0.79 and 0.73, and batched random overwrites
0.59 and 0.71, all faster than SQLite's; through SQL, the point select, bulk insert, join and `GROUP
BY` are slower (D7, D94, D99, D100, D101).

## Downloads
One self-contained file per platform, with the licenses and the README:
- Linux: `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` are static and run on any
  distribution; the `-linux-gnu` builds link glibc 2.35 or newer.
- macOS: `aarch64-apple-darwin` (Apple silicon) and `x86_64-apple-darwin` (Intel).
- Windows: `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`.

Next to them: the C API (`eggdb-capi-<version>-<target>`: header, libraries and the Python
binding) for the two Linux `-gnu` targets, both macOS targets and both Windows targets; a
`SHA256SUMS` file; a signed build provenance attestation for every archive
(`gh attestation verify <archive> -R eggspot/EggDB`); and the container image
`ghcr.io/eggspot/eggdb:0.4.0` (and `:latest`) for `linux/amd64` and `linux/arm64`, built from the
static binaries. The desktop client (`eggdb-gui`) is not in the downloads: the release workflow
builds only the `eggdb` binary and the C API, so the client is built from source (`cargo run
--release -p eggdb-gui`).

The binaries are not signed. On macOS, a file downloaded with a browser is quarantined: run
`xattr -d com.apple.quarantine eggdb` once (`curl` and the install script don't set the
quarantine). On Windows, unzip the archive and add its folder to your PATH, so that `eggdb`
works in any terminal and in `claude mcp add mydb -- eggdb mcp app.db`; SmartScreen may ask
once before the first run.

  changes only Markdown runs `lint-and-test` and skips the other jobs, and `unix-vms` and
  `other-cpus` run on `main` only:
