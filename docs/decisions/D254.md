## D254 Login slots go to the newest connection, logins get 5 seconds, idle sessions end after an hour, and the SQL servers share caps and one memory budget — Decided by research (2026-11-02); refines D22, D103, D106, D122

Issue #79 showed that any program on the same machine could lock users out of `eggdb serve`
without a password, by holding the 16 login slots with idle sockets and reconnecting every 30
seconds, and that one logged-in PostgreSQL client could grow the server without bound with
`Parse` messages. The PostgreSQL, MySQL and TDS servers now share one set of limits, in
`eggdb_platform::connection_limits`:

- **Login slots.** At most 16 connections log in at once (`MAX_LOGINS_IN_PROGRESS`). When all
  are taken, a new connection takes the slot of the oldest login that has waited at least one
  second (`LOGIN_EVICTION_AGE`), and that one is dropped. Only when every login is younger is the
  new connection refused, with each protocol's own error (PostgreSQL `53300`, MySQL 1040, SQL
  Server 17809). The age keeps a burst of real logins, such as a connection pool starting, from
  dropping its own logins half way. A login takes milliseconds on loopback, so to keep a real
  user out an attacker has to open 16 connections every second, not just hold 16 idle sockets.
- **Per peer.** A peer on another machine (only possible over TLS, D161) holds at most 8 of the
  16 slots, and when it is at its share a new connection of its own takes its oldest slot, never
  another peer's. An IPv6 address counts by its `/64` network, since one host usually holds a
  whole `/64`. Connections from this machine (loopback, Unix sockets) share all 16: they all have
  the same address, so a per-peer limit would only lower the total.
- **Authentication timeout: 5 seconds** instead of 30, as the issue asked. psql and drivers ask
  for the password before they connect, so no human typing happens inside it.
- **Idle timeout: one hour by default** (`--idle-timeout <seconds>`, `0` for none), counted
  between messages from a logged-in client, so a long query or `COPY` never trips it. PostgreSQL
  ends the session with `FATAL 57P05 idle_session_timeout`, as PostgreSQL 14's
  `idle_session_timeout` does; MySQL sends error 4031 (`ER_CLIENT_INTERACTION_TIMEOUT`, MySQL's
  `wait_timeout`); TDS closes the connection, since SQL Server has no such message.
- **PostgreSQL caps per connection**, matching the MySQL server's model: 4,096 prepared
  statements, 4,096 portals and 1 GiB (the largest message) of their text and bound parameters.
  One more is refused with `54000 program_limit_exceeded` and the connection goes on. The TDS
  server already caps `sp_prepare` handles (65,536 and 64 MiB per connection) and keeps that.
- **One memory budget for the process: 4 GiB** (`DEFAULT_MEMORY_BUDGET_BYTES`; all of memory on
  32-bit machines), passed as the same `Arc<MemoryBudget>` to every SQL server of `eggdb serve`.
  Each message over 64 KiB holds its size against it while it is read and handled, and
  PostgreSQL's prepared statements and portals hold theirs for as long as they live. A message
  that does not fit ends its connection (`53200`, MySQL 1041, SQL Server 701), since its body is
  never read; a `Parse` or `Bind` that does not fit fails with `53200` and the connection goes on.
  4 GiB lets one client send a full 1 GiB value and bind it, while 64 connections can no longer
  hold 64 GiB between them.

The limits live in the platform crate rather than a new crate because the three servers already
depend on it and the code is small; the shared listener crate of D122 can move them later.

Left: rows a suspended portal has already materialized are not counted against the budget; the
other protocol servers (RESP, MongoDB, CQL and the rest) do not use the shared limits yet; and
the budget's size is not a command-line option yet.

**Refined (2026-11-02, security review round 1 of the batch).** Two weaknesses remained:

- *Logins held `--max-connections` slots.* Each accepted connection took one of the
  `--max-connections` slots before its login slot, and a refused login waited up to two seconds
  for its startup packet, so about 40 idle sockets a second filled all 64. Now the accept loop
  takes the login slot first, and a connection takes a `--max-connections` slot only once it has
  logged in; `--max-connections` counts logged-in connections and the 16 login slots count the
  rest. A connection is refused at once, before any login slot, when the logged-in connections
  are already at the limit, and after its login when another took the last slot meanwhile. A
  refused connection is answered by one of eight refusal threads, which waits at most 250 ms
  for the startup packet (PostgreSQL, TDS) before it answers and closes; with no refusal thread
  free it is closed at once.
- *Large messages kept their budget while the connection idled.* The reservation of a message
  over 64 KiB was given back only when the next message arrived; each server now gives it back
  once the message is handled, before it waits for the next one.
