## D1012 Learned graph embeddings: node2vec — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D31, D55, D248)

- `CALL eggdb.node2vec(dimension, walkLength, walksPerNode, windowSize, epochs, returnFactor, inOutFactor)` yields
  `nodeId` and `embedding` (a list of floats, normalized to length 1), from Bolt, Cypher, Gremlin's procedures and
  SQL/PGQ's `GRAPH_TABLE (g CALL node2vec(...))` (D1008). Defaults: 64 dimensions, walks of 20 steps, 10 walks per
  node, a window of 5, one epoch, both factors 1.
- The method is node2vec (Grover and Leskovec, 2016), written from the paper: second-order random walks biased by
  the return factor `p` and the in-out factor `q` (with both at 1 it is DeepWalk), then a skip-gram model with
  negative sampling (Mikolov and others, 2013: five negatives drawn by count to the power 0.75, a learning rate
  falling linearly from 0.025, a random window up to `windowSize`) trained by stochastic gradient descent. Unlike
  FastRP (D436), the vectors are learned from the walks, so nodes that share neighbourhoods end close together.
- Every random choice is seeded from node ids and the walk round, so the same graph gives the same embeddings, as
  every other EggDB algorithm does. Training that would make more than four billion vector updates is refused with
  a message naming the arguments to lower, so one call cannot hold the server for hours.
- GraphSAGE and other neural message-passing models stay out: they need feature tensors and a training loop the
  in-database model layer (D31) would host.
