## D517 MQTT over WebSockets — Decided by the code-only session (2026-11-11, D355); roadmap M16

Browser MQTT clients (MQTT.js, Paho's JavaScript client) speak MQTT inside WebSocket binary
frames. `--mqtt-listen` now takes them on the same port instead of a second listener: an MQTT
connection starts with a `CONNECT` byte (`0x10`), an HTTP request with `G`, so the first byte
chooses, and a client that sends nothing within ten seconds is dropped.

- **Handshake (RFC 6455):** a `GET` with `Upgrade: websocket` and `Sec-WebSocket-Key` gets
  `101 Switching Protocols` with the `Sec-WebSocket-Accept` hash, and `Sec-WebSocket-Protocol`
  set to the first of `mqtt` or `mqttv3.1` the client offered; anything else gets `400`. The
  request path is not checked (clients use `/mqtt` by convention). The handshake is limited to
  8 KiB and ten seconds.
- **Frames:** client frames must be masked (RFC 6455 5.1); binary and continuation payloads feed
  the MQTT reader as one byte stream, so an MQTT packet may span frames and a frame may hold
  several packets; pings are answered with pongs, a close frame is echoed and ends the session,
  text frames end it as a protocol error, and frames over 32 MiB are refused. Every packet the
  broker writes goes out as one binary frame, and frames from the broker and pongs share one
  lock so they never interleave.
- **Authentication and limits** are MQTT's own, unchanged: the `CONNECT` user and password, the
  connection limit and the memory budget.
- **Left out:** TLS (`wss://`) with the rest of the listener's TLS, permessage-deflate, and
  `Origin` checks, which matter once the listener leaves loopback.

**Status:** code written, unbuilt (code-only mode, D355).
