## D135 .NET apps on PostgreSQL's protocol through Npgsql: implicit transactions per `Query` message and per pipeline up to `Sync`, portals that end with their transaction, `DISCARD`, cancellation by a per-session signal registered under the backend key, and the catalog rows Npgsql's type loading reads — Decided by the build loop (by research, 2026-10-29); roadmap item 45, applies D1, D5, D9, D12, D102, D103, D104, D129, D131

Item 45 makes Npgsql, the .NET driver for PostgreSQL, run apps against `eggdb serve`. Npgsql
loads the server's types with one multi-statement `Query` when a data source first connects,
sends every command through the extended protocol with one `Sync` per command or per
`NpgsqlBatch`, resets a pooled connection with `DISCARD ALL` before reusing it, and cancels a
command with a `CancelRequest` on a new connection. Everything is written from PostgreSQL's
public protocol documentation ("Message Flow": "Multiple Statements in a Simple Query",
"Pipelining", "Canceling Requests in Progress") and the `DISCARD`, `pg_proc`, `pg_range` and
`pg_sleep` pages of its manual; Npgsql's own sources (PostgreSQL License) were consulted only to
see which queries and messages it sends, never copied.

**An implicit transaction is the session's, opened lazily by the first write.** `eggdb-sql`'s
`Session` gains `start_implicit_transaction`, `commit_implicit_transaction` and
`roll_back_implicit_transaction`. While one is started, a statement outside a `BEGIN` block that
writes keeps the store's write transaction open instead of committing, marked as implicit;
reading statements still read committed data (or the open write transaction's own changes), so
a pipeline that only reads never takes the one writer and never makes another connection wait.
A `BEGIN` among the statements turns an open implicit transaction into a block that includes
what came before, as PostgreSQL does; `COMMIT` or `ROLLBACK` ends it with PostgreSQL's warning
"there is no transaction in progress" and the next statement starts another. The session reports
itself idle in an implicit transaction (`transaction_status`, `in_block`), since it is not a
block a client opened. The alternative, a block opened by the server before every pipeline, was
rejected: it would take the store's single writer for every read-only command and serialize all
connections.

**The PostgreSQL server ends the implicit transaction where PostgreSQL does.** A `Query` message
starts one and ends it after its last statement: committed when every statement succeeded, else
rolled back, so `INSERT ...; INSERT ...; SELECT 1/0` leaves nothing. Every extended-protocol
message (`Parse`, `Bind`, `Describe`, `Execute`) starts one if none is started, and `Sync` ends
it: committed when no message failed since the last `Sync`, rolled back otherwise, so an
`NpgsqlBatch` whose second command fails leaves nothing of the first. A commit that fails is
reported as an error before `ReadyForQuery`. A failed function-call message rolls back too. Other
front ends (`eggdb sql`, restores, MCP, TDS, MySQL) never start one and keep their behavior.

**Portals end with their transaction.** After a `Sync` or a `Query` leaves the session idle,
every portal is closed, as PostgreSQL drops a transaction's portals at its end; inside a block a
suspended portal lives on to the block's end. Prepared statements live until `Close` or
`DISCARD ALL`.

**`DISCARD` is a statement of the PostgreSQL dialect.** `DISCARD ALL` (refused with `25001`
inside a block) returns every run-time parameter to the values the client sent when it
connected, forgets the session's sequence values, and makes the server forget the connection's
prepared statements and portals; `DISCARD PLANS` and `DISCARD TEMP` change nothing, since EggDB
caches no plans and has no temporary tables yet; `DISCARD SEQUENCES` forgets `currval` and
`lastval`. `RESET name` and `RESET ALL` also return to the values sent when connecting
(`Session::remember_connection_settings`, called by the server after the startup parameters are
applied) instead of the server's defaults, as PostgreSQL does, so a pooled Npgsql connection
keeps the `Search Path` or `Options` of its connection string after its reset.

**Cancellation is a signal per session, registered under the backend key.** `eggdb-sql` gains
the public `CancelSignal` (a shared atomic flag) and `Session::cancel_signal`. Each statement
enters the session's signal into a thread-local for its duration, and the engine checks it at
every row it scans (`for_each_matching_row`) and every row it charges to its working memory
(joins, sorts, groups, results, generated rows), and every ten milliseconds in `pg_sleep`; a
raised signal fails the statement with `57014` "canceling statement due to user request", which
rolls back what the statement wrote like any error. The server draws a 4-byte secret key from the
platform's secure random source for every authenticated connection, sends it in
`BackendKeyData`, and registers the connection's signal under its process ID and key in a table
shared by the server's connections (`eggdb-pgwire`'s `BackendKeys`), removed when the connection
ends; a connection whose key could not be drawn is not registered, so a zero key never cancels
anything. A `CancelRequest` (read before authentication, as PostgreSQL requires) raises the
signal only when the process ID is registered and the key matches, compared without an early
exit, then the server closes the request's connection without an answer; a request that matches
nothing is logged and changes nothing. The connection lowers its signal when a new request
starts after `ReadyForQuery`, so a cancel that arrives while the connection is idle is dropped,
as PostgreSQL drops it, while one that arrives between the messages of a pipeline stops the next
statement. The check is a thread-local read and a relaxed atomic load per row, which the `bench` job's
scan, join and sort lines measure.

**`pg_sleep(seconds)` is a function of the PostgreSQL dialect.** It sleeps in ten-millisecond
slices, checking the cancel signal between them, and returns an empty text value (PostgreSQL's
`void`, which EggDB has no type for: a client that reads the column's type sees `text`).

**Npgsql's type loading reads `pg_proc` and `pg_range`.** Npgsql finds array types by joining
`pg_type.typreceive` to `pg_proc` and comparing `proname` with `array_recv`, and joins `pg_range`
for range and multirange types. `pg_proc` is a new catalog relation (PostgreSQL's columns) whose
rows are the functions the catalog names: `array_in`, `array_out`, `array_recv` and `array_send`
with PostgreSQL's OIDs; array types now name all four as their input, output, receive and send
functions. `pg_range` is a new, empty relation, since EggDB has no range types yet. Npgsql's
queries are kept as a fixture (`crates/eggdb/tests/data/npgsql/load-types.sql`) that a unit test
and a socket test run.

**Checked by the real driver.** CI's `pg-apps` job runs a C# program
(`crates/eggdb/tests/clients/dotnet/NpgsqlAppCheck`, Npgsql 8.0.5 restored from NuGet, never
shipped) against the `postgres:17` container and against `eggdb serve`, and fails unless both
print the same bytes: type loading, CRUD with typed parameters over pooled connections (each
reuse sends `DISCARD ALL`), `int[]` values, a rolled-back and a committed transaction, a batch,
a batch whose second command fails and leaves nothing, and `SELECT pg_sleep(30)` cancelled with
`NpgsqlCommand.Cancel()` after one second.

Known differences, documented in `docs/sql.md`: Npgsql's reset of a connection that holds
prepared statements (`SET SESSION AUTHORIZATION DEFAULT`, `CLOSE ALL`, `UNLISTEN *`,
`pg_advisory_unlock_all()`) is not supported yet, so apps that call `NpgsqlCommand.Prepare()` or
turn on automatic preparation need `No Reset On Close=true` for now; array parameters are not
supported yet (array results are); `pg_sleep`'s result type is `text`; a server stop still waits
for a running statement to end.
