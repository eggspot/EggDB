## D566 MongoDB multi-document transactions on a one-member replica set — Decided by the code-only session (2026-11-11, D355); roadmap M9, D197

Drivers start a transaction only on a replica set member or `mongos`, and Prisma's MongoDB
connector needs a replica set for every write, so EggDB's MongoDB listener could not serve them.

- **The handshake.** `eggdb serve --mongo-replica-set <name>` makes the listener a replica set of
  one: `hello` adds `setName`, `setVersion`, `secondary: false`, and `hosts`, `primary` and `me`
  naming the address the client connected to. Without the flag nothing changes, and a
  `startTransaction` is refused with `IllegalOperation` (20) as a standalone `mongod` does.
- **Staged writes.** `startTransaction` with a `txnNumber` and `autocommit: false` opens a
  transaction on the connection. Each command with that `lsid` and `txnNumber` runs against an
  `eggdb_keyspace::Overlay`: a keyspace that stages puts and deletes over the store's keyspace
  and reads them back on top of the committed keys, so the transaction reads its own writes and
  nobody else sees them. `commitTransaction` writes every staged change in one write transaction;
  `abortTransaction` (or a new `startTransaction`, or the connection closing) drops them. A retried
  `commitTransaction` of the transaction just committed answers ok; any other unknown number is
  `NoSuchTransaction` (251) with the `TransientTransactionError` label, so drivers retry.
- **Limits.** Reads inside a transaction see the latest committed keys, not a snapshot taken at
  its start, and two transactions writing the same document are not detected as a write
  conflict: the later commit wins. A transaction belongs to the connection it started on, and a
  cursor opened inside one does not outlive its command. `txnNumber`, `autocommit` and
  `startTransaction` are taken off every command before it runs, so retryable writes on the
  replica set run once as ordinary writes. Change streams are not built.
