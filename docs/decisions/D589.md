## D589 Kafka static membership — Decided by the code-only session (2026-11-12, D355); roadmap M16, D33, D213, D525

Consumers with `group.instance.id` (Kafka Streams and stateful consumers on Kubernetes) restart without
a rebalance: the broker remembers the instance and hands its new member id the old assignment. The Java
client refuses `group.instance.id` against a broker whose JoinGroup is older than v5 or whose
OffsetCommit is older than v7.

- JoinGroup goes to v5, SyncGroup and Heartbeat to v3, LeaveGroup to v3 and OffsetCommit to v7. All of
  them are the non-flexible encodings; the flexible ones stay with the flexible-versions item.
- A group keeps a map from instance id to member id. A member that joins with an instance id gets a
  member id made from it. When a known instance joins again with no member id while the group is
  stable and its protocols are unchanged, the old member is replaced by the new id in place: same
  generation, same assignment, the leader moved if it was the leader, and no rebalance. If the group is
  rebalancing or the protocols changed, the old member is dropped and the join goes through a normal
  rebalance.
- A member id that does not match the instance's current one gets `FENCED_INSTANCE_ID` (82) from
  JoinGroup, SyncGroup, Heartbeat, OffsetCommit and LeaveGroup.
- LeaveGroup v3 takes a list of members, each by member id or instance id, and answers each one.
  Static members still expire after their session timeout, which removes the instance and rebalances.
- JoinGroup v5 lists each member's instance id to the leader.
- OffsetCommit v5 and later drop the retention time, and v6 and later carry the leader epoch per
  partition, which is read and ignored.

Not done: `MEMBER_ID_REQUIRED` for v4+ dynamic members (the broker may skip it and clients accept the
first answer), the instance id in DescribeGroups v4, and the new rebalance protocol (KIP-848).
