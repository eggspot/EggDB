## D108 The Oracle dialect: names that swap case on the shared catalog, the empty string as NULL, `ROWNUM` as a source-row limit, implicit transactions, `ORA-` errors; no Oracle wire protocol — Decided by the build loop (2026-10-27); roadmap item 25, applies D1, D5, D9, D10, D16, D19

**The dialect.** `Dialect::Oracle` (`--dialect oracle`) reads Oracle Database's SQL as Oracle's
SQL Language Reference (23ai) documents it, never Oracle's software (D1). It is a fourth branch
of the same lexer, parser and session as PostgreSQL's (D98), MySQL's (D106) and SQLite's (D107),
on the same tables: `--` and `/* */` comments, `'...'`, `N'...'` and `q'[...]'` strings,
`"..."` identifiers, `:name` and `:1` bind variables numbered by first appearance, `!=`, `^=`
and `~=` for `<>`, Oracle's reserved words, and identifiers longer than the engine's 63 bytes
refused with `ORA-00972` rather than cut. There is no Oracle wire protocol (D10): the dialect
runs through `eggdb sql`, `eggdb shell` and the embedded API.

**Names (decided by judgement).** Oracle folds unquoted names to upper case, the other dialects
to lower case, and all four share one catalog. The least invasive correct mapping is an
involution applied where Oracle names meet the catalog: a quoted Oracle name whose letters are
all upper case is kept in lower case, one whose letters are all lower case is kept in upper
case, and a mixed-case name is kept as written. Unquoted Oracle words fold to lower case like
the other dialects' words. Result column names, dictionary views, `.schema` and errors apply
the same swap on the way out. So `CREATE TABLE emp` in Oracle and `CREATE TABLE emp` in
PostgreSQL make the same table, shown as `EMP` in Oracle and `emp` in PostgreSQL; `"Emp"` is
`"Emp"` in both; `"emp"` in Oracle is a different table from `EMP`, as in Oracle, and is `"EMP"`
in PostgreSQL. No catalog or file-format change is needed. Alternatives rejected: storing
Oracle names in upper case (every table made in another dialect would need quotes in Oracle),
and folding Oracle names to lower case without the swap (`"emp"` and `EMP` would collide).

**The empty string.** The parser turns `''` into NULL in Oracle's dialect, so inserts, updates
and comparisons see NULL; Oracle's functions return NULL instead of an empty result, and `||`
and `CONCAT` treat NULL as empty. The literal-rows fast path is off in Oracle's dialect so every
insert goes through this rule.

**Types (decided by judgement).** The engine has no exact decimal yet, so `NUMBER(p)` and
`NUMBER(p,0)` map to the smallest integer type that holds p digits (`smallint` to 4, `integer`
to 9, `bigint` to 18), and `NUMBER` without precision, `NUMBER(p,s)` with a scale, `FLOAT` and
`BINARY_DOUBLE` to `double precision`; `INTEGER`, `INT` and `SMALLINT` are Oracle's
`NUMBER(38)`, so `bigint`. `VARCHAR2`, `NVARCHAR2` and `CHAR` map to `varchar(n)` (characters,
no padding), `CLOB` and `LONG` to `text`. `/` divides exactly when the quotient is whole and in
floating point otherwise, so `7/2` is `3.5` as in Oracle. Identity columns use the
auto-numbering of D106 and must be the first column of the primary key. `DATE` and `TIMESTAMP`
wait for item 19d. Numbers print as Oracle converts them to text (`.5`).

**`ROWNUM`.** Oracle numbers rows as they pass `WHERE`, before grouping and sorting.
`ROWNUM <= n`, `< n`, `= 1`, `> 0` and their mirrored forms, as `AND`ed conditions of `WHERE`
with integer constants, become a source-row limit on the select (`Select::source_row_limit`):
the executor stops reading after n rows pass the rest of the filter, before `GROUP BY` and
`ORDER BY`, which is Oracle's documented meaning (and `ROWNUM > 1` or `= 2` find nothing). The rows kept
for the limit are charged to the statement's work memory like sorted and grouped rows.
`ROWNUM` anywhere else is refused as not supported rather than answered differently.

**Transactions.** `Session::autocommit` is false in Oracle's dialect: the first change starts a
transaction that stays open until `COMMIT` or `ROLLBACK`, and `CREATE TABLE`, `DROP TABLE` and
`TRUNCATE TABLE` commit before and after themselves. `BEGIN` is PL/SQL's and refused. As in
MySQL's dialect, a failing statement that wrote nothing keeps the transaction, and one that
already wrote rolls it back (no statement savepoints yet; listed in docs/sql.md). `eggdb sql`
and `eggdb shell` commit an open transaction when they end, as SQL*Plus does on exit
(`EXITCOMMIT`), which keeps `eggdb sql`'s promise that statements before a failure stay
committed; the embedded API's `close` rolls back as before, so programs commit explicitly.

**Functions and leakage.** Oracle's functions are a separate expression kind
(`ExprKind::OracleFunction`) that only the Oracle parser creates, as D107 did for SQLite: the
other dialects cannot reach them, and the Oracle parser answers `ORA-00904` for any function
outside Oracle's list, so PostgreSQL's (`char_length`, `version`) do not leak in. `DECODE`
is evaluated by the executor, its first argument once and its results lazily, so its size stays
linear in the query, with Oracle's 255-argument limit. `LPAD`, `RPAD`, `REPLACE`, `||`, `UPPER`,
`LOWER` and `INITCAP` check the size of their result against the same 1,000,000,000-byte
limit as SQLite's functions before they allocate (D9), with `ORA-01489`.

**Errors.** A translation from the engine's SQLSTATE errors to Oracle's numbers and wording,
shown as `ORA-00942: table or view does not exist`; `SqlError::with_oracle_code` and
`SqlError::vendor` tell callers which numbering applies. Errors without an Oracle counterpart
keep the PostgreSQL wording; features EggDB lacks are `ORA-03001: unimplemented feature: ...`.

**Sequences (not in this item).** `CREATE SEQUENCE`, `NEXTVAL` and `CURRVAL` need a counter kept
in the file and advanced outside the transaction that reads it; that is a catalog entry kind of
its own with format tests (D35, D96), and comes as its own item. Until then they are refused
with `ORA-03001`, as are `MERGE`, set operators and `LISTAGG`.
