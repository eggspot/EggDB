## D112 Subqueries, WITH queries and set operations as intermediate tables of the statement, correlated subqueries per distinct outer value — Decided by the build loop (by judgement, 2026-10-27); applies D1, D2, D9, D10, D109, D111

Item 30 adds scalar, `IN`, `EXISTS` and `ANY`/`ALL` subqueries, derived tables, `WITH` and
`WITH RECURSIVE`, `UNION`/`INTERSECT`/`EXCEPT` with their `ALL` forms, and `RIGHT` and `FULL`
joins, in all four dialects.

**Intermediate results are tables of the statement.** A derived table, a `WITH` query and each
step of a recursive one are run to completion and their rows written, encoded as stored rows, to
an in-memory map of the statement under table ids counted down from the top of the id space
and names no user can type. A read view lays that map over the store, so the existing planner,
joins, grouping and sorting read an intermediate table exactly as a stored one, and it
disappears with the statement. The table's definition is never encoded: it is kept in a
registry of the thread's intermediate tables, by its name, while the statement holds the table,
so no decoder that reports damage ever reads it. Output columns of one name keep it for display
and get unique internal names (the name, the marker character and the position), so `*` shows
both and naming one is ambiguous (`42702`); MySQL refuses such a derived table (1060) and Oracle
(`ORA-00918`), as their manuals say. The rows are converted to the column's type once, so the
encoding's type check holds. Reading them back costs a decode, which is the price of one
execution path; a streamed operator tree replaces this when the planner gets one.

**Uncorrelated subqueries run once.** Before a `SELECT` runs, every subquery in it is
prepared: column names that do not resolve inside the subquery but do in the query directly
around it become outer references. A subquery without any runs once (with `LIMIT 1` added for
`EXISTS` and `LIMIT 2` for a scalar subquery, which needs to know only whether there is a second
row), and the expression keeps its result: one value, or the column's values with a hash set of
their equality keys built on first use when there are eight or more and all share one family of
types whose equality keys agree with `=` (integers and `numeric`, floats, text, booleans, dates
and time stamps, `timestamptz`, `jsonb`); any other mix is compared value by value with `=`, so
the hash never disagrees with the comparison (D111's `numeric` against `double precision`).

**Correlated subqueries run per distinct outer value.** A correlated subquery is kept as a
template; for each outer row its outer references are replaced by the row's values and the
subquery runs through the ordinary path, so `WHERE inner.k = <value>` uses the primary key or an
index (item 19c) like any constant condition. Results are remembered by the encoded outer values
(up to 32 MiB, then forgotten and rebuilt), so a subquery runs once per distinct outer value.
The common case is decorrelated: an `EXISTS` (or `NOT EXISTS`) whose subquery is a plain
`SELECT` without grouping, aggregates or `OFFSET`, and whose outer references appear only in
`WHERE` conjuncts of the form `inner_expression = outer_column`, runs once without those
conjuncts as `SELECT DISTINCT inner_expression, ...`, and each outer row then probes a hash set of
the keys (a semi- or anti-join by lookup): a NULL outer value finds nothing, as `=` does, and an
outer value of another family of types than the keys falls back to the per-value run, so the
hash never decides what `=` would not. The other conjuncts are then evaluated on every inner
row once, where a per-value run might have skipped some, so a conjunct that fails on a row no
outer value matches (`1/0`) can fail the statement; PostgreSQL promises no order of evaluation
either. Rewriting `IN`, scalar aggregates and the rest into joins is left for the planner work of
item 19e: the per-value run is exact in three-valued logic by construction (it is the same
evaluation as the uncorrelated case), it already reads by key, and a rewrite must special-case
NULLs (`NOT IN` against a NULL), cardinality errors and dialect rules that the substitution gets
for free. An aggregate whose argument names only outer columns belongs to the outer query in
PostgreSQL and SQLite; that is refused with `0A000` rather than computed in the wrong query.
The work of a correlated subquery grows with the number of distinct outer values, with no
statement timeout yet; IN and scalar-aggregate decorrelation are on item 19e's list. Outer
references reach one level out only (farther ones are `0A000`), and correlated subqueries stand in the
select list, `WHERE` and `ORDER BY` (only `WHERE` in grouped queries): conditions with them are
evaluated after the rest of `WHERE` has filtered the rows, so they never block index use.

**Set operations** run each operand, then give every column one type by PostgreSQL's `UNION`
rules (integers widen to `bigint`, `numeric`, `real`, `double precision`; text types to `text`;
`date`, `timestamp`, `timestamptz` in that order; a string constant or NULL takes the other side's
type), convert the values, and combine them by hashing whole rows' equality keys, so duplicates
agree with `DISTINCT`: `UNION` keeps first occurrences, `INTERSECT ALL` keeps min(m, n) copies,
`EXCEPT ALL` max(m - n, 0). MySQL turns a type mismatch into strings, SQLite compares values as
they are, Oracle answers `ORA-01790`. `INTERSECT` binds tighter in PostgreSQL and MySQL; SQLite
and Oracle (which spells `EXCEPT` as `MINUS` too) evaluate left to right. A chain of operations is
evaluated along its left spine without recursion.

**`RIGHT` and `FULL` joins** keep the right table's rows in memory with a hash of their join keys
and one matched flag each; after the scan, the rows never matched go through the rest of the
joins extended with NULLs. Every `WHERE` condition then waits until after the outermost such
join, so a condition on the left tables cannot remove a row whose right partner would wrongly
come out unmatched.

**Limits.** Subqueries nest at most 32 levels (also bounded by the 64 levels of expression
nesting), a statement has at most 1,024 `SELECT`s, so parsing, preparing and dropping a statement
stay well inside the stack and linear in its size. Recursion stops with `54001` after 1,000,000
steps (MySQL: 1,000 and error 3636, its `cte_max_recursion_depth` default). Every intermediate
table, kept result, hash set and set-operation key is counted against the statement's 1 GiB of
work memory, now shared by all of a statement's nested queries, so a hostile query fails with
`53200` instead of exhausting the process. Unreferenced `WITH` queries still run;
`MATERIALIZED` is accepted and changes nothing.

**Superseded in part by D151.** Correlated subqueries now reach any query around them and stand in grouped queries and in `UPDATE`/`DELETE`; `LATERAL`, `FULL JOIN ... USING` and data-modifying `WITH` run.
