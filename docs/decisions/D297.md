## D297 Joined `UPDATE` and `DELETE` in every dialect: one join of the target and the other tables, the target's rows found again by key, each changed or deleted once — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory item 1, follows D138's `MERGE`

PostgreSQL (`UPDATE ... FROM`, `DELETE ... USING`), SQLite (`UPDATE ... FROM`, from 3.33), MySQL
(multiple-table `UPDATE` and `DELETE`) and SQL Server (`UPDATE ... FROM`, `DELETE ... FROM`) each
let a statement change one table's rows through a join with others. Their manuals agree on what
it means: the rows of the target that join at least one combination of the other tables' rows
are changed or deleted, each once, and a target row that joins several rows is changed from one
of them, which one not being defined (PostgreSQL's `UPDATE` page, SQL Server's `UPDATE` page on
"the results of an UPDATE statement are undefined", MySQL's "each matching row is updated once").

- **One AST for all of them.** `Update::from` and `Delete::using` hold a `JoinedTables`: the
  `FROM` list, where the target sits in it (`target_at`: SQL Server and MySQL name a table of the
  list, by its alias or as the one reference to that table; PostgreSQL and SQLite keep it beside
  the list, so it joins as one more table), MySQL's other deleted tables (`more_targets_at`) and
  the table each MySQL `SET` assignment writes (`assigned_at`, with `writes_any_table`: an
  unqualified MySQL column belongs to the one listed table that has it, found when names are
  resolved; none is 1054, more than one 1052). A qualified `SET` column (`t.col`, MySQL and
  Transact-SQL) is checked against the target in the parser (Msg 4104, MySQL 1054).
- **Execution.** `joined_dml` runs one `SELECT` over the whole `FROM` list with the statement's
  `WHERE`, through the same executor as any query (joins by key, hash joins, derived tables,
  subqueries in `WHERE`), asking for every column of each stored table and `label.*` of the
  others. Each target's rows are found again from their part of a joined row: by the primary key,
  or, for a table without one, by the encoded row among the table's rows (identical rows join
  identically, so all of them are changed). The first joined row of each target row wins, rows
  are read again by key before they are written, and the writes go through `MERGE`'s
  `store_updates` and the `DELETE` path, so checks, `NOT NULL`, indexes, foreign keys and row
  triggers behave as in a single-table statement. MySQL's several targets are each written in
  turn from the same joined rows.
- **Expressions.** `SET` and `RETURNING`/`OUTPUT` are evaluated over the joined row (the target's
  part is its new row for `RETURNING` after an `UPDATE`), with the target column's type as the
  hint, as a single-table `UPDATE` does. `OUTPUT inserted.`/`deleted.` of a joined Transact-SQL
  statement name the target's label. Name resolution checks the joined statement as one
  `SELECT` (names, `SELECT` privileges on what it reads), then the targets' `UPDATE` or
  `DELETE` privilege and written columns.
- **Refused for now (`0A000`).** Subqueries in `SET` and `RETURNING` of a joined statement (they
  would need the correlation `MERGE` also refuses), a view, subquery, function, partitioned
  table or table with row-level security for the role as a target, and `EXPLAIN` of a joined
  statement. The MCP server's destructive check treats every joined statement as reaching many
  rows and names all its targets.
