## D338 SQLite's `UPDATE OR ROLLBACK | ABORT | FAIL | IGNORE | REPLACE` on D317's statement-level rollback, and D318's read-only leftovers: `SELECT ... FOR UPDATE | NO KEY UPDATE | SHARE | KEY SHARE` refused with `25006`, `LOCK TABLE` kept, `SET TRANSACTION` in an implicit transaction, `25006` for a writing function called from `SELECT`, `default_transaction_read_only` in a procedure that commits — Decided by the build loop (batch 6, 2026-11-10); roadmap M3, extends D317 and D318, corrects D318's `LOCK TABLE` item, no format change

D317 gave SQLite's `INSERT OR ...` its five conflict resolution algorithms and left `UPDATE OR
...` parsing as a syntax error. D318 left five read-only gaps. sqlite.org's "The ON CONFLICT
Clause" and "UPDATE", and PostgreSQL's `SELECT` ("The Locking Clause"), `SET TRANSACTION`,
`LOCK` and `CALL` pages and Oracle's `SET TRANSACTION` reference say how they behave; EggDB now
follows them.

- **`UPDATE OR <algorithm>` (SQLite).** The parser reads `UPDATE OR ROLLBACK | ABORT | FAIL |
  IGNORE | REPLACE` through the same `sqlite_conflict_resolution` as `INSERT OR`, which now
  answers a `ConflictResolution` (`Rollback`, `Abort`, `Fail`, `Ignore`, `Replace`) that
  `INSERT` turns into its three fields and `UPDATE` keeps as `Update::conflict_resolution`
  (`Abort` in every other dialect). The algorithms govern `UNIQUE` and primary-key, `NOT NULL`
  and `CHECK` conflicts; any other error backs out the statement as `ABORT` does.
  - `ABORT` (and plain `UPDATE`) backs out the statement and keeps the transaction (D317).
  - `ROLLBACK` rolls the whole transaction back on a conflict. `INSERT OR ROLLBACK` now does it
    only on a conflict too, as sqlite.org says; before, any error rolled the transaction back.
  - `FAIL` keeps the rows the statement changed before the conflicting row, in a transaction and
    on its own (where they commit), and stops there.
  - `IGNORE` leaves each conflicting row as it was and goes on; the tag counts the rows changed.
  - `REPLACE` deletes the rows that hold the new row's primary key or unique values, then writes
    it; a row it deleted that the statement had still to change is skipped. A `NULL` for a
    `NOT NULL` column takes the column's default, and without a default it is `ABORT`'s error. A
    `CHECK` conflict is `ABORT`'s.
  - Errors are SQLite's: `UNIQUE constraint failed: t.c` (2067, 1555 for the primary key) and
    `NOT NULL constraint failed: t.c` (1299).
- **How it works.** `FAIL`, `IGNORE` and `REPLACE` write row by row
  (`conflict_resolution::write_updated_rows_resolving_conflicts`), each row checked against the
  table as the earlier rows left it, in the order the rows are read, which is SQLite's rowid
  order: `UPDATE OR IGNORE t SET a = a + 1` over `a` = 1, 2, 3 changes only the last row, as in
  SQLite. `ABORT` and `ROLLBACK` keep the set-at-a-time write every dialect uses. `FAIL` stops
  at the first conflicting row and returns its error after writing the rows before it; the
  session keeps those rows because the statement carries `FAIL`, the same path as `INSERT OR
  FAIL` (D317). Deleted rows and changed rows run the foreign-key actions as any delete and
  update do; `REPLACE`'s deletes fire no delete triggers, as SQLite's do with
  `recursive_triggers` off.
- **`SELECT ... FOR UPDATE` in a read-only transaction (PostgreSQL, Oracle).** `FOR UPDATE`,
  `FOR NO KEY UPDATE`, `FOR SHARE` and `FOR KEY SHARE` on a permanent table are `25006 cannot
  execute SELECT FOR UPDATE in a read-only transaction`, the statement named by the first
  locking clause's strength as PostgreSQL names it (`SELECT FOR NO KEY UPDATE`, `SELECT FOR
  SHARE`, `SELECT FOR KEY SHARE`), and PostgreSQL's transaction is aborted as for any error.
  Temporary tables may be locked, as in PostgreSQL. In Oracle's read-only transaction the same
  refusal is `ORA-01456`, since Oracle allows only `SELECT` without the `for_update_clause`.
  The session reads the locking clause from the statement's tokens, as it already does for
  sequence functions, so cached plans and prepared statements are covered.
- **`LOCK TABLE` stays accepted** in a read-only transaction, in every mode. D318's "Left" and
  the roadmap said PostgreSQL refuses it; it does not: PostgreSQL classifies `LOCK` as allowed in
  a read-only transaction (`ClassifyUtilityCommandAsReadOnly`) and restricts only the strong
  modes during recovery, which EggDB has no counterpart for. Oracle allows `LOCK TABLE` in a
  read-only transaction too.
- **`SET TRANSACTION` in an implicit transaction.** In a multi-statement `Query` (or a pipeline
  up to its `Sync`), `SET TRANSACTION READ ONLY` before the implicit transaction has written
  opens it as a reader that refuses writes until the implicit transaction ends, and `SET
  TRANSACTION READ WRITE` under `default_transaction_read_only = on` opens it as a writer; no
  warning is given, since PostgreSQL treats an implicit transaction as a block. `SET
  transaction_read_only` does the same. After a write, the existing rule holds: `READ ONLY`
  refuses further writes and what was written commits. A `COMMIT` that ends such a transaction
  warns `there is no transaction in progress`, as it does after a write. A lone `SET
  TRANSACTION` still warns.
- **A writing function called from `SELECT` in `BEGIN READ ONLY`.** `SELECT f()` that calls a
  volatile function runs through the session's writer path in a read-only block too, so a write
  to a permanent table is `25006 cannot execute SELECT in a read-only transaction` (PostgreSQL
  names the inner command; EggDB names the statement, as D318 does for `CALL`), a write to a
  temporary table passes, and a function that only reads runs as before. It was `0A000`.
- **`default_transaction_read_only` and a procedure that commits.** Outside a block, under
  `default_transaction_read_only = on` (or `SET SESSION CHARACTERISTICS AS TRANSACTION READ
  ONLY`), `CALL` and `DO` now run non-atomic like any other top-level `CALL`, so a `COMMIT` or
  `ROLLBACK` inside the procedure works, and every transaction the procedure runs is read-only:
  a write to a permanent table is `25006 cannot execute CALL in a read-only transaction` (`DO`
  for a `DO` block), `nextval()` is `cannot execute nextval() in a read-only transaction`, and
  temporary tables are written. The procedure holds the store's writer while it runs, as other
  non-atomic calls do.

Tests: `statement_rollback_tests.rs` (`UPDATE OR FAIL` in a transaction and on its own, for a
unique and a `NOT NULL` conflict; `OR ABORT`; `OR IGNORE` on a unique column, the primary key
and `NOT NULL`; `OR REPLACE` deleting the rows in the way, on the primary key, and filling a
`NOT NULL` column from its default or failing without one; `OR ROLLBACK` on a conflict and not
on another error; `OR IGNORE ... FROM` refused); `read_only_transaction_tests.rs` (each locking
strength's message and the aborted block, a temporary table locked, `LOCK TABLE` accepted,
`default_transaction_read_only` outside a block, a writing and a reading function called from
`SELECT`, a procedure that commits under `default_transaction_read_only`, `SET TRANSACTION READ
ONLY` and `READ WRITE` in an implicit transaction); new cases in the SQLite, PostgreSQL and
Oracle correctness suites.

Left: `UPDATE OR FAIL | IGNORE | REPLACE` with `FROM` and on a view (`0A000`); the outer
statement's algorithm overriding the conflict clause of a SQLite trigger's own statements;
SQLite's row-by-row checking for plain `UPDATE` (`ABORT`), which EggDB checks after the whole
statement, so `UPDATE t SET a = a + 1` over a unique `a` succeeds where SQLite fails; the
`ON CONFLICT` clauses of table constraints (a file format change); `SELECT ... FOR UPDATE` inside
a routine's body in a read-only transaction, and `FOR UPDATE OF` naming only temporary tables
when a permanent table is also read; the inner command's name in the `25006` of a write from a
function or procedure; `SET TRANSACTION READ WRITE` inside a procedure after its `COMMIT`.
