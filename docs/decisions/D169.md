## D169 Declarative partitioning: partitions are tables, a catalog record links them, and queries expand into a pruned UNION ALL — Decided by the build loop (by judgement, 2026-10-31); refines D32 and D35

Part 4.M2-3 adds partitioned tables in PostgreSQL's model, with MySQL's and Oracle's forms on top.

- **Partitions are ordinary tables.** Each partition keeps its rows, indexes and constraints
  as any table does. A partitioned table has no rows of its own. A partition may itself be
  partitioned.
- **One catalog record per table in the tree** (catalog prefix `0x0E`, record version 1). It
  holds the strategy and key columns of a partitioned table, and the parent and bound of a
  partition. Bound values are stored as text and read back in the key column's type, so the
  record never depends on the row encoding. The table definitions are untouched, so the
  table-definition version does not change and older files read the same. Since this is a new
  catalog record, it is reviewed as a format change (D35).
- **Writes are routed.** `INSERT` evaluates each row's key once and passes those values to the
  chosen partition's own insert as constants, so a volatile default is never evaluated twice.
  The partition then applies its own defaults and checks. `COPY` routes in batches. `UPDATE`,
  `DELETE` and `TRUNCATE` run per surviving partition. Every partition checks its bound on every
  write, and a partitioned table refuses rows written to it directly (`23514`), so a missed path
  fails loudly instead of storing rows where no query finds them.
- **Reads are expanded.** Name resolution replaces a partitioned table with a `UNION ALL` of the
  partitions that can match the `WHERE` of the query it appears in. Pruning looks at comparisons,
  `BETWEEN`, `IN` and `IS NULL` on the key against constants, and keeps a partition unless its
  bound rules the condition out. When one partition is left, the reference names it directly,
  so its primary key and indexes serve the query. The plan cache keeps parsed text only and
  resolves each time, so pruning always sees the current constants.
- **Hash.** Rows are hashed with FNV-1a over the key's order-preserving encoding, combined per
  column. This is not PostgreSQL's hash, so a restored hash partition's rows that would not fit
  their partition here go through the partitioned table instead, as `pg_dump
  --load-via-partition-root` does.
- **MySQL and Oracle.** Named partitions declared inside `CREATE TABLE` become partition tables
  named `<table>#P#<partition>`, as InnoDB names its partition files.

Left for later: moving rows between partitions on `UPDATE`, expressions in partition keys,
identity and `AUTO_INCREMENT` columns in partitioned tables, `SELECT ... FROM t PARTITION (p)`,
MySQL's and Oracle's `ALTER TABLE ... ADD/DROP/REORGANIZE PARTITION`, Oracle interval
partitioning, SQL Server partition schemes, and propagating `CREATE INDEX` on a partitioned table
to its partitions.
