## D187 Encryption at rest: data pages encrypted with AES-256-CTR under a key from the user, marked by an incompatible feature — Decided by the build loop (by judgement, 2026-10-31); refines D20 and D23; security-critical (D35)

Part 4.M6b-3 asks for files encrypted per page with keys from a key file, a KMS or a
Vault-compatible API, and online key rotation.

- **Which bytes.** Every data page written through the log (B+tree, overflow and LSM pages, so
  every key and value) is encrypted after its 16-byte header: in the log's page images and in
  place, since the in-place copy is the logged image. Headers (type, layout, LSN), free-list
  pages, log records other than page images, and the superblock stay readable: they hold no
  keys or values, and recovery needs them without the key.
- **How.** AES-256 in counter mode (NIST SP 800-38A) over our own AES, under a page key derived
  from the user's 32-byte key with HKDF-SHA256 (RFC 5869). Each 16-byte counter block is the
  page's LSN, then the page number shifted left 16 bits with the block's index. An LSN is the
  log position of the one committed image it belongs to, so no counter block is ever used for
  two different plaintexts. Counter mode keeps pages the same size, so no page layout changes and
  `page_reserved_tail` stays 0.
- **Marking.** The page header's `flags` bit 0 (`PAGE_ENCRYPTED`) marks an encrypted page, and
  the incompatible feature `ENCRYPTED_PAGES` (bit 1) marks the file, so older releases refuse it
  instead of reading ciphertext as damage. The superblock keeps a 16-byte key check value (HMAC
  of the derived key) at offset 232, so a wrong key is refused at open rather than read as
  corruption. Checksums are over the stored (encrypted) bytes, so torn and misplaced pages are
  still caught without the key.
- **Integrity.** CRC-32C catches damage but not a deliberate change by someone who can write
  the file; authenticated encryption needs a tag per page, which waits for a reserved page tail
  (left).
- **Where keys come from.** `Options::encryption_key([u8; 32])` and the command line's
  `--key-file <file>` (64 hexadecimal digits). A new file is encrypted from its first commit;
  a file that already holds unencrypted data refuses a key. Copies made by `eggdb backup` and
  `eggdb compact` stay encrypted with the same key.

Left: authenticated page encryption (a per-page tag in the reserved tail), encrypting an existing
file and rotating keys online (rewrite every page under a new key), KMS and Vault-compatible key
sources, per-column and per-tenant keys, and the CLI's other key sources.
