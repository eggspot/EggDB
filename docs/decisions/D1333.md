## D1333 Changed pages spill before the commit, and a commit writes its log ahead — Decided by the code-only session (2026-11-25, D355); roadmap M2 "Dirty pages spill before commit" (D86, D167)

- **What users get.** A write transaction may change more pages than the page cache holds, and a value larger than the cache can be written, instead of failing with `CacheFull` or `TooLarge` (D167). `Options::spill_changes` (on by default) controls it; an in-memory, read-only or encrypted database never spills and keeps the old errors.
- **Frames.** When every frame holds a changed page, `PageCache` writes one changed, unpinned page to a scratch file and reuses its frame (`spill.rs`). The page's header and its "allocated in this transaction" and "contents checked" flags go with it. Reading or writing it again brings it back as a changed page, without a second before-image; freeing it forgets it; a snapshot that starts while pages are spilled keeps their committed images as it does for changed frames. The commit logs spilled pages after the frames, reading each back into one page buffer; a commit or a rollback empties the scratch file. The database file sees nothing before the commit, so the write-ahead log, recovery and crash safety are unchanged: the no-steal rule of D79 still holds for the database file, and the scratch file is only memory moved to disk.
- **The scratch file.** `<database>-spill`, opened by the database the first time a transaction spills, truncated at each commit and rollback, removed when the database is dropped. It is a second file only while a large transaction runs (D3 keeps one file at rest).
- **Encrypted files.** Spilled pages would reach disk in the clear, and sealing them with the page cipher would reuse its page-and-LSN nonces for different contents, so an encrypted database does not spill.
- **The log.** A commit's log records were held whole in memory until the commit. `LogWriter::write_ahead` now writes the whole log blocks buffered so far to the log once 4 MiB wait, and their page images are written in place afterwards from the log file, through the same `unwritten` path that `Durability::Normal` already uses. Records written ahead count only once the commit record seals the batch; a crash before that leaves records recovery ignores, exactly as a commit torn while being written.
- **Left.** Measuring the roadmap's check (a 1 GiB `put_reader` peaking near 32 MiB) belongs to the build-and-fix pass; the free-list and before-image structures of a huge transaction still grow with it.
- **Proof.** Page cache tests: a transaction three times the cache commits and survives a reopen; a rollback drops spilled pages and leaves the committed ones; without an opener a full cache still refuses; a commit of 1,500 pages, more than the 4 MiB the log buffers, survives a reopen. A database test commits 10,000 keys and a 160 KiB value through a 64 KiB cache and finds the scratch file gone after the database is dropped; the tests that expect the old errors now turn spilling off.
