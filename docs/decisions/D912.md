## D912 Flux variables, several results and `join` — Decided by the code-only session (2026-11-12, D355); roadmap M16, follow-up of D682 and D713

- A Flux query is now a program of statements, not one pipeline: `name = <pipeline>` keeps a stream under a name,
  a pipeline may start from a name (`cpu |> mean()`), and every statement that is not an assignment, or that ends in
  `yield()`, adds a result. Each result is written as its own annotated CSV block, in order, as InfluxDB 2 does.
  `import "..."` lines are skipped; the packages they name are not loaded.
- `join(tables: {a: x, b: y}, on: [columns], method: "inner")` (the classic join) joins two named streams: rows
  whose `on` columns are equal pair up, every other column present on both sides gets its side's key as a suffix
  (`_value_cpu`, `_value_mem`), columns on one side keep their names, and the output is grouped by the `on` columns
  that both inputs grouped by. Only the inner method is supported, as in Flux; at most 1,000,000 rows.
- A stream keeps its `range()` bounds, so `aggregateWindow()` after a variable or a join windows over the same span;
  a join spans both inputs' bounds.
- Left: the `join` package's `join.inner`/`join.left`/... with row functions, user functions defined in the query,
  `option`, and pushing windows into SQL.
