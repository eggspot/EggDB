## D1226 Subqueries in SQLite's EXPLAIN QUERY PLAN — Decided by the code-only session (2026-11-17, D355); roadmap M6c, subqueries in the tabular plans (D327)

- **What users get.** In the SQLite dialect, `EXPLAIN QUERY PLAN` (and `EXPLAIN`) of a query with subqueries lists each one as SQLite does: a `LIST SUBQUERY n` row for an `IN (SELECT ...)` read once into a list, `SCALAR SUBQUERY n` for a value read once, `CORRELATED ` before either when it reads the outer row, and the subquery's own scans as that row's children through the `parent` column, instead of refusing the query.
- **How.** The SQLite styles now plan with D327's subplans, the same planning PostgreSQL's form uses; the rows are written depth first with ids counted from 2, so plans without subqueries keep their ids.
- **Left.** A correlated `IN` is labelled a scalar subquery (D327's subplans record only whether a list was hashed), SQLite's `SEARCH ... (rowid=?)` for an outer table probed by an `IN` list, and the other dialects' tabular plans.
- **Proof.** `index_tests.rs`: an `IN` subquery as a list subquery with its scan under it, and a correlated `count(*)` in the select list as a correlated scalar subquery.
