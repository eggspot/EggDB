## D1126 Row locks across sessions, and deadlocks between row and advisory locks — Decided by the code-only session (2026-11-13, D355); roadmap M3 (row locks with `NOWAIT` and `SKIP LOCKED`, deadlocks with `40P01`, the locking clause in the tree; D32, D173, D291, D338)

- **One lock table.** Row locks join the table that already holds PostgreSQL's advisory locks and SQL Server's
  application locks: a lock named by the database and the row's stored key, shared or exclusive, held until the
  transaction ends (released where advisory transaction locks are). Every wait now registers in the shared waits map,
  so a cycle through any mix of row, advisory and application locks is found. The waiter that closed it fails with
  `40P01` "deadlock detected", MySQL 1213. Waits for `pg_advisory_lock` now detect cycles too.
- **`SELECT ... FOR UPDATE | FOR NO KEY UPDATE | FOR SHARE | FOR KEY SHARE`**, with `NOWAIT` or `SKIP LOCKED`, is
  kept on the `Select` (`locking`), and `LOCK IN SHARE MODE` too. Before the query runs, the same `FROM` and `WHERE`
  select the primary keys in the query's order, and each row is locked: exclusively for the update forms, shared for
  the share forms.
  - Waiting is the default.
  - `NOWAIT` fails at once with `55P03` (MySQL 3572, Oracle `ORA-00054`).
  - `SKIP LOCKED` passes over held rows. It stops once `OFFSET` plus `LIMIT` rows are locked, when those are
    literals, and narrows the query to the rows it locked, so a job queue's `LIMIT 1 FOR UPDATE SKIP LOCKED` hands
    each worker a different row.
  - `GROUP BY`, `DISTINCT` and `HAVING` are refused, as PostgreSQL refuses them.
- **Writers in concurrent blocks lock what they write.** A put or delete of a table row in a `REPEATABLE READ` or
  `SERIALIZABLE` block (D1123) takes the row's exclusive lock and waits for it. Two such blocks updating one row
  queue as in PostgreSQL, and the second still fails at commit if the first changed what it read. Blocks on the one
  writer need no row locks against each other, since only one runs at a time, but their `FOR UPDATE` still waits for
  rows a concurrent block holds.
- **Left:** locking through joins (`FOR UPDATE OF` a table of the join), views and tables without a primary key
  (which lock nothing for now); Oracle's `WAIT n`; using the kept clause for D338's read-only checks; and SQL
  Server's `WITH (UPDLOCK, READPAST)` hints mapped onto the same locks.
