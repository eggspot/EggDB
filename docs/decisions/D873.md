## D873 Oracle DDL and database event triggers — Decided by the code-only session (2026-11-12, D355); roadmap M5, event triggers

- The Oracle dialect parses `CREATE [OR REPLACE] TRIGGER name {BEFORE | AFTER} event [OR event ...] ON {SCHEMA |
  user.SCHEMA | DATABASE | PLUGGABLE DATABASE} [ENABLE | DISABLE] <PL/SQL block>`, where the events are the DDL
  events `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME`, `GRANT`, `REVOKE`, `COMMENT` and `DDL` (all of them), and
  the database events `AFTER LOGON` and `AFTER SERVERERROR`. `LOGOFF`, `STARTUP`, `SHUTDOWN`, `SUSPEND`,
  `DB_ROLE_CHANGE`, `ANALYZE`, `AUDIT` and the other events, `WHEN`, `FOLLOWS`/`PRECEDES` and `CALL` bodies are
  refused as not supported yet. The block is compiled when the trigger is created, so a broken one fails there.
- Triggers are kept in `eggdb_internal.oracle_system_triggers` (name in upper case, timing, events, owning user or
  `NULL` for `DATABASE`, body, enabled, created). `DROP TRIGGER name` and `ALTER TRIGGER name ENABLE | DISABLE |
  RENAME TO | COMPILE` find a system trigger by name before the table triggers.
- Firing: for an outermost Oracle statement whose command is DDL, the `BEFORE` triggers run, then the statement, then
  the `AFTER` triggers, in creation order, in one transaction (a savepoint when a transaction is already open), so an
  error from a trigger, such as `RAISE_APPLICATION_ERROR`, undoes the statement. A `SCHEMA` trigger fires only for the
  sessions of its user (Oracle's "issued by the schema's user"). Statements run by a trigger fire nothing.
- `AFTER SERVERERROR` triggers run when an outermost Oracle statement fails; their own errors are ignored and the
  original error is returned. `AFTER LOGON` triggers run when an Oracle-dialect connection signs in
  (`Session::fire_login_event_triggers`); an error fails the login.
- Event attributes: `ora_sysevent`, `ora_dict_obj_name`, `ora_dict_obj_owner`, `ora_dict_obj_type`, `ora_login_user`
  and `ora_database_name` are read without parentheses, and `ora_server_error(1)` and `ora_server_error_msg(1)` give
  the failing statement's error number and message; all are `NULL` (or 0) outside a firing trigger. Object names and
  owners are given in upper case, the default schema as the session's user.
