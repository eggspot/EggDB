## D822 SQL Server security policies — Decided by the code-only session (2026-11-12, D355); roadmap M6b, D186

- The SQL Server dialect parses `CREATE SECURITY POLICY name ADD FILTER PREDICATE fn(columns) ON table [, ...]
  [WITH (STATE = ON|OFF, SCHEMABINDING = ...)] [NOT FOR REPLICATION]`, `ALTER SECURITY POLICY name [ADD FILTER
  PREDICATE ... | DROP FILTER PREDICATE ON table] [WITH (STATE = ...)]` and `DROP SECURITY POLICY [IF EXISTS] name`.
  `BLOCK PREDICATE` and `ALTER ... PREDICATE` are refused as not supported yet.
- The predicates are kept in `eggdb_internal.sqlserver_security_predicates`. While a policy is on, each predicate is
  a restrictive row-security policy on its table (D186), `sqlserver_policy_<name>`, with `USING (EXISTS (SELECT 1
  FROM fn(columns)))`, since an inline predicate function returns a row for each row that may be seen; one permissive
  `eggdb_sqlserver_base` policy (`USING (true)`) per table makes the restrictive ones the only filter, so several
  policies on one table combine with `AND` as SQL Server's do. Turning a policy off drops its row policies and keeps
  the predicates; turning it on, or `ALTER`, makes them again.
- Differences from SQL Server: row security applies to checked roles only (D183, D186), so superusers and embedded
  sessions see every row, where SQL Server filters every user unless the function exempts them; and the function
  runs from a PostgreSQL-dialect condition. A duplicate name answers error 2714, an unknown one 15151.
- Security-policy statements count as privilege changes in the audit log (D815).
