## D314 The simulated network gives up on a connection across a long cut, cuts one way, gives each host its own latency and bandwidth, answers `NotConnected` after a reset, and a satisfied reap makes no readiness call — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M1, extends D70, D72 and D74, applies D9

D72 left the simulated network without a way to lose a connection: a cut held bytes forever, so
a test could not check what a server does when a client disappears behind a dead link, cuts were
always both ways, and every host shared one latency with unlimited bandwidth. The M1 wrap-up
review (D75) added two follow-ups: a reset end in simulation still answered its peer's address
and a shutdown, which the operating systems refuse, and the readiness queue asked the selector
for more events even when the operations it had just tried already met the reap's minimum.

What users of `eggdb-platform` (tests of the server, replication and consensus code) can now do:

- **Lose a connection across a long cut.** An end whose bytes, or whose end of sending, stay
  unacknowledged for `SimNetwork::RETRANSMISSION_TIMEOUT` gives up: its receives and sends fail
  with `ErrorKind::TimedOut`, as Linux reports `ETIMEDOUT`. The timeout is 924.6 s, Linux's
  default of 15 retransmissions (`tcp_retries2`) with the retransmission timeout doubling from
  `TCP_RTO_MIN` (200 ms) up to `TCP_RTO_MAX` (120 s). The timer runs only while the end has
  something unacknowledged and the bytes cannot cross or the acknowledgements cannot come back.
  Latency alone never starts it, so a connection survives any cut shorter than the timeout, and
  an idle connection survives any cut, as TCP without keep-alive does. The timer is on the
  simulated clock, so a plain `reap` now moves the clock to it rather than failing with
  `Stalled`. The peer that gave up forgets the connection: what it had sent and not yet had
  acknowledged is gone, though bytes that had already arrived are still read before the
  failure, as Linux's `tcp_recvmsg` returns queued data before it reports `ETIMEDOUT`; and
  the other end, if it sends once the path is open both ways, finds the connection reset
  (`ConnectionReset`), as a TCP stack answers a segment for a connection it no longer has with a
  RST. An end that only receives never learns, a half-open connection as over TCP; its receive
  waits until it is canceled.
- **Cut one way.** `SimNetwork::partition_one_way(from, to)` drops what `from` sends to `to`
  while `to`'s traffic to `from` still arrives. `partition(a, b)` is now both one-way cuts;
  `heal(a, b)` and `heal_all()` lift both directions. A connect across either direction times
  out after `CONNECT_TIMEOUT` (the SYN or the SYN-ACK is lost). On an open connection the bytes
  that can cross arrive, but their acknowledgements cannot return, so both ends with bytes in
  flight give up after the retransmission timeout, as TCP does.
- **Give a host its own link.** `SimNetwork::host_latency(ip, least, most)` adds a latency drawn
  from the seed to everything the host sends and receives, on top of the network's
  `latency(least, most)`. `SimNetwork::host_bandwidth(ip, bytes_per_second)` makes the bytes a
  host sends leave one after another at that rate, shared by all its connections, and the bytes
  it receives enter at that rate: a send of `n` bytes arrives `n / rate` after it could start
  leaving, plus the latency, queued behind the host's earlier sends. Traffic within one host
  never crosses its link. Handshakes and ends of sending are zero bytes, so they cost latency
  only. Nothing is drawn from the seed for a host without a link.
- **`NotConnected` after a reset or a timeout.** A reset or timed-out end's `peer_address()` and
  `shutdown_write()` fail with `ErrorKind::NotConnected`, as `getpeername` and `shutdown` answer
  `ENOTCONN` on Linux once a connection is reset; `local_address()` still answers. macOS's
  `getpeername` answers `EINVAL` for a socket whose connection was reset, so `OsStream` on
  Apple systems reports that `EINVAL` as `NotConnected` too, keeping one answer across the
  backends. The contract test checks it against the operating systems' sockets on Linux and
  macOS and against the simulation.
- **No readiness call in a reap that is already satisfied.** When the operations a readiness
  queue (epoll, kqueue, `poll(2)`) tries at the start of a reap finish at once and meet a
  nonzero minimum, the reap returns without the zero-timeout `epoll_wait`, `kevent` or `poll`
  it used to make for further events. That saves one system call per reap on the common
  request-and-reply path, where a send finishes at once. A reap with a minimum of zero still
  polls, since collecting what has finished is what it asks for. So that operations left
  waiting are never starved by a caller whose every reap is satisfied at once, at most 16 reaps
  in a row skip the call and the 17th polls.

Decided by research:
- **Linux's numbers.** The timeouts copy Linux's defaults (`tcp_retries2` = 15,
  `tcp_syn_retries` = 6 as in D72), the platform most servers run on. Windows gives up sooner
  (`TcpMaxDataRetransmissions` = 5, about 21 s with its defaults), but a longer timeout is the
  stricter test for code that must notice a dead peer on its own (keep-alives, request
  deadlines), which D72 keeps above the I/O layer.
- **One timer per end, not per connection.** Each end's timer follows its own unacknowledged
  bytes, so a one-way cut fails both ends only when both have something in flight, and a peer
  that gives up does not reset the other end until that end sends across an open path. A shared
  timer would fail a receiver that a real stack leaves waiting.
- **Bandwidth as a link per host.** Real bottlenecks are usually a host's access link (a slow
  uplink, a capped cloud instance), and a per-host model needs no topology. Per-pair or per-path
  limits can be added on top later without changing what a host link means.
- **A bound on skipped polls.** io_uring and IOCP return what has completed without a separate
  readiness step, so the bound is only for the readiness queues. Sixteen keeps a skipped call's
  saving on a busy loop while bounding how long a ready socket can wait unseen to sixteen
  reaps of that loop.

Left: a keep-alive model (an idle connection across a long cut is never failed by the
simulation, matching TCP with keep-alive off; `SO_KEEPALIVE` itself is not in the platform
layer yet); acknowledgements that take latency to return (an acknowledgement is immediate once
the bytes arrive and the path back is open); packet loss, duplication and reordering below TCP
(the simulation is at the stream level, so loss shows only as latency or a cut); per-pair and
per-path latency and bandwidth; `NotConnected` checked against Windows' sockets, which the
contract test skips there.
