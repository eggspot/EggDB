## D639 FSE-compressed Huffman weights in the Zstandard encoder — Decided by the code-only session (2026-11-12, D355); roadmap M2, D171, D638

D638 wrote a Huffman tree's weights directly, which reaches only bytes up to 128. Blocks whose
literals use higher bytes kept raw literals: UTF-8 text in most languages, binary keys, and
numbers stored little-endian. RFC 8878 section 4.2.1.2 compresses the weights with FSE instead.

- The weights to send are normalized to an accuracy of 6 (64 states, the format's limit for
  weights):
  - each used weight gets its share, at least 1;
  - the largest share takes up or gives back the difference.
- The distribution is written as the decoder's `read_distribution` reads it:
  - the accuracy;
  - each count plus one, in a width that shrinks as the remaining probability does, one bit
    shorter when the value is below the threshold;
  - zero runs in 2-bit steps (16 bits for 24 zeros).
- The weights are coded with two interleaved FSE states, as the reference encoder does:
  - from the last weight back;
  - an odd count starts the first state from the last weight and encodes one more;
  - the second state is flushed before the first, so the decoder reads the first state first.

  The decoder then recovers the count of weights from where the stream ends.
- The tree's size byte (below 128) gives the compressed size, so a tree over 127 bytes is not
  used. Between the two forms the shorter one is chosen. Literals that use byte 255 (255 weights)
  stay raw.
- Tests:
  - a distribution read back by the decoder's parser;
  - FSE trees for 149 and 150 weights (odd and even) read back as Huffman tables;
  - letters shifted above 128 shrinking below 70%.
