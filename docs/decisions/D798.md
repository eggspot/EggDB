## D798 SQL Server's rowversion — Decided by the code-only session (2026-11-12, D355); roadmap M10, SQL Server's types

- A column declared `rowversion` (or `timestamp`, its old name) in SQL Server's `CREATE TABLE` is `binary(8)`, and the
  session gives the table a generated row trigger right after creating it: every insert and update stamps the column
  with the next value of one database-wide sequence, `eggdb_internal.sqlserver_rowversion` (starting at 2001, just
  above SQL Server's first `@@DBTS`), as 8 big-endian bytes. Values therefore grow with every write anywhere in the
  database and compare as SQL Server's do for optimistic concurrency (`WHERE version = @old`).
- The trigger is a PL/pgSQL function in `eggdb_internal` like `eggdb_temporal`'s (D795), so it fires whatever dialect
  writes the row. An explicit value written to the column is overwritten instead of failing with SQL Server's 273.
- `timestamp`/`rowversion` stay refused in `CAST`, where SQL Server reads them as `binary(8)` only for conversions;
  `ALTER TABLE ... ADD` of a rowversion column does not attach the trigger yet.
- Left: `@@DBTS` and `MIN_ACTIVE_ROWVERSION()`, error 273, `ADD` of a rowversion column, and the type's own name in
  the catalogs.
