## D323 `CREATE TABLE ... AS` in PostgreSQL, MySQL, SQLite and Oracle, `VALUES` as a query in MySQL and SQLite, row constructors compared with rows and subqueries, and recursive `WITH` `SEARCH` and `CYCLE` — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M5, extends D303 and D128, applies D10, D19 and D32

D303 built `SELECT ... INTO` and left its other spelling, `CREATE TABLE ... AS`, together with
`VALUES` outside PostgreSQL and row constructors (`(a, b) IN (SELECT ...)`), which answered
`0A000`. Each is built from the dialects' manuals: PostgreSQL's `CREATE TABLE AS` and "Row and
Array Comparisons" (9.24, 9.25), MySQL 8's "CREATE TABLE ... SELECT Statement", "VALUES
Statement" and "Row Subqueries", SQLite's "CREATE TABLE ... AS SELECT" and "Row Values", and
Oracle's `CREATE TABLE` (`AS subquery`).

- **One statement, two spellings.** `CreateTableAs` now carries its spelling (`SELECT INTO` or
  `CREATE TABLE AS`, which picks the tag and the read-only error), `IF NOT EXISTS`, PostgreSQL's
  and Oracle's column-name list, MySQL's column definitions (`declared`), `WITH [NO] DATA` and
  MySQL's `IGNORE`/`REPLACE`. `create_table_as::run` runs the query (with `LIMIT 0` for `WITH NO
  DATA`), builds the table from the result's columns and inserts the rows as constants in the
  same transaction, as D303 does. `IF NOT EXISTS` resolves the name first and runs nothing when
  the relation exists.
- **NOT NULL as each dialect does.** PostgreSQL and SQLite make every column nullable. MySQL and
  Oracle keep `NOT NULL` of a column copied directly (a bare column or `*`) from the only table
  of a query without joins or grouping sets; any other column is nullable. SQL Server's `SELECT
  ... INTO` is unchanged (D303).
- **MySQL's column definitions.** Defined columns the query doesn't name come first, a query
  column with a defined name takes the definition, and the keys, indexes and checks defined
  apply; the rows are inserted by name, and the tag reports them as affected rows.
- **SQLite's declared types.** A column's declared type comes from its expression's affinity: a
  column reference or `*` keeps its column's (`INT`, `TEXT`, `REAL`, `NUM`), a `CAST` takes the
  cast type's, and any other expression has none. The `sqlite_schema` text is the one SQLite
  writes, `CREATE TABLE t(a INT,c)`, one column per line when the names are long.
- **`VALUES`.** MySQL's `VALUES ROW(...)` and SQLite's `VALUES (...)` are statements, set
  operands, derived tables and subqueries, through the same `ValuesList` PostgreSQL uses. MySQL's
  columns are named `column_0`, ... by filling the list's `column_names`, which a derived table's
  alias list replaces; SQLite keeps PostgreSQL's `column1`, ....
- **Row constructors.** `(a, b)` parses to the record constructor in every dialect but SQL Server.
  Two constructors compared with `=` or `<>` become the `AND`/`OR` of their fields' comparisons,
  so an index on the fields still serves them. An ordering becomes one flat internal call
  (`row_values::ROW_ORDERING`) that compares the pairs from the left and is decided by the first
  pair that is not equal, NULL when that pair holds a NULL: the standard's answer, with each
  field evaluated once and no nesting however wide the rows are (a tree one level per field
  overflowed the stack on 2,000 fields). `(a, b) IN ((1, 2), (3, 4))` is one internal call too
  (`row_values::ROW_MEMBERSHIP`) that evaluates the left row once and compares it with each
  listed row with three-valued logic, so memory grows with the list, not with the list times
  the left side. A constructor against a subquery is a new `SubqueryTest::RowCompare` (at most
  one row, `21000` for more, NULL for none; SQLite uses the subquery's first row, as SQLite
  does), and `IN`, `NOT IN` and quantified comparisons with a constructor read the subquery's
  rows as records and compare field by field with three-valued logic
  (`row_values::compare_rows`). A constructor against a composite value that is not a
  constructor keeps PostgreSQL's record comparison. Outside PostgreSQL a constructor is only an
  operand of a comparison or `IN`: anywhere else MySQL gives `1241` and SQLite `row value
  misused`, and Oracle refuses an ordering of rows with ORA-00920. In MySQL `VALUES` starts a
  query only when `ROW` follows it, so the `VALUES(col)` function keeps working inside
  parentheses in `ON DUPLICATE KEY UPDATE`.
- **PostgreSQL's options before `AS`.** `ON COMMIT PRESERVE ROWS | DELETE ROWS | DROP` is taken
  for a temporary table, as `CREATE TABLE` takes it; `USING`, `WITH (...)`, `WITHOUT OIDS` and
  `TABLESPACE` are `0A000`.
- **`SEARCH` and `CYCLE`** (PostgreSQL 14, manual 7.8.2.1 "Search Order" and 7.8.2.2 "Cycle
  Detection"). The parser keeps `SearchClause` and `CycleClause` on the `CommonTable`;
  `search_cycle::SearchCycle` checks them against the query's column list, as PostgreSQL's
  analysis does, and adds the columns in PostgreSQL's order (sequence, mark, path). It computes
  them in Rust rather than rewriting the query: the seed rows get their first values, and the
  recursive term's `SELECT` gets the parent's sequence and path appended (its `*` and `cte.*`
  are spelled out as the query's own columns first, so they don't take the added ones), from
  which each new row's values follow: depth first appends `ROW(columns)` to the parent's array,
  breadth first takes the parent's depth plus one, and `CYCLE` marks a row whose `ROW(columns)`
  is already on its parent's path. A marked row is returned but not put in the working table,
  which is what PostgreSQL's added `WHERE mark <> cycle_value` on the recursive reference does.
  `ArrayElement::Record` is new: `record[]` (OID 2287), never a table column's type, stored in
  the statement's temporary tables as its records in the row encoding, so the fields keep their
  types and an array of rows sorts field by field.

Decided by research: PostgreSQL applies SQL's NULL rules only between row constructors and
between a constructor and a subquery, and the record comparison elsewhere (manual 9.24.6), so
only those forms are rewritten. (The first version rewrote an ordering into nested `OR`/`AND`
comparisons, which evaluated the leading fields twice and nested one level per field; review
round 1 found the stack overflow, and the flat call replaced it.)

Decided by research (`SEARCH` and `CYCLE`): the cycle test is `ROW(columns) = ANY(path)`,
which compares records with NULL fields equal (manual 9.24.6, outside two row constructors), so
`search_cycle` uses the record order, not three-valued logic. The breadth-first depth is a
`bigint`, as PostgreSQL's rewrite makes it. The mark values follow PostgreSQL's `CYCLE` type
rules: an untyped string takes the other value's type, two strings are `text`, and two typed
values need a common type (`42804` otherwise).

Left: `USING`, `WITH (...)`, `WITHOUT OIDS` and `TABLESPACE` before `AS` in PostgreSQL's
`CREATE TABLE ... AS`; `SELECT *` over a `USING` or `NATURAL` join (or an unnamed `FROM` item) in the recursive
term of a query with `SEARCH` or `CYCLE` (`0A000`), `record[]` outside these columns (`ARRAY[ROW(...)]`,
binary wire format), `CREATE TABLE AS EXECUTE`, PostgreSQL's `TABLE t` as a query, MySQL's `CREATE
TABLE ... LIKE`, SQL Server's `SELECT ... INTO` keeping `NOT NULL`, Oracle's `VALUES` in `FROM`
(23ai), the keyed lookup for a correlated `(a, b) IN (SELECT ...)` (it scans the subquery's rows
per outer row), and SQLite's `:1` suffixes for duplicate column names in `CREATE TABLE ... AS`.
