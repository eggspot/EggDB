## D323 `CREATE TABLE ... AS` in PostgreSQL, MySQL, SQLite and Oracle, `VALUES` as a query in MySQL and SQLite, and row constructors compared with rows and subqueries — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M5, extends D303 and D128, applies D10, D19 and D32

D303 built `SELECT ... INTO` and left its other spelling, `CREATE TABLE ... AS`, together with
`VALUES` outside PostgreSQL and row constructors (`(a, b) IN (SELECT ...)`), which answered
`0A000`. Each is built from the dialects' manuals: PostgreSQL's `CREATE TABLE AS` and "Row and
Array Comparisons" (9.24, 9.25), MySQL 8's "CREATE TABLE ... SELECT Statement", "VALUES
Statement" and "Row Subqueries", SQLite's "CREATE TABLE ... AS SELECT" and "Row Values", and
Oracle's `CREATE TABLE` (`AS subquery`).

- **One statement, two spellings.** `CreateTableAs` now carries its spelling (`SELECT INTO` or
  `CREATE TABLE AS`, which picks the tag and the read-only error), `IF NOT EXISTS`, PostgreSQL's
  and Oracle's column-name list, MySQL's column definitions (`declared`), `WITH [NO] DATA` and
  MySQL's `IGNORE`/`REPLACE`. `create_table_as::run` runs the query (with `LIMIT 0` for `WITH NO
  DATA`), builds the table from the result's columns and inserts the rows as constants in the
  same transaction, as D303 does. `IF NOT EXISTS` resolves the name first and runs nothing when
  the relation exists.
- **NOT NULL as each dialect does.** PostgreSQL and SQLite make every column nullable. MySQL and
  Oracle keep `NOT NULL` of a column copied directly (a bare column or `*`) from the only table
  of a query without joins or grouping sets; any other column is nullable. SQL Server's `SELECT
  ... INTO` is unchanged (D303).
- **MySQL's column definitions.** Defined columns the query doesn't name come first, a query
  column with a defined name takes the definition, and the keys, indexes and checks defined
  apply; the rows are inserted by name, and the tag reports them as affected rows.
- **SQLite's declared types.** A column's declared type comes from its expression's affinity: a
  column reference or `*` keeps its column's (`INT`, `TEXT`, `REAL`, `NUM`), a `CAST` takes the
  cast type's, and any other expression has none. The `sqlite_schema` text is the one SQLite
  writes, `CREATE TABLE t(a INT,c)`, one column per line when the names are long.
- **`VALUES`.** MySQL's `VALUES ROW(...)` and SQLite's `VALUES (...)` are statements, set
  operands, derived tables and subqueries, through the same `ValuesList` PostgreSQL uses. MySQL's
  columns are named `column_0`, ... by filling the list's `column_names`, which a derived table's
  alias list replaces; SQLite keeps PostgreSQL's `column1`, ....
- **Row constructors.** `(a, b)` parses to the record constructor in every dialect but SQL Server.
  Two constructors compared with `=` or `<>` become the `AND`/`OR` of their fields' comparisons,
  so an index on the fields still serves them; an ordering becomes `a1 < b1 OR (a1 = b1 AND ...)`,
  which gives the standard's NULL answer. A constructor against a subquery is a new
  `SubqueryTest::RowCompare` (at most one row, `21000` for more, NULL for none), and `IN`, `NOT
  IN` and quantified comparisons with a constructor read the subquery's rows as records and
  compare field by field with three-valued logic (`row_values::compare_rows`). A constructor
  against a composite value that is not a constructor keeps PostgreSQL's record comparison.

Decided by research: PostgreSQL applies SQL's NULL rules only between row constructors and
between a constructor and a subquery, and the record comparison elsewhere (manual 9.24.6), so
only those forms are rewritten. A two-sided rewrite of ordering comparisons evaluates the
leading fields twice; a volatile function there is evaluated twice, which PostgreSQL avoids, and
is accepted for the index use the rewrite keeps.

Left: recursive `WITH` `SEARCH DEPTH|BREADTH FIRST BY ... SET` and `CYCLE ... SET ... USING`
(still `0A000`), `CREATE TABLE AS EXECUTE`, PostgreSQL's `TABLE t` as a query, MySQL's `CREATE
TABLE ... LIKE`, SQL Server's `SELECT ... INTO` keeping `NOT NULL`, Oracle's `VALUES` in `FROM`
(23ai), the keyed lookup for a correlated `(a, b) IN (SELECT ...)` (it scans the subquery's rows
per outer row), and SQLite's `:1` suffixes for duplicate column names in `CREATE TABLE ... AS`.
