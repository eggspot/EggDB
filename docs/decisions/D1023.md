## D1023 Backups through the server's SQL clients, and progress reports — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D141)

- A client connected to `eggdb serve` backs up the database the server holds with a statement: `BACKUP TO
  '<path>' [CLONE]` in every dialect, and Transact-SQL's own `BACKUP DATABASE <name> TO DISK = '<path>' [WITH ...]`
  for SQL Server tools (SSMS's backup dialog sends it), where `WITH` options other than EggDB's `CLONE` are accepted
  and ignored. The copy is `Database::backup_to`'s online copy of the last commit (D141), or with `CLONE` a
  copy-on-write clone (D1021); the command answers `BACKUP` with a notice naming the stamp and the copy.
- The statement writes a file on the server's disk, so, like `COPY ... TO` a file, it needs a superuser and is
  refused for a session acting as a checked role (D183). The path is the server's; a file already there is never
  replaced.
- The statement reaches the file through `KeyValueStore::backup_to`, whose default says the store keeps no file, so
  sessions over stores without one (in memory, MCP's per-call stores) refuse it plainly.
- **Progress reports.** The storage copy reports the entries committed to the copy after each batch
  (`copy_to_reporting`, `Database::backup_to_reporting`); `eggdb backup` shows a percentage on the terminal's
  standard error, never in JSON output or when standard error is not a terminal.
- Left: compaction of a file `serve` holds, which needs the server to switch every listener to the compacted file at
  once.
