## D1080 EggOS as a target — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D8)

- **The binary.** EggOS's native system call ABI is Linux's (EggOS D1), and it runs static Linux programs
  unchanged. So EggDB's EggOS binary is its static musl Linux build, the same file the `musl` job and the
  release already make. There is no second Rust target or toolchain, and no separate release asset.
- **The backend.** EggOS implements Linux's interface only in part. Its documented limits: no `/sys`, no
  io_uring, no `copy_file_range`, and `fallocate` with mode 0 only. The platform layer gains
  `eggdb_platform::os_identity`:
  - `operating_system()` and `on_eggos()` find EggOS once, by the release `uname` reports (EggOS writes
    `6.1.0-eggos`).
  - `OperatingSystem::name()` gives `EggOS`, or the build target's name elsewhere.
  - The Linux backend asks it where EggOS differs:
    - automatic I/O queues use the thread pool (or inline I/O without threads) instead of probing io_uring
      at every start;
    - CPU topology is not read from the `/sys` EggOS lacks, and stays unknown beside the affinity mask EggOS
      reports;
    - file cloning treats `ENOSYS` as "cannot clone, copy instead", which also helps Linux sandboxes that
      block the ioctl.
  - Everything else (files, `fsync`, memory maps, sockets, `epoll`, futexes, `/proc/meminfo`) is
    EggOS's Linux implementation, used as on Linux.
- **Tests.** The release check is unit-tested. The full suite inside EggOS is EggOS's stage 3 ("EggOS builds
  EggDB", its `eggos-ci` plan): EggOS boots in QEMU, builds and tests this repository, and compares the
  results with Linux's. It runs in EggOS's repository, which owns that image.
- Learned from: EggOS's own documentation (its decisions, `linux-programs.md`, `limitations.md`) and its
  `uname` identity, which are our own.
