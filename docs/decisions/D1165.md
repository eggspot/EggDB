## D1165 `tsvector`, `tsquery` and `jsonpath` as types of their own — Decided by the code-only session (2026-11-14, D355); roadmap M6a (D195, D289)

- **Built-in base types.** The three types join `citext`, `hstore`, `vector` and `geometry` as built-in base types
  (`DefinedType::TSVECTOR`, `TSQUERY` and `JSONPATH`), with PostgreSQL's OIDs 3614, 3615 and 4072. So they:
  - name themselves in `pg_typeof` and `format_type`;
  - are table column types, stored in rows under value tags of their own (31 `tsvector`, 32 `tsquery`,
    33 `jsonpath`; batch 816 added the row encoder's tags, which batch 815 missed);
  - reach clients with their own type OIDs.

  The parser takes `tsvector`, `tsquery` and `jsonpath` in PostgreSQL's dialect, and `jsonpath` is no longer
  plain text.
- **Values, checked when made and kept in canonical text** (`DefinedValue::TsVector`, `TsQuery`, `JsonPath`):
  - `tsvector`: quoted lexemes with positions and weights, sorted and merged by `eggdb-search`'s parser. Bare
    words become lexemes without positions, as `'a fat cat'::tsvector` does in PostgreSQL.
  - `tsquery`: the parsed query's printed form. A single bare word is accepted as a lexeme.
  - `jsonpath`: checked by the path parser and kept as written, trimmed.
  - Bad input is `22023`/`42601`-style `invalid input syntax for type ...`.
  - Text converts to them explicitly or on assignment; they convert back to text through the usual output.
- **Text-search functions return the new types.** `to_tsvector` and `setweight` return `tsvector`;
  `to_tsquery`, `plainto_tsquery`, `phraseto_tsquery` and `websearch_to_tsquery` return `tsquery`. `@@` takes
  either type or text. `ts_rank`, `ts_headline` and the jsonpath functions read them through their text, so
  every existing query behaves the same.
- **Comparison, equality and memory.** Values compare by their canonical text, hash with keys of their own, and
  count their text's bytes against the memory budget.
- **Not yet.** The binary wire formats of `tsvector` and `tsquery` (PostgreSQL's lexeme and operator encodings)
  are not written. Clients that ask for binary results of these columns get the binary-format error the other
  unsupported types give; text format, which drivers use by default, works.
- **Tests.** Canonical forms and refusals for all three, and a table with all three column types: `pg_typeof`
  names, `v @@ q` over stored values, a bare-word vector's printed form, and `@?` with a stored path.

- **`refcursor` columns** (batch 816, roadmap D301): a `refcursor` column is now `DefinedType::REFCURSOR` (base type,
  OID 1790) with values `DefinedValue::RefCursor`, stored under value tag 34, instead of plain text. So
  `pg_typeof` and column descriptions say `refcursor`, and the name converts back to the catalog `refcursor` that
  PL/pgSQL's cursor variables hold. `refcursor[]` columns keep `text[]` storage.
- **The file format.** Rows of these four column types use the new value tags, and their table definitions name
  the new base types. A release before this one cannot read such a table, as with any new column type. Tables
  without them are unchanged. The security review of the format change (D35) runs when the batch is built,
  checking that a damaged tag or text decodes to an error, never a panic: the decoder returns `damaged` for an
  unknown tag, and the text is read with the same checked reader as `citext`.

**Status:** code written, unbuilt (code-only mode, D355).
