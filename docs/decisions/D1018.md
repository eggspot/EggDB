## D1018 Gremlin sessions and remote transactions — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D48, D1011)

- A request that names a session (`args.session`, as the session processor and the drivers' remote transactions
  send it) runs in that session's transaction: its writes are staged in memory over the committed graph with the
  shared key-value overlay Bolt's explicit transactions use (D606), so the session reads its own writes and other
  clients see none of them until it commits.
- A session commits on `g.tx().commit()` (a script) or a bytecode request whose source instructions hold
  `["tx", "commit"]`, as gremlin-python's, gremlin-javascript's and Gremlin.Net's `tx().commit()` send it; it rolls
  back on `g.tx().rollback()` or `["tx", "rollback"]`, on `op: close`, and when the connection ends. With
  `manageTransaction: true` each request commits on its own, as Gremlin Server's option does.
- A connection holds at most 16 sessions. Bindings defined by one script are not kept for the next script of a
  session: scripts are traversals, never programs (D1011).
