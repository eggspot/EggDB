## D159 Transact-SQL procedures and functions on the shared routine store: one routine per name, bodies compiled by the batch compiler at CREATE, procedures run inside the caller's batch on the session, functions run by a read-only runner over the calling statement's writer — Decided by the build loop (by judgement, 2026-10-31); part 3.15, extends D137 and D158, applies D9, D35, D45, D157

Part 3.15 adds SQL Server's stored procedures and user-defined functions (scalar, inline
table-valued and multi-statement table-valued), called with `EXEC` in batches, over TDS RPC and
from triggers. The plan expected no decision of its own (D137 and D158 extended by notes); the
choices below are architecture, so they are recorded here instead.

**The same records as PL/pgSQL.** A Transact-SQL routine is a routine record of D158 (`0x0C`,
record version 1) with SQL Server's dialect code and the language `tsql`; no format change. The
`CREATE` text is the source of truth and is re-parsed on load. Transact-SQL has no overloads, so
a name holds one Transact-SQL routine; procedures and functions share the name space with
tables and views, as in SQL Server (Msg 2714). `ALTER` stores its text rewritten to start with
`CREATE`, as SQL Server's `sys.sql_modules` shows it. The declared SQL Server types of the
parameters and of a function's result (lengths, precision) are kept next to the engine types in
the parsed definition, because binding converts each argument to its declared type.

**Compiled by the batch compiler.** A body is compiled at `CREATE` with D137's batch compiler,
with the parameters visible as declared variables and `RETURN value` allowed, so a procedure
fails at `CREATE` for what a batch fails at before it runs. Function bodies are also checked
for side effects at `CREATE` (Msg 443, 444, 557) and again when run. The compiled program of a
function is cached per definition in the routine cache that D158 keys by the store's committed
version.

**Procedures run inside the caller's batch.** `EXEC` of a user procedure, inside a batch, is
bound (positional then named arguments, defaults, declared-type conversion, SQL Server's error
numbers), then run by the batch interpreter on the session as a nested program, like dynamic
SQL: its steps stream to the caller (result sets, messages, counts), its errors reach the
caller's `TRY ... CATCH`, `OUTPUT` values and the `RETURN` status are copied back, its `SET`
options are restored, and a changed `@@TRANCOUNT` is Msg 266. Procedures and dynamic SQL share
one nesting counter, 32 levels (Msg 217). An RPC request naming a procedure is turned into an
`EXEC @status = [schema].[name] @p = @p [OUTPUT], ...` batch over the RPC's own parameters, so
there is one path for both.

**Functions run outside the session.** A function is called once per row from expression
evaluation, where the session is not reachable, so it runs in a small Transact-SQL runner over
the calling statement's writer, table catalog and settings, with its own variables and table
variables and its own depth counter (32, Msg 217). It reads what the calling statement sees and
cannot write (functions are `STABLE`), which is SQL Server's rule anyway. Inline functions plan
their query with NULL parameters to know their columns.

**Not decided here:** table-valued functions after the first `FROM` item (`CROSS APPLY`),
`@@PROCID` and `ERROR_PROCEDURE()`, CLR, numbered and temporary procedures; they come later
without changing this layout.
