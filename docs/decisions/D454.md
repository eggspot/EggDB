## D454 SQL/XML publishing functions in the PostgreSQL and Oracle dialects — Decided by the code-only session (2026-11-11, D355); roadmap M10 (Oracle's XML functions)

- EggDB had no XML at all. The SQL/XML publishing functions, which PostgreSQL and Oracle share,
  now build XML as text (`parser/xml.rs`, `xml_functions.rs`): `XMLELEMENT([NAME] tag [,
  XMLATTRIBUTES(value [AS name], ...)] [, content ...])`, `XMLFOREST(value [AS name], ...)`,
  `XMLCONCAT(xml, ...)`, `XMLAGG(xml [ORDER BY ...])`, `XMLCOMMENT(text)`, `XMLPI([NAME] target [,
  content])`, `XMLSERIALIZE(CONTENT | DOCUMENT xml [AS type] [INDENT ...])` and `XMLPARSE(CONTENT |
  DOCUMENT text [WELLFORMED])`.
- **No XML type yet**, so nesting is decided when parsing: content that is itself one of these
  calls goes in as XML, and any other value is escaped (`&`, `<`, `>`, and `"` in attributes).
  `XMLAGG` is `string_agg` with an empty separator (wrapped so it counts as XML); `XMLSERIALIZE`
  is a cast; `XMLPARSE` passes its text through without checking it.
- Dialects: PostgreSQL requires `NAME` and writes an element without content as `<tag/>`; Oracle
  takes the name bare, upper-cases unquoted names and writes `<TAG></TAG>`. A `NULL` attribute is
  left out, a `NULL` forest member too, and a forest or concatenation of only `NULL`s is `NULL`.
  An attribute or forest member without `AS` takes its column's name. Element and target names
  are checked as XML names; a comment with `--` and a processing instruction named `xml` are
  refused, as both systems refuse them.
- Left: the `xml` type and `XMLType`, `XMLTABLE`, `XMLQUERY`, `EXTRACTVALUE` and the other XPath and
  XQuery functions, `XMLEXISTS`, and checking `XMLPARSE`'s input.
