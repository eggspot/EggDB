## D490 `pg_cancel_backend` and `pg_terminate_backend` across sessions — Decided by the code-only session (2026-11-11, D355); roadmap M6c, D25 and D488

- A session registered in the activity registry (D488) carries its cancel signal (PostgreSQL,
  MySQL and TDS listeners) and a termination flag.
- `pg_cancel_backend(pid)` cancels the running statement of every session with that pid (as a
  PostgreSQL `CancelRequest` would; the statement fails with `57014`), and
  `pg_terminate_backend(pid)` also ends the connection: a PostgreSQL connection sees the flag the
  next time it waits for the client and closes with `57P01` "terminating connection due to
  administrator command", as PostgreSQL does. Both answer whether a session had that pid.
- A role may signal its own sessions; the server's own user (the superuser) any. Others get
  `42501` "permission denied to cancel query" / "terminate process".
- The MySQL and TDS listeners do not watch the termination flag yet (their cancel works), and
  MySQL's `KILL` and SQL Server's `KILL` statements are not written. Ids are per protocol, so a
  PostgreSQL pid and a MySQL connection id can coincide; both sessions are signalled then.

**Status:** code written, unbuilt (code-only mode, D355).
