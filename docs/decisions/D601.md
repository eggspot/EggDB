## D601 pg_cron time zones per job — Decided by the code-only session (2026-11-12, D355); roadmap M10, D200, D429

pg_cron reads every schedule in one zone, `cron.timezone`, which is GMT by default. Teams running
"at midnight local time" jobs for several regions from one database want the zone set per job.
EggDB has no `postgresql.conf` for a server-wide `cron.timezone`, so the zone is kept on the job.

- `cron.job` gains a `timezone text` column. NULL or empty means UTC, as pg_cron's default.
- `cron.alter_job` gains a last parameter, `timezone text DEFAULT NULL`, so existing positional
  calls keep working. `UPDATE cron.job SET timezone = …` works too.
- A minute schedule is read in the job's local time. The runner adds the zone's offset at that
  instant (`TimeZone::offset_at`, with daylight saving time from the time zone database) before
  taking the calendar minute.
  - The zone is read as PostgreSQL's `TimeZone` setting reads it: a region or alias, an offset, or
    a POSIX rule.
  - A zone that names none of these counts the job as an invalid schedule, like a bad schedule,
    and does not run it.
- Second schedules (`'30 seconds'`) do not depend on the zone.
- `cron.job` tables made by an earlier `CREATE EXTENSION pg_cron` have no `timezone` column. The
  runner falls back to reading them without it (UTC), and `ALTER TABLE cron.job ADD COLUMN timezone
  text` plus a fresh `alter_job` brings them up to date.
- Local times that a daylight saving change skips or repeats follow plain cron: a skipped minute
  does not fire, and a repeated one fires twice.
