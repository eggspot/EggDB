## D507 dBase `.dbf` import — Decided by the code-only session (2026-11-11, D355); roadmap M11

`eggdb import --dbf <file> --table <name>` loads a dBase table into a SQL table, created from its
fields when it does not exist, like `--parquet` (D202). dBase's file layout is publicly documented
(the dBase III to 7 headers and Microsoft's Visual FoxPro table structure), so it needs no legal
check; ISAM and Btrieve have no public specification and stay on the roadmap.

- **Fields:** character and varchar fields become text (UTF-8 when the bytes are UTF-8, else
  Windows-1252, the most common code page of these files), numeric and float fields integers or
  `DECIMAL(length, decimals)`, dates dates, logicals booleans (`?` is null), Visual FoxPro
  integers, doubles, currency (`DECIMAL(19,4)`) and datetimes (Julian day and milliseconds), and
  dBase 7 integers and doubles in their sign-flipped big-endian form. General, picture and other
  binary fields become `bytea`; unknown kinds keep their text.
- **Memos:** a `.dbt` (dBase III blocks ending in 0x1A, dBase IV blocks with their length) or
  `.fpt` (FoxPro, big-endian block size and lengths) beside the table is read for memo fields; a
  memo value with no memo file is an error, not a silent null.
- **Records:** deleted records (`*`) are skipped; numbers shown as `***` (overflow) are null;
  names are lowercased so they work unquoted. The header's record count must fit the file.
- **Left out:** Visual FoxPro's `_NullFlags` column is dropped and its null bits not applied, so a
  null Visual FoxPro value reads as its stored blank; the code page byte is not mapped beyond the
  UTF-8 and Windows-1252 guess; dBase 7 timestamps (`@`) are read as text. No export.

**Status:** code written, unbuilt (code-only mode, D355).
