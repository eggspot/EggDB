## D439 In-database training: linear and logistic regression with `eggdb_fit` and `eggdb_predict` — Decided by the code-only session (2026-11-11, D355); roadmap M12

- `eggdb_fit(kind, rows)` fits a model to a query's rows and returns it as `jsonb`:
  `{"kind": "linear" | "logistic", "rows": n, "intercept": b, "coefficients": [w1, ...]}`. The rows
  come as a JSON array of `[target, feature1, feature2, ...]` arrays, which `jsonb_agg(
  jsonb_build_array(target, x1, x2))` builds from any query, so no new aggregate machinery is
  needed: `SELECT eggdb_fit('linear', jsonb_agg(jsonb_build_array(price, size, rooms))) FROM
  houses`. Rows holding a `NULL` (or a non-number) are skipped; booleans count as 0 and 1.
- `eggdb_predict(model, features)` applies a model to a `double precision[]` (or a single number):
  the linear prediction, or the logistic probability of class 1. Models are values, so they are
  kept the usual way: in a table, `INSERT INTO models SELECT 'price', eggdb_fit(...)`.
- **Fitting.** Linear regression solves the normal equations with an intercept (Gaussian
  elimination with partial pivoting and a tiny ridge term so near-duplicate features don't blow
  up; truly collinear ones are an error). Logistic regression runs Newton's method (iteratively
  reweighted least squares) for up to 50 steps with a tiny L2 term, from zero weights; targets
  must be 0 or 1. At most 256 features and 10 million rows; the whole JSON array is in memory, so
  the statement's work-memory limit bounds what can be fitted in one call.
- Names: `eggdb_` like EggDB's other built-ins (`eggdb_embed`), since PostgresML's `pgml.train`
  works on projects and stored models, a different model. Left: other kinds (trees, k-means),
  standard errors and p-values, training on more rows than fit in memory, and checking fits
  against a reference on a public dataset.
