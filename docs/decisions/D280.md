## D280 A procedure's `COMMIT` or `ROLLBACK` closes non-holdable cursors and releases transaction-level advisory locks, and `refcursor` is a type of its own — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap item 33c, finishes D262's "Not yet", applies D10 and D12; finished in part by D301

D262 let procedures end their transaction but kept every cursor they had opened, kept the
transaction-level advisory locks to the end of the `CALL`, and treated `refcursor` as `text`.
PostgreSQL's manual says otherwise: cursors are closed at transaction commit, except the
`WITH HOLD` ones and those of a `FOR` loop, which the first `COMMIT` or `ROLLBACK` makes holdable
(PL/pgSQL "Transaction Management"); transaction-level advisory locks are released at the end of
the transaction ("Advisory Locks"); a procedure with a `SET` clause cannot execute transaction
control statements (`CREATE PROCEDURE`); and `refcursor` is a type of its own (OID 1790) that
`pg_typeof` names and the protocol sends.

- **Cursors.** Each cursor a PL/pgSQL frame holds records the number of procedure
  transactions the thread had ended when it was opened (`portals::transactions_ended`). A
  `COMMIT` or `ROLLBACK` inside a procedure closes the session's non-holdable portals and adds
  one to that number (`portals::end_procedure_transaction`), and each frame drops its own
  non-holdable cursors opened before the change on its next cursor step (open, fetch, move,
  close, an exception block, the hand-over at return). So cursors opened by the procedure, by
  procedures it called and handed back, or by callers are all closed, and a later `FETCH` fails
  with `34000` `cursor "c" does not exist`, as in PostgreSQL. `FOR` loops over a query or a
  bound cursor already read their rows and keep them; `WITH HOLD` cursors stay open. A counter
  rather than a walk over every frame keeps the commit cheap and touches no frame but the
  running one.
- **Advisory locks.** The same `COMMIT` or `ROLLBACK` releases the transaction-level advisory
  locks of the session running the statement (`advisory_locks::release_active_transaction_locks`);
  session-level locks stay.
- **`SET` clause.** A procedure created with `SET name = value` runs atomically, so `COMMIT` in
  it fails with `2D000` `invalid transaction termination`, as in PostgreSQL.
- **`refcursor`.** A catalog type (`CatalogType::RefCursor`, OID 1790, category `U`) whose
  values are text: PL/pgSQL `refcursor` and bound cursor variables have it, functions returning
  `refcursor` and `INOUT refcursor` parameters send it as type 1790 in `RowDescription`, it
  converts to and from `text` and other text types, and a parameter the client declares with
  OID 1790 is read as text. A table column declared `refcursor` is stored as `text` (catalog
  types are not column types, and this keeps the file format as it is). A routine's identity
  now says `refcursor` where it said `text`, which only matters for routines created before
  this change on a development build; v0.2.0 has not shipped one.
- **`pg_typeof`.** Added: the `regtype` of its argument's type as SQL knows it before running
  (from the value's type when that is unknown), `unknown` for a quoted constant without a cast.

Not yet: `SET LOCAL` (and `set_config(..., true)`), which EggDB refuses everywhere with `0A000`,
and `SET` inside routines, which is refused with its own message; until they exist nothing set
for a transaction can outlive a procedure's `COMMIT`, and applying a routine's own `SET` clause
while it runs; a `refcursor[]` array type; `refcursor` table columns kept as `refcursor`.

**Extended by D301 (2026-11-03).** `SET LOCAL`, `set_config(..., true)`, `SET` inside routines, routines' own `SET` clause and `refcursor[]` are built; `refcursor` table columns kept as `refcursor` are still not built.
