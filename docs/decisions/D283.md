## D283 `expire`, `persist`, `cas`, `scan` and `ttl` inside an `eggdb shell` `BEGIN` block run in the block's transaction and see its own writes — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap item 20 (M3), finishes D266's "next", applies D2, D86 and D105

D266 let `put`, `get`, `del`, `incr` and `decr` join the write transaction an `eggdb shell`
`BEGIN` block holds, but refused `expire`, `persist` and `cas` inside a block, and let `scan`
and `ttl` read the last commit. A block that wrote keys and then listed them, set a time to live
and read it back, or took a lock with `cas` after changing it saw a different database from the
one its own `COMMIT` would write.

**All ten key-space commands run on the block's transaction.** `crates/eggdb/src/cli/commands/
shell_block.rs` runs every command the shell sends to a key space (`put`, `get`, `del`, `incr`,
`decr`, `expire`, `persist`, `cas`, `scan`, `ttl`) through `SharedWriteStore::with_open_transaction`,
the same path D266 built, with the write transaction's own API (`set_expiry`, `clear_expiry`,
`compare_and_set`, `time_to_live`, `scan`, `scan_prefix`, and the same on a collection):
- `scan` lists what the block would commit: keys put earlier in the block, without the ones it
  deleted, with `--prefix`, `--from`, `--to`, `-r`, `-n`, `-k` and every output
  format as outside a block. It streams entry by entry to stdout, so a large scan is never held
  in memory, and ends with the same dim `n entries` line on stderr.
- `ttl` shows the time to live the block set; `expire` and `persist` act on keys the block put
  and answer "nothing to expire/persist" for keys it deleted.
- `cas` compares against the value the block holds, not the last commit, and prints the same
  "not swapped" messages and JSON as outside a block.
- A time to live counts from the moment the block's transaction began (the write transaction's
  clock reading, as every write in it uses), takes effect at `COMMIT` with the rest of the
  block, and is gone after `ROLLBACK`.

**The same refusals as D266.** In a failed block every key-space command is refused until
`ROLLBACK`. While a `SAVEPOINT` is set, the writes (`put`, `del`, `incr`, `decr`, `expire`,
`persist`, `cas`) are refused with the message naming `RELEASE SAVEPOINT`, `COMMIT` and
`ROLLBACK`, for D266's reason: the savepoint undo log records only the session's own SQL
writes. The reads (`get`, `scan`, `ttl`) run. In a `BEGIN READ ONLY` block the writes are
refused and the reads see the last commit, which is what that block reads. `check`, `stats` and
`backup` still read the last commit: they report on or copy the file, not a transaction.

**Shared rendering, no second copy.** The scan entry printer (`scan_entry`) and the "not
swapped" message (`not_swapped`) are free functions shared by the command-line path and the
block path, so a block prints exactly what the command prints outside it.

Tests: unit tests driving the shell in process (times to live kept by `COMMIT` and dropped by
`ROLLBACK`, `expire`/`persist` on keys the block wrote and deleted, `scan` over the block's puts
and deletes in every direction and in JSON, a collection, `cas` against the block's value with
`--if-absent` and `--delete`, the savepoint and read-only refusals), and `tests/shell_blocks.rs`
running the `eggdb` binary with piped input and checking the file afterwards with separate
`get`, `ttl` and `sql` processes.

Not yet: recording key-value writes in the session's savepoint undo log, so the writes run while
a savepoint is set and `ROLLBACK TO SAVEPOINT` undoes them (D266).
