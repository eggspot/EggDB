## D692 XMLTABLE — Decided by the code-only session (2026-11-12, D355); roadmap M9 XML documents (D38), M10 Oracle's XML functions

- `XMLTABLE('row path' PASSING [BY REF | BY VALUE] xml [BY REF | BY VALUE] COLUMNS ...)` reads XML into rows in the
  `FROM` clause, in PostgreSQL's and Oracle's form, through D690's parser and XPath:
  - one row per node the row path selects;
  - each column `name type [PATH 'path'] [DEFAULT expr] [NULL | NOT NULL]` evaluates its path (the column name when
    none is given) from the row's node: the string value of the one node it selects, the `DEFAULT` (or `NULL`) when
    it selects none, an error (`21000`) when it selects several, and a string, number or boolean result as text;
    the value is then cast to the column's type;
  - `name FOR ORDINALITY` numbers the rows from 1;
  - without `COLUMNS`, Oracle's single `COLUMN_VALUE` column holds each node serialized as XML.
- It is a generated table built like `JSON_TABLE`'s: the parser turns it into the internal table function
  `eggdb_xml_table` with the document, the row path, an encoded column plan, one typed placeholder per column and
  the defaults, and `set_returning` produces its rows, so it takes whatever references `JSON_TABLE` takes.
- Left out: `XMLNAMESPACES` (refused), XQuery beyond XPath 1.0, the `NOT NULL` check (accepted, not enforced) and
  the `XMLType`/`xml` column types (columns of those types are read as text).
