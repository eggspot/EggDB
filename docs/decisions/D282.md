## D282 `eggdb follow` reads SQL Server CDC capture instances of some columns, uses net changes, survives a connection lost mid-poll, and switches to a second capture instance after a column change — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); extends D261 and D263

D261 skipped capture instances that leave out columns, never read net changes, and left DDL during
a follow to later. D263 ended the follow with exit 3 when the connection broke in the middle of a
poll, and stopped it on any SQL Server column change. Microsoft's CDC documentation ("What is
change data capture", `sys.sp_cdc_enable_table`, `cdc.fn_cdc_get_net_changes_<capture_instance>`)
describes the parts used here: `@captured_column_list` must include the primary key or the
`@index_name` columns, net changes need a primary key or unique index and return one final row
per changed row (a changed row identifier as a delete then an insert), a capture instance keeps
its column shape after DDL (new columns are ignored, dropped tracked columns become NULL), and a
second capture instance (at most two per table) lets a consumer move to the new shape without
losing changes while the two timelines overlap.

**Which capture instance.** One query (`cdc.change_tables` joined with `cdc.captured_columns`,
newest first) reads every instance with its captured columns, its minimum LSN and whether it
offers net changes keyed by the primary key (`supports_net_changes` and `index_name` equal to the
primary key index). An instance is usable only if it captures every primary key column. Without
`--changes`: an instance of every column, else change tracking, else an instance of some columns.
With `--changes cdc`: an instance of every column, else one of some. A table whose instances all
leave out a key column is named with the instance and the column, and the `try:` line creates a
second instance. When the chosen instance starts after the copy's LSN and an older usable one
covers it, the older one is read first and the follow switches later, so nothing in between is
missed.

**Columns left out.** Only the captured columns are created, copied and followed; `table_copied`
carries `left_out` and the text line says "leaves out ...". The file is a faithful copy of those
columns.

**Net changes.** No flag: an instance that offers net changes by the primary key is read with
`fn_cdc_get_net_changes_<instance>(from, to, N'all')`, ordered by `__$operation` so deletes come
before inserts and updates. Net changes would leave a row the copy saw but that was inserted and
deleted inside one range, so they start only at the LSN after every transaction committed before
the copy ended: the follow records the server time one second after the copy (or the resume) with
its UTC offset, waits until `sys.fn_cdc_map_lsn_to_time(sys.fn_cdc_get_max_lsn())` passes it, and
takes `sys.fn_cdc_increment_lsn(sys.fn_cdc_map_time_to_lsn(N'largest less than or equal', time))`.
Until then, and for ranges starting before it, all changes are read. A changed UTC offset takes a
new time. `table_copied` carries `net_changes`.

**Reconnecting mid-poll.** A poll works on a copy of the position (tables, change tracking
version, LSNs, the copy-start skip and the net-changes start) and returns it with the statements.
Only after the statements and the new positions commit in one EggDB transaction does the copy
become the position. An I/O error anywhere in the poll drops the copy, reconnects as D263 does
between polls (`--reconnect-for`), and reads the same poll again from the last applied position,
so nothing is lost or applied twice. Other server errors still stop the follow.

**Saved position.** A CDC table's state is `cdc <next LSN> <net-changes start LSN or -> <capture
instance>`, so a resume reads the instance it was reading. The older `cdc <LSN>` form is still read
(the instance is chosen again, and the net-changes start is found again).

**Column changes on a CDC table.** Each poll compares the source's columns with the followed ones:
- a followed column dropped on the source is dropped from the file (`columns_dropped`), since the
  instance would now send NULL for it; a dropped primary key column stops the follow;
- a column added on the source is named once (`columns_left_out`, with the
  `sys.sp_cdc_enable_table ... @capture_instance = N'<schema>_<table>_2'` command) and the follow
  goes on;
- when a newer usable instance of the table exists and has started (its minimum LSN is valid),
  the follow reads the old instance up to the LSN before the new one's minimum, then switches
  (`capture_switched`): followed columns the new instance leaves out are dropped, its new columns
  are added (nullable) and filled from the source's current rows by key, in the same transaction,
  and later polls read the new instance from its minimum. The fill reads rows newer than the
  position; the changes replayed after it converge, as the copy does (D261);
- if the old instance is gone before the follow reached the new one's minimum, the follow stops
  and names the lost LSN range.
On resume, a CDC table follows the columns the file and the source share; columns the file has
but the source dropped are dropped in the first poll, and a file column the instance does not
capture stops the follow with the D263 message. Change tracking tables keep D263's behaviour.

**Tested.** Unit tests cover the instance query and its reading, the choice with column subsets and
keys, the split of followed and left-out columns, the net query and its start, the saved
position in both forms, the column-change rules, the switch plan and the fill statements, the
resume rules and the classification of a lost connection. CI's `ss-follow` job adds `shop.items`
with an instance of `id, name` and net changes, adds a column on the source, creates a second
instance, checks `columns_left_out` and `capture_switched`, compares, and resumes after a stop.

Not yet: a capture instance keyed by a unique index other than the primary key uses all changes,
not net changes; a column whose data type changes on the source is not altered in the file; a
column dropped and re-added under the same name between two polls is taken as unchanged; the
fill after a switch holds the table's rows in memory, as the copy does; a connection lost during
the first copy still ends the follow.
