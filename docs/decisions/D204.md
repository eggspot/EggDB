## D204 Geometry in our own eggdb-geo, with PostGIS's function names over EWKT text — Decided by the build loop (by judgement, 2026-10-31); refines D2 and D57

Part 4.M12-2 asks for PostGIS-compatible `geometry` and `geography`, WKT/WKB/GeoJSON, spatial
predicates, R-tree indexes, and SQL Server's and MySQL's spatial functions.

- **`eggdb-geo`** from the OGC Simple Features specification (WKT, WKB), PostGIS's published
  EWKT/EWKB descriptions and RFC 7946: the two-dimensional geometry types, reading and writing
  them (every length, count and nesting checked), planar distance, area, length, envelope,
  containment and intersection, and the great-circle distance. PostGIS is GPL and its source is
  never read (D1); only its documentation of names and behaviour is used.
- **SQL through text, like vectors (D203).** The `ST_` functions take EWKT text or WKB bytes and
  return EWKT text, and `geometry(...)`/`geography(...)` columns are text, so PostGIS-style SQL
  runs now. A stored geometry type comes with the spatial index, as one slice, since both need
  the binary form inside the engine.
- **SRIDs are checked, not transformed**: mixing two SRIDs is an error, as in PostGIS.

Left: the stored type (hex EWKB output, binary wire format, catalog entry), R-tree/GiST indexes,
Z/M coordinates, geography on the WGS 84 spheroid, `ST_Transform`, overlay operations (union,
intersection, buffer), validity checks, SQL Server's `geometry::` methods, and the OGC test
suite cases.
