## D1049 Rolling upgrades with mixed versions in a cluster — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D20)

- Each release speaks a range of cluster feature levels (`LevelRange`; this release speaks level 1 only). The cluster
  runs at one level, stored as a replicated key (`cluster 00 feature-level`, 1 when absent), and everything that
  changes the wire or the log after this release is gated on that level, so a new release keeps speaking the old
  level while any member does.
- **Negotiation.** A server's `JOIN` greeting to its peers now carries its range after its node id; a greeting without
  one comes from a release before this decision and counts as level 1 only. The leader computes
  `negotiated_level`: the newest level every member speaks, never lower than the current level (levels only rise)
  and unchanged while some member's range is unknown. When it is above the stored level, a helper thread raises the
  stored level through an ordinary write (not the driver thread, whose own commit would wait on itself), so every
  member learns it in log order.
- **Refusal.** At start a server checks the stored level against its range (`may_join`): a release too old for the
  cluster's level (a downgrade after the level rose) or too new to speak it (an upgrade skipping releases) stops with
  a message saying which release to run.
- `upgrade_order` gives the order to restart members: followers in id order, the leader last, so leadership changes
  once. `docs/stability.md` describes the procedure.
- Learned from the descriptions of cluster version gates in CockroachDB and of feature compatibility versions in
  MongoDB's documentation; no code was read.
