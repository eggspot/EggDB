## D134 Oracle SQL from apps over PostgreSQL and TDS drivers: the dialect chosen per connection with `eggdb.dialect`, transactions kept by the connection's protocol, Oracle's data dictionary as catalog relations built per statement, the session user's own schema — Decided by the build loop (by research and judgement, 2026-10-29); roadmap item 44, applies D1, D9, D10, D12, D103, D108, D122, D126, D127, D129, D131, D133; supersedes in part D127

D10 rules out Oracle's own wire protocol until a lawful public specification exists, so Oracle
SQL reaches apps through the protocols EggDB already speaks. Item 44 lets a PostgreSQL or TDS
connection choose Oracle's dialect, and answers the data dictionary those apps and their tools
read. Nothing is stored: no format version, no D35 review.

**The choice (decision 1).** One setting, `eggdb.dialect`, chooses the dialect a session reads;
its value is the connection's own dialect (the one the session was opened in) or `oracle`.
PostgreSQL clients send it in the startup packet's `options` (`-c eggdb.dialect=oracle`, which
psql takes from `PGOPTIONS` and pgjdbc from its `options` property) or as `SET eggdb.dialect =
oracle`; Transact-SQL takes `SET eggdb.dialect oracle`; either goes back with the connection's
dialect or `DEFAULT`. A startup value that names no dialect ends the connection with `22023`, as
PostgreSQL ends one with a bad option; another dialect is `0A000` (MySQL and SQLite over these
protocols are not built); a change inside an open transaction is `25001`, because the dialects
treat a failing statement in a block differently. Alternatives rejected: a separate port per
dialect (one more listener per dialect, against D3's single process and config), a login option
of TDS (LOGIN7 has no free field a driver lets an app set; research found `AppName` and the
language only, both meant for other things), and choosing by database name (it would make the
same file look like two databases to tools).

**Statement boundaries (decision 2).** The new dialect applies from the next statement. A query
string or script with several statements is tokenized again from the statement after the
`SET`, so `SET eggdb.dialect = oracle; SELECT ... FROM dual` works in one psql `-c`; the text must
still split into tokens in the old dialect (an Oracle `q'[...]'` literal in the same string is a
known difference). A Transact-SQL batch, parsed as a whole before it runs, stops its syntax check
at the `SET`; the rest is tokenized and checked in the new dialect when the `SET` has run. A
pooled TDS connection's reset (`sp_reset_connection`) returns to Transact-SQL, as SQL Server
resets every `SET` option.

**Transactions follow the protocol (decision 3).** Oracle's dialect never autocommits on its
own (D108), but a PostgreSQL or TDS driver expects its protocol's rule: pgjdbc in autocommit
mode sends nothing and expects each statement committed, and sends `BEGIN` for
`setAutoCommit(false)`. So autocommit is the connection's dialect's rule, whichever dialect reads
the statements; a lone `BEGIN` (never valid PL/SQL) starts a transaction in Oracle's dialect, and
Oracle's DDL still commits what is open. TDS transaction-manager requests run as Transact-SQL
whichever dialect the connection chose (`Session::in_connection_dialect`). Over TDS,
`sp_executesql` parameters stay Transact-SQL's (`@name`), and mssql-jdbc's
`set implicit_transactions on` is refused in Oracle's dialect: known differences, since Oracle
apps do not use these drivers' parameter styles.

**Parameters and values (decision 4).** PostgreSQL drivers send `$1` placeholders (pgjdbc turns
`?` into them), so Oracle's lexer reads `$n` at the start of a token next to `:name` and `:1`.
Values go out with the protocol's closest types, from the engine type of each column, as they do
for the connection's own dialect: nothing Oracle-specific is added to either protocol.

**The data dictionary (decision 5).** `USER_`, `ALL_` and `DBA_` `TABLES`, `TAB_COLUMNS`,
`TAB_COLS`, `CONSTRAINTS`, `CONS_COLUMNS`, `INDEXES`, `IND_COLUMNS`, `SEQUENCES`, `VIEWS`,
`OBJECTS`, `TAB_COMMENTS`, `COL_COMMENTS` and `USERS`, the synonyms `TABS`, `COLS`, `IND`, `SEQ`,
`OBJ`, and `V$VERSION`, `NLS_SESSION_PARAMETERS` and `NLS_DATABASE_PARAMETERS` are a
`CatalogRelation::Oracle` variant, built once per statement from D129's catalog snapshot like
`information_schema` (D131) and SQL Server's `sys` views (D133), in
`crates/eggdb-sql/src/oracle_dictionary.rs`. This replaces item 25's materialized copies, which
only answered one dictionary view alone in `FROM`: the relations now join, group and nest like
tables, and pgwire's Describe reports their columns. Each view keeps the columns apps and tools
read, with Oracle's names, `VARCHAR2` as `text`, `NUMBER` as `bigint` and `DATE` as
`timestamp(0)`; statistics are NULL and dates 2000-01-01, because EggDB keeps neither. An
unqualified dictionary name that the user's own schemas hold as a table or view resolves to that
object, as a private object hides Oracle's public synonym; `SYS.` and the user's own prefix name
the dictionary. Writes to them are refused as for the other catalogs. The `NOT NULL` constraints
and the primary key's index are not listed (known differences).

**The session user's own schema (decision 6, supersedes D127's "the session user's own name
keeps meaning public").** D127 made users into schemas when HR's installer runs, so an app that
logs in as `hr` expects HR's tables as its own. A session reading Oracle's dialect takes the
schema named after its user, when one exists when the connection chooses the dialect (or the
session is identified), as its own: `USER_` views list it, `$user` in the search path is it, and
`HR.EMPLOYEES` from the user `hr` names it. Without such a schema, the default schema stays the
user's own, as before. The owner shown for a schema's objects is its name in upper case, the
user's name for the user's own schema, and `PUBLIC` for the default schema of a user with a
schema of its own. The schema is looked up once per choice, not per statement, to keep
statements free of an extra read (a known difference: a schema made for the user later counts
from the next connection).

**SYS_CONTEXT (decision 7).** `SYS_CONTEXT('USERENV', parameter)` with text constants is
answered when the statement is parsed, from the session's settings, search path and NLS
parameters, like `USER` and `current_schema`; Oracle's documented parameters that EggDB cannot
know (the client's host, program, module) are NULL, another namespace is NULL (no application
contexts yet), and an undocumented parameter is `ORA-02003`.

**Checks.** Unit tests of every view, the dialect switch on PostgreSQL and Transact-SQL
sessions, `$n` parameters, describe and the user's schema; socket tests of the startup option and
the TDS switch with transaction-manager requests; the hostile Oracle fuzzer covers the views,
`SYS_CONTEXT` and the `SET`. CI's `oracle-apps` job restores HR's installer unchanged, serves it
as `hr`, and compares psql's and a pgjdbc program's output for HR's queries, the dictionary and a
transaction with expected outputs written from HR's data (Oracle Database is not a CI oracle
under its license).

**Decided by research.** pgjdbc sends `options` from its connection properties in the startup
packet and `BEGIN` before the first statement after `setAutoCommit(false)`; psql passes
`PGOPTIONS` as `options`; Oracle's documented `USERENV` parameters and `NLS_SESSION_PARAMETERS`
rows (SQL Language Reference 23ai, `SYS_CONTEXT`; Database Reference, `NLS_SESSION_PARAMETERS`);
the columns of the dictionary views from the Database Reference.
