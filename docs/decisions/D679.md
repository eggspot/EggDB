## D679 InfluxQL SELECT ... INTO — Decided by the code-only session (2026-11-12, D355); roadmap M16, InfluxQL (D220, D521)

- `SELECT ... INTO <measurement> FROM ...` runs the query as any `SELECT` (buckets, fills, expressions) and writes
  each result row back as a point through the metrics store (D678), so the target measurement's tables, tag keys and
  deduplication come with it. A `db.rp.measurement` target keeps only the measurement, as there is one database and
  one retention policy. `INTO :MEASUREMENT` writes each source measurement's rows to the measurement of the same name,
  for `FROM` lists and regular expressions.
- The `GROUP BY` tags of a row become the point's tags; every other output column but `time` becomes a field (so a
  raw `SELECT *` turns the source's tags into fields, as InfluxDB does unless `GROUP BY *` is given). Null values are
  not written, and a row with no values left is skipped. Numbers keep their kind (integers as integer fields,
  others as float fields), text becomes string fields and booleans stay booleans.
- The answer is InfluxDB's: one series named `result` with `time` (the epoch) and `written`, the number of points.
