## D1025 A replica's first copy from a snapshot — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D208, D209, D1019, D1024)

- **Every copy knows where it is in the history.** The replication position (term and sequence) lives in a reserved
  key written in the same commit as each batch (D1024), and backups copy every key, so any copy of a primary, an
  archived snapshot (D208) included, carries the exact batch it holds. A replica started on such a copy follows on
  from that batch.
- **Seeding over the connection.** `eggdb serve <new file> --replica-of <primary>` on a file that does not exist
  asks the primary for a snapshot instead of batches (a hello whose position is the all-ones sentinel). The primary
  writes a fresh online backup to a temporary file, streams it in 1 MiB frames and ends with its SHA-256; the
  replica writes it to `<file>.replica-seeding`, checks the hash, syncs and renames it into place before opening it,
  so a cut connection leaves no half-copied database behind.
- **Catching up from the change archive.** A replica restored from an older archived copy may need batches the
  primary no longer keeps in memory. When the primary keeps a change archive (D1019), each archived commit carries
  its position key, so `Database::archived_batches` rebuilds the missing batches in order and the primary ships them
  before its in-memory ones; only a range neither holds whole sends the replica back to a fresh copy.
