## D111 Exact numeric, dates and times, and JSON in the one type system — Decided (by research and judgement, 2026-10-27); applies D1, D9, D10, D19, D20, D98, D109

**numeric** is EggDB's own exact decimal: a sign, a scale (digits after the point, kept as given
so `1.50` prints `1.50`) and a magnitude in base-10^9 limbs, or `NaN`. It holds up to 1,000
digits before the point and 1,000 after, where PostgreSQL allows 131,072 and 16,383: the bound
keeps every value under 225 limbs, so hostile input cannot make one multiplication, division or
power allocate or run without limit (`*` is checked against the bound before it multiplies,
`^` estimates its result's size first, and a division's dividend is at most a few thousand
digits). Results follow PostgreSQL's documented scales: `+ - *` exact, `/` at PostgreSQL's
quotient scale (at least 16 significant digits, computed from the operands' base-10,000
weights so `1/3` gives 20 digits and `10/4.0` 16), `%` with the larger scale, rounding half away
from zero, `numeric field overflow` for a value too wide for `numeric(p, s)`. `Infinity` waits;
`^` with a non-integer exponent (or an exact result past 2,000 digits) uses double precision.
Division is Knuth's long division on base-10^9 limbs; a differential test compares `+ - * / %`
with a schoolbook decimal reference written in the test and with `i128`.

Decimal constants become `numeric` in the PostgreSQL dialect, as there; the other dialects keep
their doubles for constants (MySQL's and Oracle's exact constants are a later change) except that
a decimal constant stored into a `numeric` column is read exactly. `sum(bigint)`, `sum(numeric)`,
`avg` of integers and `avg(numeric)` are exact `numeric`, which replaces item 19b's rule that ran
`sum(bigint)` only where its value printed the same. MySQL's `DECIMAL(p,s)` and Oracle's
`NUMBER(p,s)` (with a scale, or more than 18 digits) and `NUMBER` map to `numeric`; Oracle's
`NUMBER(p)` up to 18 digits keeps its integer types (D108). SQLite keeps its affinity rules, so
`DECIMAL` there stays a real.

**Dates and times** use PostgreSQL's representation: a `date` is days since 2000-01-01 (32 bits),
a `timestamp` and a `timestamptz` microseconds since 2000-01-01 00:00 (64 bits), over
PostgreSQL's range (4714-11-24 BC to 5874897 AD for dates, to 294276 AD for time stamps) in the
proleptic Gregorian calendar, so PostgreSQL's binary wire forms are the stored numbers. A
`timestamptz` is stored in UTC and shown in the session's `TimeZone`. The session's time zone
and the statement's start time (`now()`) are set for the thread while a statement runs and while
its results are handed out; the PostgreSQL protocol, which may send rows later, asks the session
for its offset when it sends them. Only UTC and fixed offsets resolve now (in POSIX's sign, as
PostgreSQL reads them); a named region is accepted, remembered and acts as UTC, because drivers
send their machine's zone name at connect and refusing it would refuse the connection; the time
zone database is its own later work. The clock is the standard library's wall clock. Input is
ISO 8601 and PostgreSQL's ISO style; `interval` is item 31, so subtracting time stamps answers
`0A000`. MySQL's `DATETIME(fsp)` is `timestamp(fsp)` and `TIMESTAMP(fsp)` is `timestamptz(fsp)`;
Oracle's `DATE` is `timestamp(0)`, a date with a time to the second, only in the Oracle dialect.

**JSON**: `json` is checked by EggDB's own parser (RFC 8259, nesting limited to 256 levels so the
recursive parser cannot overflow a thread's stack; PostgreSQL has no such limit) and stored as
written. `jsonb` is stored as its normalized text (keys sorted by length then bytes, the last
duplicate kept, numbers as `numeric` with the scale they were written with, PostgreSQL's
spacing), which MySQL's `JSON` output also matches, so MySQL's `JSON` maps to `jsonb`. `jsonb`
compares, hashes and is keyed in indexes by that text with every number's trailing zeros
removed, so `=`, `GROUP BY`, `DISTINCT` and unique indexes agree that `1.0` and `1` are equal
(as PostgreSQL's jsonb equality says) while the stored value keeps `1.0`. A `numeric` that is
exactly a `double precision` hashes as that double, so the two types group together where they
compare equal; the rest of mixed numeric and double grouping waits for static result types.
A row's `json` and `jsonb` text is parsed again when the row is read, so a damaged value is
`XX001` rather than text the JSON operators would trip on later. Normalizing may not grow a value past 16 times its
text plus 1 MiB (`1e999` written out), which bounds what a tiny input can allocate. Operators
parse the stored text on use; a binary jsonb layout can come with item 36 without changing what
users see. `json` has no equality and cannot be indexed, as in PostgreSQL.

**serial** and identity columns reuse the table's auto-increment column (D106): `serial`,
`bigserial` and `smallserial` are `integer`, `bigint` and `smallint` columns that are `NOT NULL`
and auto-increment; `GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY` marks an integer column the same
way. The column must be the first column of the primary key until named sequences (item 32).

**File format**: a table definition with a column of a new type is written in a new version 4
(type tags 9 to 14, the numeric precision and scale and the time stamps' fractional digits after
the tag, and the count of indexes always present); every other table keeps its version and its
exact bytes, and the D96 sample files are untouched. An older release refuses a version 4 table
by name. Rows keep format 1 with new value tags; every decoded value is checked against its
type's range and limits, so hostile bytes are damage (`XX001`), never a panic or an allocation
beyond the row. Index keys of the new types are order-preserving: dates and time stamps as
sign-flipped big-endian integers, `jsonb` as text, and `numeric` as a class byte, a 16-bit
decimal exponent and the significant digits, inverted for negatives, so trailing zeros and `-0`
share one key; the key bytes of the existing types do not change.

Judgement calls, made without asking (CLAUDE.md, "Questions"): the 1,000-digit bounds; the
256-level JSON nesting limit; the jsonb growth bound; named time zones acting as UTC; `now()`
per statement rather than per transaction; MySQL's and Oracle's constants staying doubles;
`GENERATED ALWAYS` accepting given values like `BY DEFAULT` (the format has no flag for it yet).

Note (D126, item 42): Oracle's decimal constants are now exact `numeric`, as PostgreSQL's are; MySQL's and SQLite's stay doubles.
