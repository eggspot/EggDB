## D771 End-user sign-in for applications (eggdb_app_auth) — Decided by the code-only session (2026-11-12, D355); roadmap M6a, end-user sign-in for apps (D37)

- **Building blocks in SQL.** `eggdb_password_hash` (PBKDF2-HMAC-SHA256, 600,000 rounds, OWASP's current advice for
  PBKDF2, 16-byte random salt, stored as `pbkdf2-sha256$rounds$salt$hash`) and `eggdb_password_verify` (constant-time,
  rounds bounded so a stored value cannot make a check run for hours); `eggdb_jwt_sign(claims, key)` signs ES256 with a
  32-byte P-256 private key (RFC 6979 nonces, `kid` the RFC 7638 thumbprint); `eggdb_jwt_public_jwk(key)`; and
  `eggdb_jwt_verify(token, jwks, issuer, audience)`, the same check the listeners use (RS256, RS384, RS512, PS256,
  ES256; `exp`, `nbf`, `iss`, `aud`; 60 seconds of leeway), returning the claims or failing with 28000.
- **`CREATE EXTENSION eggdb_app_auth`** keeps users, OIDC providers and linked identities, magic links (only the
  SHA-256 of each secret, single use, 15 minutes), sessions, failed attempts and signing keys. Sign-in by password
  (NULL on failure, and after 5 failures in 15 minutes per address, so callers can't tell a wrong password from a
  lockout), by magic link (creates the user on first use and confirms the address), and by OIDC ID token from any
  provider whose issuer, audience and JWKS are stored; a provider's verified e-mail links to an existing user only
  when the provider row allows it, since some providers let users set unverified addresses.
- **JWT sessions mapped onto row-level security.** Every session token's `sub` is one application role (D458's REST
  API runs requests as the claim's role), and it carries `user_id`, `email`, `sid` and `amr`. The REST API now sets
  `request.jwt.claims` to the verified token's claims for each request, as PostgREST does, and
  `eggdb_app_auth.current_user_id()` reads them, checking the session is neither signed out nor expired, so policies
  say `owner_id = eggdb_app_auth.current_user_id()`.
- The private signing key lives in `eggdb_app_auth.signing_keys`, readable only by its owner; sealing it with
  `eggdb_secrets` (D751) is left. Fetching provider key sets over HTTPS, the OAuth authorization-code redirect flow,
  sending the magic-link mail (the application or `eggdb serve`'s mail delivery, D747, does it), and WebAuthn (its own
  roadmap item) are left.
