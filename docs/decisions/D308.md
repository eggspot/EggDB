## D308 SQLAlchemy's dialect suite runs with the schemas its instructions ask for and to its end, and materialized views are found without a failing statement — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); refines D163

On `main` the `sqlalchemy-suite` job counted 96 passed, 13 failed and 237 errors, and stopped
there: SQLAlchemy's `pyproject.toml` passes `--maxfail=250`. All 237 errors were the setup of
`ComponentReflectionTest`, which creates tables in `test_schema`. SQLAlchemy's
`README.unittests.rst` asks every test database for two schemas, `test_schema` and
`test_schema_2`, and our provisioning made neither. With them made, the same setup failed again,
on EggDB: `CREATE MATERIALIZED VIEW` inside a transaction block answered `25P02`.

- **Suite setup.** `scripts/sqlalchemy-suite/eggdb_provision.py` creates `test_schema` and
  `test_schema_2` (`CREATE SCHEMA IF NOT EXISTS`) before the extensions, in the same
  `post_configure_engine` hook. This is what SQLAlchemy documents for PostgreSQL, not an EggDB
  workaround.
- **The whole suite runs.** `check.sh` passes `--maxfail=0`, so the pass count no longer depends
  on where the 250th failure falls, and a fix that turns errors into passes always shows in the
  count. The committed minimum is raised to 96, the count `main` measured; the coordinator raises
  it to what CI measures with this change.
- **Materialized views in a transaction block.** `Session::materialized_view_query` looked a
  name up with a `SELECT` on `eggdb_internal.materialized_views` and treated "no such table" as
  "not a materialized view". Inside a PostgreSQL block that failed statement aborted the block,
  so the first `CREATE MATERIALIZED VIEW` of a database could never run in one. It now checks
  that the registry table exists (one key read through the block's own reader) before querying
  it, so no statement fails.
- **Materialized views in any schema.** The view's table name was quoted by splitting on `.`,
  so a schema-qualified name (held with the internal qualifier) became one quoted identifier
  with the qualifier inside, which the parser refuses. It is split on the qualifier now. The
  registry keeps a view of the default schema under its plain name, as before, so existing
  registries read unchanged, and a view of another schema under its double-quoted parts
  (`"reports"."daily"`, with any `"` doubled), so no stored text holds the qualifier and a
  public view named `"reports.daily"` never shares a key with `reports.daily`. A default-schema
  name that itself starts with `"` is quoted the same way, which keeps every key unambiguous.

Not done here, each a next step for the suite: `relkind` `m` for materialized views in
`pg_class`, `nextval` of a `SERIAL` column's sequence (refused today for identity-owned
sequences), generated columns, two identity columns in one table and identity
`MAXVALUE`/`MINVALUE`/`CYCLE`, zero-column tables, the requested isolation level in `SHOW
transaction_isolation` (EggDB reports `serializable`, what it runs), psycopg's named cursors, a
bound frame offset and multidimensional arrays. `LIKE ... ESCAPE`, `FETCH FIRST` and
`UPDATE ... FROM`, which the suite also sends, come with D299, D300 and D297.
