## D695 SQL Server xml columns and their value(), query() and exist() methods — Decided by the code-only session (2026-11-12, D355); roadmap M10, SQL Server's `xml` type (D19)

- SQL Server's untyped `xml` type is accepted for columns, variables and casts, stored as text (as `text`, `ntext` and
  `nvarchar(max)` are), named `xml` in the catalog views (`system_type_id` 241) and converted like the character
  types. Typed `xml(schema_collection)` stays refused (40517).
- The `xml` methods are read where a column (`doc.value(...)`) or a qualified column (`o.doc.value(...)`) is
  followed by `.value`, `.query` or `.exist` and a parenthesis, and are evaluated with D690's XPath 1.0:
  - `value('path', 'type')`: the string value of the first node selected (or the string, number or boolean result),
    cast to the SQL Server type written in the second argument, which is parsed with the dialect's type grammar;
  - `query('path')`: the selected nodes serialized, as `XMLQUERY` (D693);
  - `exist('path')`: 1 when the path selects something, else 0 (and `NULL` for a `NULL` document).
- A two-part call whose qualifier is `dbo` stays a call of the user function in `dbo`; any other two-part
  `name.value(...)`, `name.query(...)` or `name.exist(...)` is read as an `xml` method on the column `name`, so a user
  function named `value`, `query` or `exist` must be called through `dbo.` or a schema other than a column's name.
- Left out: XQuery beyond XPath 1.0 (FLWOR, `sql:column()`, `sql:variable()`, namespace declarations), `.modify()`,
  `.nodes()` with `CROSS APPLY`, and SQL Server's `[1]`-singleton check in `value()` (the first node is taken).
