## D327 `EXPLAIN` draws a `SELECT`'s subqueries as PostgreSQL's `InitPlan` and `SubPlan` nodes with their loops under `ANALYZE`, and MySQL's dialect answers `EXPLAIN FORMAT=TREE` and `EXPLAIN ANALYZE` with MySQL 8's iterator tree — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M6c, extends D312, D286 and D109, applies D25, D10 and D12

Before this, `EXPLAIN` of a `SELECT` with a subquery answered `0A000` in every dialect, and
MySQL's dialect had only the tabular `EXPLAIN` (D109): `EXPLAIN ANALYZE` and `FORMAT=TREE` were
refused, so tools written for MySQL 8 (Workbench's visual explain, `pt-visual-explain`, the
manual's own examples) could not show a measured plan. The public references followed are
PostgreSQL 16's manual ("Using EXPLAIN", the `EXPLAIN` reference and its subplan examples) and
MySQL 8.0's reference manual ("EXPLAIN Statement", "Obtaining Information with EXPLAIN
ANALYZE").

- **Subqueries planned without running them.** `execute::explain_with_subplans` prepares the
  `SELECT` the way a run does (`subquery::prepare_for_explain`, the same `prepare_query` in its
  columns-only mode), so EggDB's own preparation decides which subqueries are correlated, and
  no subquery reads a row: an uncorrelated one gives only its columns. Each subquery found in
  the select list, `WHERE`, `HAVING`, `JOIN ... ON`, `GROUP BY`, `ORDER BY`, `LIMIT` and
  `OFFSET` (in that order, the order preparation walks them) becomes a `Subplan` with its own
  explained plan, recursively. A correlated subquery is explained from its prepared template,
  whose outer references are resolved, without the `LIMIT 1` or `LIMIT 2` the engine adds to
  an `EXISTS` or scalar subquery. Oracle's `EXPLAIN PLAN`, SQL Server's showplans, SQLite's
  `EXPLAIN QUERY PLAN` and MySQL's tabular `EXPLAIN` keep `execute::explain`, which still
  refuses subqueries, so none of them shows a plan that leaves a subquery out.
- **PostgreSQL's names and numbers.** An uncorrelated scalar, `EXISTS` or `ARRAY` subquery is
  an `InitPlan n (returns $k)` and is named `$k` where it is used: EggDB runs it once before the
  statement's rows, as PostgreSQL's init plans run. An uncorrelated `IN`, `= ANY` or `<> ALL`
  is `(hashed SubPlan n)` (`NOT` around it for `NOT IN` and `<> ALL`): EggDB builds the set once
  and probes a hash of it from 8 values. Everything else, and every correlated subquery, is
  `(SubPlan n)`, evaluated per outer row. An uncorrelated row comparison `(a, b) = (SELECT
  ...)` is an `InitPlan n (returns $0,$1)` with one parameter per column, used as
  `((a = $0) AND (b = $1))` (`OR` of `<>` for `<>`, `ROW(...)` for the ordering operators). Plans
  are numbered as PostgreSQL's planner numbers them: the select list with `ORDER BY`, `GROUP BY`
  and `DISTINCT ON`, then `JOIN ... ON`, then `WHERE`, then `HAVING`, then `LIMIT` and `OFFSET`,
  a nested subquery before the one holding it, and parameters in the order the init plans are
  made. A `LIMIT` or `OFFSET` holding a subquery keeps its `Limit` node. The plans hang under the step that evaluates the `SELECT`'s rows (the scan, the top
  of a join or `Result`, below `Sort` and `Limit`): init plans after that step's `Filter:` line
  and before its children, sub plans after its children, each label at the step's property
  column and its plan's top node two columns further in, as PostgreSQL indents them.
- **`Filter:` only where a subplan is named.** EggDB's `EXPLAIN` prints no conditions (D109).
  The step that uses a subplan in its `WHERE` now prints the whole `WHERE` as a `Filter:` line in
  PostgreSQL's spelling (`(ten < $0)`, `((unique1 > 100) AND (SubPlan 1))`, bare column names
  over one table), since that line is what ties a node to its subplan. Other steps are
  unchanged, byte for byte.
- **Loops under `ANALYZE`.** `step_times::measure_subplan` wraps each run of a subquery: the
  uncorrelated run during preparation and every `Correlation::rows` call (a run answered from
  the statement's memo or its key lookup included, as each is one evaluation). Under a
  recording it adds the run's rows and time to the subquery's entry, keyed by its position in
  the statement text, and holds the select meter for the run, so a subquery's `SELECT`, which
  now runs before the statement's own, never takes the measurement meant for the statement's
  top select. The subplan's top node prints `(actual time=t..t rows=r loops=n)` with `t` and `r`
  per run (total over `loops`, rows rounded to the nearest whole row as PostgreSQL's `%.0f`
  prints them) and `(never executed)` when it never ran. A correlated subquery's key lookup
  (built once over every inner row) runs with the meter held and counts no loop.
  Outside `EXPLAIN ANALYZE` the cost is one thread-local lookup per run.
- **MySQL's tree.** In MySQL's dialect `EXPLAIN FORMAT=TREE SELECT ...`, `EXPLAIN ANALYZE
  SELECT ...` and `EXPLAIN ANALYZE FORMAT=TREE SELECT ...` (`FORMAT = TREE` with spaces too)
  answer one row in one text column named `EXPLAIN`, holding the tree with a newline after each
  line, as MySQL 8 does. Each iterator is `-> ` indented four spaces per level, named as MySQL
  names it: `Table scan on <alias>`; `Single-row index lookup on t using PRIMARY (id=2)` for a
  point lookup or a join through the primary key, the values taken from the `WHERE` and `ON`
  equalities; `Index lookup on t using k (a=1)`; `Index range scan on t using k` and `Index
  scan on t using k`, `(reverse)` when read backward; `Filter: (t1.a > 1)` above the source
  unless a single key lookup consumes the whole `WHERE`; `Sort: t1.b DESC` (`, limit input to n
  row(s) per chunk` under a limit); `Limit: n row(s)` or `Limit/Offset: n/m row(s)`; `Nested
  loop inner join`; `Inner hash join (t1.a = t2.c2)` over `Hash`; `Append`; `Rows fetched
  before execution` for a query without a table; and `Select #n (subquery in condition|projection;
  run only once|dependent)` over each subquery's plan, numbered `#2` on in the order the
  subqueries appear in the text. Expressions are printed in MySQL's style (`t1.a`, lowercase
  `and`, `or`, `not`, `in`, `exists(select #2)`). `ANALYZE` runs the `SELECT` and adds MySQL's
  `  (actual time=a..b rows=n loops=n)` (no `(cost=...)` group: the planner has no estimates;
  a table scan under a `Filter:` carries none, as EggDB counts the rows that pass the filter,
  not the rows read)
  to the iterators PostgreSQL's form measures (D312), the `Filter` taking its source's, and to
  each subquery's top iterator. `FORMAT=TRADITIONAL` is the tabular form of D109;
  `FORMAT=JSON` and a tree or `ANALYZE` of an `UPDATE` or `DELETE` answer `0A000`.
- **Where it shows.** `eggdb explain` and MCP's `explain_query` prefix the statement with
  `EXPLAIN`, so both show the subplans in PostgreSQL's dialect, and the desktop client's plan
  view reads the new lines with its existing parser (D277): the label is an extra line of the
  step that uses it and the subplan's nodes become that step's children.
- **Bounded and panic-free.** Expression text stops at 32 levels with `...`; every list access
  is checked; the subplan tree is as deep as the statement's subqueries, which nest at most 32
  levels.

Decided by research:
- **PostgreSQL 16's text form, not 17's.** PostgreSQL 17 renamed `$0` to `(InitPlan 1).col1`
  and dropped `(returns $0)`; the batch asked for `InitPlan n (returns $0)`, the form 16 and
  earlier print and that existing tools parse, so that is the form used.
- **`hashed` for every uncorrelated `IN`.** EggDB hashes the set only from 8 values and compares
  a shorter one value by value; the plan does not change with the row count, so `EXPLAIN` and
  `EXPLAIN ANALYZE` print the same tree.
- **MySQL's tree for `SELECT` only.** MySQL 8 refuses `EXPLAIN ANALYZE` of single-table
  `UPDATE` and `DELETE` (`ER_NOT_SUPPORTED_YET`), so EggDB refuses it rather than running the
  write.
- **SQLite left for now.** SQLite has no `EXPLAIN ANALYZE`; its shell's `.scanstats on` prints
  per-loop counts after each statement. `eggdb sql`'s shell has dot-commands (`.timer`,
  `.mode`), but `.scanstats` needs a session switch that runs each SQLite `SELECT` under the
  step recording and hands the shell SQLite-shaped `QUERY PLAN` lines with `loops=` and `rows=`
  per `SCAN`/`SEARCH`, which is its own slice.

Left: `.scanstats on|off` in `eggdb sql`'s shell for SQLite's dialect (a `Session` switch that
records each `SELECT`'s steps and returns `QUERY PLAN` / `` `--SCAN t (loops=1 rows=3) `` lines,

(EggDB prints no join conditions); the rows a table scan reads before its `Filter:` in MySQL's
tree; `Filter:` and `Index Cond:` lines on steps without subplans;
PostgreSQL's `One-Time Filter` `Result` node for an uncorrelated `EXISTS` and its
`(alternatives: SubPlan 1 or hashed SubPlan 2)`; subqueries in `UPDATE` and `DELETE`, in
derived tables, `WITH` queries and set operations, and in Oracle's, SQL Server's, SQLite's and
MySQL's tabular plans; times on each iterator inside a subplan (only its top one is measured);
MySQL's `(cost=... rows=...)` estimates, `Aggregate`, `Group` and `Stream results` iterators,
`FORMAT=JSON`, and `EXPLAIN ANALYZE` of `UPDATE`, `DELETE` and `TABLE` statements.
