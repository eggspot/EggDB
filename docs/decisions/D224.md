## D224 The release publishes a multi-architecture image to GHCR; one template per cloud — Decided by the build loop (by judgement, 2026-10-31); refines D8 and D14

Part 4.M17-5 asks for `docker run ghcr.io/eggspot/eggdb` and documented AWS, Azure and Google
Cloud templates.

- **The image is the release's static binary**, as `deploy/Dockerfile` already builds it (FROM
  scratch, an unprivileged user, nothing else). The release workflow's new `image` job takes the
  `x86_64` and `aarch64` musl builds it just published, builds one image per architecture
  without emulation (the Dockerfile only copies), pushes both, joins them under the version and
  `latest`, and runs the published image's `--version`. It signs in with the workflow's own
  `GITHUB_TOKEN` (`packages: write`), so no new account or token is needed. A new GHCR package
  starts private: the owner makes it public once, in the package's settings.
- **The Helm chart defaults to that image**; the kind test in CI sets its locally built one.
- **One template per cloud, each the simplest durable shape there**: on AWS, a CloudFormation
  stack with one EC2 instance and an EBS volume kept when the instance is deleted; on Azure, a
  Bicep file with a Container Instance and an Azure Files share; on Google Cloud, a script that
  installs the same Helm chart on GKE Autopilot, so the CI-tested chart is what runs there. No
  Terraform, whose licence is no longer open source. Passwords come from each cloud's secret
  store (Secrets Manager, a secure parameter, Secret Manager), never from the template's text.
  CI lints all three.

Left: Azure Files over SMB is slower than a disk and its locking is not a local file system's,
so a managed disk on a VM may suit heavy writes better; ECS, Azure Kubernetes Service and
private networking variants; image signing with provenance attestations; an operator; and
measuring the image's size and pull time per release (D14).
