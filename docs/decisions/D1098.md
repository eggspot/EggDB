## D1098 Multi-primary SQL rows: hybrid-clock change logs, pulled over PostgreSQL's protocol, settled by a rule per table — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D18, D210, D225)

- **Where it lives.** `CREATE EXTENSION eggdb_multi_primary`, a SQL script with PL/pgSQL functions like `eggdb_cdc` (D210), so the rules, the log and the stamps are tables any SQL client can read and the logic runs inside the transaction that writes the row. A Rust apply path would have duplicated the SQL layer's index, constraint and trigger handling, which applying through SQL gets for free.
- **Capture.** `eggdb_mp.enable(schema, table, rule, resolver, counters)` reads the table's primary key from `information_schema` and puts an `AFTER` row trigger on it. Each local change gets a hybrid logical clock stamp (`eggdb_mp.tick`: 15-digit milliseconds, 6-digit counter, server name, so stamps compare as text), an entry in `eggdb_mp.log` with the row before and after as JSON, and the row's stamp in `eggdb_mp.stamps`. While `eggdb_mp.apply` runs it sets the transaction-local setting `eggdb_mp.applying`, and the trigger skips changes made under it, so applied changes are never logged again and never echo back.
- **Rules.** `lww`: the newer stamp wins, deletions included. `crdt`: the named counter columns add the remote change's delta (after minus before) to the local value whatever the stamps, so concurrent increments both count, and the other columns follow the newer stamp. `function`: a user function `(local jsonb, remote jsonb, local_stamp text, remote_stamp text) RETURNS jsonb` returns the row to keep or `NULL` to delete. It runs only when the row was also changed here; otherwise the change applies as it is. The kept stamp is the larger of the two, and applying a remote stamp advances the local clock, so later local writes order after it.
- **Transport.** `eggdb serve --multi-primary name=postgresql://...` and `--multi-primary-node` pull each peer's log each second through the in-house PostgreSQL client (`eggdb-pgwire`), using the server's own password unless the URL gives another, and TLS per `sslmode`. A batch of up to 500 changes and the peer's cursor are applied in one local transaction, so a crash re-pulls rather than loses or doubles a batch. Every server pulls from every other (full mesh), which needs no relaying.
- **Limits, stated in docs/multi-primary.md.** Primary keys are required, and a primary key change counts as a delete and an insert. Unique constraints other than the key are not reconciled across servers. The log is never pruned yet (left: prune entries every peer's cursor has passed).
