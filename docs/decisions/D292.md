## D292 Collections are renamed in one commit (`eggdb collection move`, alias `rename`), counted by `eggdb stats --collections`, read by MCP's `kv_get` and `kv_scan` through a `collection` argument, and dropped in steps behind a `0x06` mark — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap item 26, applies D2, D6, D9, D11, D20, D139 and D143; superseded in part by D320

D139 left four things out of collections: renaming one, per-collection counts in `stats`,
collections in the MCP server's key-value tools, and dropping a collection larger than the page
cache, which deleted every key in one transaction and failed with `CacheFull`.

- **Rename.** `WriteTransaction::rename_collection(name, new_name)` and
  `Database::rename_collection` move the name record (`0x02` + name) to the new name with the
  same number, so the keys, their times to live and every snapshot stay as they are, and the
  change is one commit of two keys whatever the size. A missing collection is
  `CollectionNotFound`; a new name that a collection already has, `name` itself included, is
  `AlreadyExists` (D139's kind for "never replaces"), and nothing changes.
- **The command is `eggdb collection move <file> <name> <new-name>`, with `rename` as an
  alias.** *Decided by research:* the noun-verb commands take only the core verbs, which EggDB
  shares with EggOS (D143), and EggOS owns that list. `move` ("an item moved") already covers a
  rename, as `mv` does. `rename` is an alias, as `del` is of `delete`. Output is
  `{"file","collection","new_name","moved"}`. A missing collection exits 1 (`nothing to rename`)
  and a taken name exits 3 with `already_exists`.
- **Counts.** `Database::collection_stats` and `ReadTransaction::collection_stats` return one
  `CollectionStats` per collection, in name order. Each holds `name`, `entries`, `key_bytes`
  (the collection's own keys) and `value_bytes`, read by scanning the collection, so expired keys
  are left out. *Decided by research:* `eggdb stats` keeps its promise to read no page.
  `--collections` adds the count, with `"collections":[{"name","entries","key_bytes","value_bytes"}]`
  in JSON. Plain `stats` output is byte for byte what it was. `entries` is `check`'s word for the
  same thing. Stored counters were left out: they would change the format and cost something on
  every write (D6).
- **MCP.** `kv_get` and `kv_scan` take an optional `collection`. Without it they read the
  default key space as before. With it they read that collection, and the result carries
  `collection`. A collection that is not there fails with `collection_not_found`, and the message
  lists up to 20 of the collections that are. The tools stay withdrawn under `--tables` and
  for an agent signed in with a role on `eggdb serve`'s MCP endpoint, with or without `collection`: collections are keys, and only a session with the
  key-value grant reads keys (D11). The engine reaches the tools through four default methods on
  `eggdb_sql::KeyValueRead`: `collection_names`, `has_collection`, `collection_get` and
  `collection_scan`. A store without collections answers "none". EggDB's snapshot answers from
  `ReadTransaction::collection`. The MCP call wrapper checks the call's time limit on each one.
- **Dropping in steps.** A drop deletes the name record and writes a mark, `0x06` + the
  collection's 4-byte number. The mark's value is a version byte (1) and the last name. From that
  commit on, no read sees the collection, and its name is free; a new collection of that name
  gets a new number, so it starts empty. The same transaction removes up to 512 of the keys.
  Every later commit removes up to 32 more, as the expiry sweep does (D140).
  `Database::drop_collection` commits the first step, then removes the rest in commits of up to
  512 keys. `Database::finish_collection_drops` does the same for every mark, for example after a
  crash. Each step's keys go with their deadline records, and the mark goes with the last key.
  - *Why steps.* No commit changes more than about 512 keys' pages, so a collection of millions
    of keys drops within the default page cache. Each step is an ordinary commit, so read
    transactions keep their snapshots and are never blocked.
  - *Why a mark rather than a rename.* `0x06` is the next free tag under the collections prefix
    (`0x04` and `0x05` are expiry's).
  - *The writer's cost.* The database remembers whether a mark may exist: unknown at open, set by
    a drop, cleared when a commit finds none. So a database with no unfinished drop pays one
    lookup, at its first commit after opening.
- **File format: additive.** The mark lives in the reserved prefix, which the default key space
  already hides and refuses. There is no feature flag and no new record anywhere else. A file
  without collections, or one written before D292, holds no mark and opens and behaves as before.
  A release before D292 ignores a mark and the keys left behind, which no read can reach,
  because numbers are never reused. format.md's table lists the mark.
  `a_v0_2_0_file_drops_a_collection_in_steps_across_a_reopen_and_renames_one` checks this on the
  frozen v0.2.0 sample.

**Tests.**
- Unit tests of the mark's key layout and damaged marks.
- API tests:
  - a rename that keeps keys and times to live, keeps a snapshot's view, and is refused for a
    taken name, the same name, a missing collection and a bad name;
  - 20,000 keys dropped within a 1 MiB cache, which the one-transaction drop could not do;
  - a drop left after its first step: invisible, recreated empty under the same name, its
    remaining keys removed 32 per commit and finished after a reopen, with the deadline records
    of its keys;
  - `collection_stats`.
- The v0.2.0 sample test.
- In-crate MCP tests: an unknown collection, and the grants refusing collections under
  `--tables` and agent roles.
- An end-to-end MCP test through the binary.
- A binary CLI test of `move`, `rename`, `stats --collections` and a stepped delete.
- Parser tests, and smoke-test steps.
