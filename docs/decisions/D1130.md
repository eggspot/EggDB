## D1130 The savepoint undo log bounded as a whole — Decided by the code-only session (2026-11-14, D355); roadmap M3 (D266, D307, D317, D319)

- **The gap.** Each statement's before-images stopped at 1 GiB of work memory (`53200`, D317). But after a
  `SAVEPOINT` the log keeps every statement's entries until `RELEASE`, `ROLLBACK TO` or the transaction's end, so a
  long block of statements, each under the limit, could grow the log without bound.
- **The bound.** The undo log is now a type of its own that keeps its byte count as entries are pushed and popped:
  each key, its earlier value and 64 bytes of overhead, the same measure statements charge. A write that would take
  the whole log past 1 GiB (the work-memory limit, `WORK_MEMORY_LIMIT`) while a savepoint keeps it fails with
  `53200`. The message names the limit and the hint says to release savepoints or commit in smaller transactions.
  The statement fails as any statement does, so its own entries are undone and the block goes on (or is aborted,
  per dialect, as before).
- Host entries recorded for embedded and shell key-value writes (D319) count too.
- **Left:** spilling the log to a temporary area of the file instead of failing, which needs the dirty-page spill of
  M2 (D86, D167) to have somewhere to put it.

**Status:** code written, unbuilt (code-only mode, D355).
