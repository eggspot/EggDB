## D1193 Tables made by roles that hold `CREATE` on a schema, and dropped or changed by their owners — Decided by the code-only session (2026-11-17, D355); roadmap M6b (D183); security-critical (D35)

- **What users get.** A role that holds `CREATE` on a schema (`GRANT CREATE ON SCHEMA public TO app`, stored by D1190), directly or through a role it belongs to, may `CREATE TABLE` there and becomes the new table's owner (D1192), so it reads, writes, alters, grants on and drops it. A table's owner may `ALTER TABLE` it (but not give it away: `OWNER TO` stays a superuser's) and `DROP TABLE` it. Everything else that defines objects stays a superuser's, as before (D827).
- **How.** `roles::defines_objects` names the statements that define objects; for a session whose role is checked the session asks `roles::may_define_as` first, from a read of the committed store, and only when it says no does the old refusal (`42501 permission denied for schema public`) apply. The table's owner is written in the same write as the table, unless it is temporary.
- **Limits.** The check reads committed state, so inside one transaction a role cannot yet alter or drop a table it created in that transaction; unqualified names are checked against `public`, not the search path; indexes, views, sequences and the other objects keep needing a superuser. SQL Server sessions and statements inside routines and triggers keep the old check.
- **Proof.** A unit test grants `CREATE` on `public` to a group, makes, fills, alters, reads and drops a table as a member, and is refused giving it away and dropping a table it does not own.
- **Security review.** As a D35 change it needs a security-only review pass once built, with D1192's.

**Status:** code written, unbuilt (code-only mode, D355).
