## D605 TOP in Transact-SQL UPDATE and DELETE — Decided by the code-only session (2026-11-12, D355); roadmap M10, D300, D303

`UPDATE TOP (n)` and `DELETE TOP (n)` are how SQL Server applications work through a table in
batches: queue tables, purges in chunks of 5,000 to keep the log small, Hangfire and other job
stores. EggDB refused them, because `Update` and `Delete` had no row limit.

- The Transact-SQL parser reads `TOP (expression)` after `UPDATE` or `DELETE`, then parses the
  rest of the statement with the ordinary parser. It wraps the result in a new
  `SqlServerStatement::TopRows { count, statement }`, so the shared `Update` and `Delete` keep
  their shape.
  - `TOP … PERCENT` there is refused as not supported. `TOP` in `INSERT` stays refused.
- When the session runs the wrapper, it evaluates the count as a constant (`row_count`, as
  `LIMIT` does; NULL means no limit and a negative count is an error). It then runs the inner
  statement under a thread-local row limit (`dml_row_limit`).
  - The update and delete paths take the limit as they start and clear it, so the triggers and
    cascades they run are not limited.
  - The update loop stops after that many rows have passed its `WHERE`. The delete keeps the first
    that many matched rows.
  - SQL Server picks which rows `TOP` takes without an order. EggDB takes them in key order.
- `TOP` with `FROM` (a joined update or delete), on a view, or on a partitioned table is refused as
  not supported, since those paths do not read the limit.
- The wrapper is classified, refused in functions, and kept from the SQL Server statement runner
  in the same places as `OUTPUT … INTO`.

Not done: `TOP … PERCENT` in DML, and `INSERT TOP (n)`.
