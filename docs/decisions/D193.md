## D193 The RESP protocol and Redis-compatible data types: our own server over EggDB collections, from the public protocol and command documentation — Decided by the build loop (by judgement, 2026-10-31); refines D2 and D5

Part 4.M7-1 asks for `redis-cli` and Redis clients to work against `eggdb serve --resp-listen`
with strings, hashes, lists, sets and sorted sets, expiry, RESP2/RESP3 and AUTH.

- **Clean room.** `eggdb-resp` is written from the published RESP specification and the
  public command reference (behaviour, replies and error texts); no Redis source is read, and
  none is used (its newer releases are source-available, D1). "Redis" is a trademark; EggDB is
  compatible with its protocol. CI uses `redis-cli` from Ubuntu's package and the `redis-py`
  client as test tools only.
- **One engine.** Each RESP database (0 to 15) is an EggDB collection `resp<n>` in the same file
  as the SQL tables and the key-value API, and every command runs in one read or one write
  transaction of the engine (`eggdb_resp::Keyspace`), so commands are atomic and durable like
  every other write. A key's value is one record: a format byte, its type, its expiry time and
  its encoded value (hash fields, list items, set members and sorted-set members with scores),
  so `TYPE`, `WRONGTYPE` and expiry are exact; expired keys read as missing.
- **Commands** in this first slice: connection (`PING`, `ECHO`, `AUTH`, `HELLO 2|3` with `AUTH`
  and `SETNAME`, `SELECT`, `CLIENT`, `QUIT`, `INFO`, `COMMAND`), keys (`DEL`, `UNLINK`, `EXISTS`,
  `TYPE`, `EXPIRE` and its forms, `TTL`, `PTTL`, `PERSIST`, `RENAME`, `RENAMENX`, `KEYS`, `SCAN`
  with `MATCH`, `COUNT`, `TYPE`, `DBSIZE`, `FLUSHDB`, `FLUSHALL`), strings (`GET`, `SET` with
  `EX`/`PX`/`EXAT`/`PXAT`/`NX`/`XX`/`KEEPTTL`/`GET`, `SETNX`, `SETEX`, `PSETEX`, `MGET`, `MSET`,
  the `INCR`/`DECR` family, `INCRBYFLOAT`, `APPEND`, `STRLEN`, `GETRANGE`, `GETSET`, `GETDEL`),
  hashes, lists, sets and sorted sets (the common commands, `ZADD` with `NX`/`XX`/`CH`/`INCR`,
  `ZRANGE` with `WITHSCORES`/`REV`, `ZRANGEBYSCORE`, `ZCOUNT`).
- **AUTH** checks the server's password; only its SHA-256 is kept. The listener binds only to
  loopback until it has TLS.

Part 4.M7-2 adds, in the same crate: **transactions** (`MULTI`, `EXEC`, `DISCARD`, `WATCH`,
`UNWATCH`; `EXEC` runs every queued command inside one write transaction of the engine, and
returns the null array when a watched key's stored bytes changed since `WATCH`), **pub/sub**
(`PUBLISH`, `SUBSCRIBE`, `PSUBSCRIBE` and their `UN` forms through a hub per server; messages
reach subscribers as pushes, RESP3's `>` or RESP2 arrays, at most 10,000 waiting per
subscriber, with RESP2's subscribed-mode rule), and **streams** (`XADD` with `*` or explicit IDs,
`NOMKSTREAM` and `MAXLEN`, `XLEN`, `XRANGE`, `XREVRANGE` with exclusive bounds and `COUNT`,
`XDEL`, `XTRIM MAXLEN`, `XREAD` without `BLOCK`). Scripting (`EVAL`) needs a Lua-compatible
interpreter of our own and is left with consumer groups, `XREAD BLOCK` and sharded pub/sub.

Left: per-element storage for large aggregates (each change rewrites the value today), ACL users,
TLS, pub/sub, streams, transactions (`MULTI`/`EXEC`), scripting (4.M7-2), eviction (4.M7-3),
blocking commands, `OBJECT`/`DEBUG`, cluster commands, keyspace notifications, and the
remaining commands, tracked per command in compatibility.md as they land.
