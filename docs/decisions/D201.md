## D201 Columnar encodings in their own crate, shared by columnar tables, Parquet and Arrow — Decided by the build loop (by judgement, 2026-10-31); refines D2 and D40

Part 4.M11-1 asks for columnar tables with per-column compression and vectorized analytics.

- **`eggdb-columnar` first.** The encodings a column chunk uses (bit packing, the
  run-length/bit-packed hybrid from Parquet's public specification, zigzag varint deltas,
  dictionaries) and the chunk format (encoding, min, max, sum, count, data) live in a crate
  with no engine dependency, so columnar table storage, the Parquet reader and writer
  (4.M11-3) and Arrow share one tested implementation.
- **The smallest encoding wins per chunk**, at most 2^24 values each; statistics travel with
  the chunk and are checked when it is read, so aggregates and filters answer whole chunks
  from statistics (`sum_at_least` shows the pattern) and damaged chunks are errors.
- **Not yet a table format.** `USING columnar` is not accepted until tables can be stored as
  chunks; accepting it while storing rows would promise what is not there.

Left: columnar table storage in `eggdb-storage` (row groups of chunks, deletes as bitmaps,
updates as delete plus insert), `CREATE TABLE ... USING columnar`, a vectorized executor over
chunks, float and string chunks, compression beyond encodings, and ClickBench-style queries
against DuckDB and ClickHouse in the compare job.
