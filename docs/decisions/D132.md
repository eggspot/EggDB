## D132 .NET and Java apps over TDS: RPC calls of the system procedures with parameters bound by name as typed values, prepared handles per connection, transaction manager requests as Transact-SQL, connection resets, and the implicit transactions and `IF` mssql-jdbc sends — Decided by the build loop (by research, 2026-10-29); roadmap item 23b, supersedes in part D122 (RPC and transaction manager requests, the reset bits), applies D1, D5, D9, D10, D12, D102, D122, D123

Item 23b makes Microsoft.Data.SqlClient and Microsoft's JDBC driver (mssql-jdbc) run apps against
`eggdb serve --tds-listen`. Both send every parameterized statement as a remote procedure call
(RPC) of a system procedure, SqlClient begins and ends transactions with transaction manager
requests, and SqlClient's connection pool marks the first request on a reused connection with a
reset bit. D122 answered all three with error 40517 or ignored them; this decision replaces that
part of D122. Everything is written from Microsoft's public [MS-TDS] specification and the
drivers' documented behavior; the drivers' own sources (both MIT-licensed) were read only to see
which requests they send, never copied.

**RPC requests are read in `eggdb-tdswire`'s new public `rpc` module.** A request is its
ALL_HEADERS (read as for batches, one shared reader), then calls separated by the batch flag
(0xFF) or the NoExec flag (0xFE, whose next call is read and dropped). A call names its procedure
by a UTF-16 name or by 0xFFFF and an id; `sp_executesql` (10), `sp_prepare` (11), `sp_execute`
(12), `sp_prepexec` (13) and `sp_unprepare` (15) run, by id or by name (any case, bracketed, with
a schema or database before it). Every other procedure is error 2812, as SQL Server answers for
a procedure it does not have; server cursors (ids 1 to 9) are among them, since the drivers use
them only when an app asks for scrollable or updatable result sets. A call carries at most 2,100
parameters (error 8003). Each parameter's TYPE_INFO and value are decoded at once into an
`eggdb_sql::Value` of the engine type D123 maps the SQL Server type to; values outside their
type (a `time` past midnight, a date after 9999-12-31, an integer that does not fit its width,
a PLP value whose chunks do not add up) are protocol errors, as malformed batches are.
`varchar` values are decoded as Windows-1252, the code page of the Latin1 collation the server
reports, or as UTF-8 under a UTF-8 collation; `sql_variant`, `xml`, user-defined and
table-valued parameters, the pre-7.2 types and Always Encrypted parameters are answered with
error 40517 and the connection kept, since the request was read whole.

**Parameters are bound by name as typed values, not substituted into the text.** `eggdb-sql`
gains `Session::execute_parameterized_batch(text, &[NamedParameter])`: the batch runs with SQL
Server's batch rules, and the parser reads each `@name` that is not an `@@` name as the
parameter of that name, a constant of the value's own type cast to the declared type (NULL takes
the declared type). Substituting text would need every type's literal form and would reopen
quoting bugs; the PostgreSQL protocol's `$n` path binds text because PostgreSQL's wire sends text,
while TDS sends binary values with their types. `Session::parse_parameter_declarations` reads
`@params` (`@p1 int, @p2 nvarchar(40) OUTPUT`) with the dialect's own type parser (repeated names
error 134). The server binds each RPC argument to a declaration by name (SqlClient) or by
position (mssql-jdbc), with SQL Server's errors 8144, 8145, 8162 and 8178.

**Prepared handles live per connection in the server, not in the session.** `sp_prepare` and
`sp_prepexec` parse the declarations and check the batch's syntax with
`Session::check_parameterized_batch`, then keep the text and declarations under a handle
numbered from 1 per connection; `sp_execute` binds new values to them, `sp_unprepare` forgets
them, an unknown handle is error 8179 (which mssql-jdbc answers by preparing again), and
`sp_prepexec` given an old handle forgets it first, as mssql-jdbc expects. Handles are a TDS
concept, so the table is in `eggdb-tdswire` beside the connection, bounded to 65,536 handles and
64 MiB of text per connection (error 701 past that). They survive a connection reset: SqlClient
prepares again after a pooled connection is reopened, and mssql-jdbc may reuse a handle on a
pooled connection. mssql-jdbc's batched `EXEC sp_unprepare n;` text batches fail until `EXEC`
comes (items 41 and 47), which the driver ignores by design; the handles then live until the
connection closes.

**The response follows SQL Server's token order.** Each statement ends with DONEINPROC (with
DONE_MORE, its count unless `SET NOCOUNT ON`), then RETURNSTATUS 0, then a RETURNVALUE for the
prepared handle (ordinal 0) and for every parameter the client marked as output, then DONEPROC
(DONE_MORE unless it is the request's last call, DONE_ERROR when a statement failed,
DONE_INXACT inside a transaction). mssql-jdbc reads the handle only after RETURNSTATUS, so the
order matters. An output parameter comes back with the TYPE_INFO and value it was sent with,
since no statement can assign it before item 47; a call refused before it runs is ERROR then
DONEPROC with DONE_ERROR.

**Transaction manager requests run as Transact-SQL.** `TM_BEGIN_XACT` runs `BEGIN TRANSACTION`,
`TM_COMMIT_XACT` and `TM_ROLLBACK_XACT` run `COMMIT` and `ROLLBACK TRANSACTION` (followed by
`BEGIN TRANSACTION` when the request asks to begin the next one), through the same batch path,
so the ENVCHANGE 8, 9 and 10 tokens with the transaction descriptor come from the one place
batches already report them. The isolation level is accepted and every transaction runs
serializable, as `SET TRANSACTION ISOLATION LEVEL` already did. `TM_SAVE_XACT` and the
distributed requests are error 40517: the engine has no save points yet (`SAVE TRANSACTION` in a
batch is 40517 too). The transaction descriptor in ALL_HEADERS stays read and not enforced.

**The reset bits reset the session.** A SQL batch, RPC or transaction manager request whose first
packet has RESETCONNECTION (0x08) runs `Session::reset_connection(false)` first: an open
transaction rolls back, the `SET` options, `IDENTITY_INSERT`, `@@ROWCOUNT` and
`SCOPE_IDENTITY()` return to their state after login; RESETCONNECTIONSKIPTRAN (0x10) does the same
and keeps an open transaction. The response starts with ENVCHANGE 18 (reset acknowledged), as
[MS-TDS] 2.2.7.9 lists it. A transaction rolled back by a reset is not reported with ENVCHANGE 10,
since the client asked for it.

**mssql-jdbc's transactions need implicit transactions and `IF` (decided by research).**
mssql-jdbc never uses transaction manager requests: `setAutoCommit(false)` sends `set
implicit_transactions on`, `commit()` and `rollback()` send `IF @@TRANCOUNT > 0 COMMIT TRAN` and
`IF @@TRANCOUNT > 0 ROLLBACK TRAN`, and `close()` the rollback. So the SQL Server dialect gains
`SET IMPLICIT_TRANSACTIONS ON` (`Session::autocommit` is false under it, and the first statement
that writes, DDL included, keeps its transaction open, as SQL Server's do) and `IF condition
statement [ELSE statement]` with one statement each and a condition that reads no table (the
condition is evaluated with no row in scope; one that names a column, a subquery or an aggregate
is 40517). Item 47's interpreter replaces this narrow `IF` with blocks, `IF EXISTS` and the rest
of the batch logic; a `SELECT` starting an implicit transaction waits for it too.

**Checks.** Unit tests decode every type's layout and refuse truncated and hostile requests; the
seeded fuzzer of `hostile_packets.rs` mutates RPC and transaction manager requests, before
parsing and over sockets; socket tests run CRUD, prepared handles, output parameters, errors,
transaction manager requests, resets and mssql-jdbc's implicit transactions. CI's `tds-apps` job
builds a C# program on Microsoft.Data.SqlClient 5.2 and runs a Java program on mssql-jdbc 12.8
(both MIT, downloaded by CI, never shipped) against `eggdb serve --tds-listen`, and compares their
output with `scripts/tds-apps/expected-*.out`, written by hand from Microsoft's documentation of
what SQL Server returns; a SQL Server container is not used as the oracle, since its license is
not open.
