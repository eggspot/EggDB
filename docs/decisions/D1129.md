## D1129 Savepoints undo key-value writes made through a session's writer — Decided by the code-only session (2026-11-14, D355); roadmap M3 (`ROLLBACK TO SAVEPOINT` and key-value writes through serve's sessions, D319)

- **The gap.** D319 made `ROLLBACK TO SAVEPOINT` undo the key-value commands of `eggdb shell` and embedded code,
  which run beside the session and hand it their stored changes (`record_savepoint_undo`). Writes that go through
  the session's own writer, which is how a served session's key-value tools write (`put_with_expiry`,
  `collection_put`, `collection_delete`, `increment`, `compare_and_set`, `set_expiry`, `clear_expiry`), still met
  the savepoint undo writer's defaults and were refused inside a savepoint.
- **The writer now records them.** `KeyValueWrite` gains `start_change_journal` and `take_change_journal` (by
  default the store cannot). The savepoint undo writer wraps each of those tool writes in a journal and logs every
  stored key the engine changed, deadline records and collection entries included, as a `Host` undo entry. That is
  the entry kind D319 already undoes with `restore`, so `ROLLBACK TO SAVEPOINT` puts them back exactly, in order with
  the SQL changes. A store that cannot journal still refuses with `0A000`.
- **Plumbing.** The engine's `WriteTransaction` journal (D319) gets `start_journal` and `take_journal`. A nested
  journal, such as an embedded undoable block, declines rather than steal its entries. The SQL writer and the shared
  writer use them, and the boxed and temporary-table writers pass the tool writes and the journal through.
- **Left:** RESP sessions of `eggdb serve` sharing a block with SQL (RESP's `MULTI` is its own transaction today),
  after which their writes reach this path unchanged.

**Status:** code written, unbuilt (code-only mode, D355).
