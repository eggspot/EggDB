## D371 SQL Server's batch-aborting errors roll back or doom the transaction even before any write — Decided by the code-only session (2026-11-10, D355); roadmap M3, closes one of D317's leftovers

With `XACT_ABORT OFF`, SQL Server ends the batch and rolls back the open transaction for a
batch-aborting run-time error (a conversion error such as Msg 245), whether or not the failing
statement had written; inside `TRY` the same error leaves the transaction uncommittable
(`XACT_STATE()` -1) for the `CATCH` block. D317 kept the older rule that rolled back only when the
failing statement had changed rows, and doomed a transaction inside `TRY` only under
`XACT_ABORT ON`.

- `Session::rolls_back_transaction_after` no longer asks whether the failed statement was undone:
  any error `tsql::aborts_batch_and_transaction` classifies rolls the transaction back (syntax
  errors, name-resolution errors and `RAISERROR` still do not, as before).
- Inside `TRY`, an error that would roll the transaction back marks it uncommittable, as
  `XACT_ABORT ON` already did, so `XACT_STATE()` is -1, writes and `COMMIT` are Msg 3930 and a
  batch that ends with it open rolls it back with Msg 3998.
