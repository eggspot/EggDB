## D519 CQL result paging — Decided by the code-only session (2026-11-11, D355); roadmap M16

`QUERY` and `EXECUTE` now honour the page size and paging state of their query parameters
(flags `0x04` and `0x08`), so drivers that page by default (5,000 rows in the DataStax and
ScyllaDB drivers) see `HAS_MORE_PAGES` and fetch the next page with the state they were given.

- **Stateless pages:** a paging state is 16 bytes: the offset of the next row and the first 8
  bytes of the SHA-256 of the statement's text and bound values. Each page runs the statement
  again and keeps its rows from that offset, so the server holds nothing between pages and a
  state cannot be replayed against another query (`Invalid value for the paging state`, a
  protocol error). The cost is reading the result again for every page, and rows written
  between pages may shift the offset, as Cassandra's own token-based paging also tolerates
  other writes.
- **Where:** a new `paging.rs` cuts the encoded rows result (metadata copied, the state inserted
  after the column count as protocol v4 places it); other results pass unchanged, as do
  requests without a page size or with one of 0 or less.
- **Left out:** protocol v5 framing and compression, and paging through `BATCH` (which returns
  no rows).

**Status:** code written, unbuilt (code-only mode, D355).
