## D290 SQL Server's `AT TIME ZONE` reads the Windows zone names of `sys.time_zone_info`, infinite dates are out of range in SQL Server's and Oracle's functions, and `numeric` holds `Infinity` so `extract` of an infinite date returns it — Decided by the build loop (EggAgentCode task 20261103-0137, by judgement, Microsoft's and PostgreSQL's documentation and the Unicode CLDR data, 2026-11-03); roadmap item 31b, refines D271

D271 left three date pieces to later: SQL Server's Windows zone names in `AT TIME ZONE`, infinite
dates in the SQL Server and Oracle dialects' own functions, and `extract` of an infinite value,
which failed with `0A000` because `numeric` held no infinity. They are built here.

**Windows zone names are CLDR's mapping, as data.** SQL Server names zones the way Windows does
(`Pacific Standard Time`, `W. Europe Standard Time`) and accepts only those. The 142 territory
`001` entries of the Unicode CLDR `windowsZones` mapping (public data, typeVersion 2021a in the
file read on 2026-11-03) are a table in `eggdb-sql/src/time_zones/windows.rs`, each naming the
IANA region it follows; every region is in the embedded time zone database (a unit test checks
all 142). Names match in any letter case with trailing spaces ignored, as SQL Server's default
collation compares them, and IANA names and abbreviations are refused, as SQL Server refuses
them.

**`AT TIME ZONE` in T-SQL follows Microsoft's documented rules.** The T-SQL parser reads
`value AT TIME ZONE zone` (chained, any expression as the zone) as the SQL Server function
`AT TIME ZONE`. A `datetime2`, `datetime` or `smalldatetime` is a local time in the zone: a
time the clocks skip takes the offset before the change (`02:01` on a spring-forward day comes
out as `03:01` summer time), and a time they pass twice is the earlier instant, the offset
before the change, which differs from PostgreSQL's rule (the later one), so
`TimeZone::utc_of_local_earlier` keeps it apart from `utc_of_local`. A `datetimeoffset` keeps its
instant. The result is a `datetimeoffset` with the input's fractional precision; as D123 records,
EggDB keeps a `datetimeoffset`'s instant but not its offset, so it is shown in UTC. An unknown
name is error 9820 (`The time zone parameter '...' provided to AT TIME ZONE clause is
invalid.`), and a `date`, a string or a non-string zone is error 8116.

**`sys.time_zone_info` lists the same names.** It is a server view with SQL Server's three
columns: `name`, `current_utc_offset` (`+05:30`, `-07:00`, at the statement's time) and
`is_currently_dst`, one row per table entry in CLDR's order (west to east).

**Infinite dates are out of range where the dialect has no infinity.** SQL Server and Oracle
have no infinite dates, so an infinite value written by a PostgreSQL session (D271's sentinels)
is refused with the dialect's own out-of-range error rather than computed with as a huge number:
every T-SQL date function (`DATEADD`, `DATEDIFF`, `DATEPART`, `DATENAME`, `EOMONTH`, `FORMAT`,
`AT TIME ZONE` and the rest), `CAST`, `CONVERT` and text conversion fail with error 242 (`The
conversion of a date data type to a datetime2 data type resulted in an out-of-range value.`), and
every Oracle function, date arithmetic, `EXTRACT`, assignment to a column and NLS output fail with
`ORA-01841` (`(full) year must be between -4713 and +9999, and not be 0`). This also removes an
overflow: a `date` sentinel multiplied to microseconds overflowed `i64` in both dialects.

**`numeric` holds `Infinity` and `-Infinity`, as PostgreSQL 14 does.** The value carries an
`infinite` flag beside `nan`. It sorts below and above every finite value and below `NaN`, and
its arithmetic follows PostgreSQL 14: an infinity plus a finite value or the same infinity keeps
it, opposite infinities give `NaN`, an infinity times zero is `NaN`, a finite value divided by an
infinity is `0`, infinity divided by infinity and `mod(infinity, x)` are `NaN`, `mod(x,
infinity)` is `x`, rounding and `floor`/`ceil` keep it, and `^` follows PostgreSQL's rules for
infinite bases and exponents (`2 ^ Infinity` is `Infinity`, `0.5 ^ Infinity` is `0`, `(-1) ^
Infinity` is `1`, `0 ^ -Infinity` fails with `2201F`). PostgreSQL's text input reads `Infinity`,
`inf` and their signed forms (other dialects' `numeric` input does not); casts to `double
precision` give the float infinity, a float infinity casts to `numeric` in PostgreSQL's dialect,
an integer cast fails with `0A000` (`cannot convert infinity to integer`), a `numeric(p,s)` fails
with `22003`, `to_char` prints the overflow `#`s, and the binary wire form uses PostgreSQL's
special signs `0xD000` and `0xF000`. `extract` of an infinite date, time stamp or interval
returns it for the fields `date_part` gives as an infinite double (`epoch`, `julian`, `year`,
`isoyear`, `decade`, `century`, `millennium`, and the interval's), and `NULL` for the others, as
PostgreSQL 14 does; Oracle's `EXTRACT` fails as above. `date_trunc` of an infinite value already
returned it (D271).

**Stored additively, refused by older binaries.** An infinite `numeric` is storable. The row form
sets a new flag bit `0x04` (with `0x01` for `-Infinity`) and no digits; the key form is the
positive class `0x03` with the exponent `0xFFFF` and no digits for `Infinity` (after every finite
key, whose exponent is at most `0x83E7`, before `NaN`'s `0x04`) and the negative class `0x01`
with the exponent `0x0000` for `-Infinity` (before every finite key). Every finite and `NaN`
encoding is unchanged, and the previous decoder refuses both new forms (an unknown flag bit, and
an empty digit run), so an older binary reports a file holding one as damaged and never misreads
it, as D271 did for infinite time stamps. A unit test pins the new forms, their order and the
refusal of malformed ones.

Not yet: `scale()` and `min_scale()` of an infinity (`NULL` in PostgreSQL; EggDB gives 0),
other dialects' wire encoders send an infinite `numeric` or an infinite date as text rather than
refusing it (MySQL and TDS clients reading PostgreSQL-written infinities), SQL Server's
`datetimeoffset` offsets (D123), and zones Windows adds after CLDR's mapping.
