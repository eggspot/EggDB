## D296 `eggdb follow` reads PostgreSQL's `pgoutput` protocol 2: streamed in-progress transactions kept until they commit, binary tuples, and tables created or published during a follow copied from a snapshot of their own — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap items 3.17–3.18, extends D162 and D263

D162's follow asked for protocol 1, so PostgreSQL held each transaction in its own memory and on
its disk until it committed, sent tuples in text, and a follow stopped when the source created a
table. PostgreSQL's "Logical Replication Message Formats" and "Logical Streaming Replication
Protocol" pages describe protocol 2 (PostgreSQL 14 and newer), and its "Logical Replication"
chapter describes what a subscriber does for a table added to a publication (`ALTER SUBSCRIPTION
... REFRESH PUBLICATION`: copy it from a snapshot, then skip the changes that copy already holds).

- **Options asked for.** `StreamOptions::for_server` asks a server of major version 14 or newer
  for `proto_version '2', streaming 'on'`, and adds `binary 'true'` only when every column of every
  followed, published table has a type that `decodes_binary` reads (the built-in types
  `builtin_type_name` spells; arrays, domains, enums and extension types keep text). Older
  servers keep protocol 1. A `stream` event says what was asked for. Parallel streaming
  (`streaming 'parallel'`, protocol 4) is not asked for: a single applier applies in commit
  order anyway.
- **Streamed transactions.** Inside a Stream Start/Stop block each change carries its
  (sub)transaction ID after its kind; `parse_streamed_message` takes it off and
  `StreamedTransactions` keeps the change under its top-level transaction, in memory up to
  64 MiB across all of them, past which the transaction that grew moves to
  `<file>.follow-<xid>.spool` next to the database file (records of a 32-bit length and the
  message). A Stream Abort for the top-level ID drops the transaction; for a subtransaction it
  cuts the transaction back to where that subtransaction's first change was, and forgets the
  subtransactions after it, as PostgreSQL's own apply worker does. A Stream Commit replays the
  kept messages, `Relation` messages included, through the same applier as a `Begin`...`Commit`
  transaction, with the commit position as its final position, so it is one transaction in the
  file. A first segment of a transaction already kept, a lost connection and a switch to text
  tuples start the kept transactions over (the server streams them again from the slot's
  restart point); spool files a stopped run left are removed when the next run starts. The
  position reported on a keepalive does not move while a block is open.
- **Binary tuples.** A `b` column becomes `TupleValue::Binary`, read back by the column's type
  OID from the `Relation` message into the text PostgreSQL's input function takes: integers,
  booleans, floats (`NaN`, `Infinity`), text types, `json` and `jsonb` (version 1), `bytea` as
  `\x…`, `numeric` from its base-10000 digits with its display scale, `date`, `time`, `timetz`,
  `timestamp`, `timestamptz` in UTC (with `infinity` and BC years), `interval` and `uuid`. Bytes
  that do not have the type's layout are an error naming the column, never a panic. A table that
  appears during the follow with a type outside that list restarts the stream from the last
  applied position with text tuples, so binary is never a reason to stop.
- **Tables created or published during a follow.** A `Relation` message for a table the file
  does not have gives `Change::NewTable`. When the source still has it, the follow creates a
  temporary slot with an exported snapshot on a second replication connection, reads the table's
  columns, constraints and indexes at that snapshot, and creates and copies it in one transaction
  in the file, which also saves `copied <oid>` = the snapshot's position in `eggdb_follow.state`.
  Its changes in transactions committed before that position, and their `Relation` messages,
  are skipped (they are in the copy); from it on they apply. Its foreign keys wait as
  `foreign key <oid> <name>` items and are added in the first applied transaction that ends at or
  after that position, because earlier rows they reference may not be in the file yet. Both
  survive a reconnect and a resume. When the source no longer has the table (created and dropped
  since), it is created from the `Relation` message's columns and key, with every change applied.
  A `table_added` event names it.

Not yet: `streaming 'parallel'` (protocol 4) and two-phase commit messages (protocol 3,
`two_phase`), binary forms of arrays, domains, enums, ranges, network and geometric types, a
table moved to another schema or dropped and created again under the same name during a follow
(both still stop it with a clear message), and a foreign key whose definition is longer than the
follow state's 4,000 characters.
