## D871 SQL Server BEFORE UPDATE and BEFORE DELETE block predicates — Decided by the code-only session (2026-11-12, D355); follow-up of D850

- Security policies take `ADD BLOCK PREDICATE fn(columns) ON table BEFORE UPDATE | BEFORE DELETE`, and a block
  predicate with no operation, which SQL Server applies to all four operations (`AFTER INSERT`, `AFTER UPDATE`,
  `BEFORE UPDATE`, `BEFORE DELETE`). `AFTER DELETE` and `BEFORE INSERT` are syntax errors, as in SQL Server.
- An update or delete that reaches an existing row the predicate function returns no row for fails with SQL Server's
  error 33504 ("... has a block predicate that conflicts with this operation"), where PostgreSQL-style `USING` would
  skip the row silently. Each such predicate becomes a restrictive row-security policy `FOR UPDATE` or `FOR DELETE`
  whose `USING` is `CASE WHEN EXISTS (SELECT 1 FROM fn(columns)) THEN true ELSE
  eggdb_sqlserver_block_predicate_violation('<table>') END`; that internal function always raises 33504. A predicate
  with no operation becomes the four policies, named `sqlserver_policy_<name>_block_insert`, `_block_update`,
  `_block_before_update` and `_block_delete`, and is stored once with kind `block_all`.
- The policy condition is joined after the statement's own `WHERE` with `AND`, which stops at the first false
  operand, so rows the statement does not target are not checked. A row whose `WHERE` is unknown (`NULL`) is checked
  too, so such a row can raise 33504 where SQL Server would not touch it.
- As with the other predicates (D822), only roles row security applies to are checked.
