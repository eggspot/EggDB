## D213 The Kafka protocol in our own eggdb-kafka: produce and fetch on stored record batches, groups later — Decided by the build loop (by judgement, 2026-10-31); refines D33

Part 4.M16-1 asks for Kafka clients producing and consuming (topics, partitions, consumer
groups, transactions) on the shared log.

- **Written from Apache Kafka's public protocol guide**: `ApiVersions` 0–2 (newer versions get
  error 35 with the list, so clients fall back), `Metadata` 0–1, `Produce` 3, `Fetch` 4 and
  `ListOffsets` 1, all non-flexible encodings. Advertising only these keeps every request and
  response in formats this server writes exactly.
- **Batches are stored as producers sent them.** Each record batch (magic 2) is checked (length,
  magic, CRC-32C), its base offset replaced by the partition's next offset, and kept whole in the
  collection `kafka0`, keyed by topic, partition and base offset; compressed batches stay
  compressed and clients decompress them. A fetch returns whole batches from the one holding
  the requested offset, as Kafka does. Everything is one key-value transaction per append.
- **Topics appear on first use** with one partition, as Kafka's auto-creation does by default.
- **No authentication yet**, so the listener binds only to loopback.

Left: consumer groups (FindCoordinator, JoinGroup, SyncGroup, Heartbeat, OffsetCommit and
OffsetFetch), transactions and idempotent producers, flexible request versions, SASL and TLS,
topic creation and deletion APIs, retention and compaction, partitions per topic, and a
benchmark against Kafka.
