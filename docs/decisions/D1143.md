## D1143 Subqueries in the SET of a joined UPDATE — Decided by the code-only session (2026-11-14, D355); roadmap M5 (joined `UPDATE` and `DELETE`, D297)

- **Before.** `UPDATE t SET c = (SELECT ...) FROM u WHERE ...` (and MySQL's and SQL Server's joined updates) answered
  `0A000` when a `SET` value held a subquery: the joined update evaluates `SET` values row by row with an evaluator
  that has no subquery preparation.
- **Now.** The query that finds the joined rows also computes those values. Each `SET` value that holds a subquery is
  added as an extra item after the joined tables' columns, so the select path prepares and runs the subquery,
  correlated or not, with every joined table in scope. Each planned row then takes its value from the extra column
  as a constant, still through the column's assignment rules (type conversion, `DEFAULT` checks, domains). Values
  without subqueries are evaluated as before.
- **Limits kept.** A target table without a primary key, matched by content through the null-extended rows path,
  still refuses subqueries in `SET`. Subqueries in `RETURNING` still answer `0A000`: they would have to see the rows
  after the update.
- **Left in the item:** subqueries in `RETURNING`, views, partitioned tables and tables with row-level security as the
  target, `EXPLAIN` of joined updates and deletes, SQLite's refusal of `FROM` tables in `RETURNING`, and `OUTPUT
  deleted.` of a joined Transact-SQL `UPDATE`.
