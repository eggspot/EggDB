## D1119 LSM trees per table — Decided by the code-only session (2026-11-13, D355); roadmap M2 (`WITH (storage = lsm)`, D170)

- **A table's rows move as a key prefix.** SQL tables are key prefixes of the one catalog tree (D139). `CREATE TABLE
  ... WITH (storage = lsm)` (PostgreSQL's storage-parameter syntax; `btree` and `heap` name the default) creates the
  table and then asks the store to keep every key under its row prefix in an `LsmTree` of its own
  (`KeyValueWrite::store_prefix_in_lsm_tree`, refused with `0A000` by stores without it). Indexes stay in the B-tree.
- **The route is the catalog record.** The catalog tree holds one reserved key per LSM table,
  `0xff C O L 0x00 0x08` followed by the prefix, with the LSM manifest's root page (8 bytes, big-endian). A write
  transaction refuses an empty or reserved prefix, a prefix that overlaps another LSM table's, and a prefix that
  already has keys (only a new, empty table moves). `CREATE TABLE ... AS ... WITH (storage = lsm)` is refused for now.
- **Routing sits in the transactions, below every API.** `ReadTransaction` and `WriteTransaction` load the routes
  when they begin, but only in a file that has LSM tables, so other files pay nothing. `get`, `get_with`, `put`,
  `put_if_absent`, `delete` and `put_reader` (read whole, up to `LsmTree::MAX_VALUE_BYTES`) go to the LSM tree for
  routed keys. Change capture, the change archive, replication's change list and savepoint journals see the same
  changes as before. Keys under an LSM prefix have no time to live.
- **Scans need no merge.** An LSM table owns its whole prefix, so the B-tree holds none of its keys. `Scan` now walks
  any number of disjoint segments, each a B-tree or an LSM cursor, in order from either end. It replaces the fixed
  near and far segments (collections' reserved range still splits a scan in two). `raw_scan` (differential backups)
  includes the LSM rows and leaves the route keys out, since a root is only meaningful in its own file.
- **The file says so.** The first LSM table sets the new incompatible feature bit `Features::LSM_TABLES` (`1 << 3`),
  so an older release refuses the file rather than hiding rows. `Database::check` marks the LSM trees' pages through
  `Store::check_with_lsm_roots`, so they are not counted as leaked. This is a file-format change: the build-and-fix
  pass gives it the security review D35 asks for, with a format compatibility test.
- **Left:** `get_reader` streaming of an LSM value (it answers `None` for routed keys), the concurrent-writer path
  (`concurrent.rs`), dropping a table's LSM tree with the table (the empty tree and route stay and are reused if the
  id comes back), `ALTER TABLE ... SET (storage = lsm)` with existing rows, `reloptions` in `pg_class`, and the B-tree
  and LSM bake-off in the benchmarks.
