## D1371 The client follows the system's light, dark and high-contrast theme — Decided by the code-only session (2026-11-25, D355); roadmap M6e "... and the OS's theme" (D15, D256), designed in `docs/ux/localization-and-window.md` section 3

- **What users get.** Without `--theme`, the desktop client draws the system's theme: dark when the system is dark, high contrast when it asks for more contrast, light otherwise; it reads the system again whenever the window comes to the front, so a change made meanwhile shows at the next frame. `--theme` still overrides for one run.
- **Per platform.** `Window::system_theme` reads X11's XSETTINGS (`Net/ThemeName` ending in `-dark` or naming a high-contrast theme, or `Gtk/ApplicationPreferDarkTheme` set), Windows' `AppsUseLightTheme` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize`, and macOS's `NSApp.effectiveAppearance` name, with `accessibilityDisplayShouldIncreaseContrast` winning as high contrast. Other backends answer `None` and the client stays light.
- **Left.** `View > Theme` with `System` stored in the settings, following changes live through `WM_SETTINGCHANGE`, `NSAppearanceDidChangeNotification`, the settings portal's `SettingChanged` (which comes before XSETTINGS on Linux) and the browser's `prefers-color-scheme`, Windows' `SPI_GETHIGHCONTRAST`, and the `Theme: dark (system)` status text.
- **Proof.** A unit test reads dark, light, high-contrast and preferred-dark settings from XSETTINGS data, and none from empty settings.

**Status:** code written, unbuilt (code-only mode, D355).
