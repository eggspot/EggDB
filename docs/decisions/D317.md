## D317 Statement-level rollback in MySQL, SQLite, Oracle and SQL Server: inside a transaction a failing statement undoes only its own changes and the transaction goes on; SQLite's `INSERT OR FAIL` keeps the rows before the conflict; SQL Server's `XACT_ABORT ON` still rolls the transaction back; PostgreSQL keeps `25P02` — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M3 ("Statement-level rollback"), applies D9, D10 and D173, builds on the savepoint undo log of D283 and D319

Until now a statement that failed inside a transaction in MySQL's, SQLite's, Oracle's or SQL
Server's dialect rolled the whole transaction back when it had already written a row (a multi-row
`INSERT` whose third row hit a duplicate key, an `UPDATE` that failed part-way), and left the
transaction as it was when it had not. None of those databases does that. InnoDB rolls back the
failing SQL statement and keeps the transaction (MySQL Reference Manual, "InnoDB Error
Handling"). Oracle sets an implicit savepoint before each statement and rolls back to it when the
statement fails (Oracle Database Concepts, "Statement-Level Rollback"). SQLite's default conflict
resolution is `ABORT`: it backs out the statement's changes and keeps the transaction, and `FAIL`
keeps the changes the statement made before the conflict (sqlite.org, "The ON CONFLICT Clause").
SQL Server with `XACT_ABORT OFF`, its default, ends only the statement for statement-terminating
errors and rolls back that statement's changes, while `SET XACT_ABORT ON` rolls the whole
transaction back (Microsoft Learn, "SET XACT_ABORT"). PostgreSQL has no statement-level rollback:
a failed statement aborts the transaction until `ROLLBACK` (`25P02`), which EggDB already does.

- **What users get.** In MySQL's, SQLite's, Oracle's and SQL Server's dialects,
  `START TRANSACTION`/`BEGIN`/`BEGIN TRAN` (or Oracle's and `autocommit = 0`'s implicit
  transaction), then `INSERT` (works), `INSERT` of a duplicate key (fails), `INSERT` (works) and
  `COMMIT` leaves two rows. A multi-row `INSERT`, an `INSERT ... SELECT` or an `UPDATE` that fails
  part-way leaves none of its changes, its secondary-index entries and catalog writes included,
  and the transaction keeps what came before. It works the same after a `SAVEPOINT`: the failed
  statement is undone, and a later `ROLLBACK TO SAVEPOINT` still undoes everything after the
  savepoint. A failing PL/SQL block or procedure call is one statement, so all of it is undone,
  as Oracle does. Row triggers (MySQL's, SQLite's, Oracle's) run inside their statement, so
  their changes go with it.
- **SQLite's conflict clauses.** `INSERT OR ABORT` (and plain `INSERT`) back out the statement;
  `INSERT OR FAIL` keeps the rows written before a `UNIQUE`, `NOT NULL` or `CHECK` conflict, in a
  transaction and on its own (where it commits them); `INSERT OR ROLLBACK` rolls the transaction
  back, as before; `OR IGNORE` and `OR REPLACE` never fail on a conflict. The parser used to read
  `FAIL` as `ABORT`; the `Insert` statement now carries `keeps_changes_on_conflict`.
- **SQL Server.** With `XACT_ABORT OFF` a duplicate key and the other statement-terminating errors
  roll back their statement, `@@TRANCOUNT` stays as it was and the batch goes on (inside `TRY`
  the error moves to `CATCH` with the transaction still committable). With `SET XACT_ABORT ON` the
  error rolls the whole transaction back, `@@TRANCOUNT` is 0 and the batch ends, as before (D148).
  A run-time error that ends the batch (a conversion or arithmetic error) still rolls the
  transaction back when its statement had written, as it did before this decision.
- **PostgreSQL** is unchanged: a failed statement aborts the block, every statement fails with
  `25P02` until `ROLLBACK` or `ROLLBACK TO SAVEPOINT`, and `COMMIT` reports `ROLLBACK`.
- **How it works.** The session's `write` gives the statement an undo-logging writer, the
  `UndoWrite` the savepoints already use (D283), with a log of its own when no savepoint is set
  and the savepoints' log, from the length it had when the statement started, when one is. Each
  write records the key and what it held before (`put_if_absent` needs no read). When the
  statement fails, `savepoints::undo_back_to` puts the recorded keys back newest first, through
  the temporary-object router so temporary tables come back too, and the table cache is dropped
  since the statement may have changed a definition. A statement that read and did not write
  costs nothing (the log never allocates), and a successful statement drops its log. If putting
  the keys back fails (the store refuses a write), the whole transaction is rolled back, never
  left half undone. `ROLLBACK TO SAVEPOINT` uses the same `undo_back_to`.
- **The shell.** `eggdb shell` refuses key-value commands after a statement failed under a
  savepoint (D319) by reading `Session::failed_after_savepoint`; that flag is only set in
  PostgreSQL's dialect, so in the others a failed statement no longer stops the block's
  key-value commands.

**Decided by research.**
- Undo through the session's key-level log, not a savepoint in the storage engine: the engine's
  write transaction has no nested savepoints, and the log already exists, already routes
  temporary objects and is already ordered with the savepoints' entries (D283, D319). The cost is
  one read of the previous value per written key, only in statements inside a transaction, and
  memory for those values until the statement ends.
- SQL Server's batch-aborting errors: SQL Server rolls the transaction back for most errors that
  abort the batch, but not for name-resolution errors (207, 208), syntax errors or `THROW`
  (Erland Sommarskog, "Error and Transaction Handling in SQL Server", part two). The brief asked
  to keep those errors as they are, so EggDB rolls the transaction back for a run-time error that
  ends the batch only when its statement had written (`tsql::aborts_batch_and_transaction` and
  `Session::rolls_back_transaction_after`), which is what it did before; one that failed before
  writing leaves the transaction open.
- `INSERT OR FAIL` keeps changes only for the conflicts the conflict clause governs (`UNIQUE`,
  `NOT NULL`, `CHECK`; SQLite's documentation leaves out foreign keys); any other error backs out
  the statement as `ABORT` does.
- MySQL's `CALL` runs a procedure as one statement, so an error that escapes it undoes the whole
  call. MySQL keeps the procedure's statements that ran before the failing one. Undoing the call
  is the safer of the two differences, and it is listed under "Left".

Tests: `crates/eggdb-sql/src/statement_rollback_tests.rs` with the acceptance check per dialect
(MySQL, SQLite, Oracle: insert, duplicate fails, insert, commit, two rows) plus a failed
multi-row insert in each, a part-way `UPDATE` with a unique column in MySQL, a failed statement
after a savepoint followed by `ROLLBACK TO` in MySQL, `INSERT OR FAIL` in a transaction and on
its own, `INSERT OR ABORT` and `INSERT OR ROLLBACK` in SQLite, SQL Server with `XACT_ABORT OFF`
(both failures end only their statements, the transaction stays open) and `ON` (no rows,
`@@TRANCOUNT` 0), and PostgreSQL's `25P02`; the SQL Server test of a duplicate key in a
transaction now expects the batch to go on (`sqlserver_tests.rs`); new cases in the MySQL,
SQLite, Oracle and SQL Server correctness suites (`crates/eggdb-sql/correctness/*.test`); and a
shell test in which a failed statement in a MySQL block leaves `put` working.

Left: statement-level rollback of a failing statement trigger that runs after its statement
(Oracle's statement triggers and SQL Server's `AFTER` triggers that fail still roll the
transaction back); a MySQL `CALL` that keeps the procedure's statements before the failing one;
SQL Server's rollback of the transaction for batch-aborting run-time errors that fail before
writing, and its doomed transaction (`XACT_STATE()` -1) for those errors inside `TRY`; MySQL's
transaction rollback on a deadlock or, with `innodb_rollback_on_timeout`, a lock wait timeout,
which need concurrent writers (D173); `ON CONFLICT ROLLBACK` and `FAIL` written in a SQLite
table's constraints and `UPDATE OR ...`.
