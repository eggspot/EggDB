## D264 PostgreSQL polymorphic routines are specialized per call, and transition tables are statement-scoped table variables — Decided by the build loop (EggAgentCode task 20261102-0614, 2026-11-02); extends D158

**Polymorphic types.** `anyelement`, `anyarray`, `anynonarray`, `anyenum`, `anycompatible`,
`anycompatiblearray` and `anycompatiblenonarray` are catalog pseudo-types
(`CatalogType::AnyArray` and `CatalogType::Pseudo`), so a routine's identity, `DROP FUNCTION
f(anyelement)`, `pg_proc` and `\df` name them as PostgreSQL does. They are only accepted as a
routine's parameter and result types, never as a column or cast type.

- **Matching.** A polymorphic parameter fits any argument with the lowest score, so a concrete
  overload wins. After the slots are filled, the arguments of each family must agree: the
  `anyelement` family needs one type (an `anyarray` argument gives its element type), the
  `anycompatible` family takes the common type the set operations use. Text values may be
  untyped literals (EggDB's call path sees values, not literal-ness), so they take the type the
  other arguments give, or `text`. A candidate whose arguments don't agree is dropped, so the
  call reports `42883` as PostgreSQL does; `42804` remains for a default that disagrees with
  the given arguments.
- **Running.** The chosen definition is cloned with its parameters and result replaced by the
  resolved types, and cached per (routine, resolution) in the routine cache, so the compiled
  program cache (keyed by the definition's pointer) is reused across calls with the same types.
  Nothing downstream (PL/pgSQL, `sql` bodies, `SETOF`, `RETURNS TABLE`, `OUT` parameters) knows
  about polymorphism.
- **Limits.** A `NULL` argument carries no type in EggDB's call path, so an all-`NULL` family
  resolves to `text` instead of PostgreSQL's `42804`. `$0` is not declared yet.

**Transition tables.** `REFERENCING OLD TABLE AS o NEW TABLE AS n` on an `AFTER ... FOR EACH
STATEMENT` trigger: the rows the trigger set already records for statement triggers (also for
cascaded rows, D260) become table variables under hidden names, entered for the
trigger function's call, and the function's own SQL statements (routine depth equal to the
trigger function's) have the written names replaced, with the same rewrite data-modifying `WITH`
uses. Functions it calls don't see them, as in PostgreSQL. Row-level triggers with transition
tables stay refused when they fire (`0A000`), because EggDB runs `AFTER` row triggers before
the statement's full set of rows is known: a statement's own once its rows are written, a
cascaded action's once that action's rows are written (D260).
