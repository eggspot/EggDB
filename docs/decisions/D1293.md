## D1293 SQLite's likely, unlikely, likelihood and sqlite_source_id — Decided by the code-only session (2026-11-18, D355); roadmap M2 SQLite compatibility (D10)

- **What users get.** In SQLite's dialect, the planner hints `likely(x)`, `unlikely(x)` and `likelihood(x, p)` return `x`, as SQLite's do, with `likelihood` refusing a probability that is not a constant from 0.0 to 1.0 with SQLite's message; `sqlite_source_id()` names EggDB and the SQLite version it answers as. ORMs and query builders that emit the hints (and schemas whose views keep them) run unchanged.
- **How.** The SQLite parser reads the hints as their first argument, so they cost nothing at run time; EggDB's planner takes no hint from them.
- **Left.** `load_extension`, which EggDB refuses by design (D1).
- **Proof.** Cases in `correctness/sqlite.test` read the three hints and refuse a probability of 2.

**Status:** code written, unbuilt (code-only mode, D355).

Follow-up: `sqlite_compileoption_used(name)` and `sqlite_compileoption_get(n)` answer from one fixed list, `ENABLE_JSON1`, `ENABLE_MATH_FUNCTIONS` and `THREADSAFE=1`, the options whose behaviour EggDB's SQLite dialect has. A name is matched without its `SQLITE_` prefix and, for `NAME=value` options, by its name alone, as SQLite does; an index past the list gives NULL.
