## D334 The rest of PromQL: every aggregation, `histogram_quantile`, `label_replace` and `label_join`, `bool`, vector matching, subqueries and selectors without a metric name, each query bounded by a samples limit and the memory budget — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M16, extends D220, applies D9 and D307

D220's PromQL answered selectors, the range functions, five aggregations and arithmetic, so the
queries Grafana's Prometheus dashboards are built from (top-N panels, latency percentiles from
histograms, ratios of two metrics joined on a label, relabelled legends, "max over the last
hour of a rate") failed. Built from the Prometheus documentation's querying pages (Basics,
Operators, Functions, Examples) and the HTTP API page; the acceptance tests in
`crates/eggdb-observability/src/promql_tests.rs` are those pages' examples (the
`method_code:http_errors:rate5m` matching example, the `label_replace` and `label_join`
examples, the `rate(...[5m])[30m:1m]` subquery, the `{job=~".*"}` selector the docs call bad)
and the documented values of the aggregators' example series.

- **Aggregations.** `sum`, `avg`, `min`, `max` and `count` gain `group` (1 per group), `stddev`
  and `stdvar` (population), `topk` and `bottomk` (`k` a scalar, truncated; below 1 gives
  nothing; the input series keep all their labels, the metric name too, ordered largest or
  smallest first with `NaN` last), `quantile` (φ-quantile interpolated between the two nearest
  ranks; `-Inf` below 0, `+Inf` above 1) and `count_values` (a label per distinct value,
  written as Go's shortest decimal, `+Inf`, `-Inf` or `NaN`). `by` and `without` come before or
  after the arguments. A parameter of the wrong type or a wrong argument count is refused as
  Prometheus refuses it. `min` and `max` ignore `NaN` unless every value is `NaN`, as
  Prometheus does. An aggregation keyword followed by neither `(`, `by` nor `without` is a
  metric name.
- **`histogram_quantile(φ, v)`** over classic `_bucket` series: grouped by every label but `le`
  and the metric name; buckets with the same bound are added together; counts are made
  monotonic (with Prometheus's 1e-12 relative tolerance for float noise); the rank's bucket is
  interpolated linearly from its lower bound (0 for the first bucket unless that bound is 0 or
  below, which is then the answer); a rank in the `+Inf` bucket gives the second-highest bound;
  no `+Inf` bucket, fewer than two buckets or no observations give `NaN`; φ outside 0..1 gives
  `±Inf` and a `NaN` φ gives `NaN`. Series whose `le` is not a number are left out.
- **`label_replace` and `label_join`.** The regular expression is anchored (`^(?:…)$`, so a
  partial match does not count) and runs on EggDB's own regex engine (`eggdb_sql`, now with
  `regex_captures`), with `.` matching a newline as Prometheus's `(?s)` does; a series whose
  label does not match passes unchanged. The replacement expands like Go's `regexp.Expand`
  (`$1`, `${1}`, `$$`; `$1x` names the group `1x`, which is empty). An empty result removes the
  label; an invalid label name or regex is `bad_data`; two series left with the same labels are
  Prometheus's "vector cannot contain metrics with the same labelset". `vector(s)` and
  `scalar(v)` came with them, for parameters such as `topk(scalar(...), ...)`.
- **Binary operators.** `bool` turns a comparison into 0 or 1 and drops the metric name; between
  two scalars a comparison needs it. `%` and `^` (right-associative, binding tighter than unary
  minus) and the set operators `and`, `or` and `unless` join the precedence table. Vector
  matching takes `on(...)` or `ignoring(...)` with `group_left(...)` or `group_right(...)`:
  one-to-one results keep only the `on` labels (or lose the `ignoring` ones), grouped results
  keep the "many" side's labels plus the listed labels copied from the "one" side, and the
  errors are Prometheus's own ("found duplicate series for the match group ... many-to-many
  matching not allowed", "many-to-one matching must be explicit", "grouping labels must ensure
  unique matches", "no grouping allowed for ... operation", a label in both `on` and the group
  clause).
- **Subqueries** `expr[range:step] offset d`: the inner expression is evaluated at the multiples
  of `step` inside the left-open window `(t - offset - range, t - offset]`, as Prometheus 3
  does; an empty step is the default evaluation interval, one minute. Subqueries nest and feed
  every range function. A subquery of a range vector is refused at parse time, of a scalar when
  evaluated.
- **Selectors without a metric name** (`{job="x"}`, `{__name__=~"job:.*"}`) read every metric
  the matchers can match: the `__name__` matchers pick the metric names and a matcher that
  refuses the empty value on a label the table has no column for rules the table out, so only
  candidate tables are read. A
  selector whose every matcher accepts the empty value (`{}`, `{job=~".*"}`, `{job!="x"}`) is
  refused, as are a metric name given twice and a keyword (`on`, `bool`, ...) used as a metric
  name (`{__name__="on"}` reaches it). A bad regex in a matcher is now refused at parse time.
  `/api/v1/series` takes them too.
- **Bounded work.** Each query holds a `Work` against two limits. Samples: what the query read
  stays held for its whole run, plus a range query's answer points, plus what one evaluation
  step builds (matrices, subquery points), which is given back after each step; past
  `DEFAULT_MAX_QUERY_SAMPLES` (50,000,000, Prometheus's `--query.max-samples`, changeable with
  `Endpoint::with_max_samples`) the query fails with Prometheus's "query processing would load
  too many samples into memory in query execution". Reads ask SQL for at most the samples the
  query has left, so a read never loads more than the limit allows. Memory: the held samples'
  bytes are reserved against the server's one memory budget (`Endpoint::with_memory_budget`,
  given by `eggdb serve`, D307; at most 64 KiB is not counted) and a query that does not fit
  fails at once. Subqueries may run at most 11,000,000 inner steps per query in total, so
  `x[1y:1ms]` or deep nesting is refused before it runs rather than looping.
- **Errors in Prometheus's shapes.** `{"status":"error","errorType":...,"error":...}`: a parse
  or type error is `400 bad_data`, an evaluation error (matching, duplicate label sets, the
  samples limit, a storage error) is `422 execution`, and a query the memory budget cannot take
  is `503 unavailable` with `Retry-After`.

Decided by research:
- *Which Prometheus version's window semantics?* Prometheus 3's: range selectors and subquery
  steps are left-open, which D220's range selectors already were.
- *What does a query hold against the memory budget?* 16 bytes per sample held (the
  `(time, value)` pair), not the labels: labels are bounded by the series count, which the
  samples bound too, and counting them exactly would cost a walk per step.
- *The subquery steps limit* has no Prometheus equivalent (Prometheus relies on its query
  timeout, which EggDB's HTTP API does not have yet); 11,000,000 is 1,000 subquery steps for
  each of the 11,000 points a range query may return.
- *Named capture groups* (`(?P<name>...)`, `$name`) are not in EggDB's regex engine (it follows
  PostgreSQL's advanced regular expressions), so `$name` expands to nothing, as Go does for a
  name that is no group's.
