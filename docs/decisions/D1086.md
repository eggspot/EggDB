## D1086 A fixed-memory mode: one limit split across the engine and enforced by the allocator — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D41, D166, D254)

- **One number.** `eggdb serve --memory-limit <size>` (at least 16 MiB) and `Options::memory_limit(bytes)` take one budget for the whole process, the way a container limit or a device's RAM is given.
- **The split.** Half goes to the page cache, an eighth to read transactions' snapshots and, in the server, a quarter to the connections' shared budget (`--max-connection-memory`, D254); the rest is left for statements, the catalog and thread stacks. An explicit `--cache` or `--max-connection-memory` wins over its share, and one at or above the limit is refused as a usage error. These shares are where the engine already fails gracefully: `CacheFull`, `SnapshotTooOld` and the per-protocol out-of-memory replies.
- **The backstop.** `eggdb_platform::set_process_limit` adds a process-wide cap to every `EggAllocator` on top of each value's own budget (D166), changeable at run time; `refused_allocations` counts refusals. A refused allocation ends the process as Rust's allocation failure does, which is still better than the operating system's out-of-memory killer choosing a victim; the shares keep normal work from reaching it.
- **Opt-in allocator.** The cap binds only in a build with `--features egg-allocator`, which stays opt-in under D166. The default build applies the shares and says on standard error that the allocator does not enforce the limit.
- **Left out.** Graceful recovery from a refused allocation inside arbitrary code (`try_reserve` throughout the engine) is not attempted; it would touch every collection on every path.

**Status:** code written, unbuilt (code-only mode, D355).
