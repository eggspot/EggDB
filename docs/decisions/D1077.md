## D1077 CalDAV scheduling and WebDAV ACLs — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D56, D895)

- The DAV server has one user, so both features are written for that model. The `DAV` header now adds
  `access-control` and `calendar-auto-schedule`, and `Allow` lists `ACL` and `POST`.
- **Access control (RFC 3744, `acl.rs`):**
  - `current-user-privilege-set` lists every privilege, or only the reading ones on a read-only server.
  - `acl` is one protected ACE granting `DAV:all` to the user's principal.
  - Also answered: `supported-privilege-set` (RFC 3744's tree), `acl-restrictions` (`grant-only`,
    `no-invert`), `principal-collection-set`, and empty `inherited-acl-set` and `group-membership`.
  - An `ACL` request may only restate the owner's grant (to the principal's href, `DAV:self` or the owner
    property) and is then a no-op `200`. Denies get `403 grant-only`, and other principals
    `403 recognized-principal`.
  - `principal-property-search` finds the user by name or address, all or any of the matches, and
    `principal-search-property-set` names those two properties. This is what clients use to look up
    attendees.
- **Scheduling (RFC 6638, `scheduling.rs`):**
  - The calendar home gains `inbox` and `outbox` collections (`schedule-inbox` and `schedule-outbox`
    resource types). Existing stores get them on the next request.
  - The principal answers `schedule-inbox-URL`, `schedule-outbox-URL`, `schedule-default-calendar-URL`
    and `calendar-user-type`.
  - **Free-busy:** a `POST` to the outbox with a `METHOD:REQUEST` `VFREEBUSY` (at most a year) answers a
    `schedule-response`.
    - For the user's own address it gives `2.0;Success` and a `METHOD:REPLY` `VFREEBUSY`, built from every
      calendar object's occurrences in the range (recurrences expanded; transparent and cancelled events
      left out; overlaps merged).
    - Every other recipient gets `3.7;Invalid calendar user`.
  - **Incoming iTIP** (RFC 5546), put in the inbox, is applied to the default calendar's object with the
    same UID:
    - `REQUEST` and `PUBLISH` store the object;
    - `REPLY` sets each replying attendee's `PARTSTAT`;
    - `CANCEL` marks the object `STATUS:CANCELLED`.
    - The message stays in the inbox for the client.
  - **Outgoing iTIP:** when the user puts an object they organize that has other attendees, a
    `METHOD:REQUEST` copy is queued in the outbox, with its recipients as a dead property. Deleting one
    queues a `METHOD:CANCEL`. The stored object is not rewritten, so the `ETag` the client got stays true.
