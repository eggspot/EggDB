## D1178 WebSocket transports for subscriptions and live queries, re-run only when the database changed — Decided by the code-only session (2026-11-15, D355); roadmap M6a, follows D878

- **Upgrades in `eggdb-http`.** A handler may answer `Reply::Upgraded(Upgrade)`: the server writes `101 Switching Protocols` (`Upgrade`, `Connection: Upgrade` and the upgrade's own headers) and hands the connection to the upgrade's protocol function with a reader and a writer; the bytes the request reader had already buffered are read first, and once upgraded a read that finds nothing within the connection's read poll fails with `WouldBlock` instead of waiting for a request deadline, so a protocol can do other work between messages. The connection closes when the function returns. `Reply::into_response` turns an upgrade into its bare `101` (for tests and for HTTP/3, which has no upgrade).
- **WebSocket (RFC 6455).** `eggdb_http::websocket_reply` checks the opening handshake (version 13, `Sec-WebSocket-Key`, a subprotocol from the handler's list when it names any), answers with `Sec-WebSocket-Accept` (SHA-1 and base64 from `eggdb-crypto`), and runs a session on a `WebSocket`: client frames must be masked, control frames are at most 125 bytes and not fragmented, fragmented messages are reassembled up to 16 MiB, pings are answered with pongs, and text must be UTF-8; anything else is a protocol error that closes the socket. This is a second implementation beside Gremlin's and MQTT's, which keep theirs until they move onto `eggdb-http`.
- **`/graphql` with `graphql-transport-ws`** (the graphql-ws library's protocol, used by Apollo, urql, Relay and Hasura clients): `connection_init`/`connection_ack` (a subscribe before it closes with 4401, a second init with 4429, no init within 10 s with 4408), `subscribe` with D875's query or subscription operation (a mutation gets `error`), `next` with each changed result, `complete` from either side, `ping`/`pong`, 4409 for a reused id, 4400 for anything unreadable, at most 64 subscriptions a socket.
- **`/realtime` with `eggdb-live`**: `{"type":"subscribe","id":..,"path":"/books?select=..&order=.."}` takes a REST read's path and PostgREST filters (D235) and answers `{"type":"rows","id":..,"rows":[...]}` each time the rows change; `unsubscribe` ends one, an `error` message reports a bad path or a failed run.
- **Change-driven invalidation.** Server-Sent Events (D878) and both WebSocket protocols now wrap their query in `live::on_change`: before a run it reads the store's committed version (`KeyValueRead::committed_version`), and runs the query only when that moved since the last run, so a quiet live query costs a version check every interval instead of a query. A store that does not report versions runs the query every time, as before. With checks this cheap, the default interval drops from 1 s to 250 ms. Pushing changes from the commit path, instead of checking, and sending only the rows that changed are left.
- Not yet: Supabase's realtime channel protocol (Phoenix channels with `postgres_changes`).
