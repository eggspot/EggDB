## D124 Transact-SQL views and CHECK constraints in the file: SQL Server is dialect code 4 in the view and CHECK records, with no new format version — Decided by the build loop (by judgement and by plan review, 2026-10-29); roadmap item 40a, applies D9, D10, D20, D35, D96, D114, D116, D122, D123

Item 23a refused views and `CHECK` constraints in the Transact-SQL dialect (D122), because each
keeps the dialect it was written in inside the database file (D114, D116), and the file had no
code for SQL Server. Item 40 restores SSMS and sqlpackage scripts, which are full of both, so
item 40a adds the code first, in a pull request of its own (D35: a file-format change).

**What changes in the file.** One byte value, in two places:
- the dialect byte of each `CHECK` entry in the constraints part of a table definition (format
  versions 6 and 7): `0` PostgreSQL, `1` MySQL, `2` SQLite, `3` Oracle, and now **`4` SQL Server**;
- the dialect byte of a view record (format version 8, its second byte): the same codes.

Nothing else is new: the record layouts, their versions and every existing record keep their exact
bytes, which tests pin (written by hand from the layouts, never captured from the encoder). The
encoder used to map SQL Server to `0`, but nothing ever wrote it: views and `CHECK`s were refused in
Transact-SQL, and its defaults are stored as PostgreSQL text (D123).

**Why no new version byte.** No released EggDB reads SQL records at all: v0.1.0 has no SQL layer,
so v0.2.0, which carries this change, is the first release whose files hold them (D20's promise
starts there). A development build from before this change meets a `4` as damage (`XX001`), a
refusal and never a misreading, because the decoder has no default for unknown codes. A version 9
would also have to be split again by version 7's "schema-qualified or not" rule. The D96 sample
files hold no SQL records and are untouched. **For later:** after v0.2.0, a new dialect code needs a
new version byte, because v0.2.0 reads an unknown code as damage, not as "written by a newer EggDB".

**Stored Transact-SQL text is part of the format.** A view's query and a `CHECK`'s expression are
kept as written and parsed again in Transact-SQL when used. A test keeps a corpus of such texts and
pins what each one means by its results (rows a `CHECK` accepts and refuses, rows a view returns),
so a later parser change that alters a stored text's meaning fails CI.

**Views in Transact-SQL.** `CREATE VIEW`, `ALTER VIEW` (Msg 208 when the view is missing) and
`CREATE OR ALTER VIEW`, with a column list and `WITH SCHEMABINDING` or `VIEW_METADATA`, accepted
without effect; `WITH ENCRYPTION` and `WITH CHECK OPTION` are 40517.
- **Msg 111** when the view is not the only statement of its batch; **Msg 1033** for `ORDER BY`
  without `TOP` or `OFFSET`; Msg 2714 for a name in use; **Msg 4511** for a column without a
  name (an expression without an alias and no column list, or any unnamed column of a `SELECT *`
  view, whose columns are found again by name). With a column list, an unnamed expression takes
  the list's name in the record, where the view record requires a non-empty name.
- `ALTER VIEW` and `CREATE OR ALTER VIEW` may change the view's columns freely, as SQL Server
  allows, and the views that use it are not checked (in any dialect): one fails when used if a
  column it names is gone, and otherwise sees the new columns and their types.
- `ALTER VIEW` of a table is refused with the generic Msg 50000 (SQLSTATE `42809`): SQL Server's
  own number for it could not be confirmed from public sources (decided by research).
- A table may be dropped under a Transact-SQL view, which then fails with Msg 208 when used, as SQL
  Server's views without `SCHEMABINDING` do. A `SELECT *` view follows MySQL's and Oracle's rule of
  D116 (each column found again by the name it had), and one that no longer matches is **Msg
  4413**.

**`CHECK` constraints in Transact-SQL**, inline, at table level and through `ALTER TABLE ... ADD`.
A violation is Msg 547, now also worded for `ALTER TABLE`. A subquery in one is Msg 1046 and an
aggregate Msg 175, both severity 15 (numbers and wording from public transcripts and Microsoft's
GROUP BY troubleshooting page; the severities are unconfirmed, decided by research). An unnamed one is called
`ck__<table>__<column>` (or `ck__<table>`), numbered on a clash, in lower case so that
Transact-SQL, which reads every name in lower case, can drop it by that name. SQL Server adds
random hex digits instead (a known difference).

**Renames.** Renaming a column rewrites the `CHECK` texts that name it in their own dialect, now
`[name]` with `]` doubled in Transact-SQL. Transact-SQL reads every name, bracketed or not, in
lower case (D122), so a rename to a name that is not its own lower-case form, of a column a
Transact-SQL `CHECK` names, is refused with `0A000`: the stored text could otherwise no longer find
the column. A view's text is not rewritten by a rename in any dialect (D116), so a Transact-SQL
view that names a renamed column fails when used, as SQL Server's do after `sp_rename`.

**Across dialects (a known difference, decided by plan review).** A `CHECK` or view written in
Transact-SQL and used by another dialect's statement runs its own functions (`CONVERT`, `ISNULL`,
`DATEDIFF`) as Transact-SQL, but its implicit conversions, text-to-date parsing and the wording of
errors raised inside it follow the statement's dialect, and the same holds the other way. A guard
that switched the dialect while a stored expression runs was planned and cut: views produce rows
lazily and can have predicates pushed into them, so it could not be applied there, and for `CHECK`
and `DEFAULT` it would have cost a thread-local switch on every evaluation for a case that
restored SQL Server databases, used through TDS, rarely meet. A violation is always worded in the
dialect of the statement that broke it (a PostgreSQL `INSERT` gets `23514`, a Transact-SQL one Msg
547).

**Cut from item 40a, by the plan's own cut order:** `DEFAULT` expressions other than the
constants and functions D123 folds (a new default tag), and `IDENTITY` seeds and increments other
than (1, 1) (another tag). Item 40's restore reports a default it cannot keep and rewrites other
seeds to (1, 1), listing each as a known difference; both remain on the roadmap.

**Tests.** Pinned bytes for a Transact-SQL `CHECK` table and view and for the four older codes; every
code from 5 to 255 refused as damage in both records (as a build before this change refuses 4);
every truncation, and 20,000 seeded random damages of each record, give an error and never a
panic; the stored-text corpus; Transact-SQL cases from Microsoft's CREATE VIEW, ALTER VIEW, CHECK
constraints and ALTER TABLE pages in the correctness suite; cross-dialect, rename and hostile
statement tests. A second, security-only review of the decoder and the stored-text parsing is part
of the merge (D35).
