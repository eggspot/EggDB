## D252 Public proof starts with a reproduction script, a weekly compatibility farm and measured energy — Decided by the build loop (by judgement, 2026-10-31); refines D44, D101 and D239

Track 4.X-24 asks that users can rerun every benchmark from a published repository, see the
weekly compatibility matrix and see joules per query.

- **One command to reproduce.** `scripts/reproduce-benchmarks.sh <dir>` records the commit, the
  machine (CPU, cores, memory, OS) and the toolchain, then runs the same two harnesses as CI
  (`eggdb-bench` and the SQLite comparison) with `--results`, so anyone's numbers can be compared
  line by line with `benchmarks/baseline.txt` and with each other. The benchmark code and data
  generators are already in this public repository, so it is the published benchmark
  repository; a separate one would only drift from it.
- **A weekly farm.** `scripts/compatibility.sh` holds the tool checks that the non-gating
  `compatibility` job runs on pull requests. The `Compatibility farm` workflow runs it every
  Monday and on demand, writing the matrix to the run summary and to an artifact kept 90 days.
  Each new tool joins the script, so both runs grow together. Standard runners are free for this
  public repository, and one weekly run is the rare schedule the CI rules allow.
- **Energy is measured where the hardware allows.** The script reads Intel's RAPL package
  counter around `eggdb-bench` when it is readable. It reports the run's millijoules and gates
  nothing until D44's method is fixed. Joules per query need per-workload counts and a quiet
  machine; they come with the dedicated benchmark host, which needs hardware the owner provides.

Left: pinned benchmark hardware and its published descriptions, joules per query per workload,
idle wake-ups, a public results page, chaos testing for clusters, the metering API, and the
matrix of every driver and ORM version (D12, D16) in the farm.
