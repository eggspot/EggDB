## D137 Transact-SQL batch logic: the batch compiled once into a small program of jumps over the parser's statements, each statement parsed again right before it runs with the variables' current values as constants; dynamic SQL as nested batches with their own scope — Decided by the build loop (by research, 2026-10-29); roadmap item 47, applies D1, D7, D9, D10, D122, D125, D132, D133; supersedes the single-statement `IF` of D132

Item 47 runs Transact-SQL's control-of-flow language: `DECLARE`d variables, `SET` and `SELECT`
assignment, `IF ... ELSE`, `BEGIN ... END`, `WHILE` with `BREAK` and `CONTINUE`, `RETURN`,
`BEGIN TRY ... END TRY BEGIN CATCH ... END CATCH` with the `ERROR_*()` functions, `THROW`,
`RAISERROR`, `PRINT`, `@@ERROR`, `XACT_STATE()`, dynamic SQL (`EXEC (...)`, `sp_executesql`)
and table variables that take `INSERT`, `UPDATE` and `DELETE`. Everything is written from
Microsoft's Transact-SQL reference (the control-of-flow, `TRY...CATCH`, `THROW`, `RAISERROR`,
`DECLARE @local_variable`, `SET @local_variable`, `SELECT @local_variable`, `sp_executesql`,
`@@ERROR` and `@@ROWCOUNT` pages) and [MS-TDS] 2.2.7.10 and 2.2.7.13 (the `INFO` and `ERROR`
tokens); no other database's source was read.

**One interpreter, over the statements the parser already has.** The session parses a statement
right before it runs it (the batch runner of D122 resumes the parser statement by statement).
Batch logic keeps that: `Parser::compile_batch` reads the whole batch once, as SQL Server
compiles a batch before running it, and turns its structure into a `tsql::Program`: a list of
`Instruction`s (`Run` a statement at a token position, `Test` a condition at a token position and
jump unless it holds, `Jump`, `Return`) plus the `TRY` blocks' instruction ranges and every
variable the batch declares. The session's runner walks the program: `Run` parses the statement
at its position again and runs it through the same path as any statement (`run_tokens`, with
its per-statement guards, catalog snapshot, sequences and errors in SQL Server's numbering), and
`Test` parses the condition as an expression and runs it as a one-row `SELECT`. Jumps are
indexes into the program, so `BREAK`, `CONTINUE`, `RETURN` and a jump out of a `TRY` block need
no unwinding. The rejected alternative, statements holding their nested statements as a tree run
recursively, would have had to clone and re-bind every nested statement on each loop iteration
(the binder rewrites a statement in place) and to run it outside the per-statement path.

**Variables become constants when a statement is parsed.** Each statement is parsed right
before it runs, so the parser reads `@name` as a constant holding the variable's current value
and declared type, as it already read `sp_executesql` parameters (D132). Statements keep using
indexes and the planner's constant folding (`WHERE id = @id` is a key lookup), and no expression
kind or evaluator path had to change. The cost is a parse per execution of a statement in a
loop, which the engine already pays for every statement. What this cannot express is a variable
read and assigned row by row in one `SELECT` (`SELECT @s = @s + name FROM t`): the constant
would be the value before the statement, so such a `SELECT` is refused (40517) rather than
answered differently; `SELECT @s += name FROM t` accumulates row by row and gives SQL Server's
result. The variables, the caught error and `@@ERROR` sit in a `BatchContext` behind an `Arc`
that the parser borrows; the session drops its copy before a statement runs, so an assignment
changes it in place.

**Scope follows SQL Server.** A variable is declared for the whole batch from its `DECLARE` on,
also when that `DECLARE` is in a branch that does not run, and a `DECLARE` without a value does
not reset it; table variables likewise. The compile pass checks names (137, 134), `BREAK` and
`CONTINUE` outside loops (135, 136), `RETURN` with a value (178), `THROW;` outside a `CATCH`
(10704) and mixed assignment `SELECT`s (141) before anything runs. An error inside a `TRY` block
moves to its `CATCH` block; the innermost `TRY` around the failing instruction is found from the
instruction ranges, and the `ERROR_*()` functions read the error caught by the innermost `CATCH`
block around the running instruction. Name resolution errors (207, 208) raised by the `TRY`
block's own statements are not caught, as SQL Server's deferred name resolution errors are not;
raised inside dynamic SQL they are. `THROW` ends the batch, `RAISERROR` of severity 11 to 18 ends
only its statement, and a condition that fails ends its `IF` or `WHILE`.

**Dynamic SQL is a nested batch.** `EXEC (...)` and `sp_executesql` evaluate their arguments as a
statement, then the runner compiles and runs the text with a fresh `BatchContext` and table
variables (the caller's are not visible), the `sp_executesql` parameters as its variables, and
copies `OUTPUT` parameters back afterwards. Its results and statement errors reach the client as
the caller's; an error that ends it, or any error when the caller is inside a `TRY` block,
becomes the `EXEC` statement's error in the caller. Nesting stops at 32 levels (Msg 217).

**Messages and errors in SQL Server's terms.** `QueryResult::info_messages` (`InfoMessage`:
number, severity, state, text) carries `PRINT` and low-severity `RAISERROR` text, which the TDS
server sends as `INFO` tokens before the statement's result; the text is also a notice for
other front ends. `SqlError` can carry a raised SQL Server error (`raised_in_sqlserver`): a
number up to 2147483647 (`SqlError::sqlserver_number`), a severity and a state
(`SqlError::sqlserver_state`), and whether it ends the batch; the TDS server sends the state in
the `ERROR` token. Statements that only assign variables report no step of their own, so loops
do not send a done token per assignment.

**What the protocol layer sees.** `Session::parameter_values_after_batch` gives a parameterized
batch's parameters as it left them, and the TDS server returns `OUTPUT` parameters with those
values in their declared types (the 1.04 echo of the sent bytes is gone).
`Session::take_unprepare_requests` hands over the handles `EXEC sp_unprepare n` released inside
a batch, which the TDS server forgets, since prepared handles stay a TDS concept (D132). The TDS
server registers each session's cancel signal and raises them all when it stops, and the runner
checks the signal before every condition, so a batch that loops forever ends with the server;
an attention signal from the client during a batch is still read only after it (the connection
reads one request at a time).

**Restoring scripts.** `eggdb restore --dialect sqlserver` runs SSMS's *Check for object
existence* guards, `IF [NOT] EXISTS (...)` and `IF OBJECT_ID(...) IS [NOT] NULL` around one
statement (in `BEGIN ... END` or not) and `EXEC sp_executesql N'...'` of a statement, counted as
the statement they guard; other batch logic in a script is still skipped and listed, since a
restore runs a dump's objects, not its deployment logic.
