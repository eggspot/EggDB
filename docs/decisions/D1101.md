## D1101 Stateless compute nodes: read-only servers over a page store that follow the writer's manifest — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D18, D1099)

- **Shape.** Storage is the page store of D1099; compute is any number of `eggdb serve --page-store s3://... --read-only` servers, each with a local cache that starts empty. They scale apart from storage: add or remove servers without moving data, and each fetches only the pages its queries read. Writes go to the one writer.
- **Following.** `Database::refresh_page_store` reads the manifest. When its generation moved, it opens a fresh `PageStoreFile` and page cache over it (the log replay at open brings the newest commits in), and swaps it in under the store with `Store::replace_cache`. That is refused while a read transaction or the writer holds the old cache (`SnapshotTooOld`), so a query never sees two states. `serve` retries every two seconds, so a node lags the writer by about two seconds plus the time its longest query runs.
- **Two caches.** A follower alternates between two local cache files (`.page-cache-a` and `.page-cache-b`), so building the new view never overwrites chunks the old view is still reading. Each cache's `.chunks` record lets it keep the chunks the newer manifest still names.
- **Grace for old manifests.** A writer no longer deletes a superseded chunk version at once. It lists it as retired in the manifest and deletes it after 15 minutes (`RETIRED_KEPT_MS`), so a follower on a recent manifest never finds a chunk it needs gone.
- **Left.** Read-your-writes across nodes (routing a session's reads to the writer after it writes), and autoscaling policy, which belongs to the platform (Kubernetes), not the engine.
