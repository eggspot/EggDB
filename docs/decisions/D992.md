## D992 MySQL's zero dates — Decided by the code-only session (2026-11-13, D355); roadmap M10, MySQL's types (D19, D153)

- In the MySQL dialect, `'0000-00-00'` is read into a `DATE` and `'0000-00-00 00:00:00'` (with or without a zero
  fraction, `T` or a space) into a `DATETIME` or `TIMESTAMP` as MySQL's zero date, so `mysqldump` output and
  applications from servers whose `sql_mode` allows zero dates load unchanged. Other dialects refuse them as before.
- The zero date is stored as the day just below EggDB's earliest date (`MIN_DATE - 1`) and the zero time stamp as the
  microsecond just below the earliest time stamp, so they sort below every other date, as MySQL's do, and no
  arithmetic on them can overflow. They print as `0000-00-00` and `0000-00-00 00:00:00` in every dialect.
- File format: the decoder's validity check widens by these two values, as D153 widened `time`. Old files decode as
  before; a file holding a zero date is refused by an older binary as damaged, never misread.
- Known differences: MySQL's `sql_mode` (`NO_ZERO_DATE`, `NO_ZERO_IN_DATE`) is not enforced, so zero dates are always
  accepted in the MySQL dialect; dates with only a zero month or day (`2024-00-15`) are still refused; date
  arithmetic on a zero date gives a date in 4714 BC where MySQL gives `NULL`. `DATE_FORMAT` and `EXTRACT`-style parts
  already treat it as MySQL does (D414).

**Status:** code written, unbuilt (code-only mode, D355).
