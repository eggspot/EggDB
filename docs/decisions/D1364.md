## D1364 Stored roles log in to the RESP listener — Decided by the code-only session (2026-11-25, D355); roadmap M6b "Redis ACLs, MongoDB roles, Elasticsearch roles and Cassandra roles mapped onto the one role model" (D22), the RESP part

- **What users get.** `eggdb serve --resp-listen` takes `AUTH <role> <password>` (and `HELLO <v> AUTH <role> <password>`) for every stored role that may log in and has a password, the same role and password `psql` uses. What the role reaches follows the one role model (D22): a superuser or a member of `pg_write_all_data` runs every command, a member of `pg_read_all_data` runs the commands that read and gets `NOPERM` for every write, and a role holding neither gets `WRONGPASS`, as an unknown user does. `AUTH <password>` and the default user keep working as before.
- **Why PostgreSQL's predefined roles.** The key-value, document, search and wide-column protocols have no tables to grant on. `pg_read_all_data` and `pg_write_all_data` are PostgreSQL's own roles for "read everything" and "write everything", already in the catalogs (`pg_roles`) and granted with plain `GRANT pg_read_all_data TO app`, so the same grant gives the same reach in SQL and over every protocol, which is the roadmap item's check. Finer grants (per key prefix, per collection) come with the per-protocol items; D1359's `keys=` already narrows MCP agents.
- **How reads stay reads.** A read-only login's commands run against `eggdb_keyspace::ReadOnlyKeyspace`, which reads through and refuses every write transaction with the protocol's error, so no list of write commands has to be kept in step with the command table: a blocking pop, a script's `redis.call('SET', ...)` and `FUNCTION LOAD` fail the same way. The password is checked against the role's SCRAM-SHA-256 verifier (`ScramVerifier::matches_password`), so it is never stored or compared in plain text.
- **Where.** `eggdb_sql::protocol_access` decides the reach from the stored role and its memberships; `eggdb_resp::Logins` is the RESP server's hook (`serve_with_logins`); `eggdb serve` implements it over the served file (`serve_resp::RoleLogins`). `ReadOnlyKeyspace` sits in `eggdb-keyspace`, so the MongoDB, Elasticsearch and Cassandra listeners can use the same guard when they take role logins.
- **Left.** Logins for the MongoDB (SCRAM over `saslStart`), Elasticsearch (basic authentication) and Cassandra (SASL `PLAIN`) listeners; `PUBLISH` for read-only logins (it touches no keys, so it is not refused yet); `ACL WHOAMI` and `ACL LIST` answering with the roles.
- **Proof.** A RESP server test with two known users: the writer sets a key, the reader reads it and gets `NOPERM` for `SET`, a wrong password falls back to the default user's check (`WRONGPASS`), `HELLO 2 AUTH` logs the reader in, and the default password still works.
