## D330 Redis bitmaps, HyperLogLog and geo commands over RESP, in Redis's own value formats and under the memory budget — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M7, extends D193, applies D9, D19 and D307

D19 lists bitmaps, HyperLogLog and geo among the Redis types EggDB keeps, and D193's RESP server
had none of them, so a client calling `SETBIT`, `PFADD` or `GEOADD` got `unknown command`. They
are built in `eggdb-resp` from the public command reference on redis.io (syntax, replies, error
texts and each page's examples), the public HyperLogLog layout Redis documents (the `HYLL`
header with dense and sparse encodings), Austin Appleby's public-domain MurmurHash64A, Otmar
Ertl's paper "New cardinality estimation algorithms for HyperLogLog sketches" (arXiv:1702.01284)
and the public geohash scheme. No Redis source is read (D1). None of the three is a new stored
type: as in Redis, bitmaps and HyperLogLogs are strings and a geo index is a sorted set, so
`TYPE`, `GET`, `ZRANGE`, `WRONGTYPE`, expiry, `MULTI`/`EXEC`, eviction and AOF restore treat them
like the strings and sorted sets they are, and the record format is unchanged.

- **Bitmaps** (`bitmaps.rs`). `SETBIT` and `GETBIT` address bits from the most significant bit of
  the first byte; `SETBIT` grows the string with zero bytes. `BITCOUNT` and `BITPOS` take a
  `start end` range in `BYTE` (the default) or `BIT` units with negative indexes from the end,
  clamped as Redis clamps them (both negative and reversed counts nothing); `BITPOS` for a clear
  bit without an end answers the first bit past the string, as documented. `BITOP` does `AND`,
  `OR`, `XOR`, `NOT` and Redis 8.2's `DIFF`, `DIFF1`, `ANDOR` and `ONE`, padding shorter strings
  with zeros, storing a result as long as the longest source without an expiry, and deleting the
  destination when every source is empty. `BITFIELD` runs `GET`, `SET` and `INCRBY` on signed
  fields of 1 to 64 bits and unsigned fields of 1 to 63 bits at bit offsets or `#n` field
  indexes, with `OVERFLOW WRAP|SAT|FAIL` applying to the operations after it (`FAIL` answers nil
  and writes nothing; an unsigned `SET` reads its value as 64-bit unsigned, as Redis does, so
  `SET u8 0 -1` saturates to 255); a command with a write first grows the string to its highest
  written bit. `BITFIELD_RO` takes only `GET`.
- **HyperLogLog** (`hyperloglog.rs`). A sketch is the string Redis documents: `HYLL`, an encoding
  byte (0 dense, 1 sparse), three zero bytes, and the cached cardinality as 8 little-endian bytes
  whose top bit marks it stale, then 16,384 registers, dense (6 bits each, least significant bit
  first, 12,304 bytes in all) or sparse (`ZERO`, `XZERO` and `VAL` runs). Elements are hashed with
  MurmurHash64A (seed `0xadc83b19`): 14 bits choose the register and the run of zeros after them
  (plus one, at most 51) is its value. The count is Ertl's estimator over the register histogram,
  standard error 0.81%. A new sketch is sparse and turns dense when a register passes 32 or the
  sparse form passes 3,000 bytes; it never turns back. `PFADD` answers 1 when a register changed
  (or the key was created) and marks the cache stale; `PFCOUNT` of one key answers the cache or
  computes and stores it, of several keys merges them without storing; `PFMERGE` takes the
  register maximum of the destination and the sources, dense when any input is dense, keeping the
  destination's expiry. A string that is not a sketch answers `WRONGTYPE Key is not a valid
  HyperLogLog string value.`, a sparse body whose runs do not add up to 16,384 registers
  `INVALIDOBJ Corrupted HLL object detected`. An estimate past 2^63 - 1 (every register at its
  top, which no real input reaches, only crafted bytes) is clamped there, so the reply stays
  positive and the cache stays valid. So a sketch copied from Redis with `GET`/`SET`
  counts the same here, and the other way round.
- **Geo** (`geohash.rs`, `geo.rs`). `GEOADD` (`NX`, `XX`, `CH`) stores each member in a sorted set
  with its 52-bit geohash as the score: 26 steps over longitudes -180 to 180 and latitudes
  -85.05112878 to 85.05112878, latitude bits even and longitude bits odd. Positions are decoded to
  the centre of their cell, so `GEOPOS` answers Redis's coordinates, printed with 17 decimals and
  trailing zeros removed. Distances are the haversine on a sphere of radius 6,372,797.560856 m,
  in `m`, `km`, `ft` or `mi`, printed with 4 decimals. `GEOHASH` re-encodes the position over
  latitudes -90 to 90 into the standard 11-character base-32 geohash. `GEOSEARCH` (`FROMMEMBER`
  or `FROMLONLAT`, `BYRADIUS` or `BYBOX`, `ASC`/`DESC`, `COUNT [ANY]`, `WITHCOORD`, `WITHDIST`,
  `WITHHASH`), `GEOSEARCHSTORE` (`STOREDIST` stores the distance in the query's unit as the
  score), `GEORADIUS` and `GEORADIUSBYMEMBER` (with `STORE` and `STOREDIST`) and their `_RO`
  forms share one search; `COUNT` without an order sorts nearest first, as Redis does, and a box
  keeps the points within half its height in latitude and half its width along the point's
  parallel. A store with no result deletes the destination and answers 0.
- **Errors** are Redis's texts: `bit offset is not an integer or out of range` (an offset below 0
  or at 2^32 bits, the 512 MB string limit), `bit is not an integer or out of range`, `The bit
  argument must be 1 or 0.`, the bitfield type and `OVERFLOW` messages, `invalid
  longitude,latitude pair` with six decimals, `unsupported unit provided. please use M, KM, FT,
  MI`, `could not decode requested zset member`, the `GEOSEARCH` option messages and
  `WRONGTYPE`. Arity is Redis's: `GEOSEARCH` needs 6 arguments after its name, `GEOSEARCHSTORE` 7
  and `GEODIST` 3, and `GEODIST` with more than 4 answers `ERR syntax error`.
- **Memory.** A command that grows a string (`SETBIT`, `BITFIELD`, `BITOP`'s result) first checks
  the new length against the room the server's memory budget has left (`Context::
  check_value_room`, the same room `-OOM` replies use, D307), so `SETBIT key 4294967295 1`
  against a small `--max-connection-memory` answers `-OOM` and creates nothing. Sketches are at
  most 12,304 bytes.

Tests (`tests_bitmaps_hll_geo.rs`) replay every example of the redis.io pages of these commands
with their documented replies (the Sicily coordinates, distances, geohashes and stored scores
included), the error texts, the budget, a 20,000-element sketch that turns dense and counts
within three standard errors, and a redis-cli-style session of RESP arrays and inline commands
through `RequestReader`; CI's RESP step runs `SETBIT`, `BITCOUNT`, `PFADD`, `PFCOUNT`, `GEOADD`
and `GEODIST` through `redis-cli` too.

Decided by research:
- *Command name in the `GEOSEARCH` option errors.* Redis echoes the command as the client typed
  it; EggDB writes it in capitals (`... can be specified for GEOSEARCH`), which is how redis-cli
  users and the documentation spell it.
- *Order of results without `ASC`, `DESC` or `COUNT`.* Redis answers in the order it scans its
  nine neighbouring geohash cells, which the documentation leaves unspecified; EggDB answers in
  geohash (score) order, which matches the documented examples.
- *Stored distances.* `GEOSEARCHSTORE ... STOREDIST` scores print with the shortest form that
  reads back exactly (`56.4412578701582`), as current Redis does; the documentation's older
  examples show 17 digits.

Left: coordinates are bulk strings in RESP3 too (Redis sends RESP3 doubles carrying the same
17-decimal text, which needs a preformatted double reply); a search scans every member of the
sorted set rather than the geohash ranges of the nine neighbouring cells, so large indexes wait
for D193's per-element storage; `GETRANGE`'s sibling `SETRANGE` and `PFDEBUG`/`PFSELFTEST`;
RESP benchmarks of these commands against Redis (M7's redis-benchmark and memtier item).
