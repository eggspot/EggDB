## D143 EggDB's command model: one registry crate, `eggdb-commands`, of command and tool definitions that the CLI, its help and the MCP server read; the kept names; error codes with the shared categories and per-command exit codes; JSON errors only when JSON is asked for; `restore` keeps "bring back" — Decided by the build loop (by research, 2026-10-30); command model slice 1 (batch part 2.1), applies the approved design of 2026-10-28 and D11, D15, D90, D98, D119, D120, D121

The owner chose on 2026-10-28 a shared command model for EggOS and EggDB rather than a new
language: EggDB keeps SQL and its key-value commands, and the model is the layer above them (the
same verbs, answers, errors and safety fields for people and agents). Slice 1 brings it to the
commands agents use (`get`, `scan`, `sql`, `check`, `stats`, `export`) and to the eight MCP tools.
The shared spec's canonical copy is EggOS's `docs/ux/command-model.md`; EggDB's
[ux/command-model.md](../ux/command-model.md) holds EggDB's tables and, until EggOS's copy lands,
the shared rules in short.

**The registry.** A new crate, `crates/eggdb-commands`, with no dependencies, holds two
definition types, `CommandDefinition` (not `Command`, which would clash with
`std::process::Command`) and `ToolDefinition`, as two `'static` const tables, `COMMANDS` and
`TOOLS`, beside `ERROR_CODES` (each code with its shared `Category`), `CORE_VERBS`,
`KEPT_NAMES`, `SHIPPED_TOOL_NAMES` and `COMMON_OPTIONS`. The `eggdb` binary's CLI and `eggdb-mcp`
both read it, and `eggdb-mcp` still does not depend on the `eggdb` library (D98). A tool is not a
renamed command: it has its own arguments, each mapped to an option or operand of its CLI twin
(or to a call limit, or nowhere yet), the options it always passes, its `max_effect`, `grant`
(`--allow-write` or none), `idempotent`, `open_world` and per-call `confirm` check, and its MCP
annotations are computed from those (`read` is read-only; `destroy` and `control` are
destructive). The MCP server's `tools/list` (names, titles, descriptions, input schemas and
annotations) is generated from it, and a test keeps the shipped generator as an oracle to prove
the output is byte for byte what shipped. The commands' usage lines and help bodies moved into
the registry verbatim, so `eggdb help <command>` prints what it printed.

**Names.** `eggdb`'s top-level commands act on its implied noun, the database file. Every
shipped command name is kept (`create`, `put`, `get`, `del` with the alias `delete`, `scan`,
`ttl`, `expire`, `persist`, `incr`, `decr`, `cas`, `check`, `stats`, `backup`, `compact`, `ui`,
`export`, `import`, `sql`, `serve`, `shell`, `restore`, `mcp`, `audit`, `help`, `version`), and
`collection list|add|delete` is a noun with core verbs. A test fails on any command of the parser
that is neither. `restore` keeps one meaning, "bring back", as EggOS's `wm restore` and Trash do.

**Errors.** Codes stay per product; each has one of the thirteen shared categories, and each
command declares its codes with its exit code (EggDB keeps D90's 0 to 5). MCP errors keep every
shipped field and gain `category`, and `damaged` gains `fix_command: eggdb check <file>`. The
CLI's failures carry a code: from the engine's `ErrorKind` where there is one, otherwise from
the exit code (`database_failed` for 3). A SQL error whose SQLSTATE means corruption or a lock is
`damaged` or `database_busy`, so code and exit agree. `not_a_database` and `incompatible` are
`refused`, not `failed`: nothing broke, and a retry cannot help.

**JSON only when asked for.** `--json` is another spelling of `--format json`, and the last of
the two given wins. The JSON error form, one line on stderr
(`{"error":{"code","category","message","usage","fix_command"}}`, `message` exactly the text
message), appears only when the command line asks for JSON (`--json`, `--format json`,
`-F json`), never because stdout is a pipe: a pipe already defaults the data to JSON for most
commands, but its errors have shipped as text and scripts rely on them. `eggdb sql` gains a JSON
form (one line per statement, the MCP result without its per-call envelope) and keeps text as
its default in a pipe, since its text has shipped there. `fix` is left out of CLI errors because
every CLI message ends with its own "what to do"; `fix_command` appears exactly when the text
form prints a `try:` line. `eggdb help --json` prints the registry, with the commands not in it
yet listed by words and usage only.

**Instructions.** The MCP server's `instructions` are generated from the registry: the effects,
the session's grant, the error categories and that `fix` and `fix_command` are the way out of an
error, plus what the two shipped texts said.

**Tests.** The registry test (fields, kept names and core verbs, the `_` rule for new tool names
with shipped names only from the list, annotations from fields, every argument mapping onto its
twin), the parity test (`kv_get`/`get`, `kv_scan`/`scan`, `run_sql` and `write_sql`/`sql` by
value once the envelope is removed, and the same failures by code and category, through the
built binaries), the help test (`help --json` lists exactly the registry; the main help lists
each registered command with its synopsis and summary; the doc's tables list every command, tool,
code and kept name), the shipped `tools/list` oracle, and every existing CLI and MCP test.

Decided by research, where the design left it open:
- *JSON errors and pipes:* only an explicit request, so no shipped stderr text changes in a pipe;
  explicit `--format json` switches the errors too, since it and `--json` are one setting.
- *`sql` and JSON:* `sql --format json` was a usage error (exit 2), and is now the JSON form; the
  shipped usage test checks `--format hex` instead, which stays a usage error.
- *`help --json` for a command not in the registry yet* prints its words and usage, exit 0,
  rather than an error, since the user did nothing wrong.
