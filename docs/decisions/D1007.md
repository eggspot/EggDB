## D1007 SQL/PGQ property graphs over tables — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D10, D206)

- `CREATE [OR REPLACE] PROPERTY GRAPH name VERTEX TABLES (...) [EDGE TABLES (...)]` and `DROP PROPERTY GRAPH [IF
  EXISTS] name` follow SQL:2023 part 16 (SQL/PGQ). Each element table takes `AS alias`, `KEY (...)`, `LABEL name`
  (several allowed), `DEFAULT LABEL`, `PROPERTIES (column [AS name], ...)`, `PROPERTIES ARE ALL COLUMNS` and `NO
  PROPERTIES`; an edge table needs `SOURCE KEY (...) REFERENCES vertex (...)` and `DESTINATION KEY (...)
  REFERENCES vertex (...)`. A table with no label gets its alias as its label.
- Definitions are kept as their statement text in `eggdb_internal.property_graphs (name, definition)`, so a graph
  is part of the database's one backup and needs no new storage format. The graph is a view: nothing is copied
  and every query reads the tables as they are.
- `GRAPH_TABLE (graph MATCH pattern [WHERE ...] COLUMNS (...))` is rewritten before the statement is parsed, in
  the session's pre-pass beside the database-link one (D997): every combination of vertex and edge tables the
  pattern's labels (`IS a|b` or `:a|b`) and directions (`->`, `<-`, `-`) allow becomes one `SELECT` of joins on
  the source and destination keys, and the combinations are joined with `UNION ALL` (at most 64). Element `WHERE`
  conditions and the pattern's `WHERE` become the `SELECT`'s `WHERE`; renamed properties are written back as their
  columns. A `GRAPH_TABLE` with no alias gets `AS graph_table`.
- Rewriting at the text level keeps the planner unchanged: the joins are ordinary SQL, so indexes, pushdown and
  every dialect's planner work on them as on any join.
- Left: several comma-separated path patterns, quantified paths (`{m,n}`, `+`, `*`) in `GRAPH_TABLE`, `ONE ROW
  PER STEP`, and GQL's own statements over these graphs; the graph algorithms as SQL/PGQ procedures stay a
  separate roadmap item (D248).
