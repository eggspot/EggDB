## D354 Size, idle memory and startup have final targets, checked by the weekly performance pass, not by CI — Decided (owner, 2026-11-10, through Main Chat; targets by research); amends D6, refines D34, D101 and D230, ends D253's budget raises

**The owner's order (2026-11-10).** "Set the size target for final and do check on weekly review
only instead make it in ci let our ci focus on code and release." Pull-request and `main` CI
check code, and the release workflow keeps publishing every binary's size and download size
(D75). Binary size, idle memory and startup time are measured and trimmed in the weekly
performance pass, against final targets instead of budgets that move with every change.

**What changed in CI.**
- The `footprint` job is gone from `.github/workflows/ci.yml` and from `check`'s `needs`.
- The `bench` job runs `eggdb-bench --skip footprint`. Its `footprint.*` lines no longer run on
  pull requests, so a binary that doubles no longer blocks one. D101's 2x rule still applies to
  every other benchmark.
- `scripts/footprint.sh` stays, and so do the `footprint.*` benchmarks, for the weekly pass.

**The targets** (`benchmarks/footprint.txt`, one line per system, profile and metric). They are
ceilings for the finished product, not for today. Sizes are stripped release builds; peak memory is
the process's peak resident set; ratios are start times against a Rust program that exits at once
(`eggdb-bench`'s `footprint.start` and `footprint.open_and_get`, D94).

| Metric | Linux x86-64 | macOS arm64 | Today, Linux / macOS |
|--------|--------------|-------------|----------------------|
| `full` binary (`eggdb`) | 64 MiB | 48 MiB | 17.3 / 13.3 MiB |
| `embedded` C API library | 16 MiB | 12 MiB | 10.4 / 8.2 MiB |
| `eggdb serve` idle, resident | 32 MiB | 32 MiB | not measured yet / 4.0 MiB |
| `eggdb --version`, peak resident | 8 MiB | 8 MiB | 2.9 / 1.6 MiB |
| `eggdb --version`, start ratio | 2.0 | 2.0 | 1.02 / 0.97 |
| `eggdb get` on a 10,000-entry file, peak resident | 16 MiB | 16 MiB | 5.4 / 2.2 MiB |
| `eggdb get` on a 10,000-entry file, start ratio | 3.0 | 3.0 | 1.42 / 1.05 |

**Why these numbers (research, 2026-11-10).** These are the measurements on the build Mac (Apple
silicon, macOS), with Homebrew's builds stripped:
- **SQLite 3.53.4:** the library is 1.3 MB and the CLI 1.6 MB. `sqlite3 -version` peaks at 2.1 MB,
  and a point select from a 10,000-row file at 3.0 MB.
- **PostgreSQL 17.11:** `postgres` is 8.8 MB and the installation 80 MB. It answers `pg_isready`
  15 to 38 ms after it starts, and idles at 41.6 MB resident across its six processes.
- **Redis:** not installed on the Mac (CI runs `redis:7` as a service container). Its
  documentation gives about 3 MB for an empty instance, and the first weekly pass measures it on
  CI's Linux runner beside EggDB.
- **EggDB (v0.5.0):** the `eggdb` binary is 13.9 MB and the C library 8.5 MB. `eggdb serve` prints
  its first line 10 ms after it starts and idles at 4.2 MB.

So:
- **The full binary replaces PostgreSQL, MySQL, SQL Server, Oracle, SQLite, Redis, MongoDB,
  Elasticsearch and the rest (D2).** 64 MiB on Linux is under PostgreSQL's installation alone
  and gives the roadmap's remaining models and protocols 3.7 times today's size. macOS builds
  are about 25% smaller, hence 48 MiB.
- **The `embedded` library holds every SQL dialect today.** Its 16 MiB and 12 MiB ceilings leave
  1.5 times today's size, so its growth is watched closely. The SQLite-sized target of D6 and
  D41 (smaller than SQLite on a microcontroller) belongs to a smaller profile still to be built
  (D34), which gets its own line when it exists.
- **Idle memory.** 32 MiB for an idle server is below PostgreSQL's 41.6 MiB, about 8 times
  today's macOS figure, and leaves room for the caches and listeners a server adds. 8 MiB and
  16 MiB for one-shot commands are about 4 and 5 times SQLite's 2.1 and 3.0 MB, and about 3 times
  today's Linux figures.
- **Startup.** D14 asks for a first start "well under a second". A ratio of 2.0 for
  `--version` and 3.0 for open-and-get keeps the binary's own start within a few milliseconds of
  any program's.

**The weekly pass (Saturdays, D101).** It runs `scripts/footprint.sh` on Linux and macOS. The
script measures every line above, prints each against its target with its share, and writes the
table to the job summary when `GITHUB_STEP_SUMMARY` is set:
- `OVER` (above the target) fails the script, and the pass trims the binary or the memory in
  that pass;
- `NEAR` (80% of the target or more) is the trend warning: the pass finds where the bytes went
  (the text section's size per crate, D253's method) and trims them before the next pass;
- everything else is reported only.

Targets change only by a new decision. Budgets are no longer raised per pull request, which
ends D253's raises.

**Not covered yet.** The `server` profile is not built as an artifact of its own (D230), so it
has no line. `serve`'s time to its first line is measured by hand, not by the script, because
bash has no portable clock below a second. The WebAssembly module's line is printed when it was
built and has no target until the browser build is measured (D230).
