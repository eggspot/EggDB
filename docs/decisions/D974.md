## D974 Compaction's lock window closed by checking the locked file is still at its path — Decided by the code-only session (2026-11-13, D355); roadmap M14, D141's known limit

- D141 left a window: a program that opened the database's path an instant before a compaction renamed the
  compacted file over it, and took its lock after the compaction closed the old file, would write to the replaced
  file.
- The platform layer now names files by identity (`FileIdentity`: device and inode on Unix systems, volume serial
  number and file index on Windows, read with `GetFileInformationByHandle` through a handle opened for attributes
  only): `OsFile::identity` for an open handle and `file_identity_at` for whatever a path leads to now. Where the
  platform cannot tell (targets without either), both answer `Unsupported`.
- Opening a database file records the identity of the handle it opened, takes the lock as before, and then checks the
  path still leads to that file. If the path was renamed over meanwhile, it drops that handle and its lock and opens
  the path again, up to eight times, and answers `Locked` if the file keeps changing under it. A failed identity
  check (`Unsupported`) keeps today's behaviour.
- `file_identity::tests` renames a file over a path a handle holds and checks the identities differ.

**Status:** code written, unbuilt (code-only mode, D355).
