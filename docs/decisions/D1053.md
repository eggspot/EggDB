## D1053 Benchmarks at scale: YCSB and a TPC-C mix on a Raft cluster — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D7, D18)

- `eggdb-cluster-bench` (a workspace binary, never shipped) starts `eggdb serve --cluster` processes on one machine,
  waits for the node that takes writes, loads the data through it, and drives the workload over the PostgreSQL protocol
  with EggDB's own client, so what it measures is what an application on the cluster sees: commits that return once a
  majority stored them (D1038), and reads on followers.
- **YCSB.** Core workloads A (50 % reads, 50 % updates), B (95/5) and C (read only) over `usertable` with one 100-byte
  field, keys chosen with YCSB's scrambled Zipfian distribution (constant 0.99, Gray et al.'s method). Updates go to the
  leader; reads are spread over every node.
- **TPC-C.** The specification's nine tables and five transactions in its mix (45 % New-Order, 43 % Payment, 4 % each of
  Order-Status, Delivery and Stock-Level), with NURand for customers and items and each client at home in one
  warehouse. Cardinalities are reduced (10,000 items, 300 customers per district, no initial orders) so a run loads in
  seconds; the result is reported as tpmC but is not an audited TPC-C result, which needs the full scale and an
  auditor (an owner decision, as D58's audited LDBC run is).
- Every run prints `name value unit` lines (throughput, p50 and p99 per operation, tpmC, aborted transactions).
  `cluster-bench.yml` runs the four workloads weekly in the Saturday performance pass (D7, D101) and keeps the lines;
  they are not a PR gate, as cluster numbers on shared runners vary too much for one.
- Learned from the YCSB paper and core workload definitions and the TPC-C specification; no code was read.
