## D1027 Delayed standbys and standbys fed by log shipping — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D18, D1019, D1024)

- **Log shipping is the change archive.** A standby in another region needs no connection to the primary: the
  primary's change archive (D1019) is its log, and any file transport (a shared volume, `rsync`, object storage
  synced to a directory) ships its segments. `eggdb serve <file> --standby-of <directory>` applies every archived
  commit after its position, in order, each in one transaction with its position, and reads the directory again
  every second; segments it has fully read are not read again, by segment number, so pruning (D1020) cannot make it
  skip one. The standby serves reads and refuses writes (it is fenced, D1026).
- **Where a standby starts.** `eggdb restore` now records, in the restored copy, the stamp of the last archived
  commit it holds (the copy's own, or the last replayed one), under a reserved engine key. A standby without one
  refuses to start, with the command that gives it one.
- **Delayed standbys.** `--apply-delay <seconds>` applies each commit only once its commit stamp (which carries the
  primary's time in microseconds) is that old, so a delayed standby still holds the database as it was before a
  mistaken `DROP` or `DELETE` reached it, for as long as the delay.
- A gap in the archive (commits the primary made without archiving them) stops the standby with a message to
  restore it again; it never applies a history with a hole. Promoting a standby to a primary is the replication
  switchover's work (D1026) once it is restarted as a replica, and is left for a later slice.
