## D1342 WHERE filters compiled once per scan into a flat program — Decided by the code-only session (2026-11-25, D355); roadmap M5 "A query compiler for hot prepared statements' expressions, compiled to a flat program" (D40)

- **What users get.** A scan's `WHERE` clause no longer walks the expression tree and resolves column names for every row when it is made of what the program runs: columns, integer, boolean and `NULL` constants, `=`, `<>`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, `NOT`, `IS [NOT] NULL` and bare boolean columns. The filter is compiled once per scan, of a table or of joined rows, with every column resolved to its place in the row.
- **Exactly the evaluator's answers.** The program uses SQL's three-valued logic and the engine's own comparison, and decides a comparison only when both sides are integers or both are booleans, the cases where the evaluator's comparison is plain ordering. Any other value in a row (text, numeric, floats, a type the column did not promise under SQLite's dynamic typing) makes it answer "undecided" for that row, and the scan asks the evaluator, so results and errors never change. Nothing the program runs can fail.
- **Why this first.** Keeping parsed plans in prepared statements, which the item waits on, is its own work; compiling per scan already removes the per-row name lookups for the filters that dominate scans, and the same program can be kept with a plan later.
- **Left.** Keeping programs with prepared statements' plans, compiling projections, arithmetic, text and numeric comparisons with their collations and conversions, and the TPC-H Q1 and Q6 timings.
- **Proof.** A unit test runs a filter with `OR`, `AND`, `IS NOT NULL` and comparisons over rows of mixed integer widths, `NULL`s and text, checking the three-valued answers and the deferral; a filter with a text constant does not compile.

**Status:** code written, unbuilt (code-only mode, D355).
