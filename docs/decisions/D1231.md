## D1231 ts_token_type, ts_parse and ts_debug — Decided by the code-only session (2026-11-17, D355); roadmap M8, text search (D30, D983)

- **What users get.** PostgreSQL's set-returning text search functions for looking inside the parser: `ts_token_type(['default'])` (`tokid`, `alias`, `description`, the 23 token types), `ts_parse('default', text)` (`tokid`, `token`, every token in order, blanks included) and `ts_debug([config,] text)` (`alias`, `description`, `token`, `dictionaries`, `dictionary`, `lexemes`), as psql's and pgAdmin's text search tools call them.
- **How.** Record rows like `hstore`'s `each` (D288) through the set-returning function table, from `eggdb_search`'s token types and word splitter; a blank is the text between two words. `ts_debug` names the dictionaries a built-in configuration maps the token's type to (`<language>_stem` for words, `simple` otherwise), the lexeme from the configuration, `{}` for a stop word, and NULL for blanks. The parser named must be PostgreSQL's `default`.
- **Left.** `ts_debug` of a configuration made with `CREATE TEXT SEARCH CONFIGURATION` (refused with `0A000`), `regdictionary[]` and `text[]` types for the list columns (given as array text), the other token types (`email`, `url`, `float`, ...) that EggDB's word splitter does not produce yet, `ts_stat` and `unnest(tsvector)`.
- **Proof.** `citext_tests.rs`: token types 1 and 23, a parse with blanks and a number, and `ts_debug` showing a stop word's `{}` and a stem; an unknown parser refused.
