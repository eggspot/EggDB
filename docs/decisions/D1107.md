## D1107 SQL tables synced offline-first through a capture trigger and the key-value sync replica — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D210, D228, D1106)

- **Rows become sync keys.** A synced row's key is `schema.table`, a zero byte and its primary key as JSON. Its value is the row as JSON, or none for a deletion. SQL tables thereby ride on D228's replica, stamps and last-writer-wins without a second sync format, and the server needs no copy of the tables' schema: it relays the user's space (D1106).
- **Capture on the device.** `CREATE EXTENSION eggdb_sync` and `eggdb_sync.enable(schema, table)` add an `AFTER` row trigger that logs each change in `eggdb_sync.outbox` in the same transaction, offline included. An update that changes the primary key logs a deletion of the old key and the new row. `sync_tables` hands outbox rows to the replica (each stamped by the device's hybrid clock) and removes them only after the replica has them, so a failure loses nothing.
- **Write-back without echo.** Changes from the server that won on the device's replica (`Replica::apply_changed`, `sync_over_http_changed`) are written into the tables by `eggdb_sync.write_row`, one transaction per batch, under the transaction-local setting `eggdb_sync.applying`, which the trigger skips. Received rows therefore never return to the outbox. Keys of tables not enabled on the device are kept in the replica but not written.
- **Cursors in the file.** The send and receive cursors are kept per server URL in the `eggdb.sync_cursors` collection, so each call moves only what is new and survives restarts. A call loops until neither cursor moves.
