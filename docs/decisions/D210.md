## D210 Change streams start as a trigger-fed transactional outbox delivered to webhooks — Decided by the build loop (by judgement, 2026-10-31); refines D28

Part 4.M14-5 asks for changes streamed in a Debezium-compatible format to Kafka, AMQP and
webhooks, with a built-in outbox.

- **The outbox is the capture.** `CREATE EXTENSION eggdb_cdc` installs `eggdb_cdc.outbox` and the
  row trigger function `eggdb_cdc.capture()`, which records `before` and `after` as JSON in the
  same transaction as the change: exactly the committed changes are captured, in commit order,
  with no new engine hook. Engine-level capture (all tables, no triggers, every data model)
  comes with the replication commit hook (D209).
- **Delivery is at least once.** `eggdb_sql::cdc::deliver_changes` hands the oldest events to a
  sink and deletes only those the sink accepted, stopping at the first refusal, so order holds
  and nothing is skipped. `eggdb serve --cdc-webhook` posts them to an `http://` URL with our own
  minimal HTTP client; Kafka and AMQP sinks come with those protocols (4.M16).
- **Events follow Debezium's documented envelope** (`before`, `after`, `source`, `op`, `ts_ms`)
  with schemas off, so consumers written for Debezium's JSON read them.

Left: Kafka, AMQP, MQTT and NATS sinks, https webhooks (TLS client), retries with backoff and a
dead-letter table, Debezium's `schema` section and transaction metadata, capture without
triggers, and a consumer test that receives every commit of a workload.
