## D975 SQL Server's partition functions and schemes — Decided by the code-only session (2026-11-13, D355); roadmap M2, D169's SQL Server half

- `CREATE PARTITION FUNCTION f (type) AS RANGE LEFT | RIGHT FOR VALUES (...)`, `CREATE PARTITION SCHEME s AS PARTITION f
  [ALL] TO (filegroups)` and their `DROP`s are kept in `eggdb_internal.sqlserver_partition_functions` and
  `…_schemes` (the boundaries as their source literals). Filegroups are accepted and ignored, as EggDB has one file.
  Errors follow SQL Server's: 2714 for a duplicate, 7702 for a scheme on an unknown function, 7706 for dropping a
  function a scheme uses, 7716 for dropping what does not exist, 1921 for a table on an unknown scheme.
- **Tables.** `CREATE TABLE t (...) ON s(column)` becomes a range-partitioned table on that column (the parser keeps
  the scheme in `PartitionBy::scheme`), and after it is created the session creates one partition per range of the
  function, `t_p1` … `t_p<n+1>`, numbered as SQL Server numbers partitions, through D316's `PARTITION OF` in
  PostgreSQL's dialect. Rows go to their partitions by the existing range routing and pruning.
- **`RANGE LEFT` without a format change.** EggDB's ranges are lower-inclusive and upper-exclusive; `RANGE RIGHT`
  boundaries map onto that directly. A `RANGE LEFT` boundary belongs to the range below it, so its range's upper bound
  is the next value after it: the integer plus one, the date plus one day, the timestamp plus one microsecond
  (EggDB's resolution), the string followed by `chr(1)` (no text holds `chr(0)`). Types with no next value
  (`decimal`, `float`, `money`) refuse `RANGE LEFT` with a message pointing to `RANGE RIGHT`.
- **Left.** `ALTER PARTITION FUNCTION ... SPLIT | MERGE RANGE`, `ALTER PARTITION SCHEME ... NEXT USED`,
  `$PARTITION.f(value)`, `sys.partition_functions`, `sys.partition_schemes` and `sys.partition_range_values`, and
  indexes created on a scheme (accepted, and built as for any partitioned table).
