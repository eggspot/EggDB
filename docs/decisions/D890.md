## D890 `QUALIFY` — Decided by the code-only session (2026-11-12, D355); roadmap M10, D240

- A `SELECT` takes `QUALIFY condition` after `WHERE`, `GROUP BY`, `HAVING` and `WINDOW`, as Snowflake, GoogleSQL,
  Spark SQL, Teradata and DuckDB write it: the rows whose condition holds after window functions are computed are
  kept, before `DISTINCT`, `ORDER BY` and `LIMIT`. It is accepted in every dialect, as an extension where the dialect
  has no such clause, since none of EggDB's dialects gives `qualify` another meaning after those clauses; `qualify`
  is now a clause word, so it is no longer read as a table's implicit alias.
- D240 planned a stage after window functions in the executor. The parser instead rewrites the select into a derived
  table, which needs no executor change: when the condition calls a window function, it becomes a hidden column of
  the select (named with EggDB's hidden-column marker, so `*` leaves it out) and the outer query keeps the rows where
  it is true; otherwise the condition runs in the outer query over the select's output columns, so
  `QUALIFY place <= 1` can name a window function's alias. `DISTINCT` moves to the outer query, after the filter.
- Limits of the rewrite: `ORDER BY` after `QUALIFY` names output columns (not source columns left out of the select
  list), and a condition that both calls a window function and names a select alias is refused by name resolution.
