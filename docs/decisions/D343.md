## D343 HTTP request bodies sent with `Content-Encoding: gzip` or `deflate` decoded before the handler on the Elasticsearch, REST API and InfluxDB write listeners, bounded by the body limit (`413` for a zip bomb) and the memory budget, and `400` for an HTTP/1.1 request without exactly one `Host` header — Decided by the build loop (batch 6, 2026-11-10); roadmap M6a, extends D325 and D249, applies D9 and D307

Clients compress what they upload: Elasticsearch clients (`http_compress`), Logstash, Beats and
Fluent Bit send gzip `_bulk` bodies, Telegraf and the InfluxDB clients send gzip line protocol,
and HTTP libraries add `Content-Encoding: deflate`. EggDB's HTTP server read those bodies as they
came, so a handler saw compressed bytes and the InfluxDB write route refused them with `415`.
RFC 9112 also asks a server to refuse an HTTP/1.1 request without a `Host` header, which EggDB
answered. Built from RFC 1950 (zlib), RFC 1951 (DEFLATE), RFC 1952 (gzip), RFC 9110 (content
codings, `415` with `Accept-Encoding`) and RFC 9112 (§3.2, `Host`).

- **The inflater stays in `eggdb-content`** (std only, no dependencies, D249), and `eggdb-http`
  depends on it; no new crate. Next to `inflate` it gains `gunzip(data, limit)` and
  `zlib_inflate(data, limit)`, both answering a `DecompressError`: `PastLimit(limit)` when the
  output would pass `limit`, or `Corrupt`. An internal `inflate_prefix` returns the output with
  the number of bytes the DEFLATE stream used, so the trailers after it can be read.
  - `gunzip` reads every member one after another (multi-member gzip, as `cat a.gz b.gz`
    makes), each header with its optional extra field, name, comment and header CRC-16 (checked),
    refuses reserved flags and methods other than DEFLATE, checks each member's CRC-32 and
    `ISIZE` (length modulo 2³²), counts `limit` over all members, and refuses bytes after the
    last member that are not another member.
  - `zlib_inflate` is HTTP's `deflate` coding: a zlib stream (window info at most 7, header
    check, no preset dictionary) with its Adler-32 checked and nothing after it; a body without
    a zlib header, or one that does not decode as zlib, is read as raw DEFLATE, as browsers
    accept, and must end where the stream ends.
  - `crc32` (zip.rs) now uses a 256-entry table built at compile time; same values, one
    lookup per byte instead of eight shifts, since every gzip body goes through it.
- **Opt-in per listener, per request.** `Limits::decode_content_encoding` is a function of the
  request answering whether its body is decoded; none by default
  (`Limits::decoding_content_encoding()` decodes every request,
  `decoding_content_encoding_of(f)` the ones `f` picks). `eggdb serve` decodes on the
  Elasticsearch listener (`--es-listen`), the REST API (`--rest-listen`) and the observability
  listener (`--observability-listen`) except Prometheus remote write
  (`eggdb_observability::wants_content_decoded`), whose body is snappy by the protocol and
  decoded by the endpoint itself. S3 stores bodies as sent (`Content-Encoding` is object
  metadata there), so it stays off, as do DynamoDB, SQS, MCP and the metrics listener. The
  field is a function and not the plain switch planned because the observability listener
  serves both InfluxDB writes and remote write on one port.
- **Decoding.** After the body is read (with `Content-Length` or chunked), the
  `Content-Encoding` values (every header line, comma-separated, case-insensitive) are undone
  last first: `gzip` and `x-gzip`, `deflate`, and `identity` (skipped). At most four stacked
  codings. The handler gets the decoded body, no `Content-Encoding` or `Transfer-Encoding`
  header, and a `Content-Length` with the decoded length. An empty body is passed on as it is.
- **Bounds.** Each decoded body may be at most the listener's `max_body_bytes` (the existing
  body limit; no second limit): a larger one, such as a 65 KB gzip of 10 MB of zeros, is
  answered `413` as soon as the inflater passes the limit, so a zip bomb never grows past it.
  The output is also limited to what the server's memory budget has left (at least the 64 KiB
  every connection may hold uncounted); passing that is the listener's over-budget answer
  (`503` with `Retry-After`, or the Elasticsearch error), and the decoded body is held against
  the budget, together with the compressed body while both are in memory, until the request is
  answered (D307).
- **Refusals.** A coding other than those, or more than four stacked, is `415 Unsupported Media
  Type` with `Accept-Encoding: gzip, deflate` (RFC 9110 §15.5.16), only where decoding is on; a
  body that does not decode, fails its CRC-32, `ISIZE` or Adler-32, or has bytes after its
  stream is `400`. Each closes the connection, like the server's other refusals. The InfluxDB write
  route's own `415` for compressed line protocol is gone.
- **`Host`.** An HTTP/1.1 request with no `Host` header, and any request with two or more, is
  answered `400` ("an HTTP/1.1 request needs exactly one Host header") before its body is read
  or `100 Continue` is sent; HTTP/1.0 may leave it out. The value is not checked further. The
  server's own client (`eggdb_http::request`, webhooks) already sends `Host`; the hand-written
  test requests now do too.
- **Tests.** `eggdb-content`: vectors from the gzip and zlib tools (with a file name, header
  CRC, extra field, multi-member, an empty member), DEFLATE streams wrapped in gzip and zlib
  with the limit hit, each check failing on a changed byte, and 20,000 mutated gzip, zlib and
  raw bodies that never panic. `eggdb-http`, over a real listener: each coding, stacked codings
  in one and two header lines, a chunked gzip body, `415` with `Accept-Encoding`, `400` for
  damaged bodies, a zip bomb and a gzip of a zip bomb answering `413`, a body the budget
  cannot take answering `503`, listeners that do not decode, the `Host` rules, the budget back
  at zero after each, and 20,000 mutated gzip and deflate bodies through the decoder.
  `eggdb-observability`: gzip line protocol through a listener set up as `eggdb serve` sets it,
  with remote write's snappy body still accepted.

Left out: `br` (Brotli) and `zstd` request bodies, compressed responses (`Accept-Encoding` from
clients), and a handler that reads the body as it is decoded (D325's streaming bodies).
