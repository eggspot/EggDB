## D156 The built-in MCP server, part 3: `--tables` as a filter on what SQL reads from the store, the key-value tools withdrawn under it, a gap between calls, and EggDB's own value and row limits for every session — Decided by the build loop (by judgement and Claude Fable's design, 2026-10-30); item 49b-2, applies D9, D11, D35, D45, D100, D119, D121

Item 49b-2 lets the user limit an agent to some tables (`eggdb mcp --tables a,b`) and closes
two follow-ups of D119: a minimum gap between calls, and an engine-wide limit on the size of
one value and one row.

**Visibility is a filter under SQL, not checks where names resolve.** `eggdb_sql::VisibleTables`
names the tables and views an agent may see; `VisibleTables::read` wraps the call's read
snapshot in a `VisibleRead`, which makes every other table, view and sequence read as absent:
`get` answers nothing and `scan` passes over it. The filter classifies keys by the SQL key
layout (`encoding::key_owner`): a definition (table and sequence spaces) by name, rows and index
entries by table number, foreign-key references and dependencies when either side is hidden,
comments by owner; schema records, user-defined types and the catalog's counter stay visible,
and a key it cannot read is hidden. At the start of each read it scans the table and sequence
definitions once to learn the visible table numbers and which sequences a visible table owns
(a sequence is visible when named or owned by a visible table). Everything above, name
resolution, view expansion, the plan cache, every catalog (`pg_catalog`, `information_schema`,
SQL Server's `sys` views and `INFORMATION_SCHEMA`, Oracle's dictionary, MySQL's and SQLite's
catalogs, `Session::relations`, the MCP schema resource), reads through it, so there is no list
of places to keep in step: a catalog added later is filtered by construction. The rejected
alternative, a visibility check in `name_resolution.rs` plus a filter in each catalog builder,
needs every new catalog and every resolution path to remember it, and one missed path leaks a
table. Hidden reads as missing, never as forbidden: the agent gets the same `42P01` (and the
same `not_found` from the tools) for a hidden table as for one that does not exist, so a refusal
is not an oracle. A listed view over an unlisted table fails as missing, since its query is
resolved through the same filter.

What the filter does not hide: schema names, user-defined types, and what a visible table's own
definition records (a foreign key's target name, a listed view's text). Table numbers and OIDs
are not renumbered, so their gaps show that other objects exist. Names match exactly as stored,
split at the first dot (`public.` and `dbo.` mean the default schema); the CLI checks at start
that each names a table, view or sequence (`table_not_found`, exit 1, with the stored name when
only the case differs), skipped while a writer holds the file.

**Read-only servers only in this release.** `--tables` with `--allow-write` is a usage error,
and `ServerConfig` with both fails with `StartFailure::TablesWithWrites`. A writing call would
need the filter on its writer too (a write to a hidden key refused, and a commit that rolls back
when a refusal was swallowed, as D121 noted), which is a follow-up.

**The key-value tools are withdrawn.** A new `Grant::KeyValueStore` in `eggdb-commands`, held by
every server not started with `--tables`, marks `kv_get` and `kv_scan`; `ToolDefinition::offered`
takes `Grants { allow_write, key_value_store }`. A call to either on a limited server answers
`limited_to_tables` (category `needs_grant`), so no key outside SQL is read. The `instructions`
gain one sentence saying the session is limited and not naming the tables. The audit's
`server_started` record gains `tables` (only when given) and `call_gap_ms`.

**A gap between calls.** `--call-gap <ms>` (default 100, 0 to 10,000): a call that opens the file
first waits until the gap has passed since the previous call ended, so a user's writer, which
tries the lock once, finds the file free between an agent's rapid calls. The wait comes before
the call's deadline is set, so it is not charged to the time limit; the audit's duration
includes it. Writers that wait for the lock stay a follow-up.

**EggDB's own value and row limits.** `eggdb_sql::MAX_VALUE_BYTES` (1 GiB, PostgreSQL's limit on
one value) and `MAX_ROW_BYTES` (2 GiB) are the default and the ceiling of every session's
`set_max_value_bytes` and `set_max_row_bytes`, and of the thread's limits outside a session, so
every value builder that checks the value limit (D119's rule) and every row counted with
`RowBytes` stops there in every session, not only under MCP. A stored value was already at most
1 GiB (D88). The error names EggDB's limit when the ceiling is hit, and keeps the shipped
session wording when a lower session limit is.

**Tests.** `eggdb-sql`: a store filtered to some tables, queried in PostgreSQL, SQL Server and
Oracle dialects (hidden tables refused directly, by schema, in joins, subqueries and CTEs, and
through a view; `pg_class`, `information_schema.tables`, `pg_description`, `sys.tables`,
`INFORMATION_SCHEMA.TABLES`, `all_tables`, `all_sequences` and `Session::relations` list only
what is visible), a scan of every SQL key through the filter that finds no hidden name, row or
comment, and unknown names; the engine limits' messages and ceilings. `eggdb-commands`: the
grants and the new code. `eggdb-mcp`: tools, dialects, catalogs and the schema resource on a
limited server, the key-value refusal, instructions, audit, the refusal with writes, and the
gap. The built binary: an agent limited to tables in every dialect and catalog, the banner and
`eggdb audit`, startup refusals, and the gap.
