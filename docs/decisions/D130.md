## D130 PostgreSQL's string, date/time and JSON functions: back references and lookaround by a bounded, memoized backtracking search; PostgreSQL's template patterns in their own module; whole rows only as `FROM` item names — Decided by the build loop (by research, 2026-10-29); roadmap item 36, applies D1, D9, D10, D19, D98, D111, D119, D128

Item 36 brings the rest of PostgreSQL's string, date/time and JSON functions to the PostgreSQL
dialect. Other dialects are unchanged: the new function names stay `42883` there, as before.

**Regular expressions: one parser, two matchers.** D128's parser now also reads back references
(`\1` to `\9`, and `\nn` while that many groups are closed), lookahead and lookbehind
(`(?=re)`, `(?!re)`, `(?<=re)`, `(?<!re)`, whose parentheses do not capture and which hold no
back references, as PostgreSQL requires), the constraint escapes `\m \M \y \Y \A \Z`, embedded
options at the start of the pattern (`c i m n p s t w x q`; `b` and `e`, the other flavours, are
`0A000`) and `***=`. A pattern that needs none of them, and is matched without the newline
options, still runs on D128's thread-list automaton, so `~` on ordinary patterns keeps its
linear time and speed. Every other match, and every match whose position or groups a function
needs (`regexp_match`, `regexp_replace`, `substring`, ...), runs a backtracking search over a
second program compiled from the same tree (`Save` slots for the groups, a progress check that
ends a loop whose body matched nothing, sub-programs for lookaround). While the pattern has no
back references, the search remembers every (instruction, position) state it has explored
(a bit set of at most 2^26 states, cleared word by word after each search, so a global
`regexp_replace` does not pay for the whole set each time); the states are shared by the starts
of one search, so finding the leftmost match costs time linear in the text times the program, as
the automaton does. With back references no state can be remembered, so the search is
exponential in the worst case, and D128's budget of 10^9 steps per match ends it with `54000`.
Lookaround answers are cached per position.

**Which match.** The search takes the leftmost start, then the longest or the shortest match there
by PostgreSQL's rule for the whole pattern (the greediness of its first quantified atom; an
alternation is greedy; no quantifier means longest): `regexp_match('abcd', 'a|ab')` is `{ab}` and
`substring('XY1234Z', 'Y*?([0-9]{1,3})')` is `1`, as the manual shows. Among the paths that
give that match, the groups come from the first in priority order (earlier alternatives first,
greedy quantifiers longest first). PostgreSQL decides each group by its own greediness instead;
the two agree on the manual's examples and differ only on patterns whose groups can split the same
match in several ways, a known difference in sql.md. Global iteration moves past an empty match
by one character; `regexp_split_*` ignores empty matches at the start, at the end and right
after a match, as the manual says.

**`SIMILAR TO`.** `a SIMILAR TO p ESCAPE e` is `a ~ similar_to_escape(p, e)`, as PostgreSQL
rewrites it, with the same converted pattern text (`^(?:...)$`, `%` as `.*`, `_` as `.`, `(` as
`(?:`, the escape character's next character as `\` and that character). `substring(s SIMILAR p
ESCAPE e)` splits `p` at the two `e"` separators and makes the first part lazy, so it matches as
little as it can, which PostgreSQL's `{1,1}?` achieves through its hierarchical rules and EggDB's
priority order needs written out; more than two separators is `2201B`.

**PostgreSQL's template patterns in `pg_format.rs`.** The plan was to share D126's Oracle format
model engine. PostgreSQL's patterns differ in what the engine is built around: text that is not
a pattern is copied (Oracle refuses it), `FM` applies to the next pattern only (Oracle's
toggles), `TH`/`th` suffixes, `MS`, `US`, `FF1`–`FF6`, `IDDD`, `OF`, `TZH`/`TZM`, `RM`, and for
numbers `PR`, `SG`, `V` and `EEEE` with PostgreSQL's sign and blank placement; and its errors are
SQLSTATEs, not `ORA-` codes. So `pg_format.rs` has its own tokenizer, writer and reader, and
shares the calendar (`datetime`'s civil-day and ISO-week functions, now `pub(crate)`) and the
month and day names of `oracle_datetime.rs`. Numbers are formatted from their exact `numeric`
digits (a float through its shortest exact text), rounded half away from zero, overflow shown as
`#`. `to_date` and `to_timestamp` read numbers greedily unless the next pattern also reads digits
(`YYYYMMDD`), skip separators loosely as PostgreSQL does without `FX`, adjust years of fewer than
four digits toward 2020, and check every field (`22008` with the input text).

**JSON.** `json` results are written with PostgreSQL's spacing for each function (`{"a" : 1}`
from `json_build_object`, `{"a":1}` from `row_to_json`, `[1, 2]` from `json_agg` and `, \n `
between rows or arrays in it, `{ "a" : 1 }` from `json_object_agg`); `jsonb` results go through
D111's normalizer. Dates and time stamps become ISO 8601 strings with a `T`, a `timestamptz` with
the session's offset as `+hh:mm`. `jsonb_set`, `jsonb_insert`, `#-`, `-` and `||` edit the parsed
tree and normalize it again.

**Whole rows only as `FROM` item names.** EggDB has no record type. When `row_to_json`,
`to_json`, `to_jsonb`, `json_build_array`, `json_agg` or `jsonb_agg` is given a bare name that
names an item of the same `FROM` (`row_to_json(t)`, `json_agg(t)`), the parser replaces it with
an internal `whole_row(t.*)`, which marks every column of `t` as needed and evaluates to the
row as a JSON object of its columns; a column of that name, if one exists, wins, as in
PostgreSQL. `row(...)` is accepted as `row_to_json`'s argument and gives `f1`, `f2`, ... A whole
row elsewhere (`SELECT t FROM t`) stays `42703`.

**Set-returning functions with several columns.** D128's registry gains functions whose rows
are records: in `FROM`, `json_each` gives the columns `key` and `value`, `json_array_elements`
the column `value` (an alias renames the table, not the columns); alone in a select list, a
one-column record is its value and a wider one its record text (`(a,"""foo""")`), as psql shows
PostgreSQL's records. `regexp_matches`, `regexp_split_to_table` and `json(b)_object_keys` are
ordinary one-column functions.

**Limits (D9, D119).** Every function that can build a large value checks the session's value
limit before it builds it, and a result past 1 GiB is `54000` (`requested length too large`):
`repeat`, `lpad`, `rpad`, `replace`, `concat`, `format`, `overlay`, `regexp_replace`, the
regular expression arrays, every JSON builder and aggregate, `to_char`. Templates are at most
100,000 characters. Hostile patterns, templates and documents return errors, never panic, which
seeded tests in each module check.

**`md5` lives in the SQL core.** `md5()` is a checksum function of SQL, not cryptography EggDB
relies on, so its RFC 1321 implementation is a private module of `eggdb-sql` with the RFC's test
suite, rather than a new primitive of `eggdb-crypto` (D23) that would add a dependency and a
security review for a hash no protocol of EggDB uses.

**`AT TIME ZONE`** is the function `timezone(zone, value)`, as in PostgreSQL, with the zones the
rest of EggDB knows: `UTC` and its aliases, POSIX-style fixed offsets (`'+05'` is five hours west,
as in PostgreSQL) and an `interval`. A named region is `22023` until the time zone database
comes (D111), rather than acting as UTC, since a wrong instant here would be silent.

**Checks.** 45 new cases in the PostgreSQL correctness suite (and the five that were marked as
differing now pass), unit tests in each new module (the manual's examples for every function
group, RFC 1321's suite, seeded hostile inputs), and CI's `pg-functions` job, which runs
`scripts/pg-functions/cases.sql` through psql 17 against the `postgres:17` container and against
`eggdb serve` and fails on any byte of difference.
