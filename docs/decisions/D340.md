## D340 Two-variable statistics (`regr_*`, `covar_samp`, `covar_pop`, `corr`) in PostgreSQL's and Oracle's dialects, `42803` for an ungrouped direct argument of a hypothetical-set aggregate, and SQLite's and SQL Server's NULL ordering — Decided by the build loop (batch 6, 2026-11-10); roadmap M5, extends D321, applies D9 and D10

D321 left PostgreSQL's two-variable aggregates unbuilt (`regr_slope(y, x)` answered `42883`),
read a hypothetical-set aggregate's direct arguments for every row without checking that they
are grouped, and gave SQLite's and SQL Server's dialects PostgreSQL's NULL order (NULLs last for
`ASC`). PostgreSQL's "Aggregate Functions for Statistics" table, Oracle's `REGR_ (Linear
Regression) Functions`, `CORR`, `COVAR_POP` and `COVAR_SAMP` references, SQLite's "The ORDER BY
clause" ("NULLs are considered smaller than any other value") and Microsoft's "SELECT - ORDER BY
Clause" ("NULL values are treated as the lowest possible values") say how they behave; EggDB
now follows them.

- **Twelve aggregates on one accumulator.** In PostgreSQL's and Oracle's dialects `regr_count`,
  `regr_sxx`, `regr_syy`, `regr_sxy`, `regr_avgx`, `regr_avgy`, `regr_r2`, `regr_slope`,
  `regr_intercept`, `covar_pop`, `covar_samp` and `corr` take the dependent value first and the
  independent one second (`paired_aggregate_arguments`, an internal call users cannot write).
  `bivariate_aggregates::PairSums` keeps the pair count, the sums of X and Y and the sums of
  squared and cross deviations, updated with the Youngs-Cramer step PostgreSQL's
  `float8_regr_accum` documents, so values far from 0 lose no precision to cancellation. A pair
  with a NULL on either side is skipped. An overflow from finite inputs is `22003`; an infinite
  or NaN input makes the dependent sums NaN, as PostgreSQL does.
- **Results as PostgreSQL defines them.** `regr_count` is a `bigint` and 0 over no pairs; every
  other result is `double precision` and NULL over no pairs. `covar_samp` is NULL for one pair;
  `regr_slope`, `regr_intercept`, `regr_r2` and `corr` are NULL when X has no spread
  (`regr_sxx` = 0, a vertical line); `corr` is also NULL when Y has none, and `regr_r2` is 1
  then (a horizontal line). `corr` is `sxy / sqrt(sxx * syy)`, with the two square roots taken
  apart only when that product overflows.
- **Call forms.** `DISTINCT` (over the pair), `FILTER` and `OVER` work in PostgreSQL; Oracle's
  grammar has no `DISTINCT` for them, so it is ORA-30482. One or three arguments are `42883`
  (`function regr_slope(unknown) does not exist`) in PostgreSQL and ORA-00909 in Oracle; a
  non-numeric argument is `42883` naming both argument types, checked when the query is
  analysed for columns of known type and per row otherwise. MySQL, SQL Server and SQLite have
  none of these functions, so their dialects keep their unknown-function errors (`1305`, `195`,
  `no such function`).
- **Direct arguments of hypothetical-set aggregates.** `rank(x) WITHIN GROUP (ORDER BY x)`
  checks its direct arguments as if they stood outside the aggregate, as PostgreSQL's grouping
  check does, so a column that is neither grouped nor functionally dependent on the grouping is
  `42803` `column "t.x" must appear in the GROUP BY clause or be used in an aggregate function`
  (ORA-00979 through Oracle's shared mapping). Grouped columns and constants still work.
- **SQLite's and SQL Server's NULL ordering.** D321's parse-time default now covers these two
  dialects as well as MySQL: an `ORDER BY` item without `NULLS FIRST` or `LAST` sorts NULLs
  first for `ASC` and last for `DESC`, in queries, set operations, window definitions and
  `STRING_AGG ... WITHIN GROUP`. The planner's rule that a nullable column's index replaces a
  sort only when the NULL order matches therefore applies to them too; reading such an index
  in two ranges is D341's.

Decided: Oracle's dialect returns `double precision` values computed as PostgreSQL computes
them, where Oracle returns `NUMBER` for `NUMBER` arguments (the same trade D321 made for its
results' precision); an `ORDER BY` inside these calls is not accepted (it changes nothing in
PostgreSQL and Oracle has none); Oracle's error for an ungrouped direct argument is the one its
`not a GROUP BY expression` mapping gives.

Tests: `bivariate_aggregates.rs` (a line's slope, intercept and full correlation, every result
of the same pairs, pairs with a NULL, numbers of every type, no rows, one row, vertical and
horizontal lines, values offset by 1e9, infinity and overflow, the error naming both types);
new cases in the PostgreSQL correctness suite (every function on the same table, `GROUP BY`
with one-pair and no-spread groups, no rows, `DISTINCT`, `FILTER`, a running window, `42883`
for one argument and for text, `42803` for an ungrouped direct argument with and without
`GROUP BY` and a grouped direct argument that works), the Oracle suite (the same values in
Oracle's spelling, one row, an analytic `REGR_SLOPE`, ORA-30482 and ORA-00909), the MySQL, SQL
Server and SQLite suites (each one's unknown-function error), and the SQLite and SQL Server
suites (NULLs first and last with and without an index, `NULLS LAST`, `TOP` and a window).

Left: Oracle's `NUMBER` results for these functions, its `CORR_S`, `CORR_K` and `STATS_*`
functions, and PostgreSQL's `ORDER BY` inside a two-variable aggregate call.
