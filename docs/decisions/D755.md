## D755 Bitemporal tables (eggdb_temporal) — Decided by the code-only session (2026-11-12, D355); roadmap M11, bitemporal tables (D50)

- `CREATE EXTENSION eggdb_temporal`, then `eggdb_temporal.enable(schema, table, key_columns)`, makes an existing table
  bitemporal. It adds `valid_from` and `valid_to` (the valid period, when a fact is true; `-infinity` to `infinity` by
  default, so existing rows stay true always) unless the table declares them already, and `recorded_from` and
  `recorded_to` (the recorded period, when the database knew it). It creates `<table>_history` with the same columns,
  the view `<table>_versions` (the table and its history together), and a generated row trigger.
- The trigger keeps the recorded period: every insert and update stamps the row `recorded_from = now()`, and every
  update or delete first copies the old row into the history with `recorded_to = now()`. It refuses a valid period
  that is empty (22000) or overlaps another row with the same key (23P01), so the key and `valid_from` identify a row.
  A table whose primary key is the business key alone cannot hold several periods per key; it needs `valid_from` in
  its key, or no primary key.
- `update_period(schema, table, key, start, end, changes)` and `delete_period(schema, table, key, start, end)` change a
  fact for part of its valid time, as SQL:2011's `FOR PORTION OF` does: rows that straddle a boundary are split at it
  (the old part keeps the row, the rest becomes a copy), then the rows inside the period are updated or deleted. Keys
  and changes are JSON objects of column names and values. Gaps are not filled.
- `as_of(schema, table, valid_at [, recorded_at])` returns the versions true at `valid_at` as known at `recorded_at`
  (now by default), and `history(schema, table, key)` every version of one key, both as `jsonb`; the versions view
  serves typed queries.
- SQL:2011's `PERIOD FOR`, `FOR SYSTEM_TIME AS OF`, `FOR PORTION OF` and SQL Server's and MariaDB's system-versioned
  syntax onto the same columns, history kept after `TRUNCATE`, and the view following later `ALTER TABLE`s are left.
