## D284 Suspended portals' rows, RESP, MongoDB, CQL and memcached hold their memory against the one server budget, and `eggdb serve --max-connection-memory <size>` sets it — Decided by research (EggAgentCode task 20261103-0137, 2026-11-03); refines D254

D254 gave the PostgreSQL, MySQL and TDS servers one memory budget (`MemoryBudget` in
`eggdb_platform::connection_limits`, 4 GiB) and left three things open (issue #79): the rows a
suspended portal has already materialized were not counted, the other protocol servers of
`eggdb serve` did not use the budget, and its size was not an option. A logged-in client could
still grow the server without bound by opening many suspended portals (each `Execute` with a row
limit keeps the rest of its result), by sending RESP bulk strings or CQL frames up to their
per-message caps on many connections, by leaving MongoDB cursors open, or by asking memcached for
many 1 MiB items in one `get`.

- **One flag, `--max-connection-memory <size>`.** Sizes take the forms of `--resp-max-memory`
  (`4096`, `64k`, `512m`, `8g`); the default stays `DEFAULT_MEMORY_BUDGET_BYTES` (4 GiB, all of
  memory on 32-bit machines), and less than `1m` is a usage error, since every request over
  64 KiB counts and a smaller budget would refuse ordinary traffic. It is named `--max-<what>`
  like `--max-connections`, and says "connection" because it bounds what connections hold, not
  the page cache (D79) or the RESP keyspace (`--resp-max-memory`). The same `Arc<MemoryBudget>`
  goes to every listener the budget covers.
- **What counts.** `UNCOUNTED_BUFFER_BYTES` (64 KiB, the size of a connection's own read
  buffer) is the line: a request or reply at or under it is not counted, one over it holds its
  bytes (`Reservation::hold_if_large`) while it is read and answered, and gives them back before
  the connection waits for the next one.
  - *PostgreSQL portals.* When `Execute` stops at its row limit, the rows left are measured
    (`eggdb_sql::held_row_bytes`, the engine's own work-memory estimate) and held with the
    portal's text and parameters; each later `Execute` gives back the bytes of the rows it sent,
    and `Close`, a new `Bind` of the same name, the end of the transaction, `DISCARD ALL` and the
    end of the connection give back the rest. The rows count against the per-connection 1 GiB cap
    of D254 too. A suspension that does not fit fails with `53200 out of memory` (the rows sent
    so far stay sent, the portal can no longer run), and the connection goes on.
  - *RESP.* Each bulk string's declared length is held, twice (the read buffer and the
    argument), before it is read (`RequestReader::next_request_within`); a request that does not
    fit is answered `-OOM command not allowed: ...` and ends its connection, since the rest of it
    is never read. A reply that does not fit is replaced by the same `-OOM` error and the
    connection goes on.
  - *MongoDB.* A message's length is held before its body is allocated; one that does not fit is
    answered with `ExceededMemoryLimit` (146) and ends its connection. A cursor holds the BSON size
    of the documents it has not returned (server-wide, as drivers continue cursors on other
    connections), gives back each batch's bytes on `getMore`, and the rest when it is exhausted,
    killed or swept; a `find` or `aggregate` whose cursor does not fit fails with 146. Replies are
    not counted: one batch is at most 16 MiB (`MAX_BATCH_BYTES`), as in MongoDB, and refusing a
    reply would orphan the cursor it opened.
  - *CQL.* A frame's declared length is held before the rest is read; one that does not fit is
    answered with `Overloaded` (`0x1001`) on its stream and ends its connection. A result that
    does not fit is replaced by `Overloaded` and the connection goes on.
  - *memcached.* A value's declared length is held before it is read; one that does not fit is
    skipped (read and dropped in small chunks) and answered `SERVER_ERROR out of memory storing
    object`, so the connection goes on as memcached's does. A `get` reply that does not fit is
    answered `SERVER_ERROR out of memory`.
- **The error is each protocol's own**, so clients and their retry logic treat it as the
  original's out-of-memory or overload answer.

Tests: `connection_limits` unit tests for `hold_if_large`; `eggdb_sql::held_row_bytes`;
`a_request_past_what_admit_allows_stops_before_its_bulk_is_read` for the RESP reader; the
Mongo cursors' unit test; and per protocol a test that exhausts a small budget and checks the
error, that the bytes come back and that another session goes on
(`crates/eggdb-pgwire/tests/limits.rs`, `crates/eggdb-resp/src/tests.rs`,
`crates/eggdb-mongowire/src/tests.rs`, `crates/eggdb-cql/src/tests.rs`,
`crates/eggdb-memcached/src/lib.rs`), plus `crates/eggdb/tests/serve.rs` through the real binary
with `--max-connection-memory 1m` and a RESP client.

### Security review

- *Threat.* A logged-in client (or, for RESP, memcached and CQL before `AUTH`, any local
  program) makes the server allocate until the operating system kills it, taking every other
  session down. The budget turns that into a refused request for the client that asks for too
  much, while the bytes already held by others stay theirs.
- *Before allocation.* RESP, MongoDB, CQL and memcached hold a request's declared length before
  the buffer for it grows, so a header claiming 512 MiB costs nothing; pgwire, MySQL and TDS
  already did (D254).
- *Release on every path.* Every hold is a `Reservation` that gives its bytes back when dropped,
  so a connection that ends mid-request, an error path or a swept cursor cannot
  leak budget; the portal path releases explicitly on each of its error returns and the tests
  check `used_bytes()` returns to zero.
- *Fairness.* A refused request never takes bytes from another connection; a budget full of one
  client's open portals or cursors refuses new ones until they close (PostgreSQL portals end with
  their transaction, Mongo cursors after ten idle minutes), which bounds how long one client can
  hold it. Per-connection caps (D254's 1 GiB, RESP's 512 MiB bulk, Mongo's 48 MB message, CQL's
  16 MiB frame, memcached's 1 MiB item) still apply under the budget.
- *Multi-key reads stop early* (round-1 security review). memcached's `get`, `gets`, `gat` and
  `gats` hold each item's reply bytes before copying it and stop with `SERVER_ERROR out of
  memory` once the budget is short (a refused `gat` touches nothing); RESP's `MGET`, `KEYS`,
  `SINTER`, `SUNION` and `SDIFF` measure their reply as they gather it against the room the
  budget has left and stop with `-OOM`. The connection stays usable. Tests:
  `a_multi_get_of_many_items_past_the_memory_budget_stops_before_copying_them_all`,
  `replies_of_many_keys_stop_with_oom_once_they_pass_the_reply_room`.
- *Accounting is an estimate.* Row and document sizes are measured, not exact allocator bytes;
  the work memory of a statement while it runs is bounded separately by the engine (1 GiB per
  statement).

Not yet: Kafka, MQTT, AMQP, NATS, STOMP, Bolt and the HTTP listeners (REST, Elasticsearch, S3,
DynamoDB, observability, metrics, MCP) keep their own per-message caps but do not hold against
the budget; RESP pub/sub messages queued for a slow subscriber are not counted; other replies (and
RESP's `EXEC`, single large values and range reads) are built before they are measured, so a
refused one still costs its size for a moment; and PostgreSQL
portals still materialize their whole result before the first row is sent.
