## D875 A GraphQL API generated from the schema — Decided by the code-only session (2026-11-12, D355); roadmap M6a, D37

- `eggdb-api` answers `POST /graphql` and `POST /v1/graphql` (a JSON body with `query`, `variables` and
  `operationName`, or an `application/graphql` body) beside the REST API, on the same listener and sign-in, so every
  root field runs as SQL in the signed-in user's session and roles and row security apply unchanged.
- The schema follows Hasura's conventions, which GraphQL clients and examples for PostgreSQL expect: per table
  `<table>`, `<table>_by_pk(<key columns>)` and `<table>_aggregate { aggregate { count sum avg max min stddev ... }
  nodes }` on the query root, and `insert_<table>(objects, on_conflict)`, `insert_<table>_one(object)`,
  `update_<table>(where, _set, _inc)`, `update_<table>_by_pk(pk_columns, ...)`, `delete_<table>(where)` and
  `delete_<table>_by_pk(...)` on the mutation root, with `affected_rows` and `returning`. Filters take Hasura's
  boolean expressions (`_and`, `_or`, `_not`, `_eq` ... `_lte`, `_in`, `_nin`, `_like`, `_ilike`, `_similar`, `_regex`
  and their negations, `_is_null`, `_contains`, `_contained_in`), with `order_by` (the six directions), `limit`,
  `offset` and `distinct_on`.
- Relationships come from foreign keys, with no metadata to track: a table with a key to another gets an object
  relationship named after the referenced table (and after a one-column key's name without `_id`), and the
  referenced table gets an array relationship named after the referencing table, with its own `where`, `order_by`
  and paging. Both also filter (`where: {author: {name: {_eq: "Ada"}}}` becomes `EXISTS`).
- Each root field becomes one SQL statement that builds its JSON with `json_build_object` and `json_agg`, from
  quoted identifiers and quoted literals only (GraphQL names cannot hold quotes); the mutations of one request run in
  one transaction, so one failing field undoes them all. Errors come back as GraphQL `errors` with HTTP 200, as
  Hasura's do.
- The GraphQL reader in `graphql.rs` implements the October 2021 specification's executable documents (operations,
  variables with defaults, aliases, arguments, directives, fragments and inline fragments, block strings, Unicode
  escapes), with a nesting limit of 64 and a 1 MiB document limit; `@include` and `@skip` apply; type-system
  definitions are refused.
- Left: introspection (`__schema`, `__type`, written next in D876), subscriptions, nested inserts, aggregate relationships
  (`<table>_aggregate` under a relationship), computed fields, and a table literally named `graphql`, which the
  GraphQL path hides from REST.
