## D927 Column-level lineage captured from statements — Decided by the code-only session (2026-11-12, D355); roadmap M6c, D51 and D244

- `eggdb_column_lineage(statement text) RETURNS jsonb` reads an `INSERT ... SELECT`, a `CREATE TABLE ... AS` or a
  `CREATE VIEW` (PostgreSQL syntax) and answers `{"target": table, "columns": [{"column", "sources": [...]}]}`: for
  each target column, the `table.column` sources its expression reads. It follows table aliases, joins, derived
  tables, `WITH` queries and set operations (positionally); a `*` traces to `table.*`; a column with no table named
  in a query over several tables is traced to each of them, an over-approximation lineage tools accept. The target's
  column list, when the statement gives one, names the columns; otherwise the select list does. Subqueries inside
  expressions are not followed yet.
- `eggdb_catalog.capture_lineage(job, statement)` (`CREATE EXTENSION eggdb_catalog`) records the table-level edges in
  `eggdb_catalog.lineage` and the column-level ones in the new `eggdb_catalog.column_lineage`, and
  `openlineage_event` now gives each output dataset OpenLineage's `columnLineage` facet (`fields` → `inputFields`).
- Lineage is captured when a pipeline or a person passes the statement; capturing every statement a session runs is
  left, as it would cost every write.
