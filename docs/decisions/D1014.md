## D1014 RDF in the MCP tools, with `eggdb rdf get` and `eggdb rdf run` — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D11, D38, D922)

- Two MCP tools give agents the file's RDF graphs: `rdf_get` runs one SPARQL 1.1 query and returns the SPARQL 1.1
  JSON results (a graph as N-Triples text), offered to every agent like `run_sql`; `rdf_run` runs one SPARQL update
  in one transaction and returns the quads inserted and deleted, offered only with `--allow-write`, like
  `write_sql`, and recorded in the audit log as every write is.
- The command model (D143) needs a CLI twin for every tool and `<noun> <verb>` names with core verbs, so the
  twins are a new noun, `rdf`: `eggdb rdf get <file> <sparql>` (read) and `eggdb rdf run <file> <sparql>` (`run`,
  the core verb for a statement). They share `eggdb sql --sparql`'s code (D922), and each refuses the other kind
  of request with a message naming the right command.
- An update that deletes (`DELETE`, `CLEAR`, `DROP` or `MOVE`) is destructive: `rdf_run` refuses it without
  `confirm: true`, with a message telling the agent to ask its user, a new confirm check `quad_delete` in the
  command model. Unlike `write_sql` the server does not yet ask the user itself mid-call; the agent asks.
- The MCP crate stays free of the RDF store: `DatabaseOpener` gains `sparql(text, write)`, which the `eggdb`
  binary implements by opening the file for that call alone, as every other tool does. A new error code,
  `sparql_error`, reports a failed query or update.
