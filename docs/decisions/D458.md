## D458 Bearer tokens on the generated REST API, with the token's role per request — Decided by the code-only session (2026-11-11, D355); roadmap M6a, extends D235 and D185

- With `--auth-rules`, the REST API also takes `Authorization: Bearer <token>`. The token is
  checked against each `jwt` rule's key set and policy in order (the same RS256/PS256/ES256 check
  as the PostgreSQL listener, D185); the claim the policy names (`sub` unless `user_claim=` says
  `role`, as PostgREST does) is the role.
- The role must have a `jwt` rule of its own (its first matching rule is `jwt`) and be a stored
  role with LOGIN; then the request's statements run as that role, so its grants and row-level
  security policies apply. Each request is checked on its own: there is no session.
- HTTP Basic with the server's user keeps working; a refused token answers 401 `PGRST301` with
  `WWW-Authenticate: Bearer` and `Basic`.
