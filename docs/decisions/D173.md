## D173 Savepoints by an undo log of previous values, and lock clauses accepted over the one writer — Decided by the build loop (by judgement, 2026-10-31); refines D86 and D172

Part 4.M3-2 asks for each database's isolation levels, row and table locks, savepoints and
two-phase commit.

- **Savepoints** keep, while at least one is set, an undo log of each key's previous value. It
  is written by a wrapper around the block's writer, so it costs a read per write only while
  savepoints exist. `ROLLBACK TO` writes the logged values back in reverse, through the same
  temporary-object routing as the writes, and drops the table cache. In PostgreSQL's dialect, a
  failed statement inside a block with savepoints marks the block aborted instead of rolling
  the storage transaction back, so `ROLLBACK TO` can recover, as PostgreSQL's subtransactions
  allow. SQL Server's `SAVE TRANSACTION` and `ROLLBACK TRANSACTION name` use the same log.
  SQLite's outermost `SAVEPOINT` begins a transaction and its `RELEASE` commits.
- **Locks need no lock manager yet.** A block holds the database's one writer (D86), so no
  other session writes while it is open: `FOR UPDATE`, `FOR SHARE`, `NOWAIT`, `SKIP LOCKED`
  and `LOCK TABLE` already hold, and are parsed and accepted. Once SQL sessions run on
  concurrent transactions (D172), these clauses become the reads that a commit checks.
- **Isolation levels** stay accepted, and every block is serializable, which is at least as
  strong as the level asked for.

Left: two-phase commit (`PREPARE TRANSACTION`, `COMMIT PREPARED`, MySQL's `XA`), which needs a
prepared transaction's changes kept durably and its keys locked against other writers;
per-statement snapshots for read-only `READ COMMITTED` blocks; deadlock detection between
advisory locks.
