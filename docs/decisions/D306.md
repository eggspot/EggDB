## D306 `eggdb mcp --allow-write --tables`: a table listed with columns takes inserts and changes to its listed columns with the hidden values merged back below the engine, a listed table's foreign key to an unlisted one is checked by the writer, and a view may take a column list — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 51 and 52, finishes three of D281's "Not yet", applies D9, D11, D35, D156, D257 and D281; security-critical (D35)

D281 left a table listed with columns read-only, froze a listed table with a foreign key to an
unlisted one, and hid any view given a column list. All three stay in the store filter
(`VisibleTables`, `crates/eggdb-sql/src/visible_tables.rs`), under every statement kind, so
`UPDATE ... FROM`, `DELETE ... USING`, MySQL's multi-table forms (D297), `MERGE`, `OUTPUT ...
INTO` and `SELECT ... INTO` (D303) are covered without a list of statements: they resolve names
through the same filtered store, so an unlisted table is missing (`42P01`) and `SELECT ... INTO`
creates its table only under a listed name.

**Writes to a table listed with columns.** The engine still sees the narrowed definition
(D281). When it writes a row of such a table, the writer (`VisibleWrite`) rebuilds the full
row before it reaches the store:

- a key already stored is a change: the stored row's hidden values are kept and the listed
  ones replaced; a key not stored is a new row: each hidden column takes its default
  (`execute::default_value`, the engine's own evaluation), then the table's `NOT NULL` and
  every check and domain run on the full row (`PreparedChecks`);
- the indexes the narrowed definition drops (over a hidden column) are kept by the writer:
  their entries are computed from the full rows (`indexes::entry_key`) and moved when a listed
  column of a mixed index changes;
- a key change or delete is refused (`42501`, "cannot delete rows of ... or change their
  key"), since the engine writes it as a delete and an insert, and the hidden values would be
  lost or reset. The one exception is a row the same transaction inserted, so a savepoint or
  statement rollback (whose undo log sits above the filter and records the narrowed row) can
  remove it; the undo of a change re-puts the narrowed old row, which merges back the same way;
- definitions, comments, policies and `ANALYZE` stay refused.

**No answer may depend on a hidden value.** A failure that depends on a value the agent cannot
see would let it learn that value by trying, so the writer refuses, whatever the values, the
writes whose outcome would need one, and computes nothing it cannot show:

- a change to a listed column that a check, unique index or foreign key ties to a hidden
  column (`TiedColumn`), decided from the definition and the columns changed, never from the
  check's result; changes that keep the value go through;
- an insert when a hidden column takes a generated value (identity, `serial`, a sequence
  default), has a domain, has a default that calls a user routine, holds a subquery or cannot be
  read, or when a unique index or foreign key over a hidden column would get a key without
  NULLs (it would be checked against other rows or another table);
- every write to a partitioned table or partition (its bounds may use a hidden column) and every
  change to a table that another listed table references through a hidden column (the engine
  would look for that column in the narrowed parent).

A check, `NOT NULL` or default that fails on a new row's own values is an ordinary error
(`23514`, `23502`, or the default's state) whose text names the table only, never the hidden
column, its value or a failing row. A new row's checks may mix listed values with defaults: no
other row's hidden value takes part. `RETURNING`, triggers and the undo log see only the
listed columns.

**A listed table's foreign key to an unlisted one.** D257 froze its rows because the engine,
under the filter, finds the parent missing. Now the writer reads the unlisted parent's
definition and the child's foreign keys to it from the unfiltered store at the start of the
transaction (`ParentsOutside`), shows the writing session the child's definition without those
foreign keys (so the engine neither checks nor lists them), and checks each new row and each
change of the key columns itself (`constraints::check_parent_outside_the_session`, the engine's
own lookup on the unfiltered store). A missing parent is the dialect's usual foreign-key error
(`23503`, MySQL 1452, Oracle ORA-02291, SQLite's `FOREIGN KEY constraint failed`), with the
parent's column list left out of MySQL's text; it names the parent table, already named by the
tie, and only the agent's own key values. What it reveals is whether a key exists in the parent,
which is what a foreign key means; no row or column of the parent is read back. Such a foreign
key is checked at once even when deferrable, SQLite's `PRAGMA foreign_keys` is honoured, and
the child's definition stays frozen. When the parent or child cannot be read as tables, the rows
stay frozen as before. `OutsideLink::blocked_changes` for this tie is now "change its
definition".

**Column lists on views.** A view listed with columns, such as `roster(id,name)`, reads as a
view whose query is `WITH eggdb_shown_columns (all its columns) AS (its query) SELECT (the
listed ones) FROM eggdb_shown_columns`, quoted in the view's dialect, with only the listed
columns in its definition, catalogs, comments and grants. Its query still runs under the
filter, so a hidden table or column it reads fails as before. It cannot be replaced, dropped
or written through (`42501` for the definition; the rewritten view is not updatable). A SQL
Server view whose query starts with `WITH` cannot nest in a CTE and is reported at start, like
a column the view does not have.

Rejected: restating the engine's insert path (identities, sequences, domains, cascades) at the
key level for hidden columns, which would need a second copy of that logic to stay in step;
refusing the oracle-prone writes only when they would fail, which is the oracle; a store-trait
method letting the engine ask the filter about a hidden parent, which every store wrapper
(undo log, temporary objects, routine calls) would have to forward and would fail open if one
did not.

**Tests.** `eggdb-sql` (`visible_writes_tests`): inserts and upserts with defaults, changes that
keep hidden values, hidden and mixed index entries counted and moved, the tied-column refusal
for three values, a check over a hidden column on insert without detail, the generated, unique,
foreign-key and routine-default refusals, `NOT NULL`, a savepoint rollback, deletes and key
changes refused, a view listed with columns, foreign keys to an unlisted table in PostgreSQL,
MySQL and SQLite with no parent value in the errors, and joined `UPDATE`/`DELETE`, `MERGE`,
`SELECT ... INTO` and `OUTPUT ... INTO` reaching an unlisted table; `visible_tables_tests`: the
start report for views. `eggdb-mcp` (`tests/tables.rs`) and the built binary (`tests/mcp.rs`):
an update and an insert through `write_sql` keep the hidden value, and a delete is refused.

**Not yet.** Deleting rows of a table listed with columns; inserts whose hidden column takes a
generated value; checking a unique index or foreign key over a hidden column without an oracle;
a listed child whose foreign key points at a hidden column of a listed parent (its inserts fail
with a damaged-key error, closed); the same filter for `eggdb serve` sessions.
