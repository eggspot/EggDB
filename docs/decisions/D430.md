## D430 `deleted.` in a Transact-SQL `UPDATE`'s `OUTPUT` — Decided by the code-only session (2026-11-11, D355); roadmap M10

- A Transact-SQL `OUTPUT` becomes the statement's `RETURNING` list (D300), which an `UPDATE`
  evaluates over the new row, so `deleted.` was refused there. Now the parser gives `deleted.`
  columns and `deleted.*` an internal label (`output_into::DELETED_LABEL`, which starts with a
  NUL character no written name can hold), and when the list mentions it, `execute::update`
  evaluates `RETURNING` over two sources, the table under its own label and again under the
  internal one, each row being the new row followed by the old one. `inserted.` keeps meaning the
  new row, so `OUTPUT deleted.price, inserted.price` shows both. `OUTPUT ... INTO` goes through
  the same list.
- `deleted.` in an `INSERT`'s `OUTPUT` stays an error, as in SQL Server. `TOP (n) [PERCENT]` in
  `UPDATE`, `DELETE` and `INSERT` stays refused: `Update` and `Delete` have no row limit, and
  adding one touches every place that builds them; a `PERCENT` also needs the count of matching
  rows first. Left for a design of its own.
