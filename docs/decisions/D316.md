## D316 Partitioned tables move rows on `UPDATE`, take expressions in their keys, and give every partition the parent's indexes, tracked by links in the partition record (version 2) — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M2, extends D169, applies D35; security-critical (D35)

D169 left three gaps in partitioning: an `UPDATE` through the partitioned table that changed a
row's key failed instead of moving the row, partition keys were columns only, and `CREATE INDEX`
on a partitioned table stayed on the parent, so no partition used it. Each now works as
PostgreSQL 17's manual describes it (chapter 5.12 "Table Partitioning", `CREATE TABLE`,
`CREATE INDEX` and `ALTER INDEX`), with MySQL's forms where MySQL has them.

- **Rows move.** An `UPDATE` that names a partitioned table runs per surviving partition as
  before (D169). A partition's own update now takes the rows whose new values no longer fit its
  bound out of the update: their index entries and keys are deleted from that partition (a
  foreign key that references the partition sees an update, as PostgreSQL 15 and later treat a
  cross-partition update), and the new rows are kept. Once every partition is done, the kept
  rows are inserted through the table the `UPDATE` named, so they go where they belong; a row no
  partition takes fails with `23514 no partition of relation "t" found for row` (MySQL's 1526,
  Oracle's ORA-14400), and the whole statement is undone. Rows are inserted only after every
  partition has run, so a moved row is never updated twice. `RETURNING` shows moved rows, and
  the count includes them. An `UPDATE` that names a partition, or a sub-partitioned table, moves
  rows only within it: a row leaving it fails with `violates partition constraint`, as in
  PostgreSQL. The other checks of a moving row are the ones of the partition it lands in.
- **Expressions in keys.** `PARTITION BY RANGE ((expr))`, `LIST (lower(name))` and
  `HASH ((expr))` in PostgreSQL (a function call needs no extra parentheses, and an expression
  that is a bare column is that column), and `RANGE (EXTRACT(YEAR FROM d))`, `LIST (expr)` and `HASH (expr)`
  in MySQL. A key part is stored as its text and the dialect it was written in, parsed once per
  statement and evaluated on each row in the table's own scope, so a partition whose columns are
  in another order evaluates it on its own rows. The part's type is the expression's type (an
  integer in MySQL, which requires one), and bounds are read in it. Refused, with PostgreSQL's
  errors: subqueries (`0A000`), aggregates (`42803`), functions whose value changes between calls
  (`random`, `now`, `nextval`, `current_user`, user-defined routines and the like: `42P17
  functions in partition key expression must be marked IMMUTABLE`), expressions without a column
  (`42P17`), and primary keys and unique constraints on a table whose key has an expression
  (`0A000 unsupported UNIQUE constraint with partition key definition`). An expression whose type
  EggDB cannot work out is refused with a hint to cast it. Routing evaluates the columns an
  expression reads once per inserted row and passes them as constants, as D169 does for key
  columns. Pruning compares a `WHERE` term with the key expression after dropping positions and
  the table's own qualifier, so `WHERE lower(name) = 'ann'` reads one partition; any other
  expression keeps every partition. `pg_get_partkeydef` and the `23514` detail show
  `LIST (lower(name))` and `RANGE ((id / 100))` as PostgreSQL does.
- **Indexes reach every partition.** `CREATE [UNIQUE] INDEX` (and `ALTER TABLE ... ADD UNIQUE`)
  on a partitioned table defines the index on the parent and gives each partition, at every
  level, an index with the same columns, method, order and uniqueness: an equivalent index the
  partition already has and that no other parent index uses is taken, otherwise one is created
  and named as PostgreSQL names it (`<partition>_<columns>_idx`, `_key` for a constraint; the
  parent's name in MySQL, whose partitions share index names). `CREATE TABLE ... PARTITION OF`,
  MySQL's and Oracle's named partitions and `ATTACH PARTITION` do the same for every index the
  parent has, so a partition created or attached later has them too (this replaces D169's copy
  of the unique constraints). A unique index on a partitioned table must include every key
  column (`0A000`). `CREATE INDEX ... ON ONLY t` defines it on the parent alone;
  `ALTER INDEX [IF EXISTS] parent_idx ATTACH PARTITION part_idx` attaches a partition's index
  (refused with PostgreSQL's `cannot attach index` errors and details when the table is not a
  partition of the index's table, the definitions differ, or either side is already attached),
  and attaching a primary key's name to a partition's primary key is accepted, since every
  partition keeps its own. `DROP INDEX` of a parent index drops the partitions' indexes attached
  to it; dropping an attached partition index is `2BP01 cannot drop index p_v_idx because index
  t_v_idx requires it`. `DETACH PARTITION` keeps the partition's indexes and detaches them.
- **Catalogs.** An index on a partitioned table has `relkind` `I`; `pg_index.indisvalid` is
  false until every partition, at every level, has an attached index (computed from the links,
  so an `ON ONLY` index becomes valid once the last partition's index is attached, as in
  PostgreSQL); `pg_inherits` links each partition index to its parent index.
- **Format (D35).** The partition record (prefix `0x0E`) gains record version 2, written only
  when a key has an expression or a partition has attached indexes, so files without either keep
  version 1's bytes. Version 2 puts a kind byte before each key part (`0` a column name, `1` an
  expression: the dialect byte of the table definitions and the text), and after a partition's
  bound a count and that many pairs of varints (the partition's index id, the parent's index
  id); a record with a repeated id on either side is damaged. Index ids are the per-table ids
  the table definition gives its indexes, so renames keep the links. An older EggDB reports version 2 as a
  newer format.

Decided by research: Oracle's `ROW MOVEMENT` is off by default (ORA-14402), but EggDB keeps no
per-table switch yet, so rows move in every dialect, as with `ENABLE ROW MOVEMENT`; the clause is
still accepted. PostgreSQL decides immutability from each function's catalog entry; EggDB's
built-in functions carry no volatility yet, so a list of the functions whose value changes
between calls stands in, and user-defined routines are refused in keys.

Left: `DISABLE ROW MOVEMENT` and ORA-14402 in Oracle; row-level `DELETE` and `INSERT` triggers on
the source and target of a moved row (the `BEFORE UPDATE` trigger runs, as in PostgreSQL, but
the source's delete and the target's insert triggers do not fire separately, and statement
triggers of the target's insert do); user-defined `IMMUTABLE` functions and collations or
operator classes in keys; pruning on an expression written differently from the key (`1 + x`
against a key of `x + 1`); unique indexes on keys with expressions;
`relispartition` and `pg_partition_tree` for partition indexes; `CREATE INDEX CONCURRENTLY`
and `REINDEX` on partitioned tables; linking a partition's primary key to its parent's
(`ALTER INDEX parent_pkey ATTACH PARTITION part_pkey` is accepted and links nothing, since
primary keys are not indexes with ids yet); MySQL's list of functions allowed in partition keys
(1564), its integer-only keys (1659) and `YEAR()`, `TO_DAYS()` and the other functions that
list allows (a key that calls one EggDB lacks is accepted and every `INSERT` then fails), and
PostgreSQL's `42883` for an unknown function in a key (`0A000` today); `CHANGE COLUMN` and
`RENAME COLUMN` in MySQL on a column a key reads, which do not rewrite the key yet.

Key columns and older files (review round 1): a key that depends on the session's settings is
refused with `42P17` as PostgreSQL refuses STABLE functions: casts from `timestamptz` to a date,
time, timestamp or text, casts from text, `date` or `timestamp` to `timestamptz`, text output of
dates, times and intervals, text to a date or time type or a catalog type, `to_char`, `to_date`,
`to_timestamp(text, text)`, `age`, and `date_trunc`, `extract` and `date_part` on a
`timestamptz`, and `+`, `-` and comparisons between a `timestamptz` and a `date`, `timestamp` or
interval (`timezone(zone, t)` is IMMUTABLE in PostgreSQL and stays allowed). `DROP COLUMN` of a
column the key of the table or of any of its partitions reads is refused with `42P16 cannot
drop column "b" because it is part of the partition key of relation "f"`; `RENAME COLUMN` on a
partitioned table rewrites the key's column names and expression texts and renames the column in
every partition (their keys too), and renaming an inherited column on a partition is `42P16
cannot rename inherited column`, as in PostgreSQL. A partition record of version 1 that has a
parent (every file from v0.2.0 and v0.3.0, whose partitions hold D169's copies of the parent's
unique indexes) is read with each of the parent's unique indexes linked to the first equivalent
unlinked index of the partition, so those copies count for `indisvalid` and go with
`DROP INDEX` and `DROP CONSTRAINT`; the links are written as version 2 at the partition's next
change. A unique index made `ON ONLY` the parent whose partitions already have an equivalent
unique index is therefore valid at once, where PostgreSQL waits for `ATTACH PARTITION`.

Review round 2: PostgreSQL partition keys now take only what is known `IMMUTABLE`: columns,
constants, operators (with the `timestamptz` checks above, and `||` only between two text
values or arrays), casts that read no setting, and an allow-list of built-in functions (math,
text, `make_date`/`make_time`/`make_timestamp`/`make_interval`, the JSON path extractors, the array
functions, `timezone(zone, t)`, and `date_trunc`, `extract`, `date_part` and two-argument `age`
off `timestamptz`). Every other function, `concat`, `format`, `to_json(b)`, `json(b)_build_*` and
`make_timestamptz` among them, is `42P17` (PostgreSQL accepts some of them that EggDB's list
lacks). A table-qualified column in a key (`(pe.a)`, `(public.pe.a)`) is checked against the
table and stored without its qualifier, so `PARTITION OF` and `RENAME` keep working. `DROP COLUMN`
on a partition of a column its parent has is `42P16 cannot drop inherited column`, and on the
parent it drops the column from every partition too; MySQL answers a dropped key column with
1054 `Unknown column 'c' in 'partition function'`. An index that leaves a table, by `DROP INDEX`,
`DROP COLUMN` or any other path, takes the links naming it with it; a new index never takes an id
that a link still names; and reading the catalog ignores a link whose index or parent index no
longer exists. Known limit: a partition record of version 2 carries no feature bit, so v0.3.0 can
still drop a partition's index without removing its link; such a link is then ignored, and its id
is not reused. Left: `ALTER COLUMN TYPE` and `ADD COLUMN` on a partitioned table still change only
the table named, and on a partition they are not refused as inherited.
