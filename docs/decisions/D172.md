## D172 Concurrent writers as optimistic transactions over the single-writer engine, with snapshot and serializable checks at commit — Decided by research (build loop, 2026-10-31); refines D86 and D87

Part 4.M3-1 asks for many writers at once, snapshot isolation and serializable isolation. The
research of 2026-10-31 asked for MVCC next to D86's single writer, not in place of it. So the
first step adds concurrency above the storage engine and leaves the engine's one-writer commits
unchanged:

- **Optimistic transactions.** `Database::begin_concurrent(isolation)` gives a transaction
  that reads a snapshot (a read transaction, D86) and keeps its writes in an ordered map, so it
  reads its own writes and blocks nobody. `commit` takes the writer as `begin_write` does,
  checks, applies the writes and commits, all in one ordinary write transaction.
- **Serializable** is backward validation: every key read is compared with its value now,
  and every scanned range is scanned again and compared by entry count and an FNV-1a hash of
  its keys and values. When all match, the transaction would have read the same at its commit
  point, so the committed transactions are equivalent to running them one at a time in commit
  order. Comparing values, not versions, accepts a key that changed and changed back, which
  serial order allows.
- **Snapshot isolation** compares only the keys it writes with their snapshot values: first
  committer wins, write skew allowed.
- **Conflicts** are `ErrorKind::Conflict`, and the SQL layer will map them to each dialect's
  serialization failure (PostgreSQL `40001`, MySQL 1213, SQL Server 1205, Oracle ORA-08177).
- **Tests.** A checker replays every committed transaction in commit order and asserts its
  reads saw the serial state. Other tests cover write skew under both isolations, a phantom in
  a scanned range, and four threads of transfers keeping the total.

Left: SQL sessions running on concurrent transactions (`BEGIN ISOLATION LEVEL ...` with the
dialect errors, which 4.M3-2 builds on), collections and expiring keys inside concurrent
transactions, row versions in the storage engine so that changes larger than memory spill,
and waiting on a predicate lock instead of failing at commit.
