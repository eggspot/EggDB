## D318 Read-only transactions in PostgreSQL's, MySQL's and Oracle's dialects (`SET TRANSACTION READ ONLY`, `START TRANSACTION READ ONLY`, `default_transaction_read_only`, `transaction_read_only`), and the routine settings D301 left: `RESET ALL` and `SET eggdb.dialect` inside routines, `ALTER FUNCTION ... SET | RESET`, and `current_setting` reading what a routine set earlier in the same statement — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M3, applies D9, D10 and D173, finishes D301's "Not yet" items for routines, extends D131 and D151

D131 accepted `SET TRANSACTION` and every isolation level, but `SET TRANSACTION READ ONLY` was
`0A000`, `default_transaction_read_only` was remembered and not applied, and only `BEGIN READ
ONLY` refused writes, temporary tables' included. D301 left `RESET ALL` and `SET
eggdb.dialect` inside routines `0A000`, had no `ALTER FUNCTION ... SET`, and read
`current_setting` when the statement was parsed. PostgreSQL's `SET TRANSACTION`, `BEGIN` and
`ALTER FUNCTION` pages and "Configuration Settings Functions", MySQL's "START TRANSACTION,
COMMIT, and ROLLBACK Statements" and "SET TRANSACTION Statement", and Oracle's `SET
TRANSACTION` reference say how they behave; EggDB now follows them.

- **What a read-only transaction refuses.** As PostgreSQL's manual lists: `INSERT`, `UPDATE`,
  `DELETE`, `MERGE` and `COPY FROM` unless the table is temporary, every `CREATE`, `ALTER` and
  `DROP` (temporary objects too), `COMMENT`, `GRANT`, `REVOKE`, `TRUNCATE`, `CREATE TABLE AS`
  and `nextval()`, with `25006 cannot execute <command> in a read-only transaction`. Definition
  commands are refused by their tag before they run; every other write goes through
  `ReadOnlyTransactionWrite`, a writer that lets temporary keys through to the session's
  temporary objects (D151) and refuses any other key with the statement's command, so a
  `CALL` or a volatile function that tries to write is refused at its first write. In MySQL's
  dialect the error becomes 1792 `Cannot execute statement in a READ ONLY transaction.`, and in
  Oracle's `ORA-01456: may not perform insert/delete/update operation inside a READ ONLY
  transaction`.
- **How the transaction is held.** `BEGIN READ ONLY` keeps its reader block (D173), which
  never takes the writer; it may now write temporary tables, whose changes its `COMMIT` keeps
  and its `ROLLBACK` (or a failure, or `ROLLBACK TO SAVEPOINT`) undoes, through the same undo
  log as a writing block. `SET TRANSACTION READ ONLY` before the block's first query gives the
  writer back and becomes a reader block; after a write it keeps the writer and refuses further
  writes, so what was written still commits. `SET TRANSACTION READ WRITE` before the first
  query takes the writer. A statement outside a block under `default_transaction_read_only`
  runs in a reader block of its own.
- **First query.** The session remembers whether the block ran a statement other than `SET`,
  `RESET`, `SHOW` and the transaction commands (PostgreSQL's first snapshot). After one, `SET
  TRANSACTION READ WRITE` in a read-only block is `25001 transaction read-write mode must be
  set before any query`, and an isolation level other than the block's is `25001 SET
  TRANSACTION ISOLATION LEVEL must be called before any query`; inside a savepoint both are
  `25001`, with PostgreSQL's subtransaction wording. Outside a block `SET TRANSACTION` warns
  `SET TRANSACTION can only be used in transaction blocks`.
- **Settings.** `default_transaction_read_only` is now a Boolean setting (`22023` for anything
  else) that every new transaction follows, and `SET SESSION CHARACTERISTICS AS TRANSACTION
  READ ONLY | READ WRITE` sets it. `transaction_read_only` shows the current transaction's mode
  (the default outside a block), kept in step after every statement, so `SHOW` and
  `current_setting` read it; `SET transaction_read_only` and `SET transaction_isolation` are
  `SET TRANSACTION`.
- **MySQL.** `START TRANSACTION READ ONLY | READ WRITE [, WITH CONSISTENT SNAPSHOT]`; `SET
  TRANSACTION READ ONLY | READ WRITE` applies to the next transaction, a single autocommitted
  write included, and is error 1568 while one is open; `SET SESSION TRANSACTION` sets the
  `transaction_read_only` and `transaction_isolation` variables, which every later transaction
  follows; `SET GLOBAL TRANSACTION` is accepted and changes nothing, as other global variables.
- **Oracle.** `SET TRANSACTION READ ONLY [NAME 'name']` opens a reader block, so the
  transaction reads one snapshot, as Oracle's transaction-level read consistency does, until
  `COMMIT` or `ROLLBACK`; a statement that commits implicitly (`CREATE TABLE` and the rest)
  ends it first. Any `SET TRANSACTION` once a transaction is open is `ORA-01453`. `READ WRITE`
  and `ISOLATION LEVEL` are accepted. SQLite and SQL Server have no read-only transactions;
  their `SET TRANSACTION ISOLATION LEVEL` stays accepted.
- **`RESET ALL` inside routines.** It adds a session entry to the routine journal (D301) for
  every parameter whose value differs from its default and every custom parameter, so the
  routine, its callers in the statement and the session afterwards see each reset as a `RESET
  name` would give it; `eggdb.dialect` is left alone, as at the top level.
- **`SET eggdb.dialect` inside routines.** The value is checked when the routine runs (`22023`
  for an unknown dialect) and journaled like any parameter, so its scope is D301's; when the
  statement ends the session switches dialect as a top-level `SET eggdb.dialect` does. The
  routine's own statements keep the routine's language. A switch the session refuses (inside a
  transaction block, or a dialect the connection cannot take) is a warning on the statement's
  result, since the statement has already run.
- **`ALTER FUNCTION | PROCEDURE | ROUTINE ... SET | RESET`.** The routine is kept as its
  `CREATE` text, so the change rewrites that text: the parser records where each `SET`
  clause sits (`SettingSpan`), the clauses of the parameters the statement names (all of them
  for `RESET ALL`) are removed, and one `SET name TO 'value'` per parameter it sets is appended,
  which the `CREATE` grammar takes after the body. `SET name FROM CURRENT` writes the value the
  parameter has when `ALTER` runs, as `CREATE` does, and `SET name TO DEFAULT` is `RESET name`.
  The new text is parsed again and must keep the routine's kind and signature before it is
  saved, so the routine keeps its settings after a restart and in other sessions.
- **`current_setting` at run time.** It is now its own expression (`CurrentSetting`), holding
  the parameter's name, `missing_ok` and the value at parse time. When it runs, the last active
  journal entry for the parameter wins, so `SELECT set_tenant(), current_setting('app.tenant')`
  reads what `set_tenant` set; with no entry, the parse-time value is used. A `set_config`
  earlier in the same statement's text is read at parse time. An unset custom parameter
  (`app.x`) is an error only when the call runs, as in PostgreSQL, and the column is titled
  `current_setting` even when the value is NULL.

Decided by research: the isolation level compared after the first query is the one `BEGIN
ISOLATION LEVEL` or `SET TRANSACTION` named for the block, else `serializable`, the level
`SHOW transaction_isolation` reports, rather than PostgreSQL's default `read committed`, so
EggDB stays consistent with what it shows; `CREATE TEMP TABLE` is refused in a read-only
transaction, because PostgreSQL refuses every `CREATE`, while writes to an existing temporary
table pass; a statement under `default_transaction_read_only` in an implicit transaction (a
multi-statement `Query`) commits its temporary-table writes when it ends rather than with the
implicit transaction, since it never holds the writer; MySQL's next-transaction flag is taken by
the next `START TRANSACTION` or the next write, not by a read in between.
