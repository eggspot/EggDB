## D365 `pg_partition_tree`, `pg_partition_ancestors`, `pg_partition_root` and `relispartition` for partition indexes — Decided by the code-only session (2026-11-10, D355); closes one of D316's leftovers

psql's `\d+`, pgAdmin and pg_dump read the partition hierarchy through these functions and
`pg_class.relispartition`. `pg_partition_ancestors` existed but returned no rows, and
`relispartition` was false for every index.

- **One source.** `pg_inherits` already lists table partitions and the index links of D316;
  the three functions read the same pairs (`relations::inheritance_pairs`), so they agree with
  `pg_inherits` for tables and indexes alike. They load the catalog snapshot like the other
  catalog functions when the statement names them.
- **`pg_partition_tree(regclass)`** returns `relid`, `parentrelid`, `isleaf`, `level` for the
  relation and every relation below it, level by level, children by OID; a partitioned table or
  index with no partitions is not a leaf. **`pg_partition_ancestors(regclass)`** returns the
  relation and its ancestors, nearest first. **`pg_partition_root(regclass)`** returns the top
  ancestor. All three return nothing (or NULL) for a relation that is neither a partition nor
  partitioned, or an unknown OID, as PostgreSQL does.
- **`relispartition`** is true for an index attached to its table's parent's index.
