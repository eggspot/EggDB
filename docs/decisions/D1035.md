## D1035 `eggdb follow` of SQL Server: type changes, unique-index capture instances, replaced tables, and a copy that reconnects — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D282)

- **Type changes.** The per-poll column query now carries each column's type (the same `INFORMATION_SCHEMA.COLUMNS`
  fields the copy reads) and the table's object ID. A followed column whose declared type differs from the one followed
  becomes `ALTER TABLE ... ALTER COLUMN <name> <type> [NOT NULL]` in the poll's transaction, with a `columns_retyped`
  event. Microsoft's CDC documentation says a tracked column's type change is carried to the change table, and change
  tracking reads the table itself, so both kinds keep following.
- **Unique-index capture instances.** The capture-instance batch reads `cdc.index_columns` with each instance and
  whether its `index_name` is a unique index other than the primary key with `supports_net_changes`. A table with no
  primary key whose chosen instance has such an index takes the index's columns as its key: the file gets a `UNIQUE`
  constraint instead of `PRIMARY KEY`, changes are applied by those columns (`IS NULL` for a NULL key value), and net
  changes are read. A table with a primary key keeps D282's rule (net changes only when the index is the primary key).
- **Replaced tables.** Each poll compares a CDC table's object ID with the one seen before. A different ID means the
  table was dropped and created again (CDC drops its capture instances with it). The poll reads the new table's
  columns, key and capture instances; when an instance that captures the key has started, the file's table is emptied
  (or dropped and created again when its shape changed) and copied from the source in the poll's transaction, and the
  table follows the new instance from the current maximum LSN with all changes (not net changes, which could hide a
  row the copy saw). Until the instance starts the table waits; without one the follow stops with the
  `sys.sp_cdc_enable_table` command. A change-tracking table that is replaced stops with a message, because its
  tracking restarts with the new table and the changes in between are lost. The object ID is not saved, so a
  replacement while the follow is stopped is not seen.
- **Lost connection during the first copy.** The copy reads each table before writing it, so an I/O error while
  reading reconnects for `--reconnect-for` seconds and reads that table again; the follow's starting position was taken
  before the copy, so the rows read later converge as D261 describes.
- Learned from Microsoft's documentation of `sys.sp_cdc_enable_table`, `cdc.index_columns` and change data capture
  with DDL; no code was read.
