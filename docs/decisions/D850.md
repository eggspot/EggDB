## D850 SQL Server block predicates — Decided by the code-only session (2026-11-12, D355); follow-up of D822

- Security policies (D822) take `ADD BLOCK PREDICATE fn(columns) ON table AFTER INSERT | AFTER UPDATE` (and `DROP
  BLOCK PREDICATE ON table AFTER ...`): a write whose new row the predicate function returns no row for is refused,
  since row security now checks `WITH CHECK` on `INSERT` and `UPDATE`. Each becomes a restrictive policy: `FOR INSERT
  WITH CHECK (EXISTS (SELECT 1 FROM fn(columns)))` or `FOR UPDATE USING (true) WITH CHECK (...)`, beside the filter
  predicates' `USING` policies, each named by its kind (`sqlserver_policy_<name>_filter`, `_block_insert`,
  `_block_update`). The stored predicates now carry their kind.
- `BEFORE UPDATE` and `BEFORE DELETE` block predicates, and a block predicate with no operation (which SQL Server
  applies to all four), are refused as not supported yet: PostgreSQL-style `USING` would hide the rows silently where
  SQL Server raises an error.
