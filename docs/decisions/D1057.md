## D1057 Replicated (quorum-style) queues — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D33)

- RabbitMQ's quorum queues are queues replicated by Raft, with poison-message handling. In EggDB a queue's messages are
  already rows of the database, so on a `serve --cluster` group (D1038) every publish, acknowledgement and requeue is
  a write that commits through the Raft log before the broker answers: the queue survives losing a minority of
  servers, with no second replication mechanism for messages. What was missing is what clients of quorum queues ask
  for at the protocol level.
- `queue.declare` reads `x-queue-type`: `classic` and no type behave as before; `quorum` is accepted only for a durable
  queue that is neither exclusive nor auto-delete, and refused with `PRECONDITION_FAILED` otherwise, as RabbitMQ
  refuses it; `stream` is refused with a message pointing at the Kafka listener, which is how EggDB serves streams;
  any other type is refused.
- `x-delivery-limit` bounds redeliveries: a message delivered more than that many times again (its receive count
  minus one) is dead-lettered with reason `delivery_limit` when the queue has a dead-letter exchange, and dropped
  otherwise, instead of being delivered again, for pushed deliveries and `basic.get` alike.
- AMQP clients write to the cluster's leader; a follower's database is fenced (D1038), so its publishes fail with the
  leader's id in the error. Left: `x-delivery-count` headers on redeliveries, and leader locators.
- Learned from RabbitMQ's quorum queue documentation; no code was read.
