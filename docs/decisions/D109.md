## D109 Secondary indexes: entries on the key-value engine beside the rows, table definitions in format version 3, a planner of fixed rules, `EXPLAIN` in each dialect's style — Decided by the build loop (2026-10-27); roadmap item 19c, applies D2, D7, D9, D10, D20, D35, D98

**Storage.** A secondary index is a range of the same ordered key space as the rows (D98):
prefix, `0x04`, the table number and the index number (4 bytes each, big-endian), the indexed
columns' values in the primary key's order-preserving encoding (NULL after every value), then
the row's primary-key bytes (or hidden row number). The value is empty. Every entry carries the
row key, so entries of equal values stay distinct, a unique index needs no second layout, and
equal values come out in primary-key order. Finding a row from an entry skips the indexed values
by their types; damaged bytes are `XX001`, never a panic, and a seeded fuzzer feeds damaged
entries and definitions to the decoders.

**Writes.** Entries are written and removed in the same write transaction as their rows by every
statement that changes rows (`INSERT` with `IGNORE`, `REPLACE` and upserts, `UPDATE`,
`DELETE`, `TRUNCATE`, `DROP TABLE`), so the engine's atomic commit and crash recovery cover
them; a test kills `eggdb sql` mid-script and checks every index against its rows. A unique
index is checked by a range read of the new values that skips the row's own entry. `UPDATE`
removes the old entries of every changed row before writing the new ones, so uniqueness is
checked at the end of the statement as the primary key already is (D98), and swapping values
works. NULLs never conflict, as in PostgreSQL, MySQL and SQLite. A conflict on a unique index
behaves like one on the primary key for `INSERT IGNORE`, `REPLACE` (every conflicting row is
removed) and `ON DUPLICATE KEY UPDATE`/`ON CONFLICT DO UPDATE` (the conflicting row is updated).
`CREATE INDEX` fills a new index in the statement's transaction from a forward scan, a thousand
rows at a time, charged to the 1 GiB work memory and released after each batch.

**Catalog (security-relevant format change, D35).** Index definitions live in the table
definition. A table with indexes is written as table-definition format version 3: the version 2
body (version 3 allows at most one `AUTO_INCREMENT` column, which must lead the primary key),
then the index count (at least one, at most 1,024) and per index its number (4 bytes, little-
endian), name, a unique byte (0 or 1) and its 1 to 32 distinct column numbers. A table without
indexes is still written as version 1 or 2, byte for byte as before, so files that do not use
indexes stay readable by older releases, and an older release refuses a version 3 table by name
(`0A000`) instead of misreading it. Tests pin the version 3 bytes, cut every encoding at every
length, damage each marker and refuse version 4. The D96 sample files are untouched. A
consistency check (`Session::check_indexes`) proves each row has exactly its entries and no
unique index holds a value twice; `eggdb check` reads pages and keys and does not run it,
because the engine below SQL does not know tables.

**Names (decided by judgement).** Each dialect names indexes as its database does: PostgreSQL
`t_a_key` for a `UNIQUE` constraint and `t_a_idx` for an unnamed `CREATE INDEX`, numbered on a
clash, and one namespace with tables; MySQL the first column, then `_2`, per table; SQLite
`sqlite_autoindex_t_N` for every `UNIQUE` constraint; Oracle `SYS_C` and seven digits. Names
are unique across the database except in MySQL, where they are per table, as there; a name that
two tables share (made through MySQL) must be dropped with MySQL's `DROP INDEX name ON t`.
Errors take each database's wording: PostgreSQL's `duplicate key value violates unique
constraint "i"`, MySQL's `Duplicate entry 'v' for key 't.i'` (1062, and 1061, 1072, 1091),
SQLite's `UNIQUE constraint failed: t.a` (2067), Oracle's `ORA-00001`, `ORA-01452`, `ORA-00955`
and `ORA-01418`; the duplicate-key error carries its table internally so each dialect can name it.

**Planning (decided by judgement, no statistics yet).** For the primary key and each index the
planner takes the longest leading run of columns compared with constants by `=`, `IN (list)`
(at most 256 ranges in all) or `IS NULL`, then one range on the next column (`<`, `<=`, `>`,
`>=`, `BETWEEN`, case-sensitive `LIKE 'prefix%'`), and picks a unique key fully fixed by `=`,
then the longest equality run, then a range, then the primary key over an index. A constant is
used only when it converts to the column's type exactly and is of the same family; the whole
`WHERE` still filters every row read, so a range only has to contain the answer, and a test
compares random queries and changes with and without indexes. `ORDER BY` that continues a key's
matched columns in one direction reads the key in order (backward for `DESC`), skips the sort
and stops at `LIMIT`; an index without a matching `WHERE` is read in order only under a
`LIMIT`, the primary key always. A join reads its inner table through an index on its join
columns when the outer side is a key lookup or the hash table would pass 64 MiB, as primary-key
lookups already do (D100). Covering reads that skip the table are left for later.

**`EXPLAIN`.** PostgreSQL's dialect prints the plan's nodes without costs (`Seq Scan on t`,
`Index Scan [Backward] using i on t`, `Sort`, `Limit`, `Nested Loop`, `Hash Join`); MySQL's
gives its `EXPLAIN` columns with `type` `ALL`, `const`, `eq_ref`, `ref`, `range` or `index`;
SQLite's gives `EXPLAIN QUERY PLAN` rows (`SEARCH t USING INDEX i (a=? AND b>?)`); Oracle's
`EXPLAIN PLAN` waits for `PLAN_TABLE`. Tests prove an indexed lookup reads only its range by
counting the entries the store reads.

**Catalog views.** MySQL `SHOW INDEX`, keys in `SHOW CREATE TABLE` and `UNI`/`MUL` in
`DESCRIBE`; SQLite `PRAGMA index_list` and `index_info` and index rows in `sqlite_schema`;
Oracle `USER_INDEXES`, `ALL_INDEXES`, `USER_IND_COLUMNS` and `ALL_IND_COLUMNS`; `.schema` in the
shell prints each table's `CREATE INDEX` statements.
