## D1100 Archive uploads without a staging file, and a simulation of restoring under failures — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D226, D920, D921)

- **Copies built in memory.** `Database::backup_to_bytes` runs the same snapshot copy as `backup_to`: key by key, from one read snapshot, so the writer never waits. It writes into the deterministic in-memory file system (`SimFileSystem`) instead of the disk, and returns the copy's bytes. `eggdb backup <file> s3://...` uses it when the database file is at most 1 GiB. The copy is checked by opening it in memory (`Database::from_image`) and running `check`, its SHA-256 is taken from the bytes, and it is uploaded from memory (multipart above the single-request size, D921). A server with a small or read-only disk (a container, a serverless instance) can then archive. A larger database still stages its copy beside the file, so memory never has to hold more than 1 GiB of copy; the limit is a constant, and the weekly pass can raise it with measurements.
- **Restore under failures, simulated.** The restore path now reads through a small `ArchiveObjects` trait (a bucket's manifest, its locked manifest lines and the copies). A test drives it with 200 seeds of injected faults: errors, truncated bodies, flipped bytes, missing objects and failed listings on any request. Every seed either restores a copy byte-identical to the archived one, which opens and checks with every entry, or fails with no file at the target. It never leaves a partial or damaged database. This is the "simulator test of restoring under failures" D226 left open.
