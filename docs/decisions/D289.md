## D289 SQL/JSON's `JSON_EXISTS`, `JSON_VALUE`, `JSON_QUERY` and `JSON_TABLE`, `json(b)_populate_record(set)` and the jsonpath datetime methods run on D272's bounded path evaluator — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap item 36, refines D272

D272 left `json(b)_populate_record(set)`, the `datetime()` family of path methods and the
SQL-standard query functions for later. They are built here, written from the SQL standard's
SQL/JSON clauses and PostgreSQL 17's and Oracle's documentation, no code read.

- **Datetime items without a new JSON variant.** `.datetime()`, `.datetime(template)`,
  `.date()`, `.time([p])`, `.time_tz([p])`, `.timestamp([p])` and `.timestamp_tz([p])`
  (`crates/eggdb-sql/src/json_path/temporal.rs`) make a datetime item, held inside the
  evaluator as an object whose first key starts with a NUL character. No document or `vars`
  object can hold that key, because the `jsonb` parser refuses `\u0000` (D272), so the public
  `Json` type and every match on it stay as they were. Member, wildcard and recursive accessors
  treat the item as a scalar, `.type()` names its SQL type, `.string()` gives its ISO text, and
  a result that leaves the evaluator is that ISO text (`"2017-03-10T12:34:56+03:00"`), as
  PostgreSQL's `jsonb` output of a datetime is.
- **Reading strings.** Without a template, the input must be one of the ISO forms PostgreSQL
  tries (`yyyy-mm-dd`, `HH24:MI:SS[.US]` with an optional `TZH[:TZM]`, and the two joined by a
  space or `T`); the parts are then read by D271's date and time input, so infinity and range
  checks are the same as a cast's. A template goes through `to_timestamp`'s reader
  (`pg_format::template_moment`), and the fields it holds choose `date`, `time`, `timetz`,
  `timestamp` or `timestamptz`. PostgreSQL also requires the template's separators to match the
  input exactly; EggDB reads them as leniently as `to_timestamp` does.
- **Time zones.** Comparing a date or a time stamp with a `timestamptz`, a `time` with a
  `timetz`, and the conversions between them need the session's time zone, so only the `_tz`
  functions and the SQL/JSON query functions make them; the others fail with `22031` and
  PostgreSQL's hint. A date and a time are not comparable (unknown). An unrecognized string is a
  suppressible `22031`, so `silent`, lax filters and `ON ERROR` handle it.
- **The query functions are internal calls.** The parser turns `JSON_EXISTS`, `JSON_VALUE` and
  `JSON_QUERY` (in PostgreSQL's and Oracle's dialects, which share the syntax) into calls of
  internal functions whose arguments are the document, the path, the `PASSING` values as one
  `jsonb_build_object` call, a `CAST(NULL AS type)` placeholder for `RETURNING`, and integer
  codes for the wrapper, quotes and behaviors, followed by the `DEFAULT` expressions
  (`crates/eggdb-sql/src/sql_json.rs`). The evaluator reads the placeholder's static type for
  the result type and evaluates a `DEFAULT` expression only when its clause applies, so no new
  syntax tree node was needed.
- **Errors and behaviors.** A suppressible path error, a coercion to the `RETURNING` type that
  fails, several items (`22034`) and an object or array in `JSON_VALUE` (`2203F`) go to
  `ON ERROR` (NULL by default, `FALSE` for `JSON_EXISTS`); a `DEFAULT ... ON EMPTY` that fails
  goes to `ON ERROR` too, as PostgreSQL documents. `ERROR ON EMPTY` raises `22035` whatever
  `ON ERROR` says, as the standard's rules read; PostgreSQL's documentation does not settle
  whether its `ON ERROR` catches that error. Fatal path errors (the 1,000-node and
  1,000,000-item limits, an undefined variable) and a document that is not JSON are always
  raised. `WITH CONDITIONAL WRAPPER` wraps only when there is more than one item, and `OMIT
  QUOTES` with a wrapper is a syntax error, as in PostgreSQL. Oracle's `JSON_QUERY` returns text
  by default, and Oracle's order of `ON ERROR` before `ON EMPTY` is accepted in both dialects.
- **`JSON_TABLE` is a table function with a plan argument.** The `COLUMNS` tree (`FOR
  ORDINALITY`, regular columns read like `JSON_VALUE`, or like `JSON_QUERY` when they have
  `FORMAT JSON`, a wrapper or quotes clause or a JSON, array or composite type, `EXISTS`
  columns and `NESTED [PATH] ... COLUMNS`) is encoded as one length-prefixed text argument, the
  output columns are typed placeholders as in D272's column definition lists, and the column
  `DEFAULT` expressions follow them. A child row joins its parent row, siblings' rows are a
  union, and a parent whose nested paths find nothing still gives one row with NULL children, as
  PostgreSQL's example outputs show. Each nesting level has its own ordinality counter. A column
  without `PATH` reads `$."name"`. The row path's errors give no rows unless `ERROR ON ERROR` is
  written (Oracle's `NULL ON ERROR` is the same as `EMPTY`). Paths must be string constants.
- **Bounds.** A plan nests at most 32 levels (`54001` in the parser, damage when decoding), the
  rows one call produces across all levels are at most 1,000,000 (`54000`), every path keeps
  D272's limits, and decoding a hand-written plan (a quoted `"*json_table*"` call) returns
  errors, never panics.
- **`json(b)_populate_record(set)` take a table's or a composite type's row type.** For
  `NULL::t` or `CAST(NULL AS t)` where `t` is a table or view, the parser, once it has the
  user-defined types and still finds no type `t`, keeps a row type marker; name resolution then
  replaces it with one typed placeholder per column of `t` (search path applied), and the rows
  are read member by member exactly as `json_to_record`'s are. A composite type is filled the
  same way from its attributes. A missing name fails with `42704`, a non-row type with `42804`.

Not yet: a base record that is not NULL in `json_populate_record` (`0A000`), the functions in a
select list (`SELECT json_populate_record(...)` and `(...).*`), a column alias list on them,
`JSON_TABLE`'s `PLAN` clause and path names used by it, MySQL's `JSON_VALUE` and `JSON_TABLE`
(its path language differs), `JSON_SERIALIZE`, `JSON_SCALAR`, `JSON()` and the `IS JSON`
predicate, PostgreSQL 17's `.decimal()` path method, and a `jsonpath` type of its own.
