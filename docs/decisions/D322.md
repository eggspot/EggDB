## D322 Generated columns in every dialect: PostgreSQL's `GENERATED ALWAYS AS (expr) STORED | VIRTUAL`, MySQL's and SQLite's `[GENERATED ALWAYS] AS (expr) [VIRTUAL | STORED]`, SQL Server's computed columns and Oracle's virtual columns, kept in table definition format version 14 — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M5, applies D9, D10, D19, D20, D32 and D35; security-critical (file format)

`GENERATED ALWAYS AS (expr) STORED` answered `0A000` in PostgreSQL's dialect, SQL Server's `c AS
(expr)` answered "Computed columns are not supported", and MySQL, SQLite and Oracle refused the
clause. Applications and dumps that use them (ORMs map computed properties to them, `pg_dump`
writes them) could not create their tables. Each dialect's behavior is taken from its manual:
PostgreSQL's "Generated Columns" (ddl-generated-columns, with PostgreSQL 18's virtual columns),
MySQL's "CREATE TABLE and Generated Columns", SQLite's "Generated Columns" (gencol.html), SQL
Server's "Specify Computed Columns in a Table" and Oracle's `CREATE TABLE` "virtual_column_definition".

- **Definition.** The parser reads each dialect's spelling into one `GenerationSpec` on the
  column (expression, its text, stored or virtual, whether a type was written). `CREATE TABLE` and
  `ALTER TABLE ADD COLUMN` check the expression (`generated_columns::define`): its columns must
  exist; no subquery, aggregate or function that changes between calls (the list partition keys
  use, D316); references to other generated columns only where the dialect allows them, ordered
  without loops; no `DEFAULT` with it. A call to a user-defined function is refused: one not declared
  `IMMUTABLE` with the dialect's "not immutable" error, an `IMMUTABLE` one with `0A000`, as its
  call is not resolved when a row is written yet. A computed column without a type takes its
  expression's static type. SQL Server's `c AS expr` reads the whole expression after `AS`, so
  `c AS (a + b) * 2` works. MySQL's rule that a generated column refers only to generated
  columns before it is checked again after `FIRST` or `AFTER` moves a column (`3107`). A
  partitioned table, its partitions and a table attached as a partition take no generated
  column (`0A000`), through `CREATE TABLE`, `ALTER TABLE ... ADD COLUMN` and `ATTACH PARTITION`.
- **Storage.** `TableDefinition.generated` lists, for each generated column, its position, the
  dialect its expression is written in, the expression's text and whether it is stored. A table
  with generated columns is written in table definition format version 14: every section of
  version 13, then a count (at least 1) and, per column in increasing position, a varint
  position, a kind byte (0 virtual, 1 stored), a dialect byte and the expression's text. A table
  without generated columns keeps writing the version it wrote before, so files that never use
  the feature are unchanged. An older EggDB refuses a version 14 record by name ("written in
  format version 14, which this EggDB cannot read", `0A000`), never by misreading it as plain
  columns. The reader refuses as damaged an empty list, a position out of range or out of order,
  a column with a `DEFAULT` or `AUTO_INCREMENT`, an unknown kind or dialect and an empty
  expression; the unit tests cover the round trip, every truncation and those refusals. This is a
  file format change, so it is security-critical under D35.
- **Values.** Virtual columns are kept like stored ones: the value is computed when the row is
  written, so a read gives what the expression would and costs nothing (D6). `PreparedChecks`
  carries a `Generator` that fills every generated column, in dependency order, before the
  `NOT NULL` and `CHECK` tests on every write path: `INSERT` (including the literal fast path,
  which hands tables with generated columns to the general one), `UPDATE` (again after `BEFORE`
  triggers), upserts, `MERGE`, cascaded foreign-key updates, `COPY`, bulk loads, table rewrites
  and `ADD COLUMN` over existing rows.
- **Errors and catalogs** follow each dialect, as listed in sql.md's "Generated columns".

Decided by research:
- *Store virtual columns or compute them on read?* Store them. The brief allows it when behavior
  matches, which holds only for expressions that give the same value on every call. Every
  dialect but SQL Server requires that at definition. SQL Server lets a computed column that is
  not `PERSISTED` call `GETDATE()`, `NEWID()` and the like and computes it on each read, which a
  kept value cannot match, so EggDB refuses such a column with `0A000` and a hint (compute it in
  the query or a view) until virtual columns are computed on read. (The first version of this
  entry said the expressions were immutable in every dialect; review round 1 found this SQL
  Server case and corrected it.) With that, the stored value always equals the computed one,
  reads stay a plain row decode, and indexes on virtual columns need no expression index. The cost is the column's bytes per row, which MySQL's and SQLite's virtual
  columns avoid; computing on read is left for when the storage engine's column projection
  (D40) makes it cheap.
- *PostgreSQL without `STORED`?* PostgreSQL 18 made `VIRTUAL` the default and refuses indexes on
  virtual columns; EggDB follows 18 (the newest documented behavior) rather than 17's syntax error.
- *Where the generation lives in the format.* In the table definition, not a side record: a side
  record would let an older EggDB open the table and accept writes into generated columns
  without computing them, silently. A new version makes older readers refuse.

Left: SQL Server's `sys.computed_columns` rows (the view exists, empty); SQLite's and Oracle's
`CREATE TABLE` text and `eggdb dump` in those dialects writing the generation clause; MySQL's
`SHOW CREATE TABLE` clause; virtual columns computed on read instead of kept; `ALTER TABLE ...
ALTER COLUMN ... SET EXPRESSION AS (...)` and `DROP EXPRESSION` (PostgreSQL), `MODIFY` of a
generated column (MySQL); generated columns in partition keys; SQL Server's non-persisted computed
columns over functions that change between reads (refused until then); user-defined functions in
generation expressions (an `IMMUTABLE` one is refused with `0A000` until its call is resolved on
write); PostgreSQL's stable casts (such as `timestamptz` to `text`) in a generation expression,
which are accepted where PostgreSQL refuses them; generated columns in partitioned tables.
