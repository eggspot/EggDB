## D103 The PostgreSQL server: an `eggdb-pgwire` crate over the SQL core, a thread per connection, SCRAM-SHA-256 with our own `eggdb-crypto`, and one user whose verifier is derived at startup — Decided by the build loop (2026-10-27); roadmap item 21, applies D1, D5, D9, D12, D22, D23, D35, D102
**Crates.** `eggdb-crypto` holds SHA-256 (FIPS 180-4), HMAC-SHA-256 (RFC 2104), PBKDF2-HMAC-SHA-256
(RFC 8018), strict Base64 (RFC 4648) and a constant-time comparison, written from the standards
with no dependencies and checked against their published vectors (FIPS 180-4 and NIST,
RFC 4231, RFC 7914) in `crates/eggdb-crypto/tests/vectors.rs`. `eggdb-pgwire` speaks the
PostgreSQL protocol v3 from PostgreSQL's public protocol documentation: message codecs,
SCRAM-SHA-256 (RFC 5802, RFC 7677, checked against RFC 7677's example exchange), the
connection state machine and the server. It depends on `eggdb-sql`, `eggdb-crypto` and
`eggdb-platform` and is generic over `eggdb_sql::KeyValueStore`, so the engine core never
depends on a protocol; the `eggdb` binary passes its database. The platform layer gains
`secure_random` (`/dev/urandom` on Unix, `BCryptGenRandom` on Windows) and `stop_signals`
(`SIGINT`/`SIGTERM`, console control events).

**Threads.** One thread and one `eggdb_sql::Session` per connection, at most 64 by default
(`--max-connections`); the next client is answered `53300 too_many_connections` after its startup
packet, by at most 8 short-lived refusing threads, and anything beyond that is closed. Sessions
share the database as the engine allows: snapshot readers and one writer at a time; a second
writer waits the database's write timeout (5 s) and then fails with `55P03`. Sockets use
`std::net` (portable, so no OS code outside the platform layer) with a 200 ms read poll, so a
stop request is seen within that time. A stop ends idle connections with `57P01
admin_shutdown`, lets running statements finish, rolls back open blocks and returns.

**Hostile clients.** Startup packets are limited to 10,000 bytes and messages before
authentication to 16 KiB; after it, to 1 GiB plus 1 MiB (the largest value plus room), read in
64 KiB steps so memory follows the bytes actually sent. Startup and authentication must finish
within 30 s. Every parser returns errors as values; malformed messages end the connection with
`08P01`. A failed password is answered after a delay of 250 ms per failure in the last minute,
at most 5 s, and logged with the client's address.

**Credentials.** This release has one user per server, named with `--user` (default `eggdb`);
its password comes from `EGGDB_PASSWORD` or `--password-file` (first line, `-` for stdin),
never the command line, where `ps` shows it. At startup the server derives the SCRAM-SHA-256
verifier (StoredKey, ServerKey) with a fresh 16-byte random salt and 4,096 PBKDF2 iterations
(RFC 7677's minimum and PostgreSQL's default) and keeps only that; nothing is written to the
database file. An unknown user gets an exchange that looks the same (a salt derived from a
per-server random secret and the name) and fails at its end with the same `28P01` message.
Passwords must be ASCII, since SASLprep (RFC 4013) is not implemented: for ASCII it is the
identity, so libpq and drivers compute the same proof. Users and roles stored in the database,
with their verifiers, come with D22's roles (M6a).

**Not in this release**, each refused or ignored harmlessly: TLS and channel binding
(`SCRAM-SHA-256-PLUS`), query cancellation (a `CancelRequest` is closed without effect), COPY,
`LISTEN`/`NOTIFY`, the function call protocol, the replication protocol, pipelining's implicit
transaction (each `Execute` and each statement of a multi-statement `Query` commits on its own
outside an explicit block), and catalog queries for GUI tools (`\d` in psql fails with a
readable error).

**Size (D6).** The `eggdb` binary grows by the server and the cryptography; the growth is
measured by CI's `bench` job and reported in the pull request. The reason is roadmap item 21:
psql and drivers connecting is a v0.2.0 must-have.

**Review fixes (2026-10-27, before merge).** Two independent reviews of the pull request found
these, now fixed:
- The authentication deadline and the stop request were checked only when a read timed out, so
  a client sending a byte every 100 ms escaped both. Both are now checked before every read,
  and each read waits at most the time left before the deadline, and never more than 200 ms, so
  a stop is seen within about 200 ms even in the middle of a message, before or after
  authentication. The refusing threads use the same reads with a 2 s deadline.
- Client-supplied names (the user, the database) were written to the log unescaped, so a name
  with a line break could forge log lines. They are now escaped (backslash, double quote,
  control characters as `\n`, `\r`, `\t`, `\u{..}`), and `eggdb serve` also replaces any
  control character left in a log line.
- `Execute` of a portal that was not described typed its columns from the rows, which could
  disagree with `Describe` of the statement (`coalesce(NULL, id)` described as `text`, sent as
  binary `int4`). `Execute` now describes the statement the same way `Describe` does and sends
  every value in that type; typing columns from the rows stays only in the simple query
  protocol, whose values are text.
- A portal that ran to completion ran its statement again on a second `Execute` (an `INSERT`
  inserted twice). It now answers with its command tag and a count of 0 (`INSERT 0 0`,
  `SELECT 0`), and a portal whose statement failed answers `55000`.
- `RowDescription`, `DataRow` and `ParameterDescription` with more than 32,767 entries (or a
  value over 2 GiB) are refused with `54011` or `54000` instead of a wrapped 16-bit count.
- A second writer's `55P03` names what a SQL client can do (retry once the other session's
  write transaction ends), not a Rust option.
- At most 16 connections may be starting up or authenticating at once (fewer when
  `--max-connections` is lower), so slow or failing logins cannot take every slot; more get
  `53300`.
- `EGGDB_PASSWORD` stays in the server's environment while it runs; docs/cli.md says so and
  recommends `--password-file`.

Known and left for M6a: portals live until closed rather than until their transaction ends,
`Parse` checks syntax only, and a multi-statement `Query` or an extended-protocol batch commits
statement by statement outside `BEGIN`.
