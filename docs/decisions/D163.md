## D163 The compatibility list, and what makes a tool "supported" — Decided by the build loop (by judgement, 2026-10-31)

`docs/compatibility.md` lists every tool, driver, ORM and migration tool EggDB is checked with,
its version, its protocol and how it is checked. Release notes quote it.

- **Supported:** a CI job runs the tool itself, or replays what it sends, on every pull request,
  so a change that breaks it fails the PR.
- **Expected to work:** EggDB answers every catalog query and protocol message the tool is known
  to send, and unit tests check those answers, but no CI job runs the tool. This covers GUI tools
  that cannot run headless in CI (pgAdmin, DBeaver) or whose licence forbids it (SSMS).

A tool moves from "expected to work" to "supported" only when a CI job covers it. Its status
never goes down without a note in the release notes.

For pgAdmin, part 3.19 adds the statistics views and catalogs it reads on every connection and
dashboard refresh:
- `pg_stat_activity` (this session), `pg_stat_database` (zeros), `pg_locks`,
  `pg_prepared_xacts`;
- `pg_extension` (`plpgsql`), `pg_user`, `pg_cast`, `pg_operator`, `pg_aggregate`, and empty
  foreign-data, replication, subscription, full-text and statistics catalogs;
- the privilege functions, which answer true, since EggDB has one user (D22's roles come with
  M6a);
- `pg_is_in_recovery`, `pg_backend_pid`, `pg_postmaster_start_time`, `pg_size_pretty` (as
  PostgreSQL rounds), and the size functions, which answer 0 until EggDB measures relations.

These catalogs live in their own module, `pg_catalog/monitoring.rs`, as `information_schema`
does.
