## D448 Application-lock deadlocks choose one victim — Decided by the code-only session (2026-11-11, D355); roadmap M10 (PR #91's leftover)

- Every waiter of `sp_getapplock` (and of MySQL's `GET_LOCK`, D422, which shares the locks) checks
  while it waits whether its wait closes a cycle. When two waiters close one, both saw it and both
  gave up with status -3, where SQL Server makes one victim and lets the rest go on.
- Now each wait carries a ticket from one counter, in the order the waits began, and a waiter
  finding a cycle walks it (`cycle_through`, a depth-first search through the sessions it waits
  for) and gives up only when it holds the newest ticket of the cycle's members: the session whose
  wait closed the cycle, as the old test expects, and exactly one of them. The others keep
  waiting and are granted the lock once the victim's session or transaction releases what it
  holds.
- SQL Server picks its victim by `DEADLOCK_PRIORITY`, then by the cheaper transaction to roll
  back; EggDB has neither, so "the newest wait" stands in. `SET DEADLOCK_PRIORITY` is left.
