## D764 Tenants isolated by schema (eggdb_tenancy) — Decided by the code-only session (2026-11-12, D355); roadmap M6b, isolation of tenants by schema or by database (D32, D234)

- `eggdb_tenancy.create_tenant_schema(tenant, template)` gives a tenant its own schema beside D234's isolation by
  row. The schema and a role share the tenant's name, so the default `search_path` (`"$user", public`) resolves the
  tenant's tables first for that role without per-role settings, and an application connecting as the tenant's role
  uses unqualified names.
- Each base table of the template schema is copied without rows by `CREATE TABLE ... AS SELECT * ... WHERE false`
  (exact column types), then given its `NOT NULL`s, defaults, primary key and unique constraints from
  `information_schema`; a `nextval` default gets a sequence of the tenant's own, so tenants never share counters.
  Foreign keys, checks, indexes beyond the keys, triggers and identity columns are not copied yet.
- The schema is revoked from `PUBLIC`; the tenant role gets `USAGE` on its schema and `SELECT`, `INSERT`, `UPDATE`
  and `DELETE` on its tables and its sequences' use, nothing else.
- `upgrade_tenant_schemas(template)` is the migration across tenants: it adds the template's new tables and new
  columns (types rebuilt from `information_schema`, with defaults and `NOT NULL`) to every tenant schema made from it,
  refusing (0A000) a column it cannot rebuild (arrays, user-defined types, serials). Dropped or changed columns are not
  followed. `drop_tenant_schema(tenant)` drops the schema with `CASCADE` and keeps the role.
- Isolation by database is left: a function cannot create a database inside a transaction, so it needs a server-side
  command.
