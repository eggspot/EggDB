## D421 MySQL events (`CREATE EVENT`) on the job scheduler — Decided by the code-only session (2026-11-11, D355); roadmap M10

- **Statements.** The MySQL dialect parses `CREATE [DEFINER = ...] EVENT [IF NOT EXISTS] name ON
  SCHEDULE {AT ts | EVERY n unit [STARTS ts] [ENDS ts]} [ON COMPLETION [NOT] PRESERVE] [ENABLE |
  DISABLE [ON SLAVE]] [COMMENT '...'] DO body`, `ALTER EVENT` (schedule, completion, `RENAME TO`,
  status, comment and body), `DROP EVENT [IF EXISTS]`, `SHOW EVENTS [LIKE ...]` and `SHOW CREATE
  EVENT`, with MySQL's errors (1537 exists, 1539 unknown, 1542 interval not positive, 1521 `ENDS`
  before `STARTS`, 1525 a time that doesn't read) and note 1588 for an `AT` in the past without
  `PRESERVE` (the event is not kept). The body is one statement or a `BEGIN ... END` block,
  checked by the stored-program compiler when the event is created. Units are every MySQL
  interval unit, compound ones included (D415).
- **Storage.** Events live in an internal table, `eggdb_internal.mysql_events` (the schema the
  materialized views already use), keyed by lower-cased `database.name`; times are seconds since
  1970 UTC, computed from the statement's expressions in the session's time zone, and the
  interval is kept as MySQL wrote it (`'1:30' HOUR_MINUTE`). Using a table rather than a new
  catalog record keeps the file format as it is and lets the scheduler read events with SQL, as
  pg_cron's jobs (D200) are read. `SHOW CREATE EVENT` rebuilds the `CREATE` text from the stored
  fields, so it stays right after `ALTER EVENT`.
- **Running.** `eggdb serve`'s job thread now also calls `jobs::run_due_events` each minute: every
  enabled event whose next run has come runs in its own MySQL session, in its database, as an
  inline MySQL program (`plpgsql::run_mysql_inline`), in one transaction. A recurring event then
  moves to its first run after now (missed runs while the server was down are skipped, not
  replayed); a one-time event, or a recurring one past `ENDS`, is disabled with `PRESERVE` and
  dropped without it, as MySQL does.
- **Known differences.** The scheduler ticks once a minute, so an event runs up to a minute late
  and one scheduled `EVERY` few seconds runs once a minute (D576 runs them to the second). `information_schema.EVENTS` in MySQL's
  view stays empty, the `event_scheduler` variable doesn't switch the scheduler off, and failures
  are counted but not logged (MySQL writes them to its error log).
