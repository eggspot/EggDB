## D1022 A locked manifest, and WORM for local archives — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D53, D919)

- **Locked manifest.** D919 locked each copy in the bucket, but `manifest.jsonl` is rewritten at every backup, so
  it cannot be locked, and whoever can write it could point a restore at a different SHA-256. With `--lock-days`,
  each manifest line is now also stored on its own, under the same Object Lock retention, as
  `manifest.d/<copy>.json`. Readers list `manifest.d/` and let each locked line take the place of the copy's line in
  `manifest.jsonl`, so a locked copy is always checked against a hash nobody could change. `manifest.jsonl` stays
  as the writable index older readers know.
- **WORM for local archives.** `eggdb backup <file> <directory> --lock-days <n>` makes each archived file read-only
  and immutable where the platform layer can set it: the user immutable flag through `chflags` on Apple systems and
  the BSDs, and the immutable attribute through `FS_IOC_SETFLAGS` on Linux, which needs `CAP_LINUX_IMMUTABLE`. The
  manifest records `locked_until` and whether the file is immutable, and retention (`--keep`, D1020) never removes a
  file before its lock ends; afterwards it clears the flag and removes it.
- What local WORM does not do: an administrator, or the owner for the user flag, can clear the flag; only a
  bucket's Object Lock in compliance mode (D919) or WORM storage hardware resists a privileged attacker. The docs say
  so, and the manifest's `immutable: false` shows where only the read-only permission applied.
