## D717 Kafka transaction timeouts — Decided by the code-only session (2026-11-12, D355); roadmap M16, Kafka transactions (D213, D694)

- `InitProducerId` now keeps the producer's `transaction.timeout.ms` with its transactional id. A timeout below 1 ms
  or above 900,000 ms (Kafka's default `transaction.max.timeout.ms`) is refused with `INVALID_TRANSACTION_TIMEOUT`
  (50), as Kafka does.
- A transaction starts its clock when its first partition or offset is added. Once it has been open longer than its
  timeout, the coordinator aborts it (abort markers, the aborted ranges for `read_committed` readers, pending offsets
  dropped) and raises the epoch, so the old producer's next `AddPartitionsToTxn`, `AddOffsetsToTxn`,
  `TxnOffsetCommit` or `EndTxn` gets `INVALID_PRODUCER_EPOCH` (47).
- The abort happens when the transaction is next touched, and a sweep over every transactional id runs at most once
  every ten seconds per process (Kafka's default cleanup interval), on the next authenticated request, so an
  abandoned transaction stops holding back the last stable offset without a background thread.
- The stored transaction state gained the timeout and start time at its end; state written before reads as a
  60-second timeout with no clock started.
