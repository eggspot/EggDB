## D281 `eggdb mcp --tables` tighter: a table may be listed with only some columns, a table an unlisted one references takes inserts, and a new policy or stored expression may not call a user routine or hold a subquery — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); follows up D257's "Left for later", applies D9, D11, D35, D156 and D257; security-critical (D35)

D257 left three gaps in the agent's table allow-list: the stored code a listed table may gain,
the listed table that an unlisted one references (frozen whole, though an insert cannot reach
the other table), and a way to show only some columns.

**Column lists.** `--tables "orders(id,total),customers"` shows `orders` with only `id` and
`total`. The limit sits in the same store filter as D156's (`VisibleTables`), not in the
statements: for a table listed with columns, `VisibleRead` and `VisibleWrite` return its
definition with the other columns removed (as `DROP COLUMN` would leave it: the primary key,
indexes, checks, foreign keys, identities, default dialects and domains renumbered, and the
indexes, checks and foreign keys over a left-out column dropped), every row re-encoded with only
the listed columns, and they hide the entries of the dropped indexes, the table's statistics, its
SQLite text and the comments on anything but the table itself. So `SELECT *`, `describe_table`,
`sample_rows`, every catalog and every name resolution, a view's, a function body's, a CTE's or a
subquery's, find only the listed columns, and naming another fails as an unknown column
(`42703`). Rules, all failing closed:

- the list must hold the table's primary key (rows are keyed by it), the table must exist when
  the session starts, and a view takes no list. `VisibleTables::unservable_column_lists` reports
  each problem, and `eggdb mcp` refuses to start on one (exit 1, `column_not_found`); a list that
  stops matching later (a renamed column) shows fewer columns, or hides the whole table once its
  primary key or every listed column is gone, never more;
- a table listed with columns cannot be changed at all, even with `--allow-write` (`42501`,
  "may read only some of its columns"): a row written through the narrowed definition would lose
  the hidden values and skip the hidden indexes and checks. Its name is not one a confined writer
  may create either;
- the same table given twice with different columns is a usage error; the library keeps the
  first.

The grammar keeps every old spelling: a comma inside parentheses separates columns, not names,
and a name holding `(` or `)` cannot be given (as a name holding a comma could not). `names()`,
the banner, the audit's `server_started.tables` and the `add it` line (quoted, since `(` is
special in a shell) show the lists.

Rejected: enforcing column limits with D183's column `GRANT`s (needs a role in the user's file and
misses the catalogs and `SELECT *` expansion done by the owner); hiding the columns as "dropped"
in the definition and merging them back on write (needs the engine's row, index and check logic
restated at the key level for every write; listed as "Not yet").

**A table an unlisted one references.** D257 froze a listed table's rows when an unlisted table
had a foreign key to it. At the start of each write transaction the writer now reads, from the
unfiltered store, the unlisted table's foreign keys to the listed one and the listed columns they
point at (`KeyGuard`). A new row and a change that keeps those columns' values go through; deleting
a row, or a write that changes one of those columns, is refused whatever the foreign key's
action, since `CASCADE`, `SET NULL` and `SET DEFAULT` would write the hidden table and `NO ACTION`
and `RESTRICT` would have to read it (the filtered engine sees neither). A key change is a delete
of the old key, so it is refused too. The definition stays frozen. When the foreign keys cannot
be read or their columns not found, the rows stay frozen as before. The refusal names both tables
(`cannot delete a row of "parents" or change a column a foreign key points at: ...`), and
`OutsideLink::blocked_changes` now says what is refused as a verb phrase for the banner. The other
direction (a listed table with a foreign key to an unlisted one) still freezes the listed table:
its inserts would need the hidden table checked.

**Stored code.** D257 refused a new or changed column default, generated expression or `CHECK`
that calls a user-defined routine. A row-security policy is checked the same way when written
(`USING` and `WITH CHECK`), and a new expression of either kind that holds a subquery is refused
too, since the check does not look inside subqueries; a policy whose stored text cannot be read
back is refused. Index expressions and partial-index predicates do not exist yet (the parser
refuses them); indexes are column numbers inside the table definition, so when they come the
definition check covers them.

Decided by research: should a listed table whose *existing* defaults, checks, policies or
triggers call a user routine be refused for writes, or for reads where policies run? No. Every
read and write of the agent's session, including routine bodies, dynamic SQL and triggers, goes
through the same filtered store (`CallStore` wraps each one), `SECURITY DEFINER` does not switch
stores, plan caches hold parsed statements rather than resolved tables, foreign sources and jobs
are not enabled under `eggdb mcp`, and there is no file-writing function, so an existing routine
finds unlisted tables missing. The user wrote those definitions, and refusing them would break
common row-security setups (`USING (tenant_id = current_tenant())`) for no gain. The one residue
is a routine that catches the missing-table error and takes another path under the filter; it is
a known limit, not a refusal.

**Security review.** Threat cases covered, each by a test with its exact refusal or state:

- a left-out column read directly, with `SELECT *`, `t.*`, in `WHERE`, `ORDER BY`, `GROUP BY`, a
  function call, a CTE and an `IN` subquery, in the PostgreSQL, MySQL and SQLite dialects:
  `42703`, and no row value, index key, comment or index name of it is readable by any key;
- a listed view over a left-out column and a function whose body reads one: they fail (`42703`);
  an unlisted view over the table stays missing (`42P01`); a view listed with columns is hidden;
- `information_schema.columns`, `describe_table` and `sample_rows` show only the listed columns;
- a column list missing the primary key, naming an absent column, empty, on a view, or on a table
  not there yet: reported at start and the table hidden;
- every change to a table listed with columns (insert, update, delete, truncate, alter, comment,
  analyze, policy, drop, create under its name): `42501`, and the file unchanged;
- inserts, upserts and changes to other columns of a table an unlisted one references go through;
  deletes, key updates, `TRUNCATE` and `ALTER` are refused for `CASCADE`, `SET NULL` and
  `NO ACTION` foreign keys, and the referencing rows are unchanged;
- a table listed with columns whose hidden column holds a foreign key to a listed table: that
  key is dropped from the narrowed definition, so the parent is treated as referenced by an
  unlisted table (`ReferencedBy` link): its deletes, key updates and `TRUNCATE` are refused and
  the child rows unchanged (round-1 security review;
  `a_foreign_key_on_a_hidden_column_keeps_the_listed_parent_from_losing_rows`); column grants
  on a hidden column are hidden, and grants and policies of a table in a schema are attributed to
  that table, not to a table named like the schema;
- a new policy calling a user routine in `USING` or `WITH CHECK`, a policy with a subquery, and a
  default calling one: refused; a policy with built-in expressions and writes to a table whose
  existing policy calls a user routine work.

Not covered here: the `eggdb serve` sessions (D257's "Not yet"), and names a definition shows (a
listed table's default or policy text may name a hidden column).

**Tests.** `eggdb-sql` (`visible_tables_tests`, `visible_writes_tests`): the column reads, keys and
start report above, the referenced-table writes, the column-limited table's refusals and the
policy refusals. `eggdb-mcp` (`tests/tables.rs`): a column-limited server through every tool and
its audit, the delete refused with its message, and the policy and default refusals. The built
binary (`tests/mcp.rs`): column lists through `eggdb mcp` in three dialects with the banner, the
referenced table's insert and refused delete, and the start-up and usage refusals. `eggdb` argument
tests: the grammar and its usage errors.

**Not yet.** Writing a table listed with columns (the hidden values would have to be merged back
into each row, with their indexes and checks kept); a column list on a view; inserts into a listed
table that has a foreign key to an unlisted one; the same filter for `eggdb serve` sessions.
