## D1191 Routine grants stored, and `role_routine_grants` and `role_udt_grants` — Decided by the code-only session (2026-11-17, D355); roadmap M6b (D326, D344)

- **What users get.** `GRANT EXECUTE ON FUNCTION` (and `PROCEDURE`, `ROUTINE`) is stored like the other object grants of D1190, with `WITH GRANT OPTION` and `REVOKE`; the argument list after the name is read and not kept, so a grant names every overload of a routine, and an unqualified name means `public`. `information_schema.role_routine_grants` and `role_udt_grants` list the stored routine and type grants whose grantee is an enabled role of the current user (every one for a superuser session), and `routine_privileges` and `udt_privileges` list them after PostgreSQL's defaults. `table_privileges` and `role_table_grants` now say `YES` in `is_grantable` for a privilege granted `WITH GRANT OPTION` (D1189).
- **Scope.** Routine calls are not checked against these grants yet (every role executes every routine, as PostgreSQL's default lets `PUBLIC`), and `has_function_privilege` keeps that default. The two views are appended to the information schema's list, so the relations before them keep their OIDs.
- **Proof.** A unit test grants `EXECUTE` with the grant option and `USAGE` on a composite type to a group, reads both views as roles that do and do not hold them, and revokes by a qualified name.

**Status:** code written, unbuilt (code-only mode, D355).
