## D1076 TLS in the shared HTTP layer, and JMAP over HTTPS — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D56, D894)

- `eggdb_http::Limits` gains `tls: Option<&ServerConfig>` and `with_tls`.
  - With it, the HTTP server secures every accepted connection with EggDB's own TLS before reading its
    first request. The handshake runs on the connection's thread, waiting at most 10 seconds, so a slow
    client never holds up accepting others.
  - A failed handshake, a plain-HTTP client included, ends the connection without an answer.
- The connection code now reads and writes a `Socket` (`socket.rs`): plain TCP, or a TLS session shared by
  the reading and writing halves. They take turns on the connection's one thread, so the mutex between them
  is never contended. The raw TCP socket is kept for timeouts and for the half-close before lingering.
  Requests, keep-alive, `100 Continue`, paced writes, streamed and chunked responses and lingering behave as
  over plain TCP.
- JMAP is the first listener to use it: with `--tls-certificate`/`--tls-key` (or `--tls-self-signed`),
  `--jmap-listen` is HTTPS only, with the same certificate as the SQL, SMTP and IMAP listeners. That
  completes the roadmap's "TLS" for the mail item: STARTTLS for SMTP and IMAP (D1075), HTTPS for JMAP.
- The other HTTP listeners (REST, metrics, observability, Elasticsearch-compatible, DAV, …) keep their
  current behaviour. Moving each to HTTPS, and lifting their loopback-only rules once they have it, is now
  one `with_tls` call each, recorded for their own items.
- Tested: the HTTP layer answers an HTTPS request through EggDB's TLS client, and gives a plain request
  nothing.
- Learned from: RFC 9110, RFC 9112 and RFC 8446. No HTTP or TLS server source was read.

**Status:** code written, unbuilt (code-only mode, D355).
