## D801 PostgreSQL 18's OAUTHBEARER login — Decided by the code-only session (2026-11-12, D355); roadmap M6b, OAUTHBEARER

- The rule file (D185) gains the method `oauth`: `<user|all> oauth jwks=keys.json issuer=... audience=...
  discovery=https://login.example/.well-known/openid-configuration [scope=openid] [user_claim=sub] [leeway=60]`. It
  checks the same OpenID Connect tokens as `jwt`, but they arrive through SASL's `OAUTHBEARER` mechanism (RFC 7628)
  as PostgreSQL 18's libpq sends them, instead of as a clear-text password.
- The PostgreSQL listener offers only `OAUTHBEARER` to such a user. A client initial response with `auth=Bearer
  <token>` is verified with D185's JWT code (signature from the key set, issuer, audience, expiry with leeway) and must
  name the user logging in, who must be a stored role with `LOGIN`; then `AuthenticationOk` follows with no
  `SASLFinal`, as PostgreSQL does. An empty `auth=` (libpq's discovery request) is answered with `SASLContinue`
  carrying `{"status":"invalid_token","openid-configuration":<discovery>,"scope":<scope>}`; after the client's
  acknowledging message the login fails, and libpq runs its device flow and connects again with a token.
- Like the other external methods it needs TLS or the local socket, since a bearer token is a secret. Malformed
  GS2 headers, separators or `auth` values end the connection with 08P01. The REST API's bearer sign-in accepts
  `oauth` roles too.
