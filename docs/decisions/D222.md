## D222 Android through JNI in C over the C API, iOS through an XCFramework — Decided by the build loop (by judgement, 2026-10-31); refines D8, D16, D17 and D41

Part 4.M17-2 asks for EggDB embedded in mobile apps, with Kotlin and Swift wrappers over the C
API, correct under Android's Doze and iOS's background limits.

- **Android needs JNI.** The Java driver calls the C API through Java's foreign function API,
  which Android's runtime does not have. The Kotlin wrapper (`drivers/kotlin`) is a thin layer
  that, as D16 allows for every language's driver, calls a small JNI file in C. That C file calls
  the C API, so no protocol or storage logic sits in either, and the Rust side gains no
  hand-written JNI and no new `unsafe`. Text and SQL cross as UTF-8 byte arrays, because JNI's
  string functions use modified UTF-8, which mangles characters outside the Basic Multilingual
  Plane. A statement's results come back in one call, as one flat array of byte arrays (D17:
  batched crossings).
- **The same Kotlin and C run on any JVM**, so CI checks them on Linux without an emulator.
  The C API is also linted for the Android and iOS targets in the `cross` job.
- **iOS gets an XCFramework** (`scripts/apple/xcframework.sh`) of the static C API for devices,
  the simulator and macOS, with a `CEggDB` module map, so Xcode projects and the Swift driver
  use it directly. CI builds it on macOS.
- **Doze and suspension need no special code**: commits are durable when they return, and an
  interrupted transaction rolls back on the next open. The guide says so.

Left: emulator and simulator test runs, a Gradle module and an Android Archive, a Swift
package that pulls the XCFramework, Android's 32-bit ABIs in CI, the binding's prepared
statements and transactions as methods, and benchmarks against SQLite's Android and iOS
bindings (D17).
