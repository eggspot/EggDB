## D1262 Empty matches in MATCH_RECOGNIZE — Decided by the code-only session (2026-11-18, D355); roadmap M7 streaming SQL (D1067, D1217, D1221)

- **What users get.** A pattern that can match no rows (`A*`, `A?`, `{0,n}`) now yields its empty matches as SQL:2016 and Oracle do: `ONE ROW PER MATCH` and `ALL ROWS PER MATCH` (whose default is `SHOW EMPTY MATCHES`, now accepted when written) give one row for each, at the row where the match was tried, with `MATCH_NUMBER()` counting it, `CLASSIFIER()` NULL and the measures taken over no rows (`COUNT` 0, `FIRST` NULL). `OMIT EMPTY MATCHES` leaves them out; `WITH UNMATCHED ROWS` shows them as matches.
- **How.** `row_pattern_matches` takes a fourth argument, `'show empty matches'` or `'omit empty matches'`; with the first, a match that ends where it started is listed with `end` one before `start` and no classifiers, and the search goes on from the next row, as the standard's empty-match rule says. The rewrite joins an empty match to the row where it starts, and running measures end at the smaller of the row and the match's end, so an empty match's running set is empty too. The three-argument form, used before this, keeps leaving empty matches out.
- **Left.** Union variables in `DEFINE`.
- **Proof.** A unit test lists the empty matches of `A*` only when asked; the `MATCH_RECOGNIZE` test shows them with `ALL ROWS PER MATCH SHOW EMPTY MATCHES`, leaves them out with `OMIT EMPTY MATCHES` and counts them with `ONE ROW PER MATCH`.
