## D900 SQL Server's `SYSTEM_VERSIONING = ON` in `ALTER TABLE`, and history retention — Decided by the code-only session (2026-11-12, D355); roadmap M14, follow-up of D795

- A system-time period is now kept once declared, in `eggdb_temporal.declared_periods`: by `PERIOD FOR SYSTEM_TIME
  (start, end)` in a SQL Server or MariaDB `CREATE TABLE` (with or without `SYSTEM_VERSIONING = ON`), by SQL Server's
  `ALTER TABLE t ADD ..., PERIOD FOR SYSTEM_TIME (start, end)`, and whenever versioning is turned on. SQL Server
  keeps the period after `SYSTEM_VERSIONING = OFF`, and so does EggDB.
- `ALTER TABLE t SET (SYSTEM_VERSIONING = ON [(HISTORY_TABLE = s.h, DATA_CONSISTENCY_CHECK = ON|OFF,
  HISTORY_RETENTION_PERIOD = ...)])` turns versioning on over the kept period (`eggdb_temporal.enable_declared_versioning`);
  without one it fails with SQL Server's 13510. On a table already versioned it only changes the retention, as SQL
  Server uses the same statement for that.
- `HISTORY_RETENTION_PERIOD = INFINITE | n DAY[S] | WEEK[S] | MONTH[S] | YEAR[S]`, in `CREATE TABLE` or `ALTER TABLE`,
  is kept in `eggdb_temporal.history_retention`. A statement-level trigger on the history table removes the versions
  whose period ended longer ago than the retention after each insert into it, and setting the retention removes the
  ones already past it. SQL Server cleans up in a background task instead; the outcome a query sees is the same, and
  a table that is never written keeps its old versions until the next change. `INFINITE`, `OFF` or turning versioning
  off removes the rule and its trigger.
- The support tables and functions are created with `IF NOT EXISTS` / `OR REPLACE` when first needed, so databases
  where `eggdb_temporal` was installed before this change get them without an extension upgrade.
- Left: invisible (`HIDDEN`) period columns, which need hidden columns in the catalog (a file format change).
