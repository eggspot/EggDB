## D218 Cassandra CQL in our own eggdb-cql, with CQL tables as SQL tables — Decided by the build loop (by judgement, 2026-10-31); refines D2, D5 and D10

Part 4.M16-6 asks for Cassandra drivers (CQL native protocol v4/v5) and wide-column tables.

- **Wide-column is the relational table.** A CQL table is a partitioned, clustered table: a
  primary key of partition columns then clustering columns, rows sorted by the clustering
  columns within a partition. That is a SQL table whose primary key is those columns in that
  order, which EggDB's storage already keeps sorted by key. So a keyspace is a SQL schema and a
  CQL table is a SQL table, and the same rows answer CQL, SQL and every SQL protocol, with no
  second storage format (D2).
- **CQL is translated, not executed separately.** Statements are parsed by our own CQL parser
  and rewritten into the PostgreSQL dialect: `INSERT` and `UPDATE` become `INSERT ... ON
  CONFLICT ... DO UPDATE`, because both are upserts in CQL; counters become `COALESCE(c, 0) + n`;
  `INSERT ... IF NOT EXISTS` becomes `ON CONFLICT DO NOTHING RETURNING` and answers `[applied]`;
  a `SELECT` without `ORDER BY` is ordered by the partition and clustering keys, descending
  where `CLUSTERING ORDER` says so. Bound values are rendered as typed SQL literals.
- **What SQL cannot hold is kept in `eggdb_cql.tables`**: which key columns are the partition
  key, the descending clustering columns, and each column's CQL type (`varint`, `counter`,
  `timeuuid`, `tinyint` and `inet` are stored as `numeric`, `bigint`, `uuid`, `smallint` and
  `text`, and answered as their CQL types). Tables made with SQL are served too, with the first
  primary key column as the partition key.
- **Drivers connect as to a single-node Cassandra 3.11 cluster** in `datacenter1`: `system.local`
  with one token, an empty `system.peers`, `system.peers_v2` unconfigured (so drivers fall back,
  as with 3.11), and `system_schema` keyspaces, tables and columns built from the SQL catalog.
  Protocol v4 only; a driver offering v5 is told so and steps down.
- **Sessions run as the server's user** in its database, with the same roles and row security as
  the SQL listeners (D22).

Left: collections, tuples and user-defined types; TTL and `USING TIMESTAMP` (write times);
lightweight transactions beyond `IF NOT EXISTS`; paging state (every result is one page);
protocol v5 framing and compression; secondary indexes, materialized views and `ALTER TABLE`;
schema events; prepared statements shared between connections; TLS; and a benchmark against
ScyllaDB and Cassandra.
