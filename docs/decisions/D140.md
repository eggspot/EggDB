## D140 Expiring keys and atomic counters: deadlines as two records under the reserved prefix, by key and by deadline; time from the database's clock, never earlier than the last commit; commits sweep 32 expired keys; a read-only-compatible feature bit; counters as decimal text changed by the one writer; compare-and-set; the CLI, the shell and the UI as Claude Fable designed them — Decided by the build loop (by research, 2026-10-30); roadmap item 27, applies D2, D9, D15, D20, D35, D86, D87, D139

Item 27 lets a key, in the default key space or in a collection, expire at a deadline, and lets
applications change a value atomically: a counter that adds a step, and a compare-and-set that
replaces a value only when it is the one expected. Both come through the embedded API, the
command line, the shell and the terminal UI.

**Deadlines as records beside the key.** A value stays the bytes the application stored; the
deadline lives in two records under the reserved prefix of D139 (`0xff 'C' 'O' 'L' 0x00`), so the
default key space hides and refuses them like collections: `0x04` + stored key holds a version
byte and the deadline (microseconds since the Unix epoch, 8 bytes big-endian), and `0x05` +
deadline + stored key is an empty index entry sorted by deadline (format.md "Keys and trees").
The stored key is the key as the tree holds it, so a collection's key carries its collection's
prefix and dropping a collection removes its deadlines. *Why:* changing the value's bytes would
need a new value encoding for every existing value; the by-deadline index lets a sweep find
expired keys in order without scanning everything. *Cost:* a key with a time to live is 14 bytes
shorter than other keys (498 with 4 KiB pages, 488 in a collection).

**Time.** A transaction's time is the database's clock when it begins, never earlier than the
last commit's stamp (the hybrid clock of D20/D86): a wall clock set back after a commit cannot
bring an expired key back, and a read transaction keeps its time, so a key that expires while it
lives stays readable in it, as its snapshot does. A key is expired once that time reaches its
deadline. `Options::clock` takes any `Clock`; a `SimClock` makes time move only when a test moves
it (re-exported from `eggdb`).

**Reads hide, writes remove.** `get`, `get_with`, scans and the collection versions leave
expired keys out; `put`, `put_if_absent`, `delete`, `increment` and `compare_and_set` treat them
as absent and remove what is left of them. Every commit removes up to 32 expired keys from the
front of the index (a bounded sweep in the writer, never a helper thread: the database has no
thread of its own, and the sweep cannot outgrow the page cache), and `Database::remove_expired`
removes all of them in commits of 1,024. A scan skips an expired entry by looking its deadline up
and stepping on (`Cursor::step_back` re-lends the entry it kept, so a lent scan copies nothing).

**Nothing for files that never expire a key.** The first commit that gives a key a time to live
sets the read-only-compatible feature bit `EXPIRING_KEYS` (bit 0, format.md "Feature flags").
The database knows from the bit at open whether to look deadlines up at all, so a file without
it reads and writes exactly as before (D6). *Why read-only compatible:* a release without
expiring keys would show expired keys, a read it may still make, but could write a key without
removing its deadline, and the next release would then expire a key that was meant to stay; the
bit lets it open such a file read-only and never write it. The v0.2.0 sample files carry no bit
and open unchanged.

**Counters and compare-and-set.** A counter is a value that is a decimal integer written as text
(`42`, `-7`, no plus sign, spaces or leading zeros), from `i64::MIN` to `i64::MAX`, as Redis's
`INCRBY` keeps them, so `get` and every client read it as it is. `increment(key, by)` reads and
writes it in the one write transaction (D86), so increments from many threads never lose a count;
an absent key counts as 0, and a value that is not a counter or a sum out of range fails with the
new `ErrorKind::NotAnInteger`. `increment` keeps the key's time to live, as Redis does; `put` and
a `compare_and_set` that stores a value remove it, as Redis's `SET` does. `compare_and_set(key,
expected, new)` takes `None` for "absent" on either side.

**Command line, shell and UI** follow Claude Fable's design (D15; ux/cli.md section 21, ux/ui.md
"Expiring keys and counters"): `put --ttl <time>`, `ttl`, `expire`, `persist`, `incr`, `decr` and
`cas` (`--if-absent`, `--delete`), all with `-C`; one time grammar for input and output (`1500ms`,
`30s`, `5m`, `1h30m`, `7d`) kept in `eggdb-ui`, which the CLI shares; the same words in the shell;
in the UI the time left in the key list and the viewer, `t` with a confirm modal, and `+`/`-`.

**Decided by research while building** (recorded in the batch plan): the UI shows the time left
as of its last read instead of a live countdown, since it reads no clock of its own and its
golden screens must stay deterministic; exports carry live keys without their deadlines, as
Fable's design leaves `expires_at` in exports for later; the engine takes a time to live of zero
as "remove the key", while the CLI refuses it and points at `eggdb del`.
