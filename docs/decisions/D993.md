## D993 `eggdb follow mysql://` through the binary log — Decided by the code-only session (2026-11-13, D355); roadmap M10, following a live MySQL (D13, D162)

- `eggdb follow <file> mysql://user@host:port` copies a MySQL server's databases into the file and keeps it in step by
  reading its binary log as a replica does, like the other follows (D162, D263, D988).
- The binary log reader is EggDB's own (`eggdb_mysqlwire::binlog`), from MySQL's public replication documentation:
  `COM_BINLOG_DUMP` with checksums and heartbeats, event headers, format descriptions, rotations, `QUERY` and `XID`
  events, table maps and version 1 and 2 rows events. Column values decode for every type MySQL 5.6 and later write:
  integers (read unsigned where the column is), `FLOAT`, `DOUBLE`, `DECIMAL`'s packed form, `DATE`, `DATETIME2`,
  `TIMESTAMP2`, `TIME2`, `YEAR`, strings and blobs, `ENUM`, `SET`, `BIT` and binary `JSON`. Every length is checked.
- Preconditions: `log_bin` on, `binlog_format=ROW`, `binlog_row_image=FULL`, and a primary key on every followed table;
  each failure is named with the setting to change.
- No lock is taken: the position is noted before the copy, and changes are applied idempotently by primary key
  (`REPLACE` for written and updated rows, a `DELETE` first when an update changes the key, `DELETE` for removed rows),
  so changes made during the copy converge. Each source transaction is applied with the new position in one
  transaction, in the MySQL dialect, so zero dates and MySQL literals keep their meaning.
- A DDL statement on a followed database stops the follow with exit 3, naming it, as with SQL Server; the file holds
  every transaction before it.
- Left: TLS to the source and `caching_sha2_password`'s full authentication (the client's limits), GTID positions,
  applying DDL, and the pre-5.6 temporal column formats (refused with how to upgrade them).
