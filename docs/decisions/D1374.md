## D1374 Stored roles log in to the Elasticsearch-compatible listener — Decided by the code-only session (2026-11-25, D355); roadmap M6b "Redis ACLs, MongoDB roles, Elasticsearch roles and Cassandra roles mapped onto the one role model" (D22), the Elasticsearch part, following D1364

- **What users get.** `eggdb serve --es-listen` takes HTTP basic authentication as any stored role that may log in, with its SQL password: a superuser or a member of `pg_write_all_data` acts as the server's own user, and a member of `pg_read_all_data` reads every document and gets `403` for anything that writes, as an `--es-users` reader does. The server's user and `--es-users` readers are checked first, unchanged.
- **How.** `eggdb_esrest::RoleLogins` is the API's hook (`Api::with_role_logins`); a read-only role is a new principal that reads without the `--es-users` document filter (its reach is "everything, read only", not "documents that name me") and goes through the same refusal of writing requests. `eggdb serve` implements the hook with D1364's `RoleLogins` over the served file, which now checks the password once for both listeners.
- **Left.** MongoDB (SCRAM over `saslStart`) and Cassandra (SASL `PLAIN`) logins.
- **Proof.** An API test with two known roles: the writer indexes a document, the read-only role counts it and gets `403` for a write, and a wrong password gets `401`.
