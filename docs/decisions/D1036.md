## D1036 Raft's durable state in the file, snapshots and log compaction — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D20, D211)

- `eggdb_consensus::Node` stays free of I/O (D211). It records what changed in its durable state, and
  `Node::take_changes` hands it over as `Changes`: the term and vote when either changed, the first rewritten log index
  with the entries from there to the end, an installed snapshot and a compacted one. The caller stores them in one
  durable write before it sends the messages the node returned, which is the order the paper's correctness argument
  needs (votes and appended entries are on disk before anyone hears about them). `Node::recover` rebuilds a node from
  what storage read back and refuses a log with a gap (`BrokenLog`).
- Snapshots follow the paper's section 7: `Node::compact(through, data)` replaces the applied log up to `through` with
  a snapshot; a leader whose follower needs an entry it no longer has sends `InstallSnapshot` with the whole snapshot;
  the follower keeps its log after the snapshot when the entry at the snapshot's index has the snapshot's term and
  drops it otherwise, and reports the snapshot as `installed`, which the state machine restores before applying later
  entries. A snapshot travels as one message for now; streaming it in chunks belongs to the transport (next item).
- In the file, the state lives under the engine's reserved prefix (`raft` keys: `state`, `snapshot`, `log` by index),
  not in the 32 header bytes D20 reserved: a key-value commit writes the hard state and the entries in one durable
  commit with one sync, which two separate places (header and tree) could not. The header bytes stay reserved, and
  `docs/format.md` says so. `Database::consensus_state` and `Database::save_consensus` read and write it; for a database
  the snapshot's data is empty, because the database file is the state.
- The simulation now stores every node's changes in `MemoryStorage` after each step and tick, crashes rebuild nodes
  from it with `Node::recover`, and logs are compacted every 97 rounds, so partitions, drops and crashes run with
  snapshots being installed; a new test has a follower that missed twenty entries catch up from a snapshot.
