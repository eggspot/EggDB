## D231 Audit records are hash-chained, and `eggdb audit --verify` checks the chain — Decided by the build loop (by judgement, 2026-10-31); refines D11 and D26

Track 4.X-3 asks for a tamper-evident audit log of logins, privilege and schema changes and
chosen data access, retention policies and crypto-shredding erasure.

- **Tamper evidence first, on the audit log that exists.** Every record `AuditLog::append` writes
  now starts with `"prev"`, the SHA-256 of the line before it (all zeros for the first), computed
  under the file's exclusive lock, so concurrent writers still produce one chain. `eggdb audit
  <file> --verify` walks the file. A record whose link does not match the line before it, or a
  record without a link once the chain has begun, marks where the file was changed, and the
  command fails there. Records from before this release, at the start, are counted as
  unchained and accepted.
- **What a chain proves and what it does not**: it finds any edit, deletion or insertion inside
  the file. Someone who can rewrite the whole file can rewrite the whole chain, and truncating
  the newest records leaves a valid prefix. Anchoring the newest digest outside the file
  (printing it, sending it to a log server, or signing it with the server's key) closes those
  gaps and is next.
- **One log for everything** comes after: logins, role and privilege changes and DDL from every
  protocol, written through the same chained `AuditLog` into one audit file per database, with
  the MCP records as one kind among them.

Left: anchoring digests, server events (logins, privileges, schema changes, chosen tables'
reads) in the audit, retention policies, and crypto-shredding: per-subject keys whose
deletion makes their data unreadable in the file and in every backup (D23).
