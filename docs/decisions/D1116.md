## D1116 Completion backends as the automatic choice — Decided by the code-only session (2026-11-13, D355); roadmap M1 (IOCP as Windows' automatic choice, io_uring and IOCP sockets as the default network backends, D67, D69, D165)

- **What the benchmark shows.** `benchmarks/baseline.txt` has `linux net.round_trip` at 0.981: an io_uring round
  trip takes 98% of an epoll one on CI's Linux runner, so the completion backend is no slower where it was measured.
- **Network queues.** With no backend asked for, `OsNetwork::net_queue` now runs io_uring on Linux and an I/O
  completion port on Windows, and falls back to the readiness backend (epoll, kqueue, `poll(2)`) or the portable one
  when the kernel refuses (a seccomp profile that blocks `io_uring_setup`, a kernel before 5.11, a Windows without
  the port). Android keeps epoll: its kernels often build io_uring but its seccomp policy refuses it to apps.
- **File queues.** Windows' automatic choice is the completion port (`IoBackend::Iocp`); the file is reopened per
  port, so two queues on one file still work. A failed port falls back to the thread pool, or inline without
  threads, as before.
- **The switch is one constant per layer** (`AUTOMATIC_PREFERS_COMPLETION` in `os_net.rs`,
  `AUTOMATIC_PREFERS_COMPLETION_PORTS` in `io.rs`), so the build-and-fix pass sets it back to `false` for a system
  whose first measured line comes out above 1.0, with that line recorded here.
- **The benchmark compares like with like.** `net.round_trip` now pits the completion backend against the readiness
  backend asked for by name (`completion_backend_to_readiness_backend`, renamed from `..._to_automatic_backend`, the
  value kept), since the automatic choice is now the completion backend itself.
- The network contract tests run every readiness backend by name, so epoll and kqueue stay covered.
