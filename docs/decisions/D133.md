## D133 SQL Server's metadata for tools: `sys` views and `INFORMATION_SCHEMA` built per statement from the catalog snapshot with object ids from hashes of names, the catalog procedures answered in Rust by `EXEC` and RPC, table variables only for `INSERT ... EXEC`, engine types shown as the most common SQL Server type — Decided by the build loop (by research, 2026-10-29); roadmap item 41, applies D1, D9, D10, D12, D122, D123, D124, D129, D131, D132

Item 41 lets metadata tools browse an EggDB database over TDS: mssql-jdbc's `DatabaseMetaData`,
SqlClient's `GetSchema`, and the queries tools write against `sys` and `INFORMATION_SCHEMA`.
What each driver sends was read from their MIT-licensed sources (mssql-jdbc 12.8.1's
`SQLServerDatabaseMetaData`, SqlClient's `SqlMetaData.xml`) and the procedures' result sets from
Microsoft Learn (D1: no SQL Server software was read or run).

**The catalog is D129's snapshot shown SQL Server's way.** In the Transact-SQL dialect a `FROM`
item `sys.X` or `INFORMATION_SCHEMA.X` is a catalog relation (a variant of `CatalogRelation`,
module `crates/eggdb-sql/src/sqlserver_catalog/`), built once per statement from the same
snapshot that answers `pg_catalog` and PostgreSQL's `information_schema`. Only the qualified
names reach them, as in SQL Server; they are read-only. Seventeen `sys` views have rows
(`objects`, `tables`, `views`, `columns`, `types`, `schemas`, `indexes`, `index_columns`,
`foreign_keys`, `foreign_key_columns`, `key_constraints`, `default_constraints`,
`check_constraints`, `identity_columns`, `sequences`, `databases`, `sql_modules`) and four are
empty until procedures and triggers exist (`procedures`, `parameters`, `triggers`,
`extended_properties`); `INFORMATION_SCHEMA` has fourteen views with SQL Server's columns (not
PostgreSQL's) and values (`dbo`, `nvarchar`, `BASE TABLE`, no `NOT NULL` check constraints).
Column names are in lower case, since the dialect folds every name (D122); the procedures'
result columns keep SQL Server's spelling, which the drivers read by name.

**Object ids are hashes, like OIDs.** Every table, view, sequence and constraint (`PK`, `UQ`,
`F`, `C`, and `D` for a column default) gets an `object_id` from FNV-1a over its kind, owner and
name, folded into 2^24 to 2^31 - 1, collisions taking the next free number in a fixed order
(D129's assignment with its own range), so `OBJECT_ID` is stable across statements and
restarts and changes on a rename. `dbo` (EggDB's `public`) is schema 1, `guest`,
`INFORMATION_SCHEMA` and `sys` are 2 to 4, other schemas count from 5 in name order. A table with
a primary key shows it as its clustered index 1, otherwise a heap 0; secondary indexes are 2 and
up; unique indexes are unique constraints, as in D129. Defaults are named
`df__<table>__<column>`, since the table definition does not keep a default constraint's name.
The database is `database_id` 5, the only row of `sys.databases`.

**Types.** D123 keeps several SQL Server types as one engine type, so the catalog shows each
engine type as the SQL Server type most columns of it were declared with: `varchar(n)` and
`character(n)` as `nvarchar(n)` and `nchar(n)` (over 4,000 as `nvarchar(max)`), `text` as
`nvarchar(max)`, `bytea` as `varbinary(max)`, `timestamp(3)` as `datetime`, other `timestamp(p)`
as `datetime2(p)`, `timestamptz(p)` as `datetimeoffset(p)`, `numeric(p,s)` as `decimal(p,s)`,
`smallint` as `smallint` (a `tinyint` column too), `boolean` as `bit`; anything else as
`nvarchar(max)`, as TDS sends it. `sp_columns` and `sp_datatype_info` use the ODBC codes (3.x for
the `_100` procedures and `@ODBCVer = 3`, 2.x otherwise) and report `max` types with length 0.

**The catalog procedures are Rust, not SQL.** `sp_tables`, `sp_columns`, `sp_columns_100`,
`sp_pkeys`, `sp_fkeys`, `sp_statistics(_100)`, `sp_special_columns(_100)`,
`sp_datatype_info(_100)`, `sp_stored_procedures`, `sp_sproc_columns(_100)`, `sp_help`,
`sp_helpindex`, `sp_databases` and the undocumented `sp_columns_managed`, `sp_indexes_managed`
and `sp_indexcolumns_managed` SqlClient's `GetSchema` calls build their result sets from the
snapshot directly, with SQL Server's `LIKE` patterns (`%`, `_`, `[...]`, compared without regard
to case) where the procedure takes them. Writing them as SQL over the `sys` views would need
procedures (3.15) and would cost a full query per call. They run from `EXEC` and `EXECUTE` (by
position or `@name = value`, `DEFAULT`, Msg 119, 201, 8144, 8145), from a procedure name as the
first statement of a batch (mssql-jdbc's `sp_datatype_info_100 @ODBCVer=3`), and from an RPC
request by name: the TDS server writes the call as an `EXEC` with its parameters bound as typed
values (D132), so one path runs them. Another procedure is Msg 2812; `sp_executesql` and the
other RPC procedures inside a batch are 40517. `sp_help` returns its several result sets, each
reported as its own step of the batch.

**Table variables, only as far as the drivers need them.** mssql-jdbc's `getColumns` and
`getImportedKeys` send `DECLARE @t TABLE (...)`, `INSERT INTO @t EXEC sp_...` and a `SELECT`
over `@t` joined with `sys.foreign_keys` (with `COLLATE database_default`). A batch now keeps
its table variables in memory, cleared when the batch starts and ends and on a connection
reset; `FROM @t [alias]` reads them as an intermediate table of the statement (D128's generated
tables). Only `INSERT ... EXEC` fills one (Msg 213 when the columns do not match); other
`INSERT`s into a table variable, `UPDATE`, `DELETE`, constraints on one and scalar `DECLARE`
wait for item 47's batch interpreter, which takes this storage over. `COLLATE` in a
Transact-SQL expression is accepted and has no effect (comparisons stay binary, D122). `PRECISION`
is no longer a reserved word in the dialect, as the drivers use it as a column name.

**Metadata functions** read the snapshot, which a statement naming one (`OBJECT_ID`,
`OBJECTPROPERTY`, ...) loads up front, also for `IF` conditions. `SERVERPROPERTY` answers
`ProductVersion` `16.0.1000.0`, `EngineEdition` 3 (so mssql-jdbc and SqlClient take their
on-premises paths), `Edition` `EggDB (64-bit)` (not a Microsoft edition name), the collation and
the flags; an unknown property is NULL, as in SQL Server. `SYSTEM_USER` is the login,
`CURRENT_USER`, `USER` and `USER_NAME()` are `dbo` (the one login owns the database).

**Left for later.** Three-part names (`master.sys.databases`, `[db].sys.schemas`, so
`GetSchema("Databases")` and `getSchemas(catalog, ...)`), `schema.table.column` references
(mssql-jdbc's `getSchemas()`), `EXEC sp_executesql` inside a batch, SSMS's own queries (3.21),
procedures and their parameters (3.15), `sys.all_objects`, `sys.system_objects`,
`sys.partitions`, `sys.dm_*`, row counts (`CARDINALITY`, `sp_spaceused`), and showing the exact
declared SQL Server type (`tinyint`, `varchar`, `money`, `smalldatetime`), which needs the type
in the table definition (D35).

**Size (D6).** The relations' column lists, the type table and the procedures add to the
binary as the PostgreSQL catalog did; a statement that names no `sys` or `INFORMATION_SCHEMA`
view, metadata function or catalog procedure loads none of it.
