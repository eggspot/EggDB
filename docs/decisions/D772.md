## D772 WebAuthn passkeys for app sign-in — Decided by the code-only session (2026-11-12, D355); roadmap M6a, WebAuthn and passkeys for app sign-in (D54)

- `webauthn_registration(attestation_object, client_data_json, challenge, origin, rp_id, user_verification)` checks a
  `navigator.credentials.create` response (WebAuthn Level 2, sections 7.1): the client data's type, challenge
  (compared in constant time) and origin; the authenticator data's relying-party hash, user-present flag and, when
  asked, user-verified flag; the attested credential's id and COSE key, which must be ES256 on P-256 and a point on
  the curve. It returns the credential id, the key as an uncompressed SEC 1 point, the counter, the AAGUID and the
  attestation format. Attestation statements are not checked (the `none` conveyance passkeys use by default), so an
  authenticator's make is taken on trust.
- `webauthn_assertion(public_key, authenticator_data, client_data_json, signature, challenge, origin, rp_id,
  stored_count, user_verification)` checks a `navigator.credentials.get` response (section 7.2): the same client
  data and flags, then the DER ECDSA signature over the authenticator data and the SHA-256 of the client data, and
  returns the new signature counter, refusing (28000) one that did not grow when either counter is non-zero, as a
  sign of a cloned authenticator.
- A CBOR reader of our own (definite lengths, integers, byte and text strings, arrays, maps and simple values; depth
  16, 1024 items, 64 KiB inputs) reads the attestation object and the COSE key.
- `eggdb_app_auth` (D771) keeps passkeys and single-use challenges (5 minutes), with the relying-party id, origin and
  whether user verification is needed as settings; `register_passkey` and `sign_in_with_passkey` turn the checks into
  stored credentials and sessions (`amr` `hwk`).
- RS256 and EdDSA credential keys, attestation verification (`packed`, `tpm`, `android-key`, `apple`), and several
  allowed origins are left.
