## D947 The engine's hot threads asked onto performance cores — Decided by the code-only session (2026-11-13, D355); roadmap M1, follow-up of D356's `ThreadOptions::hot`

- **Which threads.** The engine core runs on its callers' threads; the threads it starts itself are the file I/O
  workers (`eggdb-io-<n>`), and the protocol servers start one session thread per connection, which runs the SQL.
  Both are latency-critical, so both are marked; the accept loops and background jobs are not.
- **I/O workers** are started with `ThreadOptions::hot()`.
- **Session threads** are started by `std::thread::Builder::spawn_scoped`, which `ThreadOptions` cannot do, so they call
  the new `eggdb_platform::prefer_performance_cores_for_current_thread()` first. It only hints and never pins: pinning
  every session to the performance cores would leave the efficiency cores idle under a busy server. On Apple's
  systems it asks for the user-interactive quality of service; on Windows it turns power throttling off for the
  thread (`SetThreadInformation(ThreadPowerThrottling)` with the execution-speed bit controlled and cleared, Windows'
  high quality of service), which the scheduler keeps on performance cores. Linux and the BSDs have no unprivileged
  hint (raising `uclamp_min` needs `CAP_SYS_NICE`), so there it does nothing.
- `ThreadOptions::hot` uses the same Windows hint now, and pins to the performance cores only where no hint was taken.

**Status:** code written, unbuilt (code-only mode, D355).
