## D616 Kafka log compaction — Decided by the code-only session (2026-11-12, D355); roadmap M16, D33, D213, D494

Compacted topics (`cleanup.policy=compact`) are Kafka's changelog tables. Kafka Streams state
stores, Kafka Connect's offset and config topics, and every "latest value per key" topic depend on
old values being dropped while each key's newest record is kept. D494 wrote retention and left
compaction.

- `CreateTopics` reads `cleanup.policy`: `delete` (the default), `compact`, or both. Anything else
  is refused with `INVALID_CONFIG`.
- The policy is kept as a flag in a 21st byte of the topic record. Older records without that
  byte read as `delete`. Time and size retention still apply when they are set, so
  `compact,delete` does both.
- `compaction::compact` does what Kafka's log cleaner does, over every batch but the newest (the
  "active segment"):
  - each record whose key has a later record anywhere in the partition is dropped;
  - a tombstone (null value) is dropped once its batch is older than one day, Kafka's default
    `delete.retention.ms`;
  - records keep their offsets: a batch is rewritten with its kept records, count, length and
    CRC-32C, and its header (base offset, last offset delta, timestamps, producer fields) is
    unchanged;
  - a batch with nothing kept is removed;
  - records without a key are kept;
  - compressed and control batches are left alone, since compaction would have to recompress
    them.
- Compaction runs inside the append's write transaction each time the partition's next offset
  passes a multiple of 1,000, instead of on a background thread.
- A test builds three batches and checks the result:
  - the first batch held only overwritten keys and is removed;
  - the second keeps its latest record and drops its old tombstone, with a valid CRC;
  - the newest batch is untouched.

Not done: compressed batches, `min.cleanable.dirty.ratio` and the other cleaner settings,
