## D1041 A distributed planner for sharded tables, as a rewrite over `eggdb_foreign` — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D212)

- `SHARD TABLE <table> BY <column> ON '<source>', ...` records in `eggdb_internal.sharded_tables` that a table's rows
  live on shard servers, one foreign source (D229) per shard; the coordinator declares the table with its columns
  too, which gives the planner the column types. `UNSHARD TABLE` forgets it, and `SHOW SHARD FOR <table> KEY '<value>'`
  says where a row with that key goes, using the hash routing of the shard maps (D212), so loaders place rows the way
  the planner routes reads.
- **The plan.** A single-table `SELECT` on a sharded table becomes one query every chosen shard runs and a final query
  over their answers:
  - without aggregates, each shard gets the filter, the select list (aliased `c0`, `c1`, ...), the ordering and
    `LIMIT limit + offset`; the final query orders, limits and offsets the union;
  - with aggregates or `GROUP BY` (on columns), each shard groups by the same columns and computes partials
    (`count` and `sum` as they are, `min` and `max` of their argument, `avg` as a sum and a count); the final query
    groups by the keys and combines them (`sum` of counts, `sum` of sums, `min` of mins, `max` of maxes, sum over
    count for averages), then applies `HAVING`, `ORDER BY`, `LIMIT` and `OFFSET`, with every aggregate and group
    column in them rewritten to the combined form;
  - a filter whose top-level conjunction fixes the shard column to a literal (and has no `OR`) reads only that
    key's shard.
- **Why a rewrite, not a new executor.** The coordinator already reads remote sources with `eggdb_foreign`, row by row
  as JSON, under its permission rules. The planner turns the query into ordinary SQL: a `UNION ALL` of
  `eggdb_foreign(source, shard query)` per shard, each column cast back to its type, under the final query. The local
  engine runs it, so every expression, type and dialect detail of the final step is the engine's own. The rewrite
  works on the statement's tokens, so the pushed clauses are exactly the user's text.
- Refused with `0A000`, naming what the planner runs: joins, subqueries reading the table, `DISTINCT`, aggregate
  `DISTINCT`, window functions, set operations and `GROUP BY` on expressions. Writes to a sharded table are not
  distributed yet; they go to the shard `SHOW SHARD FOR` names.
- Learned from the scatter-gather and partial aggregation descriptions in the distributed SQL literature (Citus,
  Vitess and Greenplum documentation); no code was read.
