## D1312 Routine EXECUTE checked in statements — Decided by the code-only session (2026-11-25, D355); roadmap M8 roles (D183, D1191)

- **What users get.** A role that is not a superuser may call a function or a procedure only with `EXECUTE` on it, held by the role, a role it belongs to or `PUBLIC`; otherwise `42501 permission denied for function <name>`. As in PostgreSQL, `PUBLIC` holds `EXECUTE` on every routine until `REVOKE EXECUTE ... FROM PUBLIC` takes it away, so nothing changes for databases that never revoke it, and `GRANT EXECUTE ... TO PUBLIC` gives it back. `has_function_privilege`, `information_schema.routine_privileges` and `role_routine_grants` follow the same rule. Superuser sessions are never checked.
- **How.** Routine grants are stored as before (D1191), keyed by schema and name, so one grant covers a name's overloads. A revoke from `PUBLIC` on a routine keeps a record holding nothing instead of deleting it, which tells the default apart from a revoked one. The check runs where a function call or `CALL` has chosen its routine.
- **Left.** Per-overload grants (by argument types), and the routine's `SECURITY DEFINER` owner being checked instead of the caller inside the routine.
- **Proof.** A roles test calls a function and a procedure through `PUBLIC`'s default, refuses both after the revokes, answers `has_function_privilege`, runs the function again through a grant to a role the user belongs to, and the procedure through a grant back to `PUBLIC`; superuser calls never stop.
