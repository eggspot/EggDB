## D1279 ODBC block fetches — Decided by the code-only session (2026-11-18, D355); roadmap M6 ODBC driver (D1236, D1278)

- **What users get.** Applications that fetch many rows a call (Power BI, Excel, Tableau and most report tools set `SQL_ATTR_ROW_ARRAY_SIZE` above 1) get them: `SQLFetch` (and `SQLFetchScroll` forward) fills that many rows of every bound column, column-wise (each column's buffer an array of `buffer_length`-sized elements and its indicator an array) or row-wise (`SQL_ATTR_ROW_BIND_TYPE` the size of one row's structure), moved by `SQL_ATTR_ROW_BIND_OFFSET_PTR` when set, and reports the rows fetched (`SQL_ATTR_ROWS_FETCHED_PTR`) and each row's status (`SQL_ATTR_ROW_STATUS_PTR`: success, success with information, error, or no row past the end). Before, `SQLSetStmtAttr` accepted these attributes and ignored them, so such applications read one row and garbage.
- **How.** The statement keeps the block attributes; a fetch fills each row as before at its element's address. With more than one row, a row that fails conversion is marked `SQL_ROW_ERROR` and the call returns `SQL_SUCCESS_WITH_INFO`, as ODBC asks; with one row the call fails as before. `SQLGetStmtAttr` answers the array size and bind type set.
- **Left.** Scrollable cursors, `SQLSetPos`, and parameter arrays (`SQL_ATTR_PARAMSET_SIZE`).
- **Proof.** The ODBC test fetches three rows two at a time into a bound array and reads the counts and statuses, then the end.
