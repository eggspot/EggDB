## D235 The generated API starts as REST in PostgREST's conventions, as SQL in the caller's session — Decided by the build loop (by judgement, 2026-10-31); refines D37

Track 4.X-7 asks for REST, GraphQL, gRPC and OData APIs generated from the schema, realtime
subscriptions and end-user authentication.

- **REST first, in conventions people already use.** `eggdb-api` serves every table of a schema
  with PostgREST's documented URL grammar (filters as `column=op.value`, `select`, `order`,
  `limit`, `offset`, `Prefer` headers, `Content-Range` counts), so existing clients, examples
  and front-end libraries work against `eggdb serve --rest-listen` unchanged.
- **Every request is a SQL statement in a session of the signed-in user**, built from checked
  identifiers (letters, digits, `_` and `$`, quoted) and quoted literals, never from raw text.
  Roles, grants and row security (D22, D234) therefore apply to the API exactly as to SQL
  clients, and the API has no permissions of its own to get wrong. Values arrive as untyped
  literals that SQL converts to each column's type, so the API needs no type mapping.
- **Sign-in is the server's user over HTTP Basic** in this slice. End-user authentication, with
  JSON Web Tokens whose role claim picks the SQL role (the JWT verification of
  `eggdb_auth::jwt` is already there), is the next step, with realtime subscriptions over
  change capture (D210).

Left: JWT sign-in with roles per request, embedded resources (foreign-key joins in `select`),
`or=` and `and=` groups, `POST /rpc/<function>`, upserts (`Prefer: resolution=...`), an OpenAPI
document, GraphQL, gRPC (with our own HTTP/2, D34) and OData, realtime subscriptions, and TLS.
