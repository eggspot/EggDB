## D301 Run-time parameters follow transactions and routines as in PostgreSQL: `SET LOCAL` and `set_config(..., true)` end with the transaction, a routine's `SET` clause applies while it runs, `SET` works inside routines, and `refcursor[]` exists — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 17 and 18, finishes D280's "Not yet", extends D104 and D158

D104 kept PostgreSQL's run-time parameters per session and refused `SET LOCAL` and
`set_config(name, value, true)`; only `search_path` came back at a `ROLLBACK`. D158 parsed a
routine's `SET` clause but ignored it while the routine ran, and refused `SET` inside routines.
D280 left `refcursor[]` out. PostgreSQL's `SET` page, "Configuration Settings Functions",
`CREATE FUNCTION` ("SET configuration_parameter") and PL/pgSQL "Transaction Management" say how
they behave; EggDB now follows them.

- **Transactions.** The session keeps, for its transaction, the parameter values it had before
  the first change (`TransactionSettings`, taken lazily, so a transaction that changes nothing
  pays nothing) and, for each parameter set with `SET LOCAL`, the value it takes back at
  `COMMIT`. `ROLLBACK` (and `COMMIT` of a failed block, or a `COMMIT` whose deferred checks or
  store commit fail, review round 1) restores every value; the settings end only once the data's
  outcome is known, in `COMMIT` and when an implicit transaction ends. `COMMIT` restores
  the `SET LOCAL` ones, so a `SET` after a `SET LOCAL` of the same parameter, or before it, is
  what stays, as PostgreSQL documents. A savepoint saves both, and `ROLLBACK TO SAVEPOINT`
  restores them. This replaces the `search_path`-only restore. It applies in PostgreSQL's
  dialect only: SQL Server's `SET` options, MySQL's variables and SQLite's pragmas keep their own
  rules. The transaction is a `BEGIN` block, or an implicit transaction of more than one
  statement (as PostgreSQL's implicit transaction blocks); outside one, `SET LOCAL` warns `SET
  LOCAL can only be used in transaction blocks` and changes nothing, and `set_config(..., true)`
  lasts only for its statement.
- **Routines.** Changes made while a statement runs routines go into a per-thread journal
  (`routine_settings`): each entry is a parameter, its value and whether it lasts for the
  session, the transaction or the routine. A routine's `SET` clause adds routine entries when it
  starts and the routine runs with those values (its `RoutineSettings` is `Changed`); at its exit
  they end, and so do the `SET LOCAL` entries made inside it for the parameters the clause
  names, while a plain `SET` inside it stays (PostgreSQL: "an ordinary SET command ... overrides
  the SET clause"). `SET`, `SET LOCAL`, `RESET name` and `set_config` in PL/pgSQL and `sql`
  bodies add entries. Each running routine recomputes its settings from the statement's
  settings and the active entries when the journal's version changed, at its next step, so a
  caller sees what a routine it called set. An exception handler that catches an error ends the
  entries made in its block; a procedure's `COMMIT` ends the transaction entries and marks the
  session ones committed, and its `ROLLBACK` ends the session entries not yet committed. When
  the statement ends, the session applies the surviving session and transaction entries (only
  the committed session ones when it failed). While a routine's settings differ from the
  statement's, its statements run with its own `search_path` and time zone. Statements whose
  settings never change pay one thread-local read per step.
- **The journal stays linear (review round 1).** A routine's own change updates its settings
  and marks them in step with the journal, so it does not recompute them; a caller recomputes
  once when it resumes. Entries are coalesced within each level (the innermost open `SET` clause
  or exception block): a session entry replaces the uncommitted and ended entries of the same
  parameter at that level, a transaction entry right after another of the same parameter takes
  its value, a block that ends without an error merges its entries into the enclosing level, a
  caught error drops them, a routine's exit drops its clause entries, and a procedure's
  `COMMIT` keeps one committed entry per parameter. So a loop of `n` `SET`s costs `O(n)` and the
  journal holds a few entries per parameter and level, whatever the iteration count.
- **`SET name TO DEFAULT` is `RESET` (review round 1).** In every scope, at the top level and in
  routines' entries, a parameter set to its default takes the value the client sent when it
  connected (`Session::remember_connection_settings`), as `RESET` does, and the built-in default
  when none was sent.
- **`SET ... FROM CURRENT`.** The value the parameter has at `CREATE` is written into the stored
  definition as `SET name TO 'value'`, so the routine keeps it after a restart, as PostgreSQL's
  `proconfig` does.
- **`refcursor[]`.** An array element type (`ArrayElement::RefCursor`, element code 29, array
  OID 2201 `_refcursor`) for values, variables, parameters and results. Like `refcursor`
  (D280), it is not a column type: a table column declared `refcursor[]` is stored as `text[]`,
  so the file format does not change; the element code is refused in a stored column type, as
  the other catalog element types are.
