## D1084 A QEMU Cortex-M run in CI — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D223, D1082, D1083)

- New excluded crate `crates/eggdb-cortex-m`, a `#![no_std]`, `#![no_main]` program for `thumbv7m-none-eabi`
  (Cortex-M3). It is never published or shipped, and has no third-party crates.
  - **Start-up of our own:**
    - `link.x` lays out QEMU's `mps2-an385` board: 4 MiB of flash at 0, 4 MiB of RAM at `0x2000_0000`,
      `.data` loaded from flash, `.bss`, and the stack at the top of RAM.
    - `startup.rs` holds the vector table, a reset handler that copies `.data` and clears `.bss` (each
      `unsafe` step documented), a 2 MiB bump allocator for `alloc`, and the panic handler.
    - `build.rs` passes the linker script.
  - **Semihosting** (`semihosting.rs`): `BKPT 0xAB` with `SYS_WRITE0` writes to the host console, and
    `SYS_EXIT` ends the run, so QEMU exits 0 on success and 1 on failure.
  - **The run:**
    - A 1 MiB flash array in RAM, behind a `Flash` driver that only clears bits, holds the wear-levelled
      region (D1083).
    - `FlashFile` under `PageFile::create_in`, and a 64 KiB fixed-frame `PageCache::with_frame_buffer`
      (D1082).
    - A `Store` with a counting clock (the board has no wall clock; the hybrid clock needs only order).
    - It writes 300 keys in one transaction, commits, reads every key back in a read transaction, and runs
      `Store::check` over the whole file.
- CI job `cortex-m` (in `check`'s `needs`):
  - It installs the target and `qemu-system-arm`, runs clippy for the crate, then `cargo run --release` in
    the crate's directory. Its `.cargo/config.toml` sets the target and the QEMU runner, and the run is
    bounded to 5 minutes.
- Left: size and memory budgets per microcontroller profile (the next roadmap line), a run on real
  hardware, and a Cortex-M4/M7 build with its FPU.
- Learned from: ARM's Cortex-M3 and semihosting documentation, and QEMU's `mps2-an385` board description.
  No runtime crate's source was read.
