## D627 AMQP 1.0 released and modified outcomes — Decided by the code-only session (2026-11-12, D355); roadmap M16, D217, D352, D540

AMQP 1.0 receivers settle deliveries with one of four outcomes, and clients rely on the
difference: Azure Service Bus SDKs and Qpid JMS `abandon` with `modified{delivery-failed}`, and
"not for me, give it to someone else" with `modified{undeliverable-here}`. EggDB treated every
`released` and `modified` the same way: returned to the queue with the delivery counted.

What each outcome now does, following the specification's section 3.4 (`Outcome::of`):

| Outcome | Effect |
|---|---|
| `accepted` | the message is removed |
| `rejected` | the message goes to the queue's dead letters (D540) |
| `modified` with `undeliverable-here` | the message goes to the queue's dead letters |
| `modified` with `delivery-failed` | the message is returned with its delivery counted, so redelivery flags and dead-lettering by count see it |
| `released`, and `modified` without either flag | the message is returned as if never sent, its receive count unchanged |

- `undeliverable-here` asks that the message not come back to this receiver. EggDB has no
  per-link routing, so the dead letters are where it cannot come back to the same consumer.
- `modified`'s `message-annotations` are not merged into the message.
- A unit test maps each state, with and without the flags, to its outcome.
