## D107 The SQLite dialect: affinity onto the engine's types, `INTEGER PRIMARY KEY` as the row id, SQLite's errors with extended result codes, `eggdb::sql` in the embedded API — Decided by the build loop (2026-10-27); roadmap item 24, applies D1, D5, D9, D10, D16, D19, D20

**The dialect.** `Dialect::Sqlite` (`--dialect sqlite`, also `sqlite3`) reads SQLite's SQL as
sqlite.org documents it (datatype3, the `lang_*` pages, `lang_corefunc`, the PRAGMA and
result-code pages), never SQLite's source (D1). It is a third branch of the same lexer, parser
and session as PostgreSQL's (D98) and MySQL's (D106), on the same tables: `"..."`,
`` `...` `` and `[...]` identifiers folded to lower case like unquoted names (SQLite's names are
case-insensitive), `'...'` strings without escapes, the parameters `?`, `?NNN`, `:name`,
`@name` and `$name` numbered in the lexer as SQLite numbers them (a repeated name keeps its
number, `?` takes one more than the largest so far, 1 to 32766), and a parameter without a value
is NULL, as SQLite binds it.

**Types (decided by judgement).** The engine has one type per column, so the dialect maps the
affinity of the declared type name (datatype3.html's rules, in order) onto the engine's types:
`INTEGER` affinity to `bigint`, `TEXT` to `text` (declared lengths are not enforced, as in
SQLite), `REAL` to `double precision`, no type at all to `text`, and `NUMERIC` affinity to
`double precision`, except `BOOLEAN` (`bigint`, since SQLite stores 1 and 0) and names
containing `DATE` or `TIME` (`text`, the form SQLite's date functions read and write). A
declared `BLOB` is refused until the blob type exists, rather than storing bytes as text. This
is the honest minimum: values keep the column's type where SQLite would let a column hold any
storage class; the differences are listed in docs/sql.md and marked in the suite. `TRUE` and
`FALSE` are the integers 1 and 0, comparisons print as 1 and 0, any number is a condition
(`WHERE active`: the parser wraps a condition that is not already boolean in `sqlite_truth`),
`LIKE` ignores ASCII case, `GLOB` becomes `LIKE` with a converted constant pattern, and `/` and
`%` by zero give NULL. Reals print with up to 15 significant digits and a decimal point, as
SQLite's shell prints them.

**Row ids.** A column declared exactly `INTEGER PRIMARY KEY` (on the column, or as the table's
one-column key, and not `DESC` or `WITHOUT ROWID`) uses the auto-numbering of D106, stored in
table definition version 2: no file-format change. `AUTOINCREMENT` is accepted only there.
`last_insert_rowid()` reads a new `QueryResult::last_insert_rowid`: the row-id column's value
(given or assigned) or the hidden row id of a table without a key; `changes()` and
`total_changes()` follow the statements' row counts. All three, and `PRAGMA user_version`,
`foreign_keys`, `journal_mode` and `synchronous`, are session state (the PRAGMAs are not kept
in the file: a known difference). Unknown PRAGMAs do nothing, as SQLite documents.

**Internal functions and limits.** SQLite's own functions are a separate expression kind
(`SqliteFunction`, named by a `&'static str` only the SQLite parser builds), so no SQL text in
any dialect can call them by name. `replace`, `hex`, `quote` and `printf` check the length of
their result before building it against SQLite's default `SQLITE_MAX_LENGTH` (1,000,000,000
bytes) and refuse longer ones with `string or blob too big` (`SQLITE_TOOBIG`), so nested calls
cannot ask for more memory than that (D9). Names starting with `sqlite_` are reserved for
tables, as in SQLite.

**The schema table.** `sqlite_schema` and `sqlite_master` are answered by running the query on
a scratch table built from the catalog (type, name, tbl_name, rootpage, sql), so `WHERE`,
`ORDER BY` and aggregates work on it; it cannot be joined with stored tables yet. Its `sql` is
a `CREATE TABLE` regenerated from the catalog, since the catalog does not keep the statement's
text.

**Transactions.** As in SQLite, a failing statement inside `BEGIN` leaves the transaction open
when it had not written yet (the engine has no statement savepoints, so one that had written
rolls the transaction back, as for MySQL), `INSERT OR ROLLBACK` rolls it back, `BEGIN` inside a
transaction and `COMMIT` or `ROLLBACK` outside one are errors, and `CREATE TABLE` stays inside
the transaction.

**Errors.** Engine errors are translated at the session's edge into SQLite's wording (`near
"FORM": syntax error`, `no such table: t`, `UNIQUE constraint failed: t.id`, `NOT NULL
constraint failed: t.c`, ...) and carry SQLite's extended result code
(`SqlError::with_sqlite_code`, `SqlError::vendor() == Some(Dialect::Sqlite)`; 1555
`SQLITE_CONSTRAINT_PRIMARYKEY`, 1299 `SQLITE_CONSTRAINT_NOTNULL`, 20 `SQLITE_MISMATCH`, 1
`SQLITE_ERROR` for the rest); the SQLSTATE stays the engine's, so tools that read SQLSTATEs keep
working. `SqlError`'s `Display` is `Error: <message>`, as SQLite's shell prints it, and `eggdb
sql` and `eggdb shell` add a `Result code: NAME (n)` line (decided by judgement: the shell's
own line has no code, the code is what programs match on). `sqlite_result_code_name` names the
codes. `sqlite_version()` reports 3.46.0, the release whose documentation the dialect follows.

**The embedded API.** `eggdb::sql` re-exports the SQL types and adds `Store`, the `Database`
as the key-value store SQL runs on (moved from the CLI, which now uses it too):
`db.sql_store().session(Dialect::Sqlite)` gives a `Session` in any dialect. It is the minimal
API consistent with what exists (`Session::execute` and friends); a typed row API and
statements prepared once and run many times come with the drivers (D17).

**The suite.** `crates/eggdb-sql/correctness/sqlite.test` (155 cases) runs in the same runner
as the other dialects' (D105); its `error` lines name the extended result code after the
SQLSTATE. Three cases are marked as differing. The parser is fuzzed with SQLite fragments as
D9 requires.

**Not in this item.** Reading and writing SQLite's own file format (D13's "SQLite files") is a
later item; until then EggDB keeps its own file and runs SQLite's SQL on it.
