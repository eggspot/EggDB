## D1349 EXPLAIN shows the key a comparison with an InitPlan uses — Decided by the code-only session (2026-11-25, D355); roadmap M6c "An index used for a comparison with an InitPlan's $k" (D327)

- **What users get.** `EXPLAIN SELECT ... WHERE id = (SELECT max(id) FROM ...)` shows `Index Scan using t_pkey` (or the index's scan in MySQL's, SQLite's, Oracle's and SQL Server's plan forms), the access the run uses, instead of a full scan. D327 left the difference: a run evaluates an uncorrelated scalar subquery before it plans, so it reads by key, while `EXPLAIN`, which runs no subquery, planned with nothing to compare.
- **How.** While `EXPLAIN` plans (a scoped flag), an uncorrelated scalar subquery compared with an indexed column counts as a value of that column's type, so the planner's key choice sees the comparison exactly as it will at run time; the value itself is never shown or used beyond the choice. Correlated subqueries, which a run cannot evaluate before planning, keep the scan both in the run and in the plan.
- **Proof.** An `EXPLAIN` test shows the primary key read for a comparison with an `InitPlan`, the `InitPlan` still listed, and the query itself returns the right row.
