## D1186 A real directory and libpq's device flow in CI — Decided by the code-only session (2026-11-15, D355); roadmap M6b, follows D802 and D801

- **LDAP.** The new `ldap` CI job starts an OpenLDAP directory (the `bitnami/openldap` image, a test service only) with users alice and bob, serves a database over TLS with a rule file that signs alice in by a simple bind to `cn=alice,ou=users,...` (`prefix=`/`suffix=`) and bob by D802's search-and-bind (`basedn=`, `search_attribute=cn`, an admin `bind_dn=`), and checks with psql that each logs in with the directory's password and is refused with a wrong one (`scripts/ldap/check.sh`). StartTLS and LDAPS against a real directory are left to a later job that also gives the directory a certificate.
- **OAUTHBEARER.** The new `oauth` CI job installs psql 18 and `libpq-oauth` from the PostgreSQL apt repository and runs `scripts/oauth/check.sh`: a small OpenID issuer of the check's own (`issuer.py`, standard library only, its RS256 tokens signed by `openssl` with a key made for the run, the key set written by `jwks.py`) answers discovery, the device authorization endpoint and the token endpoint, granting the device code at once. EggDB serves an `oauth` rule for dana naming that issuer. psql connects with `oauth_issuer`, so libpq first asks EggDB where to sign in (D801's discovery reply), runs the real device flow against the issuer, and logs in with the token; the check also sees the device code libpq printed. `PGOAUTHDEBUG=UNSAFE` lets libpq talk to the issuer over plain HTTP on 127.0.0.1, which it otherwise refuses.
- Both jobs are in `check`'s `needs`, so a change that breaks either login fails the PR.
