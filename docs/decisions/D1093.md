## D1093 iOS Simulator runs, and a Swift package that downloads each release's XCFramework — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D222, D16, D353)

- **Tests where the app runs.** `scripts/apple/test-simulator.sh` builds the XCFramework as `drivers/swift/CEggDB.xcframework` (inside the package, since SwiftPM wants a binary target's path relative to it) and runs the Swift package's XCTest suite twice: `swift test` on the Mac and `xcodebuild test` on the first available iPhone simulator. CI's `apple-mobile` job runs it, so the Swift driver, the static C API and the module map are exercised on iOS on every PR. Until now the job only built the framework.
- **Publishing.** The release workflow gains an `xcframework` job on macOS that zips `CEggDB.xcframework` (the bundle is named after the binary target, which SwiftPM requires) as `eggdb-vX.Y.Z-apple.xcframework.zip`. Its artifact joins the release assets, `SHA256SUMS`, the attestation and the sizes table through the existing `eggdb-*` pattern.
- **Where the manifest lives.** A remote binary target needs its URL and checksum in `Package.swift`, but the checksum exists only after the tagged commit is built, so a manifest on `main` (and therefore in the tag) would always name the previous release. The `swift-package` job therefore writes the manifest after publishing, with `scripts/apple/swift-package.sh`, into the `swift-package` branch: one commit per release on top of the last, never force-pushed, holding `Package.swift`, the Swift sources and a README. Apps depend on `branch: "swift-package"` or pin a revision. A second repository or extra tags were rejected: a repository is a new account-level resource for the owner, and a second tag scheme would sit beside the `vX.Y.Z` tags `tag-from-trailer.sh` manages. Only the newest version moves the branch.
- **Left.** Device (not simulator) runs, which need signing identities, an owner matter.
