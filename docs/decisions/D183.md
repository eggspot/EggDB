## D183 Roles, users and table privileges stored in the database, checked by the name resolver — Decided by the build loop (by judgement, 2026-10-31); refines D22 and D161; security-critical (D35)

Part 4.M6a-2 asks for roles, users and `GRANT`/`REVOKE`, with each protocol authenticating
against stored verifiers.

- **Roles are catalog records** (key space `0x11`), with `LOGIN`, `SUPERUSER`, the roles they
  belong to, and the password only as a SCRAM-SHA-256 verifier in PostgreSQL's documented
  `pg_authid.rolpassword` form (`SCRAM-SHA-256$4096:<salt>$<StoredKey>:<ServerKey>`, a 16-byte
  random salt from the process's secure random source). A password given already in that form
  is stored as it is, as PostgreSQL does. Passwords outside ASCII are refused until SASLprep
  lands.
- **Table privileges are catalog records** (key space `0x12`, one per table and grantee) holding
  `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` and `TRIGGER`; `PUBLIC` is a
  grantee. Roles inherit what the roles they belong to hold, to 32 levels; a membership cycle is
  refused with `0LP01`.
- **Checked where names are resolved.** Every table a statement reads needs `SELECT`, and the
  table an `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE` or `COPY ... FROM` targets needs that
  statement's privilege. A view's body is checked as the view, not as the caller. A failure is
  `42501 permission denied for table t`.
- **Who is checked.** Embedded sessions and the server's own user (`eggdb serve --user`) are
  superusers and are never checked, so nothing changes for databases without roles. A stored role
  that logs in through PostgreSQL's protocol is checked unless it is `SUPERUSER`. Until object
  ownership lands, only superusers create, change or drop objects and manage roles; a checked
  role gets `42501 permission denied for schema public`.
- **Syntax**: PostgreSQL's `CREATE ROLE`/`CREATE USER` (`LOGIN`, `SUPERUSER`, `PASSWORD`, `IN
  ROLE`; the other options are accepted), `ALTER ROLE`, `DROP ROLE` (refused while the role holds
  privileges), `GRANT`/`REVOKE` on tables and of roles; MySQL's `CREATE USER 'u'@'h' IDENTIFIED BY`,
  Oracle's `CREATE USER u IDENTIFIED BY p` and SQL Server's `CREATE LOGIN` and `CREATE USER` map
  to the same records. `pg_roles` lists stored roles.

Left: MySQL and TDS logins for stored roles (their verifiers differ from SCRAM's), column,
schema, sequence and routine privileges, object owners, `WITH GRANT OPTION` (accepted and
ignored), `SET ROLE` to a granted role, `has_table_privilege`, `relacl`, and `information_schema`'s
privilege views.
