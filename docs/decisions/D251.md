## D251 Resumable batch copies and verified differences in the `eggdb_migration` extension — Decided by the build loop (by judgement, 2026-10-31); refines D13 and D58

Track 4.X-23 asks for a fleet control plane (inventory, canary upgrades, placement by hardware),
chargeback and showback on D44's metering, tenant lifecycle APIs, databases per user at millions
of tenants, MPP analytics with workload queues, and resumable petabyte-scale migrations with
verified differences. This slice does the migration primitives a single database needs.

- **Resumable without state.** `copy_batch` copies the next rows in key order after the largest
  key the target already holds, so the target itself is the checkpoint: an interrupted job
  resumes from any session with nothing to repair. `eggdb_migration.jobs` only records progress
  for people and dashboards.
- **Verified, row by row.** `compare` reports keys missing on either side and rows whose
  columns differ (compared as `to_jsonb` of the whole row), so "migrated" means the comparison
  is empty, not that the copy finished. It also catches rows the source gained behind the copy,
  which the key-order copy does not take.
- **Inside one database for now.** Source and target are tables EggDB can reach in one session,
  such as a table loaded from a dump (D13) or read through `eggdb_foreign` (D229). Petabyte
  scale needs the distributed SQL of M15 to split the key range across nodes; the same two
  functions then run per range.

Left: hash-based range comparison (Merkle summaries, so equal ranges need not be read twice),
parallel ranges across nodes, the fleet control plane, chargeback and showback, tenant lifecycle
APIs, per-user databases at scale, and MPP workload queues.
