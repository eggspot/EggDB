## D792 Floating point, tables and the start function in EggDB's WebAssembly interpreter — Decided by the code-only session (2026-11-12, D355); roadmap M5, WebAssembly functions

- `f32` and `f64` value types are accepted everywhere a value type appears (parameters, results, locals, globals,
  block types) and kept on the operand stack as their IEEE 754 bits, like the integers; `Value` gains `F32` and
  `F64` and so loses `Eq`.
- Every WebAssembly 1.0 float instruction runs (`crates/eggdb-wasm-vm/src/float.rs`): constants, loads and stores,
  comparisons, `abs`/`neg`/`copysign` on the sign bit alone (as the specification asks, NaN payloads included),
  `ceil`, `floor`, `trunc`, `nearest` (ties to even), `sqrt`, the four operations, `min`/`max` with NaN
  propagation and -0 below +0, conversions, `demote`/`promote` and the four reinterpretations. Trapping float-to-int
  conversions trap with the new `InvalidConversion` for NaN and `IntegerOverflow` out of range; the saturating ones
  (`0xfc` 0 to 7, emitted by default by current LLVM) clamp and turn NaN into 0, which is what Rust's `as` does.
- `memory.copy` and `memory.fill` (`0xfc` 10 and 11, also emitted by default) run with bounds checks and one fuel
  unit per 64 bytes besides the instruction's own; `memory.init`/`data.drop` stay unsupported with passive segments.
- One function table (`funcref`, at most 1,000,000 elements) filled by active element segments, and `call_indirect`
  with the specification's three traps (`UndefinedElement`, `UninitializedElement`, `IndirectCallTypeMismatch`, the
  last comparing whole function types). A start function of type `[] -> []` runs when the instance is created, under
  the same limits as a call.
- Imports still refuse the module: host functions come with `CREATE FUNCTION ... LANGUAGE wasm` and its permissions.
- Left: imports, multi-value results and blocks, and running the official spec test suite in CI.
