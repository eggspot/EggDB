## D1176 OData `$batch` and options inside `$expand` — Decided by the code-only session (2026-11-15, D355); roadmap M6a, follows D877 and D910

- **`$expand` options.** Each expanded navigation property takes OData's options in parentheses, separated by `;`: `$select`, `$filter`, `$orderby`, `$top`, `$skip`, `$count` and a nested `$expand`, as in `authors?$expand=books($filter=pages gt 100;$orderby=title desc;$top=5;$count=true;$expand=reviews)`. `$filter` and `$orderby` go into the related rows' query (the same filter grammar as the entity set's); `$top` and `$skip` page each parent's related collection; `$count=true` adds `<name>@odata.count` before it. Without `$orderby`, related rows come in key order, so pages are stable. Nesting stops at 8 levels; any other option (`$levels`, `$search`, ...) is refused with 400, as a service that does not support it must.
- **`$batch`.** `POST /odata/$batch` takes both forms the standard defines:
  - `multipart/mixed` (OData 4.0): each part an `application/http` request; a nested `multipart/mixed` part is a change set. The answer is `multipart/mixed` with one `application/http` part per request, a change set answered as a nested multipart, or, when it fails, by the one failing response, as the standard says.
  - JSON (OData 4.01): `{"requests": [{"id", "method", "url", "headers", "body", "atomicityGroup"}]}`, answered as `{"responses": [...]}`; every request of a failed atomicity group gets the failing status and error.
- Reads in a batch run one by one through the same handlers as single requests. The writes of a change set or an atomicity group run in one session between `BEGIN` and `COMMIT` (`Endpoint::atomically`), so all of them happen or none does: an SQL error, a `404` for a missing key or a malformed part rolls the set back. Inside a set, a URL may name an entity inserted by an earlier request through its `Content-ID` (`$1`, `$1/...`), from that insert's `Location`.
- The write handlers were split into a statement builder (`insert_statement`, `update_statement`, `delete_statement`) and a response builder (`inserted`, `changed`) so single requests and sets share them. A change set holds only inserts, updates and deletes; a batch inside a batch is refused; a batch holds at most 1000 requests.
- Not yet: `dependsOn` ordering beyond the order given, `Prefer: continue-on-error` (a failed read never stops the batch anyway), and asynchronous batches.
