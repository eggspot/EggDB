## D1297 MySQL's JSON functions — Decided by the code-only session (2026-11-18, D355); roadmap M4 MySQL compatibility (D10, D1291)

- **What users get.** In MySQL's dialect: `JSON_EXTRACT(doc, path[, path ...])` (one value as JSON, or an array of every match when several paths or a wildcard are given; NULL when nothing matches), `JSON_UNQUOTE`, `JSON_LENGTH(doc[, path])`, `JSON_KEYS(doc[, path])`, `JSON_CONTAINS(target, candidate[, path])`, `JSON_VALID` and `JSON_TYPE` (MySQL's names: `OBJECT`, `ARRAY`, `STRING`, `INTEGER`, `DOUBLE`, `BOOLEAN`, `NULL`), with MySQL's path language: `$`, `.key`, `."quoted key"`, `[n]` (`[0]` also reaching a non-array value itself, as MySQL's auto-wrapping does), `.*` and `[*]`. Only SQLite's dialect had JSON functions under these names before, so MySQL applications storing JSON columns could not read them.
- **How.** A module answering in MySQL's dialect only, beside D1291's, over EggDB's own JSON parser; values are written in the normalized form (`{"a": 1, "b": [1, 2]}`), which is MySQL's output form; containment is the same rule as PostgreSQL's `@>`, which MySQL's `JSON_CONTAINS` follows. Invalid documents fail with MySQL's "Invalid JSON text in argument n" and bad paths with "Invalid JSON path expression".
- **Operators.** `doc->'$.path'` and `doc->>'$.path'` work in MySQL's dialect as `JSON_EXTRACT` and `JSON_UNQUOTE(JSON_EXTRACT(...))`: the MySQL lexer now reads `->>`, the MySQL parser reads both arrows, and a selector starting with `$` takes MySQL's meaning (PostgreSQL's operators keep theirs).
- **Editing.** `JSON_SET`, `JSON_INSERT`, `JSON_REPLACE`, `JSON_REMOVE`, `JSON_MERGE_PATCH` and `JSON_QUOTE` reuse SQLite's JSON editing (the same path syntax), their results normalized as MySQL stores JSON: keys sorted by length then bytes, a repeated key's last value kept (documents are read that way too).
- **Aggregates.** `JSON_ARRAYAGG(v)` and `JSON_OBJECTAGG(k, v)` are PostgreSQL's `jsonb_agg` and `jsonb_object_agg` under MySQL's names, whose output is MySQL's form.
- **Search.** `JSON_SEARCH(doc, 'one' | 'all', pattern[, escape])` gives the path of the first string value matching the pattern as `LIKE` does, or every such path as an array, NULL when none.
- **Paths at any depth.** `$**.key` and `$**[n]` find the leg at any depth below, as MySQL's `**` does.
- **Left.** `JSON_SEARCH`'s path arguments, and `JSON_TABLE` in MySQL's dialect.
- **Proof.** A case in `correctness/mysql.test` extracts, unquotes through `->>`, measures, lists keys, tests containment and uses D1291's `LOCATE` and `SUBSTRING_INDEX`; a unit test follows member, quoted-key, element and wildcard paths, refuses paths without `$` and with a bad index, unquotes a string with an escape and leaves plain text alone, and names a fractional number's type.
