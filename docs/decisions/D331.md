## D331 Elasticsearch-compatible `_mget`, `_msearch`, `_update_by_query` and `_delete_by_query`, with update scripts in a small Painless subset, under the memory budget — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M8, extends D196, applies D9 and D307

D196's REST API left multi-get, multi-search and the by-query APIs out, so clients that batch reads
(`mget` helpers, dashboards sending `_msearch`) or change documents in bulk by query failed. Built
from the Elasticsearch and OpenSearch REST references (Multi get, Multi search, Update by query,
Delete by query, Update) only, in `crates/eggdb-esrest` (`src/api/multi.rs`,
`src/api/by_query.rs`, `src/script.rs`, `src/source_filter.rs`).

- **`_mget`** at `GET`/`POST /_mget` and `/<index>/_mget`. `docs` entries name `_index` (or take
  the URL's index), `_id` and an optional `_source` (`false`, a pattern, an array of patterns, or
  an object with `includes`/`excludes`, also `include`/`exclude`); `routing` and `stored_fields`
  are accepted and ignored (one shard, no stored fields). The `ids` short form needs the URL's
  index. The URL's `_source`, `_source_includes` and `_source_excludes` set the default filter.
  All documents are read in one read transaction, so they come from one snapshot, in request
  order; a missing document is `found: false`, a missing or invalid index an `error` object in
  that entry, and the request still answers `200`. A request with nothing to get, or entries
  without index or id, is `400 action_request_validation_exception` listing each problem as
  Elasticsearch numbers them (`1: index is missing for doc 0;`).
- **Source filtering.** Patterns match full dotted paths, `*` matches any run of characters
  (dots included); an object or array is kept when its own path is included or when something
  under it is; excludes win over includes; arrays of objects are filtered element by element.
- **`_msearch`** at `GET`/`POST /_msearch` and `/<index>/_msearch`. The body is NDJSON pairs of a
  header line and a search body line (`\r\n` accepted, trailing blank lines ignored, an empty
  header line or `{}` meaning the URL's index or every index). The header's `index` is a string
  (comma-separated) or an array; `_all` and `*` mean every index, and a name with `*` (such as
  `logs-*`, which Kibana and Grafana send) is a pattern matching the existing indices, none
  matched being an empty result; `ignore_unavailable: true`
  skips missing indices (the same flag now works on `_search?ignore_unavailable=true`). Each pair
  runs through the same search as `_search` and answers with its own `status`: a missing index
  is `404 index_not_found_exception`, an unknown query `400 parsing_exception`, an invalid name
  `400 invalid_index_name_exception`, while the others still answer. The response is
  `{"took": ms, "responses": [...]}`. A header that is not JSON or not an object, a body line
  that is not JSON, a header without its body line or an empty body fail the whole request with
  `400`, as Elasticsearch fails while parsing.
- **`_update_by_query` and `_delete_by_query`** at `POST /<index>/_..._by_query`. The body takes
  `query` (any query `_search` takes) or the URL's `q=`, `max_docs` (body or URL, at least 1),
  `conflicts` (`abort`, the default, or `proceed`, body or URL), `script` (update only) and
  `slice` (`{"id": i, "max": m}`, manual slicing: a request changes only the documents whose id's
  FNV-1a hash modulo `m` is `i`, so the `m` requests of one slicing change every matching
  document exactly once; `m` must be more than 1 and `i` from 0 to `m - 1`, otherwise `400
  illegal_argument_exception` as Elasticsearch words it); other members are `400 parse_exception: request does not
  support [x]`. `refresh`, `wait_for_completion`, `requests_per_second` and `slices` in the URL
  are accepted: writes are visible at once and the request always completes before it answers.
  How it runs, as Elasticsearch documents it: one read transaction takes a snapshot of the
  matching documents' ids and versions; the changes then run in batches of `scroll_size`
  documents (URL, default 1000, at most 10 000), each batch one write transaction. A document
  whose version changed, or that was deleted, since the snapshot is a version conflict: with
  `conflicts=proceed` it is counted in `version_conflicts` and skipped; with `abort` the batch
  it was found in commits its other documents, then the request stops and answers `409` with a
  `version_conflict_engine_exception` per document in `failures`. `max_docs` counts documents
  changed (updated, deleted or left by `noop`), so with `proceed` conflicts do not use it up.
  The snapshot keeps a fingerprint (FNV-1a) of each document's source next to its version, so a
  document deleted and indexed again (its version restarts at 1) is a conflict too, unless it is
  byte for byte the document the query read. `total` counts every matched document the request
  reached, conflicts included, capped at `max_docs`, as Elasticsearch's does. A batch also closes
  early once it has written 16 MiB of documents, so one write transaction stages at most that
  much plus one document (review round 2).
  Without a script, `_update_by_query` writes each document back with its version raised, as
  Elasticsearch re-indexes it. The response carries `took`, `timed_out`, `total`, `updated`
  (update only), `deleted`, `batches`, `version_conflicts`, `noops`, `retries`,
  `throttled_millis`, `requests_per_second` (`-1.0`), `throttled_until_millis` and `failures`.
- **Update scripts** (`script.rs`), shared by `_update_by_query`, `POST /<index>/_update/<id>`
  and `_bulk`'s `update` action. A script is a string or an object with `source` (or `inline`),
  `lang` (only `painless`) and `params`; stored scripts (`id`) are refused. The subset covers
  what the references' update examples use: `ctx._source.a.b = expr`, `+=`, `-=`, `*=`, `/=`,
  `%=`, `ctx._source.n++` and `--` (prefix or postfix), `ctx._source['name']`,
  `ctx._source.remove('f')`, `ctx._source.list.add(expr)`, `ctx.op = 'noop' | 'none' | 'delete'
  | 'index'`, and expressions of numbers, strings, `true`, `false`, `null`, `params.x` or
  `params['x']`, `ctx._source` paths, `ctx._id`, `ctx._index`, `ctx._version`, `+ - * / %` with
  precedence, unary minus and parentheses. Numbers follow Java's `long` and `double`: integers
  stay integers and wrap, integer division truncates, `/ by zero` is an error, a string on
  either side of `+` concatenates. A script that does not compile is `400 script_exception`
  (`compile error: ...`) before anything runs; one that fails on a document (a missing field
  incremented, a path through a missing object, a non-number in arithmetic, a non-finite
  result) rolls back its batch and answers `400` with a `script_exception` failure naming the
  document, earlier batches staying committed. Nothing in the subset loops or recurses beyond 64
  levels of nested parentheses and call arguments together (`a.f(a.f(...))` counts each call as a
  level, and a call on anything but `ctx` or `params` is refused before its arguments are read),
  so a script cannot hang or exhaust the stack. A script has at most 1,000 operators, calls,
  call arguments and statements together, a string it builds at most `eggdb-http`'s body limit
  (1 MiB), and after every statement the document must still fit in that limit and nest at most
  128 levels (under the 256 the JSON reader takes), so `s += s` repeated or a document added into
  itself fails with `script_exception` instead of exhausting memory or the stack. The document's
  size is measured once, then kept up to date from what each statement replaces, adds or
  removes, so a statement costs the size of the values it touches, not a walk of the whole
  document (review round 2). Number
  literals follow Painless: an integer is decimal, or octal with a leading `0` (`010` is 8), and
  must fit a `long`; a literal with `.` or an exponent is a `double` (`1.` is `1.0`, `.5` is
  `0.5`); the stored text is always valid JSON. `_update` with both `script` and `doc` is
  `400 action_request_validation_exception` ("can't provide both script and doc"), as
  Elasticsearch validates it.
- **Memory (D307).** Request and response bodies stay under `eggdb-http`'s budget. On top of
  that, `Api::with_memory_budget` (which `eggdb serve` passes the server's one budget) holds what
  these APIs gather beyond 64 KiB: the documents an `_mget` returns, the answers an `_msearch`
  builds, and a by-query snapshot's ids (each counted as its length plus 56 bytes). A request
  past the budget answers `429 circuit_breaking_exception`, as the HTTP layer does. An
  `_msearch` holds at most 1,000 searches (`400 illegal_argument_exception` past that), so one
  request cannot queue an unbounded number of index scans.

Decided by research:
- *Scripts or `doc`?* Elasticsearch's `_update_by_query` takes only `script`; EggDB had no
  scripts, and a `doc` member there would be an EggDB-only extension clients never send. A small
  Painless subset covers the documented examples (`ctx._source.count++`, `+= params.count`,
  `add`, `remove`, `ctx.op`), so it was built, and also serves `_update` and bulk `update`.
- *One transaction or batches?* Elasticsearch documents by-query APIs as a snapshot followed by
  batches, with version conflicts and committed earlier batches; clients and `conflicts=proceed`
  depend on those counters. Batches keep each write transaction bounded too, so the snapshot plus
  `scroll_size` batches was chosen over one transaction for the whole index.
- *A script failure.* Elasticsearch stops at a failed batch and reports it in `failures`; EggDB
  rolls that batch back as one transaction, so a failure never leaves half a batch written.
- *Status of a failed by-query request.* The highest status among `failures` (`409` for
  conflicts, `400` for scripts), as Elasticsearch's by-query response reports.

Left: `wait_for_completion=false` tasks (`_tasks`), `_rethrottle` and parallel `slices` (the URL's
automatic slicing; manual `slice` in the body works); by-query APIs, `_search` and `_count` over
several indices or index patterns in the URL (patterns work in `_msearch` headers); `_msearch/template` and
`max_concurrent_searches` as a limit; `q=` searching nested fields (it searches each document's
top-level fields, as `_search` does); Painless beyond the update subset (conditions, loops,
comparisons, method calls other than `add` and `remove`, `ctx._now`, list indexing) and stored
scripts; `upsert`, `scripted_upsert` and `detect_noop` on `_update`; `_source` filtering on
`_search` and `GET _doc`; and an OpenSearch benchmark of these APIs (D196's benchmark item).
From review round 2: a per-index monotonic `_seq_no` (or tombstone versions) instead of the
version plus source fingerprint for conflicts, so a re-created identical document is a conflict
as in Elasticsearch; a budget of scanned documents per request for `_msearch` and `_search`
(each of the 1,000 searches still scans its indices whole) and a CPU limit across all documents
of one by-query request (each script stays bounded by its own 1,000 operations); and a fuzz
target for the script parser.
