## D1348 Dynamic data masking: the design — Decided by the code-only session (2026-11-25, D355); roadmap M6a "Dynamic data masking: SQL Server's MASKED WITH and Oracle's redaction, after its decision" (D22, D285)

D285 left dynamic data masking for a decision of its own. This is it; the code follows in its own batch, with the security review D35 asks of authorization work.

- **What it is for.** SQL Server's `MASKED WITH (FUNCTION = '...')` and Oracle's `DBMS_REDACT` hide column values from users who may query a table but not see its sensitive columns in full: support staff see `aXXX@XXXX.com` and `XXX-XX-1234`. Both vendors document it as a way to limit exposure in results, not a security boundary: a user who may filter on a column can still learn its values by guessing (`WHERE salary > 100000`). EggDB keeps that model and says so in its docs; row and column security (D22, D285) remain the boundary.
- **Where masks live.** In a catalog space of their own, `COLUMN_MASK_SPACE` (`0x24`), keyed by table id and column name, holding the mask function's text, not in the table definition, so no table format changes and a release that does not know masks simply shows real values to everyone (masking only ever removes information). Renaming or dropping a column renames or drops its mask; dropping the table drops them all.
- **Mask functions.** SQL Server's four: `default()` (`xxxx` for strings, at most their length; `0` for numbers; `1900-01-01` for dates and times; `0x00` for binary), `email()` (first letter, `XXX@XXXX.com`), `random(low, high)` for numbers, `partial(prefix, "padding", suffix)`; and `datetime("Y"|"M"|"D"|"h"|"m"|"s")` from SQL Server 2022. Oracle's redaction types map onto them: `DBMS_REDACT.FULL` to `default()`, `PARTIAL` to `partial`, `RANDOM` to `random`, `REGEXP` to a regular-expression replacement (Oracle's `REGEXP_REPLACE` semantics, already built), with Oracle's policy expression deciding per session, as `DBMS_RLS` policies do (D1321).
- **Who sees real values.** A role with the `UNMASK` permission (SQL Server's `GRANT UNMASK`, database-wide, and SQL Server 2022's per-schema, table and column forms; Oracle's `EXEMPT REDACTION POLICY`) and every superuser and table owner. The permission is an object grant (D1310's grant store) on the database, schema, table or column.
- **Where masking happens.** On the values a statement returns to a user without `UNMASK`, never on what it reads: filters, joins, grouping and ordering see real values, as both vendors do. A result column that is a masked column, directly or through a view, gets that column's function; any other result column computed from a masked column (an expression, an aggregate, a function call) gets `default()`, as SQL Server does, decided conservatively by name, so an expression is masked whenever it could depend on a masked column. `SELECT ... INTO`, `INSERT ... SELECT` and `CREATE TABLE ... AS` by such a user copy masked values, as SQL Server does. Every protocol and the MCP server get masked rows, since masking happens in the engine's result, not in a protocol layer.
- **Catalogs.** `sys.masked_columns` and `sys.columns.is_masked`, `REDACTION_POLICIES` and `REDACTION_COLUMNS` in Oracle's dictionary, and the masks in `pg_dump`-style and `sqlcmd`-style scripting output.
- **Tests that must exist.** Each function on each type; a user with and without `UNMASK`, at each grant level; filters on masked columns finding real rows; expressions, aggregates, views, set operations and subqueries masked; copies masked; the mask following a rename and going with a drop.

**Status:** decided; the code is left (code-only mode, D355).
