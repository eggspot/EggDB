## D426 MySQL and TDS clients refuse an infinite date or number instead of reading it as text — Decided by the code-only session (2026-11-11, D355); roadmap M10, finishes D290

- A PostgreSQL session can store `infinity` in a date or time stamp and `Infinity` or `NaN` in a
  `numeric` (D271, D290), but MySQL's and SQL Server's types hold neither, and their drivers
  failed on the text. Before a result set's column metadata is sent, the MySQL and TDS servers
  now look for such a value (`Value::is_unbounded`); finding one, they send the dialect's
  out-of-range error instead of the result: MySQL's 1292 (`Incorrect datetime value: 'infinity'
  for column 'c' at row n`, SQLSTATE `22007`) for a date or time stamp and 1264 (`Out of range
  value for column 'c' at row n`, `22003`) for a number; SQL Server's 242 (date to datetime out
  of range) and 8115 (arithmetic overflow), severity 16, ending the statement.
- The check runs over the rows already built, so it adds one pass over a result; a statement that
  wrote the rows has still written them, as when MySQL fails while sending a row.
- `double precision` infinities and NaN count too, since MySQL's `DOUBLE` refuses them as well;
  the PostgreSQL protocol still sends them as PostgreSQL does.

**Status:** code written, unbuilt (code-only mode, D355).
