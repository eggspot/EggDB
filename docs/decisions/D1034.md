## D1034 `eggdb follow` of pgoutput protocols 3 and 4, more binary types, and moved or replaced tables — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D296)

- From PostgreSQL 15 `eggdb follow` asks for `proto_version '3'` with `two_phase 'on'`, and from PostgreSQL 16 for
  `proto_version '4'` with `streaming 'parallel'`. The parser reads Begin Prepare, Prepare, Stream Prepare, Commit
  Prepared and Rollback Prepared, and the abort position protocol 4 adds to Stream Abort.
- A prepared transaction's statements are written to the file's follow state (`eggdb_follow.state`, items
  `prepared <gid> <index>`) in the same transaction that moves the follow's position past its Prepare. Commit Prepared
  applies them and deletes them in one transaction; Rollback Prepared deletes them. Because they are durable, a
  follow stopped between the two needs nothing from the source again, and the position reported to the source never
  has to stay behind a prepared transaction. A prepared Stream Prepare takes the streamed spool the same way.
- When a prepared transaction that changed a table's columns rolls back, the applier puts back the table shapes it
  knew before the Begin Prepare, so the next Relation message is compared with the shape the file still has.
- Binary tuples: `BinaryTypes` reads arrays (any dimensions, lower bounds, quoting as `array_out` does, `;` between
  boxes), ranges and multiranges, `inet`, `cidr`, `macaddr`, `macaddr8`, and the geometric types, and the source's
  own enums, domains, ranges, multiranges and arrays, loaded from `pg_type` and `pg_range` (OIDs from 16384). A
  Relation with a type the loaded list does not read reloads it once, then falls back to text tuples as before.
  Nesting is limited to 8 levels, and element counts are checked against the bytes left, so a hostile value is an
  error, not a large allocation.
- A table moved to another schema becomes `ALTER TABLE ... SET SCHEMA`, then `RENAME TO` when its name changed too. A
  table moved out of the followed schemas is skipped from then on, and one moved in is created and copied as a new
  table.
- A Relation with a new OID under a name the applier already knows is a replaced table. Follow asks the source
  whether the old OID still exists: when it does, the old table was renamed or moved, so the file's table is renamed
  to match (and the transaction's pending changes to it are pointed at the new name); when it does not, the file's
  table is dropped along with the transaction's pending changes to it. Either way the new table is then created and
  copied from its own snapshot, as for a table created during the follow (D296).
- Learned from PostgreSQL's documentation of the logical replication message formats and of the binary send formats
  (`array_send`, `range_send`, `inet_send`, the geometric `*_send` functions); no code was read.
- Left: a table created inside a prepared transaction that then rolls back stays in the file; a `TRUNCATE` naming
  several tables is not cut when one of them is replaced.
