## D648 INSERT ... EXEC into tables — Decided by the code-only session (2026-11-12, D355); roadmap M10, D159

`INSERT INTO #results EXEC usp_report @year = 2026` is how Transact-SQL code captures a
procedure's result set. Monitoring scripts fill temp tables from `sp_who2` or `sp_spaceused` the
same way. EggDB ran `INSERT ... EXEC` only into table variables, and a table target was a syntax
error.

- The T-SQL dispatcher looks ahead for `INSERT [INTO] name [(columns)] EXEC|EXECUTE`. The name
  may be schema-qualified, bracketed or `#temporary`. It parses the rest into a new
  `SqlServerStatement::InsertExecute` holding the table, the column list and the procedure call.
- The session runs the procedure the way `INSERT @t EXEC` does. Messages and row counts pass
  through, and the rows of every result set are gathered. They become a plain `INSERT` with
  constant `VALUES` rows, run through the ordinary statement path, so the target's checks,
  identity, defaults for unlisted columns and triggers all apply. A wrong column count gets the
  usual `INSERT` error. A procedure that returns no rows inserts none.
- Refused, with the roadmap item left open:
  - `INSERT ... EXEC ('dynamic SQL')`;
  - `INSERT ... EXEC sp_executesql`.
- The statement is classified for destructive-statement checks as running the procedure, and is
  refused inside functions as `INSERT EXEC`.
- Test: `insert_exec_fills_a_table_from_every_result_set_of_a_procedure`. Its procedures return
  two result sets, and no rows with a column list.
