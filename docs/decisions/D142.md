## D142 The C API: one header `eggdb.h` and the `eggdb-capi` library; opaque handles, a status from every call with the message per thread, buffers the caller frees for single values and batches the handle owns for scans and SQL results, scans that outlive their transaction, SQL values typed with their printed text, parameters as text; shipped beside each release — Decided by the build loop (by research, 2026-10-30); roadmap item 29, applies D1, D3, D9, D16, D17, D87, D139, D140, D141

Item 29 makes the embedded database usable from any language that can call C, and is the layer
the official drivers of D16 will sit on.

**One crate, one header.** `crates/eggdb-capi` builds a shared library, a static library and an
rlib (for its own Rust tests) from `extern "C"` functions over the `eggdb` crate, and
`crates/eggdb-capi/include/eggdb.h` declares them. It holds no storage or SQL logic: each
function checks its arguments and calls the Rust API. The library is named `eggdb_capi`
(`libeggdb_capi.so`, `eggdb_capi.dll`), not `eggdb`, since a library named `eggdb` would collide
with the `eggdb` crate's own outputs in the build directory. The header has no comments, by the
project's rule; [c-api.md](../c-api.md) is its manual, and the Rust items carry rustdoc.

**Calls.** Every function returns an `int` status: 0, the 23 codes of the Rust `ErrorKind`s
(1 to 23, `EGGDB_ERR_OTHER` for kinds a later release adds), or the C API's own (100 and up:
invalid argument, in use, read transaction, SQL, internal). The message goes to a thread-local
slot read by `eggdb_last_error()`, and a SQL failure's SQLSTATE by `eggdb_last_sqlstate()`, as
C interfaces commonly pair a code with a message (SQLite's result codes and `sqlite3_errmsg`,
POSIX's per-thread `errno`).
*Why not error objects:* a status and a per-thread message cost nothing on success, need no
free, and every foreign-function interface reads an `int` and a `char *` without declaring a
struct.

**Handles.** `eggdb_db`, `eggdb_txn`, `eggdb_scan` and `eggdb_sql` are opaque pointers to Rust
boxes. A database is shared by any number of threads (`Arc<Database>`); a transaction or SQL
session keeps the database alive, so `eggdb_close` and `eggdb_compact` refuse with
`EGGDB_ERR_IN_USE` while one is open instead of leaving them dangling. A transaction is a Rust
`ReadTransaction` or `WriteTransaction` whose lifetime is tied to the `Arc` it holds beside it
(dropped after it, by field order); that is the only lifetime extension, in one function with
its `// SAFETY:` argument. Ending a handle with NULL does nothing.

**Memory.** Two rules, chosen by size (D17): a single value (`eggdb_get`) and the collection
names are copied into a buffer the caller frees with `eggdb_free(pointer, length)`, so they
outlive the transaction; a scan's batch and a SQL call's results are written into memory the
handle owns and reused, and are read in place until that handle's next call. A batch is one
call for up to 256 entries (or about a mebibyte) or for every row of a statement, with no call
per value: C reads `eggdb_entry` and `eggdb_value` arrays directly, and
`eggdb_result_value(result, row, column)` is an inline function in the header.

**Scans outlive their transaction.** An `eggdb_scan` keeps its range and where it stopped, not a
borrow of a transaction; each `eggdb_scan_next` is read in the transaction passed with it.
*Why:* a Rust `Scan` borrows its transaction, which a C handle could only hold with a second
lifetime extension and an order of frees the caller must get right; a resumable cursor needs
neither, lets a long export continue across short read transactions, and costs one seek per
batch.

**SQL.** A session is `Session<Store>` on the database, in the dialect named at open. Each value
comes as a kind (`NULL`, integer for booleans and integers, real, blob, text for everything
else), its number when it has one, and, for every value but NULL, its text exactly as the
dialect's clients print it (NUL-terminated); a blob gives its bytes. *Why:* numbers stay
numbers without parsing, every other type (numerics, dates, JSON, UUIDs, intervals) has one
faithful form today, and a typed binary layout per SQL type can be added as new kinds later
without breaking these. Parameters are text values (`eggdb_parameter`) passed to
`Session::execute_prepared`, the path the wire protocols use, so a value never has to be quoted
into SQL. Prepared statement handles (D17's fifth rule) wait until the engine keeps a parsed
plan between executions; today they would only re-parse.

**Panics.** No input may reach a panic (D9); every function also runs inside
`std::panic::catch_unwind`, so a build that unwinds returns `EGGDB_ERR_INTERNAL`. The release
profile aborts on panic for speed, so a release library stops the process on a bug rather than
unwinding across the boundary, which would be undefined behavior.

**Checks.** Rust tests call every function as C would; a header test parses `eggdb.h` and
compares its constants, functions (with their parameter counts) and structs (with their fields
and types) against the Rust source; a C program compiled with warnings as errors, a C++
compile of the header and the Python `ctypes` example run in CI on Linux and macOS (the Python
example alone on Windows, whose runners have no C compiler set up for MSVC in their shell), and
in the release workflow on each library its runner can load.

**Shipped beside each release.** The release workflow builds the library for the glibc, macOS
and Windows targets and publishes `eggdb-capi-<version>-<target>` archives with the header, the
libraries, the Python example and the manual, next to the `eggdb` binary, whose archive and
size budget (D6, D14) stay as they are. The musl targets are left out: their default static C
runtime does not produce shared libraries.

**Not in this release:** prepared statement handles, declared parameter types and binary
parameters, `COPY`, cancelling a running statement, asynchronous completion (D17's sixth rule),
the open options beyond flags, durability and cache size, `check` and `stats`, and the
per-language drivers (D16).
