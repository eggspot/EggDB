## D909 GraphQL nested inserts — Decided by the code-only session (2026-11-12, D355); roadmap M6a, follow-up of D875

- `insert_<table>` and `insert_<table>_one` accept Hasura's nested insert input: a relationship field (named after a
  foreign key, D875) whose value is `{data: ...}` inserts the related rows in the same transaction:
  - an object relationship (`author: {data: {...}}` on `books`) inserts the parent first and sets the row's foreign
    key columns from it;
  - an array relationship (`books: {data: [...]}` on `authors`) inserts the row first and each child with its
    foreign key columns set from it.
- Each top-level object becomes one statement of data-modifying `WITH` steps (the parents, the row, the children),
  each `INSERT ... VALUES` so literals take their columns' types; the inserted top-level rows are kept in a temporary
  table made `LIKE` the target, and `returning` (or the `_one` object) is built from it by a statement after the
  inserts, so relationships in the response see the rows just inserted. The temporary table is dropped at the end of
  the field; everything runs in the mutation's one transaction, so a failure undoes all of it.
- Limits: one relationship deep (a nested object that nests again is refused), `affected_rows` counts the top-level
  rows only (Hasura counts the nested ones too), and `on_conflict` is refused with nested data.
