## D229 Federation starts as one set-returning function over sources the operator allows — Decided by the build loop (by judgement, 2026-10-31); refines D18 and D29

Part 4.M18-5 asks to query other EggDB servers and external sources as foreign tables.

- **`eggdb_foreign(source, query)` returns one `json` object per row.** The set-returning
  framework derives a function's result type from its arguments' types, and a foreign query's
  columns are only known when it runs, so rows come back as JSON objects that the rest of the
  query unpacks (`o->>'name'`). Filters, joins and aggregates then work as on local rows, with
  no planner change. `CREATE FOREIGN TABLE` with declared columns, pushing filters down, and
  `IMPORT FOREIGN SCHEMA` come next, on top of the same readers.
- **The engine never opens a connection itself.** `eggdb-sql` only calls a reader the host
  program installs (`set_foreign_source`, like `set_random_source`), keeping protocols out of
  the engine (CLAUDE.md, layout). The `eggdb` program installs one that reads PostgreSQL's
  protocol through our own client (`eggdb-pgwire`), so other EggDB servers and PostgreSQL
  servers answer, and reads Parquet files through `eggdb-parquet`.
- **Off unless allowed.** A function that reaches the network or the disk from SQL is a server-
  side request forgery and file-read risk for every role that can run queries. `eggdb` installs
  the reader only when `EGGDB_FOREIGN_SOURCES` lists URL prefixes, and refuses any other
  source with `HV000` (`fdw_error`). Embedded programs decide for themselves.

Left: foreign tables with declared columns and filter pushdown, MySQL, SQL Server and HTTP or S3
sources, Parquet over object storage, credentials per source instead of `PGPASSWORD`, joins
across servers planned as a distributed query (D212), per-role permission to use a source, and
a timeout and row limit per call.
