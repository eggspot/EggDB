## D802 LDAP search-and-bind, StartTLS and LDAPS — Decided by the code-only session (2026-11-12, D355); roadmap M6b, LDAP

- The `ldap` rule (D185) takes `server=ldaps://host:636` for TLS from the first byte, or `starttls=1` for LDAP's
  StartTLS extended operation (OID 1.3.6.1.4.1.1466.20037, RFC 4511 section 4.14) before TLS on the same connection.
  Either needs `ca=<file>` (read relative to the rule file, like `jwks=`): the directory's certificate must chain to
  it and name the server's host, through EggDB's own TLS client (`eggdb-auth` now depends on `eggdb-tls`). A rule
  that asks for TLS without a certificate authority is refused when the rule file loads, rather than encrypting
  without checking who answers.
- `basedn=` switches to search-and-bind, as PostgreSQL's `ldapbasedn` does: the server binds as `bind_dn=` with
  `bind_password=` (anonymously without them), searches the whole subtree under the base DN for entries whose
  `search_attribute=` (`uid` by default) equals the user name, as a BER equality filter so the name needs no filter
  escaping, asks for no attributes (`1.1`), and with exactly one entry found binds as that entry's DN with the
  password. No entry or several fail the login; a failing search account is reported as the directory's refusal.
- Responses are now read one LDAP message at a time (header, then exactly the declared length), since a search
  answers with several messages; the 64 KiB per message bound stays.
- Left: checking against a real directory (OpenLDAP, Active Directory) in CI, and `ldapurl`-style rules.
