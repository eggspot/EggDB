## D513 MySQL `MATCH ... AGAINST` — Decided by the code-only session (2026-11-11, D355); roadmap M8

The MySQL dialect parses `MATCH (columns) AGAINST (query [IN NATURAL LANGUAGE MODE [WITH QUERY
EXPANSION] | IN BOOLEAN MODE | WITH QUERY EXPANSION])` into a function that returns the columns'
relevance as a `double`, 0 when they do not match.

- **Words:** InnoDB's rules: tokens of letters, digits, `_` and `'`, folded to lower case, at
  least three characters (`innodb_ft_min_token_size`), and not in InnoDB's default stopword list.
- **Natural language mode:** each distinct query word the text holds adds `1 + ln(count)`. InnoDB
  weighs words by their rarity across the table (BM25-like IDF); EggDB has no table-wide index
  yet, so relevance differs from MySQL's while matching the same rows. Query expansion is read and
  searched as natural language mode.
- **Boolean mode:** `+` required, `-` excluded, `>` and `<` raise and lower a word's weight, `~`
  makes it count against, `word*` matches a prefix, `"phrases"` match consecutive words, and
  parentheses group without changing meaning. A row matches when no excluded word appears, every
  required word does, and at least one word matched.
- **Conditions:** MySQL takes numbers as conditions (non-zero is true), so in the MySQL dialect a
  `WHERE`, `HAVING`, `CHECK` or `FILTER` condition that is an integer or floating-point number is
  now read that way instead of refused; this is the first piece of the roadmap's "booleans as
  integers".
- **Left out:** `FULLTEXT` keys are still refused in `CREATE TABLE` (they wait for the in-file
  inverted index, D195), so `MATCH` scans the rows; no `ngram` parser; SQL Server's `CONTAINS` and
  `FREETEXT` and SQLite's FTS5.
