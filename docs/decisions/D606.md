## D606 Bolt transactions held open across messages — Decided by the code-only session (2026-11-12, D355); roadmap M13, D207, D504

D207 accepted `BEGIN` and `COMMIT` but committed every statement as it ran, and refused a
`ROLLBACK` after a write. Neo4j drivers' `session.executeWrite(tx => …)` and Spring Data Neo4j's
`@Transactional` rely on a rollback undoing the work, and on other sessions not seeing it before the
commit.

- A Bolt connection now stages an explicit transaction's writes in memory (`staged::StagedChanges`)
  instead of applying them.
- Every `RUN` between `BEGIN` and `COMMIT` runs against a `Staged` keyspace:
  - reads see the transaction's own staged puts and deletes over the committed keys;
  - writes go to a copy of the staged changes, kept only if the statement succeeds, so a failed
    statement changes nothing;
  - a `clear` is staged as well.
- `COMMIT` applies the staged changes, one write transaction per database touched (Cypher uses
  one). A failure answers `TransactionCommitFailed`. `ROLLBACK`, `RESET` and a new `BEGIN` discard
  them.
- Staged changes are limited to 64 MiB per transaction. A statement that would go past that fails
  with advice to commit in smaller transactions.
- Isolation is read-committed with last-writer-wins at commit. A transaction reads committed data
  as of each statement, and its commit does not check for conflicting commits made since; Neo4j
  takes locks instead.
- A unit test covers reading one's own writes, a failed statement leaving no trace, and only
  `COMMIT` reaching the base keyspace.

Not done: conflict detection at commit, and transactions spanning several databases atomically.

**Status:** code written, unbuilt (code-only mode, D355).
