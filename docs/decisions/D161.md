## D161 EggDB's own TLS 1.3 and 1.2 for every listener, and listeners beyond loopback only with TLS — Decided by the build loop (by judgement, 2026-10-31); supersedes part of D102

Part 4.M6a-1 gives EggDB its own TLS, written from the RFCs on its own cryptography (D1, D23),
and with it lifts D102's loopback rule for servers that have a certificate.

**What is built.**
- `eggdb-crypto` gains SHA-384/512, generic HMAC and HKDF (RFC 5869), ChaCha20-Poly1305
  (RFC 8439), AES-128/192/256 and AES-GCM, X25519 (RFC 7748), P-256 ECDH and ECDSA with RFC 6979
  nonces, and RSA PKCS#1 v1.5 and PSS signatures. Each is checked against its published vectors
  and Wycheproof's cases.
- A new crate `eggdb-tls` holds DER, PEM, X.509 certificates, private keys (PKCS#8, SEC 1,
  PKCS#1), self-signed P-256 certificates, chain and name verification (RFC 5280, RFC 6125), the
  TLS 1.3 handshake, key schedule and record layer (RFC 8446, checked byte for byte against
  RFC 8448's traces), TLS 1.2 with ECDHE and AEAD suites only (RFC 5246, RFC 8422, RFC 5288,
  RFC 7905) with extended master secret (RFC 7627), a server and a client, `TlsStream` over any
  byte stream, and `ServerConnection` for servers that upgrade a TCP connection.
- PostgreSQL: `SSLRequest` is answered `S`, PostgreSQL 17's direct TLS is accepted with ALPN
  `postgresql`, and SCRAM-SHA-256-PLUS binds the login to `tls-server-end-point` (RFC 5929).
- MySQL: `CLIENT_SSL` is offered and an SSL request moves the login onto TLS.
- SQL Server: PRELOGIN negotiates encryption ([MS-TDS] 2.2.6.5), with the handshake inside
  PRELOGIN packets: full encryption, login-only encryption for a loopback client that asks only
  for that, and TDS 8 strict (TLS first, ALPN `tds/8.0`).
- `eggdb serve --tls-certificate --tls-key`, `--tls-self-signed` and `--tls-min-version`, designed
  by Claude Fable (docs/ux/cli.md section 29).

**The listener rule (supersedes part of D102).** A server with TLS may listen on any address, and
every connection from another machine must use TLS; programs on the same machine may still
connect without it. A server without TLS keeps D102: loopback addresses only. Authentication stays
mandatory everywhere (D22).

**Choices made by judgement.**
- AES is portable constant-time code (computed S-box, no CPU AES instructions, no `unsafe`), so it
  is slower than ChaCha20-Poly1305 in software. The server therefore orders the ChaCha20-Poly1305
  suites first for each version. CPU AES instructions are a performance-pass item.
- RSA signs without the CRT, so no primes are needed and there is no CRT fault attack; it is
  about 4x slower, which matters little because generated certificates are P-256.
- Self-signed certificates are P-256 with ECDSA-SHA256, CA:FALSE, extended key usage server and
  client authentication, subject alternative names, and no key usage extension. Some OpenSSL 1.1
  builds treat a self-signed certificate without keyCertSign as not self-signed.
- TLS 1.2 is accepted by default (`--tls-min-version 1.2`): older JDBC and .NET drivers still
  need it. It is limited to ECDHE with AEAD suites, extended master secret when the client offers
  it, no resumption and no renegotiation (an empty `renegotiation_info` is answered). A server that
  could do TLS 1.3 sets the downgrade sentinel when it negotiates 1.2.
- No session tickets are issued, and received ones are ignored: resumption is a later item.
- A read that ends without `close_notify` is an error, not end-of-file. The database protocols
  frame their own messages, so a cut connection is always visible.
- A TDS 8 strict PRELOGIN answer says encryption is not supported inside TLS: the connection is
  already encrypted, and the client does not start a second handshake. The CI check with
  SqlClient's `Encrypt=Strict` confirms or corrects this.
- Client certificates (mutual TLS) are not built here; a client answers a CertificateRequest with
  an empty Certificate. Server-side client authentication by certificate is part 4.M6b-1.
