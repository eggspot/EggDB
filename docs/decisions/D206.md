## D206 Property graphs in our own eggdb-graph: a Cypher subset first, SQL/PGQ and GQL next — Decided by the build loop (by judgement, 2026-10-31); refines D2, D38 and D55

Part 4.M13-1 asks for property graphs over tables queried with SQL/PGQ `GRAPH_TABLE`, GQL and
Cypher, and graph algorithms.

- **A native graph on the shared keyspace first.** Nodes, relationships and both adjacency
  directions are records of one collection (`graph0`), written through the key-value interface
  the other data models use (D197), so a query is one engine transaction and the graph is in
  the same file, backup and log as everything else. Graph *views* over relational tables
  (`CREATE PROPERTY GRAPH ... VERTEX TABLES ... EDGE TABLES`) need the SQL planner to read
  `GRAPH_TABLE` and come with SQL/PGQ; they will compile to the same pattern matcher.
- **Cypher from the openCypher specification** (Apache-licensed language documents, no Neo4j
  code): reading and updating clauses, patterns with labels, properties, either direction and
  variable length (at most 15 hops, relationship-unique within a match), three-valued logic,
  parameters, aggregation with implicit grouping, and the common scalar functions. Errors carry
  Neo4j's documented status codes so Bolt drivers (4.M13-2) raise their usual exceptions.
- **Limits against hostile queries**: expression nesting, path length and row counts are bounded,
  and a failing query changes nothing.
- **Algorithms as a library** (breadth-first shortest path, weakly connected components,
  PageRank) until procedures (`CALL ...`) exist in the query language.

Left: SQL/PGQ and GQL, graph views over tables, `CALL` procedures exposing the algorithms,
named paths and `shortestPath()`, `MERGE ... ON CREATE/ON MATCH`, `FOREACH`, `UNION`, list
comprehensions, indexes on labels and properties (matching scans every node now), uniqueness
constraints, and the LDBC benchmark.
