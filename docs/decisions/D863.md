## D863 PostgreSQL `login` event triggers — Decided by the code-only session (2026-11-12, D355); follow-up of D787

- `CREATE EVENT TRIGGER name ON login EXECUTE FUNCTION f()` is accepted (PostgreSQL 17's event), without a `WHEN
  TAG` filter, which PostgreSQL refuses too (0A000). `TG_EVENT` and `TG_TAG` are both `login` inside the function.
- `Session::fire_login_event_triggers` runs the enabled `login` triggers in name order in one transaction. The
  PostgreSQL listener calls it once a connection has authenticated and taken its startup settings, before
  `ReadyForQuery`; an error from a trigger is sent as a FATAL error and the connection closes, so a trigger can refuse
  logins, as in PostgreSQL. A failed login's trigger writes are rolled back with it.
- The trigger list is read without the role's privilege checks (it lives in an internal table the role cannot be
  granted), while the trigger functions run as the logging-in role. Sessions in another dialect fire nothing.
- Left: `table_rewrite` firing, sub-commands of `ALTER TABLE` as separate rows, a way past a broken login trigger
  (PostgreSQL's `event_triggers = off`), and SQL Server's and Oracle's DDL and logon triggers.
