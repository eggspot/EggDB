## D181 SQLite's C API as a library of its own, libsqlite3, on EggDB's SQLite dialect — Decided by the build loop (by judgement, 2026-10-31); refines D16 and D17

Part 4.M5-4 asks for existing SQLite programs to link against EggDB's `sqlite3_*` API.

- **A crate of its own**, `eggdb-sqlite3`, builds `libsqlite3` (a shared and a static library),
  so a program links with `-lsqlite3` against it instead of SQLite. Keeping it out of
  `eggdb-capi` means EggDB's own C API never exports SQLite's names. The header
  `include/sqlite3.h` is ours, written from SQLite's published C interface: the declarations,
  result codes and type codes it provides.
- **What it does.** `sqlite3_open`/`_open_v2` open an EggDB file, or a database in memory for
  `:memory:` (D175). A connection is a SQL session in the SQLite dialect. `sqlite3_exec` runs a
  script and calls back per row. `sqlite3_prepare_v2` takes the first statement and returns its
  tail. `bind_*` keep typed parameters, with blobs in `bytea`'s input form. `sqlite3_step` runs
  the statement at its first step and walks its rows. `column_*` read them, and texts and blobs
  stay valid until the next step, reset or finalize, as SQLite promises. `sqlite3_errmsg`,
  `sqlite3_errcode`, `sqlite3_changes`, `sqlite3_total_changes` and `sqlite3_last_insert_rowid`
  report as SQLite does, and the error codes are the dialect's SQLite codes.
- **Tests** call it as a C program would: create, insert with every bind type, read back with
  every column function, a failing statement's message through `sqlite3_free`, and `exec` with
  a callback.

Left: `sqlite3_create_function`, `sqlite3_busy_timeout`, `sqlite3_backup_*` and the rest of the
interface, statements that stream rows instead of collecting them at the first step, the
release workflow packaging `libsqlite3`, and running SQLite-using programs (the sqlite3 shell,
Python's `sqlite3` module) against it in CI.
