## D468 Elasticsearch point in time (`_pit`) — Decided by the code-only session (2026-11-11, D355); roadmap M8, D196 and D348

- `POST /<index>/_pit?keep_alive=<time>` (comma-separated indices, `ignore_unavailable`) reads
  the indices' documents once and answers `{"id": ...}`. A `_search` whose body has
  `"pit": {"id": ..., "keep_alive": ...}` searches that copy instead of the current documents,
  renews the keep-alive when one is given, and answers `pit_id` at the top, so `search_after`
  pages over one unchanging set of documents. Naming indices in the path together with `pit`
  is refused, as Elasticsearch does.
- `DELETE /_pit` with `{"id": ...}` frees one (`num_freed` 1, or 404 with 0).
- Keep-alives use scroll's time units up to 24 hours (D467); at most 500 are open (429 past that);
  expired ones are dropped on each call. The copy is shared by reference between the context and
  each search's page, so a search over a point in time does not copy the documents again.
- The documents are held in memory, so a point in time costs its indices' size until it is
  freed or expires; counting it against the server's memory budget is not written.
