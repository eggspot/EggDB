## D503 Cypher constraints and indexes on labels and properties — Decided by the code-only session (2026-11-11, D355); roadmap M13, D206

- `eggdb-graph` reads Neo4j 5's schema commands before Cypher: `CREATE CONSTRAINT [name]
  [IF NOT EXISTS] FOR (n:Label) REQUIRE n.p IS [NODE] UNIQUE` (or `REQUIRE (n.a, n.b) IS UNIQUE`,
  or the older `ON (n:Label) ASSERT ...`), `... REQUIRE n.p IS NOT NULL`, `CREATE [RANGE|TEXT|POINT]
  INDEX [name] [IF NOT EXISTS] FOR (n:Label) ON (n.a, ...)`, `DROP CONSTRAINT|INDEX name [IF EXISTS]`,
  and `SHOW [ALL] CONSTRAINTS|INDEXES` (rows with `id`, `name`, `state` for indexes, `type`,
  `entityType`, `labelsOrTypes`, `properties`). Unnamed rules get a name from their kind, label and
  properties.
- Rules are records of their own in the graph's keyspace (kind `5`). Creating a constraint that
  the stored nodes already break fails with `ConstraintCreationFailed`; an equivalent rule or a
  reused name answers `ConstraintAlreadyExists`/`EquivalentSchemaRuleAlreadyExists` unless
  `IF NOT EXISTS`.
- Every node write (`CREATE`, `MERGE`, `SET`, `REMOVE`) checks the constraints of the node's
  labels: a uniqueness constraint refuses a second node with equal values (only when all its
  properties are present, as Neo4j does), an existence constraint a node without the property,
  with `Neo.ClientError.Schema.ConstraintValidationFailed`, rolling the query back.
- Indexes are recorded and listed but do not speed lookups yet, and uniqueness is checked by
  scanning the label's nodes; both wait for the graph's own index structures. Relationship
  constraints and indexes are not written.
