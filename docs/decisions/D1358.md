## D1358 A key allow-list for the MCP key tools: eggdb mcp --keys — Decided by the code-only session (2026-11-25, D355); roadmap M6d "A per-session key allow-list, so the MCP key-value tools work under --tables and --mcp-tables (D328)"

- **What users get.** `eggdb mcp --keys <prefixes>` (comma-separated, `0x..` for hex, repeatable, at most 256) names the key families an agent may reach. The key tools are then offered even with `--tables` or a role, and reach only keys of the default key space that start with a listed prefix: `kv_get` and the key writes refuse any other key, `kv_scan` clips every range it reads to the prefixes, so other keys never appear, and a `collection` argument is refused, since collections are whole key spaces the list does not name.
- **Why prefixes.** Applications name key families by prefix (`session:`, `cart:`), so a prefix list grants a family in one word and a scan stays a set of contiguous ranges, each read in key order with the paging `kv_scan` already has.
- **What it does not open.** `resp_get` reads the RESP keys, a different key space, so with `--keys` it is refused too; `stats`, `check` and `backup` stay refused under `--tables`. Without `--tables` or a role, `--keys` still narrows the key tools to the prefixes, so it is also a plain allow-list.
- **Errors.** `outside_key_prefixes`, category `needs_grant`, with what to do.
- **Left.** `--mcp-keys` for the MCP endpoint of `eggdb serve`, and key-level grants for roles (D328's other item).
- **Proof.** An acceptance test serves a file with `--tables users --keys session:,greet --allow-write`: `kv_get` reads `session:1` and refuses `secret:1`, `kv_scan` lists exactly `greeting`, `session:1` and `session:2`, `put` stores `session:3` and refuses `secret:2` (which stays absent), and a collection and `resp_get` are refused.
