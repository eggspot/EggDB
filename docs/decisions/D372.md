## D372 A failing Oracle statement trigger undoes only its statement; SQL Server's `AFTER` triggers keep rolling the transaction back — Decided by the code-only session (2026-11-10, D355); roadmap M3, closes one of D317's leftovers

Statement triggers run after their statement's rows are written (`write_firing_triggers`), so
when one failed, the statement's own undo log was already gone and the session rolled the whole
transaction back.

- **Oracle.** A trigger is part of its statement: when the statement or its trigger fails, the
  statement and everything its triggers did are undone and the transaction goes on. In a
  transaction, the session now sets an internal savepoint (a name starting with a NUL byte, which
  no identifier can hold) before a writing statement, rolls back to it when a statement trigger
  fails, and releases it afterwards in every case; nested trigger statements stack their own.
- **SQL Server.** Decided by research: SQL Server runs triggers with `XACT_ABORT ON` by default,
  so an error in an `AFTER` trigger ends the batch and rolls the transaction back (Msg 3609 when
  the trigger itself ended it). EggDB already does that, so the roadmap item's SQL Server half
  needs no change.

**Cost.** In an Oracle transaction each writing statement pushes and pops one savepoint mark;
the statement's undo entries were already logged for statement-level rollback (D317).
