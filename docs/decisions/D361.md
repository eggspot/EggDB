## D361 Subpartitions (MySQL `SUBPARTITION BY`, Oracle composite partitioning) and Oracle's row movement switch — Decided by the code-only session (2026-11-10, D355); extends D169, D316 and D337, with its D35 review

**Subpartitions.** EggDB already partitions partitions (PostgreSQL's multi-level partitioning,
D169), so a subpartition is a partition of a partition: `o#P#p0#P#p0sp0`. The parser takes
MySQL's `SUBPARTITION BY HASH | KEY [ALGORITHM = n] (...) [SUBPARTITIONS n]` after a range or
list key (`1500` after a hash key, as MySQL refuses it) and Oracle's `SUBPARTITION BY HASH |
RANGE | LIST (...) [SUBPARTITIONS n]`, and each partition may list its subpartitions with their
bounds. Without a list, hash subpartitions are named `<partition>sp<n>` as MySQL names them, and
their count is `SUBPARTITIONS n` or 1. A list whose length differs from `SUBPARTITIONS n` is
`1485`; range and list subpartitions must be listed (`ORA-14160`; Oracle's `SUBPARTITION
TEMPLATE` is not parsed yet). `PARTITION (name)` and Oracle's `SUBPARTITION (name)` already find
partitions at every level by their own name, so selecting a subpartition needs nothing new.
Left: the maintenance `ALTER`s of D358 and D360 create plain partitions on a subpartitioned
table, and `SUBPARTITION TEMPLATE`.

**Row movement.** Oracle refuses an `UPDATE` that changes a row's partition (`ORA-14402`) unless
the table has `ENABLE ROW MOVEMENT`; D316 accepted the clause but moved rows everywhere. EggDB
now keeps the switch on the partitioned table's record: a table created in the Oracle dialect
without the clause, or with `DISABLE ROW MOVEMENT`, refuses moves; `ENABLE ROW MOVEMENT` in
`CREATE TABLE` or `ALTER TABLE` allows them, and `ALTER TABLE ... DISABLE ROW MOVEMENT` refuses
them again. The check runs after the rows of the update were read and before the moved rows are
inserted, so the statement's rollback undoes the rows already taken out of their partitions.
Other dialects never set it, and Oracle tables created before this decision keep moving rows,
since their records carry no switch.

**D35 review of the format change.** The partition record (catalog prefix `0x0E`) gains version
3, written only when a partitioned table has an option, which today means only disabled row
movement: it reads as version 2, the flag byte may carry `4`, and an options byte ends the
record (`1` row movement disabled; any other bit, a zero byte, or options on a record without a
key is damage). Files without such a table are written exactly as before, so they stay readable
by older EggDB versions; a file with one is refused by them as a newer format, through the
record's existing version check. No upgrade step is needed: older records read as row movement
allowed. Downgrading a file means `ALTER TABLE ... ENABLE ROW MOVEMENT` on each such table,
which writes the record back at version 1 or 2. A test checks the version 3 round trip and that
an allowed table still writes version 1.
