## D312 Oracle's `EXPLAIN PLAN` writes Oracle's `PLAN_TABLE` rows and `DBMS_XPLAN.DISPLAY` formats them; SQL Server's `SET SHOWPLAN_TEXT`, `SET SHOWPLAN_ALL` and `SET STATISTICS PROFILE` answer with SQL Server's result sets; all three are drawn from EggDB's own plan — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); roadmap M6e and the SQL dialects row, extends D109 and D277, applies D10 and D12

Before this both dialects refused to explain (`not_supported`), so a tool written for Oracle or
SQL Server could not show a plan. The public references followed are Oracle's SQL Language
Reference (`EXPLAIN PLAN`), Database Reference (`PLAN_TABLE`) and PL/SQL Packages and Types
Reference (`DBMS_XPLAN`), and Microsoft's Transact-SQL reference for the three `SET` options.

- **One plan, three spellings.** `crates/eggdb-sql/src/explain.rs` turns the planner's
  `ExplainedQuery` into abstract steps (`Result`, `Append`, `Sort`, `Limit`, `NestedLoop`,
  `HashJoin`, `Hash`, a scan by its access path, a full scan, a key lookup). PostgreSQL's text
  form is printed from them as before, byte for byte. `explain/oracle_plan.rs` and
  `explain/showplan.rs` name the same steps the way each vendor does. PostgreSQL's `Hash` step
  has no counterpart in either, so its child moves up to the join.
- **Oracle's names.** `SELECT STATEMENT` (or `UPDATE STATEMENT` with an `UPDATE` row naming the
  table, and the same for `DELETE`) is row 0. A full scan is `TABLE ACCESS FULL`. A keyed scan is
  `TABLE ACCESS BY INDEX ROWID` over `INDEX UNIQUE SCAN` (a primary-key point lookup or a join
  through the primary key), `RANGE SCAN` or `RANGE SCAN DESCENDING`. Joins are `NESTED LOOPS` and
  `HASH JOIN`, a sort is `SORT ORDER BY`, a limit is `COUNT STOPKEY`, a union is `UNION-ALL` and a
  query without a table is `FAST DUAL`. Names are shown in Oracle's case (`EMP`, `EMP_DEPT_IX`),
  the owner is filled in for a schema-qualified table, and the alias is `E@SEL$1` (`UPD$1`,
  `DEL$1`).
- **`EXPLAIN PLAN [SET STATEMENT_ID = '<id>'] [INTO <table>] FOR <statement>`.** The statement is
  planned, never run, and must be a `SELECT`, `UPDATE` or `DELETE` (others are `not_supported`).
  Without `INTO`, the rows go to `PLAN_TABLE`, which is created on demand in the session's
  schema with the 36 columns of Oracle's reference, in their order and types. A table named by
  `INTO` must already exist (`ORA-00942` otherwise), as Oracle requires. Each `EXPLAIN PLAN` takes
  the next `PLAN_ID` (the largest so far plus one) and writes `STATEMENT_ID`, `PLAN_ID`,
  `TIMESTAMP` (`SYSDATE`), `OPERATION`, `OPTIONS`, `OBJECT_OWNER`, `OBJECT_NAME`,
  `OBJECT_ALIAS`, `OBJECT_TYPE` (`TABLE`, `INDEX`, `INDEX (UNIQUE)`), `OPTIMIZER` (`ALL_ROWS` on
  row 0), `ID`, `PARENT_ID`, `DEPTH` and `POSITION` (the place among siblings; row 0's, which is
  Oracle's cost, stays NULL). The rows are written by ordinary `INSERT`s in the session's own
  transaction, so they need the user's `INSERT` privilege and roll back with it, as in Oracle.
  `EXPLAIN PLAN` is one statement, all or none: under autocommit its writes run in a
  transaction of their own, and inside a transaction under a savepoint, so a failure part-way
  (a too narrow `INTO` column, a constraint) leaves no row. The `PLAN_ID` is the largest in the
  table plus one, or one above the last this process gave out when that is larger, so two
  sessions of one server never write the same `PLAN_ID`.
  Costs, cardinalities, bytes, times and predicates stay NULL: EggDB's planner has no estimates.
- **`SELECT … FROM TABLE(DBMS_XPLAN.DISPLAY[(table, statement_id, format)])`.** The parser reads
  the call as a table function, and before the query runs the session replaces it with the
  formatted lines as a one-column `VALUES` list named `PLAN_TABLE_OUTPUT`, so `SELECT *`, a
  column list and `WHERE` work as on any table. It shows the plan with the largest `PLAN_ID`
  (of that `STATEMENT_ID` when one is given): `Plan hash value: <n>` (FNV-1a of the operations,
  stable for the same plan), then the `Id | Operation | Name` table with operations indented by
  their depth, then a `Note` saying EggDB gives no estimates. That is the shape of Oracle's
  `BASIC` format, which is what the data supports; `format` is accepted and does not change it.
  No plan gives Oracle's line `Error: cannot fetch last explain plan from PLAN_TABLE` (or `…
  plan for statement_id '<id>'`). Arguments must be string literals or NULL. Only the first
  table of a `FROM` is replaced, and at most 10,000 plan rows are read back (the read itself
  stops there, `FETCH FIRST 10000 ROWS ONLY`).
- **SQL Server's names.** A full scan is `Clustered Index Scan` on the primary key's index, or
  `Table Scan` for a table without a primary key. A keyed scan is `Clustered Index Seek` or
  `Index Seek` with `ORDERED FORWARD` or `BACKWARD`. Joins are `Nested Loops` and `Hash Match`
  (logical `Inner Join`), and `Sort`, `Top`, `Concatenation` and `Constant Scan` stand for the
  rest. An `UPDATE` or `DELETE` gets `Clustered Index Update`/`Delete` (or `Table …`) on top.
  Objects are `OBJECT:([t].[index] AS [alias])`, each part bracketed and `]` doubled.
- **`SET SHOWPLAN_TEXT ON`.** Every later statement except `SET` options is not run, as
  Microsoft's reference says ("Transact-SQL statements are not executed"); the check comes
  before every other path in the session, so `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVE
  TRANSACTION`, `ROLLBACK TRANSACTION <name>`, `USE`, `CREATE`/`DROP DATABASE`, `INSERT BULK`,
  `THROW`, `RAISERROR`, `PRINT`, `WAITFOR`, `RETURN` and variable assignments are shown, not run.
  `DECLARE` (and `DECLARE @t TABLE`) declares its variables without their initial values, the
  way SQL Server's compile knows them, so later statements bind. Control flow is not evaluated:
  the batch's statements are walked once in order, `IF` and `WHILE` conditions are shown as
  their own row, both branches of an `IF` and a loop's body appear once, and `GOTO`, `BREAK`,
  `CONTINUE` and `RETURN` do not jump, so a loop whose exit depends on its own writes still
  ends. `EXEC` of a user procedure and `EXEC(...)` walk their statements the same way, so their
  plans are shown and nothing inside runs; `EXEC` of a system procedure is shown. Microsoft's
  reference says `SET SHOWPLAN_ALL` "cannot be specified inside a stored procedure" and must be
  alone in its batch, so `SET SHOWPLAN_TEXT` and `SET SHOWPLAN_ALL` inside `EXEC(...)`,
  `sp_executesql` or a procedure body fail with error 1067, which ends the batch, whether plans
  are on or off; changing `eggdb.dialect` there while plans are on fails the same way, since
  the statements after it would leave SQL Server's dialect and run (review round 2: nested code
  could turn plans off and then run a `DELETE`). MCP's `explain_query` also refuses
  (`not_a_plan`) any result whose columns are not `StmtText`, so it only ever returns a plan. A `SELECT`,
  `UPDATE` or `DELETE` returns two result sets, as SQL Server does: one `StmtText` row with the
  statement's text, then one `StmtText` row per operator drawn as SQL Server's tree (`  |--`,
  five columns per level, a `|` down to each later sibling). Other statements return only the
  first. `SET SHOWPLAN_ALL ON` returns one result set in SQL Server's 18 columns (`StmtText`
  through `EstimateExecutions`): the statement's row (`NodeId` 1, `Parent` 0, `Type` its verb),
  then a `PLAN_ROW` per operator numbered from 2 with its parent's `NodeId`. The estimate
  columns are NULL and `Parallel` is 0. Turning one option on replaces the other; `OFF` turns
  off only its own.
- **`SET STATISTICS PROFILE ON`.** The statement runs, and after its own result comes a
  `SHOWPLAN_ALL` result with `Rows` and `Executes` first. EggDB measures the statement, not each
  operator, so the statement's row and its top operator carry the rows it returned or changed and
  one execution; the other operators' counts are NULL. A statement EggDB cannot plan runs without
  the extra result. `SET STATISTICS IO` and `TIME` are accepted and print nothing;
  `SHOWPLAN_XML` and `STATISTICS XML` are `not_supported`.
- **Read-only callers and the client.** `Session::set_explain_plan_displays(true)` makes
  `EXPLAIN PLAN` write no plan table and answer with the `PLAN_TABLE_OUTPUT` lines `DISPLAY` would
  show right after it, so `eggdb explain --dialect oracle` and MCP's `explain_query`, which open
  the file read-only, print Oracle's display; in SQL Server's dialect they run
  `SET SHOWPLAN_TEXT ON` first and print its operator tree, and the same setting makes a
  statement EggDB cannot plan there (an `INSERT`, a `DROP TABLE`) `not_supported`, as in
  Oracle's dialect, instead of a success holding only the statement's text. The desktop client's `Ctrl/Cmd+E`
  runs `EXPLAIN PLAN FOR` and `SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY)` rolled back in Oracle's
  dialect, and `SET SHOWPLAN_ALL ON`, the statement and `SET SHOWPLAN_ALL OFF` (run even when the
  statement fails) in SQL Server's; `Ctrl/Cmd+Shift+E` there uses `SET STATISTICS PROFILE`, the
  statement rolled back with SQL Server's own `SAVE TRANSACTION` / `ROLLBACK TRANSACTION` (or
  `BEGIN TRANSACTION` / `ROLLBACK`), and in Oracle's dialect says `not_supported`. The plan view
  reads all four answers into its tree: Oracle's rows by their indent, with `Rows`, `Cost` and the
  `Predicate Information` lines when present; SQL Server's statement row as the root and each
  `PLAN_ROW` under its `Parent`, named `<PhysicalOp> <object>` with the table taken from
  `OBJECT:(…)`; `SHOWPLAN_TEXT` by its five-column `|--` levels. A hovered node fills `bg2`; its
  tooltip (operation, second row and the engine's lines, wrapped at 480 px) shows after 600 ms of
  rest or at once with `Ctrl/Cmd+Shift+Space`, and `Esc` hides it; a click selects as `Enter`
  does (`docs/ux/workspace.md` 5.4).
- **Per-step times in `EXPLAIN ANALYZE`.** The executor measures the steps it can attribute
  and `EXPLAIN ANALYZE` prints PostgreSQL's `(actual time=a..b rows=n loops=1)` on each of them,
  which the desktop client's plan view reads into its own time and share per node: the top
  node (the statement's rows), a scan, the top of a join, a `Sort` (starting when its input
  ends, with the rows it handed up) and each branch of an `Append`. Times are milliseconds from
  the start of execution to the step's first and last row, so a step ends no earlier than the
  steps under it, as PostgreSQL's inclusive times do. A step the executor never read (a scan
  under `LIMIT 0`) says `(never executed)`. A scan that is itself the top node (a `SELECT`
  with `OFFSET` and no `LIMIT`, which has no `Limit` node) carries the rows it handed up, the
  skipped ones included, not the statement's. The timing costs nothing when nobody analyzes: a
  `SELECT` asks a thread-local recording for a meter once (`step_times::claim`), and only
  under `EXPLAIN ANALYZE` of a `SELECT` is there one, given to the outermost select, never to
  a select running inside it; rows are then counted as the source hands them on, and the clock
  is read at the first row and at the end, not per row.
- **Bounded and panic-free.** Depth in `DISPLAY` is cut at 64 spaces, numbers convert with
  saturation, and every malformed `EXPLAIN PLAN` or `SET` form is a parse error.
