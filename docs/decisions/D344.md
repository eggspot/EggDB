## D344 PostgreSQL's `aclexplode`, `acldefault`, `makeaclitem` and `aclitem` input, `has_type_privilege`, `has_tablespace_privilege`, `has_server_privilege`, `has_foreign_data_wrapper_privilege` and `has_parameter_privilege`, `information_schema.routine_privileges`, `udt_privileges`, `enabled_roles` and `applicable_roles`, and `pg_namespace.nspacl`, all answered from the grant model the engine enforces — Decided by the build loop (batch 6, part P9, 2026-11-10); roadmap M6b, finishes D326's "Left" privilege catalog items, applies D9, D12, D35

D326 answered the main privilege inquiry functions and the standard's table and column privilege
views from the grants statements are checked with, and left the rest of that surface: tools still
got `true` from `has_type_privilege` and `has_tablespace_privilege` for every role, an error from
`has_server_privilege`, `has_parameter_privilege`, `aclexplode`, `acldefault` and `makeaclitem`,
no `routine_privileges`, `udt_privileges`, `enabled_roles` or `applicable_roles`, and NULL in
`pg_namespace.nspacl`. pgAdmin and DBeaver read ACLs through `aclexplode(coalesce(acl,
acldefault(...)))`, psql's `\dn+` shows `nspacl`, and ORMs and agents ask `enabled_roles` which
roles a session acts as. Built from PostgreSQL 16's manual: "Access Privilege Inquiry
Functions" and "System Catalog Information Functions" (functions-info), "Privileges" (ddl-priv,
with its table of privilege abbreviations and default privileges), and the `information_schema`
chapters on `routine_privileges`, `udt_privileges`, `enabled_roles` and `applicable_roles`.

- **The rest of the inquiry functions.** Each takes the role by name, OID or `public` (or uses
  the current user), the object by name or OID, and PostgreSQL's privilege list (comma-separated,
  any case, each optionally ` WITH GRANT OPTION`), with errors in PostgreSQL's order and codes:
  - `has_type_privilege` (`USAGE`): a type named as `regtype` reads it, built-in or user-defined
    (an enum, domain, range or composite type on the search path or qualified), `42704 type "x"
    does not exist` otherwise. Every role holds `USAGE` on every type, as PostgreSQL grants it
    to `PUBLIC` by default and EggDB checks no type use.
  - `has_tablespace_privilege` (`CREATE`): `pg_default` and `pg_global`, `42704 tablespace "x"
    does not exist` otherwise. Only superusers hold `CREATE`, as only they create objects
    (D326's `may_define_objects`); PostgreSQL's tablespaces grant `PUBLIC` nothing either.
  - `has_server_privilege` and `has_foreign_data_wrapper_privilege` (`USAGE`): EggDB has no
    foreign servers or wrappers, so a name is `42704 server "x" does not exist` (or
    `foreign-data wrapper "x" does not exist`) and an OID gives NULL.
  - `has_parameter_privilege` (`SET`, `ALTER SYSTEM`): any parameter name, as PostgreSQL takes
    any name; superusers hold both, and other roles neither, since no `GRANT SET ON PARAMETER`
    is stored (PostgreSQL also answers false for a role without such a grant, even for a
    parameter any session may set).
  A superuser holds every privilege with its grant option; a checked role never holds a grant
  option, as D326 says. The functions load the catalog snapshot as their siblings do.
- **`aclitem` values.** EggDB keeps an `aclitem` as PostgreSQL's output text
  (`grantee=privileges/grantor`, `PUBLIC` as an empty grantee, `*` after a privilege held with
  its grant option, names in double quotes when they hold anything but ASCII letters, digits and
  `_`). Input text (a cast to `aclitem`, the items of an `aclitem[]` given to `aclexplode`) is
  read as PostgreSQL's `aclitemin` reads it: white space around names, `""` inside quotes, the
  old `group` and `user` key words, a missing grantor meaning the session's user (OID 10), and
  PostgreSQL's errors: `22P02` for `missing "=" sign`, `invalid mode character: must be one of
  "arwdDxtXUCTcsA"` (PostgreSQL 16's letters, as `relacl` already uses), `a name must follow the
  "/" sign`, `unrecognized key word` and `extra garbage at the end of the ACL specification`;
  `42622 identifier too long` past 63 bytes; `42704 role "x" does not exist`. The parser works
  on `char_indices` and `get` (no indexing that input can make panic) and is checked by a
  randomized test.
- **`aclexplode(aclitem[])`** is a set-returning function with PostgreSQL's columns `grantor`
  and `grantee` (`oid`, 0 for `PUBLIC`), `privilege_type` (`INSERT`, `SELECT`, ... `ALTER
  SYSTEM`) and `is_grantable`, one row per privilege of each item in the order of PostgreSQL's
  privilege bits. It works in `FROM` (`SELECT * FROM aclexplode(relacl)`) and in a select list,
  where each row is a record with those field names. A NULL list gives no rows; a NULL item is
  `22004 ACL arrays must not contain null values`. Role names map to OIDs as `pg_roles` lists
  them (the session's user 10, predefined roles their own, stored roles their hashed OID); a name
  of digits that names no role is read as the OID it is, so `aclexplode` reads back what
  `acldefault` writes for an OID without a role (PostgreSQL never meets that case, as its
  `aclitem` is binary).
- **`acldefault("char", owner)`** returns PostgreSQL 16's default ACL for the object kinds of
  the manual's table (`c`, `r`, `s`, `d`, `f`, `l`, `L`, `n`, `p`, `t`, `F`, `S`, `T`), the
  `PUBLIC` item first and then the owner's, as PostgreSQL builds it (`{=X/eggdb,eggdb=X/eggdb}`
  for a function, `{}` for a column), and `XX000 unrecognized object type abbreviation` for
  another letter. **`makeaclitem(grantee, grantor, privileges, grantable)`** takes PostgreSQL
  16's comma-separated list (`TEMP` and `TEMPORARY` alike, `RULE` ignored, `22023
  unrecognized privilege type` otherwise); `grantable` gives every listed privilege its grant
  option.
- **`pg_namespace.nspacl`** writes what the engine enforces on each schema, since schema grants
  are not stored yet (D326): the owner holds `USAGE` and `CREATE` and `PUBLIC` holds `USAGE`,
  so `public` shows `{pg_database_owner=UC/pg_database_owner,=U/pg_database_owner}` exactly as
  on PostgreSQL 15 and later, `pg_catalog` and `information_schema` show PostgreSQL's
  `{eggdb=UC/eggdb,=U/eggdb}`, and `pg_toast` keeps PostgreSQL's NULL. A schema a user creates
  shows the same two items instead of PostgreSQL's NULL, because PostgreSQL's NULL means "the
  owner only" (`acldefault('n', owner)`) and EggDB lets every role use every schema: a tool that
  reads the ACL then agrees with `has_schema_privilege`.
- **The four views**, filtered as the standard and PostgreSQL filter them and as D326's views
  are: a superuser session is the grantor of everything and sees every row, a checked role sees
  rows whose grantee is itself, a role it belongs to, or `PUBLIC`.
  - `enabled_roles`: the current user and every role it belongs to, at any depth (D326's
    `role_closure`); a superuser session uses every role (`pg_has_role` is true for all), so it
    lists every role `pg_roles` lists.
  - `applicable_roles`: each stored membership whose member is an enabled role, with
    `is_grantable` `NO` (no `ADMIN OPTION` is stored); a superuser session also sees the database
    owner's implicit membership in `pg_database_owner`, as PostgreSQL's view adds it.
  - `routine_privileges`: `EXECUTE` held by `PUBLIC` on every routine `information_schema.routines`
    lists (PostgreSQL's default, and EggDB does not check calls), and for a superuser session
    also the owner's own `EXECUTE` with `is_grantable` `YES`, in `aclexplode(acldefault('f',
    proowner))`'s order. A checked role is not shown the owner's row: under D326's convention the
    session's user is the displayed owner, and telling a checked role it may grant would be
    wrong.
  - `udt_privileges`: the same for `TYPE USAGE` on composite types (PostgreSQL's view selects
    `typtype = 'c'`; EggDB has no row types of tables in `pg_type` yet).

Decided by research (from PostgreSQL's documentation and the repo's decisions):
- **The engine's model, not PostgreSQL's defaults, where they differ.** Every answer is what a
  statement of that role would be allowed (D326's rule): a role is told `true` only where the
  engine lets it act. Where the engine is more permissive than PostgreSQL's default (schema
  `USAGE` for every role), the catalog shows the engine's rule (`nspacl`), so the inquiry
  functions and the ACL columns never disagree.
- **No new storage.** Nothing here writes or reads a new record: parameter, type, tablespace and
  schema grants stay unstored (D326's "Left"), and the answers change when they are stored.
- **`aclitem` stays text.** Keeping the output text as the stored form (as D326's `relacl` does)
  avoids a second representation; input is parsed and written back in canonical form.

Security review: everything here only reads. Every checked-role answer is false for grant
options, tablespace `CREATE` and parameters, and true only for type `USAGE` and the defaults
every role already holds, matching what statements allow. The views add no grant a role cannot
already see through D326's views or `pg_roles`; memberships of other roles are hidden from a
checked role. The `aclitem` parser takes client text, never indexes or slices by byte position,
bounds names at 63 bytes, and is run over 20,000 random inputs.

Test vectors (`crates/eggdb-sql/src/pg_catalog/privilege_tests.rs`, the `functions-info`
chapter of `crates/eggdb-sql/correctness/postgresql.test`): the manual's default-privilege table
through `acldefault` for every kind, `makeaclitem` with lists, `RULE` and grant options,
`aclexplode` over `relacl`, `acldefault` and literal lists in `FROM` and in a select list, NULL
lists and items, `aclitem` input with quoted names, key words and each error, types by name and
OID including user-defined ones, tablespaces, servers, wrappers and parameters for superusers,
checked roles and `public`, `nspacl` of system and user schemas, and the four views seen by a
superuser and by a checked role.

Left: storing schema, type, routine, parameter (`GRANT SET ON PARAMETER`) and tablespace
privileges and `WITH GRANT OPTION` (then these answers and `nspacl` follow them), foreign servers
and wrappers, `information_schema.role_routine_grants` and `role_udt_grants`, and a column type
known before the query runs for a field of a select-list `aclexplode` record
(`(aclexplode(acl)).privilege_type`).
