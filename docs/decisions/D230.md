## D230 Build profiles are measured artifacts first; the server/full split of the binary follows — Decided by the build loop (by judgement, 2026-10-31); refines D6, D14 and D34

Track 4.X-1 asks for `embedded`, `server` and `full` profiles, each one binary, with budgets
measured per profile.

- **Two profiles exist as artifacts today.** `embedded` is the C API library (`libeggdb_capi`)
  and the WebAssembly module (`eggdb-wasm`). The linker keeps only the code their exports reach,
  so no protocol server is in them. `full` is the `eggdb` binary, which serves every protocol.
  `scripts/footprint.sh` builds them in release, strips them, and reports each size per system
  against its line in `benchmarks/footprint.txt`. CI runs it on Linux and macOS. A size over its
  budget fails until the budget is raised in the same PR with the reason (D6). `--update`
  rewrites the system's lines after a deliberate change, as the benchmark baseline does (D80).
- **`server` needs the binary split.** A server without the GUI, MCP and the less common
  protocols means a Cargo feature on `eggdb` for each listener group, and gating the `serve`
  options and their wiring. That touches every listener, so it is its own change, made once the
  listener list settles. Until then `server` is measured as `full`.

Left: the `server` feature split, budgets for idle memory and first start per profile (D14's
installers job measures them for `full`), and a microcontroller profile once the engine builds
without `std` (D223).
