## D1045 Rebalancing simulated under load, partitions, clock skew and node failures — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D18, D212)

- `eggdb_cluster::simulation::simulate_rebalancing` runs a seeded world: clients write keys routed with a map they
  refresh only when refused; nodes join, are decommissioned (they leave the placement but keep serving until their
  shards are moved off), crash and come back with their data, get cut off by partitions, and have clocks offset by up
  to ±300 ms with 250 ms allowed between nodes. Every 25 steps `rebalance` (D212) plans moves, and each move runs
  `ShardMove`'s steps (D1040's protocol): copy, catch up the keys written meanwhile, cut over.
- The model keeps the rules the real moves keep: a node accepts a write only with the current epoch for a shard its
  own view of the map gives it; a cut-over needs both the old and the new owner reachable, and both adopt the new map
  in the same step, so no node is left believing it owns a shard it lost; a move whose node fails or is cut off is
  given up (and its partial copy dropped) rather than waited on forever; a new owner takes in the old owner's
  timestamps through its hybrid clock (D1042) and gives the move up when they are further ahead than allowed.
- Checked properties: no acknowledged write is missing from its shard's owner at the end; no node ever accepted a
  write for a shard the authoritative map did not give it; after the faults heal, the shards end within one of even
  across the members. The test runs 25 seeds and also requires moves to have completed and clock refusals to have
  happened, so the faults are exercised.
- Learned from the deterministic-simulation testing descriptions D211 already follows (FoundationDB's); no code was
  read.
