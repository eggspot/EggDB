## D162 Live copies with `eggdb follow`: PostgreSQL through logical replication (`pgoutput`) from a temporary slot's snapshot, SQL Server through change tracking polls, with our own clients — Decided by the build loop (by judgement, 2026-10-31)

Parts 3.17 and 3.18 let users move a running database to EggDB with no downtime (D13's "follow a
live database through its replication or change stream"). Both need a client of the source's
protocol, which EggDB now has: `eggdb_pgwire::client` (TLS, SCRAM-SHA-256 and `-PLUS`, simple
queries, `COPY TO STDOUT` and copy-both streams) and `eggdb_tdswire::client` (PRELOGIN
encryption, TDS 8 strict, SQL logins, batches). Both are written from the protocols' public
documentation, as D1 requires. TLS comes from D161.

**PostgreSQL.**
- `follow` creates the publication, unless `--publication` names one. It then opens a
  replication connection and runs `CREATE_REPLICATION_SLOT … TEMPORARY LOGICAL pgoutput
  EXPORT_SNAPSHOT`. This is the legacy syntax, so PostgreSQL 10 and later accept it.
- It reads the catalog and the rows in a `REPEATABLE READ` transaction set to the exported
  snapshot. The schema is built from `pg_attribute` (`format_type`, defaults, identity) and
  `pg_constraint` (`pg_get_constraintdef`): primary, unique and check constraints at creation,
  foreign keys and other indexes after the rows. Rows move with `COPY … TO STDOUT` into EggDB's
  `COPY … FROM STDIN`.
- Then it runs `START_REPLICATION` with `pgoutput` protocol 1 from the slot's consistent point.
  Each source transaction is applied as one EggDB transaction of generated SQL, keyed by the
  replica identity.
- It reports its position in standby status updates. A keepalive outside a transaction counts as
  applied up to the server's WAL end, because logical decoding has sent everything committed
  before it. That is also what `--until caught-up` waits for.
- Sequences are copied at creation and again at the stop, since the stream does not carry them.
- The slot is temporary: a lost connection ends the follow with exit 3, and nothing is resumed
  silently. A publication EggDB created is dropped at the stop.

**SQL Server.**
- Change tracking is required (`sys.change_tracking_databases`, `sys.change_tracking_tables`).
  EggDB's own TDS server has no change tracking, so its "Invalid object name" counts as "change
  tracking is off".
- The tables are created from `INFORMATION_SCHEMA` with SQL Server's types. The current change
  version is read before the rows are copied.
- Every `--poll` seconds it applies `CHANGETABLE(CHANGES …)` up to the then-current version, as
  a delete then an insert of the current row by primary key. That is idempotent, so changes made
  during the copy are safe to apply twice.
- Every value travels as `nvarchar(max)`, converted on the server: binary with style 1, dates and
  times with 126, float with 3, money with 2. The client therefore decodes only `nvarchar`.
- CDC is not read yet.

**Not done.** Logical replication protocol 2 (streamed large transactions), binary tuples, DDL
changes during a follow, resuming after a lost connection, and user-defined types beyond those
EggDB has (D152).
