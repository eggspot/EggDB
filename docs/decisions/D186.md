## D186 Row-level security: PostgreSQL's policies stored per table and applied where names are resolved — Decided by the build loop (by judgement, 2026-10-31); refines D22 and D183; security-critical (D35)

Part 4.M6b-2 asks for row policies, column privileges and dynamic masking.

- **PostgreSQL's model and syntax**: `ALTER TABLE t ENABLE|DISABLE ROW LEVEL SECURITY`, `CREATE
  POLICY name ON t [AS PERMISSIVE|RESTRICTIVE] [FOR ALL|SELECT|INSERT|UPDATE|DELETE] [TO roles]
  [USING (...)] [WITH CHECK (...)]` and `DROP POLICY [IF EXISTS]`. Policies are catalog records
  (key space `0x13`, one per table and policy, the conditions kept as SQL text) and the switch is
  a record of its own (`0x14`); both go with the table when it is dropped, as its grants do now.
- **Applied to checked roles only** (D183): superusers, embedded sessions and the server's own
  user bypass row security, as PostgreSQL's superusers and `BYPASSRLS` roles do. A checked role
  on a table with row security sees the rows that pass the `OR` of its permissive policies'
  `USING` and the `AND` of its restrictive ones; with no policy for it, no rows (default deny).
- **Where**: a read of the table becomes a query over it filtered by the policies, expanded the
  way a view is, so joins, subqueries and views all see the filtered rows; `UPDATE` and
  `DELETE` add the condition to their `WHERE`. `COPY t TO` is refused under row security (`COPY
  (SELECT ...) TO` applies it), and `MERGE` is refused.
- **New rows**: `WITH CHECK` conditions are not evaluated yet, so `INSERT`, `UPDATE` and `COPY
  FROM` under row security are allowed only when every applicable policy says `WITH CHECK
  (true)`; otherwise they fail with `42501`, which is safe rather than permissive.

Left: evaluating `WITH CHECK` on new rows, `FORCE ROW LEVEL SECURITY` (needs owners), column
privileges, dynamic data masking (SQL Server's `MASKED WITH`), Oracle VPD and SQL Server security
predicates, and `pg_policy`/`pg_policies` in the catalog.
