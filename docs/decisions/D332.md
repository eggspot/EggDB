## D332 Oracle's analytic functions run on the shared window code with `IGNORE NULLS` and `FROM LAST` in the window call, `RATIO_TO_REPORT` and `KEEP` are rewritten onto window and array aggregates, and Oracle's `REGEXP_*` take the leftmost match the pattern finds first — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M10, extends D151, D130 and D300, applies D9 and D10

Oracle's dialect answered `ROW_NUMBER`, `RANK`, `LAG` and the other window functions with
`ORA-00904`, and had no `REGEXP_*`, `RATIO_TO_REPORT` or `KEEP`. Each is built from Oracle's SQL
Language Reference (23ai): "Analytic Functions", the pages of each function, "Aggregate
Functions" (`FIRST`, `LAST`) and "Oracle Regular Expression Support" (Appendix D).

- **Window functions.** The eleven window functions and every aggregate with `OVER` are the
  same `window_call` as in the other dialects (D151), parsed by Oracle's own call reader
  (`parser::oracle`, `oracle_analytic_function`). Oracle's options for `LAG`, `LEAD`,
  `FIRST_VALUE`, `LAST_VALUE` and `NTH_VALUE` become a `ValueTreatment` (`ignore_nulls`,
  `from_last`) carried in the call's encoded function name (`"lag ignore nulls"`, `"nth_value
  from last"`), so the window header keeps its nine slots and named windows, `EXPLAIN` and the
  split into inner select items are unchanged. `IGNORE NULLS` makes `LAG` and `LEAD` count only
  rows whose value is not NULL (an offset of 0 is the row itself), and makes the frame of
  `FIRST_VALUE`, `LAST_VALUE` and `NTH_VALUE` skip those rows; `FROM LAST` counts `NTH_VALUE`'s
  `n` back from the frame's end. `IGNORE NULLS` is read both inside the parentheses after the
  first argument and after them, as the reference's two syntax diagrams allow. Oracle's errors:
  `ORA-30485` for a ranking function, `NTILE`, `LAG` or `LEAD` whose inline window has no `ORDER
  BY`, `ORA-30484` without `OVER`, `ORA-00909` for the wrong number of arguments.
- **`RATIO_TO_REPORT(expr) OVER ([PARTITION BY ...])`** is `expr / NULLIF(SUM(expr) OVER (same
  partition, whole frame), 0)` with Oracle's division, built with D300's whole-partition window
  (now `parser::windows::whole_partition_call`, shared with analytic `LISTAGG`). `ORDER BY` in
  its `OVER` is `ORA-30487`.
- **`aggregate KEEP (DENSE_RANK FIRST | LAST ORDER BY ...) [OVER ([PARTITION BY ...])]`** for
  `MIN`, `MAX`, `SUM`, `AVG`, `COUNT` (with `*`), `VARIANCE`, `STDDEV` and their `_SAMP` and
  `_POP` forms. The parser writes one ordered array aggregate per value and per `ORDER BY` key
  (D149's array aggregate with the aggregate `ORDER BY`, or the whole-partition window with that
  order under `OVER`), so every array is sorted the same way, and `oracle_keep` takes the run of
  equal keys at the start (`FIRST`) or the end (`LAST`), NULL keys equal to each other, and feeds
  those values to the grouping code's own accumulator (`WindowAggregate`), so the aggregate's
  result type and rules are the plain aggregate's. No new executor path or aggregate state.
- **`REGEXP_LIKE`, `REGEXP_COUNT`, `REGEXP_INSTR`, `REGEXP_SUBSTR`, `REGEXP_REPLACE`** with
  Oracle's arguments in Oracle's order (`oracle_regexp`), on D128's pattern parser and D130's
  backtracking search. Oracle's defaults differ from PostgreSQL's: `.` does not match a newline
  unless `match_parameter` has `n`, `m` makes `^` and `$` match at lines, `x` ignores spaces,
  `i`/`c` set the case (the last wins), any other letter is `ORA-01760`; `REGEXP_REPLACE`'s
  `occurrence` defaults to 0, every match; a missing `replace_string` deletes the matches; an
  empty source, pattern or result is NULL; a position or occurrence below 1 (below 0 for
  `REGEXP_REPLACE`'s occurrence), a negative `return_option` or a subexpression outside 0 to 9
  is `ORA-01428`; a subexpression the pattern does not have gives NULL or 0.

**Decided by research.** *Which match does Oracle return: POSIX's leftmost-longest or the first
the pattern finds?* Appendix D says the engine follows POSIX ERE with Perl-influenced
extensions (lazy quantifiers, `\d`, `\w`, `\s`), but Oracle's engine is a backtracking one: it
tries alternatives in order and takes the first that matches at the leftmost position
(regular-expressions.info's Oracle page, and Oracle's lazy quantifiers, which only make sense in
that model). So a new `leftmost_first` option in `regex::Options` makes the search stop at the
first path that reaches the end of the pattern in priority order (alternatives left to right,
greedy quantifiers longest first, lazy ones shortest first) instead of PostgreSQL's longest or
shortest match there: `REGEXP_SUBSTR('ab', 'a|ab')` is `a`, where PostgreSQL's
`regexp_substr` gives `ab`. The memo of D130 still bounds the search, since a state that failed
once fails from every start. *What does `RATIO_TO_REPORT` give when the partition sums to 0?*
The reference documents only the NULL case; NULL was chosen over `ORA-01476`, as the function
reports shares and gives NULL wherever the share is undefined. *What does `REGEXP_REPLACE` give
for a NULL pattern?* The source, as `REPLACE` does for a NULL search string. *`QUALIFY`?* D240
names Snowflake, GoogleSQL and Spark SQL; none of EggDB's five dialects has the clause, and in
each of them `FROM t qualify` already reads `qualify` as a table alias, so adding it to one
would change how existing queries parse. It waits for the first of those dialects, as D240
plans.

Left: `QUALIFY` (with the first dialect that has it, D240); `DISTINCT` in window aggregates
(`LISTAGG (DISTINCT ...) OVER`, `COUNT(DISTINCT x) OVER`); `KEEP` on `LISTAGG`; Oracle's window
`RANGE` offsets that are intervals over dates checked against Oracle's rules; negated bracket
expressions that still match a newline without `n` (the search excludes it from `.` and from
`[^...]` together); `\z`, `[=e=]` and `[.ch.]`; and `x` treating `#` as a comment as PostgreSQL's
expanded syntax does.
