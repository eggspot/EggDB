## D351 Cypher label predicates in expressions (`n:A:B`, `n:A|B`, `r:T|U`, and `(n:A|B)` in `MATCH` patterns), `CALL { ... }` subqueries run row by row, `shortestPath()` and `allShortestPaths()` as expressions, and `MERGE` refusing a null property value — Decided by the build loop (batch 6, 2026-11-10); roadmap M13, extends D206 and D333

D333 left four parts of Cypher out: label predicates in expressions, `CALL {}` subqueries,
`shortestPath()` outside `MATCH`, and the error `MERGE` answers for a null property value. Each is
built from the openCypher 9 reference (the Apache-licensed language documents) and the behaviour
Neo4j's Cypher manual documents for it; no Neo4j code is used or read. The tests are the manual's
examples (the Alice, Bob, Charlie and Dora graph with its `:Counter` node for subqueries, the
movie graph for shortest paths).

- **Label predicates.** `n:A` is true when the node has the label, `n:A:B` when it has all of them
  and `n:A|B` when it has any of them (Neo4j 5's label expressions); on a relationship they test
  its type, so `r:T|U` is true for a `T` or `U` relationship and `r:T:U` is never true. A null
  value gives null, any other value is a `TypeError`. The predicate binds after property lookups
  and before every operator, as openCypher's grammar places it (`NOT n:A`, `n:A AND m:B`).
  Mixing the two symbols (`:A:B|C`, `:A|B:C`, `:A|:B`) is Neo4j's `SyntaxError` "Mixing label
  expression symbols ('|', '&', '!', and '%') with colon (':') is not allowed. Please only use
  one set of symbols." `&`, `!` and `%` are not parsed yet.
- **Where `|` belongs.** A `|` after a label continues the label expression when a label name
  follows it, except in the three places where a `|` also ends what comes before it: a list
  comprehension's `IN` list and `WHERE` predicate, a pattern comprehension's `WHERE` predicate and
  `FOREACH`'s `IN` list, each at its own bracket level. There the `|` always ends that part, so
  `[x IN xs WHERE x:A | x.name]` maps the nodes labelled `A` to their names, and a disjunction is
  written in parentheses: `[x IN xs WHERE (x:A|B) | x.name]`. Inside any bracket, parenthesis,
  map or `CASE` nested in those parts, and in a comprehension's mapping, `|` is the label
  disjunction again (`[x IN xs | x:A|B]`). The rule needs no backtracking and no look-ahead past
  one token, and it never reads a mapping as a label: `[x IN xs WHERE x:A|B | x.name]` is a
  `SyntaxError` rather than a guess.
- **Label alternatives in patterns are supported** in `MATCH`, `OPTIONAL MATCH`, pattern
  comprehensions and shortest paths: `(n:A|B)` matches a node with either label, as Neo4j 5 does;
  `[r:T|U]` already matched either type (D206). `CREATE` and `MERGE` need a node's labels joined
  with `:`, so `(n:A|B)` there is a `SyntaxError` before anything runs.
- **`CALL { ... }` subqueries** run once for each incoming row, in the query's one transaction.
  An importing `WITH a, b` as the subquery's first clause brings outer variables in (`WITH *`
  brings all of them); other outer variables are not visible inside. An importing `WITH` that
  aliases (`WITH a AS b`) or has `DISTINCT`, `ORDER BY`, `SKIP`, `LIMIT` or `WHERE` is Neo4j's
  `SemanticError` "Importing WITH should consist only of simple references to outside
  variables. ..."; a first `WITH` whose items are not plain variables (`WITH 1 AS x`) is an
  ordinary `WITH`. A subquery that ends in `RETURN` adds its columns to each outer row, one outer
  row for each row it returns (none drops the row); a returned name that is already an outer
  variable is the `SemanticError` "Variable `x` already declared in outer scope". A unit
  subquery (one that writes and has no `RETURN`) passes each outer row through, refreshed after
  its writes. `UNION` and `UNION ALL` work inside, each part with its own importing `WITH`, and
  subqueries nest. `Clause::writes()` looks inside a subquery, so a query whose only write is in
  a subquery needs write access (`AccessMode` in read mode) and runs in a write transaction.
  `CALL { ... } IN TRANSACTIONS` is refused with `FeatureNotSupported` (a query is one
  transaction here), and a subquery inside `FOREACH` is the `SyntaxError` Neo4j gives for a
  reading clause there. The rows one subquery clause produces are bounded by D206's row cap.
- **`shortestPath()` and `allShortestPaths()` as expressions** (`RETURN length(shortestPath((a)-[*]-(b)))`,
  `WHERE shortestPath(...) IS NOT NULL`) run the same bounded breadth-first search as in `MATCH`
  (D333, the same per-query budgets) and give the path or null, and the list of paths (empty when
  none). Both end nodes must be variables bound by earlier clauses (a `SemanticError` otherwise);
  an end bound to null gives null.
- **`MERGE` with a null property value** fails before it matches or creates anything with
  Neo4j's `SemanticError` "Cannot merge the following node because of null property value for
  'x': (:L {x: null})", and for a relationship "Cannot merge the following relationship because
  of null property value for 'x': ()-[:R {x: null}]->()", whether the null is written in the
  query or comes from a `$parameter`. A null never equals anything, so such a pattern could never
  match and every run would create a new element; Neo4j refuses it for that reason.

Decided by judgement (recorded for review):
- The `|` rule above follows the plan review's rule (the disjunction binds only after `:` when a
  label name follows) and adds the parenthesis requirement in the three `|`-ended places, because
  any look-ahead rule there either reads `[x IN xs WHERE x:A | y]` as a label `y` or misreads
  `[x IN xs WHERE x:A|B]`; a rule that is sometimes wrong silently is worse than one that asks
  for parentheses.
- The outer-variable clash is checked against each outer row when the subquery runs rather than
  by a scope analysis at parse time, because the parser keeps no scopes; a query whose outer
  clauses produce no rows does not report the clash.

Left: the `CALL (a, b) { ... }` variable-scope form (Neo4j 5.23), `CALL { ... } IN TRANSACTIONS`,
the label-expression operators `&`, `!` and `%`, and `FINISH`.
