## D366 A partition's primary key attached to its parent's — Decided by the code-only session (2026-11-10, D355); closes one of D316's leftovers, with its D35 note

D316 linked partition indexes to their parent's by index id, but primary keys have no index id,
so `ALTER INDEX parent_pkey ATTACH PARTITION part_pkey` was accepted and linked nothing, and
`pg_inherits`, `relispartition` and `pg_partition_tree` (D365) never showed primary keys.

- **The link.** A primary key takes the reserved id `u32::MAX` (`PRIMARY_KEY_LINK`) in the
  partition record's index links, which no index id reaches. A partition whose primary key has
  the same column names, in order, as its parent's is linked when it is created or attached
  (`reach_partition`), when an older file's links are built (`unique_index_links`), and by
  `ALTER INDEX parent_pkey ATTACH PARTITION part_pkey`, which now refuses keys that differ
  (`cannot attach index`, "The index definitions do not match.").
- **Catalogs.** `pg_inherits` lists the pair, the partition's key has `relispartition`, and the
  partition tree functions follow it.
- **Stale links.** A link whose table lost its primary key is dropped when the catalog loads,
  as for a dropped index.

**D35 note.** No version changes: index links were already varint pairs. An older release
reading a file with such a link finds no index with that id and drops the link in memory when
it loads the catalog, so it reads the file as before this decision.

**Left:** dropping an attached partition's primary key (`2BP01` in PostgreSQL) is not refused.

**Status:** code written, unbuilt (code-only mode, D355).
