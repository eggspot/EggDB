## D139 Collections: named key spaces as key prefixes in the file's one tree, with a catalog of names to never-reused numbers, hidden from and refused by the default key space; eggdb-jsonl version 2; the CLI, the shell and the UI as Claude Fable designed them — Decided by the build loop (by research, 2026-10-30); roadmap item 26, supersedes in part D87 (item 9) and D98 (decision 2), applies D2, D9, D15, D20, D35, D87, D90, D93, D96

Item 26 lets one file hold several named key spaces beside the default one, each its own ordered
map of byte-string keys to byte-string values, through the embedded API, the command line, the
shell and the terminal UI.

**Key prefixes, not trees of their own.** D87 planned collections as trees named in the catalog
tree, behind an incompatible feature flag. They are key prefixes in the file's one B+tree
instead: every key that starts with `0xff 'C' 'O' 'L' 0x00` belongs to them. Below that prefix,
`0x01` is the catalog (a version byte and the next collection number), `0x02` + name maps a name
to a version byte and its 4-byte big-endian number, and `0x03` + number + key holds that
collection's entries (format.md "Keys and trees"). *Why:* the catalog tree and multi-tree
transactions do not exist yet, and a feature flag would make every older release refuse a file
the moment it gains a collection; prefixes need no change to the page format, the log, the
checker or the sample files, keep one transaction over any number of collections for free, and
cost almost nothing per key thanks to B+tree prefix truncation (D82). *Costs:* a collection's
keys are ten bytes shorter than the default key space's (502 with 4 KiB pages), and dropping a
collection deletes its keys one by one in one transaction, so a collection that changes more
pages than the page cache holds fails with `CacheFull` (a larger `--cache` fixes it). Numbers
are never reused, so a key a crash or a bug might leave of a dropped collection is never read
as a key of a later one. When the catalog tree arrives (M2), a later decision can move a
collection into a tree of its own without changing the API.

**The default key space hides them.** Its scans skip the reserved prefix (a scan whose range
spans it reads two key ranges, below and above, so no key of a collection is ever read), its
`get` and `delete` never see such keys, and its `put` and `put_if_absent` refuse them with the
new `ErrorKind::ReservedKey`, so no write through the default key space can damage a
collection. SQL keeps its own prefix in the default key space (`0xff 'S' 'Q' 'L' 0x00`, D98) and
stays visible to scans as before; D98's plan to move SQL into a collection named `sql` is not
done (SQL in collections is later work), which supersedes that part of D98.

**API.** `Database::create_collection`, `drop_collection` (each one commit, returning whether
anything changed), `collection_names`, `max_collection_key_bytes` and `collection(name)`, a
`Collection` whose `get`, `put` and `delete` are one-step transactions;
`ReadTransaction::collection` and `WriteTransaction::collection` give a `ReadCollection` or a
`WriteCollection` with the default key space's method names, as D87 item 9 promised, plus
`create_collection`, `drop_collection` and `collection_names` on the transactions. A missing
collection is an error (`ErrorKind::CollectionNotFound`), never an empty map, so a typo cannot
read as "no data"; a name that cannot be one is `InvalidCollectionName`. Names are 1 to 128
bytes of UTF-8 without whitespace or control characters, so they print as text everywhere and
the label `default key space` can never be one.

**Command line, shell and UI** follow Claude Fable's design (D15; ux/cli.md section 20, ux/ui.md
"Collections"): `eggdb collection list|add|delete <file> [name]`; `-C`/`--collection` on `get`,
`put`, `del`, `scan`, `export` and `import`; a missing collection exits 1 with the command that
adds it, and `put --create -C` and `import -C` make it; eggdb-jsonl version 2, written only for
files with collections, tags entries with a `collection` field and keeps empty collections as
collection lines (`export -C` writes a plain version 1, `import -C` loads everything into one
collection); `.collection` in the shell with the choice in the prompt; the `C` picker in the UI,
which also adds collections because the UI holds the file's lock, the sidebar from 110 columns,
`Keys in <name>` and an `In collection` line in the confirmations.

**Decided by research while building** (recorded in the batch plan): the picker's letters `j`,
`k`, `a`, `C`, `g`, `G` and `q` are commands, so typing to narrow the list is left out; the
"collection dropped by another program" warnings of the design are left out, since the shell and
the UI hold the file's lock (a writer excludes every other open, a read-only open excludes
writers), so no other program can drop a collection under them; import into one collection with
`-C` checks every key against the collection, so the same key in two sections of a version 2
export follows `--on-conflict` instead of silently keeping the last.

**Tests.** API tests for isolation across reopens, ranges, prefixes and both ends of a scan
inside a collection, the default key space's scans across the reserved prefix, reserved keys,
rollback of a create, drop, names, key limits, snapshots and read-only files, and a model test of
random changes to three key spaces against three maps; a v0.2.0 sample file takes collections
and keeps its entries; eggdb-jsonl version 2 reading and refusals; CLI, shell and UI-scenario
tests, a real-database UI test, and a smoke-test step.
