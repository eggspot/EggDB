## D1095 The whole workspace tested on six other CPUs under QEMU, in shards — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D8, PR #86)

- **CPUs.** 32-bit x86 (natively, with `gcc-multilib`), 32-bit ARM, big-endian s390x, RISC-V 64, POWER little-endian and LoongArch 64, the last five under QEMU's user-mode emulation with Ubuntu's cross GCC as the linker (`gcc-14-loongarch64-linux-gnu` for LoongArch, whose Rust target is tier 2 with host tools). Together they cover 32-bit `usize`, big-endian memory, weak memory ordering (ARM, POWER, RISC-V) and the newest Linux architecture.
- **One script, one table.** `scripts/qemu-test.sh` holds each CPU's Rust target, packages, linker and runner, and runs a shard of tests with `CARGO_TARGET_<TARGET>_LINKER` and `_RUNNER` set, so a developer reproduces a CI failure with one command. The workflow asks the script for the target and packages instead of repeating them.
- **Shards.** Emulated test runs are several times slower, so each CPU runs three shards in parallel jobs: `engine` (format, storage, crypto, columnar, both platform crates, `eggdb`), `sql` (`eggdb-sql`), and `rest` (the workspace minus those). Eighteen jobs run on pushes to `main` only, with a 90-minute ceiling; the public repo pays nothing for them, and pull requests stay fast. The GUI (no display), fuzzing, the benchmarks and the suites that need outside services or data are left out, since emulation adds nothing to what their native runs check.
- **Also fixed.** The root `Cargo.toml` listed `crates/eggdb-platform-core` twice among the workspace members; one entry remains.
