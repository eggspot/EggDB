## D1061 Benchmarks against nats-server and ElasticMQ — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D7, D216)

- `eggdb-broker-compare` (D1056's crate) adds two subcommands.
- `nats` uses a NATS client of the crate's own (`CONNECT`, `PUB`, `SUB`, `MSG`/`HMSG`, `PING`/`PONG`) against
  `eggdb serve --nats-listen` and nats-server 2.10 started with `-js`. It measures three things:
  - Core publishing: 200,000 messages of 100 bytes, a `PING` after every 100, timed per window.
  - One subscriber receiving those messages on a second connection.
  - JetStream publishing: a file-storage stream created through `$JS.API.STREAM.CREATE`, then 20,000 messages
    with at most 100 awaiting their acknowledgement.
- `sqs` uses a client of the AWS JSON 1.0 protocol over one kept-alive HTTP/1.1 connection, against
  `--sqs-listen` and ElasticMQ (`softwaremill/elasticmq-native:1.6.0`). Each request is signed with Signature
  Version 4 through `eggdb_auth::sigv4::authorization`, the crate's first dependency, our own code. ElasticMQ
  does not check signatures.
  - It creates a queue and sends 5,000 messages of 100 bytes, one per request.
  - It then receives them ten at a time and deletes each one.
  - Batch actions wait for D58's legal check (roadmap's SQS line), so neither side is measured with them.
- Both run in CI's `broker-compare` job:
  - ElasticMQ runs as a service container.
  - nats-server is started with `docker run`, because a service container cannot be given `-js`.
  - EggDB's broker gains `--nats-listen 127.0.0.1:14222 --sqs-listen 127.0.0.1:19324`.
  - The results are uploaded with the other broker comparisons. They are reported, not gated, as D1056 says.
- Learned from: the public NATS client protocol and JetStream API documentation, and the public SQS API
  reference (AWS JSON 1.0). No ElasticMQ or nats-server source was read.
