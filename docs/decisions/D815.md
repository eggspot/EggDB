## D815 Server events in the chained audit log — Decided by the code-only session (2026-11-12, D355); roadmap D26, D231

- `eggdb_sql::audit_events` carries server events to a sink the program installs once (`set_audit_sink`, as
  `set_model_provider` does): `Login`, `SchemaChange` and `PrivilegeChange`, each with the user, database, protocol,
  a detail and whether it succeeded. Without a sink nothing is built.
- A session reports every statement that changes the schema (tables, indexes, sequences, views, types, domains,
  routines, triggers, packages, synonyms, schemas, databases, extensions, materialized views, event triggers,
  `TRUNCATE`) or privileges (roles, grants and revokes, row-level security), with its text, after it ran, failed ones
  included. This covers every protocol, since they all run statements through the session.
- The PostgreSQL listener reports each login, accepted or refused, with the client's address and the method
  (`AuthMethod::name`, new: `scram-sha-256`, `ldap`, `jwt`, `oauth`, `cert`, `reject`).
- `eggdb serve` with `EGGDB_AUDIT=1` writes them as `server_event` records into the database's audit file, the one
  `eggdb mcp` writes (D231's "one log for everything"), through the same hash chain; `eggdb audit` shows them as
  `<time>  schema change by alice: CREATE TABLE ...`. A record that cannot be written is reported on standard error
  and does not stop the statement or login.
- Left: MySQL and TDS logins, reads of chosen tables, anchoring the newest digest outside the file, and retention.
