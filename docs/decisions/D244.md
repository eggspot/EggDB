## D244 The catalog, quality rules and lineage are tables and functions in the `eggdb_catalog` extension — Decided by the build loop (by judgement, 2026-10-31); refines D42 and D51

Track 4.X-16 asks for a data catalog with a glossary and stewardship, lineage through
OpenLineage, the Atlas and OpenMetadata APIs, a schema registry and data contracts, master data
management and data quality rules. This slice does the glossary, quality rules and lineage.

- **Inside the database, as SQL.** `CREATE EXTENSION eggdb_catalog` adds the `terms`, `tags`,
  `quality_rules`, `quality_results` and `lineage` tables and the `check_quality`, `upstream` and
  `openlineage_event` functions, written in PL/pgSQL like the other bundled extensions (D236 to
  D238). The catalog is then backed up, replicated, permissioned and queried like any other data,
  with no catalog service beside the database (D3).
- **Quality rules are row conditions.** A rule is a boolean SQL condition on one table, true
  for a good row; NULL counts as a failure. Each check appends to `quality_results`, so trends
  are a query away and a pg_cron job plus `eggdb_bi` alerts (D238) turn rules into monitoring.
  A condition runs with the caller's privileges, like a view, so writing rules is a privilege to
  grant only to roles trusted to write SQL; the docs say so.
- **Lineage is edges between named assets**, so assets outside the database (a CRM, a file, a
  dashboard) take part too. `upstream` walks at most 100 hops, and `openlineage_event` emits the
  OpenLineage `RunEvent` shape, so EggDB's lineage feeds Marquez, DataHub and other collectors.

Left: column-level lineage captured from queries, the Atlas and OpenMetadata APIs, a schema
registry and data contracts, entity resolution, match and merge and golden records, profiling
(D42), and the console screens for all of it.
