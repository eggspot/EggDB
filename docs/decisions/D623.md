## D623 msdb's SQL Server Agent views — Decided by the code-only session (2026-11-12, D355); roadmap M10, D27, D200, D523

D523 runs SQL Server Agent jobs, with their definitions in `eggdb_internal` tables, and left out
the `msdb` views. SSMS's Job Activity Monitor, dbatools' `Get-DbaAgentJob`, and the monitoring
queries every SQL Server shop has ("which jobs failed last night") read `msdb.dbo.sysjobs`,
`sysjobsteps`, `sysschedules`, `sysjobschedules` and `sysjobhistory`.

- The Agent's set-up statements now also create five views over its tables:
  - `sysjobs`: `job_id`, `name`, `enabled` as 1 or 0, `description`, `start_step_id`.
  - `sysjobsteps`: `job_id`, `step_id`, `step_name`, `subsystem` (`TSQL`), `command`,
    `database_name`, and the flow fields at SQL Server's defaults (go to the next step on
    success, quit with failure on failure, no retries).
  - `sysschedules`: `schedule_id`, `schedule_uid`, `name`, `enabled`, and the `freq_*` and
    `active_*` fields as stored.
  - `sysjobschedules`: `schedule_id`, `job_id`, and next-run fields of 0.
  - `sysjobhistory`: `instance_id`, `job_id`, `step_id`, `step_name`, `message`, `run_status`,
    `run_date` (`yyyymmdd`) and `run_time` (`hhmmss`) as integers, and `run_duration` of 0.
- Ids follow from names, since D523 addresses jobs and schedules by name:
  - `job_id` and `schedule_uid` are the MD5 of the name as a `uniqueidentifier`, stable across
    sessions;
  - `schedule_id` and `instance_id` number rows in name and time order.
- `msdb.dbo.<view>` and `msdb..<view>` resolve to the views; other `msdb` objects resolve as
  before.
- The views exist once an Agent procedure has run in the file. Before that, reading them reports a
  missing relation, as there is nothing to show.
- A Transact-SQL test adds a job and a step, starts it, and reads `sysjobs`, `sysjobsteps` and the
  step's successful history row.
