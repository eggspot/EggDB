## D120 The MCP audit log: a sidecar `<file>.mcp-audit.jsonl`, one JSON line per call written and synced before the result is sent, opened anew for each record, not tamper-evident — Decided by the build loop (owner's spec of 2026-10-28, and by research); plan item 49a, applies D3, D11, D26

D11 asks that every agent action be logged where the owner can see it. The owner's spec for
item 49 puts the log next to the database, not in it: `<file>.mcp-audit.jsonl`. So a read-only
agent never writes the database, the log can be read while a server holds the file, and the
database's format does not change. It is the one file besides the database that EggDB writes
for it, an exception to D3's "one file" for an access log.

**What a record holds.** `server_started` (time, version, pid, database, read-only, time limit);
one `call` per `tools/call` and `resources/read`, refused and failed ones included: the time
(RFC 3339, UTC, microseconds), the client's `name` and `version` from `initialize`, the protocol
version, the tool, the arguments (re-encoded as ASCII JSON; over 64 KiB they are cut, with
their size kept), the outcome, the error code and SQLSTATE, the result's size in bytes, the
rows and whether it was cut, and the duration; and `time_limit_exceeded` from the watchdog
(D119). Never the result's content. Arguments hold SQL as sent, so literals such as tokens,
password hashes or personal data land in the file: docs/mcp.md says to protect it like the
database.

**How it is written.** A record is durable before the result leaves: if it cannot be written,
the call answers `audit_unavailable` and its result is withheld, and a server whose first record
(`server_started`) fails does not start; there is no option to turn the log off. Each record
opens the file anew, through `eggdb_platform::user_files::open_private_append_no_follow`:
created with mode 0600 on Unix (on Windows it takes the directory's permissions), refused when
the path is a symbolic link or another file took its place while it was opened, so a planted
link cannot send records elsewhere; then the file's exclusive lock (waiting up to a second),
one write of the whole line, and a sync. Several servers on one database never interleave
lines, and the file can be moved aside at any time: the next record starts a new one. A second
OS user's server fails closed on the 0600 file. At 1 GiB the file takes no more records and calls
are refused until it is archived or removed; nothing is deleted automatically.

**Not tamper-evident, and it says so.** A hash chain without a key can be recomputed by anyone
who can write the file, and the storage's page checksums already catch accidental damage, so
research advised dropping the chain this plan first had: the log records every call in order and
`eggdb audit` reports lines that are not records, but the docs make no tamper-evidence claim.
D26's tamper-evident audit waits for keys kept outside the file (D23). The agent's own tools
cannot reach the file; an agent that also has a shell can.

**`eggdb audit <file>`** reads it without opening the database (`-n` for the newest lines,
`--format json` for the records as stored), retries for a second on Windows, where the writer's
lock blocks reads for the moment it writes, and shows control characters in logged text escaped
so a record cannot drive the terminal. Its layout is Claude Fable's (docs/ux/cli.md, section 17).
