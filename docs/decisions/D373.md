## D373 SQLite's `UPDATE OR FAIL | IGNORE | REPLACE` with `FROM` and on a view — Decided by the code-only session (2026-11-10, D355); roadmap M3, closes one of D338's leftovers

D338 resolved conflicts row by row only for a plain `UPDATE`; with `FROM` the parser refused the
algorithm, and on a view the executor refused it.

- **With `FROM`.** The joined update writes through `merge::store_updates`, now
  `store_updates_resolving` with the statement's algorithm: a row whose new values break `NOT
  NULL` or a `CHECK` is skipped under `IGNORE` and stops the statement under `FAIL` (the rows
  before it stay written, D317's `keeps_failed_statement_changes`); unique conflicts go through
  D338's `write_updated_rows_resolving_conflicts`, which leaves the row as it was (`IGNORE`),
  deletes the rows in the way (`REPLACE`) or stops (`FAIL`), and only the rows it wrote fire
  `AFTER` row triggers and are counted. `MERGE` keeps `ABORT`.
- **On a view.** SQLite views change only through `INSTEAD OF` triggers, so the trigger runs and
  the algorithm is not refused; a view without such a trigger (an automatically updatable view
  in the other dialects) still refuses a row-by-row algorithm with `0A000`. Whether the outer
  algorithm overrides the conflict clauses of the trigger's statements is D338's other leftover.
- **REPLACE and `NOT NULL`.** The joined path does not yet put a column's default in place of a
  `NULL` under `REPLACE`; it fails as `ABORT` there.
