## D138 ORMs and migration tools unchanged: `INSERT ... SELECT` through the `INSERT` path, advisory locks in one table per process keyed by store, Flyway with its session-level lock while there is one writer, Transact-SQL `MERGE` with `OUTPUT` on the `MERGE` executor, `SAVE TRANSACTION` recorded but not rolled back to, `OPENJSON` as a derived table, EF Core 8 — Decided by the build loop (by research, 2026-10-30); roadmap item 48, applies D1, D9, D12, D86, D122, D126, D131, D132, D135

Item 48 runs three tools people use to own their schema and data, unchanged, against EggDB: an
SQLAlchemy 2.0 ORM app and Flyway 10 migrations over PostgreSQL's protocol, and an EF Core 8 app
over SQL Server's. What each sends was taken from the tools' own permissive sources and from
running them against stubs (SQLAlchemy through a stub DB-API driver, EF Core through fake
ADO.NET objects under its interceptors, Flyway's sources and pgjdbc's wire log); no database's
source was read.

**`INSERT ... SELECT` runs the query, then the `INSERT` path.** SQLAlchemy's ORM inserts several
rows of a table as `INSERT INTO t (a, b) SELECT p0::VARCHAR, p1::DATE FROM (VALUES (...), ...)
AS imp_sen(p0, p1, sen_counter) ORDER BY sen_counter RETURNING t.id, t.id AS id__1` and pairs
the returned keys with its objects by the order. `InsertSource::Query` holds the query; the
executor runs it to completion first (so a statement that reads its own target, `INSERT INTO t
SELECT ... FROM t`, sees the table as it was before), turns each result row into typed constants
and runs them through the existing `VALUES` path, so conversions, defaults, identity, checks,
unique and foreign keys, `RETURNING`/`OUTPUT` and the row order are exactly those of `INSERT ...
VALUES`. Every dialect gets it; SQL Server's `INSERT ... OUTPUT ... SELECT` too. A text value the
query produced is typed `text`: PostgreSQL resolves an untyped literal in the select list to the
target column's type, EggDB needs a cast there (`SELECT '2024-01-01'::date`).

**Advisory locks: one table per process, keyed by store and lock key.** Flyway serializes
migrations with `pg_try_advisory_lock` / `pg_advisory_unlock` (or the `_xact_` forms). The locks
must be seen by every session over the same store and by no other store, and must not reach the
file. `advisory_locks.rs` keeps a process-wide table (a mutex and a condition variable) keyed by
the store's address and the key (one `bigint`, or two `integer`s); a session owns a numbered
holder, released when the session drops, so a store's address is never reused while one of its
locks is held. Each statement enters the holder into a thread-local, as the cancel signal is
entered (D135), so the functions need no session argument; outside a transaction the guard
releases transaction-level locks at the statement's end, inside one `COMMIT`, `ROLLBACK` and the
end of an implicit transaction release them. Session locks count re-entries, exclusive and shared
modes conflict as PostgreSQL's do, a waiting `pg_advisory_lock` wakes on every release and checks
the cancel signal every 10 ms. Not done: deadlock detection between advisory locks (a deadlock
waits until a cancel), `pg_locks`, and the warning of an unlock of a lock not held.

**Flyway runs with its session-level lock while there is one writer.** By default Flyway uses two
connections: the first keeps a transaction open around `pg_try_advisory_xact_lock` and later
inserts the history row while the second connection's migration transaction is still open. The
store has one writer (D86), so the second write transaction fails with `55P03` instead of
deadlocking. `flyway.postgresql.transactional.lock=false` (Flyway's own setting) makes Flyway use
one connection and the session-level lock, which runs migrate, info and validate exactly as on
PostgreSQL. CI's `pg-apps` job runs Flyway that way on both servers; the default mode waits for
concurrent writers (roadmap 4.M3-1). Flyway also needed `set_config(name, $1, false)` with
parameters (the value is read at parse time, as constant `set_config` already was) and `SET ROLE`
to the session's own user (and `NONE`, `RESET ROLE`) as a no-op; another role is `0A000` until
roles exist (4.M6a-2).

**Transact-SQL `MERGE` with `OUTPUT` runs on D126's `MERGE` executor.** EF Core 8 inserts several
rows of a table with identity keys as `MERGE [t] USING (VALUES (@p0, ..., 0), ...) AS i (...,
_Position) ON 1=0 WHEN NOT MATCHED THEN INSERT (...) VALUES (i.[...], ...) OUTPUT INSERTED.[Id],
i._Position;`. The Transact-SQL parser reads `MERGE [INTO] target [[AS] alias] USING source ON
condition`, `WHEN MATCHED [AND condition] THEN UPDATE SET ... | DELETE`, `WHEN NOT MATCHED [BY
TARGET] [AND condition] THEN INSERT ...` and `OUTPUT` into the same `MergeStatement` Oracle's
`MERGE` uses; `DELETE` is an update with no assignments whose `DELETE WHERE` is true. `OUTPUT`
projects rows of three sources, `inserted` (the stored row, identity included, from the insert's
`RETURNING`), `deleted` (the row before the change) and the source alias, so `$action`-free
`OUTPUT` lists work; rows of changed rows come before rows of inserted ones, in their own orders.
`VALUES` lists as derived tables, which the source needs, are now read in Transact-SQL as in
PostgreSQL. Not done: `WHEN NOT MATCHED BY SOURCE`, a second `WHEN MATCHED`, `$action`, `TOP`,
table hints and `OUTPUT ... INTO` (40517).

**`SAVE TRANSACTION` is recorded; rolling back to it is refused.** EF Core sends `SAVE TRANSACTION
[__EFSavePoint]` before `SaveChanges` inside a user transaction and rolls back to it only when
`SaveChanges` fails. The store has no save points yet, so the session records the name and
`ROLLBACK TRANSACTION name` (or a transaction manager rollback naming it) of a recorded save
point is error 40517 with the transaction left as it was; it is never a silent full rollback. A
`ROLLBACK TRANSACTION` naming anything else rolls back everything, as before. The transaction
manager's save requests now go the same way.

**`OPENJSON ... WITH` is a derived table over an internal set-returning function.** EF Core 8
translates `list.Contains(x)` to `x IN (SELECT [c].[value] FROM OPENJSON(@p) WITH ([value] int
'$') AS [c])`. The parser rewrites `OPENJSON(json [, path]) WITH (column type ['path'] [AS JSON],
...) [AS] alias` into a derived table: `SELECT CONVERT(type, <value at path>) AS column, ... FROM
*openjson*(json)`, where `*openjson*` yields each element of an array, or an object as one row,
and the value functions return a scalar (or, with `AS JSON`, an object or array) at the path and
NULL otherwise, SQL Server's lax mode. Paths take `$`, `.key`, `."quoted key"` and `[n]`; a
column without a path reads the key named as the column is written. This reuses the derived-table
and set-returning machinery instead of a new kind of table source. Not done: `OPENJSON` without
`WITH` (the `key`, `value`, `type` form), `strict` paths and `CROSS APPLY` (40517).

**EF Core 8, not 9; the checks extend `pg-apps` and `tds-apps`.** EF Core 9's migrations take
`sp_getapplock` through `EXEC @result = ...`, which waits for stored procedures (3.15); EF Core 8
(LTS) sends neither. The plan's separate `orm-apps` job was folded into the jobs that already
start the servers and clients: `pg-apps` runs the SQLAlchemy ORM section of `app_check.py` and
`FlywayCheck.java` on PostgreSQL 17 and EggDB and requires the same bytes, `tds-apps` runs
`EfCoreAppCheck` against hand-written expected output (SQL Server is not a CI oracle, D132).
