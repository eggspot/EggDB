## D1366 A key per tenant database, and crypto-shredding — Decided by the code-only session (2026-11-25, D355); roadmap M6b "Per-column and per-tenant keys" (D23, D187, D234), the tenant part; security-critical (D35)

- **What users get.** `eggdb serve <directory> --tenant-databases <n> --key-file <file>` gives each tenant database its own random 32-byte key instead of the server's key. Dropping a tenant (`DROP DATABASE`) forgets its key before removing its file, so the file, a copy that escaped, and every backup of it can no longer be read: crypto-shredding, which D234 left. Without a server key nothing changes.
- **Where keys live.** In one keyring, `tenants/tenant-keys.eggkeys`, sealed with AES-256-GCM under the server's key with a fresh random nonce on every save and the format's magic as associated data, so a changed file or a wrong server key is refused rather than misread, and the tenant names are hidden too. A save writes a new file, syncs it and renames it over the old one, so a crash leaves the old keyring or the new one. Keys come from the platform's secure random source.
- **How it fits.** Tenant files are opened with `Options::encryption_key(tenant key)`; a new tenant gets its key, kept, before its file is created; a tenant made from a template is copied with the template's key and then compacted under its own (D1365), so no two tenants share a key. A keyring that cannot be read leaves every tenant unopened, failing closed.
- **Left.** Per-column keys (a column encrypted under a named key, readable only by roles that hold it), keys per tenant for tenancy by row (D234's `eggdb_tenancy`), rotating the server key that seals the keyring, and keeping a shredded tenant's name so it is not created again by mistake.
- **Proof.** A unit test adds two tenants' keys, finds no tenant name in the sealed file, reads the keyring back with the server key, refuses it with another key, shreds one tenant, and reads back only the other.

**Status:** code written, unbuilt (code-only mode, D355).
