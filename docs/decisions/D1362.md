## D1362 Dynamic data masking, first slice: SQL Server's masks and UNMASK — Decided by the code-only session (2026-11-25, D355); roadmap M6b "Dynamic data masking" (D22, D285), the code D1348 decided; security-critical (D35)

- **What users get.** `CREATE TABLE ... (email varchar(100) MASKED WITH (FUNCTION = 'email()'), ...)`, `ALTER TABLE t ALTER COLUMN c ADD MASKED WITH (FUNCTION = '...')` and `... DROP MASKED`, `GRANT UNMASK TO r` and `REVOKE UNMASK FROM r`, in every dialect. The functions are SQL Server's `default()`, `email()`, `random(low, high)` and `partial(prefix, "padding", suffix)`. A role that is not a superuser, holds no `UNMASK` (itself or through a role it belongs to) and does not own the table gets masked values in every result a statement returns; filters, joins, grouping and ordering still see real values, as D1348 decided and as both vendors document. Masking is a way to limit exposure in results, not a boundary: row and column security remain the boundary (D1348).
- **Storage.** In `COLUMN_MASK_SPACE` (`0x24`) as D1348 reserved: one record per masked column, keyed by table and column, holding the function's text, and one marker per role holding `UNMASK`. Masks move with `ALTER TABLE ... RENAME` and `RENAME COLUMN`, and go with the table (`roles::forget_table`), so a later table of the same name starts unmasked; a release that does not know masks shows real values, as D1348 accepted.
- **Who may change them.** Masks: a superuser or the table's owner (`42501`, SQL Server's 15247, for anyone else). `UNMASK`: a superuser.
- **Which result columns are masked.** The session reads the masks once per statement text, only for a checked role, and only when the text names a masked column. A result column named like a masked column gets that column's function (two different functions under one name give `default()`); a column named like an unmasked column of a masked table shows as it is; every other result column, which could be an expression over a masked column, gets `default()`. This follows D1348's "decided conservatively by name": a statement that names a masked column can over-mask a column of another table it joins, never under-mask, except for an alias of an unmasked column that reuses a masked column's name, which shows that column's mask instead.
- **How.** `masking.rs` holds the functions, storage and `ResultMasks`; `session/masking.rs` runs the four commands before the parser (as other session-level commands do) and strips `MASKED WITH (...)` from a `CREATE TABLE`, recording the masks after it succeeds (as invisible columns do, D1032); `run_text` wraps the result callback, so every protocol sees masked rows.
- **Left.** `UNMASK` per schema, table and column (SQL Server 2022), `datetime()`, Oracle's `DBMS_REDACT` policies, `sys.masked_columns`, `sys.columns.is_masked` and Oracle's redaction views, masks in scripting output, the MCP tools' own statement path, and result columns traced to their source columns instead of matched by name.
- **Proof.** Session tests: a role sees `aXXX@XXXX.com` and `0` for masked columns and real names, finds a row by filtering on the real e-mail, gets `default()` for an expression and an aggregate over masked columns, sees real values after `GRANT UNMASK` and masked ones again after `REVOKE`, and a new `partial()` mask after `ADD MASKED`; the owner sees real values; a non-owner cannot drop a mask or grant `UNMASK`; an unknown function is `22023`; a table dropped and created again is unmasked; a mask follows a column and a table rename. A unit test pins each function.

**Status:** code written, unbuilt (code-only mode, D355).
