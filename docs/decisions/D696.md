## D696 SQL Server xml.nodes() in CROSS APPLY and OUTER APPLY — Decided by the code-only session (2026-11-12, D355); roadmap M10, SQL Server's `xml` type (D19, D695)

- `FROM t CROSS APPLY t.doc.nodes('/order/line') AS l(c)` (and `OUTER APPLY`, and `doc.nodes(...)` without the table
  name) makes one row per node the path selects, with the node in column `c`. It is built as D692's `XMLTABLE`
  generated table with one serialized-node column, so it reads the earlier `FROM` items the way `JSON_TABLE` and
  `XMLTABLE` read them.
- `c.value(...)`, `c.query(...)` and `c.exist(...)` on such a row read relative paths (`@sku`, `qty`, `.`) from the
  row's node. The methods now evaluate a path from the document node first and, when that selects nothing and the
  value is a single element, again from that element. On a whole document a relative path that names nothing at
  the top but something under its root element therefore finds that, where SQL Server returns nothing; absolute
  paths are unchanged.
- `query()` and `exist()` have their own internal functions for this (`eggdb_xml_node_query`,
  `eggdb_xml_node_exist`), so Oracle's `XMLQUERY` and `EXISTSNODE` keep evaluating from the document node.
- Left out: `.modify()` (XML DML), and the alias column list being optional (SQL Server requires it too).
