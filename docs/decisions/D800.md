## D800 SQLite FTS5 tables, searched without an index — Decided by the code-only session (2026-11-12, D355); roadmap M8, SQLite's FTS5

- SQLite's dialect accepts `CREATE VIRTUAL TABLE [IF NOT EXISTS] t USING fts5(columns, options)`: the columns become
  an ordinary rowid table of text columns, kept with the statement's own text in `sqlite_schema` so SQLite tools see a
  virtual table. Column options (`UNINDEXED`) and table options (`tokenize`, `prefix`, `content`, ...) are accepted;
  every column is searched with the unicode61 tokenizer's rules (runs of letters and digits, lower-cased; diacritics
  are kept). Any other module fails with SQLite's "no such module".
- `x MATCH 'query'` is parsed in SQLite's dialect into an internal call the evaluator answers from the row of the
  table named `x` (`crates/eggdb-sql/src/sqlite_fts.rs`), with FTS5's query syntax from SQLite's documentation: bare
  and quoted terms, phrases (`"a b"` and `a + b`), prefixes (`egg*`), initial tokens (`^egg`), implicit and explicit
  `AND`, `OR`, `NOT`, parentheses, column filters (`col : x`, `{a b} : x`, `- col : x`) and `NEAR(a b, n)` (10 by
  default). Syntax errors read "fts5: syntax error near ...". A query is bounded to 10,000 terms.
- There is no inverted index yet, so a `MATCH` reads every row. `bm25(t)` therefore cannot see corpus-wide document
  frequencies or lengths: it returns minus the sum over query terms of the term's saturated frequency in the row
  (k1 = 1.2), which orders a query's rows by how often they hold its terms, lower first like SQLite's. `highlight(t,
  col, open, close)` and `snippet(t, col, open, close, ellipsis, tokens)` mark the matched terms of the row's last
  `MATCH`. The hidden `rank` column is not there; `ORDER BY bm25(t)` stands in for `ORDER BY rank`.
- Left: the inverted index in the file and BM25 over it (with FTS5's own `rank`), the porter and trigram tokenizers,
  diacritic folding, `UNINDEXED` taking effect, FTS5's auxiliary tables and `INSERT INTO t(t) VALUES('optimize')`.
