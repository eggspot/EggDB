## D950 `pg_export_snapshot()` in a read-write block — Decided by the code-only session (2026-11-13, D355); roadmap M3, finishes D369's leftover

- PostgreSQL exports a read-write transaction's snapshot, which never includes the exporter's own uncommitted changes:
  an importer sees what was committed when the exporter's snapshot was taken. D369 refused it because EggDB's writer
  reads its own changes.
- EggDB's writers are serialised and a block holds the one writer from its start, so no commit can land between the
  block's start and the export: the latest commit is exactly the snapshot the block started from. When a statement in
  a read-write block names `pg_export_snapshot`, the session opens a read transaction at the latest commit before the
  statement runs and keeps it, wrapped as D369's `ExportingRead`, until the block commits or rolls back; the export
  hands out that reader's snapshot, and its ids are forgotten when the block ends, as for a read-only block. Other
  statements of a writer block open no reader.
- A text that starts the block and exports in one batch (`BEGIN; SELECT pg_export_snapshot()`) still answers `0A000`,
  since the reader is opened before the text's first statement runs; clients that export (pg_dump, logical
  replication tools) send them separately. The `0A000` outside a block now says a block is needed, not a read-only one.
