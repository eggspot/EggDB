## D754 A ledger on a table that already has rows — Decided by the code-only session (2026-11-12, D355); roadmap M6b, a ledger on a table that already has rows (D236)

- `eggdb_ledger.protect(schema, table)` no longer needs an empty table. After adding the three ledger columns it
  numbers the existing rows with a temporary sequence (`eggdb_ledger.adoption_order`, dropped at once), in the order a
  scan reads them, then chains them in that order with the same hash `append()` computes for a new row: SHA-256 of the
  previous hash and the row's JSON without `ledger_hash` and `ledger_previous`. The chain's head and count go into
  `eggdb_ledger.chains`, so the next insert continues the chain and `verify` checks the adopted rows like the rest.
- Numbering by a sequence instead of by key handles tables with no primary key and duplicate rows. The order of
  adopted rows says nothing about when they were written; the chain only proves they have not changed since `protect`.
- `protect` now returns the number of rows it adopted (`bigint`, 0 for an empty table) instead of `void`.
- Adopting in batches for very large tables, and SQL Server's `WITH (LEDGER = ON)` on an existing table, are left.
