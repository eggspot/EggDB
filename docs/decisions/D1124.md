## D1124 Collections and expiring keys inside concurrent transactions — Decided by the code-only session (2026-11-13, D355); roadmap M3 (D172)

- **Buffered like every other write.** `ConcurrentTransaction` gains `put_with_expiry`, `collection_get`,
  `collection_put` (with an optional time to live), `collection_delete`, `has_collection` and `collection_names`.
  Default-space writes keep their map; a time to live sits beside the key and is dropped by a later plain `put`.
  Collection writes are keyed by (collection, key). Reads see the transaction's own writes first.
- **Checked like every other write.** Serializable transactions record each collection key they read and compare it
  with the writer's view at commit. Snapshot transactions compare each collection key they write with its snapshot
  value (absent when the collection did not exist then). Either mismatch is `ErrorKind::Conflict`.
- **Applied through the ordinary APIs.** At commit the writes go through `WriteTransaction::put_with_expiry` and
  `WriteCollection::put`, `put_with_expiry` and `delete`. Deadline indexes, collection entry counts and the change
  archive are kept exactly as for any write, and the time to live counts from the commit, when the key is written. A
  collection dropped before the commit fails it with `CollectionNotFound`.
- **SQL sees them.** The concurrent SQL writer (D1123) forwards the key-value tools' calls (`put_with_expiry`,
  `collection_put`, `collection_delete`, `collection_get`, `has_collection`, `collection_names`), so the MCP and
  wire sessions' key-value statements work inside a `SERIALIZABLE` block.
- **Left:** counters (`increment`) and compare-and-set inside concurrent transactions, which need a read-modify-write
  recorded as a read, and collection scans that include the transaction's own writes.
