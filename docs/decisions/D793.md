## D793 CREATE FUNCTION ... LANGUAGE wasm — Decided by the code-only session (2026-11-12, D355); roadmap M5, WebAssembly functions

- PostgreSQL's dialect accepts `LANGUAGE wasm`. The body is PostgreSQL's two-string form for loadable code,
  `AS '\x0061736d...', 'export'`: the module's bytes in hex (as a `bytea` literal prints them, `0x` also taken) and
  the exported function to call, which defaults to the routine's own name when only the module is given. The two
  strings are kept in the stored body separated by a NUL, which no SQL text holds; every other language still
  refuses the two-string form ("a routine in a loadable object file").
- At `CREATE FUNCTION` the module is parsed with EggDB's interpreter (D232, D792), the export must exist, and its
  WebAssembly signature must match the SQL one exactly under the type mapping `boolean`, `smallint`, `integer` → `i32`,
  `bigint` → `i64`, `real` → `f32`, `double precision` → `f64` (and no result for `void`). Procedures, OUT
  parameters, defaults, sets and other types are refused for now. `pg_language` lists `wasm` (OID 13579, trusted:
  the module has no imports, so it can only compute) and `information_schema.routines` shows `EXTERNAL`.
- A call parses the module once per thread (a cache of 32 modules keyed by the body text), makes a fresh instance
  (so calls share no memory or globals and stay pure), converts the arguments by assignment, and runs the export
  under the default limits (10 million instructions, 256 pages, 512 frames). A trap fails the statement with 38000
  and the trap's text. A NULL argument gives NULL without running the module, for `STRICT` or not, since a
  WebAssembly function cannot take NULL.
- `eggdb-wasm-vm` gains `Module::export_signature` and the public `ValueType`.
- Left: text, `bytea` and other types passed through the module's memory with an allocator export, set-returning
  functions, host functions (row reads, logging) behind permissions, limits per role from settings.
