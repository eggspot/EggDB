## D1175 GraphQL nested inserts at any depth, with `on_conflict` at every level — Decided by the code-only session (2026-11-15, D355); roadmap M6a, follows D909

- D909's nested inserts went one relationship deep and refused `on_conflict`. The insert is now built by a recursion over the input object: each object, at any depth, becomes one data-modifying `WITH` step, so one top-level object is still one statement in the mutation's transaction:
  - an object relationship (`author: {data: {...}}`) inserts the parent's step first, after its own parents, and links the row's foreign key columns to it;
  - an array relationship (`books: {data: [...]}`) inserts each child after the row's step, linked to it, and the children's own relationships follow the same rules.
- Steps are named from a counter (`eggdb_graphql_step_<n>`), not from their position, because a parent is named before its own parents are written. The top-level row keeps D909's `eggdb_graphql_new` step and its temporary table for `returning`.
- `on_conflict` is taken where Hasura takes it: the mutation's argument for the top-level rows, and beside `data` in a relationship input for that relationship's rows (`author: {data: {...}, on_conflict: {constraint: authors_pkey, update_columns: [name]}}`). Each becomes that step's `ON CONFLICT ON CONSTRAINT ... DO UPDATE`/`DO NOTHING`, with its `where`.
- An object relationship's `on_conflict` must update at least one column, as in Hasura: `DO NOTHING` returns no row for an existing parent, so the child would have nothing to link to. Array relationships may use `DO NOTHING`.
- At most 16 relationships deep, so a hostile request cannot build an unbounded statement.
- `affected_rows` still counts the top-level rows only (D909).
