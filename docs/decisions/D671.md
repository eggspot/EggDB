## D671 EVAL, EVALSHA and SCRIPT in the RESP server — Decided by the code-only session (2026-11-12, D355); roadmap M7, Lua scripting (D27, D193)

- `eggdb-resp` runs `EVAL`, `EVALSHA`, `EVAL_RO`, `EVALSHA_RO` and `SCRIPT LOAD | EXISTS | FLUSH [SYNC|ASYNC] | KILL`
  on the `eggdb-lua` interpreter (D667–D670). `eggdb_lua::run_script` sets `KEYS` and `ARGV`, installs the `redis`
  table (`call`, `pcall`, `error_reply`, `status_reply`, `sha1hex`, `log` with the `LOG_*` levels, `setresp`, and
  `replicate_commands` and `set_repl` as accepted no-ops) and converts the first returned value to a reply by Redis's
  Lua-to-RESP2 rules. Replies reach the script by the RESP2-to-Lua rules: nil bulk and nil array become `false`,
  statuses and errors become `{ok=…}` and `{err=…}`, doubles become strings, maps flatten to arrays.
- A script runs in one write transaction of the keyspace, the same way `EXEC` does (an `OpenTransaction`), so it is
  atomic for other clients. As in Redis, a script error does not roll back the writes made before it. `EVAL` inside
  `MULTI` queues and runs at `EXEC` in that transaction. `SELECT` inside a script does not change the caller's
  database.
- Read-only scripts (`EVAL_RO`, `EVALSHA_RO` and a `#!lua flags=no-writes` shebang) run in a read transaction behind a
  keyspace whose writes fail with Redis's "Write commands are not allowed from read-only scripts." Other shebang
  flags are accepted and have no effect; an unknown engine or flag is refused as Redis refuses it.
- Commands a script may not call (`EVAL` and its kin, `SCRIPT`, `MULTI`/`EXEC`/`WATCH`, the subscribe family,
  `MONITOR`, `AUTH`, `HELLO`, `CLIENT`, `CONFIG`, `QUIT`, `RESET`) answer "This Redis command is not allowed from
  script".
- The script cache is one `ScriptCache` per server, shared by its connections and empty after a restart, as in
  Redis. `Context` gains `scripts: Option<&ScriptCache>`; replays and embedded callers pass `None`, where `EVAL` still
  runs and `EVALSHA` answers `NOSCRIPT`, so an old AOF that relies on `EVALSHA` after `SCRIPT LOAD` does not replay
  those commands.
- A script stops after 100 million interpreter steps instead of after Redis's busy-script time limit, so `SCRIPT KILL`
  always answers `NOTBUSY`. The step budget makes the stop deterministic; a clock-based limit and killing a script from
  another connection are left out. So are global-variable protection, `redis.breakpoint` and `redis.debug`, and
  Redis Functions (`FUNCTION`, `FCALL`).
