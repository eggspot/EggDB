## D631 SQLite's VACUUM INTO and a writer of whole SQLite files — Decided by the code-only session (2026-11-12, D355); roadmap M5, D180, D384

SQLite applications back up a live database with `VACUUM INTO 'file'`, and tools hand an SQLite
file to programs that only read SQLite. D384 accepted `VACUUM` but left `VACUUM INTO` refused
until EggDB could write SQLite's file format (D180).

- `eggdb-sqlite-format` gets `write_database`, which builds a whole new file in memory: the
  100-byte header (4,096-byte pages, UTF-8, schema format 4, rollback journal mode, no free
  pages), table b-trees built bottom-up from rows sorted by rowid, index b-trees whose interior
  cells carry the entries that separate their children (every entry kept exactly once), records
  with SQLite's smallest serial types, and overflow pages for payloads over a page's local limit.
  `sqlite_schema` is the table b-tree rooted at page 1. Index entries sort by SQLite's `BINARY`
  collation with `DESC` keys honoured. Editing a file in place, with the rollback journal or the
  write-ahead log, stays left.
- `VACUUM [schema] INTO 'file'` in the SQLite dialect copies every main-schema table with its
  rows, the indexes constraints make (`sqlite_autoindex_<table>_<n>`, numbered in the order
  `PRIMARY KEY` and `UNIQUE` appear in the table's text, as SQLite numbers them), the indexes
  `CREATE INDEX` made, views and triggers, with the text `sqlite_schema` shows. An `INTEGER
  PRIMARY KEY` column becomes the rowid (NULL in the record, as SQLite stores it); other tables
  number their rows from 1 in key order. Values map to SQLite's classes: integers, reals,
  text, blobs; booleans as 0 and 1, `numeric` as an integer when it is whole, other types as
  their text.
- The engine writes no files itself. A new `NewFileWriter` trait creates the file; embedded
  entry points (`eggdb sql`, `eggdb shell`, `libsqlite3`) give their sessions
  `eggdb::sql::LOCAL_FILES`, which refuses an existing file as SQLite does. Servers give their
  sessions none, so a client never writes files on the server's machine: `0A000`.
- Refused with `0A000` until they are written: `WITHOUT ROWID` tables (their b-tree is an index
  b-tree, roadmap M5), partial and expression indexes, and indexes over `NOCASE` or `RTRIM`
  columns (the writer sorts by `BINARY` only). Inside a transaction block it fails with `25001`,
  as SQLite does. The file is built in memory before it is written.
- Tests: the writer's round trips through the reader (3,000 rows with a 20 KB blob and negative
  and large rowids, a 300-object schema spilling page 1 into a tree, a 4,000-entry index walked
  in order, `DESC` keys and value classes), and the session's `VACUUM INTO` copy, refusals and
  existing-file error.

**Status:** code written, unbuilt (code-only mode, D355).
