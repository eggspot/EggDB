## D151 The rest of the query language: window functions computed over the grouped rows in the select-list expansion, `LATERAL` run per distinct set of the values it names and joined back on hidden key columns, correlated subqueries at any depth through a chain of enclosing rows, data-modifying `WITH` run in order before the statement, updatable views rewritten to their table, and temporary tables and views kept in the session's memory — Decided by the build loop (by judgement and PostgreSQL's public documentation, 2026-10-30); roadmap item 30b (batch part 3.07), applies D1, D9, D10, D35, D112, D116, D128, D131; supersedes in part D112, D116 and D131

Items 30 and 33 (D112, D116) left `LATERAL`, `FULL JOIN ... USING`, correlated subqueries more
than one level out, in grouped queries and in `UPDATE`/`DELETE`, data-modifying `WITH`, window
functions beyond D131's three, ordered-set aggregates, updatable views with `WITH CHECK OPTION`
and temporary tables for later. They are built here, each on the machinery that already exists.

**Window functions (extends D131).** A window call stays one internal function call in the
expression tree, its definition encoded in its first arguments (function, `ORDER BY` directions,
key counts, the frame as four letters, the two frame offsets, a reference to a named window and
whether it has a `FILTER`), followed by its arguments, filter, partition and order keys. Named
windows (`WINDOW w AS (...)`, `OVER w`, `OVER (w ORDER BY ...)`) are resolved by the parser right
after the `WINDOW` clause, with PostgreSQL's copy rules (`42P20` for an overridden `PARTITION BY`
or `ORDER BY` or a copied frame). D131's select-list expansion computes them: the inner select
evaluates every key over the grouped rows, and each window's values come from sorting the rows
by partition and order keys and walking each partition with its peer groups and frame. A select
item that contains windows inside an expression is split into its window-free parts (inner select
items) and its windows, and evaluated over both afterwards. When windows are present the select's
`ORDER BY` moves into the expansion (output names and numbers keep their meaning; other
expressions become hidden items), so the order may use windows, aggregates and columns outside
the select list. Aggregates over windows use the grouping code's own accumulators (a new
`WindowAggregate`), incrementally when the frame starts at the partition's start and excludes
nothing, and recomputed per row otherwise. `FILTER (WHERE ...)` wraps an aggregate's argument
in another internal function; ordered-set aggregates (`percentile_cont`, `percentile_disc`,
`mode`) are aggregates whose `WITHIN GROUP` order is the D131 aggregate `ORDER BY`.

**`LATERAL` and `FULL JOIN ... USING`.** A `FROM` item marked `LATERAL` (or `CROSS`/`OUTER
APPLY`, or a function or `VALUES` list naming an item before it) is prepared with the items before
it as its outer query. When it names them, the distinct sets of the values it names are read from
those items joined as written, the item runs once per set (as a correlated subquery does, D112),
and its rows are stored with the set's values in leading hidden columns (marked so that `*` and
`alias.*` leave them out). The join to it becomes an inner join (a `LEFT` join stays left) whose
condition adds `key = hidden key` per value, or `IS NOT DISTINCT FROM` when a set held a NULL.
This keeps the executor's joins as they are, at the cost of materializing the lateral rows. A
`FULL JOIN ... USING` is rewritten before execution into `FULL JOIN ... ON` with the merged column
replaced by `coalesce(left, right)` in the select list, `*`, `WHERE`, `GROUP BY`, `HAVING`,
`ORDER BY` and later `ON` conditions.

**Correlated subqueries.** An outer column reference carries its depth (1 for the query directly
around). A subquery that names a query two or more levels out makes every query between correlated
too; a template records the (depth, column) pairs it reads, its own and its nested templates', and
each instance runs with the chain of enclosing rows, so substitution at any depth reads the right
row and the memo key includes every value read. In a grouped query, a correlated subquery's outer
columns must be grouping keys or columns they determine; the grouping maps them to the group row
(`42803` otherwise). `UPDATE` and `DELETE` keep the prepared templates and evaluate their
correlated `WHERE` conjuncts, `SET` values and `RETURNING` with them, all before the first write.

**Data-modifying `WITH`.** `WITH` at the top of a statement may hold `INSERT`, `UPDATE` or `DELETE`
and precede an `INSERT`, `UPDATE` or `DELETE`, as a new statement (`WithStatement`). Its `WITH`
queries run in order, each result kept as a table variable under a hidden name (the frames the
Transact-SQL table variables already use), and every reference to a `WITH` name in what follows is
replaced by that variable. They run one after the other on the same data, so later parts see
earlier changes; PostgreSQL runs them on one snapshot. A known difference, documented, accepted for
the simplicity of running each part with the existing executor.

**Updatable views.** `INSERT`, `UPDATE` and `DELETE` on a view follow PostgreSQL's rules for
automatically updatable views: the statement is rewritten, view by view down to the table, with
the view's columns replaced by their expressions, its condition added to `UPDATE` and `DELETE`,
and assignments allowed only to plain columns. `WITH [LOCAL | CASCADED] CHECK OPTION` is checked
by a hidden `RETURNING` item that evaluates the conditions to check on each new row (`44000` when
not true). **File format (D35):** the view definition's flags byte gains `4` (local check option)
and `8` (cascaded); a view without a check option keeps the same bytes, and a release before this
one refuses a view that has one as damaged, as it does every unknown flag.

**Temporary tables and views.** They live in schema `pg_temp` and in the session's memory, never
in the database file: the session wraps every reader and writer so that keys belonging to
temporary objects (catalog entries named `pg_temp.*`, rows and indexes of table ids in a range
reserved for them, and the comment, dependency, reference and `ON COMMIT` keys that name them) go
to a per-session ordered map with an undo log that the session's commit and rollback follow. The
engine code does not change: creating, altering, dropping, indexing and constraining a temporary
table use the same functions, and only the table-id allocation (a session range instead of the
database's counter) knows about them. Unqualified names find a temporary relation first; a view
over a temporary relation becomes temporary. This makes temporary tables free of disk writes and
invisible to every other session, and needs no cleanup after a crash; the cost is memory (1 GiB per
session at most) and that changing them still takes the database's write transaction.
