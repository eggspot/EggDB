## D684 MySQL ENUM members, UNSIGNED ranges and YEAR's range checked — Decided by the code-only session (2026-11-12, D355); roadmap M10, MySQL's types (D19, D646)

- D646 stored `ENUM`, `UNSIGNED` integers and `YEAR` on the nearest type and left their rules out. The MySQL column
  type parser now notes each rule and the column definition adds it as an implicit, unnamed `CHECK` constraint, so it
  holds on every `INSERT` and `UPDATE` with no new stored type:
  - `ENUM('a', ...)`: the value is one of the members;
  - `TINYINT`, `SMALLINT`, `MEDIUMINT` and `INT UNSIGNED`: 0 up to 255, 65,535, 16,777,215 and 4,294,967,295;
    `BIGINT UNSIGNED` and `DECIMAL`/`NUMERIC UNSIGNED`: not below 0 (D646 keeps `BIGINT UNSIGNED` signed, so its
    top is 2^63 - 1);
  - `YEAR`: 1901 to 2155, or 0.
  `NULL` passes each check, as it does in MySQL.
- MySQL's strict mode answers these with errors 1265 ("Data truncated") and 1264 ("Out of range value"); EggDB
  answers with its check constraint error (3819). The checks appear as constraints in `SHOW CREATE TABLE` and
  `information_schema.check_constraints`, where MySQL shows none.
- Still left: `ENUM` ordering by member index, `SET` member checks and member order, two-digit years, `b'...'` bit
  literals (the lexer's numeric tokens borrow the source text, so a converted value needs a new token kind), the
  spatial types, zero dates and the full `TIME` range.
