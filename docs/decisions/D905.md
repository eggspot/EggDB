## D905 pgRouting's spanning trees and maximum flows — Decided by the code-only session (2026-11-12, D355); roadmap M12, follow-up of D782 and D882

- `pgr_kruskal(edges_sql)` and `pgr_prim(edges_sql)` return a minimum spanning forest as `(edge, cost)` rows, as
  pgRouting's do: the edges form an undirected graph, an edge weighs the cheaper of its non-negative `cost` and
  `reverse_cost`, and an edge with both negative is not in the graph. Kruskal's rows come in the order the edges were
  chosen (by weight, then id); Prim's grow a tree from the smallest vertex of each component in turn. Self-loops are
  never chosen.
- `pgr_maxFlow(edges_sql, source, target)` returns the maximum flow as a `bigint`; `pgr_pushRelabel`,
  `pgr_edmondsKarp` and `pgr_boykovKolmogorov` return `(seq, edge, start_vid, end_vid, flow, residual_capacity)` for
  each edge direction that carries flow. Edges give whole `capacity` and optional `reverse_capacity`; zero or
  negative means no arc; a fractional capacity is an error.
- All four flow functions compute the same maximum flow with one algorithm, Edmonds-Karp (shortest augmenting paths,
  O(V·E²)): the maximum flow's value is unique, and pgRouting documents the three as different algorithms for the same
  result. Where several flow assignments reach the maximum, which one is returned may differ from pgRouting's.
- The work is done by `eggdb_route_spanning_tree` and `eggdb_route_max_flow` in `eggdb-sql`'s routing code, called by
  the extension's SQL like the earlier routing functions.
