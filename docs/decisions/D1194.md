## D1194 `FORCE ROW LEVEL SECURITY` with table owners — Decided by the code-only session (2026-11-17, D355); roadmap M6b (D326); security-critical (D35)

- **What users get.** PostgreSQL's rule: a table's owner (D1192), and the roles that belong to it, are not held to the table's row security policies, unless `ALTER TABLE ... FORCE ROW LEVEL SECURITY` says they are; `NO FORCE` lets them through again. Superusers and `BYPASSRLS` roles skip policies as before (D979), and every other role is held to them as before.
- **How.** `row_security::applicable`, which decides whether a statement's role meets a table's policies, now returns no policies when the role's closure holds the table's owner and the stored switch (already kept by `FORCE`) is not forced.
- **Proof.** A unit test makes a role a table's owner and reads every row, forces row security and reads only its own, while another role keeps reading only its own.
- **Security review.** As a D35 change it needs a security-only review pass once built: owners come only from a superuser's `OWNER TO` or from creating the table (D1193).

**Status:** code written, unbuilt (code-only mode, D355).
