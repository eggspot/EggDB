## D565 Redis Cluster of one node, and sharded pub/sub — Decided by the code-only session (2026-11-11, D355); roadmap M7, D193

Many Redis deployments are clusters, and their clients (redis-py's `RedisCluster`, Lettuce's and
Jedis's cluster clients, ioredis's `Cluster`) refuse a server that does not answer `CLUSTER
SLOTS` or `CLUSTER SHARDS`. Until EggDB shards (M15), a server started with `--resp-cluster`
answers as a cluster of one node that holds all 16,384 slots, so every key routes to it and
`MOVED`/`ASK` never happen:

- `CLUSTER INFO` (`cluster_state:ok`, one node, every slot assigned), `SLOTS`, `SHARDS` and
  `NODES` naming the address the client connected to, `MYID` (forty hex digits drawn from that
  address), `KEYSLOT` (CRC16/XMODEM of the key or of its `{hash tag}`, modulo 16,384, as Redis
  computes it), `COUNTKEYSINSLOT` and `GETKEYSINSLOT` (database 0's keys filtered by slot, read
  with `KEYS *` and so held to its reply limit), `REPLICAS` (none).
- Without the flag, `CLUSTER` answers `ERR This instance has cluster support disabled`, as a Redis
  without `cluster-enabled` does. `INFO` still says `cluster_enabled:0`; `SELECT` of another
  database is not refused yet.
- **Sharded pub/sub.** `SSUBSCRIBE`, `SUNSUBSCRIBE` and `SPUBLISH` work with or without the flag:
  shard channels are their own namespace (`PUBLISH` does not reach them, nor `SPUBLISH` plain
  channels), messages arrive as `smessage`, and a subscribed RESP2 connection may run them, as
  the error text already said.
