## D1359 Key grants per agent on eggdb serve's MCP endpoint — Decided by the code-only session (2026-11-25, D355); roadmap M6d "MCP key writes for agents acting as a role, through key-level grants (D328)", and the `eggdb serve` part of D1358

- **What users get.** A line of `--mcp-token-file` takes `keys=<prefixes>` (comma-separated, `0x..` for hex). That agent's sessions get D1358's key allow-list: the key tools are offered even though the agent acts as a stored role, and reach only keys of the default key space under those prefixes; with `writes=confirmed` the key writes (`put`, `del`, `incr`, `cas`, `expire`, `persist`) are offered too, with the same confirmations as on stdio.
- **Why a grant in the token file, not in SQL.** D328 refused key tools to role agents because a role's privileges are on tables, and the key-value store sits beneath them. Key families have no catalog objects to grant on, and inventing `GRANT ... ON KEYS` would add a privilege kind every dialect's catalogs would then need to show. The token file is where the owner already decides each agent's role, time limit, quota and writes (D491, D522), so the key grant sits beside them, per agent, and the SQL privilege system stays as the dialects define it.
- **Limits.** RESP keys, collections, `stats`, `check` and `backup` stay refused for role agents, as in D1358.
- **Left.** Key grants shown in an admin view of the endpoint, and changing them without restarting the server.
- **Proof.** A unit test reads `keys=session:,0x00ff` into two prefixes and refuses odd-length hex; the behaviour of the allow-list itself is D1358's acceptance test, since both paths build the same `ServerConfig::key_prefixes`.
