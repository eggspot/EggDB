## D737 MongoDB users and built-in roles — Decided by the code-only session (2026-11-12, D355); roadmap M9, other users and roles (D197, D475)

- Beside the server's own user (`--user`, which holds `root`), the MongoDB listener keeps users in
  `admin.system.users`, one document per `<db>.<user>` with its roles and SCRAM verifiers (SCRAM-SHA-256 at 15,000
  iterations and SCRAM-SHA-1 over MongoDB's `md5("<user>:mongo:<password>")` digest at 10,000), written as text by
  `eggdb-auth`'s new `to_stored` forms; passwords are never kept.
- Commands: `createUser` (with `pwd`, `roles`, `mechanisms` and `customData`), `updateUser`, `dropUser`,
  `dropAllUsersFromDatabase`, `grantRolesToUser`, `revokeRolesFromUser`, `usersInfo` (one user, a list, every user
  of the database or `forAllDBs`, with `showCredentials`) and `rolesInfo`, with MongoDB's error codes for a user
  that exists (51003), is missing (11) or names an unknown role (31).
- Sign-in: `saslStart` on a database looks up that database's user, so drivers authenticate created users with
  SCRAM-SHA-256 or SCRAM-SHA-1 (`authSource`); unknown users still fail the same way known ones with a wrong
  password do.
- Authorization by the built-in roles: reads need `read`, `readWrite`, `dbAdmin` or `dbOwner` on the database;
  writes (and `aggregate` ending in `$out` or `$merge`) need `readWrite` or `dbOwner`; collection and index
  definitions also accept `dbAdmin`; user commands and `admin.system.users` need `userAdmin` or `dbOwner`; the
  `*AnyDatabase` roles held on `admin` and `root` cover every database. Refusals answer `Unauthorized` (13).
  `connectionStatus` shows the signed-in user's roles.
- Left out: user-defined roles (`createRole`), privileges finer than these roles, `$external` and x.509 users, and
  authentication restrictions.
