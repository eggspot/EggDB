## D809 CQL user-defined types — Decided by the code-only session (2026-11-12, D355); roadmap M16, CQL collections, tuples, user-defined types and counters (D19, D218)

- `CREATE TYPE [IF NOT EXISTS] [ks.]name (field type, ...)` and `DROP TYPE [IF EXISTS] [ks.]name`. A type is kept in
  `eggdb_cql.types (keyspace_name, type_name, definition)`; `CREATE TYPE` without `IF NOT EXISTS` fails on the primary
  key when the type exists, and `DROP TYPE` without `IF EXISTS` fails for an unknown type. Both report a `TYPE`
  schema change.
- A type name the parser does not know becomes an unresolved user type; translation looks it up in the statement's
  keyspace (`Catalog::user_type`), inside collections and tuples too, for `CREATE TABLE`, `ALTER TABLE ADD` and
  `CREATE TYPE` (types may nest).
- A user type is stored and sent like a tuple: its column holds a JSON array in field order with `null` for unset
  fields, and the binary value is the fields' `[bytes]` in order. Metadata writes the UDT option (`0x0030`: keyspace,
  name, then each field's name and type). Frozen and non-frozen are treated alike, as for collections (D730).
- The table metadata keeps a user type with its whole definition (`udt<ks.name, field type, ...>`, `stored_name`), so
  reading a table's columns needs no type lookup; a later `DROP TYPE` does not change tables that use it.
- Values are written `{field: value, ...}` (a word or quoted name before `:` starts a field, so map literals with
  `true`, `false`, `null`, `NaN` or `Infinity` keys still parse as maps); unknown fields are refused.
- Left: `ALTER TYPE`, selecting a field (`home.street`), updating one field, and `system_schema.types`.
