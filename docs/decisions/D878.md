## D878 Live queries and GraphQL subscriptions over Server-Sent Events — Decided by the code-only session (2026-11-12, D355); roadmap M6a, D37

- A REST `GET /<table>` with `Accept: text/event-stream` stays open as a live query: the same PostgREST-style
  filters, ordering and paging, run again every interval, and the rows are sent as a `rows` event (a JSON array)
  each time they differ from the last event. A failing run sends an `error` event and ends the stream.
- A GraphQL `subscription` (D875's query root fields) sent to `/graphql` with `Accept: text/event-stream` is served
  in graphql-sse's distinct-connections mode: a `next` event with `{"data": ...}` each time the result changes, a
  `next` event with `errors` then `complete` on failure. Without that header a subscription is refused with a hint.
- Polling rather than change capture: the engine's change streams (CDC, D28) are per data model and not yet a
  per-query invalidation signal, and re-running the query in the signed-in user's session keeps roles and row
  security exact. The interval is one second (`X-EggDB-Live-Interval`, 100 ms to 60 s, sets another), and
  `X-EggDB-Live-Events: n` ends the stream after n events (tests and one-shot clients). A `: keep-alive` comment
  every 15 quiet seconds keeps proxies from closing the stream and finds clients that left; a write error ends it.
- `Endpoint::reply` now returns a reply tied to the store's lifetime, so a streamed body can run queries while it is
  sent. Each live query holds one connection thread, as every HTTP connection does until M6a's event loop.
- Left: WebSocket transports (`graphql-transport-ws`, Supabase-style realtime channels), change-driven invalidation
  instead of polling, and sending only the rows that changed.
