## D319 Key-value writes go into a savepoint's undo log: `ROLLBACK TO SAVEPOINT` in an `eggdb shell` block undoes the `put`, `del`, `incr`, `decr`, `expire`, `persist` and `cas` made after the savepoint, times to live and collection entries included — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap item 20 (M3), finishes D283's "Not yet", applies D9, D173 and D266, supersedes in part D283

D266 and D283 ran the shell's key-value commands on the write transaction a `BEGIN` block holds,
but refused the writes while a `SAVEPOINT` was set: the savepoint undo log (D173) recorded only
the session's own SQL writes, so `ROLLBACK TO SAVEPOINT` would have left them in place. A user
who set a savepoint to try something out could not touch keys until `RELEASE SAVEPOINT`.

**What users can do.** Inside a block, with any number of savepoints set, every key-space command
runs. `ROLLBACK TO SAVEPOINT s` undoes the key-value writes made after `s` together with the SQL
changes made after it, in the order they happened, and keeps everything before it; `RELEASE
SAVEPOINT s` keeps them in the block, where a rollback to an outer savepoint or `ROLLBACK` still
drops them; savepoints nest. Values, deletions, counters, times to live (set, replaced or removed
with `persist`) and entries of collections (D292) all come back exactly as they were. In
SQLite's dialect a `SAVEPOINT` outside a block begins one (D173), and the key-value commands join
it the same way. Embedded code gets the same with
`SharedWriteStore::with_open_transaction_undoable(session, work)`.

**How it works.**
- **The engine records what it changes.** `WriteTransaction` (`crates/eggdb/src/transaction.rs`)
  can keep a journal of its stored changes: while `journaled(work)` runs, each of the four
  functions every write goes through (`put_raw`, `put_raw_from_reader`, `put_if_absent_raw`,
  `delete_raw`) records the stored key and what it held before, read just before the change, for
  changes that happened only. A key's deadline records (D140) and a collection's prefixed entry keys
  are stored keys like any other, so the journal covers them without special cases, and a
  later piece of key-value state written through the same functions is covered too. Nothing is
  recorded and nothing is read when no journal is open, so transactions without a savepoint
  pay nothing.
- **One ordered undo log.** The session's undo log (`crates/eggdb-sql/src/session/savepoints.rs`)
  holds two kinds of entries, `Statement` (a SQL write, as before) and `Host` (a change made
  outside the session's statements). `Session::record_savepoint_undo` appends host entries when a
  savepoint is set in a block that writes, so SQL and key-value changes share one sequence and
  one set of savepoint marks: `ROLLBACK TO`, `RELEASE`, MySQL's same-name replacement and
  SQLite's savepoint-begun transaction need no second copy of their rules.
- **Restoring stored keys.** `KeyValueWrite::restore(key, previous)` puts a key back as it was,
  with a default of `put` or `delete`; the store behind `SharedWriteStore` overrides it to write
  the stored key directly (`WriteTransaction::restore_stored`), since `put` refuses the reserved
  keys of collections and times to live and would drop a time to live. Statement entries keep
  going through the temporary-table routing as before; host entries skip it.
- **The shell.** `crates/eggdb/src/cli/commands/shell_block.rs` runs every key-space command
  through `with_open_transaction_undoable`, which turns the journal on only when the session has a
  savepoint. The savepoint refusal is gone. A new refusal follows PostgreSQL: after a statement
  fails while a savepoint is set, the block refuses every statement until `ROLLBACK TO
  SAVEPOINT` or `ROLLBACK`, and now so do the key-value commands, with that message
  (`Session::failed_after_savepoint`; `transaction_status` keeps answering "in block" there,
  since the block can go on).

**Decided by research.**
- Journal stored changes in the engine rather than key-level changes in the shell: a key-level
  log would have to know how times to live and collections are laid out (two deadline keys per
  key, prefixed entry keys) and would miss whatever the engine adds later (collection counts,
  D320); the four stored-write functions are the one place every change passes.
- One undo log in the session instead of a second log in the shell: SQL and key-value writes in
  the same block can touch the same stored key, and only one ordered log puts it back right; the
  session already owns every savepoint rule of every dialect.
- Refusing key-value commands after a failed statement under a savepoint matches PostgreSQL, where
  every command of an aborted transaction fails until `ROLLBACK TO SAVEPOINT` or `ROLLBACK`
  (PostgreSQL manual, "SAVEPOINT" and "ROLLBACK TO SAVEPOINT"); the default shell dialect is
  PostgreSQL's.

Tests: shell tests (`crates/eggdb/src/cli/shell_tests.rs`) for `BEGIN; put a; SAVEPOINT s; put
b; del a; ROLLBACK TO SAVEPOINT s; COMMIT` leaving `a` and not `b` (checked with separate `get`
runs), `RELEASE SAVEPOINT` keeping writes through `COMMIT` and dropping them with `ROLLBACK`,
three nested savepoints with an inner release, times to live set, replaced and removed and
collection entries put and deleted after a savepoint, key-value and SQL writes undone together,
SQLite's savepoint-begun transaction, and the refusal after a failed statement; a library test
in `crates/eggdb/src/sql.rs` checking times to live and collection entries come back exactly;
and the `with_open_transaction_undoable` doc example.

Left: the same savepoint undo for key-value writes made through other front ends inside a SQL
block (a pgwire or MySQL session's key-value functions, `eggdb serve`'s RESP commands do not join
SQL blocks yet), and the plan view's or MCP's use of savepoints with key-value writes, none of
which exists today; and a bound on the savepoint undo log as a whole (each statement's
before-images stop at 1 GiB with `53200`, D317, but the log keeps every statement's and
key-value write's entries until `RELEASE`, `ROLLBACK TO` or `COMMIT`; roadmap M3).
