## D1199 `CREATE DATABASE ... TEMPLATE`: tenants isolated by database — Decided by the code-only session (2026-11-17, D355); roadmap M6b (D32, D234)

- **What users get.** On a server that serves a directory of databases, PostgreSQL's `CREATE DATABASE acme TEMPLATE tenant_template` makes the new database a copy of the template database at its last commit: its schema, rows, roles, grants and owners, while sessions on the template keep working. A SaaS application keeps one template database and gives each tenant a database of its own, the strongest isolation beside D234's rows and D764's schemas: separate files, separate roles, one backup each. `template0` and `template1` still mean an empty database.
- **How.** The parser reads `TEMPLATE [=] name` among `CREATE DATABASE`'s options; the served-databases interface gains `create_from`, which the server's directory implements with the online copy `backup` already uses (`Database::backup_to`), then opens the copy as a served database, with the tenant-directory layout when one is set. Another server, or none, refuses it as before (`0A000`), and a missing template is `3D000 template database "..." does not exist`.
- **Left.** Applying `upgrade_tenant_schemas` across tenant databases (one database at a time from outside), and MySQL's and SQL Server's ways of copying a database.
- **Proof.** A unit test makes a database from a template through a fake directory and refuses a missing template.
