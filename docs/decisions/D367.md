## D367 MySQL unique keys on tables partitioned by an expression — Decided by the code-only session (2026-11-10, D355); closes one of D316's leftovers

PostgreSQL refuses primary keys and unique constraints when a partition key has an expression,
and EggDB refused them in every dialect. MySQL allows them: every unique key, the primary key
included, must contain every column the partitioning expression reads (`1503`), so
`PRIMARY KEY (id, sold)` with `PARTITION BY RANGE (YEAR(sold))` is the usual table.

- **Rule.** In the MySQL dialect the columns an expression part reads count as key columns, so
  `CREATE TABLE` and `CREATE UNIQUE INDEX` (on the table and, through D316's propagation, on its
  partitions) accept a unique key that covers them and refuse one that does not with `1503 A
  UNIQUE INDEX must include all columns in the table's partitioning function`. Other dialects keep
  PostgreSQL's refusal.
- **Why per-partition checks suffice.** Two rows with the same unique key have the same values
  in every column the expression reads, so the expression gives the same value and both rows
  land in one partition, where its own unique index finds the duplicate.

**Left:** user-defined `IMMUTABLE` functions in keys need routine calls during routing, which has
no reader or table cache today; a design first.

**Status:** code written, unbuilt (code-only mode, D355).
