## D986 Search that respects each user's permissions — Decided by the code-only session (2026-11-13, D355); roadmap M8, enterprise search (D56, D22)

- In SQL nothing new is needed: row security policies (D22) already filter what `@@`, `ts_rank` and the other
  search functions see, so a table of documents with a policy on its readers column searches by permission.
- The Elasticsearch-compatible API gets readers: `eggdb serve --es-users <file>` lists users who may only read, one per
  line as `name:sha256-of-password:group,group`. The file holds digests, never passwords, so it can be kept with the
  deployment's configuration.
- A reader sees a document only when its permission field (`--es-permission-field`, a dotted path into `_source`,
  `readers` by default) holds the reader's name, one of the reader's groups, or `*`, as a string or in an array of
  strings. A document without the field is hidden from readers: a missing field is never read as "everyone".
- The filter is applied where documents are gathered for a search, so hits, totals, aggregations, `_count`,
  `_msearch`, scrolls and points in time agree, and to `_doc`, `_source` and `_mget`, where a hidden document answers
  as missing (`404`), so its existence is not revealed.
- Readers are refused (`403 security_exception`) every request that writes or changes settings; only `GET`, `HEAD`,
  searches, counts, `_mget`, `_analyze`, `_field_caps`, scrolls and closing a point in time are open to them. The
  `--user` account keeps full access and sees every document.
- This follows document-level security as OpenSearch's security plugin and Elasticsearch offer it, in EggDB's own
  simpler form: one permission field instead of role queries. Field-level security and role queries are left.
