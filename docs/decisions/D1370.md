## D1370 The full-value view reads a RESP aggregate's elements — Decided by the code-only session (2026-11-25, D355); roadmap M6e "The full-value view of a RESP aggregate" (D329), designed in `docs/ux/data-models.md` section 8

- **What users get.** On a RESP keys tab, `Enter`, `F2` or a double-click on the `value` cell of a hash, list, set, sorted set or stream opens the full-value view reading `Loading…` under `value · hash · 12 fields`, reads the elements off the window's thread, and shows them as pretty-printed JSON: an object for a hash, arrays for a list and a set, `[member, score]` pairs for a sorted set, `{"id", "fields"}` entries for a stream. `Copy` copies that JSON. A key gone since the page was read keeps its `(gone)` cell and opens nothing; an error shows in the view's body, dimmed.
- **How.** The tab asks for an aggregate read as it asks for a page (`RunRequest::aggregate`), so it runs on the connection's worker with the run's cancel handle and `Stop`; the worker selects the key's database and sends one command (`HGETALL`, `LRANGE 0 9999`, `SMEMBERS`, `ZRANGE 0 9999 WITHSCORES`, `XRANGE - + COUNT 10000`) in one pipeline, and `resp_keys::aggregate_json` turns RESP2's flat pairs and RESP3's maps and pair arrays alike into JSON. Scores stay numbers when they spell finite numbers.
- **Left.** The `JSON` / `Table` segmented control and the table form, `SSCAN` for sets over 10,000 members, the `… showing the first 10,000 of N` line, and `Esc` cancelling the read.
- **Proof.** A unit test turns a hash (flat and RESP3 map), a sorted set, a list and a stream into the JSON the design shows and checks the commands each type sends.

**Status:** code written, unbuilt (code-only mode, D355).
