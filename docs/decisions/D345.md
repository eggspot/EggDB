## D345 MySQL's `EXPLAIN FORMAT=JSON` as MySQL 8's `query_block`, `(cost=... rows=...)` and the `Aggregate`, `Group aggregate` and `Stream results` iterators in `FORMAT=TREE`, and `EXPLAIN [ANALYZE]` of multi-table `UPDATE` and `DELETE` and of `TABLE t`, all from EggDB's own plan and an EggDB cost model — Decided by the build loop (batch 6, part P10, 2026-11-10); roadmap M6c, extends D327, D312 and D109, applies D10, D12 and D25

D327 gave MySQL's dialect the iterator tree of `EXPLAIN FORMAT=TREE` and `EXPLAIN ANALYZE`, but
only for a `SELECT`, with no estimates and no aggregation iterators, and refused `FORMAT=JSON`,
which MySQL Workbench's visual explain and many tools read. D342 made MySQL's `TABLE t [ORDER
BY] [LIMIT]` a query, which `EXPLAIN` still refused. The public reference followed is MySQL 8.4's
reference manual ("EXPLAIN Statement", "Obtaining Information with EXPLAIN ANALYZE", "EXPLAIN
Output Format"), whose examples give the shape of each form.

- **One planned statement for every MySQL form.** `explain::plan` plans the statement once and
  hands every renderer a `Planned`: the planner's `ExplainedQuery`, the write on top of it for an
  `UPDATE` or `DELETE` (`PlannedWrite`: which sources are written and whether the statement joins
  other tables), and, for the tree and JSON forms only, the row count of every table the plan
  reads (`TableRows`). The planner now also says how a `SELECT` aggregates
  (`ExplainedQuery::grouping`: whether it has groups, its aggregate calls and its `HAVING`).
  PostgreSQL's, Oracle's, SQL Server's and SQLite's plans are unchanged byte for byte.
- **The cost model, EggDB's own.** MySQL's numbers come from its optimizer's cost constants and
  InnoDB's statistics; EggDB has neither, so its estimates are its own and **differ from what
  MySQL prints for the same data**. A table's row count is the one `ANALYZE TABLE` recorded, or,
  for a table never analyzed, its rows counted up to 10,000 when the plan is made (reading keys
  only, so `EXPLAIN` of a huge unanalyzed table costs at most 10,000 key reads and estimates at
  most 10,000 rows). A partitioned table's rows live in its partitions, so its count is the
  one `ANALYZE` recorded or 0. From that:
  - a full or index scan reads every row; a single-row lookup reads one; an index lookup or range
    scan reads the table's rows times a tenth per equality and a third per range bound it uses;
  - reading `n` rows costs `0.25 + 0.1 n` (one seek, then a row each);
  - a `WHERE` keeps a tenth of the rows per equality (and `IS NULL`), nine tenths per `<>`, a
    third per other comparison, a ninth per `BETWEEN`, a tenth per item of an `IN` list (at most
    half), products for `AND`, `1 - Π(1 - s)` for `OR`, `1 - s` for `NOT`;
  - a nested loop costs its outer side plus its outer rows times its inner side; a hash join
    costs both sides plus `0.1` per row of each; an `ON` condition keeps its fraction of the
    pairs unless a key lookup consumed it;
  - an aggregate without groups gives one row, with groups a tenth of its input (at least one),
    each costing `0.1` per input row; `HAVING` keeps its condition's fraction;
  - a sort adds `0.1 n log2 n` and gives at most `LIMIT + OFFSET` rows; a limit gives at most its
    count after the offset.

  Numbers print as MySQL 8 prints them: three significant digits below 100 (`0.55`, `1.67`),
  whole numbers up to 100,000, and engineering notation above (`998e+3`, `1.01e+6`).
- **`FORMAT=TREE`.** Every iterator but `Hash` and the `Select #n` labels ends in
  `  (cost=c rows=r)`, before `ANALYZE`'s ` (actual time=...)`. A `SELECT` with aggregates and no
  `GROUP BY` puts `Aggregate: count(0), sum(t1.b)` (`count(*)` is `count(0)`, as MySQL prints it)
  over its source and `Filter:`; one with `GROUP BY` puts `Group aggregate: ...` there, or
  `Group (no aggregates)`; a `HAVING` is a `Filter:` above it. A sort over an aggregate or a join
  has `Stream results` between them. Under `ANALYZE` the aggregate (or the `HAVING` filter above
  it) carries the groups handed up and the source under it the rows it read.
- **`FORMAT=JSON` (MySQL's version 1).** One row in the `EXPLAIN` column holding MySQL's
  document, two spaces per level: `query_block` with `select_id`, `cost_info.query_cost`, then
  `ordering_operation` (`using_filesort`, and `cost_info.sort_cost` when EggDB sorts), then
  `grouping_operation` (`using_temporary_table: true`, as EggDB groups in a hash table), then
  `table` for one table or `nested_loop` for a join. Each table has `table_name`,
  `access_type` (`ALL`, `const`, `ref`, `eq_ref`, `range`, `index`, as the tabular form),
  `possible_keys`, `key`, `used_key_parts`, `ref` (`const` for a lookup on constants),
  `rows_examined_per_scan`, `rows_produced_per_join`, `filtered`, `using_join_buffer: "hash
  join"`, `backward_index_scan`, `cost_info` (`read_cost`, `eval_cost` at `0.1` per row
  produced, `prefix_cost`) and `attached_condition` (the `WHERE` on the last table unless a key
  lookup consumed it, the `ON` condition on a hash or loop join's inner table). A query without
  a table is `"message": "No tables used"`; a `UNION ALL` read through a derived table is
  `union_result` with one `query_specifications` block per branch. `EXPLAIN ANALYZE
  FORMAT=JSON` answers 1235 "... 'EXPLAIN ANALYZE with JSON format'", as MySQL 8.4 does with
  `explain_json_format_version=1`, its default.
- **Writes.** MySQL 8.4's manual says `EXPLAIN ANALYZE` "can be used with SELECT statements,
  multi-table UPDATE and DELETE statements, and TABLE statements". A multi-table `UPDATE` or
  `DELETE` (`UPDATE t1 JOIN t2 ... SET`, `UPDATE t1, t2 SET`, `DELETE t1 FROM ...`, `DELETE FROM
  t1 USING ...`) is planned as the `SELECT` over its whole `FROM` and `WHERE` that it reads, and
  every MySQL form shows it: the tree puts `Update t1 (buffered)` or `Delete from t1 (buffered),
  t2 (buffered)` over the join (EggDB collects every matched row before it writes, which is what
  `buffered` means), JSON marks each written table `"update": true` or `"delete": true`, and the
  tabular form has a row per table. `EXPLAIN ANALYZE` runs the write, and its top iterator
  carries `(actual time=t..t rows=0 loops=1)`: the write iterator hands up no rows, as in MySQL;
  the steps under it are not measured. A single-table `UPDATE` or `DELETE` under `EXPLAIN
  ANALYZE` keeps MySQL's refusal, error 1235 "... doesn't yet support 'EXPLAIN ANALYZE for this
  statement'", raised when the statement is read so nothing runs; under `FORMAT=TREE` it answers
  `-> <not executable by iterator executor>`, and its JSON is MySQL's single-table form, with no
  `cost_info` and no `rows_produced_per_join`.
- **`TABLE t`.** `EXPLAIN`, `EXPLAIN FORMAT=TREE|JSON|TRADITIONAL`, `EXPLAIN ANALYZE` and
  PostgreSQL's `EXPLAIN` accept `TABLE t` (with MySQL's `ORDER BY` and `LIMIT`) and explain it as
  the `SELECT * FROM t` it is.
- **Bounded and panic-free.** The selectivity walk stops at 32 levels, aggregate collection at
  32, the row count at 10,000 keys; every list access is checked and numbers that are not finite
  print as 0.

Decided by research:
- **Single-table writes stay refused under `ANALYZE`.** MySQL 8.4's manual lists only
  multi-table `UPDATE` and `DELETE`, and MySQL answers `ER_NOT_SUPPORTED_YET` (1235) for the
  single-table ones; the plan's review (round 2, item 14) kept that text.
- **`Group aggregate` for every `GROUP BY`.** MySQL prints `Group aggregate` over a sorted input
  and `Aggregate using temporary table` under `Table scan on <temporary>` otherwise. EggDB groups
  in one pass with a hash table and no second scan, so the tree shows one `Group aggregate` line
  over the source (and JSON's `grouping_operation` says `using_temporary_table: true`).
- **Costs differ from MySQL's on purpose.** Copying MySQL's numbers would need its cost
  constants, InnoDB's page statistics and its optimizer's formulas; the model above is stated
  here so the numbers can be read and compared between EggDB plans, which is what tools and
  agents use them for.
