## D320 Collections keep their entry counts up to date on every write, so `eggdb collection list` and `stats --collections` are instant; collections are renamed in `eggdb shell` and `eggdb ui`, and long drops show their progress — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap item 26 (M4), finishes D292's "Not yet" list but the drivers and MCP writes, applies D2, D6, D9, D15, D20 and D35. Security-critical: it changes what the file stores (D35)

D292 counted a collection by reading every key, so `stats --collections` took time in proportion
to the data, `collection list` showed no counts, renaming lived only on the command line, and a
long drop printed nothing until it ended.

- **What users can do.**
  - `eggdb collection list` prints each name with its entry count right-aligned after the longest
    name (`cache     1,204 entries`); in JSON the `collections` array is unchanged and `counts`
    is added with `stats --collections`'s objects.
  - `eggdb stats --collections` reads one record per collection, so it is as instant as `stats`.
  - `eggdb shell` runs `collection list|add|delete|move|rename` as the command line does, without
    the file. It follows a rename of the collection in use and leaves a deleted one. Inside a
    transaction block `list` reads the last commit, and `add`, `delete` and `move` are refused.
  - `eggdb ui` renames the highlighted collection with `e` in the picker, and the shown one with
    `e` in the sidebar (prefilled editor, the add editor's checks). It follows the shown
    collection, and the default key space and a read-only file keep their names.
  - `eggdb collection delete` on a terminal shows
    `deleting collection cache: 120,000 of 1,000,000 entries…` on stderr, every second.
  - The library adds `Database::drop_collection_with_progress` and `DropProgress`.
- **The count record.** Under the collections prefix, `0x07` + the collection's 4-byte number
  holds a version byte (1) and three big-endian `u64`s: the collection's stored `0x03` keys,
  their bytes without the ten-byte prefix, and their values' bytes. `create_collection` writes it
  as zeros. A drop deletes it in its first commit, before any key goes. A rename leaves it, since
  it is keyed by number.
- **Kept on every write, written once per commit.** `WriteTransaction` keeps, per collection
  number it touched, the count it read and whether it changed. The four stored-write functions
  (`put_raw`, `put_raw_from_reader`, `put_if_absent_raw`, `delete_raw`) adjust it. For a
  collection with a count, a write first reads the old value's length through the new
  `eggdb_storage::WriteTransaction::value_len`, which reads no overflow page past the first. The
  commit writes each changed count once, after the expiry sweep and the drop steps, so their
  removals count too. Puts, replaces, `put_if_absent`, counters, compare-and-set, deletes, the
  sweep, drops and rollbacks all go through those four functions. A rolled-back transaction
  never writes its counts. The default key space pays a prefix compare per write.
- **Savepoints (D319).** A savepoint's undo log replays stored changes through the same
  functions, so a key put back counts again. For a count record itself, the journal keeps the
  count as the transaction holds it rather than as stored, so undoing a drop after writes to the
  same collection in the same savepoint restores the right count.
  `a_journaled_drop_and_put_undone_in_reverse_restore_the_count` and the shell's savepoint test
  check it.
- **Files without counts.** A collection made before D320 has no record and is counted by
  reading its keys. `Database::collection_stats` on a writable database whose writer is free
  commits the count (`try_begin_write`; a busy writer just gets the scanned answer). `collection
  list` and `stats --collections` open the file read-only. When they meet an uncounted
  collection they reopen it for writing for a moment, with no busy wait, and keep the counts;
  they skip that when another program holds the file. From then on every write keeps the count.
  Writes to an uncounted collection change nothing, so nothing is half counted.
- **File format (D20, D35).** The first commit that writes a count record sets the new
  read-only-compatible feature bit 1, `COLLECTION_COUNTS`. A release before D320 would write a
  collection's keys without changing its count, so it opens such a file read-only. It can still
  read every key: the record sits in the reserved prefix that it already hides. A count record
  with a version above 1 is `Incompatible`; one of any other length is `Corrupt`, an error and
  never a panic. `backup`, `compact` and snapshot copies carry the records and the feature bits
  as they are. `export` and `import` rebuild the counts through `create_collection`.
  `check`'s entry total includes the records, as it includes the catalog and name records.
- **Decided by research.**
  - *Counts include expired keys until the sweep removes them.* The count is the stored keys,
    the only figure a write can keep without a clock. Redis's `DBSIZE` and its keyspace
    statistics count keys whose time has passed in the same way, until they are reclaimed.
    `scan` keeps hiding them, and the docs say so wherever counts are shown.
  - *Counts live in the file, not in memory.* That makes `stats` instant from a cold open and
    on a read-only file. One record per changed collection per commit keeps the cost to one
    lookup per collection write (D6). That was D292's objection to stored counters, now paid
    for by the instant answer the roadmap asked for.
  - *A read-only-compatible bit, not an incompatible one.* An older release reads correctly and
    only its writes would be wrong, which is ext4's case for read-only compatible (format.md).
  - *`e` renames in the UI.* `e` means "edit what is highlighted" there, `m` and `r` are taken.
    The CLI verb stays `move` (D143).
  - *The shell takes the command line's noun-verb `collection` commands* rather than new dot
    commands, so they behave exactly like the CLI. `.collection` keeps choosing the key space.
