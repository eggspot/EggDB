## D1153 A JNI binding for the JDBC driver on Java before 22 — Decided by the code-only session (2026-11-14, D355); roadmap M5 (D16, D182)

- **One interface, two bindings.** The JDBC driver's native calls now sit behind `NativeCalls`: open, connect,
  execute, prepare, bind, run, step, columns, reset, finalize, and COPY in and out. Two classes implement it:
  - `FfmCalls`, Java's foreign function and memory API (the code `NativeSession` and `NativeStatement` held
    before);
  - `JniCalls`, the new JNI binding in `drivers/java/jni/eggdb_jdbc.c`, a library of its own (`eggdb_jdbc`)
    found through `-Deggdb.jni=<path>`, `EGGDB_JNI_LIBRARY` or `java.library.path`.

  `NativeSession` and `NativeStatement` hold plain `long` handles and call whichever binding is in use.
- **Choosing the binding.** It is chosen once:
  - on Java 22 or newer, the foreign function binding;
  - on older Java, JNI;
  - when `FfmCalls` cannot load, JNI as well;
  - `-Deggdb.binding=jni|ffm` overrides the choice.
- **Shared encoding.** Typed parameters are encoded once by `Bindings` for both paths: integers, `BigInteger` in
  range, reals, booleans, blobs, and text for the rest. The JNI side returns results in the same flat byte-array
  form as the Kotlin binding, and errors as `EggDbNativeException`, turned into `SQLException` with its SQLSTATE.
- **Java 17 is the floor.** Every JDBC class but the five foreign-function ones (`FfmCalls`, `NativeLibrary`,
  `KeyValueApi`, `EggDbTransaction`, `EggDbKeyValue`) compiles with `--release 17`, so the driver loads on Java 17
  and 21. The direct key-value API (`EggDbKeyValue`) still needs Java 22, which its Javadoc already states.
  Java 17 is the oldest release still in wide support, and the driver's records and pattern matching need 16.
- **CI.** `scripts/c-api/check.sh` compiles the driver that way, builds the JNI library with warnings as errors,
  and runs the Java check twice: once through the foreign function API, once with `-Deggdb.binding=jni`.
- **Not reused from Kotlin.** The Kotlin JNI library is bound to the Kotlin driver's class names in the same
  package, so the JDBC binding has its own library. Both follow the same flat-result layout.
