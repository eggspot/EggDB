## D805 X25519MLKEM768 in TLS 1.3 — Decided by the code-only session (2026-11-12, D355); roadmap M6b, post-quantum key exchange

- `named_group::X25519_MLKEM768` (0x11ec) joins the groups. TLS 1.3 prefers it (`TLS13_GROUPS`: X25519MLKEM768, X25519,
  P-256); TLS 1.2 keeps `SUPPORTED_GROUPS` (X25519, P-256), since the hybrid group is defined for TLS 1.3 only.
- Shares follow the IETF hybrid design: the client sends the ML-KEM-768 encapsulation key then its X25519 public key
  (1,216 bytes); the server answers with the ML-KEM-768 ciphertext then its X25519 public key (1,120 bytes); the shared
  secret is the ML-KEM secret then the X25519 secret (64 bytes).
- The client sends two key shares, X25519MLKEM768 and X25519, so a server without the hybrid group still answers
  without a HelloRetryRequest; it uses whichever ephemeral key matches the server's chosen group.
- The server's side is `server_key_exchange(group, client_share, fill_random)`, which encapsulates for the hybrid group
  and does plain ECDHE for the others; a malformed encapsulation key or a low-order X25519 key is refused with
  `illegal_parameter`.
- `SessionInfo.key_exchange_group` reports the group on both sides, so operators can see post-quantum connections.
