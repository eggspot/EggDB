## D1264 TRUNCATE in logical replication — Decided by the code-only session (2026-11-18, D355); roadmap logical replication to PostgreSQL subscribers (D1243, D1245, D1263)

- **What users get.** `TRUNCATE` on a published table reaches PostgreSQL subscribers as one pgoutput `Truncate` message, when the publication publishes truncates (the default), instead of one delete per row; a publication with `publish = 'insert, update, delete'` no longer sends a truncation at all, and one with `publish = 'truncate'` alone now sends it. Row filters do not apply to it, as in PostgreSQL. Rows written to the table after the truncation in the same transaction arrive as inserts.
- **How.** `TRUNCATE` still deletes the rows and now also counts the truncation under a small key of its own per table (key space `0x22`), which capture without triggers records with the rows. Logical decoding turns that key into a `Truncate` change placed first in its transaction, drops the table's row deletions of that transaction and reads its other row changes as inserts. Debezium-style change data capture ignores the key and keeps sending the deletions, as before. The key belongs to its table, so a session limited to some tables (`--tables`) may truncate those it may change. `DROP TABLE` removes the key.
- **Left.** The `CASCADE` and `RESTART IDENTITY` option bits, which are sent as 0; streamed and two-phase transactions.
- **Proof.** A unit test decodes a captured transaction with a truncate mark, one deleted row and one written again, into a truncate and an insert; the walsender test builds the `Truncate` message.
