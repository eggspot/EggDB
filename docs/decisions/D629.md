## D629 MySQL partition maintenance statements — Decided by the code-only session (2026-11-12, D355); roadmap M2, D169, D358, D360

`ALTER TABLE t ANALYZE|CHECK|OPTIMIZE|REPAIR|REBUILD PARTITION p1, p2 | ALL` appear in DBA scripts,
pt-online-schema-change's checks and Percona's maintenance jobs. D358 and D360 left them out, so
those scripts stopped at a syntax error.

- The MySQL dialect parses the five forms as one `AlterAction::MaintainPartitions` with the named
  partitions, or `ALL`.
- Running it checks what it can, and does nothing more:
  - the table must be partitioned;
  - every named partition must exist, with the same errors as `DROP` and `TRUNCATE PARTITION`.
  EggDB keeps no per-partition statistics, fragmentation or damage for these statements to act
  on.
- The statements answer as an `ALTER TABLE`. MySQL answers `ANALYZE`, `CHECK`, `OPTIMIZE` and
  `REPAIR` with a result set (`Table`, `Op`, `Msg_type`, `Msg_text`), which is not produced: a
  known difference.
- They change no data, so the destructive-statement check lets them pass.
- A MySQL test runs each form, refuses an unknown partition, and finds the rows unchanged.

Still left from the item: Oracle's `MERGE PARTITIONS a TO b` range form.
