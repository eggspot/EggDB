## D1339 A top-N for DISTINCT ON with LIMIT, and why sorts do not spill yet — Decided by the code-only session (2026-11-25, D355); roadmap M5 "Sorts, joins and groups that spill to disk ... and a top-N for ... DISTINCT ON limits" (D100, D341)

- **What users get.** `SELECT DISTINCT ON (...) ... ORDER BY ... LIMIT n [OFFSET m]` holds at most `n + m` rows however many it reads, instead of sorting every row and then keeping the first of each group: PostgreSQL's usual "latest reading per sensor, first ten sensors" query no longer needs memory for the whole table.
- **How.** `DistinctTopRows` keeps, per group (the `DISTINCT ON` values by their equality keys), the group's first row in sort order and arrival order, and at most `n + m` groups. A row replaces its group's row only when it sorts strictly first, so ties keep the earliest row as the full sort's stable order does. A new group enters only when it sorts before the last kept group, which it then evicts. An evicted group can never belong to the answer: the groups that beat it only get better. `WITH TIES` and `PERCENT` keep the full sort.
- **Why no spilling yet.** The executor hands every query's result on as one materialized list, so a sort that spilled its input to disk would still build its whole output in memory; spilling sorts, joins and groups pays only once results stream (the "resumable executor that streams rows" item). It is left for that work, with `PERCENT`, which needs the row count first.
- **Proof.** A test compares `DISTINCT ON` with four `LIMIT`/`OFFSET` pairs, zero and past the end included, over 2,000 rows in 40 groups, with the same query's full answer cut by hand.
