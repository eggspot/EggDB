## D773 Crypto-shredding with per-subject keys (eggdb_shredding) — Decided by the code-only session (2026-11-12, D355); roadmap M6b, crypto-shredding (D26, D53, D231, D246)

- `CREATE EXTENSION eggdb_shredding` gives each data subject a random 256-bit key, made on the subject's first
  `seal` and stored only wrapped (AES-GCM, `eggdb_seal`, D751) by a key-encryption key the session sets in
  `eggdb_shredding.wrapping_key`. The wrapping key never touches the file, so a stolen file or backup holds nothing
  that opens a subject's values.
- `shred(subject)` replaces the wrapped key with NULL and records it. The subject's sealed values stay in the tables,
  the history and every backup, but without the key they are noise: that is how erasure reaches copies that a
  `DELETE` cannot. A backup taken before the shred still holds the wrapped key, so the guarantee for older backups is
  that the wrapping key is kept apart from them (in a KMS or the secrets store), and rotating it after a shred makes
  older wrapped keys useless too.
- Holds (`place_hold`, `lift_hold`) override shredding for legal and regulatory needs: `shred` returns false and logs
  `waiting for hold <name>`, to be run again once the hold is lifted.
- The old key bytes leave the file's pages when they are rewritten (`eggdb compact`); rewrapping every subject key
  under a new wrapping key, transparent sealing of columns by trigger, and per-column and per-tenant page keys in the
  storage engine are left.

**Status:** code written, unbuilt (code-only mode, D355).
