## D1280 ODBC parameter arrays — Decided by the code-only session (2026-11-18, D355); roadmap M6 ODBC driver (D1278, D1279)

- **What users get.** Bulk loads that bind arrays of parameter values (`SQL_ATTR_PARAMSET_SIZE` above 1, as SSIS, Informatica, Talend and most ETL tools do for inserts) run the statement once per set: column-wise (each parameter's buffer an array; fixed-size C types step by their size, others by `buffer_length`) or row-wise (`SQL_ATTR_PARAM_BIND_TYPE` the size of one set's structure). `SQL_ATTR_PARAMS_PROCESSED_PTR` gets the sets processed and `SQL_ATTR_PARAM_STATUS_PTR` each set's status; `SQLRowCount` gives the rows all sets changed.
- **How.** Each set's values are read at its element's address and run as one statement, in the connection's transaction or autocommit. The run stops at the first set that fails: that set is `SQL_PARAM_ERROR`, the later ones `SQL_PARAM_UNUSED`, and the call returns `SQL_SUCCESS_WITH_INFO` when earlier sets ran, `SQL_ERROR` when the first one failed, with the failure in the statement's diagnostics.
- **Left.** Sending the sets as one batch to the engine (each set is a round of its own), `SQL_ATTR_PARAM_OPERATION_PTR` to skip sets, and data at execution (`SQLParamData`, `SQLPutData`).
- **Proof.** The ODBC test inserts three ids in one call, the third a duplicate, and reads the processed count, the statuses and the two rows stored.

**Status:** code written, unbuilt (code-only mode, D355).
