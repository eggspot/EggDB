## D199 MySQL stored programs compile onto the shared routine interpreter — Decided by the build loop (by judgement, 2026-10-31); refines D27 and D106

Part 4.M10-2 asks for MySQL procedures, functions, triggers and events.

- **One interpreter.** PL/pgSQL and PL/SQL already compile into the routine interpreter's
  program (blocks, variables, branches, loops, labels, raised errors). MySQL's compound
  statements compile into the same program (`RoutineLanguage::MySql`, compiled in
  `parser/mysql_routines.rs`), and the interpreter runs their SQL in the MySQL dialect, so
  expressions, types and functions inside a body behave as in the rest of a MySQL session.
  `REPEAT ... UNTIL` becomes a loop that exits on its condition at the end; `LEAVE` and
  `ITERATE` become the interpreter's labelled exit and continue; a `CASE` with no matching
  branch raises SQLSTATE `20000`; `SIGNAL` raises its SQLSTATE with `MESSAGE_TEXT`.
- **Stored as written.** A routine keeps its `CREATE` text with dialect MySQL, as the other
  dialects' routines do, and is compiled again when loaded.
- **OUT parameters through user variables.** `CALL p(@x)` assigns the procedure's output to
  `@x` after the call commits, as MySQL clients expect; the call itself returns no row.
- **Refused, not approximated:** handlers, cursors, named conditions and `GET DIAGNOSTICS` are
  errors that say so at `CREATE` time. A MySQL `CONTINUE` handler resumes after the failing
  statement, which the interpreter's exception blocks (rolling back to the block start) do not
  model; it needs its own step kind.

Left: handlers, cursors (`DECLARE ... CURSOR`, `OPEN`, `FETCH`, `CLOSE` with `NOT FOUND`),
named conditions, `RESIGNAL`, `GET DIAGNOSTICS`, user and system variables set inside bodies,
compound bodies in triggers checked against this compiler, events (4.M10-3), `SHOW CREATE
PROCEDURE` and `information_schema.ROUTINES` details, and MySQL error numbers on failures.
