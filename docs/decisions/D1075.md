## D1075 STARTTLS for SMTP and IMAP — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D56, D892, D893)

- With `eggdb serve --tls-certificate --tls-key` (or `--tls-self-signed`), the mail listeners secure
  connections with the same certificate as the SQL listeners. The setup reaches them as a new
  `eggdb_mail::ServerConfig::tls`.
- **SMTP** (RFC 3207):
  - `EHLO` lists `STARTTLS` until the connection is secured.
  - `STARTTLS` answers `220 2.0.0 Ready to start TLS`, runs the handshake, and forgets the earlier
    greeting and envelope, as the RFC asks.
  - A second `STARTTLS` is `503`; without a certificate it is `454`.
  - Plain-text delivery stays allowed, since other mail servers may not use TLS.
- **IMAP** (RFC 3501 §6.2.1, RFC 2595):
  - Until the connection is secured, the greeting's and `CAPABILITY`'s list replaces `AUTH=PLAIN` with
    `STARTTLS LOGINDISABLED`.
  - `LOGIN` and `AUTHENTICATE` are answered `NO [PRIVACYREQUIRED]`, so the password never crosses in plain
    text.
  - `STARTTLS` answers `OK Begin TLS negotiation now` and runs the handshake.
- The two servers now read and write through one stream (`transport.rs`: plain, TLS or closed) inside a
  `BufReader`, instead of a cloned socket pair, so the stream can be swapped for its TLS form mid-connection.
  Bytes a client pipelined before the handshake end the connection, closing RFC 3207's injection hole.
- Tested: an IMAP client is refused before `STARTTLS` and signs in after it, over EggDB's own TLS client.
- Left: implicit TLS ports (465 and 993), `STARTTLS` and `AUTH` toward `--smtp-relay`, and JMAP over HTTPS.
  JMAP needs TLS in the shared HTTP layer, where every HTTP listener can use it.
- Learned from: RFC 3207, RFC 3501 and RFC 2595. No mail server source was read.
