## D121 The built-in MCP server, part 2: `write_sql` under `--allow-write`, destructive statements confirmed by the user, the watchdog never ending a write that began to commit — Decided by the build loop (owner's spec of 2026-10-28, two plan reviews and research); plan item 49b-1, applies D9, D11, D35, D45, D119, D120

Item 49 lets AI agents use an EggDB database through `eggdb mcp` (D119, D120). This slice, 49b-1,
lets them change it when the user allows it. `--tables` (49b-2) gets a decision of its own.

**A separate write tool.** `eggdb mcp <file> --allow-write` adds one tool, `write_sql`; `run_sql`
and every other tool stay read-only on every server. A tool's MCP annotations describe the tool,
not one call, so a `run_sql` that could write would have to drop `readOnlyHint` and clients
would ask the user before every read; with two tools the reads keep `readOnlyHint: true` and can
be approved once, `write_sql` carries `readOnlyHint: false, destructiveHint: true,
idempotentHint: false`, and only `write_sql` opens the file read-write (the exclusive lock), so
reads never block the user's writers longer than in 49a. Without `--allow-write`, `write_sql` is
not listed, and a call to it answers `read_only`, naming the missing grant, rather than "unknown
tool". A write sent to `run_sql` answers `read_only` with the fix "Send it with write_sql".

**One statement, one transaction.** `write_sql` runs one statement under 49a's rules (no second
statement, no transaction control, no `COPY`). It commits on its own when it succeeds: on Oracle,
where a statement opens a block, the server sends its own `COMMIT` through `Session::execute`
after a successful statement (`Session::in_block`); a failed statement changes nothing. Each
call may change at most 256 MiB (the bytes of the keys and values it writes), counted as it
writes; past that the call is rolled back and answers `write_too_large`. A file the server cannot
open for writing answers `not_writable` with a fix; there is no startup check, since a file's
permission bits do not say whether this user may write it.

**Destructive statements.** `eggdb_sql::destructive_statement` parses the text the way
`run_one_statement` does, with no database, and classifies it with an exhaustive `match` over the
statement types, so a statement type added later must be classified to compile. Destructive:
`DROP` of a table, view, index, sequence or schema; `ALTER TABLE ... DROP COLUMN`, `DROP
CONSTRAINT` and MySQL's `DROP PRIMARY KEY` (the rows that break the dropped rule cannot be told
apart afterwards); a column's type change (`ALTER COLUMN ... TYPE`, MySQL's `MODIFY` and
`CHANGE`); `TRUNCATE` (where the dialect has it); `DELETE` and `UPDATE` whose `WHERE` names no
column of the target table, or that have none (`WHERE 1 = 1`, `WHERE EXISTS (SELECT ... FROM
other)`; a column of the target inside a subquery does not count, which errs toward asking).
Not destructive: `INSERT` in every form (`REPLACE`, `INSERT OR REPLACE`, `ON DUPLICATE KEY
UPDATE`), `CREATE` including `CREATE OR REPLACE VIEW`, `ALTER SEQUENCE ... RESTART`, renames,
`ADD COLUMN`, `ADD CONSTRAINT`, `COMMENT ON`, `PRAGMA` (session-only), `EXPLAIN` (EggDB has no
`EXPLAIN ANALYZE`), session settings. **A statement that can run other statements is
destructive** (an Oracle anonymous block, `CALL`, `EXECUTE IMMEDIATE`, `DO`), since what it runs
is not known before it runs; EggDB parses none of them yet, and a test makes the rule visible: each
must fail to parse or classify as destructive. `WHERE id IS NOT NULL` still deletes every row:
the confirmation guards against accidents and is not a security boundary, and docs/mcp.md says so.

**Two ways to confirm.** When the client declared form elicitation in `initialize`
(`capabilities.elicitation` empty, or with `form`; a client offering only `url` mode cannot show
a yes-or-no form), the server sends `elicitation/create` before it opens the file (`mode: "form"`
on 2025-11-25) with a message of its own wording (designed by Claude Fable, docs/ux/cli.md
section 18): the statement's kind and objects from the parse (ten, then "and N more"), CASCADE
named, names that mix alphabets flagged, the SQL in a code fence longer than any run of
backticks in it, with control, line-separator and bidirectional characters shown as `\u{...}`
escapes, escaped first and then cut at 2,000 characters with "(N more characters not shown)",
and Markdown in names escaped; and one required boolean `run`, default false. `accept` with
`run: true` runs it; `decline`, `cancel` or `run: false` answer `declined_by_user`; an error
response answers `confirmation_failed`. Otherwise the call needs `confirm: true`
(`needs_confirmation` says so), which is the agent's word, not the user's, and the tool's
description tells the agent to ask its user first. `Session::run_one_statement_if_confirmed`
re-parses the text when it runs and refuses a destructive statement that is not exactly the one
confirmed (`Unconfirmed`), so what runs is what the user saw.

**While the user is asked.** The server waits inside the `tools/call`: nothing is open, no lock
is held, the watchdog is not armed and the time limit has not started (classification, the
question and the `call_started` record all come before it). `ping` is answered; other requests
wait, at most 16 (notifications do not count; the seventeenth gets `-32603`); a
`notifications/cancelled` for a waiting request removes it, and one for the call being confirmed
ends it with no response, as MCP asks, after the server sends `notifications/cancelled` for its
own question. The end of stdin does the same and stops the server. There is no expiry: the
server reads stdin with a blocking read, a timer would need a reader thread, and a wait holds
nothing; the earlier plan's single-use nonce table is the one question id in hand.

**The watchdog and commits.** 49a's watchdog ran its `overrun` after letting go of its lock, so a
commit could start while the process was exiting. Its state is now `Idle`, `Armed` or `Firing`,
moved to `Firing` under the lock before `overrun` runs; a write's commit first calls
`disarm_for_commit`, which succeeds only if the watchdog is not firing, and the deadline is not
checked inside a commit. So either the commit starts and the watchdog never fires for that
call, or the watchdog fires and no commit starts: `time_limit_exceeded` always means nothing was
committed, and a client restarting the server never doubles a non-idempotent `INSERT`. The
watchdog's own record now waits at most 250 ms for the audit file's lock (another server may
hold it): exiting promptly releases the database, which matters more than that one record.

**A committed change is never reported as failed.** If closing the file fails after a commit,
the call answers success with a `warning`; if the `call` record cannot be written after a
commit, `audit_unavailable` says the change WAS committed and not to send it again; if the
`call_started` record cannot be written, nothing runs.

**Audit.** `server_started` records `allow_write`. Every record of a call has a `call_id`
(`<pid>-<server start in ms>-<n>`, so a process id reused after a restart cannot pair a
crashed server's write with another server's call). A `write_sql` that is about to run writes and syncs `call_started` first, so a
server that dies during the write leaves a record without a `call`, which `eggdb audit` shows
with the outcome `unknown`. A write's `call` record adds `confirmation` (`elicitation` or
`confirm_argument`), `committed` and `warning`; the outcomes add `needs_confirmation`,
`declined_by_user`, `confirmation_failed`, `cancelled`, `not_writable` and `write_too_large`.

**Left for later.** `--tables` (49b-2, read-only servers first; with `--allow-write` it needs
the store wrapper's commit to check its refusal flag and roll back, since in autocommit
`Session::write` commits before the flag can be read); the 2026-07-28 protocol era with its own
confirmation form; key-value writes; a confirmation expiry.
