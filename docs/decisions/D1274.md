## D1274 ST_Dump and ST_DumpPoints — Decided by the code-only session (2026-11-18, D355); roadmap M4 geospatial (D204, D1272)

- **What users get.** PostGIS's `ST_Dump(geom)` and `ST_DumpPoints(geom)` in `FROM` return `path` (`integer[]`) and `geom`: the parts of a multi-geometry or collection (`{1}`, `{2}`, nested collections `{2,1}`), a single geometry whole with an empty path, or every vertex (`{ring, point}` in a polygon, `{polygon, ring, point}` in a multipolygon), each keeping the input's SRID, as tools use them to explode geometries into rows.
- **How.** Two record-returning functions beside `ts_parse` and `ts_debug`, with their rows built by walking the geometry. Writing them showed that the record rows of `ts_token_type`, `ts_parse` and `ts_debug` (D1231) were never wired into the rows of a function in `FROM`, which would have returned no rows: they are now.
- **Left.** `ST_DumpRings`, `ST_DumpSegments`, and the composite `geometry_dump` type in the select list.
- **Proof.** A test dumps a multipoint and a point, and the points of a polygon in order with their paths.

**Status:** code written, unbuilt (code-only mode, D355).
