## D1243 pgoutput protocol versions 2 to 4 on EggDB's replication protocol — Decided by the code-only session (2026-11-17, D355); roadmap M14, PostgreSQL's replication protocol served (D18, D103, D1031)

- **What users get.** A subscriber that asks `START_REPLICATION ... (proto_version '2' | '3' | '4', ...)`, as PostgreSQL 14 to 17 subscribers and Debezium do, is served instead of being sent version 1 silently, and one that asks for an unknown version (`5`) or none is refused with PostgreSQL's messages (`client sent proto_version=5 but server only supports protocol 4 or lower`, `proto_version option missing`). The other options (`publication_names`, `streaming`, `two_phase`, `binary`, `origin`) are read and kept.
- **Decided by research.** Versions 2 to 4 add messages for streamed in-progress transactions, two-phase commits and parallel apply; a server sends them only when it chooses to stream or a transaction is prepared, and always may send each transaction whole after its commit. EggDB's change log holds committed transactions only, so it sends every transaction whole with version 1's message layout, which is valid in every version; `binary 'true'` may still get text tuples, which subscribers read per column.
- **How.** `walsender` parses the parenthesized options of `START_REPLICATION` (quoted values, doubled quotes) and `protocol_version` checks the version before streaming starts.
- **Left.** Publications naming tables (EggDB has no `CREATE PUBLICATION` yet, so every table is sent), streaming large transactions before commit, two-phase decoding, and binary tuples.
- **Proof.** `walsender.rs` tests: version 4 with streaming and binary accepted and its options read, version 5 and a missing version refused, and the existing command test with its options.

**Status:** code written, unbuilt (code-only mode, D355).
