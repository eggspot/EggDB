## D299 `DISTINCT ON`, `NATURAL` joins, `LIKE ... ESCAPE`, SQLite `GLOB` classes and PostgreSQL `RECURSIVE` views are each rewritten onto a mechanism the engine already has, and `DISTINCT ON` keeps the first row of each key after the sort — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 3, 4, 5 and 8

Five pieces of standard query syntax that applications send unchanged were refused with `0A000`.
Each manual defines them as shorthand for something EggDB already runs, so each is built as that
rewrite, in one place, rather than as a new path through the executor.

- **`DISTINCT ON (expr, ...)`** (PostgreSQL's `SELECT` page, "DISTINCT Clause"). `Select` gains
  `distinct_on: Vec<Expr>`; `distinct` stays false for it, so `ORDER BY` may name expressions
  outside the select list as the manual allows, and `Select::removes_duplicates()` is what the
  optimisations that must not reorder or filter across a duplicate removal ask (condition
  pushdown into a derived table or view, decorrelated lookups, streamed function rows,
  automatically updatable views). The executor resolves each expression with `ORDER BY`'s rules
  (an output column's number or alias, else an expression over the `FROM` items); in a grouped
  query only output columns, since the grouped row no longer holds the tables' columns (else
  `0A000`). The manual's rule that the expressions "must match the leftmost `ORDER BY`
  expressions" is checked as: each of the first `min(n, m)` `ORDER BY` items is one of the `n`
  `DISTINCT ON` expressions, compared after both resolve to an output column or by expression
  shape; otherwise `42P10`. Rows are deduplicated by the values' equality keys (NULLs equal, as
  `DISTINCT`): after the sort when there is one, so the first row in `ORDER BY` order wins and
  `LIMIT`/`OFFSET` count the kept rows, and while streaming when there is no sort or an index
  already gives the order. Beside a window or set-returning function in the select list, which
  moves the select into an inner query, it answers `0A000` for now.
- **`NATURAL [INNER | LEFT | RIGHT | FULL] JOIN`** (PostgreSQL's "Joined Tables", MySQL's `JOIN`
  clause, SQLite's `SELECT`, Oracle's joins). A new `JoinCondition::Natural` is resolved where
  `USING` already is (`join::resolve`): the names, in the left side's output order, that the
  right table also shows, deduplicated, then the same pairing, type and ambiguity checks as
  `USING` (`42702` when the left side has a name twice, as PostgreSQL), so `*`, the merged
  `FULL JOIN` column and the needed-column analysis behave exactly as for the equivalent
  `USING`. No common name gives a cross join, as the manuals say. Column privileges count an
  entry whose columns are not known (a derived table) as having every name, so a hidden column
  can never be compared through a `NATURAL` join. Transact-SQL has no `NATURAL`, and MySQL no
  `FULL`.
- **`LIKE | ILIKE pattern ESCAPE e`** (every dialect; PostgreSQL's "Pattern Matching"). The
  pattern becomes `like_escape(pattern, e)`, PostgreSQL's own function that rewrites a pattern
  with another escape character into the backslash form the matcher already reads (PostgreSQL
  stores `LIKE ... ESCAPE` the same way). `ESCAPE ''` means no escape character; more than one
  character, or a pattern ending in its escape character, is `22025`; a NULL escape gives NULL.
  SQLite's three-argument `like(pattern, text, escape)` is the same rewrite. The dialect
  differences left are roadmap lines, not reasons to keep five copies of the matcher: SQLite's
  error text for a long escape, Oracle's `ORA-01424`, SQLite's "no match" (not `22025`) for a
  pattern ending in its escape character, which the rewrite cannot express because a `LIKE`
  pattern cannot say "never matches", and, from before this decision, `\` read as an escape in
  SQLite and Transact-SQL `LIKE` without `ESCAPE`, where it is an ordinary character.
- **SQLite `GLOB` character classes.** A constant pattern without `[` still becomes a
  case-sensitive `LIKE` (so the planner's prefix ranges keep working); any other pattern, and
  any pattern that is not a constant, runs `sqlite_glob`, a matcher for `*`, `?` and `[...]` with
  SQLite's documented class rules (`^` negates, `]` first and `-` first or last are themselves,
  ranges by code point, an unclosed `[` never matches). It returns NULL for a NULL operand and
  never fails on hostile input.
- **`CREATE [OR REPLACE] [TEMP] RECURSIVE VIEW name (columns) AS query`** (PostgreSQL's
  `CREATE VIEW`). The manual defines it as `CREATE VIEW name AS WITH RECURSIVE name (columns) AS
  (query) SELECT columns FROM name`; the parser builds exactly that text (names quoted with
  PostgreSQL's identifier rules, the common table taking the view's unqualified name) and parses
  it, so the stored definition, `pg_get_viewdef` and every later use are an ordinary view over a
  recursive `WITH`. The column list is required, as in the grammar (`42601` without it).

`DISTINCT ON` and `ORDER BY` items that name a source column are compared by the column they
resolve to, so `DISTINCT ON (c) ... ORDER BY o.c` is accepted as in PostgreSQL; other
expressions are compared by shape. A string, decimal or boolean constant, or an integer outside
PostgreSQL's 32-bit integer constants, in `DISTINCT ON` is `42601` "non-integer constant in
DISTINCT ON", as PostgreSQL answers.

`CREATE TEMP RECURSIVE VIEW` (without `OR REPLACE`) goes to the view parser like the other forms
(review round 1 found it on the table path).

Not yet: a `NATURAL` join's column-privilege check reads every earlier `FROM` item as the join's
left side, including items before a comma that the join does not compare, so `SELECT 1 FROM staff
s, probe p NATURAL JOIN teams t` is a false `42501` when `staff` has an unreadable column that
`teams` shares (never a bypass); the check should take the join group's start, as `join.rs`
does, with a session test using `GRANT SELECT (column)`.

Not decided here: making `DISTINCT ON` an index-ordered "first row per key" scan, which the
benchmarks will ask for if it matters.
