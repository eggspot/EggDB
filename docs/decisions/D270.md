## D270 CREATE DATABASE and DROP DATABASE run through the server's databases, one file each — Decided by the build loop (by judgement, 2026-11-02); refines D184

D184 left creating and dropping databases while serving. The SQL layer now parses them in
PostgreSQL's, MySQL's (`CREATE`/`DROP DATABASE` and `SCHEMA`, which are the same thing there) and
SQL Server's dialects and runs them through `ServedDatabases`, a trait the server implements.

- **A database is a file.** `CREATE DATABASE shop` makes `shop.eggdb` in the served directory;
  `DROP DATABASE shop` closes and removes it. A name must be a safe file name on every
  platform: 1 to 63 letters, digits, `_` or `-`, not starting with `-` and not a Windows
  device name (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, and `COM` or `LPT` followed by
  a digit `0` to `9` or a superscript `¹`, `²` or `³`, in any case); anything else is `42602`.
  `$` is refused: no client needs it in a database name, and it is a variable in every shell
  that a file name reaches. PostgreSQL's `WITH` options (owner, encoding, template,
  locale), MySQL's character set and collation and SQL Server's file options are accepted and
  ignored, since one engine stores every database the same way.
- **Who may.** Each database keeps its own roles, so a role is checked where it matters.
  The server's own user creates and drops any database. A stored role creates one when it is a
  superuser or has `CREATEDB` (stored in the role's flags, shown in `pg_authid.rolcreatedb`) in
  the database its session is on, since the new database has no roles yet. A stored role is
  trusted only in the database that authenticated it: another database's role of the same name
  is a different role, with its own password, so a superuser of one database who creates a role
  named like another database's superuser gains nothing there. `DROP DATABASE` by a stored-role
  session of any database but its own is `42501` (MySQL `1044`, SQL Server `916` through
  `USE`), and its own is in use (`55006`); only the server's own user drops other databases.
  Without ownership of databases, nothing else drops.
- **In use.** `DROP DATABASE` of the database the session is connected to, or of one any other
  session is connected to, is `55006` (SQL Server's error 3702); PostgreSQL's `WITH (FORCE)`
  is accepted but does not end other sessions. Not inside a transaction block (`25001`), except
  in MySQL's dialect, where it commits the open transaction as other DDL does.
- **Outside a server** (embedded, `eggdb sql`) both are `0A000` with a hint, as before.
- **Listing.** A session with the server's databases refreshes `pg_database` (and every catalog
  reading the database names) at each statement, so a database another session created shows
  in `\l` at once.
- **Switching.** A connection holds the database it is connected to for as long as it uses
  it; that hold is what makes `DROP DATABASE` wait (`55006`). MySQL's `USE` and `COM_INIT_DB`
  and T-SQL's `USE` move the connection to another served database: the server builds a new
  session there with the same user, dialect, settings and limits. Only the server's own user
  moves, keeping its rights in every database: a session that logged in as a stored role was
  authenticated by its own database's roles, which say nothing about another database's role
  of the same name, so `USE` of another database fails with `42501` (MySQL `1044`, SQL Server
  `916`) before the connection moves, with a hint to connect to the target directly, where that
  database's roles check the password (round-2 security review: matching roles by name let a
  superuser of one database become another's). A session runs on one store, so
  statements after such a `USE` in the same batch fail with `0A000` and run in the next
  batch; `USE` inside a transaction is `25001`. MySQL and SQL Server match database names
  ignoring ASCII case, PostgreSQL's startup packet exactly, and two databases never differ
  only by case.
- **The server's side.** `eggdb serve <directory>` keeps the default database (the first
  file, which every other protocol serves) and the others, opened with the server's options;
  the default is never dropped, and serving one file or `--read-only` creates and drops
  nothing (`0A000`).
- **Next: what a switch leaves behind.** The session a `USE` replaces is closed, so nothing
  that lives only in it moves to the target: SQL Server `#temp` tables and PostgreSQL or MySQL
  temporary tables are dropped, and the session's locks are released (PostgreSQL advisory locks
  taken with `pg_advisory_lock`, MySQL's `GET_LOCK`, SQL Server's `sp_getapplock` with
  `@LockOwner = 'Session'`). In SQL Server and MySQL a `#temp` table or a named lock outlives a
  `USE`; carrying them across (or refusing a `USE` while one is held, with a message that names
  it) is left for a later step.
