## D363 Ids for rows written straight into a partition, and subpartitions selected alone — Decided by the code-only session (2026-11-10, D355); closes two of D337's leftovers

- **Ids.** PostgreSQL 17 numbers a row inserted into a partition from the partitioned table's
  identity sequence. EggDB's partitions have no identity column of their own (D337), so an
  `INSERT` into a table that is a partition, has no identity column itself, and whose root has
  one now numbers its rows as the root would: the column is added to the column list when the
  statement leaves it out, `ParentIdentity` fills each row (counting across every partition, as
  an insert through the root does), and `GENERATED ALWAYS` refuses a given value (`428C9`)
  unless `OVERRIDING`. It applies only when the identity column sits at the same position in the
  partition as in the root, which every partition EggDB creates satisfies; an attached table
  with its columns in another order keeps today's behavior. `INSERT ... SELECT` into a
  partition is not numbered yet.
- **Subpartitions selected alone.** `INSERT INTO t PARTITION (sp)` (Oracle `SUBPARTITION (sp)`)
  named only a subpartition, so the row's partition at the first level was not in the selection
  and every row was refused. The first level now admits a row when its partition or any
  partition below it is selected, and passes the selected names below it down to the partition,
  which refuses rows outside them (`1748` / `ORA-14401`).

**Left:** `LOAD DATA ... PARTITION` comes with `LOAD DATA` (M10); `PARTITION ()` on a table whose
row-level security policies apply (`0A000`) needs the selection carried into the policy's view.
