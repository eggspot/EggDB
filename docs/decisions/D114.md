## D114 Sequences as catalog objects saved with the writer and re-saved after a rollback; CHECK and FOREIGN KEY constraints in table definition format version 6; statement-level foreign keys through a reverse-reference key space; ALTER TABLE by rewriting rows — Decided by the build loop (by judgement, 2026-10-28); applies D1, D9, D10, D18, D20, D32, D96, D109, D111

Item 32 adds what `pg_dump` output needs before item 35 can restore it: sequences, `ALTER TABLE`
and enforced constraints, in the dialects that have them.

**Sequences are catalog objects of their own.** A sequence lives under the SQL prefix in a new
key space, `0x05` followed by its name, never inside a table definition, so no existing table
changes bytes. Its value is a format version byte (1), a type tag (`smallint`, `integer` or
`bigint`), six little-endian 64-bit numbers (start, increment, minimum, maximum, cache, last
value), a flags byte (cycle, `is_called`) and an optional owner (table and column names). It
is read strictly: a zero increment, a cache below 1, a minimum not below the maximum, a start
outside them, bounds outside the type, unknown flags or a truncated value are damage (`XX001`),
a newer version is refused by name. Tables and sequences share one namespace, as PostgreSQL's
relations do. `CACHE` is remembered and has no effect: every value is saved.

**How `nextval` is durable and non-transactional.** EggDB has one writer at a time (D86), so a
statement that calls a sequence function (found in its tokens) or inserts into a table whose
default calls `nextval` runs as a write, loads the sequences into per-statement state, and the
function works on that state; when the statement succeeds the changed sequences are written
through the same write transaction. So a value is durable no later than the commit of the
transaction that used it, and two sessions never get the same value while a transaction holds
it. PostgreSQL never rolls a sequence back; EggDB keeps that by remembering, per session, every
sequence changed since the transaction began, with the value it had when the transaction first
read it, and when the transaction rolls back (`ROLLBACK`, a failed statement, a failed block, a
closed session) by writing the changed values again in a small transaction of their own, only
for a sequence that still holds the value it had before: one that another transaction moved in
between is left alone, so the re-save never rewinds a committed value. When that small
transaction cannot start, the statement reports it. Between the rollback and the re-save another
connection's writer can take the lock first and see the older value; values that only a
rolled-back transaction used can then be handed out again, and a value that a committed row
holds never is. That window is documented as a known difference. A crash loses only advances
that no committed transaction used. Chosen over a second writer or a
side file because the engine has one writer and one file (D3); the killed-process test checks
that after any crash `nextval` returns more than every stored id.

**Sequence functions stay in their dialects.** `nextval`, `currval`, `lastval`, `setval(seq, n
[, is_called])`, `'name'::regclass` (a minimal `regclass`: the name resolved as PostgreSQL
resolves one, printed as a name; `::oid` and `pg_class` are item 37) and `pg_catalog.`-qualified
calls are PostgreSQL's only; Oracle has `seq.NEXTVAL` and `seq.CURRVAL` through internal
functions nobody can call by name; MySQL and SQLite have no sequences. A non-constant argument
works (all sequences are loaded then). `serial` and identity columns stay on the
`AUTO_INCREMENT` column of D111, unchanged, so existing files keep their bytes; `pg_dump`'s
spelling of them (a sequence and `SET DEFAULT nextval(...)`) gives a real sequence.

**Constraints are stored with the table, in format version 6, only when a table has them.**
Version 6 is the version 5 layout followed by the primary key's constraint name (absent when it
is `table_pkey`), the `CHECK` constraints (name, the dialect it was written in, its expression
text) and the foreign keys (name, column numbers, the parent table's name, the parent's column
names, the `ON DELETE` and `ON UPDATE` actions and whether it was declared `DEFERRABLE`). A table
that another table's foreign key references, or that owns a sequence, is written in version 6
too, with a flags byte after the primary key's name (`referenced`, `owns a sequence`), kept up to
date whenever a foreign key or an `OWNED BY` is added, dropped or renamed: otherwise the release
before this one, which reads up to version 5 and knows neither, could delete a referenced row,
drop or truncate the parent, or drop an owner without its sequence. It now refuses those tables
by name. It still does not know sequences themselves (they are keys it ignores), so it could
create a table named like a sequence: a documented downgrade limit. A table without any of
these keeps its version and bytes; the D96 sample files are untouched. A version 6 table
that has no constraint, duplicate or empty constraint names, more than 1,024 checks or foreign
keys, a foreign key wider than 32 columns, a column number out of range or unknown action codes
is damage; an older release refuses version 6 by name. A check is kept as text and parsed with
its own dialect when a statement uses it, because PostgreSQL's parse trees are not a format we
want to freeze. `NOT NULL`, `UNIQUE` and `PRIMARY KEY` keep their existing storage (column flag,
unique index of D109, key order).

**Foreign keys: a reverse key space, checks at the end of each statement.** Each foreign key
also writes an empty key `0x06`, parent name (length-prefixed), child name, so a `DELETE` or
`UPDATE` on a parent finds its children with one short range read instead of decoding the
catalog. Child rows are checked at the end of each statement (a multi-row `INSERT` may insert a
row before its parent), with NULL in any key column skipping the check (`MATCH SIMPLE`); the
parent is found through the planner with `=` on the parent's key, so it uses the primary key or
a unique index, and equality is SQL equality (`1` matches `1.0`, `char(n)` pads, `uuid` is case
blind). A parent's deleted or changed rows go into a work queue processed after the statement's
own writes: `NO ACTION` and `RESTRICT` fail when the statement ends. PostgreSQL checks `RESTRICT`
at once, so a statement that moves a referenced key away and back (the key swap `UPDATE p SET id =
3 - id` over ids 1 and 2) passes here and fails there; that is a known difference until
`RESTRICT` gets its own immediate check. `CASCADE` deletes or updates the children,
`SET NULL` and `SET DEFAULT` change them and check the result, and every changed child row is
queued in turn. The queue, not recursion, carries cascades, so a chain of any depth cannot
overflow the stack; children are read in batches of 1,024, every queued row is charged to the
statement's work memory (1 GiB, D100, `53200` beyond), and a cascade more than 100,000 levels
deep stops with `54001`. A child is found through an index on its key columns when one exists;
EggDB creates none (PostgreSQL does not either), so a cascade over a large child without one
reads the child once per parent row, as PostgreSQL does. `DEFERRABLE` and `INITIALLY DEFERRED`
are accepted and checked at statement end: deferring to `COMMIT` is a known difference. SQLite
enforces foreign keys only after `PRAGMA foreign_keys = ON`, as SQLite does by default; checks
are always enforced.

**ALTER TABLE rewrites rows when it must, in bounded batches.** `ADD COLUMN` without a default
writes nothing to the rows: a shorter row already reads its missing columns as NULL. With a
default, every existing row gets the default's value, evaluated per row (so `nextval` numbers
them), rewritten in place a thousand rows at a time; this costs a rewrite where PostgreSQL 11+
stores a "missing value", but needs no format change and old rows read correctly in every
release. `DROP COLUMN`, `ALTER COLUMN TYPE`, `ADD PRIMARY KEY` and dropping the primary key
rebuild the table under a new table number: rows move a thousand at a time, through the same
checks as an `INSERT` (so a duplicate is `could not create unique index`), indexes are rebuilt
with them, and the old rows and entries are removed, all in one transaction. `ADD CONSTRAINT`
validates existing rows in batches and leaves nothing behind on a violation. Renames rewrite
dependent definitions: foreign keys that name the table or column, owned sequences, and column
names inside check expressions (by token, skipping function calls). Every catalog change is in
the statement's transaction, so a failed `ALTER` leaves the table as it was.

**Dependencies.** Dropping a table that other tables' foreign keys reference is `2BP01`
(MySQL 3730, Oracle ORA-02449) unless `CASCADE`, which drops those foreign keys; dropping a
sequence a column default uses is `2BP01` unless `CASCADE`, which drops the defaults; a
sequence `OWNED BY` a column goes with that column or its table, and dropping that table while
another table's default uses the sequence is `2BP01` unless `CASCADE`; a table's own
(self-referencing) foreign keys count as dependents like any other's when their parent key or
column is dropped; `ALTER COLUMN ... TYPE` on a column of a foreign key, on either side, must
keep the two types comparable (`42804`, MySQL 3780, ORA-02267) and re-checks the rows; dropping a column drops the
indexes and checks on it, and refuses (or with `CASCADE` drops) foreign keys of other tables
that need it. SQLite drops a referenced parent and leaves the children's foreign key pointing
at nothing, as SQLite does.
