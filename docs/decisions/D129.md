## D129 PostgreSQL's catalog for psql's `\d` family: relations built from the stored definitions once per statement, OIDs from hashes of names, PostgreSQL's display form worked out from the stored text — Decided by the build loop (by plan review and by research, 2026-10-29); roadmap item 37 part b (37b), applies D1, D9, D10, D12, D20, D35, D100, D112, D116, D128

psql's `\d`, `\dt`, `\di`, `\dv`, `\ds`, `\dn`, `\l` and `\du` read PostgreSQL's system catalog
(`pg_class`, `pg_attribute`, `pg_index`, `pg_constraint` and the rest) and print what they find.
EggDB has its own catalog (table, view, sequence, schema and comment records, D20, D116), so part
b of item 37 shows that catalog in PostgreSQL's shape.

**The relations are intermediate tables of the statement, built from the stored definitions.**
In the PostgreSQL dialect a `FROM` item `pg_catalog.X`, or `X` alone (PostgreSQL searches
`pg_catalog` first unless `search_path` lists it after another schema), is one of 24 catalog
relations with PostgreSQL 16's columns and column types: `pg_class`, `pg_attribute`, `pg_type`,
`pg_namespace`, `pg_index`, `pg_constraint`, `pg_attrdef`, `pg_description`, `pg_database`,
`pg_roles`, `pg_am`, `pg_collation`, `pg_sequence`, `pg_depend`, `pg_tablespace`, and nine that
are always empty here (`pg_inherits`, `pg_policy`, `pg_statistic_ext`, `pg_publication`,
`pg_publication_rel`, `pg_publication_namespace`, `pg_trigger`, `pg_rewrite`,
`pg_auth_members`). The name resolver turns such an item into a generated table (the mechanism
of D128's set-returning functions), filled when the statement is prepared. The first statement
part that needs the catalog loads a snapshot of it from the statement's own reader, through the
existing readers of tables, views, sequences, schemas and comments; the snapshot lives in a
thread-local frame entered for each statement (as the search path and the sequences are) and
holds each relation's rows once built, so a relation read three times, or by a correlated
subquery for every outer row, is built once. A statement whose text names no catalog function
and no `reg*` type, and whose `FROM` items are not catalog relations, never loads it:
`nextval('s'::regclass)` in a default or an `INSERT` keeps its plain name lookup. A stored
default, `CHECK` or view whose text needs the catalog loads it when the statement first reads
that table's or view's definition (the table cache remembers which definitions need it), so no
statement fails for lack of it. psql's index query joins `pg_class`, `pg_class` and `pg_index`
in a comma list with the join conditions in `WHERE`, so top-level `WHERE` equalities between
two sources of a comma, `CROSS` or inner join become hash join keys as `ON` equalities do (only
where the filter would run right after that join anyway: never across a `RIGHT` or `FULL`
join, never into an outer join), and `oid` keys use the integer hash. The relations are
read-only (`42501`), as nothing would keep a change to them; nothing is stored, so there is no
file-format change and no D35 review.

**OIDs are hashes of names.** The catalog's own relations, the built-in types, the system
schemas (`pg_catalog` 11, `public` 2200), the roles (the session's user is 10, the predefined
roles have their PostgreSQL 16 numbers), the access methods, collations and tablespaces keep
PostgreSQL's OIDs, so `'pg_catalog.pg_class'::regclass` is 1259 as psql expects. Every other
object's OID is FNV-1a over its kind, its owning table (for an index, constraint or default) and
its name, folded into 16385 to 2^32 - 1; objects of one space that collide take the next free
number in the order of their kind, owner and name, so the result does not depend on the order
the store returns them. An OID is stable across statements and restarts, which psql's
two-step `\d` (look up the OID, then ask about it) needs, and changes when the object is renamed,
which PostgreSQL's does not (a known difference). Storing an OID per object would need a
file-format change for no gain the browsing needs.

**Types for the catalog, not for tables.** `SqlType::Catalog` holds a small `Copy` kind (`oid`,
`name`, `"char"`, `pg_node_tree`, `xid`, `aclitem`, `anyarray` and the `reg*` kinds), so
`SqlType` stays `Copy` and the dialects other than PostgreSQL see one new arm. `oid` and `xid`
values are `Value::Oid`; a `reg*` value is resolved when its cast runs and carries both its OID
and the name it shows (`Value::Reg`), so the wire protocol writes its text or binary form without
the snapshot. `name`, `"char"` and `pg_node_tree` values are text with the declared type, which
psql sees in the column type OIDs; `int2vector` and `oidvector` are array kinds with subscripts
from 0, written separated by spaces. None of them can be a column type of a table: the parser
takes them in casts only.

**PostgreSQL's display form is worked out, not stored.** `pg_get_constraintdef` and
`pg_get_expr` show a `CHECK` constraint or a default as PostgreSQL's pretty form, from the stored
text (the form the user wrote, or the form `pg_dump` wrote) and the column types: the stored
text is parsed, its constant casts are dropped, and the casts PostgreSQL's operator resolution
adds are put back (`0::numeric` against a `numeric` column, `level::text` and
`ARRAY['debug'::character varying]::text[]` for a `varchar` list, `'-3'::integer` for a negative
constant), with PostgreSQL's pretty parenthesization. A corpus of constraints and defaults
observed on PostgreSQL 16, each written both ways, pins it; an expression outside the rules is
shown as stored rather than failing the query. Indexes are shown as `btree` and ascending,
unique indexes as `UNIQUE` constraints and EggDB's auto-increment columns as `generated by
default as identity`, because the table definition does not record more yet (decided by
research before the plan; storing an index's method and order, a unique index's origin and the
identity kind is roadmap item 37c).

**Left for later.** `COMMENT ON` a catalog relation stays refused (`42501`) rather than stored,
since the relations are rebuilt for each statement and have no record to hang a comment on. The
non-pretty display forms are the pretty form in one pair of parentheses, without PostgreSQL's
parentheses around nested casts (`('pg_class'::regclass)::text`); psql reads only the pretty
form. `reg*` input follows PostgreSQL 16 for names, numbers (octal and hexadecimal as `oid`
reads them), array bounds and the `numeric`, `float`, `char` and `varchar` modifier limits, but a
cast between two `reg*` types fails when it runs rather than when the statement is analysed, and
`numeric(p,-s)`, `interval year(3)` and `timestamp(7)`'s warning are not handled.

**The check is psql itself.** CI's `pg-catalog` job fills PostgreSQL 16 and EggDB (through
`pg_dump` and `eggdb restore`) with the same fixture and requires psql 17's output for every
command of `scripts/pg-catalog/commands.txt` to be the same bytes on both, keeping the queries
psql sent as an artifact. Always-on cargo tests run the queries psql 16, psql 17 (from CI's
artifact, through `record.sh`'s `QUERIES`) and psql 18 sent to PostgreSQL (recorded with
`scripts/pg-catalog/record.sh`) against the restored fixture and compare every row and column
type with PostgreSQL 16's, and unit tests cover the query shapes whose catalogs are empty here
with rows, the snapshot being loaded once per statement, and `\d` of one table among 10,000.

**Size (D6).** The stripped release `eggdb` grows from 3,863,080 to 4,012,312 bytes on aarch64
macOS (+149,232, +3.9%) for the 24 relations' column lists, the built-in type table, the row
builders, the functions and the deparser; a statement that names no catalog relation, catalog
function or `reg*` type does not load or build any of it.
