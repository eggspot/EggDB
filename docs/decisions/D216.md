## D216 SQS on the durable queues and core NATS, both in our own crates — Decided by the build loop (by judgement, 2026-10-31); refines D33

Part 4.M16-4 asks for SQS and NATS clients.

- **SQS in `eggdb-sqs`, on `eggdb-http` and `eggdb-queues`.** The endpoint speaks the AWS JSON
  1.0 protocol (`X-Amz-Target: AmazonSQS.<Action>`), which current AWS SDKs use for SQS, and
  not the older XML query protocol. The queues are the durable leased queues of D214, in the
  same collection `queue0`, so a message sent through SQS can be consumed over AMQP and the
  other way round. A received message's receipt handle names the queue and the message id;
  deleting it acknowledges the lease, and a visibility timeout of 0 returns it to the queue.
  Queue URLs carry the account `000000000000`, as local SQS-compatible servers do.
- **Every request is signed.** SigV4 (AWS4-HMAC-SHA256) is checked over the method, path,
  query, signed headers and body hash, with the scope's date and service from the request; the
  access key is the server's user and the secret is the server's password. SigV4 needs the
  secret itself, so `serve` keeps one copy of the password in memory only when `--sqs-listen` is
  given. The signature is compared in constant time. The request's date is not yet checked
  against the clock (AWS allows 15 minutes), which leaves replays of a captured request open on
  loopback until it is. (Superseded by D219: SigV4 moved to `eggdb_auth::sigv4`, which checks
  the date.)
- **MD5 written by us** from RFC 1321, only for the `MD5OfMessageBody` checksum SDKs verify;
  never for security.
- **Core NATS in `eggdb-nats`.** The client protocol from the public NATS documentation, with
  subscriptions held in memory and delivery at most once, which is what core NATS promises.
  Queue groups pick one member per message in turn. `INFO` reports protocol 1 and version
  `2.10.0` so client libraries enable headers; a slow subscriber is cut off by a five-second
  write limit instead of holding up every publisher.

Left: FIFO queues, message attributes, batch actions, long polling (`WaitTimeSeconds`),
dead-letter queues and visibility timeouts other than 0 on `ChangeMessageVisibility` for SQS,
and a check of the request date (done in D219); JetStream (durable streams and consumers, which would sit on
`eggdb-kafka`'s log), no-responders status messages, token and NKey authentication, clusters
and leaf nodes for NATS; TLS for both, and benchmarks against ElasticMQ and nats-server.
