## D591 Keyspace notifications and CLIENT LIST, INFO and KILL — Decided by the code-only session (2026-11-12, D355); roadmap M7, D12, D193

Sidekiq, Bull and cache-invalidation layers subscribe to `__keyspace@*__` and `__keyevent@*__`
channels. Redis Insight, `redis-cli --stat` and operators use `CLIENT LIST` and `CLIENT KILL`.

### Keyspace notifications

- `CONFIG SET notify-keyspace-events <flags>` takes Redis's flags: `K`, `E`, `g$lshzxetmnd` and `A`.
  `CONFIG GET` shows them as Redis does, with `A` first and `K` and `E` last. The setting is
  server-wide and starts empty, as in Redis.
- After each command, the server takes the keys the command put and the keys it deleted (the
  recording keyspace now records deletes too). Each key gets the event Redis names for that
  command: `set`, `lpush`, `rpop`, `hset`, `zincr`, `xadd`, `expire`, `rename_from` / `rename_to`,
  `xgroup-create` and so on.
  - The event goes to `__keyspace@<db>__:<key>` (`K`) and `__keyevent@<db>__:<event>` (`E`) when the
    event's class is on.
  - A key that a command other than `DEL`, `UNLINK`, `GETDEL` or `RENAME` emptied also gets `del`,
    as when `LPOP` takes a list's last element.
- Not published: lazy and active expiry (`x`), eviction (`e`), key misses (`m`), `new` (`n`), and the
  commands run inside `EXEC`, whose writes are recorded under `exec`. `FLUSHDB` and `FLUSHALL`
  publish nothing, as in Redis.

### CLIENT

- Every connection registers in a server-wide `Clients` registry with its address, local address,
  start time and a clone of its socket. After each command it reports its name, database,
  protocol, subscriptions by kind, `MULTI` queue length, watched keys and last command.
- `CLIENT LIST [TYPE normal|pubsub|master|replica] [ID id …]` prints one Redis-format line per
  connection: id, addr, laddr, name, age, idle, flags `N`/`P`/`x`, db, sub/psub/ssub, multi,
  watch, cmd and resp. The memory fields read 0 and fd reads -1. `CLIENT INFO` prints the caller's
  line.
- `CLIENT ID` now answers the connection's real id.
- `CLIENT KILL ip:port` (the old form, `OK` or `No such client`) and `CLIENT KILL` with `ID`,
  `ADDR`, `LADDR`, `TYPE`, `USER`, `SKIPME` and `MAXAGE` (a count) shut the chosen sockets down.
- A connection that kills itself with `SKIPME no` is closed after its reply.
- `CLIENT NO-EVICT` and `NO-TOUCH` answer `OK`.

Not done: `CLIENT PAUSE`, `UNBLOCK`, `TRACKING` and `REPLY`, and `HELLO`'s id, which still reads 1.
