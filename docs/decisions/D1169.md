## D1169 Tables, their indexes and identity sequences keep their OIDs across renames — Decided by the code-only session (2026-11-14, D355); roadmap M6a (the catalog)

- PostgreSQL keeps a relation's OID when it is renamed; tools such as pgAdmin, DBeaver and ORMs' schema caches key on it. Until now `pg_catalog` hashed each relation's schema-qualified name into its OID (D129), so `ALTER TABLE ... RENAME TO` gave the table and every index on it a new OID.
- A table's OID now hashes its stored table id (`TableDefinition::id`, which a rename keeps) instead of its name. Its primary key index hashes "primary key of" that id, a secondary index its own `IndexDefinition::id` with the table id, and an identity column's implicit sequence the column's position with the table id. These requests use an owner no name can produce, so they never collide with name-based requests.
- Views and stand-alone sequences still hash their names: they have no stored id yet. Giving them one is a storage change for the file format pass (D20).
- Changing a schema (`ALTER TABLE ... SET SCHEMA`) keeps the OID too, as in PostgreSQL. OIDs of existing tables change once, at the first snapshot after this change; nothing stores them.
