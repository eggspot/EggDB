## D261 `eggdb follow` reads SQL Server's change data capture (CDC) per table, with change tracking for the rest, and stops when cleanup passes its position — Decided by the build loop (by judgement, 2026-11-02); extends D162

D162 followed SQL Server only through change tracking and said "CDC is not read yet". Many
SQL Server databases have CDC on instead (it feeds their ETL), and CDC carries every row image,
so `follow` now reads it too.

**Which way each table is read.**
- Without `--changes`, a table is read through CDC when the database has CDC on
  (`sys.databases.is_cdc_enabled`) and the table has a capture instance of all its columns
  (`cdc.change_tables`, newest instance first, `cdc.captured_columns` compared with
  `sys.columns`). Otherwise it is read through change tracking, when that is on. One follow can
  mix both, so a database part-way through a move from one to the other still follows.
- `--changes cdc` or `--changes change-tracking` reads every table one way. Every table that
  cannot be read that way is named before the first row is copied, with the command that fixes
  the first (`sys.sp_cdc_enable_table` or `ENABLE CHANGE_TRACKING`). The option is named for
  what it chooses, the source of the changes, in the style of `--poll` and `--publication`.
- A table read through CDC needs a primary key, because each change is applied by key.

**How CDC is read.**
- Before the copy, the position is `sys.fn_cdc_get_max_lsn()`. Each table's next LSN is the
  later of `sys.fn_cdc_increment_lsn(position)` and `sys.fn_cdc_get_min_lsn(instance)`: an
  instance created after the last captured transaction starts after it, and the copy follows.
- Each poll reads `cdc.fn_cdc_get_all_changes_<instance>(next, max, N'all update old')`, ordered
  by `__$start_lsn`, `__$seqval` and `__$operation`, then sets next to the increment of max.
  Changes made during the copy are applied again, in order, which converges like D162's
  change tracking.
- `__$operation` 1 deletes by key; 2 and 4 delete by key and insert the row image; 3, the
  update's old image, deletes the old key. D162's brief said to skip 3, but with `N'all'` an
  update of a primary key would leave the old row behind, so the old image is read and used.
- LSNs travel as `CONVERT(nvarchar(max), lsn, 1)` and are held as 80-bit numbers, written back
  as `binary(10)` literals.

**Position and cleanup.** The position (the change tracking version and the CDC LSN) is held
for the length of the follow, as D162's change tracking version is; resuming is a separate part.
When an instance's minimum LSN passes the table's next LSN (the cleanup job removed changes not
yet applied), or the instance is gone, the follow stops with exit 3 and tells the user to follow
again into a new file. The `stopped` event carries `lsn` next to `change_version`.

**Tested.** Unit tests cover the LSN text, the operation mapping, the per-table choice, the query
text and the statements. CI's `ss-follow` job runs SQL Server 2022 in Docker with SQL Server
Agent on (`MSSQL_AGENT_ENABLED=true`, which CDC's capture job needs) and follows it under writes,
mixed, forced either way, and past a manual `sys.sp_cdc_cleanup_change_table`, comparing with
go-sqlcmd against `eggdb serve --tds-listen`.

**Not done.** Capture instances that leave out columns (they are skipped, not read in part),
net changes (`fn_cdc_get_net_changes_*`), and DDL during a follow (a second capture instance).
