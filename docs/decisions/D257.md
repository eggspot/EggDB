## D257 `eggdb mcp --allow-write --tables a,b`: the read filter of D156 also sits under the writer, refusing every change outside the listed tables and freezing a listed table that a foreign key or an unlisted view ties to one outside — Decided by the build loop (by judgement, 2026-11-02); follows up D156's "left for later", applies D9, D11, D35, D121, D183 and D255; security-critical (D35)

D156 offered `--tables` on read-only servers only: a writing call needed the filter on its writer
too, and a commit that rolls back when a refusal was swallowed.

**The writer is filtered, not the statements.** `VisibleTables::write` wraps a write transaction
in a `VisibleWrite`. Its reads hide what `VisibleRead` hides, so name resolution, triggers'
functions, procedures and functions (SQL and PL/pgSQL bodies, dynamic SQL), view expansion,
`nextval`, `COPY` and every catalog find the other tables missing (`42P01`) exactly as on a
read-only server; nothing above the store needs a list of statement kinds or escape routes. Its
changes are checked against an allowlist by the key's owner (`encoding::key_owner`):

- a listed relation's keys (definition, trigger and partition records, comments on it, its
  statistics, grants, policies and row-security switch) and a visible table's rows and index
  entries; the catalog counter; temporary objects (session-local);
- a new table or view only under a listed name (its table number is learnt from the definition
  written), a new sequence only when a listed table owns it (`serial`, identity);
- a foreign-key or view-dependency record only when neither side is hidden;
- everything else is refused with `42501` naming the object: other relations (including a name
  that exists but is hidden, so `CREATE TABLE secrets` cannot shadow one), renaming a listed table
  to an unlisted name, schemas, types, routines, packages, roles, comments on schemas, and keys
  outside SQL. Routines are refused because a stored routine outlives the session and may run
  later, unfiltered, in the user's own sessions (a trigger on an unlisted table calling it);
- a trigger record is never written, even on a listed table (`CREATE`, `ALTER`, `ENABLE` and
  `DISABLE TRIGGER` are refused; dropping the table still removes its triggers): an existing
  function attached to a listed table would run in every later session that changes it, where
  no filter applies.

A delete of a refused key that is not there is no change and is not refused, since the engine
deletes some keys unconditionally. A transaction in which any change was refused rolls back at
commit, even when a PL/pgSQL handler caught the error.

**Ties across the list freeze the listed side.** Under the filter the engine does not see a
foreign key or view that joins a listed table to a hidden one, so it would neither cascade into
nor check the hidden side. At the start of each write transaction the writer scans the reference
and dependency records once for such ties (`OutsideLink`): a foreign key either way blocks the
listed table's rows and definition; an unlisted view reading a listed table, or a listed view
reading an unlisted relation, blocks the listed one's definition. The refusal names both, and
`eggdb mcp` lists the ties in its banner at start. Rejected: refusing only the change kinds that
can reach the other side (a delete or key update on a referenced table), which needs the engine's
cascade logic restated at the key level; listing the other table is the user's fix.

**Errors name what the agent tried to change; ties name the other table.** A table the agent
names directly still reads as missing, never as forbidden (D156), so a refusal is no oracle for
direct names. A tie's refusal names the unlisted table, as the task asked ("a clear error naming
the table"), because the user needs it to widen `--tables`; it reveals the name of a table tied
to a listed one, which D156 already shows for a foreign key's target.

**Why not the privilege layer.** The server can run calls as a stored role (D183, D190), whose
`GRANT`s limit what the agent reads and writes. It needs a role created in the user's file;
D183's checked roles cannot run any DDL, so an agent could not create or alter even its own
tables; and privileges are checked at name resolution as the statement's role, which leaves
foreign-key cascades (run by the engine, as in PostgreSQL) outside them. The store filter covers
all three without changing the file.

**CLI.** `--tables` with `--allow-write` is no longer a usage error, and
`StartFailure::TablesWithWrites` is removed. With `--allow-write` a listed name that is not in
the file yet is accepted (the agent may create it, the banner says so); a name whose letter case
differs from a stored one is still refused. The agent's instructions gain a sentence saying what
it may change.

**Tests.** `eggdb-sql` (`visible_writes_tests`): inserts, updates, deletes with a cascade between
listed tables, `CREATE TABLE` under a listed name with a `serial`, `ALTER`, `CREATE INDEX`,
`COMMENT`, `ANALYZE` and `DROP` work; unlisted tables, `nextval` of an unlisted sequence, an
unlisted new name, shadowing a hidden name, a view, a sequence and a rename are refused; functions,
replacing a trigger's function, schemas, types and roles are refused; a trigger and a procedure
that reach an unlisted table fail and change nothing; foreign keys both ways and an unlisted view
freeze the listed table; the ties are named; a caught refusal rolls back at commit; deleting an
absent key is no change. `eggdb-mcp`: a writing server limited to tables, the instructions, and
the store after each refusal. The built binary: the same through `eggdb mcp`, the banner, and the
start check.

**Left for later.** A listed table's own stored expressions (a column default, a check, a
generated column, an index expression or a policy) may still call an existing user-defined
function, which then runs in the user's later, unfiltered sessions: refusing definitions that
name a user-defined routine needs the definition's expressions read at the key level, so it is
the next step. Allowing an insert into a table an unlisted table references (it cannot cascade);
column-level limits; the same filter for `eggdb serve` sessions.

**Refined (2026-11-02, security review round 1 of the batch).** Dropping a trigger deleted its
table's trigger record, which the writer let through as a change to a listed relation. A write
transaction now notes every trigger record it deletes and every table definition it deletes, and
refuses at commit (`42501`, rolled back) when a trigger record went without its table: `DROP
TRIGGER` is refused, while `DROP TABLE` and `DROP VIEW` still take their triggers with them.
`DROP TRIGGER`, disabling a trigger, `DROP POLICY` and disabling row level security are also
destructive in D255's classifier, so without `--tables` they ask first.


**Refined (2026-11-02, security review round 2 of the batch).** A confined writer also refuses
(`42501`, rolled back) a table definition whose new or changed column default, generated
expression or `CHECK` calls a user-defined routine, such as `ALTER TABLE t ALTER COLUMN x SET
DEFAULT evil()`: like a trigger, it would run that routine in every later session that writes
the table, where `--tables` does not confine it. Built-in functions stay allowed, and defaults
and checks the table already had are not checked again.

**Refined by D306 (2026-11-03).** A listed table with a foreign key to an unlisted one no longer
has its rows frozen: the writer checks its new and changed keys against the unlisted table, and
only its definition stays frozen.
