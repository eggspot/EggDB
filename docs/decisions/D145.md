## D145 Command model slice 3: paging by cursor over what is stored, with `row list` and the tool `row_list` as the first list to page; dry runs only where exact, as the real run on a scratch copy; confirmation checks read from the registry — Decided by the build loop (by research, 2026-10-30); command model slice 3 (batch part 2.3), builds on D143, D144, D114, D119, D121, D141 and the approved design of 2026-10-28, Claude Fable's design in [ux/cli.md](../ux/cli.md) section 25

**Pages.** A new list command takes `-n, --limit <count>` and `--after <cursor>`, and a new list
tool takes `limit` and `after` and answers `{items, truncated, truncated_by, next_cursor}`. Shipped
lists keep their forms (`collection list`, `scan`, `kv_scan`, `list_tables`). Paging is by
position, never by offset: the cursor names the position just after the last item returned, and
the next page starts strictly after it, each page from one snapshot. So a cursor stays valid while
a writer commits between pages: items added before it are not read, items added after it are,
removed items do not appear, and nothing that stays is repeated or skipped. An offset would shift
under every insert or delete ahead of it.

**The cursor format.** `<list letter><version>.<lowercase hex>`: `r1.` for rows, `t1.` for tables.
The hex holds a 32-bit FNV-1a check of what the list is of (the table's `schema.name` for rows,
nothing for tables) and then the position: for rows, the row's key within its table as the
storage keeps it (the encoded primary key, or the hidden row id of a table without one); for
tables, the kind (table before view), the schema's length, the schema and the name. It is opaque
ASCII, safe in a shell and in JSON, versioned by its second character, and checked before it is
used: one that is not a cursor, continues another list, or (for rows) another table is refused as
`invalid_arguments` with one shared message per case, never read from an arbitrary place. A
position is only ever the start of a scan bounded to the table, so any text is safe to give (a
fuzzed test checks it). The codec lives in `eggdb-commands` (`encode_cursor`, `decode_cursor`,
`check_cursor`), which the CLI and `eggdb-mcp` both use.

**Rows as stored.** `eggdb_sql::Session::read_stored_rows` reads a table's rows in key order from
one snapshot, starting after a position, and hands each row's position and values to a visitor;
`eggdb row list` (a new noun with the core verb `list`) and the tool `row_list` both use it, so
their pages are the same by construction, as D144's twins share `eggdb_sql::relations`. A view
has no stored order and is refused as `not_a_table` (category `refused`, exit 3, `fix_command`
`eggdb table sample <file> <view>`). Without `--limit`, `row list` streams every row in JSON and
prints a page of 100 in text, which needs a page's rows to align. In text the next page's
command goes to stderr; in JSON the records stay one object per line and one trailer line
`{"truncated":true,"next_cursor":"…"}` follows only when `--limit` cut the page, so a script
reading `n` records knows the next line is the trailer. `row_list` returns at most `limit` rows
(1 to 1,000, 100 by default) and 1 MiB, at least one row, with `columns` for the types;
`truncated_by` says which limit cut it. `table list` pages the same way; `list_tables` keeps its
shipped arguments and result.

**Dry runs only where exact.** `--dry-run` exists only where its report can be exactly a real
run's: `import` (eggdb-jsonl, unchanged) and now `restore` and `import --csv`. These run the real
restore or load on a scratch copy and throw it away: the file's last commit is copied to
`<file>.restoring` or `<file>.importing` as `eggdb backup` copies it (D141; the file is opened
read-only, so a writer makes it busy), or with `restore --create` the usual staging file is built,
and the copy is removed instead of renamed. The file and its sequences never change, the report is
the real report with `"dry_run":true` (present only in a dry run, so shipped reports stay byte for
byte) and its verdict in the conditional, and the exit code is a real run's. SQL has no dry run: a
rolled-back statement still moves sequences (D114), and `explain` is SQL's preview. A registry
test fails on `--dry-run` anywhere else.

**Confirmation checks.** The MCP server now picks its confirmation flow from each tool's `confirm`
field (`destructive_statement` for `write_sql`, D121) rather than from the tool's name, and `help
--json` shows the check's sentence as `confirm_when`. No CLI command prompts a person.

**Nothing shipped breaks.** The eight shipped tools keep their `tools/list` entries byte for byte
(the shipped generator is the oracle for them), `row_list` follows them, and every shipped text,
JSON line and exit code is unchanged; `table list` (unreleased) gains its two options and accepts
`-n`, which it refused before.

Decided by research, where the design left it open:
- *The first paged list:* a table's rows, as the new noun `row` with `list`, since no shipped tool
  pages rows (`sample_rows` gives the first rows only, `run_sql` with `OFFSET` shifts under
  writes), and an agent reading a large table needs exactly that; `table_list` would duplicate
  `list_tables`.
- *Positions from the storage key:* exact for every table, with or without a primary key, and
  needing no SQL literal of any type; the check of the table catches a cursor of another table.
- *Exact dry runs by copying:* the only way to make the report a real run's without moving
  sequences or holding a transaction over a whole restore; the cost, the file's size once, is
  stated in the help.
