## D123 SQL Server's types, conversions and functions in the Transact-SQL dialect, with no file-format change — Decided by the build loop (by judgement and by plan review, 2026-10-28); roadmap item 39, applies D10, D19, D111, D113, D119, D122

**Types map onto the engine's.** Every SQL Server type item 39 brings is kept as one of the engine's
types, so the file format does not change and PostgreSQL SQL reads the same columns:

| SQL Server | Kept as | Same as SQL Server | Known differences |
| --- | --- | --- | --- |
| `bit` | `boolean` | 1, 0 and NULL; `'TRUE'`/`'FALSE'` and non-zero numbers convert; printed 1/0; BITN | PostgreSQL SQL sees `true`/`false` |
| `tinyint` | `smallint` | `CAST` and `CONVERT` check 0-255 (220) | a column takes -32,768..32,767; INTN 2 on the wire |
| `money`, `smallmoney` | `numeric(19,4)`, `numeric(10,4)` | 4 places, rounding half away from zero, the range on `CAST` (8115) | a column has `numeric(19,4)`'s range; decimal arithmetic; prints 4 places (SQL Server 2); to an integer truncates (SQL Server rounds); DECIMALN on the wire |
| `float(n)`, `real` | `double precision`, `real` | | |
| `date`, `time(n)` | `date`, `time(min(n,6))` | DATEN, TIMEN | the 7th fractional digit is dropped; `24:00:00` can be stored (sent as text) |
| `datetime`, `smalldatetime` | `timestamp(3)`, `timestamp(0)` | `CAST` rounds to 1/300 s (the `datetime` page's table) or to the minute (29.999 s up), takes at most 3 fractional digits (241) and checks the type's range (242) | a column keeps what it is given; DATETIME2N on the wire; the default text form is ISO, not style 0 |
| `datetime2(n)` | `timestamp(min(n,6))` | printed with its scale | the 7th fractional digit is dropped |
| `datetimeoffset(n)` | `timestamptz(min(n,6))` | equal and ordered by instant; DATETIMEOFFSETN | **the offset is not kept**: values come back in UTC with `+00:00`; item 40's restore report counts the values whose offset was not zero |
| `uniqueidentifier` | `uuid` | text forms, `NEWID()`, GUIDN, printed in upper case | ordered by its bytes, not SQL Server's group order (changing it changes index keys, a format change); `NEWSEQUENTIALID()` is random |
| `char`/`nchar`/`varchar`/`nvarchar(n \| max)`, `text`, `ntext`, `sysname` | D122's map; `sysname` is `varchar(128)` | 1 without a length (30 in `CAST`); `CAST` pads and cuts | binary collation (D122); `'a' = 'a '` is false for `varchar` |
| `binary(n)`, `varbinary(n \| max)`, `image` | `bytea` | `0x` constants (an empty `0x` is no bytes, `0x123` is `0x0123`); `CAST` pads `binary(n)` with zeros and cuts | a column checks neither length nor padding (as MySQL's in D113) |

`rowversion`/`timestamp`, `sql_variant`, `xml`, `hierarchyid` and the spatial types answer
40517. Every column-level difference comes from the table definition not keeping the declared
SQL Server type; keeping it is a file-format change for after v0.2.0 (roadmap), which then also
brings DATETIMN, MONEYN and INTN1 on the wire. Expressions follow SQL Server exactly, because
there the target type is known.

**Conversions are SQL Server's, in the SQL Server dialect only.** `CAST`, `CONVERT`, assignment
to a column, `+` and comparisons use the "Data type precedence" list (the operand of lower
precedence converts to the other's type) and the conversion chart (a forbidden pair is 529
when explicit and 206 when implicit: date and time types with numbers, `uniqueidentifier` with
numbers, `date` with `time`). A fraction stored into or cast to an integer is truncated, where
PostgreSQL rounds. Text becomes a date or time through SQL Server's own reading alone, never
PostgreSQL's first: ISO 8601 (with `T`, `Z` or an offset, which only `datetimeoffset` keeps),
`yyyymmdd`, `m/d/y` (DATEFORMAT mdy; `d/m/y` for styles 3 to 5 and 103 to 105), month names
and AM/PM, at most 64 characters, two-digit years 00-49 in this century and 50-99 in the last.
Seven fractional digits are read and the seventh is dropped, not rounded, so `.9999999` stays
in its second (DATEDIFF's documented examples depend on it). `CONVERT` writes and reads the
styles 0, 23, 101, 103, 112, 120, 121 and 126 (126 leaves out a zero fraction); the other
documented styles answer 40517 and unknown ones 281.

**Where each rule is chosen (D7).** The `INSERT` and `UPDATE` executors pick SQL Server's
assignment once per statement. `+` and comparisons keep the engine's paths and turn to SQL
Server's rules only inside the branches that already fail with "operator does not exist", so
the other dialects and every successful comparison cost nothing more. A string literal read as a
date, time, bit or GUID asks for the dialect only before that parse.

**Functions.** `CAST`, `CONVERT(type, value [, style])`, `ISNULL` (the replacement takes the first
argument's type and length), `DATEADD` (a decimal count is truncated, the day clamps to the
month's end, 517 outside years 1 to 9999, 9810 for a time part on a `date`), `DATEDIFF` (the
number of boundaries crossed; weeks start on Sunday; 535 past an `int`; nanoseconds count
microseconds times 1,000), `CHARINDEX` and `LEN` (in Unicode characters, as an `_SC` collation
counts; `LEN` leaves out trailing spaces), `NEWID()`, `SYSDATETIMEOFFSET()`, `COUNT` as `int`
(8115 past 2^31-1), `SCOPE_IDENTITY()` as `numeric(38,0)` and `@@ROWCOUNT`. Every value these
build (`+` on strings or bytes, `CAST` and `CONVERT` to text or binary) checks its size with
the session's value limit before it is allocated (D119) and is at most 1 GB (7119).

**Statements.** `ORDER BY ... OFFSET n ROWS [FETCH {FIRST|NEXT} m ROWS ONLY]` fills the engine's
limit and offset (OFFSET without ORDER BY is 102, with TOP 10741). `OUTPUT` fills the engine's
`RETURNING`: `inserted.` columns on `INSERT` and `UPDATE`, `deleted.` on `DELETE`; `deleted.` in
`UPDATE` (it needs the old row) and `OUTPUT ... INTO` are 40517, `inserted.` in `DELETE` 4104.
On the wire its rows end with the DML's DONE command and count. `SELECT total = qty * price`
names a column.

**Session values are read when a statement runs.** `@@ROWCOUNT` (the rows a `SELECT` returned or
a DML changed; 0 after `SET`, `USE`, `BEGIN TRAN`, `COMMIT` or a failure) and
`SCOPE_IDENTITY()` (the last value an identity column got, given or generated; an `INSERT` into a
table without one leaves it; NULL before the first) live in the session outside its settings,
so no statement copies the settings, and each statement reads them as it starts, so a statement
prepared once and run many times (item 23b's `sp_prepare`/`sp_execute`) sees the current
values. 23a's `@@TRANCOUNT` is still a constant of the parse; 23b moves it the same way.

**Defaults.** A column default is a constant, or a `CAST`/`CONVERT` of one, folded to the
column's type and kept as PostgreSQL text (`DEFAULT ((0))` on a `bit` column is `false`),
`GETDATE()` and its kin, `SYSDATETIMEOFFSET()`, `NEWID()` or `NEWSEQUENTIALID()`. Any other
expression (`dateadd(day,(30),getdate())`) answers 40517 until item 40a.

**No file-format change in this item; item 40a takes it.** Views, `CHECK` constraints and
defaults written in Transact-SQL, and `IDENTITY` seeds and increments other than (1,1), need the
SQL Server dialect or the seed in the file, a format change with its own compatibility tests and
security review (D35). Rendering them as PostgreSQL text is not realistic (SQL Server's
functions have no PostgreSQL form), so item 40a, a pull request of its own merged before item
40's restore reader, adds a fifth dialect code to the version 6 `CHECK` and version 8 view
records, stores Transact-SQL defaults with it, and keeps identity seeds.

**Item 40's expected outputs** must not depend on case-insensitive comparison or ordering,
trailing-space equality, `uniqueidentifier` ordering or `datetimeoffset` offsets.

**Left for item 39b** (after item 43 if time is left before the freeze): `SUBSTRING`, `LEFT`,
`RIGHT`, `REPLACE`, `STUFF`, `REPLICATE` and `SPACE` (with SQL Server's 8,000-byte cut),
`REVERSE`, `TRIM`, `CONCAT`, `DATALENGTH` (which needs `N'...'` kept apart from `'...'`), `IIF`,
`CHOOSE`, `DATEPART`, `DATENAME`, `YEAR`, `MONTH`, `DAY`, `EOMONTH`, `TRY_CAST`, `TRY_CONVERT`,
`DATEDIFF_BIG`, `ROUND`, `CEILING`, `FLOOR`, `COUNT_BIG`, `@@ERROR`, `@@IDENTITY`, the other
styles, and `SUM`, `AVG` and decimal division with SQL Server's result types. `TOP ... PERCENT`
and `WITH TIES` stay 40517.

**Size (D6, D115).** The binary grows by the conversions and functions, an expected 60 to 120
KB; the footprint check reports it and blocks only above 2x.

Judgement calls, made without asking (CLAUDE.md, "Questions"): mapping onto existing types
rather than a format change; dropping the 7th fractional digit; date and time types refusing
conversion to and from numbers (SQL Server allows it for `datetime` only, which the engine
cannot tell from `datetime2`); a timestamp plus a number adding days (`datetime`'s rule,
accepted for `datetime2` too); lengths in Unicode characters; no trailing-space equality, so
equality agrees with index keys and grouping; the 1 GB cap on built values.
