## D1138 The top-N heap keeps ties for WITH TIES — Decided by the code-only session (2026-11-14, D355); roadmap M5 (a top-N for `WITH TIES`, `PERCENT` and `DISTINCT ON` limits, D100, D341)

- **Before.** `FETCH FIRST n ROWS WITH TIES` (PostgreSQL, Oracle) and `TOP n WITH TIES` (SQL Server) sorted every
  matching row, since the rows tied with the n-th are unbounded (D341).
- **Now.** The top-N heap keeps the n + m smallest rows, as for a plain limit, plus a list of every other row tied
  with the heap's largest:
  - a row equal to the largest joins the list;
  - a smaller row replaces the largest. The row it pushes out joins the list when it still ties with the new
    largest. Otherwise the list, whose rows all tied with the old largest, is dropped and its memory released;
  - a larger row is dropped before it is charged.

  At the end the list sorts in after the heap by sort keys and arrival, and the existing tie check cuts the result
  exactly as the full sort's does. Work memory holds the kept rows and the current ties, not every row.
- **Left:** `PERCENT`, which needs the row count before it knows n (a counting pass first), and `DISTINCT ON`, whose
  first row per group is chosen after sorting. Both still sort every row. Spilling sorts, joins and groups to disk
  needs a codec for every value type in temporary runs, and is the next part of this item.

**Status:** code written, unbuilt (code-only mode, D355).
