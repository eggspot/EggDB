## D303 Transact-SQL `MERGE` with two `WHEN MATCHED` clauses, `$action` and `TOP`; `OUTPUT ... INTO` on `INSERT`, `UPDATE`, `DELETE` and `MERGE`; `SELECT ... INTO new_table` in Transact-SQL and PostgreSQL — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 29 and 30, extends D138 and D291

D291 left `MERGE`'s second `WHEN MATCHED`, `$action`, `TOP` and `OUTPUT ... INTO` at 40517, and
`SELECT ... INTO` was 40517 in Transact-SQL and `0A000` in PostgreSQL. Applications use all of
them: EF Core and hand-written upserts log changes with `OUTPUT $action, inserted.*, deleted.*
INTO @log`, stored procedures stage rows with `SELECT ... INTO #work`, and PostgreSQL scripts
copy tables with `SELECT * INTO copy FROM t`. This decision builds them on the existing
executors, from SQL Server's `MERGE`, `OUTPUT` and `SELECT - INTO` references and PostgreSQL's
`SELECT INTO` page.

- **Matched clauses.** `MergeStatement::update` became `matched: Vec<MergeUpdate>`. The parser
  takes up to two `WHEN MATCHED [AND condition] THEN UPDATE | DELETE` clauses with the same rule
  as D291's by-source ones (the first needs `AND`, one `UPDATE` and one `DELETE`, else Msg
  10714); a second `WHEN NOT MATCHED [BY TARGET]` is Msg 10714 too. Oracle's `MERGE` still has
  one clause. A matched pair takes the first clause whose condition holds; a target row two
  source rows would change is still the "stable set of rows" error. A `DELETE` clause now
  deletes the row directly instead of first running it through an empty update.
- **Planning before writing.** The executor first lists every action (matched pairs, by-source
  rows, unmatched source rows to insert), then writes them. That keeps each row's action
  decided on the rows as they were before the statement and makes `TOP` a cut of that list.
- **`TOP (n) [PERCENT]`.** Parsed into D300's limit markers and evaluated by
  `execute::row_limit`, so `PERCENT` rounds up and past 100 is Msg 1031. SQL Server applies
  `TOP` to the joined rows that qualify for an action, in no stated order; EggDB keeps the
  matched rows first, then the by-source ones, then the inserts, each in scan order, which is
  deterministic.
- **`$action`.** The Transact-SQL lexer reads `$` followed by a letter as part of a word, so
  `$action` is a column name. `OUTPUT` resolves it against one more source with a single
  `nvarchar(10)` column holding `INSERT`, `UPDATE` or `DELETE` for each row.
- **`OUTPUT ... INTO`.** The parser keeps the `OUTPUT` list on the statement as before and
  appends a marker column (`*end of output into*`), then the second `OUTPUT` list if there is
  one, so wildcards such as `inserted.*` need no table lookup when parsing. The statement is
  wrapped in `SqlServerStatement::OutputInto { statement, destination }`. The session runs it in
  one write: the inner statement (with its own binding and privilege), then the rows before the
  marker go into the target table through the `INSERT` path or into a copy of the table
  variable, which replaces the variable only when the write succeeded. So a key, `NOT NULL` or
  type error in the target, or a missing target (Msg 208), undoes the whole statement, as in SQL
  Server. The rows after the marker are the statement's result; without a second list it returns
  no rows. A column count that does not match the target is Msg 213.
- **`SELECT ... INTO`.** The parser takes `INTO` after the select list only in the outermost
  query of a statement (`query_depth` 0, not in a function body); a second `INTO` in a set
  operation is Msg 196, in a subquery the old refusal. The statement becomes
  `Statement::CreateTableAs { name, temporary, query }`, named for the general form so that
  `CREATE TABLE ... AS` can reuse it. In one write it runs the query, creates the table with one
  nullable column per result column (its name and type; a Transact-SQL column without a name is
  Msg 1038), and inserts the rows. `#name` in Transact-SQL and `TEMPORARY`/`TEMP` in PostgreSQL
  make a temporary table; `UNLOGGED` is accepted and ignored. The tag is `SELECT n`, as both
  products report it. Roles with checked privileges cannot run it, like `CREATE TABLE`.

**Tests.**
- `crates/eggdb-sql/src/sqlserver_tests.rs`: two `WHEN MATCHED` clauses with `$action`,
  by-source deletes with `$action`, `TOP (n)` and `TOP (n) PERCENT` (and Msg 1031), the Msg 10714
  refusals for matched and not-matched clauses, and `OUTPUT ... INTO` a missing table as Msg 208.
- `crates/eggdb-sql/src/output_into_tests.rs`: `OUTPUT ... INTO` a table variable from `UPDATE`,
  `DELETE` and `INSERT` with a column list, into a table with a second `OUTPUT`, `MERGE ...
  OUTPUT $action ... INTO`, into a `#temporary` table, and failures (a duplicate key in the table
  variable, a count mismatch, a missing table) that leave the target table as it was.
- `crates/eggdb-sql/src/select_into_tests.rs`: Transact-SQL `SELECT ... INTO` with an alias, a
  `WITH` query, `TOP` and `#temporary`, an empty result, and Msgs 2714, 1038 and 196;
  PostgreSQL's `SELECT ... INTO [TEMPORARY TABLE]`, a rolled-back one, and `42P07`.
- `crates/eggdb-sql/src/lexer/sqlserver.rs`: `$action` is a word.

**Not yet:**
- `deleted.` in a Transact-SQL `UPDATE`'s `OUTPUT` (D138's refusal stays).
- `CREATE TABLE ... AS` and `CREATE TABLE ... AS ... WITH [NO] DATA` (PostgreSQL, MySQL, SQLite,
  Oracle).
- `SELECT ... INTO` keeping the source columns' `NOT NULL` and `IDENTITY` property, as SQL
  Server does, and `ON filegroup`.
- `DELETE` triggers for `MERGE`'s deletes (by-source deletes never fired them either).
- SQL Server's refusal of an `OUTPUT ... INTO` target that has enabled triggers, `CHECK`
  constraints or foreign keys (EggDB fires and checks them instead).
- Describing a prepared `OUTPUT ... INTO` statement that still returns rows.
- PostgreSQL's `MERGE` (PostgreSQL 15 and later).
