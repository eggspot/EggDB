## D1323 EggOS's GUI and `eggdb-gui` stay two toolkits, joined at Wayland — Decided by the code-only session's research (2026-11-25, D355); refines D15, D191 and D256; roadmap M6e

**Question.** Should EggOS's native GUI toolkit and EggDB's `eggdb-gui` become one toolkit (D15's research item)?

**What the two are today** (both read at their `main` of 2026-11-25; both MIT OR Apache-2.0, both written by us):
- EggOS's `userland/toolkit` (EggOS D132): `no_std`, nothing allocates, its widgets live in a fixed array so a program pays only for the window it shows; text is the bitmap faces Egg Mono 8x16 and Egg Sans 16 without anti-aliasing (EggOS D109, D132); it draws into windows of EggOS's own window server (`/dev/window`), at scale 1x or 2x, with damage tracking; about 15,000 lines. EggOS also runs Linux programs that speak Wayland through its server `eggway` (EggOS D140), which copies each `xdg_toplevel`'s shared-memory pixels into a window with the desktop's chrome.
- EggDB's `eggdb-gui` (D191, D256): `std`, allocating, an RGBA canvas with anti-aliased shapes, TrueType text read from the system's fonts by our own reader, a virtualized results grid for millions of rows, accessibility trees for UI Automation, NSAccessibility and AT-SPI2, windows from the platform layer on Windows, macOS and X11, and the same frames in the browser through a canvas; about 39,000 lines.

**Decision.** They stay two toolkits, and EggDB's client reaches EggOS as an ordinary Wayland client:
- Their constraints pull apart. One toolkit would either bring allocation, TrueType rasterizing and the grid into EggOS's smallest programs (its installer, settings and picker), against EggOS's rule that a program pays only for what it shows, or hold a data client that scrolls millions of rows and must answer three desktop accessibility APIs and a browser to EggOS's fixed arrays and bitmap fonts. Neither project gains enough to pay that.
- EggDB's EggOS binary is its static Linux build (D1080), so the client's way onto EggOS is the platform layer's Wayland window backend, which Linux Wayland desktops need anyway (roadmap: Wayland windows, D256). `eggway` serves exactly that: `wl_shm` buffers, `xdg_toplevel`, pointer and keyboard. No EggOS-specific window code goes into EggDB.
- What they share is the design, not the code: both toolkits' designs come from Claude Fable, and the command model already has one canonical spec in EggOS (`docs/ux/command-model.md`) that EggDB links to. New shared vocabulary (design tokens, the agent-visible element tree) is written once as a spec in one repository and linked from the other, as the command model is.
- Neither repository depends on the other's crates: each builds, releases and is tested on its own, as the owner's rule of one session per project folder also assumes.

**Revisit when** EggOS's toolkit takes TrueType text and allocation for its own reasons, or a client screen needs something only EggOS's window server offers; then a shared crate for the pixel-level parts (the canvas and text shaping) is the first candidate, not the widget tree.

**Left.** The Wayland window backend in `eggdb-platform` (with its IME input), and a check of the client on EggOS through `eggway`.

**Status:** research recorded; no code (code-only mode, D355).
