## D999 EggDB's own HTTP/2, HPACK and gRPC framing — Decided by the code-only session (2026-11-13, D355); roadmap M11, Arrow Flight SQL (D29, D37)

- Arrow Flight SQL, and the gRPC APIs of D37, run on gRPC, which runs on HTTP/2. A new crate, `eggdb-http2`, written
  from RFC 9113 (HTTP/2) and RFC 7541 (HPACK) with no third-party code and no dependency, holds: frames with padding
  and priority fields stripped; HPACK decoding with its static and dynamic tables, size updates and Huffman strings,
  and stateless encoding (literals without indexing, static names reused); a server connection; and gRPC's
  length-prefixed message framing with its status codes.
- The Huffman code is derived, not copied: RFC 7541's code is canonical, so the crate's 257-entry table was generated
  from each symbol's code length, checked to fill the code space exactly (Kraft sum 1) and against the RFC's own
  examples (`www.example.com` encodes to `f1e3 c2e5 f23a 6ba0 ab90 f4ff`).
- The server answers prior-knowledge HTTP/2 (`h2c`, as gRPC clients use without TLS; `h2` over EggDB's TLS when ALPN
  arrives). It announces 100 concurrent streams and a 16 MiB receive window, returns window updates as data arrives,
  and answers each completed request in turn, honouring the client's connection and stream send windows (reading
  frames while waiting for `WINDOW_UPDATE`), `SETTINGS`, `PING`, `RST_STREAM` and `GOAWAY`. Requests are handled one
  at a time per connection: correct for any client, and multiplexing gains come later.
- Limits keep hostile peers bounded: frames of at most 16 KiB, header blocks and decoded header lists of at most
  256 KiB, request bodies and gRPC messages of at most 64 MiB, and windows within 2^31 - 1; any breach is a connection
  error sent in `GOAWAY`.
- Left: Flight SQL's services on top, ADBC, TLS with ALPN, and serving several streams concurrently.

**Status:** code written, unbuilt (code-only mode, D355).
