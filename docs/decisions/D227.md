## D227 Edge copies are archived copies cached by their SHA-256; tiers by age wait for page-level storage — Decided by the build loop (by judgement, 2026-10-31); refines D18 and D226

Part 4.M18-3 asks for storage tiers by age and read-only edge replicas.

- **An edge copy is an archived copy, cached where it is read.** `eggdb sql s3://bucket/prefix
  [--at <time>]` picks the copy the manifest names for that time (D208, D226), keeps it in a local
  cache named by its SHA-256, and runs read-only queries on it. A cached copy is checked against
  its SHA-256 before use, so a second query in the same region costs no download, a damaged
  cache file is fetched again, and two times that name the same copy share it. Any number of
  edge sites can read one bucket without the primary knowing them. They are as fresh as the
  last archive, which suits reference data, catalogs and reports.
- **Live edge replicas** that follow the primary's commits are the read replicas of D209 placed
  near readers. They need no new mechanism, only the transport `eggdb serve` will carry.
- **Tiers by age** (recent pages on local disk, older ones in object storage, read back on
  demand) need the page cache to fetch missing pages from a remote store, the page-level work
  D226 leaves. It is recorded there and not started here.

Left: tiered pages by age, an edge server (`eggdb serve` on an edge copy, refreshed when the
manifest grows), cache size limits and eviction, and per-table placement rules (which tables
live at which tier or edge).
