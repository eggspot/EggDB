## D300 `WITH TIES` and `PERCENT` in every dialect that has them ride D149's row window, and `STRING_AGG ... OVER` and analytic `LISTAGG` are the aggregate over the whole partition in `WITHIN GROUP` order — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 6 and 7, extends D149, supersedes in part D123

D149 built Oracle's `FETCH ... PERCENT` and `WITH TIES` as markers in the query's limit
expression, read by the row window (`execute::RowLimit`), which sorts before it counts and keeps
the rows after the last one that sort equal to it. PostgreSQL's `FETCH FIRST`, Transact-SQL's
`TOP ... PERCENT` and `TOP ... WITH TIES`, and the windowed forms of `STRING_AGG` and `LISTAGG`
were refused (`0A000`, Msg 40517). D123 left `TOP ... PERCENT` and `WITH TIES` at 40517; this
decision replaces that part of it.

- **PostgreSQL `FETCH { FIRST | NEXT } [ count ] { ROW | ROWS } { ONLY | WITH TIES }`** (the
  `SELECT` page, "LIMIT Clause"). `ONLY` is the same limit as `LIMIT count`; no count is 1, a
  negative one is `2201W` "LIMIT must not be negative", and `LIMIT` with `FETCH` is `42601`
  "multiple LIMIT clauses not allowed". `WITH TIES` reuses D149's `oracle_fetch_with_ties`
  marker, since the standard defines the same behaviour for both; without `ORDER BY` in the same
  query level it is `42601` "WITH TIES cannot be specified without ORDER BY clause", as the
  manual says. MySQL and SQLite have no `FETCH` and keep refusing it.
- **Transact-SQL `TOP (expression) [PERCENT] [WITH TIES]`** (the `TOP` page). `WITH TIES` alone
  reuses the same marker. `PERCENT` gets its own markers, `sqlserver_top_percent` and
  `sqlserver_top_percent_with_ties`, because SQL Server differs from Oracle at the edges: a
  percent outside 0 to 100 is Msg 1031 "Percent values must be between 0 and 100." (`2201W`),
  where Oracle reads a negative percent as none and more than 100 as all. Both round the row
  count up, as the manuals say, so the percent is applied by D149's `percent_of`. `WITH TIES`
  without `ORDER BY` is Msg 1062. `TOP (100) PERCENT` at the top of a view keeps D125's reading
  (the `TOP` and its `ORDER BY` are ignored, as Microsoft documents); any other percent in a view
  is now an ordinary limit.
- **`STRING_AGG ... OVER` and analytic `LISTAGG`**. Oracle's SQL Language Reference gives
  `LISTAGG (...) [WITHIN GROUP (order_by_clause)] OVER (query_partition_clause)`: only a
  partition, with the values ordered by `WITHIN GROUP`. SQL Server itself refuses `STRING_AGG`
  with `OVER`, but Azure Synapse documents the same shape (`OVER ([PARTITION BY ...])`), and
  queries written for it arrive over TDS, so EggDB accepts that form. Both are written as the
  existing window aggregate (`string_agg` for Transact-SQL, D149's array aggregate under
  `oracle_listagg` for Oracle, so `ON OVERFLOW` and the NULL rules stay the same) over a window
  whose `ORDER BY` is the `WITHIN GROUP` list and whose frame is `ROWS BETWEEN UNBOUNDED
  PRECEDING AND UNBOUNDED FOLLOWING`. The window sorts each partition in that order before
  feeding the aggregate, so every row of a partition gets the whole partition joined in
  `WITHIN GROUP` order, with no new executor path (`parser::windows::whole_partition_aggregate`).
  An `ORDER BY` inside Oracle's `OVER` is `ORA-30487` "ORDER BY not allowed here"; anything but
  `PARTITION BY` inside the Transact-SQL one is a syntax error. `LISTAGG (DISTINCT ...) OVER`
  answers `0A000` for now, as window aggregates have no `DISTINCT` yet.

`TOP (NULL) PERCENT` (with or without `WITH TIES`) is Msg 1006 "TOP clause contains an invalid
value.", as SQL Server refuses a NULL `TOP` value; it no longer reads as 0 percent.

Not decided here: `TOP ... PERCENT` in `UPDATE`, `DELETE` and `INSERT`, `TOP` in `MERGE`, and
PostgreSQL's `2201W` for a NULL count with `WITH TIES` (a NULL count still means no limit). Not
yet: a plain Transact-SQL `TOP (NULL)` without `PERCENT` still means no limit (it shares
PostgreSQL's `LIMIT` path); SQL Server answers Msg 1006 there too.
