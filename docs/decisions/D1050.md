## D1050 MPP distributed analytics with workload queues — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D58)

- **Parallel shards.** D1041's planner already pushes filters, partial aggregates and limits to every shard. The
  coordinator now reads the shards' answers all at once, one thread per shard, through the same foreign source reader
  `eggdb_foreign` uses (`foreign::read_rows`, with the caller's role, so the same permissions apply), and runs the final
  query over them as a `VALUES` list of JSON rows. A query therefore takes as long as its slowest shard rather than the
  sum of all of them. When the answers hold more than 10,000 rows, which the final step would not want gathered in
  memory, it falls back to the streaming `UNION ALL` of `eggdb_foreign` calls.
- **Workload queues.** `CREATE WORKLOAD QUEUE <name> (CONCURRENCY <n> [, TIMEOUT <ms>])` defines a process-wide
  admission queue, kept in `eggdb_internal.workload_queues` so it survives a restart (loaded when first used). A
  session that sets `eggdb.workload_queue` waits for a place before each statement runs, in arrival order, and is
  refused with `57014` (as a cancelled statement is) once it has waited longer than the queue's timeout. Statements
  run from inside an admitted one on the same thread (triggers, internal statements) are not queued again, so a queue
  of one place cannot deadlock on itself. `SHOW WORKLOAD QUEUES` reports places, running and waiting statements,
  admissions and timeouts. Analytics sessions go to a narrow queue and leave the server's other connections free.
