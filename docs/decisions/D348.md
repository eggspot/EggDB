## D348 Elasticsearch-compatible `_update` upserts (`upsert`, `doc_as_upsert`, `scripted_upsert`), `detect_noop` and nested `doc` merges, and `search_after` with multi-field `sort`, `sort` values on each hit and `_source` filtering on `_search` — Decided by the build loop (batch 6, 2026-11-10); roadmap M8, extends D196 and D331, applies D9

D196's `_update` refused a missing document and wrote every `doc` update, even one that changed
nothing, and merged only top-level members, so a nested object in `doc` replaced the stored one.
`_search` sorted by one field, gave hits no `sort` values and had no way to page past the first
10 000 hits. Clients that write with `doc_as_upsert` (Logstash's Elasticsearch output with
`action => update`), rely on `noop` to skip unchanged documents, or page deep results with
`search_after` failed or misbehaved. Built from the
Elasticsearch and OpenSearch REST references (Update API, Paginate search results, Sort search
results, Retrieve selected fields) only, in `crates/eggdb-esrest` (`src/api.rs`, the new
`src/sort.rs`, `src/script.rs`); tests in `src/tests.rs`, `src/sort.rs` and `src/script.rs` are
those pages' examples.

- **Upserts.** When the document is missing, `_update` inserts the `upsert` document (`201`,
  `result: created`, `_version` 1, the index created as indexing does) instead of answering
  `404 document_missing_exception`, which stays the answer when there is no `upsert`. With
  `doc_as_upsert: true` the `doc` itself is inserted (it wins over `upsert`). With a script, the
  `upsert` document is inserted as it is and the script runs only on later updates, unless
  `scripted_upsert: true`: then the script runs on the `upsert` document with `ctx.op` starting
  as `create` and `ctx._version` `null`, and may set `ctx.op` only to `create` (insert what the
  script built) or `noop`/`none` (insert nothing, answering `result: noop` with `_version` -1
  and no `_seq_no`, as Elasticsearch's missing-document `GetResult` gives); another value is a
  `400 script_exception` (`Operation type [delete] not allowed, only [noop, create] are
  allowed`). The scripted upsert keeps D331's Painless subset and limits.
- **Validation** follows Elasticsearch's `UpdateRequest.validate`, listing every problem in one
  `400 action_request_validation_exception`: `script or doc is missing`, `can't provide both
  script and doc`, `doc must be specified if doc_as_upsert is enabled`. `doc` and `upsert` that
  are not objects, and `doc_as_upsert`, `scripted_upsert` and `detect_noop` that are not
  booleans (or the strings `true`/`false`), are `400 x_content_parse_exception`. Other body
  members are ignored, as before.
- **Nested merge.** A `doc` merges into the stored source as Elasticsearch's
  `XContentHelper.update` does: a member that is an object on both sides merges member by
  member, at any depth; anything else (arrays included) replaces the stored value; new members
  are appended. Bulk `update` actions run the same code, so they get upserts, merges and
  `noop`.
- **`detect_noop`**, true unless the body sets it to false: a `doc` that changes nothing is not
  written; the answer is `200` with `result: noop`, the stored `_version` and `_seq_no`, and
  `_shards` `{"total":0,"successful":0,"failed":0}` (the Update API page's example). Values
  compare as parsed JSON: object members in any order; numbers by value among integers and
  among decimals, while `1` and `1.0` differ (Java's `Integer` and `Double`); strings, booleans
  and arrays exactly. Scripts are not noop-checked: a script answers `noop` only by setting
  `ctx.op`, as in Elasticsearch, and every `noop` now reports zero shards.
- **`_source` on `_update`.** The body's `_source` or the URL's `_source`, `_source_includes`
  and `_source_excludes` add a `get` object (`_seq_no`, `_primary_term`, `found`, the filtered
  new `_source`) to a `created`, `updated` or `noop` answer, using D331's source filter.
- **`sort`.** The body's `sort` takes a field name, an object of fields (`"field": "desc"` or
  `"field": {"order", "mode", "missing"}`; `format`, `unmapped_type` and `numeric_type` are
  accepted and ignored) or an array of either; the URL's `sort=field:desc,other` is read when
  the body has none. Fields sort ascending by default, `_score` descending; `_doc` (and
  `_shard_doc`, which needs no point in time on one shard) is the document's position among the
  searched documents, the tiebreaker Elasticsearch documents. Ties after every sort field keep
  that position order. Unknown orders and modes are `400 parsing_exception` (`Unknown SortOrder
  [up]`, `Unknown SortMode [most]`), an unknown option `[field_sort] unknown field [x]`;
  `_script` and `_geo_distance` sorts are refused by name.
- **Field kinds without mappings.** A sort field is numeric when any matched document holds a
  number (or boolean, as 1 and 0) there, otherwise text (Elasticsearch's `keyword`); a
  `.keyword` suffix with no such member reads the field without it, as dynamic mappings' keyword
  subfield does. Text compares by bytes, numbers by value. Arrays sort by their minimum
  ascending and maximum descending, or by `mode` (`min`, `max`, `sum`, `avg`, `median`; `avg`
  and the `median` of an even count, the mean of the two middle values, round for integer
  fields, as Elasticsearch does for `long`: `[2, 3]` sorts as 3).
- **Missing values** go last in either direction (`missing: _last`), or first with `_first`, or
  take a given `missing` value. As Elasticsearch, a numeric field's missing value is shown in the
  hit's `sort` as the extreme it sorts as: `9223372036854775807` or `-9223372036854775808` for
  integer fields, `"Infinity"` or `"-Infinity"` for decimal ones; a text field's is `null`. So
  sort values copied into `search_after` page correctly.
- **`sort` values on each hit** come after `_source`: numbers as stored (the picked array element's
  own text), text as strings. With a sort that leaves out `_score`, hits' `_score` and
  `max_score` are `null` unless `track_scores: true`.
- **`search_after`** (a non-empty array) keeps the hits whose sort values come strictly after
  it, so hits tied with it are skipped as in Elasticsearch, which is why `_doc` is the
  recommended tiebreaker. `hits.total` and aggregations still count every match. Errors, as
  Elasticsearch words them, all `400 illegal_argument_exception`: `` `from` parameter must be
  set to 0 when `search_after` is used. ``, `Sort must contain at least one field.` when there
  is no sort, `search_after has N value(s) but sort has M.`, and `Failed to parse search_after value
  for field [f].` for a value that does not read as the field's kind (numbers and numeric
  strings, `Infinity` included, for numeric fields and `_score`/`_doc`; strings, numbers,
  booleans or `null` for text). A `search_after` that is not an array is `400 parsing_exception`.
- **`_source` on `_search`.** The body's `_source` (`false`, patterns, `includes`/`excludes`) or
  the URL's `_source`, `_source_includes` and `_source_excludes` filter each hit's source with
  D331's filter; `false` leaves `_source` out of the hits. `_msearch` searches get the same.
- **Memory.** Nothing new is buffered beyond what `_search` already holds (the matched
  documents and one sort key per hit) and what one update already parses (the stored and the
  new document, each bounded by the request body limit), so D307's budget is unchanged.
- **Left out** (roadmap M8): scroll (`scroll=1m`, `_search/scroll`, `DELETE _search/scroll`)
  with contexts bounded in count and memory, point in time (`pit`), `_search/template` and
  `_msearch/template` with Mustache, `if_seq_no`/`if_primary_term` and `retry_on_conflict`,
  sorting by `_script` and `_geo_distance`, `nested` sorts, sorts refused for unmapped fields
  (EggDB has no mappings yet, so an absent field sorts as missing instead of failing with
  `No mapping found for [f] in order to sort on`), and `_source` filtering on `GET _doc`.
