## D1180 `json_populate_record` on a table's row type in expressions, its column alias list in FROM, and no named `JSON_TABLE` `PLAN` — Decided by the code-only session (2026-11-15, D355); roadmap M6a (SQL/JSON, D289, D302), follows D1166 and D1167

- **A table's row type in an expression.** `SELECT json_populate_record(null::t, '{...}')` for a table or view `t` (D1167 refused it): the parser's `*row_type*('t')` marker is filled by the name resolver, while it walks the statement's expressions, with each column's name and a NULL of its type. `sql_json::populate_scalar` builds the row from those, an anonymous record with the table's column names, so `(…).column` reads a field and the value prints as PostgreSQL prints a row. Typing gives the call the type `record`. Hidden columns stay out; a view's columns of unknown type are `text`.
- **A column alias list on the FROM form.** `FROM json_populate_record(null::pt, '...') AS r(a, b)` renames the output columns in order, fewer names than columns keeping the rest; more is `42601`. The document's keys still match the row type's own field names, as in PostgreSQL, so `fill_row_type` appends those names after the typed placeholders when aliases are given, and `populate_rows` matches keys against them.
- **`JSON_TABLE`'s named `PLAN`** (`PLAN (p1 OUTER (p2 CROSS p3))`) is decided against for now. D1166's `PLAN DEFAULT (...)` covers the joins between nested paths; PostgreSQL 17 shipped `JSON_TABLE` without any `PLAN` clause and Oracle has none, so no client EggDB is compatible with sends the named form, and it stays refused with `0A000` and a hint to use `PLAN DEFAULT`. It is reconsidered if a dialect EggDB serves adds it.
- Tests: `json_populate_record_in_a_select_list_is_one_composite_value` (the table row type now answers) and `json_populate_record_in_from_takes_a_column_alias_list`.

**Status:** code written, unbuilt (code-only mode, D355).
