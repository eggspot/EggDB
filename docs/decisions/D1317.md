## D1317 Incremental refresh of continuous aggregates — Decided by the code-only session (2026-11-25, D355); roadmap M11 continuous aggregates (D736)

- **What users get.** TimescaleDB's `CALL refresh_continuous_aggregate('view', window_start, window_end)` recomputes only the buckets in `[window_start, window_end)` of a continuous aggregate, with `NULL` for an open end, so a policy or a backfill touches the recent buckets and leaves older ones as they were. `add_continuous_aggregate_policy` now schedules exactly that, with the window `now() - start_offset` to `now() - end_offset` (open where an offset is `NULL`), as TimescaleDB does, instead of refreshing the whole view. A window whose start is not before its end fails with `22023`, and a name that is not a materialized view with `42809`.
- **How.** A continuous aggregate is a materialized view kept as a table (D736). The procedure, in the extension's PL/pgSQL, finds the view's bucket column from its defining query (the name given to its `time_bucket(...)`), deletes that window's rows and inserts the defining query's rows of the same window. A view without a `time_bucket` column is refreshed whole.
- **Left.** Invalidation logs that track which buckets changed since the last refresh, and real-time aggregates (`materialized_only => false`).
- **Proof.** A time-series test builds an hourly aggregate, adds rows to two hours, refreshes one hour's window and sees only that bucket change, then refreshes with open ends and sees both.

**Status:** code written, unbuilt (code-only mode, D355).
