## D1113 Databases per tenant at millions of tenants, and a tenant lifecycle API — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D58, D32)

- **A database per tenant, opened on demand.** A served directory with `--tenant-databases <open>` keeps each tenant in its own file, so a tenant is isolated, backed up, exported and deleted as one file (D3's "one file per database"). Files live under `tenants/<aa>/<bb>/<name>.eggdb`, the two levels from the name's SHA-256, so a million tenants make about 15 files per directory. A tenant's database opens when a session first attaches to it. Past `<open>` open databases, the least recently used ones no session holds are closed, so memory and file handles stay bounded whatever the tenant count. Only active tenants cost anything at run time (D6).
- **The registry is a table.** `eggdb_tenants.registry` in the served directory's default database records each tenant's state (`active`, `suspended`, `over_quota`, `deleted`), quota and times. SQL can read it and it pages by name. Suspended and deleted tenants are kept in memory as refused, so a session naming one is answered as if the database did not exist, with no registry read on the hot path.
- **Lifecycle API.** `--tenant-api-listen` (bearer password, HTTPS off the machine): create (file and registry row), list a page after a name, get (with the file's size), suspend, resume, set quota, export (a verified `backup_to` copy beside the tenant's file), and delete. Delete refuses the tenant at once and keeps its file for 7 days, so a mistaken delete can be resumed, then a background pass drops the file and the row. The same pass marks tenants whose file is over quota as `over_quota`, for the operator or billing (D44) to act on. Refusing writes past a quota is left for later.
- **Scale check.** Per-tenant cost when idle is one registry row and one file, and the directory listing at startup reads only top-level files, so startup time does not grow with tenants.
