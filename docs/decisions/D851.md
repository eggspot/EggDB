## D851 Oracle VPD static policies — Decided by the code-only session (2026-11-12, D355); follow-up of D186

- PL/SQL `DBMS_RLS.ADD_POLICY`, `DROP_POLICY` and `ENABLE_POLICY` (named or positional arguments) run as a package
  intercept, like `DBMS_SCHEDULER`. `ADD_POLICY` calls the policy function once with the object's schema and name and
  keeps the predicate it returns in `eggdb_internal.oracle_rls_policies`; an empty or `NULL` predicate means no
  restriction, as in Oracle.
- Only static policies run: `static_policy => TRUE`, or `policy_type => DBMS_RLS.STATIC | SHARED_STATIC`. Oracle's
  default is `DYNAMIC`, which calls the function on every statement; evaluating it once would silently apply a stale
  predicate, so `DYNAMIC` and the context-sensitive types are refused with `ORA-28104` and a hint. A predicate that reads
  `SYS_CONTEXT('USERENV', ...)` still varies by user, because the predicate is evaluated per query. Column-level VPD
  (`sec_relevant_cols`) is refused as not supported yet.
- Each enabled policy becomes restrictive row-security policies on the table (`eggdb_vpd_<policy>_<statement>`) beside
  a permissive `eggdb_oracle_base` policy, with `FORCE ROW LEVEL SECURITY` so the owner is filtered too (Oracle
  exempts only `SYS` and `EXEMPT ACCESS POLICY`). `SELECT` and `DELETE` get `USING`; `UPDATE` gets `USING` and, with
  `update_check => TRUE`, `WITH CHECK`; `INSERT` is checked only with `update_check => TRUE`, as in Oracle. `INDEX`
  in `statement_types` is accepted and ignored.
- Stored row-security conditions are read in the PostgreSQL dialect, so an Oracle predicate is stored wrapped as
  `eggdb_oracle_predicate('<predicate>')`, which the condition reader (and only it) parses in the Oracle dialect with
  the session's settings. The predicate is parsed once at `ADD_POLICY` time so a broken one fails there with
  `ORA-28113`.
- Left: dynamic and context-sensitive policies (calling the function per statement), column-level VPD, policy groups
  and the `DBA_POLICIES` view.
