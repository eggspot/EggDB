## D784 Tenant-aware backup and restore (eggdb_tenancy) — Decided by the code-only session (2026-11-12, D355); roadmap M14, tenant-aware backup and restore (D234)

- `eggdb_tenancy.backup_tenant(tenant)` is a logical backup of one tenant across both isolation styles: the tenant's
  rows of each table isolated by row (D234), selected by the table's tenant column, and every table of the tenant's
  own schema (D764), as one JSON document (`format` `eggdb-tenant-backup-1`, the tenant, when, and each table's rows
  under `schema.table`).
- `restore_tenant(tenant, backup)` replaces only that tenant's data, in one transaction: for an isolated table it
  deletes the tenant's rows and inserts the backup's, after checking every row carries the tenant (so a backup cannot
  write into another tenant); for the tenant's schema it empties and refills each table. Rows go in through
  `jsonb_populate_recordset`, so the tables' current columns and types take them, and columns added since the backup
  get their defaults. A backup of another tenant, or naming a table outside both kinds, is refused.
- Restoring one customer to a point in time without touching the others is what a whole-file backup cannot do; the
  whole-file backup stays the disaster-recovery path. Point-in-time tenant restores from the log, very large tenants
  (streamed rather than one JSON value), and moving a tenant between databases with it are left.
