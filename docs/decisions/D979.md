## D979 Roles with `BYPASSRLS` — Decided by the code-only session (2026-11-13, D355); roadmap M6b, D326's leftover

- `CREATE ROLE ... BYPASSRLS` and `ALTER ROLE ... BYPASSRLS | NOBYPASSRLS` are kept instead of accepted and ignored:
  `StoredRole::bypass_row_security`, stored as a fourth bit of the role record's flags byte. Readers before this change
  ignore the bit, so an older binary opening a newer file applies policies to such a role, the safe direction; no
  record version change is needed.
- Row security leaves a role with the attribute alone, as PostgreSQL does: `applicable` returns no policies for it, so
  it reads and writes every row its privileges allow. Superusers already bypassed policies. `pg_roles.rolbypassrls`
  reports the attribute (and stays true for superusers).
- Left: `FORCE ROW LEVEL SECURITY`, which needs object owners (a table's owner bypasses its policies unless forced).
