## D1109 CouchDB's replication protocol: a CouchDB-compatible HTTP API with revision trees over EggDB's storage — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D48, D2)

- **What replicators need.** CouchDB's replication protocol is documented (the CouchDB docs' "Replication Protocol" chapter) as a sequence over the HTTP API: read both sides' `/{db}` info and `_local` checkpoints, read the source's `_changes` from the checkpoint, ask the target's `_revs_diff` which revisions it lacks, fetch them with `_bulk_get` or `GET ?revs=true&open_revs=...`, write them with `_bulk_docs` and `new_edits: false`, then save the checkpoint in `_local`. `eggdb-couch` implements those endpoints plus database and document CRUD and `_all_docs`, so EggDB can be either end of a CouchDB or PouchDB replication. It was written from the documentation only.
- **One storage engine.** Databases live in the keyspace collections `couch<n>` of the served file (`DatabaseKeyspace`, D2), with a catalog in database 0. Each document keeps its revision tree (revision, parent, deletion flag), the bodies of its leaves only (a non-leaf body is dropped once superseded, as compaction would), and one sequence entry, moved on each change, for `_changes`.
- **Revisions and winners.** Revision ids are `<generation>-<hash>`, the hash an MD5 of the parent, the deletion flag and the body, as CouchDB's are. Replicated writes take the revision path from `_revisions` (`start`, `ids`). The winner is CouchDB's: the highest generation among the live leaves, then the greater hash, and among deleted leaves when all are deleted. Two replicas holding the same tree therefore show the same document, which the tests check after a two-way exchange.
- **Changes feed.** `normal` and `longpoll` (polling the store every 200 ms, at most 60 s, `timeout` honoured), `since=now`, `limit`, `style=all_docs` (every leaf), `include_docs` and a POSTed `doc_ids` filter. `continuous` is answered as `longpoll`, which replicators accept as one batch per request.
- **Security.** HTTP Basic sign-in as the server's user and password (compared by SHA-256 in constant time), the server's TLS settings off this machine, the shared memory budget and rate limiter, and bounded bodies.
- **Left.** Attachments (refused with `415` until stored as blobs), design documents' views and Mango queries, and `_session` cookie sign-in.
