## D278 Screen readers read values, states and structure and act on the GUI through the same keys a person presses — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); issue #29, applies D8, D9, D15 and D256

Until now the accessibility tree of the connect card and the main window gave the platform bridges
names, roles, a value string and five states, and the bridges passed on names and roles: a screen
reader could hear `File, edit text` but not the caret, could not press `Open`, tick `Open
read-only`, expand a tree row or walk the results grid by row and column. Section 7 of
`docs/ux/workspace.md` asks for values, states, patterns and grid structure on every OS.

- **One model, in the platform layer.** `eggdb_platform::window` carries everything a bridge
  needs, so no bridge knows a screen: `AccessRole` gains `Toolbar`, `ComboBox`, `TextArea`,
  `Alert`, `Tree`, `TreeItem`, `Grid`, `ColumnHeader` and `Cell`; `AccessState` gains `expanded`,
  `invalid`, `read_only` and `password` (UIA `IsPassword`, AT-SPI's password-text role, the
  `AXSecureTextField` subrole; AT-SPI's `InsertText` and `DeleteText` on it are refused, since
  its value is mask dots, so only a whole new value reaches it); `AccessNode` gains `description`, `caret` (`AccessCaret`, anchor and
  caret in characters), `actions` (`AccessActions`: invoke, toggle, expand/collapse, set value,
  focus, select), `table` (row and column counts), `cell` (row and column index), `tree_position`
  (level, position, set size) and `shortcut`. `AccessNode` has a `Default`, so screens set only
  what they have.
- **Requests are window events.** A bridge turns a screen reader's call into an `AccessRequest`
  (node id and `AccessAction`: `Focus`, `Invoke`, `Toggle`, `Expand`, `Collapse`, `Select`,
  `SetValue(text)`, `SetCaret`) through `access_request`, which refuses a node that is gone,
  disabled, read-only for a value, or does not offer the action, and values longer than 65,536
  characters. The request arrives as `WindowEvent::AccessRequested`, so it is handled on the
  window's thread between frames like a key.
- **Actions are keys.** `eggdb_gui::accessibility` gives each role its default actions, and
  `Workspace::access` answers a request by moving the focus to the node (`ConnectCard::focus_node`,
  `MainWindow::focus_node`) and pressing the keys a person would press: `Enter` invokes, `Space`
  toggles a checkbox, selects a tree row and opens the dialect menu, `Right`/`Left` expand and
  collapse a tree row, a new value is `Ctrl/Cmd+A` and the typed text, a caret is `Home` and
  arrows with `Shift`. The toolbar's `Run`, `Run all`, `Explain` and `Stop` press their shortcut
  from the editor. The query editor takes a value or caret directly (typing would trip
  bracket closing and indentation), and so does a connect-card input's new value, as one edit
  (`ConnectCard::set_focused_value`, control characters dropped) rather than one key press per
  character. So everything a screen reader does goes through the code the
  keyboard tests already cover, and nothing a screen reader sends can do what no key can.
- **The screens fill it in.** The connect card's fields carry their caret and selection, the
  failed field is `invalid`, `Protocol` is a combo box and `Open` names `Enter`. In the main
  window the toolbar is a toolbar with shortcuts on its buttons, the dialect pill a combo box with
  `expanded`, the editor a text area with its caret and `invalid` while an error shows, the error
  strip an alert, the object tree a tree of items with level, position, set size and expanded,
  the grid a grid with its row and column count, its headers column headers and its cells cells
  with row and column, the plan a tree of items with its costs as the description, and the DDL a
  read-only text area. Background tabs, result segments and the inspector's blocks offer no action
  yet, because no key reaches them.
- **UI Automation (Windows).** Each node answers the control patterns its actions and fields
  allow: Invoke, Toggle, Value, ExpandCollapse, SelectionItem, Grid and GridItem, Table and
  TableItem, through our own vtables on the same provider object; `SetFocus` requests the focus.
  Properties add the pattern values, `AcceleratorKey`, `FullDescription`, `IsDataValidForForm`,
  level, position and set size, and the assertive live setting of an alert; a changed value,
  toggle, expand state or selection raises a property-changed event, a newly selected cell or row
  `ElementSelected`, and the focus event stays.
- **AT-SPI2 (Linux and the BSDs).** Nodes serve the interfaces their actions and roles allow:
  `Action`, `Text`, `EditableText`, `Selection`, `Table` and `TableCell`, and `Component.GrabFocus`
  requests the focus; state sets add expandable, expanded, multi-line, read-only and invalid;
  `set_tree` raises `StateChanged`, `TextChanged`, `TextCaretMoved`, `TextSelectionChanged`,
  `SelectionChanged` and description and value property changes. The X11 loop turns the bridge's
  requests into window events.
- **NSAccessibility (macOS).** Elements are an `EggDBAccessElement` subclass of
  `NSAccessibilityElement` whose getters read the current node (value, focused, enabled, selected
  text range, expanded, row and column counts and ranges, disclosure level, help) and whose
  `accessibilityPerformPress` and setters for focus, value, selected text range and expanded queue
  requests; `isAccessibilitySelectorAllowed:` answers from the node's actions.
- **Browser.** The ARIA mirror's JSON adds `expanded`, `invalid`, `readonly`, `description` and
  `shortcut`, and `web/card.js` sets `aria-expanded`, `aria-invalid`, `aria-readonly`,
  `aria-description` and `aria-keyshortcuts`; the new roles map to `toolbar`, `combobox`,
  `textbox`, `alert`, `tree`, `treeitem`, `grid`, `columnheader` and `gridcell`.
- **Tests.** Unit tests on the model (`access_request`, `allows`), on the default actions, the
  key translation, character offsets and the tree dump (`accessibility::describe`, one line per
  node with value, caret, states, actions, grid and tree structure); golden dumps of the connect
  card at first start and of the main window's sample; requests driven through `Workspace::access`
  and `MainWindow::access_keys` (toggle, invoke, set value, caret, segment switch, open); UI
  Automation's patterns through the COM vtables on Windows; AT-SPI2's interfaces and events as
  pure message encoding; and the NSAccessibility role and press mapping.

Not yet: a hand check with VoiceOver (macOS), Narrator (Windows), Orca (Linux) and a browser
screen reader (NVDA or JAWS with Firefox or Chrome, VoiceOver with Safari) on the connect card and
the main window, which the unit tests cannot replace; UI Automation's Text pattern
(`ITextProvider`, ranges and the error annotation) and Selection pattern on the tree and grid;
NSAccessibility's row elements (`accessibilityRows`) for the grid and the tree, live-region
announcements for status and alert nodes there, shortcuts and subroles; UI Automation's `Invoke_Invoked` event, row
headers and multiple selection; AT-SPI2's text attributes, character extents (the whole node today),
sentence and paragraph boundaries (read as lines), row headers and selected rows and columns; the
main window's mirror in the browser; announcements of the grid's selection size (`2 rows by 2 columns selected`) as a
platform selection event; actions on background tabs, result segments, the inspector's blocks and
the dialect menu's items; and pointer-driven focus (D279).
