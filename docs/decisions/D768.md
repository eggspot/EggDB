## D768 Row pattern matching for complex event processing (match_recognize) — Decided by the code-only session (2026-11-12, D355); roadmap M16, `MATCH_RECOGNIZE` for complex event processing (D55)

- `row_pattern_matches(rows jsonb, pattern text) RETURNS jsonb` is the matcher of SQL:2016's row pattern recognition:
  `PATTERN` syntax with variables, concatenation, `|`, grouping and the `*`, `+`, `?` and `{n,m}` quantifiers, greedy
  or reluctant (`*?`), over one object per row saying which variables hold. A variable no row defines holds for every
  row, as an undefined pattern variable does. It compiles the pattern to a small program run by a backtracking
  matcher with an explicit stack (never recursion over rows), Perl-style preferment, `AFTER MATCH SKIP PAST LAST ROW`,
  empty matches skipped, a loop that consumes nothing left after one try, and limits on pattern size (4 KiB,
  10,000 instructions, nesting 50, repeats 1000), rows (1,000,000) and steps (20,000,000, then 54000).
- `eggdb_streams.match_recognize(query, partition_by, order_by, pattern, definitions)` is the SQL form until the
  `MATCH_RECOGNIZE` clause is parsed: `definitions` is a JSON object of variable → SQL condition evaluated on each
  row of the query (window functions such as `lag(price) OVER (...)` stand in for `PREV`), rows are taken per
  partition in order, and each match comes back with its partition, number, first and last row as JSON, row count
  and the classifier of each row.
- Left: the `MATCH_RECOGNIZE` clause itself in the parser, `MEASURES` with `FIRST`/`LAST`/`PREV`/`NEXT` and running
  versus final semantics, `ONE ROW` versus `ALL ROWS PER MATCH`, other `AFTER MATCH SKIP` modes, `PERMUTE`, anchors
  and exclusion syntax.
