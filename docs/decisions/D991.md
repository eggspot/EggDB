## D991 MySQL's spatial types — Decided by the code-only session (2026-11-13, D355); roadmap M10, MySQL's types (D19, D845)

- `GEOMETRY`, `POINT`, `LINESTRING`, `POLYGON`, `MULTIPOINT`, `MULTILINESTRING`, `MULTIPOLYGON` and
  `GEOMETRYCOLLECTION` (or `GEOMCOLLECTION`) columns are stored as the PostGIS-compatible `geometry` type (D845), so
  one stored form serves both dialects and every geometry function works on them. A `SRID n` attribute right after
  the type is accepted. The subtype is not enforced yet: a `POINT` column takes any geometry.
- MySQL's spatial function names that differ from PostGIS's only in name map onto the existing functions: `POINT(x,
  y)`, the `ST_...FromText` and `ST_...FromWKB` families, `ST_AsWKB`, `ST_AsWKT`, `ST_Distance_Sphere`,
  `ST_Latitude` and `ST_Longitude`. Names the two share (`ST_AsText`, `ST_X`, `ST_Distance`, `ST_Contains` and the
  rest) already work.
- Over the MySQL protocol a geometry column is `MYSQL_TYPE_GEOMETRY` and its value is MySQL's internal form, the SRID
  as four little-endian bytes then little-endian WKB, in both the text and binary protocols, so MySQL connectors
  decode it as they do from MySQL.
- Left: enforcing the column subtype and SRID, axis order for geographic SRIDs (MySQL puts latitude first for 4326),
  and MySQL's `ST_GeometryType` spelling (`POINT` rather than `ST_Point`).
