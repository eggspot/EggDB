## D1043 Global indexes over sharded data — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D18)

- A global secondary index places each entry on the shard its indexed value hashes to, not on its row's shard, so a
  lookup by value reads one index shard and then only the shards that hold matching rows, instead of every shard.
- **Consistency.** `eggdb_cluster::global_index::GlobalIndex` names an entry `FF "gix" 00` + name + value + primary key
  (each length-prefixed, so values never run into each other) and gives `entry_changes`: deleting the old value's
  entry and writing the new one's, nothing when the value did not change. These writes join the row's own write in one
  distributed transaction (D212) and commit at its one timestamp (D1042), so a snapshot read never sees an entry
  without its row or a row without its entry. A seeded simulation updates and deletes rows of three row shards with
  an index over two index shards and checks, at timestamps through the run, that every row's entry is where its
  value hashes and that the index holds exactly as many entries as there are rows (`Participant::scan_at` reads an
  index shard's entries for a value prefix at a timestamp, under the same wait rule as `read_at`).
- **SQL.** `CREATE GLOBAL INDEX <name> ON <table> (<column>) ON '<source>', ...` registers an index of a sharded table
  (D1041) in `eggdb_internal.global_indexes`, with one foreign source per index shard. On each index shard the
  entries live in `eggdb_global_index (index_name, value, shard_key)`. When a `SELECT`'s filter fixes the indexed
  column to a literal and the shard key is not fixed, the coordinator asks that value's index shard for the matching
  shard keys and plans the query over their shards only. `SHOW SHARD FOR INDEX <name> VALUE '<value>'` says where an
  entry goes; `DROP GLOBAL INDEX` forgets the index.
- Left: writing the index entries from SQL writes to a sharded table (writes are not distributed yet, D1041), and a
  backfill of an index created over existing rows.
- Learned from the descriptions of global secondary indexes in DynamoDB, Spanner and CockroachDB documentation; no
  code was read.
