## D356 Code-only batch 2 (M1): OpenBSD and DragonFly on `poll(2)`, NUMA placement, hybrid cores — Decided by the code-only session (2026-11-10, D355); extends D65, D73

- **OpenBSD and DragonFly** join the readiness backends' `poll(2)` list (their `nfds_t` is an
  `unsigned int`, their `sockaddr` layouts and `EINPROGRESS` are in D355's connect code). CI's
  `unix-vms` job gains `openbsd` and `dragonflybsd` entries that test the platform layer with each
  system's packaged Rust, because rustup ships no toolchain for either; a packaged compiler older
  than the pinned one fails that job, which the build-and-fix pass will see.
- **NUMA placement:** `MemoryRegion::place_on_numa_node(node)` binds a region from the operating
  system to one node with `mbind(MPOL_BIND, MPOL_MF_MOVE)`, through `syscall` with each Linux
  architecture's number so no libc version is needed. Heap regions (simulations) and other systems
  are `Unsupported`. Work is placed by node with the existing `numa_node_cpus` and
  `ThreadOptions::pin`.
- **Hybrid cores:** Windows' `PROCESSOR_RELATIONSHIP.EfficiencyClass` marks the cores of the
  highest class as performance cores and the rest as efficiency cores (one class means not
  hybrid). macOS reports only counts, so `CpuTopology::with_performance_core_count` carries
  `hw.perflevel0.logicalcpu` when `hw.nperflevels` is above one, and `performance_cpu_count`
  answers from either source. `ThreadOptions::hot()` asks for the user-interactive quality of
  service on Apple's systems (which keeps a thread on performance cores) and elsewhere pins an
  unpinned thread to the available performance CPUs, best effort.
