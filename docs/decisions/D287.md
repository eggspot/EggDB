## D287 `restore` and `import` wait for a busy file like every other command, case changes in Oracle's and SQLite's dialects check the value limit by the result they really build, and a set-returning function alone in `FROM` stops at a plain outer `LIMIT` — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); follows up D258, roadmap item 49

D258 left three follow-ups: `--busy-timeout` for `backup`, `compact`, `restore` and `transfer`
(`import` and `export`), the value check in Oracle's and SQLite's `upper`, and set-returning
functions in `FROM` that built every row before an outer `LIMIT` applied.

- **`--busy-timeout` everywhere.** `backup`, `compact` and `export` already opened the file
  through the session's options, so they waited; `restore` (and the copy its `--dry-run` makes)
  and `import` from an EggDB export built their own options and failed at once. They now take
  the same wait from `Session::busy_timeout`: five seconds by default, `--busy-timeout <ms>` from
  0 to 3,600,000, `0` for the old behaviour. When the file is still taken after the wait, the
  command exits 5 with the busy line D258 documented (`another program has it open for writing`
  for a command that reads, `another program has it open. Close it before writing, ...` for one
  that writes). Restoring an archived copy (`eggdb restore <new> <directory>` or `s3://...`) writes a new
  file and never waits for a lock.
- **Oracle's `upper`, `lower` and `initcap`.** They refused any text longer than a third of
  Oracle's 1,000,000,000-byte text limit, even ASCII text that would not grow, and checked the
  session's value limit only against that bound. They now follow D258's rule: the cheap bound
  (three times the input) first, and only when it is over the limit the exact length of the
  result, counted character by character without building it; `ORA-01489` past Oracle's limit,
  `54000` past the session's value limit.
- **SQLite's `upper` and `lower`.** SQLite's own functions change ASCII letters only, so the
  result is exactly as long as the input text. They now check that length against SQLite's
  limit (`string or blob too big`) and the session's value limit before the copy is changed,
  in place, as every other growing builder does.
- **A set-returning function in `FROM` under `LIMIT`.** When a `SELECT` reads only one
  set-returning function (`generate_series`, `unnest`, `json_each`, ... with or without
  `WITH ORDINALITY`), has no `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `DISTINCT`, aggregate,
  window function or Oracle `ROWNUM` limit, and its `LIMIT` and `OFFSET` are integer literals,
  the function stops after `LIMIT + OFFSET` rows (`rows_a_lone_function_needs` in
  `subquery.rs`, `BoundFunction::generate_at_most`). Anything else still builds every row first
  (bounded by work memory and the deadline), because those clauses need every row. Only
  literals count: an expression or parameter in `LIMIT` is evaluated once, by the executor, as
  before. The MCP server's row cap (D258) writes a literal `LIMIT`, so an agent's
  `SELECT * FROM generate_series(1, 1000000000000)` stops at `max_rows + 1` rows.

Checked by: `crates/eggdb/tests/cli_busy.rs` (each command waits at least the timeout under a
held lock, exits 5 with the busy line, and finishes once the holder lets go); unit tests in
`oracle_functions.rs` and `sqlite_functions.rs` under a small session value limit; executor
tests in `set_returning_tests.rs` that run `SELECT * FROM generate_series(1, 1000000000000)
LIMIT 3` with almost no work memory left, and show `ORDER BY`, `WHERE`, aggregates and
`DISTINCT` still see every row.

Not yet: a `LIMIT` given as a parameter or an expression; a set-returning function joined with
other tables, or with a `WHERE` the rows could be filtered by as they come; streaming the rows
to the executor instead of into a capped temporary table.
