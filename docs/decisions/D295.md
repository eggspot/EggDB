## D295 Oracle's dialect over TDS and PostgreSQL drivers: PL/SQL procedures called by name, their `OUT` parameters returned, and mssql-jdbc's `DatabaseMetaData` run as Transact-SQL — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap item 44, refines D134 and D269

D269 left two gaps for applications that read Oracle SQL through SQL Server drivers: an RPC
request naming a procedure always ran a Transact-SQL procedure, so a PL/SQL procedure could not
be called with mssql-jdbc's `{call p(?, ?)}` or SqlClient's `CommandType.StoredProcedure`, and
mssql-jdbc's `DatabaseMetaData` sends Transact-SQL (`EXEC sp_tables ...`, and for `getColumns` a
batch that declares a table variable and fills it with `INSERT ... EXEC sp_columns_100 ...`)
that Oracle's dialect refused.

- **An RPC request naming a PL/SQL procedure runs it.** When the connection reads Oracle SQL and
  the RPC names a PL/SQL procedure (`log_it`, `hr.log_it`, `"HR"."LOG_IT"`, `pkg.proc`, resolved
  as Oracle resolves the name of a `CALL`), the server runs Oracle's `CALL` with every argument
  named (`CALL log_it(P_N => @arg0, ...)`), bound as a TDS parameter of the procedure's declared
  type (D269's `@name`). An RPC parameter binds by position, or by name with or without its
  `@` and in any case (`@P_N` for `p_n`), in any order. An omitted or `DEFAULT` parameter takes
  the procedure's default, an `OUT` parameter is never passed in (it starts `NULL`, as in
  Oracle), and an `IN OUT` parameter is. A name that is not only identifiers joined by `.` is
  never put in the `CALL` text, so a name cannot carry SQL. The procedure lookup comes first; when
  no PL/SQL procedure has the name, the Transact-SQL procedure of that name runs as before
  (D269), and when neither exists the error is SQL Server's 2812.
- **`OUT` and `IN OUT` parameters come back as return values.** The `CALL`'s row of output
  parameters is not sent as a result set; each RPC parameter the call marks as output gets a
  RETURNVALUE token with its ordinal and name and the value the procedure left, in the
  procedure's declared type, as SQL Server returns output parameters, followed by RETURNSTATUS
  0. A parameter marked as output that the procedure declares `IN` is error 8162, an unknown name
  8145, a parameter given twice 8143 and one too many by position 8144, as SQL Server numbers
  them; a missing required argument is Oracle's own error from the `CALL`.
- **Over the PostgreSQL protocol, `CALL` already does what PostgreSQL does.** Oracle's
  `CALL p(...)` binds by position, with `=>` and with `$1` placeholders, and returns the `OUT`
  and `IN OUT` parameters as one row, its columns named after the parameters in Oracle's
  upper case. D295 pins this with end-to-end tests; no code changed for it.
- **A TDS batch that executes a catalog procedure runs as Transact-SQL.** On a TDS connection that
  chose another dialect, a batch (simple, `sp_executesql`, `sp_prepare`, `sp_prepexec`, or an
  RPC by name of a catalog procedure, which becomes an `EXEC`) in which an `EXEC` or `EXECUTE`
  token, read with Transact-SQL's lexer, is followed (after an optional `@status =`) by a name
  whose last part is one of SQL Server's catalog procedures (`sp_tables`, `sp_columns`,
  `sp_columns_100`, `sp_pkeys`, `sp_fkeys`, `sp_statistics`, `sp_stored_procedures`,
  `sp_sproc_columns(_100)`, `sp_datatype_info` and the others EggDB answers) runs whole in
  Transact-SQL. Oracle SQL has no `EXEC` statement and never names those procedures, so the rule
  needs no list of driver queries, as D269's `pg_catalog.` rule for PostgreSQL connections. A
  text without the letters `sp_` is not lexed again. mssql-jdbc's `getTables`, `getColumns`,
  `getPrimaryKeys`, `getProcedures` and `getProcedureColumns` therefore work while the
  connection reads Oracle SQL.
- **PL/SQL routines are in SQL Server's catalog.** `sys.objects`, `sp_stored_procedures` and
  `sp_sproc_columns` list PL/SQL procedures (type `P`) and functions (type `FN`, or `TF` for a
  pipelined function) beside Transact-SQL's, so `getProcedures` finds what an Oracle application
  calls. Their parameters are listed under their stored names, without an `@`.

Not yet: named `NOT NULL` constraints in `USER_CONSTRAINTS` (keeping the name changes the stored
table definition, D20); of overloaded PL/SQL procedures in a package, an RPC call describes the
first declared one for its output values (the `CALL` itself picks the overload as Oracle does);
`sp_sproc_columns` lists no return value row for a PL/SQL function.
