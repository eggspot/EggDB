## D1111 Federated SQL in Trino's style: `server.schema.table` names, imported on first use — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D18, D46, D229, D916, D917, D1110)

- **Names, not setup.** Trino reaches another system's table as `catalog.schema.table`. EggDB does the same with foreign servers (D916) as catalogs: a statement naming `sales.public.orders`, where `sales` is a server created with `CREATE SERVER`, reads that table. Before the statement runs, the session finds such three-part names in its tokens (the first part must name a server, so ordinary names are never touched). On first use it imports the table with `IMPORT FOREIGN SCHEMA ... LIMIT TO` (D917) into the schema `eggdb_federated_<server>_<schema>`, and rewrites the name to that foreign table, the same path Oracle database links take (`table@link`). Later statements find it imported. Another EggDB cluster is a server like any other (`eggdb_fdw` or `postgres_fdw` to its PostgreSQL port), so one statement spans clusters.
- **One query across servers.** The rewritten statement is a single query: each server's tables are foreign-table views, the filters on each are pushed into that server's query (D1110), and joins, aggregates and ordering run locally on what came back. Trino's planner works the same way when a connector cannot take the join.
- **Left.** Pushing a join between two tables of the same server into one remote query, dynamic filtering (sending one side's join keys to the other side as an `IN` list, Trino's "dynamic filters"), and re-importing when a remote table's columns change (drop the table from `eggdb_federated_*` to re-import).
