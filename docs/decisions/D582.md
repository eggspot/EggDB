## D582 MQTT flow control: Receive Maximum — Decided by the code-only session (2026-11-12, D355); roadmap M16, D526

An MQTT 5 client says in CONNECT how many QoS 1 and 2 messages it takes unacknowledged (Receive
Maximum, 65,535 when absent); the broker sent up to its own limit of 1,000 regardless and, past
that, dropped the message for that subscriber. Each subscriber now has a window, the client's
Receive Maximum capped at 1,000 (1,000 for MQTT 3.1.1 clients), and a message that finds the
window full waits in the subscriber's own queue (up to the 1,000 a kept session queues) instead
of being dropped. Each PUBACK or PUBCOMP that frees a place sends the next waiting message with a
new packet id. Waiting messages move into the kept session when the client goes away (D581), and
on resume they are sent as the window allows. A Receive Maximum of 0 is refused as the protocol
error it is. QoS 0 messages are not held back, as the specification says.

**Status:** code written, unbuilt (code-only mode, D355).
