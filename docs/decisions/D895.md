## D895 WebDAV, CalDAV and CardDAV — Decided by the code-only session (2026-11-12, D355); roadmap M16, D56

- A new workspace crate, `eggdb-dav`, serves files, calendars and address books as a front-end over the one core:
  resources kept on EggDB's key-value transactions through `eggdb_keyspace::Keyspace` in the collection `dav0`, served
  by `eggdb serve --dav-listen <address>` (default port 5232, loopback only until it has TLS; `--read-only` refuses
  changes with 403). Requests sign in with HTTP Basic as the server's user. It depends on `eggdb-keyspace`,
  `eggdb-http` and `eggdb-crypto` only, with a small namespace-aware XML reader of its own (no document type
  declarations, nesting limited to 64, 100,000 elements).
- Each path is a file (content type, body), a plain collection, a calendar or an address book, with dead properties,
  a last-modified time and an entity tag that changes at every write; a collection's tag also changes when a member
  does, which CalDAV and CardDAV clients use (`getctag`, `sync-token`).
- WebDAV (RFC 4918): `OPTIONS`, `GET`/`HEAD`, `PUT` with `If-Match` and `If-None-Match: *` (412), `DELETE` of a subtree,
  `MKCOL` and RFC 5689's extended form (409 without a parent collection, 405 when it exists), `COPY` and `MOVE` with
  `Destination` and `Overwrite`, `PROPFIND` at depths 0, 1 and infinity with `prop`, `allprop` and `propname` (unknown
  properties in a 404 propstat), `PROPPATCH` of dead properties and `displayname` (other `DAV:` properties are
  protected, 403 with 424 for the rest), and `LOCK`/`UNLOCK` as advisory locks: a token is granted and nothing is
  enforced, which is enough for clients that lock before writing (class 2) on a one-user server.
- CalDAV (RFC 4791) and CardDAV (RFC 6352): the principal `/principals/<user>/` with `calendar-home-set`,
  `addressbook-home-set` and `calendar-user-address-set`, a default `calendar` and `contacts` made on first use,
  `MKCALENDAR`, `supported-calendar-component-set`, objects checked to start with `BEGIN:VCALENDAR` or `BEGIN:VCARD`
  (`valid-calendar-data`, `valid-address-data`), and `REPORT`: `calendar-query` and `addressbook-query` (component
  filters by presence, text matches by case-insensitive containment; time ranges are not applied yet), the two
  multigets (missing hrefs as 404 responses) and RFC 6578's `sync-collection` (every member with the current token).
  `/.well-known/caldav` and `/.well-known/carddav` redirect to the principal.
- Left: time-range filters and recurrence expansion, `free-busy-query`, scheduling (iTIP), enforced locks, ACL
  (RFC 3744) beyond the one user, quotas, and TLS.
