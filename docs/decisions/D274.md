## D274 The connect card acts: the GUI reaches a database only through `Connection` in `eggdb-gui`, opens run off the window's thread through a `Connector`, and the platform layer gives the file dialog and dropped files — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap M6e, applies D8, D9, D15, D191 and D256, builds section 1 of `docs/ux/workspace.md`

Until now the connect card of `docs/ux/first-screen.md` emitted `ConnectAction::Open` and
`Browse`, and nothing acted on them. Section 1 of Fable's `docs/ux/workspace.md` says what they
do: open a typed path, choose one with the OS's file dialog, take a dropped file, show progress
that `Esc` stops, show the engine's failure as an `Error` line and a `Try:` line, and replace the
card with the main window on success.

- **One link to the database.** `Connection` (`crates/eggdb-gui/src/connection.rs`) is the GUI's
  only way to a database: an open `.eggdb` file (`eggdb::Database`) or a session on a server
  speaking the PostgreSQL protocol (`eggdb_pgwire::client::PgClient`, the client `eggdb follow`
  and the C API already use). It answers its name (the file's stem or the URL's database), its
  location (the file's name or `host:port`), the status bar's `Connected · shop.eggdb ·
  read-write` text, the `Opened shop.eggdb` toast, the user's tables, and `run` for SQL in
  PostgreSQL's dialect with each result as text (`ResultTable`, `StatementFailure`). The query
  tab, the object browser and the plan view (D275 to D277) add their calls here, never a second
  path to the engine. `eggdb-gui` now depends on `eggdb` and `eggdb-pgwire`; the server binary
  still never carries the GUI (D256).
- **Opens are a `Connector`.** `Connector::connect(&ConnectTarget)` opens a `FileTarget` (the
  resolved path and the two checkboxes) or `ConnectOptions`; `EngineConnector` is the real one,
  and tests give a slow stand-in. `Workspace` (`crates/eggdb-gui/src/workspace.rs`) owns the
  screen (`Screen::Connect(ConnectCard)` until an open succeeds, then `Screen::Main`), runs each
  open on its own thread and polls it, shows the progress state only after 120 ms so a quick
  open never flickers, and drops a stopped open's answer (its database closes when the thread
  ends). `Esc` while an open runs is `ConnectAction::StopOpening`; the status line says
  `Cancelled` for 2 s.
- **Failures in the card's words.** `ConnectFailure` keeps the engine's SQLSTATE, the message,
  the fix and the field it is about (`FailureField`), and gives the two lines of workspace.md
  1.6's table exactly: no such file, the directory missing with Create checked, not an EggDB file
  (a directory too), open in another process, permission denied, connection refused, timed out
  after 10 s, no TLS, `28P01` and `3D000` with their codes. The field takes the focus with its
  value selected and the File input gets its `error` border. The card's `CardError` is now the
  two lines as shown (`line`, `fix: Option`), 18 px each, the `Try:` line in `textPrimary`.
- **Typed paths.** Whitespace cut, `~` and `~/` expanded from `HOME` (`USERPROFILE` on
  Windows), relative paths resolved against the process's current directory
  (`resolve_typed_path`).
- **The platform layer.** `eggdb_platform::window::has_file_dialog()` is true on macOS and
  Windows; `Window::choose_file_to_open(&OpenFileDialog)` shows `NSOpenPanel` through our own
  Objective-C runtime calls, and on Windows `GetOpenFileNameW` (Explorer style, with
  `OFN_NOCHANGEDIR` so relative paths keep their meaning) with `EggDB databases (*.eggdb)` first
  and `All files` second. `GetOpenFileNameW` was chosen over `IFileOpenDialog`: on Windows Vista
  and later it shows the same dialog, without COM's vtables to declare. macOS's open panel has no
  file-type menu, so it shows every file (a file of another kind is answered by the
  not-an-EggDB-file lines). Windows and macOS report dropped files as
  `WindowEvent::FilesDropped(paths)` (`DragAcceptFiles`/`WM_DROPFILES`; the view registered for
  `public.file-url`), and macOS reports a drag coming over and leaving
  (`FileDragEntered(paths)`, `FileDragLeft`), so the card draws its 2 px `accent` border and
  `Drop to open`. `WindowEvent` is no longer `Copy`, as it now carries paths.
- **The layout without a dialog.** `ConnectCard::file_dialog` drops `Browse…`, widens the File
  input to 512 px and takes stop 3 out of the focus order. `eggdb-gui --png` keeps drawing the
  card as on a system with a dialog, so the reference checksums stay the same on every OS;
  `--no-file-dialog` draws the other layout.
- **Scripts.** `eggdb-gui --open <path>` opens a file as the card's `Open` does (`--no-create`,
  `--read-only` set the checkboxes); with `--png` the frame is the outcome, the main window or
  the card with its failure, which `tests/workspace_frames.rs` compares byte for byte with the
  library's frames.
- **Design.** The server segment's layout with the `URL` row, which did not fit workspace.md 1.4
  as written, is Fable's (recorded in `docs/ux/workspace.md` 1.4).

Not yet: drawing the `Connect to a server` segment (its fields, the `URL` input that fills them
and is rewritten from them, the protocol menu, `Use TLS` and its warning; `Connection` already
connects and reports the failures), wrapping long error lines at 512 px with at most three lines
each, the sweeping progress bar (it is drawn static), the drag-over ring on Windows (it needs an
OLE `IDropTarget`) and drops on X11 (XDND), the browser's layout without `Browse…` and its dropped
files opened in memory (`Connection::in_memory` is there for it), macOS's two-filter menu (an
accessory view), SQLite files opened as copies in memory as `eggdb sql` does, the main window's
toast and status-line text for a server (`· TLS`), and accessibility nodes for the main window.
