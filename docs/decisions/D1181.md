## D1181 gRPC server reflection, over streamed calls in `eggdb-http2` — Decided by the code-only session (2026-11-15, D355); roadmap M6a, follows D1177

- **Streamed calls in `eggdb-http2`.** The server answered a request once its body had ended. `Handler` gains `streams`, `stream_headers`, `stream_message` and `stream_trailers`, all with defaults that keep the old behaviour: when `streams` accepts a call's header fields, the response headers go out at once, each complete gRPC message the client sends (reassembled across DATA frames, uncompressed only) is answered with the messages `stream_message` returns, and the trailers follow when the client half-closes. A reset stream drops its pending events. This is what bidirectional calls need, since a client such as `grpcurl` waits for each answer before it sends its next request.
- **Reflection.** `GrpcApi` streams `grpc.reflection.v1.ServerReflection/ServerReflectionInfo` and its `v1alpha` twin, which older tools still call. `list_services` answers every table's `eggdb.v1.<Table>Service` and the reflection services; `file_containing_symbol` (any `eggdb.v1.` symbol) and `file_by_filename` (`eggdb/v1/eggdb.proto`) answer one `FileDescriptorProto` built from the same table model as D1177's `.proto` text: the row message with proto3 `optional` fields (each with its synthetic oneof, as `protoc` writes them), the key and list request messages, `DeleteResult`, and the services, `List` marked server-streaming. Other symbols get `NOT_FOUND`, extension queries `NOT_FOUND` (EggDB's messages have none), anything else `UNIMPLEMENTED`, each as the protocol's `error_response`. The caller signs in with the same `authorization` metadata as for calls, so reflection shows only what that role may read.
