## D1010 Graph property indexes in an order-preserving encoding, read as key ranges — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D206, D885)

- A property index entry's value was written with a length in front, so its keys did not sort as the values and a
  range condition (D885) read every entry of the index. Values are now written so their bytes sort as the values:
  integers as big-endian with the sign bit flipped, non-integral floats with the usual sign-flip transform, text
  with each zero byte doubled as `00 FF` and ended by `00 01` (so a shorter text sorts first and the node id that
  follows never mixes with the text), booleans as one byte. Each kind keeps its tag byte, so kinds stay apart.
- `WHERE n.p >= a AND n.p < b` and `STARTS WITH` read only the key ranges that can hold the answer: one range per
  kind the bounds compare with (a number range reads the integer range and the float range), each from its
  lowest key to the first key after its highest; every entry read is still checked against the bounds, so a
  range that reads slightly more stays exact.
- `KeysRead` gains `visit_range(start, end, visit)`. Its default walks the keys; the in-memory keyspace and the
  file's collections seek to `start` in their B-tree, so a range read costs the entries it returns.
- Existing files: the index marker's value becomes `2`. A graph whose marker is the old `1` is read by label scans
  (correct, slower) until its first write, which deletes the old entries and writes every index in the new
  encoding before the write goes on. No file format version changes: these are keys inside the graph's
  collection.
