## D568 `eggdb restore` from an SQLite file — Decided by the code-only session (2026-11-12, D355); roadmap M5, D13, D180

`eggdb sql app.sqlite` already reads an SQLite file into memory (`cli::sqlite_import`) and leaves
the SQLite file as it was. Moving to EggDB for good needs the same copy written into an EggDB
file, so `eggdb restore <file> <dump>` now recognizes a dump in SQLite's format by its header
(after the other formats it knows, and only for a regular file) and runs that import against the
opened file instead of the database in memory: tables, rows, indexes, views and triggers, with the
committed pages of a `-wal` file beside it. Statements EggDB refuses are skipped and listed, one
`skipped:` line each (and counted under `--format json`), and the restore still succeeds, as
`eggdb sql` treats them. A table that already exists in the target fails the restore as a
database error, so restoring twice does not duplicate rows; `--dry-run`, `--section` and the
dialect options do not apply to it.
