## D157 Triggers: one record per table in the file, firing inside the statement in each dialect's own order, written in the dialect that created them, nesting at most 32 deep — Decided by the build loop (by judgement, 2026-10-30); part 3.13, applies D9, D27, D35, D45, D114, D137

Part 3.13 adds triggers for SQLite, MySQL, SQL Server and PostgreSQL. The plan named this
decision D151, which an earlier part had taken; it is D157.

**One record per table, in the file.** A table's or view's triggers are one catalog record
(prefix, `0x0B`, the table's internal name) listing them in firing order, with their dialect,
timing, events, level, `UPDATE OF` columns, condition, transition tables, action and the whole
`CREATE TRIGGER` text (layout in sql.md "How SQL is stored"). One record per table means the
DML paths read one key to learn whether anything fires, and a per-session cache keyed by the
store's committed version skips even that while nothing changed. Dropping a table or view
deletes the record; renaming moves it. Every catalog (`sqlite_schema`, `pg_trigger`,
`information_schema.triggers`, `sys.triggers`, MySQL's `SHOW TRIGGERS`) is built from these
records, so a trigger created in one dialect shows in all of them.

**A trigger runs in the dialect that wrote it.** The record keeps the dialect, and its body is
stored as source and parsed when it fires, in that dialect, whatever the session's dialect is.
SQLite and MySQL bodies run on a small trigger interpreter (`triggers/body.rs`: statements,
`DECLARE`, `SET`, `IF`, `WHILE`, `SIGNAL`, `RAISE`); Transact-SQL bodies run on the batch
interpreter (D137) with `inserted` and `deleted` as table variables and `UPDATE(column)`;
PostgreSQL triggers name a function, and PL/pgSQL functions (3.14) plug in at the same place
(`TriggerAction::Function`), as Oracle's PL/SQL triggers (3.16) will with an action of their own.
PostgreSQL has no `LANGUAGE sql` trigger functions (a SQL function cannot return `trigger`), so
until 3.14 `CREATE TRIGGER ... EXECUTE FUNCTION` reports the function as missing, as PostgreSQL
does.

**Firing is part of the statement.** Row triggers fire in the DML paths (`INSERT`, its literal
fast path, upserts, `UPDATE`, `DELETE`, `MERGE`'s updates), `BEFORE` triggers before each row is
checked and written (they may change `NEW` or skip the row), `AFTER` triggers after it is
written. Statement triggers (Transact-SQL, PostgreSQL's `FOR EACH STATEMENT`) collect the
statement's old and new rows and run when the statement's writes are done. Everything happens in
the statement's transaction: when the session is in autocommit, a statement whose triggers run
opens one around itself and commits it after them, so a trigger's changes commit with the
statement or not at all (a killed-process test checks it). `INSTEAD OF` triggers replace the
write on views (and, in Transact-SQL, on tables).

**Each dialect's order and rules.** SQLite and MySQL fire in creation order (MySQL's `FOLLOWS`
and `PRECEDES` place a trigger), PostgreSQL in name order, SQL Server in creation order.
SQLite's `recursive_triggers` is off, MySQL refuses a trigger that changes the table its
statement changes (1442), SQL Server's nested triggers fire but not a trigger on itself, and
PostgreSQL triggers may recurse. Every dialect nests at most 32 deep (`MAX_TRIGGER_DEPTH`),
deeper being an error, and a table holds at most 1024 triggers, a trigger's text at most 1 MiB:
hostile definitions are errors, never crashes or hangs (D9, D45).

**Restores.** SQL Server scripts now run their triggers and `ENABLE`/`DISABLE TRIGGER`;
`pg_dump` triggers stay in the report until their PL/pgSQL functions run (3.14), Oracle's until
PL/SQL (3.16).
