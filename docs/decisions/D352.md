## D352 Heart-beats and idle limits for messaging and syslog: STOMP `heart-beat` negotiation, AMQP 0-9-1 server heartbeats, syslog TCP connections closed after `--idle-timeout`, and dropped syslog messages logged and counted (`eggdb_syslog_messages_dropped_total`) — Decided by the build loop (batch 6, 2026-11-10); roadmap M16, extends D214, D217 and D315, applies D9

D214 left AMQP's heartbeats sent by the server, D217 left STOMP's heart-beats, and D315 left an
idle limit on TCP syslog connections and any report of a batch the collector fails to store. A
peer that vanishes without closing its socket (a laptop that sleeps, a cut network) held its
connection slot until the server stopped, and a client library that expects heart-beats from the
server gave up on a healthy connection. Built from the STOMP 1.2 specification ("Heart-beating"),
the AMQP 0-9-1 specification (`connection.tune`, `connection.tune-ok` and the heartbeat frame,
section 4.2.7) and RFC 6587.

- **STOMP.** `CONNECTED` now offers `heart-beat:10000,10000` (sx = sy = 10 seconds) instead of
  `0,0`. From the client's `heart-beat:cx,cy` (absent means `0,0`, so STOMP 1.0 clients are
  unchanged) the server sends an end of line every max(sx, cy) milliseconds when cy is above zero
  and it has sent nothing else in that time, and drops a client that sent no byte for twice
  max(cx, sy) milliseconds when cx is above zero, as the specification's negotiation says. A
  header that is not two non-negative integers is refused with an `ERROR` frame. End-of-line
  heart-beats the client sends between frames are now taken off the read buffer, so a connection
  that only beats does not grow it. The offer lives in the shared `Broker`
  (`HeartBeatOffer::STANDARD`); tests serve with millisecond offers through the crate-internal
  `serve_offering`.
- **AMQP 0-9-1.** `connection.tune` proposes a heartbeat of 60 seconds (RabbitMQ's default)
  instead of 0, and the value in the client's `tune-ok` is the one used, `0` turning heartbeats
  off. The server sends a heartbeat frame (type 8, channel 0) when it has sent nothing for half
  the interval, and closes the socket, without the `connection.close` handshake, when it has
  received no byte for two intervals, as section 4.2.7 says a peer should. Any octet counts as
  traffic, not only heartbeat frames.
- **Syslog.** `SyslogCollector::new` takes the server's `--idle-timeout` (no new flag), and a
  TCP connection that sends nothing for that long is closed; an unfinished last line is stored
  as at the end of a stream. A batch the `syslog` table refuses (a changed table, a revoked
  privilege) no longer vanishes: each 500-row chunk is tried on its own, so one refused chunk no
  longer drops the chunks after it, and the refused messages are counted and reported to the
  serve log in one line per batch (`syslog dropped N messages the syslog table refused: ...`).
  Every message the collector drops is counted: datagrams longer than 16 KiB (including the
  `InvalidInput` Windows answers for them), a TCP frame refused by its framing (the connection
  is still closed), and the messages of a refused batch. The count is per collector
  (`SyslogCollector::messages_dropped`) and for the whole process
  (`eggdb_observability::syslog_messages_dropped`), which `--metrics-listen` renders as the
  counter `eggdb_syslog_messages_dropped_total`.

Decided by the plan reviews:
- *Which STOMP intervals?* The specification's: send every max(sx, cy), drop after silence of
  twice max(cx, sy). The factor 2 is the tolerance the specification leaves to the receiver;
  RabbitMQ and ActiveMQ allow a similar grace.
- *Whose AMQP interval?* The client's `tune-ok` value, as RabbitMQ does: the client may lower,
  raise or turn off the proposal. AMQP 1.0's `idle-time-out` is left (next batch).
- *Count messages, not batches,* so the metric adds up with what senders sent.

Decided by judgement (recorded for review):
- A silent STOMP or AMQP peer is closed without an `ERROR` frame or `connection.close`: it is
  presumed dead, and a write to it could wait for the write timeout.
- A STOMP heart-beat is sent up to one read poll (50 ms) after it is due; at the 10-second
  interval that is inside every client's tolerance.
- The process-wide counter is a static, like `eggdb_sql::activity`, because the metrics endpoint
  renders from process state and has no handle on the collector.

Left: AMQP 1.0's `idle-time-out` (the open performative's field, enforced and sent); a STOMP
`ERROR` frame before dropping a silent client; heart-beats over STOMP's WebSocket transport (not
built); a limit on how often a failing syslog table is reported (one line per failed batch now).
