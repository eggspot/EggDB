## D116 Schemas as name prefixes with tables in format version 7, views as format version 8 records in the table key space expanded at use, comments in their own key space — Decided by the build loop (by judgement, 2026-10-28); applies D1, D9, D10, D13, D20, D32, D96, D109, D112, D114

Item 33 adds what `pg_dump` output needs next, after item 32's sequences and constraints:
schemas with `search_path`, views and `COMMENT ON`. Items 34 (`COPY`) and 35 (`pg_dump` restore)
build on it.

**A schema is a name prefix, and `public` is today's catalog.** Every table, view and sequence
already lives under its name in its key space (D98, D114). An object in schema `s` other than
`public` is stored under the internal name `s`, a zero byte, then its name; an object in
`public` keeps the plain name it has today. So every existing file, table and sample file (D96)
keeps its exact bytes, and a database that never uses schemas looks exactly as before. A zero
byte cannot be part of a name: the parser refuses a quoted identifier that holds one (`42602`),
PostgreSQL's protocol cannot carry one, and a stored name with more than one zero byte, an
empty part or the `public` prefix is damage (`XX001`). Messages show the internal name with a
dot (`relation "app.t" already exists`). A schema itself is a record of its own, key space
`0x07` followed by its name, value a version byte (1). `public` always exists and cannot be
dropped or renamed in this release; `pg_catalog` and `information_schema` are reserved (`42939`,
like every name starting with `pg_`), the latter for item 38.

**Tables in a schema are format version 7.** A table whose internal name carries a schema is
written in version 7, the version 6 layout with the constraints part always present; a version 7
definition under a plain name, or a version 1 to 6 definition under a qualified name, is
damage. A release that reads up to version 6 refuses a version 7 table by name, so it can never
show, change or drop `app.t` as a table called `app\0t` (the lesson from item 32's review:
the previous release must refuse, not break a new invariant). Index names are unique within a
schema, as PostgreSQL's are; `DROP INDEX app.i` and an unqualified `DROP INDEX i` (found
through the search path) work.

**`search_path` is per session and resolved per statement.** The setting already existed
(`"$user", public`). At the start of each statement EggDB computes, once, the schemas of the
path that exist (`$user` is the session user; `pg_catalog` is implicitly searched first for
functions, and holds no relations yet), in thread-local state that a guard restores when the
statement ends, also on errors and for nested work. Unqualified relation names in every
statement are resolved against it before the statement runs: the first schema that holds a
table, view or sequence of that name wins; a name found nowhere stays as written so the error
names it, and when `public` is not on the path it can no longer reach `public`. New objects go
into the first existing schema of the path (`3F000 no schema has been selected to create in`
without one). `SET search_path`, `RESET`, `SHOW search_path`, `set_config('search_path', ...,
false)` (the form `pg_dump` writes; only constant arguments, and `is_local` true is `0A000`),
`current_schema()` and `current_schemas(bool)` (text in array form; arrays come later) are
PostgreSQL-only. The path is cached per session and committed version (a snapshot read reuses it until a commit changes the catalog; a write looks the `$user` schema up once), and an unqualified name costs nothing more while the path is only `public`, so point `SELECT`s stay as cheap as before (the `compare` job's `sql_point_select` line); the other
dialects have one schema and pay nothing. `nextval('name')` resolves an unqualified sequence
name against the same path when it runs; a `DEFAULT nextval('s')` is stored as text, so it
follows the path at use, where PostgreSQL binds the sequence when the default is created
(`pg_dump` writes qualified names, which behave the same).

**A view is a record in the table key space, format version 8.** A view's record sits where a
table's definition would, under its internal name in key space `0x02`, with the version byte 8:
the dialect it was written in, a flags byte (1: its select list used `*`; 2: it was created
with a column list; any other bit is damage), its query text exactly as written, its column
names, types (types may be unknown) and the names its query gave them, the existing schemas of the search
path at creation, and the relations its query names directly. Keeping views in the table key
space makes tables, views and sequences one namespace for free, and makes a release that reads
up to version 6 (or 7) refuse it by name: it cannot create a table over a view, read a view as
a table or drop it as one. Its decoder is strict: unknown dialects, flags or type tags,
duplicate or empty column names, a zero byte in a column name or the name its query gave it,
over 1,600 columns, over 64 path entries or 4,096 references,
malformed names, trailing or missing bytes are damage, and every count is bounded by the bytes
present before anything is allocated. Reading a view where a table is expected is `42809`
(`"v" is not a table`); `INSERT`, `UPDATE`, `DELETE` and `TRUNCATE` on a view are `0A000`
(views are read-only in this release).

**Views are expanded where they are used, never trusted.** When a statement names a view, its
stored text is parsed again in its own dialect and becomes a derived table of the statement,
item 30's machinery (D112): run as an intermediate result, columns renamed to the view's
columns. The view's own names are resolved with the search path stored at its creation, an
approximation of PostgreSQL binding names when a view is created. Expansion is bounded as
subqueries are: the nesting of the statement, its subqueries, derived tables and the views
they expand together stay within 32 query levels and 64 nesting levels, and all of their
`SELECT`s within 1,024 (`54001`); a view met again while it is being expanded is `42P17
infinite recursion detected in rules for relation "v"`, also when a damaged or hand-made
catalog holds a cycle. `CREATE OR REPLACE` checks the new definition with the view itself on
the expansion stack, so a view that would reach itself, directly or through others, is refused
when it is created. A view whose text no longer parses is damage (`XX001`). `SELECT *` is
expanded when the view is created, as PostgreSQL does: the column list is stored, and a view
that used `*` is narrowed to those columns, by position, when it is used, so a column added to
the table later does not appear.

**Dependencies are keys, and changes that would break a view are refused in PostgreSQL.** For
each relation a view names directly there is a key in key space `0x08`: the relation's name
(length-prefixed) then the view's name, value `0x01`. `DROP TABLE`, `DROP VIEW` and `DROP
SCHEMA` refuse with `2BP01` while views depend on the object, unless `CASCADE`, which drops the
dependent views through a queue in batches of 256, never by recursion. `ALTER TABLE` actions
that touch columns (`DROP COLUMN`, `TYPE`, `RENAME COLUMN`) check
every dependent view again after the change, in the same transaction: a view that no longer
plans, loses columns or would change a column's type makes the statement fail with `2BP01`.
Renaming a table or view (or moving it with `SET SCHEMA`, or renaming its schema) that a view
depends on is `0A000`: the stored text names it, and EggDB has no printer to rewrite view text
yet. MySQL, SQLite and Oracle keep their own behaviour: dropping or changing a table leaves its
views in place, and they fail when used until the table is back.

**Comments are records of their own.** Key space `0x09`, then the owning relation's internal
name (length-prefixed), a kind byte (1 relation, 2 column, 3 index, 4 constraint) and the part's
name; a schema's comment is kept under an empty owner with kind 5 and the schema's name. The
value is a version byte (1) and the text. `COMMENT ON ... IS NULL` (or `''`) removes it.
Creating a table, view or sequence first removes comments left under its name, dropping one
removes its comments, and renames move them. A release before this one ignores the key space:
a table it drops leaves its comments behind, and the cleanup on creation keeps a later table of
the same name from inheriting them. MySQL's `COMMENT 'text'` column option and `COMMENT='text'`
table option are stored the same way and shown by `SHOW CREATE TABLE` and `SHOW FULL COLUMNS`;
Oracle's are listed by `USER_TAB_COMMENTS` and `USER_COL_COMMENTS`, views by `USER_VIEWS`; the
shell's `.schema` prints `COMMENT ON` statements in the PostgreSQL dialect. `obj_description`
and `col_description` come with `pg_catalog` in item 37.

**What `pg_dump` writes is accepted.** `CREATE SCHEMA [IF NOT EXISTS] name [AUTHORIZATION
role]`, `ALTER SCHEMA ... OWNER TO`, `ALTER TABLE/VIEW/SEQUENCE ... OWNER TO`, `GRANT`, `REVOKE`
and `ALTER DEFAULT PRIVILEGES` (accepted with a warning that EggDB has no roles yet), `CREATE
EXTENSION [IF NOT EXISTS] plpgsql [WITH SCHEMA ...]` (any other extension is `0A000` naming it),
`COMMENT ON EXTENSION`, the `SET` parameters of `pg_dump` (`default_with_oids`,
`escape_string_warning` and `synchronize_seqscans` are remembered too) and view text with
parenthesized leading joins (`FROM ((a JOIN b ON ...) JOIN c ON ...)`, as `pg_dump` prints
every view). `CREATE MATERIALIZED VIEW`, `CREATE TYPE`, `CREATE DOMAIN`, `WITH CHECK OPTION`,
temporary and recursive views stay `0A000` with a message naming the statement, for item 35's
restore report.

**Names EggDB generates stay schema-free.** Default constraint and index names (`t_pkey`,
`t_v_key`, `t_w_idx`, `t_w_check`, `c_id_fkey`, SQLite's `sqlite_autoindex_t_1`) are built from
the table's own name, never its internal schema-qualified name, so they can be named in `DROP
CONSTRAINT` and `DROP INDEX` and survive a schema rename; the decoder treats a zero byte in a
stored column, index, constraint or parent column name as damage. Moving a table with `SET
SCHEMA` is `42P07` when one of its index or constraint names is already used in the target
schema. Owned sequences do not move with their table, because column defaults name them in text.

**Views are bounded in size too.** A view's query text is at most 1 MiB (`54000` when it is
created; a longer stored text is damage), and the view text a statement expands, counted each
time a view is used, is at most 64 MiB (`54000`), so a short statement that names a large view
hundreds of times cannot make EggDB parse gigabytes. A `BEGIN` block that rolls back, or fails
and ends, restores `search_path`.

**A `SELECT *` view follows its dialect when the tables under it change.** MySQL, SQLite and
Oracle let a table be dropped and created again under a view, so each view column keeps the
name its query gave it. PostgreSQL's views keep their columns by position, as its tables cannot
change under them. In MySQL and Oracle each view column takes, in order, the first column of the
query's output not yet taken with the name it had when the view was created (MySQL then also
compares case-insensitively when no exact name is left, as its column names are), so the
occurrences of a repeated name (`SELECT * FROM a JOIN b` with `id` in both) keep their order and
a view over tables recreated with the same or a reordered shape keeps working; a column with no
match left is MySQL's error 1356 or ORA-04063. Those names live only in the view record; the
query's output is renamed by position to the view's names inside the expansion, so repeated
names never meet. In SQLite a view without a column list is expanded again and shows the
table's columns as they are now; a view with a column list renames the output by position and,
when the number of columns no longer matches, fails when used with `expected 2 columns for 'w'
but got 3`, as SQLite does.

**Upgrade.** A zero byte is now the schema separator, so a file written by an earlier release
whose table, column, index or constraint name holds one reads as damage (`XX001`) after the
upgrade, wherever that definition is read.

**Downgrade.** A file that uses none of this is unchanged. A file with a schema, a table in a
schema or a view is refused by name by older releases wherever they read those records (listing
tables, opening the table, creating an index, which scans every definition); they still read
and change the other tables. Comments and dependency keys are ignored by them: comments can be
left over (cleaned as above), and a table an older release drops leaves its views in place,
failing when used, as MySQL's do.

**Considered and not chosen.** Keeping views in a key space of their own: an older release
would not see them and could create a table of the same name, breaking the one-namespace
invariant silently. Storing the schema inside the table definition under an unchanged key: two
tables `a.t` and `b.t` need two keys. Rewriting stored view text on renames: needs a SQL printer
for every dialect; refused for now instead. Inlining simple views into the outer query so that
indexes are used through them: a later performance pass (today a view's rows are produced once
per statement, bounded by the statement's 1 GiB work memory).
