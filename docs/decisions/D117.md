## D117 `COPY` streams through a client channel into the `INSERT` path in one transaction, scripts carry their data inline, lines up to 1 GiB, and no server files or programs — Decided by the build loop (by judgement and by research, 2026-10-28); applies D1, D9, D13, D86, D100, D103, D110

Item 34 adds `COPY ... FROM STDIN` and `COPY ... TO STDOUT` in PostgreSQL's text and CSV
formats, psql's `\copy`, and `eggdb import --csv`. It is the groundwork for item 35: a
`pg_dump` plain-format dump carries every table's rows as `COPY t (cols) FROM stdin;` followed by
tab-separated lines and `\.`. Everything is written from the PostgreSQL manual's COPY page and
the protocol chapter (D1).

**The client end is a trait.** `eggdb_sql::CopyChannel` is where a `COPY`'s data comes from and
goes to: `start_copy_in`, `read_copy_data` (append the next piece of any size, `false` at the
end), `abandon_copy_in` (the copy failed before its data ended), `start_copy_out`,
`write_copy_data` (one row) and `finish_copy_out`. `Session::execute_with_copy` and
`execute_prepared_with_copy` take one; `execute`, `execute_while` and `execute_prepared` pass a
channel that refuses (`0A000`), so a caller with no client gets an error, never a hang. The
PostgreSQL connection implements it on the socket (`CopyInResponse` flushed before reading,
`CopyData` appended, `CopyDone` ends, `CopyFail` is `57014 COPY from stdin failed: ...`,
`Flush` and `Sync` ignored until the copy ends as the protocol chapter says, any other message
fails the copy with `08P01`, and a lost connection or a stop rolls it back and ends the
connection). `COPY TO` sends one `CopyData` per row, as the protocol describes. After a failed
copy-in the existing loop already drops `CopyData`, `CopyDone` and `CopyFail` (simple query)
or everything until `Sync` (extended), so the server answers the error at once instead of
reading the rest of the data. The command-line clients implement it on stdin and stdout, a
file (`\copy`, `import --csv`) or the shell's next lines.

**Scripts carry their data inline.** `Session::execute_script` runs a script as `psql -f` does:
the data of a `COPY ... FROM STDIN` is the script's own lines after the statement's line, up to a
line `\.` or the end. Since the lexer must not see the data, the script is tokenized in rounds:
a round stops after the first statement that starts with `COPY` and has `FROM STDIN` (or
`STDOUT`) outside parentheses, the statements up to it run, its data is read from the text in
place (no copy) and reports how far it reached, and the next round lexes the rest of the `COPY`'s
own line and then the text after the data, keeping byte offsets into the whole script so error
positions stay right. Statements after the `;` on the `COPY`'s line run after the data, as in
psql. Only the PostgreSQL dialect looks for `COPY`; the other dialects tokenize as before and
refuse `COPY` with their own errors. `eggdb sql` uses `execute_script` for scripts and stdin and
`execute_with_copy` with `-c` (data from stdin); `eggdb shell` feeds its next lines.

**Rows take the `INSERT ... VALUES` path in one transaction.** Each field goes through its type's
text input exactly as a quoted constant does (`eval::string_constant`, then the assignment cast),
and the row through `StoredRows` with the table's prepared checks, as `insert_literals` does
(D100): not-null, check, primary key, unique indexes, serial and identity columns, sequences.
Defaults are parsed once per statement and evaluated per row. A `COPY FROM` is one statement in
one write transaction, so any error rolls back every row, and in a `BEGIN` block fails the block.
Foreign keys are checked every 4,096 rows and the checked rows forgotten, which is the same as
checking at the end because a `COPY` only adds rows to its own table; a table with a foreign key
to itself keeps its rows until the end (bounded by D100's 1 GiB), so rows may refer to rows later
in the data. Errors carry PostgreSQL's SQLSTATEs and a context line (`COPY t, line 3, column b:
"x"`, `COPY t, line 3: "<line>"`, or `COPY t, line 3`), a new `SqlError::context` that the
protocol sends as `W` and the command line prints as `CONTEXT:`. `COPY TO` of a table scans its
rows in key order and sends each as it is read; `COPY (query) TO` runs the query as any query
(D100's bound), then sends its rows.

**Streaming and limits.** The reader keeps one buffer: the unread part of the data and the next
pieces, compacted once more than 1 MiB has been read and at least half of it is behind; it scans
each byte once (text-format escapes and CSV quotes carry over piece boundaries) and hands out one
record at a time, so memory is one line plus one piece of input (one protocol message, at most
1 GiB, or 64 KiB from a file). A line is at most 1 GiB (`54000`), PostgreSQL's own field limit;
64 MiB was considered and refused because a `bytea` value of N bytes is 2N+2 bytes of hex in a
line, so it would refuse values of 32 MiB that `pg_dump` writes and the protocol carries
(research). Field values must be UTF-8 without NUL (`22021`). The writer escapes or quotes each
value as the manual describes, so what `COPY TO` writes reads back to the same values (a property
test of random values with tabs, newlines, backslashes, quotes, null look-alikes and non-ASCII
text checks both formats).

**The text format follows the manual literally.** Only a line that is exactly `\.` ends the data;
a `\.` inside a field reads as `.` ("any other backslashed character ... represents itself").
Refusing it was considered and rejected by research: the manual describes no other meaning, and
refusing would reject valid data. A CSV line of just `\.` (unquoted) also ends the data, and
`COPY TO` quotes a lone `\.` value. The first line's ending (`\n`, `\r\n` or `\r`) is the one the
rest must use (`22P04` with the manual's hints otherwise).

**No server files or programs.** `COPY ... FROM 'file'`, `TO 'file'` and `PROGRAM` are refused
with `42501` at parse time, as PostgreSQL refuses them to roles without the server-file
privileges: SQL never reads or writes the server's files or runs its programs (D11, D22). psql's
`\copy`, `eggdb shell`'s `\copy` and `eggdb import --csv` do it client-side, in the user's own
process with the user's own permissions. The binary format, `ON_ERROR ignore`, `COPY ... WHERE`
and encodings other than UTF-8 are `0A000` for now; `FREEZE` is accepted and changes nothing.

**`eggdb import --csv` needs an existing table** (research): it is `COPY <table> FROM STDIN
(FORMAT csv ...)` and nothing more, so a missing table is `42P01`; inferring a table of text
columns would lose types, keys and constraints, and `--create` already means "create the file".
`--table` may name columns (`people (name, id)`) and is refused when it holds a `;` or a comment
outside double quotes, so it cannot smuggle in a second statement.

**The page cache bounds one load.** Since one write transaction must fit in the page cache
(D86, D87), `eggdb import --csv` and `eggdb sql` on SQL that mentions `COPY` size the cache from
their input (four times its size plus 16 MiB, between 256 MiB and 1 GiB; `--cache` overrides).
The cache is reserved address space that becomes memory only as pages are used. `eggdb serve`
keeps its cache; large loads over the protocol need `--cache`, as the store's error says ("open
with a larger cache"), and docs/sql.md tells.

**Speed.** `eggdb-bench` gains `sql_copy.from_stdin` (100,000 rows, as a ratio to the same rows
as one `INSERT ... VALUES`) and `sql_copy.to_stdout` (as a ratio to `SELECT *` of them), gated
by D101; the macOS lines were measured with the new `--only <family>` option, which lets
`--update` add one family's lines without measuring the others again, and CI's bench job reports
the Linux numbers until their lines are added.
