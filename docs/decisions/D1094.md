## D1094 Prepared statements and transactions in the mobile bindings, gated against SQLite's own bindings — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D17, D222, D101)

- **Kotlin.** `EggDB.prepare(sql)` returns a `Statement` (`AutoCloseable`) over `eggdb_sql_prepare`. `execute(vararg parameters)` and `executeBatch(rows)` pack every parameter of every row into four parallel arrays (kind, `long`, `double`, `byte[]`), so a batch of any size crosses JNI once, as D17 requires; the C side binds, runs `eggdb_stmt_execute` per row and returns the last run's results in the existing flat form. Parameters are `null`, `Long`/`Int`/`Boolean`, `Double`/`Float`, `String` (as UTF-8 bytes, never modified UTF-8), `ByteArray` or a `Value`. `beginTransaction`, `commit`, `rollback` and `transaction { }` (roll back on any throw) are SQL statements on the same session. The flattening code is shared with `execute`.
- **Swift.** `Database.prepare` returns a `Statement` with `bind`, `execute` and `query` (stepping rows through `eggdb_stmt_step` and `eggdb_stmt_row`), finalised on `deinit` or `finalize()`; `?` is renumbered for the PostgreSQL dialect as `execute` already does. Swift calls C directly, so there is no crossing to batch.
- **The gate.** Each binding is measured against SQLite's binding in its language on the same device: Android's `android.database.sqlite` (`compileStatement`, one transaction) in the instrumented `BindingBenchmark`, and SQLite's C library from Swift (`import SQLite3`) in `testPreparedStatementsAgainstSQLitesLibrary`. Each times 5,000 inserts in one transaction and 2,000 lookups by primary key, after a warm-up round, prints the numbers, and fails above 2x, the blocking threshold of D101. Smaller regressions go to the weekly pass. The Android gate runs on both emulator ABIs of the `android` job, and the Swift gate on macOS and the iOS Simulator in `apple-mobile`.

**Status:** code written, unbuilt (code-only mode, D355).
