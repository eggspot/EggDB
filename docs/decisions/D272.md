## D272 SQL/JSON path runs on its own bounded evaluator over the parsed JSON tree, and `json_to_record` reads its column definition list as typed placeholders — Decided by the build loop (EggAgentCode task 20261102-0614, 2026-11-02); refines D130

D130 left SQL/JSON path, `json_to_record` and `date_trunc` of an interval for later.

- **Path language.** `crates/eggdb-sql/src/json_path.rs` parses a path (written from the SQL
  standard's SQL/JSON path language and PostgreSQL's documentation, no code read) into a tree and
  evaluates it over the document as `json::parse` reads it. `lax` and `strict` follow the
  standard: lax unwraps arrays for member accessors and drops structural errors, strict reports
  them with the SQL/JSON states (`2203A`, `22039`, `22033`, `22036`, `22038`). The `silent`
  argument and the `@?`/`@@` operators suppress the suppressible ones, as PostgreSQL does.
- **Hostile input.** A path of more than 1,000 nodes fails with `54001`, an evaluation that would
  produce more than 1,000,000 items with `54000`, and `like_regex` uses the engine's own regular
  expressions with a step budget (D128), so no path or document can crash the server or hang it.
- **`jsonpath` is not a type of its own yet.** The type name resolves to text and the path is
  parsed when it is used, so a bad path fails at its first use rather than at the cast. A real
  type (its OID in `pg_type`, binary I/O) is left for when a client needs it.
- **`@@` on `jsonb`.** The text search operator and the path match operator share `@@`; the
  evaluator picks the path match when the left operand is `jsonb`, which is how PostgreSQL's
  operator resolution chooses between `tsvector @@ tsquery` and `jsonb @@ jsonpath`.
- **Column definition lists.** `json(b)_to_record(set)` need the caller's columns. The parser
  appends one `CAST(NULL AS type)` per declared column to the call's arguments and keeps the
  names as the alias's column names, so the existing table-function machinery types and binds
  them without a new syntax tree field. Each column is the member of that name read through the
  type's text input, as PostgreSQL does; an object or array stays JSON text in a text column.
  A JSON array fills an array column element by element, and a JSON object a composite column
  attribute by attribute, as PostgreSQL's `populate_record` machinery does. Arrays have one
  dimension (D128), so a nested JSON array fails with `0A000`, and one that mixes nested arrays
  and scalars with `22P02`.
- **Not yet.** `json(b)_populate_record(set)` (they take a row type, `null::t`), the
  `datetime()` family of path methods, `JSON_TABLE`, `JSON_VALUE`, `JSON_QUERY` and
  `JSON_EXISTS`.
