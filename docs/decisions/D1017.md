## D1017 GraphBinary for Gremlin, and bytecode results as traversers — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D48, D1011)

- The Gremlin server reads and writes GraphBinary 1.0 (`application/vnd.graphbinary-v1.0`), written from the
  TinkerPop IO reference: a request's version byte, UUID, operation, processor and arguments map, and fully
  qualified values (type code, value flag, value) for the types requests carry: integers, longs, doubles, floats,
  shorts, bytes, booleans, chars, strings, UUIDs, dates, lists, sets, maps, vertices, edges, bytecode, `P` and
  `TextP` predicates, bindings and the enums (`T`, `Order`, `Direction`, `Cardinality`, `Column`, `Pop`, `Scope`,
  `Operator`, `Barrier`, `Pick`). GraphBinary is the default serializer of gremlin-python 3.5 and later, of
  gremlin-javascript and of Gremlin.Net, so those drivers now work without choosing GraphSON.
- A GraphBinary request is read into the same JSON shape a GraphSON request has, and the reply GraphSON shape is
  written out in GraphBinary, so both serializers share one request path, one compiler and one set of results; a
  reply goes back in the serializer its request came in.
- Results of `op: bytecode` are now traversers (`g:Traverser` with a bulk of 1, and GraphBinary's traverser type),
  as Gremlin Server sends them and as remote traversals in the drivers expect; scripts (`op: eval`) still return
  plain values. D1011's bytecode replies sent plain values, which gremlin-python's remote traversals cannot read.

**Status:** code written, unbuilt (code-only mode, D355).
