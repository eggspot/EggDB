## D228 Offline-first sync is a per-replica change log with last-writer-wins on hybrid-clock stamps — Decided by the build loop (by judgement, 2026-10-31); refines D41

Part 4.M18-4 asks for an embedded database that syncs with a server and resolves conflicts,
checked by simulating disconnected edits.

- **Each replica owns its state and its log**, both in EggDB's key-value transactions (the
  shared `Keyspace` interface, so an embedded file or a server's collection holds them): one row
  per key with its value or tombstone and its stamp, an append-only log of every row change, and
  the replica's clock. Writes work offline and survive restarts; the clock never goes back when
  the wall clock does, so a later write on the same device always wins over an earlier one.
- **Sync is two cursors.** A client sends the changes logged after the server's cursor and takes
  in the server's changes after its own. Each side keeps the incoming change only when its stamp
  is newer than the row's, in one transaction per batch, and logs it so it travels on. Batches
  are bounded, a dropped connection only repeats work, and changes travel in a small binary
  format that any transport can carry and that is checked when decoded.
- **Conflicts resolve by last writer wins**, the highest hybrid-clock stamp per key with the
  replica id breaking ties, deletions included, because it converges with no coordination and
  no merge code. Applications that need merges (counters, sets, text) get them from CRDT
  types or the sibling policy of D225 in a later slice.
- **Checked by simulation**: thirty seeds of four clients writing, deleting and syncing in random
  batches. Once everything is exchanged, the server and every client hold exactly the newest
  write of every key.

Left: the HTTP transport and authentication (`eggdb serve` taking sync requests per user), sync
of SQL tables through change capture (D210) instead of key-value rows, log compaction once every
peer has a change, partial sync (only some keys per device), per-field merges and CRDTs, and
end-to-end encryption of synced data.
