## D302 PostgreSQL 17's SQL/JSON constructors and `IS JSON` as internal functions, jsonpath `.decimal()`, a base row for `json_populate_record`, `scale()`, `min_scale()` and `trim_scale()`, and the citext extension's case-insensitive string functions — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 20, 21 and 22, finishes parts of D288's, D289's and D290's "Not yet"

D289 left the SQL/JSON constructors, the `IS JSON` predicate, the `.decimal()` path method and a
non-NULL base row of `json_populate_record` for later; D290 left `scale()`, `min_scale()` and
`trim_scale()`; D288 left the `citext` versions of the string and regular expression functions.
Each follows PostgreSQL 17's documentation and, for citext, the extension's documented functions.

- **Constructors and the predicate are internal functions.** In PostgreSQL's dialect the parser
  turns `expr IS [NOT] JSON [VALUE | SCALAR | ARRAY | OBJECT] [{WITH | WITHOUT} UNIQUE [KEYS]]`
  into `*is_json*(expr, shape, unique, negated)`, `JSON(expr [FORMAT JSON] [... UNIQUE [KEYS]])`
  into `*json*(expr, unique)`, `JSON_SCALAR(expr)` into `*json_scalar*(expr)` and
  `JSON_SERIALIZE(expr [FORMAT JSON] [RETURNING type [FORMAT JSON]])` into
  `*json_serialize*(expr, NULL::type)`, the clauses being integer codes and a typed NULL, as
  D289's query functions are. No AST node is added, so no exhaustive match changes, and a stored
  `CHECK (doc IS JSON)` is kept as its text and parsed again. A hand-written internal call with
  codes out of range is a syntax error, never a panic. `WITH UNIQUE` only checks after `WITH`
  is followed by `UNIQUE`, so `WITH CHECK OPTION` after a view's `IS JSON` still parses.
- **What each accepts.** `IS JSON` reads `text`, `bytea` (UTF-8; invalid bytes are not JSON),
  `json`, `jsonb` and `citext` values; other types are `42804` (`cannot use type ... in IS JSON
  predicate`). Text that is not JSON is false, NULL is NULL, and a `jsonb` value is always
  unique-keyed since its text is normalized. Duplicate keys are found by sorting each object's
  keys, at every depth the JSON parser allows (256 levels), so a hostile document costs
  `n log n`. `JSON()` keeps the text as written (`22P02` when it is not JSON, `22030`
  `duplicate JSON object key value` under `WITH UNIQUE KEYS`, `42804` for a non-string
  argument). `JSON_SCALAR` gives exactly what `to_json` gives, as PostgreSQL's executor does.
  `JSON_SERIALIZE` returns `text` by default or the `RETURNING` type when it is a character type
  or `bytea` (other types are `42804` when parsed); a `jsonb` argument gives its normalized text.
  The new state `22030` is `SqlState::DUPLICATE_JSON_OBJECT_KEY_VALUE`.
- **`.decimal([precision [, scale]])`.** A new `Method::Decimal(Option<DecimalModifier>)` takes
  signed integer arguments when the path is parsed (a value outside `integer` is `22023`, a
  non-integer `42601`); without arguments it is `.number()`. With them the value is checked
  like a `numeric(p, s)` type modifier (`22023` outside 1 to 1000, a hard error as in
  PostgreSQL) and rounded with `Numeric::with_modifier`; a value that does not fit is `2203G`
  (`argument "..." of jsonpath item method .decimal() is invalid for type numeric`), suppressed
  like `.number()`'s errors.
- **A base row for `json(b)_populate_record(set)`.** When the first argument is a non-NULL value
  of a composite type, its fields are the defaults: a column whose key the object lacks keeps the
  base row's value, and a NULL document returns the base row (one row for the `_record` forms).
  A base value that is not a row of the declared type is `42804`. Tables still have no composite
  type of their own (D288), so a table's row type takes only `NULL::t`.
- **`scale`, `min_scale`, `trim_scale`.** `Numeric::minimum_scale` counts the trailing zero
  digits of the magnitude past the point and `trimmed_scale` truncates to that scale, which is
  exact. Of `NaN` and the infinities the first two give NULL and `trim_scale` the value itself,
  as PostgreSQL 14 does; integer arguments are read as `numeric`.
- **citext's functions.** As the citext extension defines them, `regexp_match`, `regexp_matches`,
  `regexp_replace`, `regexp_split_to_array`, `regexp_split_to_table` add the `i` flag when their
  first argument is `citext` and the flags hold no `c`; `replace` is `regexp_replace` of the
  escaped search text with `gi`, `split_part` the field of `regexp_split_to_array` of the escaped
  delimiter with `i` (NULL for a field that does not exist, as the extension's array subscript
  gives), `strpos` compares `lower()` of both, and `translate` translates `lower()` and then
  `upper()` of the characters. Escaping puts a backslash before every character outside
  `[A-Za-z0-9_]`, as the extension does. Only the first argument being `citext` selects these
  versions, the rule D288 chose for `~`: a `citext` argument elsewhere is read as `text`, which
  differs from PostgreSQL only for an explicitly `text`-typed pattern beside a `citext` value
  (PostgreSQL resolves that to the `text` function). The `regexp_*` forms with a start position
  or occurrence, and `regexp_like`, `regexp_count`, `regexp_instr` and `regexp_substr`, have no
  citext version in the extension, so they take `citext` as `text` and keep case.

Not yet: `json_populate_record` in a select list and with a column alias list; a table's own
row type as a non-NULL base row; Oracle's `IS JSON` (lax syntax, `STRICT`, `TYPE (...)`), its
`JSON_SERIALIZE` options (`PRETTY`, `ASCII`, `TRUNCATE`) and `JSON_SCALAR` in Oracle's dialect;
`IS JSON` on a `json` value holding `\u0000`, which the JSON parser refuses.
