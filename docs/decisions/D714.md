## D714 Text extracted from PDF files — Decided by the code-only session (2026-11-12, D355); roadmap M8, text from PDF files (D56, D249)

- `eggdb-content`'s `extract_text` (and so SQL's `extract_text(bytea)`) now reads PDF files, recognised by their
  `%PDF-` header, through a reader of our own in `pdf.rs` written from the PDF specification (ISO 32000).
- Objects are found by scanning for `n g obj`, so files with damaged or missing cross-reference tables still read;
  objects inside object streams (`/Type /ObjStm`, PDF 1.5) are read too. Stream lengths given directly are used, and
  an indirect or wrong `/Length` falls back to `endstream`. Pages come in the order of the page tree from the
  catalog (inheriting `/Resources` from parent nodes), or in object order when there is no catalog.
- Content streams are decoded with `FlateDecode` (through the existing zlib inflate) and `ASCIIHexDecode`; text comes
  from `Tj`, `TJ` (a gap wider than 200 thousandths of an em becomes a space), `'` and `"`, with new lines at `T*`,
  at `Td`/`TD` moving down, and at `ET`. Inline images are skipped.
- Each font's `/ToUnicode` CMap (code space, `bfchar`, `bfrange` with a start or an array of targets, UTF-16 targets)
  maps its codes to text; other fonts' bytes are read as Latin-1.
- Bounded like the other extractors: every decoded stream and the text in all stay under the caller's limit, objects
  nest at most 64 deep and a file gives at most 100,000 pages.
- Left: encrypted PDFs, `LZWDecode` and `ASCII85Decode` content, encodings named by `/Encoding` differences without
  a `ToUnicode` map, text order by position on the page, PST files and OCR.

**Status:** code written, unbuilt (code-only mode, D355).
