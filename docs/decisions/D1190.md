## D1190 Grants on schemas, types, parameters and tablespaces stored — Decided by the code-only session (2026-11-17, D355); roadmap M6b (D326, D344)

- **What users get.** `GRANT USAGE, CREATE ON SCHEMA`, `GRANT USAGE ON TYPE` (and `DOMAIN`), `GRANT SET, ALTER SYSTEM ON PARAMETER` and `GRANT CREATE ON TABLESPACE`, with `WITH GRANT OPTION`, `REVOKE` and `REVOKE GRANT OPTION FOR`, are stored instead of being accepted with a warning and dropped. `has_schema_privilege`, `has_type_privilege` (by name), `has_parameter_privilege` and `has_tablespace_privilege` answer from them, `WITH GRANT OPTION` included, and `pg_namespace.nspacl` lists them after the owner's and `PUBLIC`'s entries (`joe=C*/eggdb`), so pgAdmin, DBeaver and `\dn+` show what was granted.
- **Storage.** One key space (`OBJECT_GRANT_SPACE` 0x1D): the object's kind byte, its name, a zero byte and the grantee, holding the privileges and the grantable ones. A privilege the object does not take (`SET` on a schema) is `0LP01`, a missing schema `3F000`, a missing role as for table grants. Dropping a schema forgets its grants. The access snapshot loads the space, so the catalog answers with the same records.
- **Scope.** The PostgreSQL and Oracle dialects parse these grants; SQL Server's `ON SCHEMA::` and MySQL's database grants keep their present handling. Statements do not yet check these privileges (only superusers define objects until owners land, D827), the defaults still hold (every role uses every schema and type), and a `REVOKE` of a default (`REVOKE USAGE ON SCHEMA public FROM PUBLIC`) changes nothing yet. Types are matched by the name written in the grant, so asking by OID finds only the defaults.
- **Proof.** A unit test grants on each kind, reads `nspacl`, asks the four inquiry functions as other roles (through a role's membership too), revokes, and checks the two errors.
- Left of the roadmap item: `information_schema.role_routine_grants` and `role_udt_grants`, and routine and sequence privileges with object owners.
