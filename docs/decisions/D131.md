## D131 Java and Python apps on PostgreSQL's protocol: `information_schema` built per statement from the catalog snapshot, its domains as their base types, and the SQL pgjdbc's and SQLAlchemy's metadata queries need (aggregate `ORDER BY`, lock-step set-returning functions, ranking window functions) — Decided by the build loop (by research, 2026-10-29); roadmap item 38, applies D10, D12, D103, D104, D116, D128, D129

Item 38 makes pgjdbc, psycopg 3 and SQLAlchemy Core apps run unchanged against `eggdb serve`.
Their CRUD runs on what was there; what they lacked was `information_schema`, a few catalog
relations and functions, and SQL forms their metadata queries use.

**`information_schema` is a set of catalog relations, not stored views.** `schemata`, `tables`,
`columns`, `views`, `sequences`, `table_constraints`, `key_column_usage`,
`referential_constraints`, `constraint_column_usage`, `check_constraints`, `routines` and
`parameters` are built in Rust from D129's catalog snapshot, once per statement and only when the
statement names them, exactly like `pg_class` (`crates/eggdb-sql/src/information_schema.rs`, a
variant of `CatalogRelation`). PostgreSQL defines them as SQL views over `pg_catalog`; running
those view texts would need SQL EggDB does not have yet (composite types, `pg_has_role`, ...) and
would cost far more per query. The module is outside `pg_catalog/` because SQL Server's
`INFORMATION_SCHEMA` (item 41) answers from the same facts with its own names and types. The
relations are in the reserved schema `information_schema` (OID 13000, relation OIDs from 13100),
listed in `pg_class` as views and in `pg_attribute`; an unqualified name reaches them only when
`information_schema` is on `search_path`, after any user table of that name on an earlier schema,
as in PostgreSQL. Writes are `42501`.

**Rows follow PostgreSQL 17's view definitions.** Every relation has PostgreSQL 17's columns in
order. `tables`, `columns` and `views` list user relations and the catalog's own (`pg_catalog`
relations as `BASE TABLE`, `pg_roles`, `pg_settings` and `information_schema` as `VIEW`), because
PostgreSQL lists every relation the user may use and EggDB's session user may use them all.
`columns` describes types as PostgreSQL's helper functions do: `data_type` is `format_type` of the
type without modifier (`ARRAY` for arrays), the lengths, precisions and scales come from the type
modifier (`character_octet_length` with UTF-8's four bytes a character, 2^30 without a limit),
`udt_*` name the `pg_catalog` type, `column_default` is the text `pg_get_expr` shows, identity
columns show `BY DEFAULT` from 1. NOT NULL columns appear as `CHECK` constraints named
`<namespace oid>_<relation oid>_<column number>_not_null` with the clause `<column> IS NOT NULL`
in `table_constraints` and `check_constraints`, as PostgreSQL 17 does (18 changes this).
`constraint_column_usage` takes a check constraint's columns from the names its stored text
uses, since EggDB keeps no dependency rows. `routines` and `parameters` are empty until EggDB has
stored functions.

**Domains as their base types.** PostgreSQL types these columns with the domains `sql_identifier`
(over `name`), `cardinal_number` (over `integer`), `character_data` (over `varchar`), `yes_or_no`
(over `varchar(3)`) and `time_stamp` (over `timestamp(2) with time zone`), whose OIDs initdb
assigns and which therefore differ between servers. EggDB types the columns with the base types
(`name`, `integer`, `character varying`, `character varying(3)`, `timestamptz(2)`). Values,
comparisons and text output are the same; a client that prints the type name of such a column sees
the base type, a known difference in sql.md, until user-defined types (3.08) let the domains
exist.

**Catalog additions for drivers.** `pg_settings` (a view: one row per session setting, from the
statement's own settings, with `max_index_keys` 32 and `max_function_args` 100 added as fixed
settings; `context` `internal` for fixed ones and `user` for the rest), `pg_opclass` and `pg_enum`
(empty until index methods and enum types arrive), `pg_get_serial_sequence`, `to_regclass`,
`to_regtype`, `generate_subscripts`, and `regproc` input and output for the built-in functions
EggDB names (`array_in`, OID 750, the input function `pg_type` shows for array types, which
pgjdbc tests). `SET SESSION CHARACTERISTICS AS TRANSACTION ...` and `SET TRANSACTION ...` accept
every isolation level (all run serializable, as sql.md says) and set
`default_transaction_read_only`; `SET TRANSACTION READ ONLY` and `SET TRANSACTION SNAPSHOT` stay
`0A000`.

**SQL the metadata queries use.** Three forms are added generally, not for these clients only:

- `ORDER BY` inside an aggregate call (`array_agg(x ORDER BY y)`, `string_agg`, the JSON
  aggregates), and the aggregates `array_agg`, `bool_and`, `bool_or` and `every`. The order keys
  ride inside the aggregate's argument as an internal function, so the stored and planned forms of
  an aggregate do not change; an ordered call buffers its inputs (charged to work memory) and
  feeds them sorted into the plain accumulator when the group ends.
- Several set-returning functions in one select list run in lock-step, as PostgreSQL 10 and later
  do: each input row gives as many rows as the longest function, the shorter ones padded with
  NULL. D128's select-list expansion now carries a list of items (column runs, set-returning
  calls, window calls) instead of one call.
- `row_number()`, `rank()` and `dense_rank()` with `OVER (PARTITION BY ... ORDER BY ...)` as
  select-list items, computed by the same expansion over the rows of the inner query: the rows
  are sorted by partition and order keys and numbered, and their order is otherwise unchanged.
  Window frames, named windows, other window functions and window calls inside expressions are
  `0A000` and left to item 3.07, which extends this expansion.

**What waits.** pgjdbc's `getPrimaryKeys` (and `getIndexInfo`) call
`information_schema._pg_expandarray`, which returns a composite value and is read with field
selection (`(f(x)).n`, `(t.keys).x`). Composite values come with user-defined types (3.08), which
adds `_pg_expandarray`; until then that call answers `0A000` and the CI comparison shows it.

**The check.** CI's `pg-apps` job restores the item 37 catalog fixture into EggDB from a
PostgreSQL 17 `pg_dump`, runs the same pgjdbc program (CRUD with prepared statements past the
driver's server-prepare threshold, a rollback and a commit, `getSchemas`, `getTables`,
`getColumns`, `getPrimaryKeys`, `getImportedKeys`) and the same psycopg 3 and SQLAlchemy Core
program (CRUD, `MetaData.reflect()` of both schemas, the inspector, a Core query) against both
servers, and fails unless each program prints the same bytes on both. The drivers are downloaded
by CI as test tools (D1) and never shipped.
