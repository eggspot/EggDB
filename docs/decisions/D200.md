## D200 Scheduled jobs as pg_cron's schema, run by the server once a minute — Decided by the build loop (by judgement, 2026-10-31); refines D27

Part 4.M10-3 asks for scheduled SQL in each dialect's form (pg_cron, SQL Server Agent, MySQL
events, Oracle `DBMS_SCHEDULER`), checked with a simulated clock.

- **pg_cron first, as ordinary objects.** `CREATE EXTENSION pg_cron` runs a script
  (`eggdb_sql::jobs`) that creates the `cron` schema, its two tables and its functions in
  PL/pgSQL, with the column names pg_cron documents, so tools that read `cron.job` work and
  jobs live in the file, are backed up with it and are covered by the transactions they are
  changed in. No hidden catalog is added.
- **The engine decides what is due; the server keeps the clock.** `eggdb_sql::jobs::run_due_jobs
  (store, epoch_seconds)` runs the jobs whose schedule fires in that minute, each in its own
  session and transaction, and records each run. `eggdb serve` calls it when the UTC minute
  changes; tests call it with any time, which is the simulated clock. An embedded file runs no
  jobs on its own: the application (or `eggdb serve`) drives the clock.
- **Cron as written in the man page and pg_cron's documentation**: five fields, lists, ranges,
  steps, names, the `@` shorthands, and either day field matching when both are restricted.
- **Each job runs as the server** in this release, as the server has one user (D183's roles
  apply once jobs record and assume their `username`).

Left: SQL Server Agent jobs (`msdb.dbo.sp_add_job` and its schedule procedures), MySQL `CREATE
EVENT`, Oracle `DBMS_SCHEDULER.CREATE_JOB`, which can store into the same tables; sub-minute
schedules, `$`, `cron.alter_job`, per-job time zones, validating at `cron.schedule`, running a
missed minute after a restart, and running jobs as their `username`.
