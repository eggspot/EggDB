## D420 `SHOW CREATE PROCEDURE|FUNCTION`, `SHOW PROCEDURE|FUNCTION STATUS` and MySQL's `ROUTINES` and `PARAMETERS` views — Decided by the code-only session (2026-11-11, D355); roadmap M10

- `SHOW CREATE PROCEDURE p` and `SHOW CREATE FUNCTION f` return MySQL's six columns (`Procedure`
  or `Function`, `sql_mode`, `Create Procedure` or `Create Function`, the client character set
  and the two collations), with the routine's stored `CREATE` text; an unknown name is error
  1305, "PROCEDURE p does not exist".
- `SHOW PROCEDURE STATUS` and `SHOW FUNCTION STATUS [LIKE ...]` list MySQL's eleven columns,
  sorted by database and name. EggDB keeps no creation or change times for routines and no
  definer, so `Modified` and `Created` are `NULL` and `Definer` is `root@localhost`.
- MySQL's `information_schema.ROUTINES` and `PARAMETERS` were empty; they now list the MySQL
  dialect's routines: `ROUTINES` gains `DTD_IDENTIFIER`, `ROUTINE_BODY`, `EXTERNAL_LANGUAGE`,
  `PARAMETER_STYLE`, `IS_DETERMINISTIC`, `SQL_DATA_ACCESS` (always `CONTAINS SQL`: the
  characteristic isn't stored), `SECURITY_TYPE`, `SQL_MODE` and the character set columns, and
  `PARAMETERS` gives a function's result as ordinal 0 and each parameter with its mode (`NULL`
  for a function's, as MySQL does). Types use MySQL's names (`int`, `varchar`, `datetime`).
- Routines of other dialects stay out of the MySQL views (they belong to the PostgreSQL ones).
  `information_schema.TRIGGERS` in MySQL's view stays empty, and trigger bodies keep their own
  smaller interpreter (`BEGIN`, `DECLARE`, `SET`, `IF`, `WHILE`, `SIGNAL`): left.
