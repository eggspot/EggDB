## D202 Parquet files read and written by our own eggdb-parquet; eggdb import and export --parquet — Decided by the build loop (by judgement, 2026-10-31); refines D29

Part 4.M11-3 asks to import and export Parquet and Arrow, query external Parquet files, and
read and write Iceberg tables.

- **Our own crate from the public specifications**: the Apache Parquet format specification and
  Apache Thrift's compact protocol for its metadata, Snappy from Google's public format
  description. No third-party crate (D1). It reads flat files with any number of row groups:
  plain and dictionary-encoded pages, data pages versions 1 and 2, uncompressed and Snappy,
  every physical type including legacy `INT96` timestamps, and the logical types for text,
  dates, timestamps (milli-, micro- and nanoseconds) and decimals. It writes one row group with
  one plain, uncompressed page per column, which every Parquet reader accepts.
- **Files reach tables through the CLI first.** `eggdb import --parquet` creates the table from
  the file's columns when it does not exist and loads the rows through `COPY`, in one
  transaction; `eggdb export --table --parquet` writes a table's rows. Reading files from SQL
  (`read_parquet(...)`) waits for a decision on which files a server's SQL may open, since
  letting any client read server-side paths is a security hole.
- **Bounded memory and hostile input.** A file is read whole, up to 4 GiB and 2^28 values; every
  length, offset, level and dictionary index is checked, and damaged files are errors.

Left: nested columns (lists, maps, structs), GZIP and ZSTD (they need our own inflate and zstd
decoders), statistics and dictionary encoding when writing, several row groups when writing,
streaming large files, `read_parquet` in SQL, Arrow IPC files and streams, Iceberg tables with
a REST catalog, and a benchmark against DuckDB's Parquet reader.
