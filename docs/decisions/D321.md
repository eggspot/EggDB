## D321 Statistical aggregates in every dialect's spelling (`stddev`, `variance`, `_samp`, `_pop`, MySQL's `STD`, Transact-SQL's `STDEV`, `STDEVP`, `VAR`, `VARP`), hypothetical-set aggregates (`rank`, `dense_rank`, `percent_rank`, `cume_dist` `WITHIN GROUP`), MySQL's NULL ordering and PostgreSQL's `2201W` for a NULL `WITH TIES` count — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M5, applies D9, D10 and D19, extends D151 and D300

`stddev` and `variance` answered `0A000`, `rank(x) WITHIN GROUP (...)` was refused as "not an
aggregate function", MySQL's dialect sorted NULLs last for `ASC` (PostgreSQL's order, the
opposite of MySQL's), and `FETCH FIRST NULL ROWS WITH TIES` returned every row where PostgreSQL
refuses it. PostgreSQL's "Aggregate Functions for Statistics" and "Hypothetical-Set Aggregate
Functions" tables and `SELECT`'s "LIMIT Clause", MySQL's "Aggregate Function Descriptions" and
"Working with NULL Values", Oracle's `STDDEV`, `STDDEV_SAMP`, `STDDEV_POP`, `VARIANCE`,
`VAR_SAMP`, `VAR_POP`, `RANK` and `DENSE_RANK` references, and Microsoft's `STDEV`, `STDEVP`,
`VAR` and `VARP` pages say how they behave; EggDB now follows them.

- **One accumulator, each dialect's names.** The parser maps each dialect's names onto six
  aggregates of one engine (`stddev_samp`, `stddev_pop`, `var_samp`, `var_pop`, plus
  PostgreSQL's `stddev` and `variance`, which compute the sample forms under their own column
  names) and two Oracle ones: Oracle's `STDDEV` and `VARIANCE` are the sample forms but 0 for
  one row, where `STDDEV_SAMP` and `VAR_SAMP` are NULL. MySQL's `STD`, `STDDEV` and `VARIANCE`
  are the population forms and its `_SAMP` forms the sample ones; Transact-SQL's `STDEV` and
  `VAR` are the sample forms and `STDEVP` and `VARP` the population ones. SQLite has none, so
  its dialect keeps `no such function`. Every form skips NULLs, is NULL over no rows, takes
  `DISTINCT` and `FILTER`, and runs as a window function through the same accumulator.
- **Exact for exact input, stable for floats.** `statistical_aggregates::Moments` keeps the
  count, the sum and the sum of squares exactly: in `i128` for integers, switching to `numeric`
  when a sum would overflow, and in `numeric` for `numeric` input. The variance is `(n·Σx² −
  (Σx)²) / (n·(n−1))` (or `n·n` for the population), divided at PostgreSQL's division scale,
  so `variance` of 1, 2, 3 and 4 is `1.6666666666666667` as in PostgreSQL; a numerator of 0 or
  less is `0`; the standard deviation is the variance's square root at the same scale
  (`Numeric::square_root`, Newton's method from a floating-point estimate, rounded). Float input
  uses Welford's running mean and sum of squared deviations, so values far from 0 lose no
  precision to cancellation; an overflow from finite inputs is `22003`, and an infinity gives
  NaN. In PostgreSQL and Oracle the result is `numeric` for integer and `numeric` arguments and
  `double precision` for floats; MySQL's and Transact-SQL's dialects cast the argument to
  `double precision`, so their results are `DOUBLE` and `float` as there. A non-numeric
  argument is `42883`.
- **Hypothetical-set aggregates.** In PostgreSQL's and Oracle's dialects, a call to `rank`,
  `dense_rank`, `percent_rank` or `cume_dist` whose parentheses are followed by `WITHIN GROUP`
  is an aggregate whose argument holds the sort directions, the hypothetical values and the
  `ORDER BY` expressions (`hypothetical_set::arguments`). For each row of the group,
  `hypothetical_set::Standing` compares the row's keys with the hypothetical row in those
  directions, with each column's `NULLS FIRST` or `LAST`, and counts the rows before it and
  equal to it (and, for `dense_rank`, the distinct keys before it, charged to the statement's
  work memory). `rank` is the rows before plus 1, `dense_rank` the distinct keys before plus 1,
  `percent_rank` the rows before divided by the rows (0 over none) and `cume_dist` (rows before
  or equal + 1) / (rows + 1). A hypothetical value is read with the key's type as its hint, so
  `rank('2024-01-01') WITHIN GROUP (ORDER BY day)` compares dates. A different number of
  arguments and `ORDER BY` expressions is `42883` (ORA-00909 in Oracle); `OVER` is `0A000`.
  `rank()` without `WITHIN GROUP` stays the window function.
- **MySQL's NULL ordering.** In MySQL's dialect an `ORDER BY` item without `NULLS FIRST` or
  `LAST` gets NULLs first for `ASC` and last for `DESC` when it is parsed, so queries, set
  operations and window definitions all sort that way. Indexes keep their entries ascending
  with NULLs last (D146), so the planner's rule that an index replaces a sort only when the
  NULL order matches, or the column is `NOT NULL`, now keeps a nullable column's index from
  being read in MySQL's dialect; primary keys still are.
- **`2201W` for a NULL `WITH TIES` count.** PostgreSQL's `FETCH FIRST n ROWS WITH TIES` is its
  own internal call, so a count that is NULL is `2201W row count in FETCH FIRST ... WITH TIES
  clause must not be null`, while `FETCH FIRST NULL ROWS ONLY` still returns every row, and
  Oracle's and Transact-SQL's `WITH TIES` keep their own rules.

Decided by research: PostgreSQL's numeric variance of identical values is `0` (scale 0), the
documented "watch out for a negative numerator" case, and EggDB answers the same for a single
row's population variance; Oracle's results are computed at PostgreSQL's division scale rather
than Oracle's 38 significant digits, as Oracle's `AVG` already is; the hypothetical values are
read for every row (they are constants or grouped columns), not once per group; MySQL's NULL
ordering is fixed in the parser, not the sort, so every consumer of an `ORDER BY` item, the
index planner included, sees one answer.
