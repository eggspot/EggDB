## D393 PostgreSQL's `lock_timeout` on the wait for the writer — Decided by the code-only session (2026-11-10, D355); roadmap M6c

EggDB has one writer per database: a statement that needs it while another transaction holds it
waits up to the database's write timeout (five seconds by default) and then fails with `55P03`.
PostgreSQL's `lock_timeout` sets how long a statement may wait for a lock; the writer is the lock
EggDB statements wait for, so it now applies there.

- `KeyValueStore::begin_write_waiting(limit)` begins the write transaction waiting at most `limit`
  (EggDB's store: `Database::begin_write_within`; the default waits as `begin_write` does).
- When the statement's `lock_timeout` (PostgreSQL's units: a number of milliseconds or `ms`, `s`,
  `min`, `h`) is above zero, the session's store wrapper uses it and a timeout is `55P03 canceling
  statement due to lock timeout`, PostgreSQL's message. Zero keeps the database's write timeout.
- Row locks, advisory locks and `LOCK TABLE` waits do not consult it yet.
