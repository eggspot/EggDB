## D128 The SQL that psql's `\d` family needs: our own linear-time regular expressions, arrays as values of expressions only, and set-returning functions and `VALUES` lists as intermediate tables of the statement — Decided by the build loop (by plan review and by research, 2026-10-29); roadmap item 37 part a (37a), applies D1, D9, D10, D19, D100, D104, D105, D112, D119

Item 37 lets psql browse a database. psql's describe queries use SQL that EggDB did not run:
regular expressions on names, `OPERATOR(pg_catalog.~)`, `COLLATE pg_catalog.default`, arrays
and their subscripts, `generate_series` and `unnest` in `FROM` (with `WITH ORDINALITY` and
outer references), `ARRAY(subquery)`, `VALUES`, `string_agg` and `quote_ident`. Part a (37a)
adds that SQL to the PostgreSQL dialect; part b adds the catalog. Other dialects are unchanged.

**Regular expressions are our own, linear in time.** `~`, `~*`, `!~` and `!~*` run PostgreSQL's
advanced syntax (the ARE core: literals, `.`, bracket expressions with ranges and classes,
`\d \w \s` and their negations, character escapes, anchors, groups, alternation and greedy and
lazy quantifiers with bounds up to 255) compiled to a program of at most 100,000 instructions and
matched by a thread-list automaton (each instruction at most once per position, no
backtracking), so a pattern such as `(a*)*b` against 100,000 `a`s ends in linear time. A
malformed pattern is `2201B` with PostgreSQL's reason; back references, lookahead and lookbehind,
the constraint escapes `\m \M \y \Y \A \Z`, embedded options and `***=` are `0A000` (they are
not regular and would need backtracking; a roadmap line). Limits, so hostile input cannot hang
or crash the server (D9): a pattern of at most 64 KiB, groups nested at most 256 deep (the parser
recurses), the program's size computed before it is built, and a budget of 10^9 automaton steps
per statement (`54000` "regular expression is too complex for this statement"). A statement
compiles each pattern once (a cache of up to 256 patterns per statement). Classes and `~*`'s case
folding follow the `C` locale, as EggDB's text comparison does: only ASCII letters fold and only
ASCII characters are in `[[:alpha:]]` or `\w`, which is what PostgreSQL does in a `C` database
(observed). A `character(n)` value keeps its trailing spaces when matched, as PostgreSQL's
`bpchar` regular expression operator does (observed; the plan had said they are stripped).

**`OPERATOR(...)`, `COLLATE` and qualified types.** `OPERATOR(op)` and `OPERATOR(pg_catalog.op)`
take every binary operator the dialect knows, with PostgreSQL's precedence for "any other
operator" (the regular expression operators have it too: `'a' || 'b' ~ 'ab'` is true).
`COLLATE` accepts `default`, `"C"`, `"POSIX"` and `ucs_basic`, optionally `pg_catalog.`, and
changes nothing, since EggDB compares text bytewise as `C` does; other names are `42704` and a
non-text operand `42804`. `pg_catalog.type` names a type wherever a cast takes one.

**Arrays are values of expressions and intermediate results, not of tables.** `SqlType::Array`
holds a `Copy` element kind (`smallint`, `integer`, `bigint`, `real`, `double precision`,
`numeric`, `boolean`, `text`, `varchar`, `bpchar`; part b adds the catalog's kinds) so `SqlType`
stays `Copy`; `Value::Array` boxes the element kind, the lower bound and the elements. Arrays have
one dimension; multidimensional arrays, slices and bounds in literals (`[1:2]=`) are `0A000`.
`ARRAY[...]`, `ARRAY(subquery)`, PostgreSQL's array literal syntax, element-wise casts,
subscripts (NULL out of bounds), `||` (of the element types' common type by D112's `UNION`
rules, with a typed NULL array counting as empty), element-wise comparisons and `x op ANY|ALL
(array)` over any array expression work as in PostgreSQL; `ANY`'s operand is parsed once, as an
expression, and when it is a plain `ARRAY[...]` (under any `::T[]` casts) it is rewritten to an
`IN` list, which stays the fast path (and keeps restored `CHECK`s such as `(level)::text = ANY
((ARRAY['debug'::character varying])::text[])` working). The parser never reads the same text
twice, so nested input cannot make it slow. An array column in `CREATE TABLE`, `ALTER TABLE` or a view
is `0A000`: storing arrays needs a file-format change (D20) and is left for a later item. Rows of
intermediate tables carry an array as its lower bound and its text form, which reads back
exactly; no table definition with an array column is ever written. Building an array checks the
session's value limit (D119) element by element and at most 2^27 elements (`54000`). Over the
PostgreSQL protocol arrays have PostgreSQL's array type OIDs and its text and binary forms;
array parameters are `0A000`.

**Set-returning functions and `VALUES` lists are intermediate tables (D112).** A function in
`FROM` (`generate_series` over the integer types, `unnest`, from a registry that part b extends
with `pg_partition_ancestors`) and a `VALUES` list become a `FROM` item the statement fills before
its `SELECT` runs, exactly as a derived table does, so the planner, joins, grouping and sorting
read them as tables. `VALUES` is a statement, a set-operation operand and a subquery, its columns
typed by D112's `UNION` rules. A function's arguments and a `VALUES` list in `FROM` may name the
outer query in a correlated subquery: the item's shape is fixed when the subquery is prepared and
its rows are generated anew for each distinct outer value (an `EXISTS` over such an item is then
not decorrelated). A function's reference to any sibling `FROM` item (PostgreSQL's implicit
`LATERAL` for functions), by its name or by a column only it has, is `0A000`; a `VALUES` list,
which PostgreSQL does not make `LATERAL`, never sees its siblings.
One set-returning function per select list runs: the select becomes an inner query of its other
items and the function's arguments, whose rows are expanded and then distinct-ed, ordered and
limited, so `ORDER BY` takes output columns there; a second function, one inside an expression,
and one in `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT` or an aggregate are `0A000`, as
PostgreSQL refuses several of them. A function's rows in `FROM` go straight into the intermediate table
as they are made, never held in a second list; the rows of a select-list function or a `VALUES`
list, which are built before they are stored, count for both copies while both are held; and all
of them count against the statement's 1 GiB (D100),
so `generate_series(1, 10^12)` ends with `53200` and not with the memory gone.

**`string_agg`, `trim` and `quote_ident`.** `string_agg(text, text)` and `string_agg(bytea,
bytea)` skip NULLs, take NULL as an empty delimiter, are NULL over no rows, take `DISTINCT`, and
check the value limit before each append; `ORDER BY` inside the call is `0A000`.
`trim([LEADING | TRAILING | BOTH] [chars] FROM s)`, `ltrim`, `rtrim` and `btrim` work as
PostgreSQL's; `quote_ident` quotes unless the name is lower-case letters, digits and underscores
and not a key word other than an unreserved one, from PostgreSQL 16's key word list (observed
with `pg_get_keywords()`, the manual's appendix C), which part b's deparser shares.

**Decided by research before the plan.** The regular expression engine is built here, in part
a, rather than with item 36's `regexp_*` functions, because psql needs `~` now and a linear-time
engine is needed by both; the catalog comes in a second pull request so this SQL can be reviewed
and merged on its own.

**Size (D6).** The stripped release `eggdb` grows from 3,598,480 to 3,747,312 bytes on aarch64
macOS (+148,832, +4.1%) for the regular expression engine, arrays, the set-returning functions,
`VALUES` and the key word list; features a statement does not use cost it nothing at run time.
