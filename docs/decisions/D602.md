## D602 pg_cron schedules checked when set, and the restart minute — Decided by the code-only session (2026-11-12, D355); roadmap M10, D200, D429

Two pg_cron behaviours D200 left out:

- pg_cron refuses a schedule it cannot read when the job is created (`ERROR: invalid schedule: …`).
  EggDB stored it and only counted it as invalid each minute, so a typo went unnoticed.
- A server restarted part-way through a minute skipped that minute's jobs, because the runner
  started counting from the minute it started in.

What changes:

- A builtin, `eggdb_cron_schedule_check(text)`, parses the schedule as the runner does. It answers
  `true`, or raises `invalid schedule: <text>` (22023), and NULL gives NULL.
  - Both `cron.schedule` forms call it before writing the job.
  - `cron.alter_job` calls it when it is given a schedule.
  - The `eggdb_` prefix keeps it out of the way of user functions.
- `eggdb serve`'s job runner starts one minute back, so the minute the server starts in is run.
  - To keep a second start within the same minute from running a job twice, the minute runner
    first reads which jobs `cron.job_run_details` already records for that minute's start time,
    and skips them.
  - Downtime longer than that minute is not caught up, as in pg_cron.
- The existing test now expects the refusal, and writes a broken schedule into `cron.job` directly
  to keep covering the runner's invalid count. A new test runs one minute twice and checks the job
  runs once, and that `alter_job` refuses `61 * * * *`.
- Jobs made by an earlier `CREATE EXTENSION pg_cron` keep their old functions until the extension
  is recreated.
