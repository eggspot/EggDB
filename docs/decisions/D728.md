## D728 Graph label and property indexes used for lookups — Decided by the code-only session (2026-11-12, D355); roadmap M13, indexes on labels and properties (D206, D503)

- The graph store keeps a label index (each label's node ids) and, for every `CREATE INDEX` and uniqueness
  constraint, a property index (the rule's property values, then the node id). Both change with every node write
  and delete, a new index or constraint is filled from the label index when it is created, and a dropped one's
  entries go with it.
- `MATCH` starts from the indexes: a node pattern whose labels and inline properties cover an index or uniqueness
  constraint reads only the nodes with those values; otherwise one with a label reads only that label's nodes.
  Uniqueness checks read the constraint's index instead of every node.
- Integers, floats, strings and booleans are indexed; an integral float is indexed as the integer, so `1` and `1.0`
  find each other as `=` says. Nodes whose value is a list or a temporal value are left out of property indexes,
  and a lookup with such a value scans instead.
- A database written before this keeps working: lookups scan until the first write transaction builds every index
  once, in that transaction.
- `WHERE` conditions (`MATCH (n:Person) WHERE n.email = $email`) did not use the indexes here; D729 added
  equalities.
