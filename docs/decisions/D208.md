## D208 Point-in-time restore starts with archived, verified snapshots; continuous log archiving follows — Decided by the build loop (by judgement, 2026-10-31); refines D24

Part 4.M14-1 asks for continuous archiving of the log to a directory or S3-compatible storage,
restore to any moment, incremental and encrypted backups, and every backup verified by a
restore.

- **Snapshots first.** `eggdb backup <file> <directory>` writes a consistent copy of the last
  commit into the directory under a UTC timestamped name, opens it read-only and checks every
  page (the restore test, run on every archive), and appends a line to `manifest.jsonl` with the
  time, size, entry count and SHA-256. `eggdb restore <new> <directory> --at <time>` restores
  the newest copy taken at or before the time after checking its SHA-256 against the manifest.
  Point in time is therefore "to the nearest archived snapshot"; running `backup` from cron or
  the job scheduler (D200) sets the granularity.
- **Continuous archiving needs the log to outlive checkpoints.** The write-ahead log recycles
  its segments at each checkpoint (format.md); shipping every segment before it is recycled,
  and replaying segments on top of a snapshot up to a commit stamp, changes the file format's
  log handling and is security- and data-critical (D35), so it is its own slice with the
  format review.
- **Nothing is deleted.** The archive keeps every copy; pruning waits for an explicit
  retention option so an archive is never shortened by surprise.

Left: continuous log shipping and replay to any commit, S3-compatible targets, incremental
copies, encrypted archives (the file's own page encryption, D187, already applies to copies of
encrypted files), retention, and the simulator test of restoring to a stamp.
