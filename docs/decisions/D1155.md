## D1155 TLS on every other listener, ended in front of each protocol server — Decided by the code-only session (2026-11-14, D355); roadmap M6a (D22, D161)

- **The rule.** Twenty-four listeners used to refuse any address but loopback because they had no TLS:
  MCP, RESP, the Elasticsearch-compatible REST API, MongoDB, Bolt, Gremlin, AMQP, MQTT, SQS, S3, DynamoDB, the
  observability endpoint, Trino, Arrow Flight SQL, SMTP, IMAP, JMAP, WebDAV, SPARQL, ClickHouse's HTTP interface,
  the REST API, CQL, STOMP and NATS. Now each takes any address when `serve` has TLS (`--tls-certificate` and
  `--tls-key`, or `--tls-self-signed`), and still refuses one outside loopback without it.
- **How.** `serve_tls_relay::TlsRelays::listener` binds the public address and gives the protocol server a
  listener on an ephemeral loopback port. The relay accepts on the public address, runs the TLS handshake with
  the server's own certificate (the same setup as PostgreSQL's, MySQL's and TDS's, with no ALPN), connects to the
  loopback port and copies bytes both ways.
  - The read side waits on the socket with `peek` while holding no lock. It asks the new
    `TlsStream::has_buffered_input` first, so data already decrypted or a record already taken from the socket is
    never stranded. It then reads one record under the stream's lock with a 200 ms timeout.
  - The write side seals whatever the protocol server sends, so server pushes (pub/sub, MQTT deliveries, NATS
    messages) go out as they come.
  - Either side closing shuts down the other.
  - This is implicit TLS, as in `rediss://`, `https://`, SMTPS and IMAPS.
- **What stays on loopback.** Listeners without authentication keep refusing other machines with or without
  TLS: memcached, Kafka Connect's REST API, etcd, ZooKeeper and Kafka. Those wait for their own authentication.
- **Certificate names.** The self-signed certificate now also names the relayed listeners' addresses.
- **Costs, until the event loop and the shared listener crate.** Each relayed connection takes two threads and
  one loopback hop, and the protocol server sees the relay's loopback address as its peer. Both go away when
  connections move to the completion-queue event loop and the shared listener crate (the next M6a items, D103,
  D122), which will end TLS inside the server.
- **Tests.** A unit test relays a connection that receives a server push and an echo. Another checks that a
  public listener without TLS is refused. CI's `tls-clients` job now also connects `redis-cli --tls`, curl over
  HTTPS and an `openssl s_client` handshake to relayed RESP, REST and MQTT listeners on a non-loopback address,
  each checking the chain against a test authority.

**Status:** code written, unbuilt (code-only mode, D355).
