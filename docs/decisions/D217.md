## D217 AMQP 1.0 on the AMQP port, STOMP in our own eggdb-stomp, and the outbox relayed into queues — Decided by the build loop (by judgement, 2026-10-31); refines D33 and D210

Part 4.M16-5 asks for AMQP 1.0, STOMP and the transactional outbox and inbox.

- **AMQP 1.0 shares `--amqp-listen` with 0-9-1.** The two versions open with different
  protocol headers, so one listener tells them apart, as RabbitMQ 4 does. Written from the
  OASIS AMQP 1.0 specification: the type system (every fixed-width type read, the ones the
  performatives need written), SASL PLAIN only (an unauthenticated AMQP header is answered with
  the SASL header), sessions, links whose source or target address is a queue name, credit
  flow both ways (we grant 500 and top up at half), multi-frame transfers in and out split at
  the client's frame size, and settlement: accepted and rejected remove a message, released
  and modified return it. Only the body crosses (data sections joined, a string or binary
  value as its bytes), so a message sent over AMQP 1.0 is read by AMQP 0-9-1, STOMP and SQS
  clients as the same bytes; outgoing messages carry a header section with the delivery count
  and a properties section with the message id.
- **STOMP in `eggdb-stomp`**, from the STOMP 1.2 specification, accepting 1.0 and 1.1:
  `/queue/` destinations are the same durable queues; `/topic/` destinations are delivered in
  memory to current subscribers. A transaction's queue sends are stored with the new
  `Queues::send_all`, all or none.
- **The outbox is D210's**: `eggdb serve --cdc-queue <name>` relays captured changes into a
  durable queue, at least once and in commit order, so every queue protocol consumes them.
- **The inbox is a documented pattern, not a feature**: a message id stays the same across
  redeliveries (`<queue>-<number>`), and a consumer records it in its own transaction
  (`docs/sql.md`, "Transactional outbox and inbox"). A built-in inbox would need the
  consumer's transaction to be ours, which only an in-process consumer has.

Left: AMQP 1.0 message annotations and properties kept end to end, transactions (the
coordinator link), dynamic nodes, link stealing and resumption, `amqp:modified` with
`undeliverable-here`, and an idle-timeout we enforce; STOMP heart-beats, `/exchange/`
destinations and selectors; a dead-letter queue for rejected messages; an in-process inbox for
embedded consumers; TLS for both.
