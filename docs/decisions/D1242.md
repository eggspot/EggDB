## D1242 More of libsqlite3's entry points — Decided by the code-only session (2026-11-17, D355); roadmap M5, `libsqlite3` (D181, D790)

- **What users get.** Programs and bindings written against newer or older SQLite headers link and run: `sqlite3_prepare` and `sqlite3_prepare_v3` (as `_v2`; the preparation flags change nothing), `sqlite3_bind_text64` (UTF-8 only, as EggDB's text is; other encodings `SQLITE_MISUSE`), `sqlite3_bind_blob64`, `sqlite3_bind_zeroblob`, `sqlite3_expanded_sql` (the SQL with bound values written in, freed with `sqlite3_free`), `sqlite3_limit` (SQLite's default limits, read-only), `sqlite3_db_filename` (the file's full path, empty in memory) and `sqlite3_db_readonly`, `sqlite3_stmt_status` (0), and `sqlite3_initialize`, `sqlite3_shutdown`, `sqlite3_busy_handler` and `sqlite3_progress_handler`, which have nothing to do because EggDB waits for its writer itself and does not run a VDBE.
- **How.** A `compatibility` module of thin wrappers over the existing prepare and bind calls; `sqlite3_expanded_sql` walks the SQL outside quotes and replaces `?` and `?N` with the bound values as SQL literals (text quoted, blobs as `X'..'`, NULL), allocating as a `CString` so the existing `sqlite3_free` frees it. Lengths above `int` are `SQLITE_TOOBIG`.
- **Left.** `sqlite3_malloc`/`sqlite3_realloc` (the library's `sqlite3_free` frees only its own strings), variadic `sqlite3_config`/`sqlite3_db_config`/`sqlite3_mprintf`, named parameters in `sqlite3_expanded_sql`, attached schemas, the hooks, and the user aggregates, collations and streamed rows already listed.
- **Proof.** A test in `tests/all/api.rs`: limits, `prepare_v3`, a 64-bit text bind with a quote, a zero blob, a refused encoding, and the expanded SQL leaving a quoted `?` alone.

**Status:** code written, unbuilt (code-only mode, D355).
