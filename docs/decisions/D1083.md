## D1083 Wear levelling, header slots on flash, and power-loss tests — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D41, D223)

- **`eggdb_format::WearLevelled`** (no `std`, `alloc` only) turns raw flash (D223's `Flash` driver trait) into
  numbered blocks, each one erase sector, written atomically and spread over the chip's wear:
  - **Atomic writes.** A block is rewritten into a fresh, erased sector. Only then is a mapping record
    appended to a journal, so a power cut at any moment leaves the block old or new, never a mix. A sector is
    reused only after the record that freed it is durable.
  - **Two journal slots,** like a file's two header slots: equal runs of sectors at the start of the region.
    - The active slot opens with a header (magic, generation, CRC-32C), written last. Then come a snapshot of
      every mapping, every sector's erase count and the logical size, then one 24-byte, CRC-checked record per
      change.
    - When it fills, the other slot is erased, given a fresh snapshot, and then its header under the next
      generation. Mounting takes the slot with the higher whole generation and replays it, passing over a
      record a cut tore.
    - Slot size is worked out from the chip so a snapshot always fits twice.
  - **Wear levelling.** Writes go to the free sector with the fewest erases (dynamic). When the spread
    between the least- and most-erased sectors passes 64, the coldest block moves out of the least-worn
    sector (static). Erase counts persist in the journal.
  - `spare` sectors (at least two) stay free for rewrites and moves. Never-written and trimmed blocks read as
    zeros.
- **`eggdb_storage::FlashFile`** is the engine's `File` (D1081) over that region:
  - Byte reads and writes are cut into blocks, with partial blocks read, changed and written back.
  - The logical size lives in the journal. Shrinking trims whole blocks and zeroes the partial tail, so
    regrown bytes read as zeros, as `File` requires.
  - Every write is durable when it returns, so `sync_data` and `sync_all` have nothing left to do, and a lone
    device takes no locks.
  - `PageFile::create_in` and `open_in` run on it, so the page file, its log and its two header slots
    live on raw flash with the same bytes as in a file.
- **Power-loss tests.** A simulated chip cuts power after any number of operations: half an erase is done,
  half a program is written. The test sweeps the cut over every operation of a write on a prepared region,
  remounts, and checks every block. The written block is old or new, and new if the write returned. Every
  other block is unchanged. Other tests cover remounts across journal turnover, wear staying within its
  spread, and `FlashFile` across blocks, sizes and the creation of a database file.
