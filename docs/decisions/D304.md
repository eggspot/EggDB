## D304 Oracle hierarchical queries (`START WITH ... CONNECT BY`) as a derived table walked depth first, and `INSERT ALL` / `INSERT FIRST` as one statement over a subquery read once — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory items 38 and 39

`CONNECT BY` and the multitable inserts were refused (`0A000`) although Oracle schemas lean on
them: HR's `employees.manager_id` exists for `CONNECT BY` queries, reports number rows with
`SELECT LEVEL FROM dual CONNECT BY LEVEL <= n`, and loads fan one staging query out to several
tables with `INSERT ALL`. Both are built from Oracle's SQL Language Reference (Hierarchical
Queries, the hierarchical pseudo-columns and operators, `SYS_CONNECT_BY_PATH`, `ORDER SIBLINGS
BY`, and `INSERT`'s `multi_table_insert`).

- **A derived table, not a new query stage.** The parser rewrites a query with a hierarchical
  clause into one that reads a derived table labelled like its `FROM` item (its alias or table
  name, or `dual`). That table's query is `SELECT <inputs>, * FROM <the FROM item>`, and
  `DerivedTable::hierarchy` (new) tells the executor to walk its rows before they become the
  derived table's rows. Name resolution, views, privileges, CTEs and subqueries already handle
  derived tables, so nothing else learns about hierarchies; the outer query keeps `WHERE`,
  `GROUP BY`, `HAVING`, `ORDER BY` and `ROWNUM`, which is Oracle's order (the walk first, then
  `WHERE`). Pushing `WHERE` conditions into a derived table is turned off for this one.
- **Inputs and slots.** `START WITH` becomes one input column; `CONNECT BY` is split so every
  part without `PRIOR` or `LEVEL` is an input column evaluated by the inner query (subqueries
  included), `PRIOR expr` is an input read from the parent row, and `LEVEL` is the child's
  level. The condition is evaluated over the child's inputs, the parent's inputs and the level.
  When one of its `AND`ed terms is `PRIOR a = b` and both sides have the same type, the
  children are found by a sorted index on `b` instead of trying every row; the whole condition
  is still checked on each candidate.
- **The walk.** Depth first with an explicit stack (no recursion, so a deep hierarchy cannot
  overflow the stack), children in the source's row order or `ORDER SIBLINGS BY` order (roots
  too), and a row emitted before its children, as Oracle returns them. Without a `LEVEL` in the
  condition a row's children are found once and remembered. Every row and remembered child list
  is charged to the statement's work memory, and the walk checks for cancellation, so `CONNECT
  BY 1 = 1` ends with the memory error instead of running forever.
- **Pseudo-columns.** `LEVEL`, `CONNECT_BY_ISLEAF`, `CONNECT_BY_ISCYCLE`, and one column per
  distinct `SYS_CONNECT_BY_PATH`, `CONNECT_BY_ROOT` and `PRIOR` in the select list, `WHERE`,
  `GROUP BY`, `HAVING` and `ORDER BY`, are hidden columns of the derived table (named with the
  hidden-column marker, so `*` never shows them); the outer query reads them by name. A select
  item that held one keeps its Oracle label.
- **Loops.** A child closes a loop when its values of the `PRIOR` expressions equal those of the
  current row or one of its ancestors, which is how Oracle finds them; with no `PRIOR` (`CONNECT
  BY LEVEL <= n`) there is no loop check, as in Oracle. Before the walk every row gets the number
  of its class of equal `PRIOR` values (one sort), and the walk keeps a count per class of the
  rows on the current path, raised on the way down and lowered when it backs up, so the check is
  one lookup per child and a deep chain is walked in time linear in its rows (review round 1
  measured 22.6 s for a 10,000-deep chain with the earlier scan of the whole path). Without `NOCYCLE` it is `ORA-01436`;
  with it the child is skipped and the row gets `CONNECT_BY_ISCYCLE = 1`. `CONNECT_BY_ISLEAF` is
  1 only when the condition finds no child at all, so a row whose only child closes a loop is
  not a leaf.
- **Errors.** `ORA-01788` for a pseudo-column without `CONNECT BY` (`ORA-30002` for
  `SYS_CONNECT_BY_PATH`), `ORA-30003` for a separator that is not a non-empty constant,
  `ORA-30004` for a value holding the separator, `ORA-30929` for `ORDER SIBLINGS BY` elsewhere,
  `ORA-30930` for `CONNECT_BY_ISCYCLE` without `NOCYCLE`, and `ORA-01489` for a
  `SYS_CONNECT_BY_PATH` longer than 4,000 bytes (Oracle's limit with the default
  `MAX_STRING_SIZE = STANDARD`), which also bounds the copying a deep path costs. `CONNECT BY` over a join, `PRIOR`
  beside a subquery and `ORDER SIBLINGS BY` a pseudo-column answer `0A000` for now: the join
  form needs the join's conditions in `WHERE` applied before the walk.
- **Multitable inserts.** `Statement::MultitableInsert` holds the kind (`ALL` or `FIRST`), the
  `WHEN` branches, the `ELSE` targets and one source query: `SELECT <each WHEN condition and
  VALUES expression>, * FROM (subquery)`. The executor reads it once, picks each row's `INTO`
  clauses (every branch that holds for `ALL`, the first for `FIRST`, `ELSE` when none does),
  then inserts each clause's rows with the ordinary `INSERT` executor, constants and `DEFAULT`,
  inside one `write_firing_triggers`, so triggers fire, privileges are checked per target and a
  failing target undoes the statement. An `INTO` clause that gets no rows is still bound (with
  one row of NULLs that is never inserted), so a missing table (`ORA-00942`), a wrong number of
  values and a missing `INSERT` privilege fail whatever the rows, as Oracle checks them when it
  parses. The tag counts every row inserted.
- **Left out.** A sequence's `NEXTVAL` advances per use instead of once per source row; rows go
  into the targets one `INTO` clause at a time rather than row by row, which only shows in
  identity values when two clauses name one table; no error-logging clause. A benchmark of a
  deep hierarchy against SQLite's recursive `WITH` comes with the next performance pass.
