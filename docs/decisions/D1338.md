## D1338 Lookup joins switch to a hash table when their outer side turns out large — Decided by the code-only session (2026-11-25, D355); roadmap M5 "Adaptive re-planning during execution" (D40)

- **What users get.** A join that the planner runs as a lookup per outer row (by primary key, or through an index) because it expected few outer rows no longer pays one lookup per row when that guess is wrong: after 4,096 lookups in one execution, the join reads the inner table once into a hash table keyed by the looked-up columns and probes it for the remaining rows. When the inner table holds more than 64 MiB of rows, it keeps looking up. Results are the same either way; only the cost changes.
- **Why this re-plan.** The planner already chooses a bounded hash build when the outer side is a full scan (and so known to be large); the costly mistakes left are lookup joins whose outer side was expected to be small, a filtered or index-driven outer whose selectivity was misjudged. Switching the inner access at runtime fixes that case without re-planning the whole query, and the switch happens at most once per join step.
- **How.** Each join step keeps a counter and, once switched, the hash table. Keys are built with the same conversion as the lookup (`key_value`, the outer value converted to the inner column's type and kept only when it compares equal), and hashed with the engine's equality keys, so a key matches in the table exactly when the lookup would find it. Rows with a NULL in a key column never match, as in a lookup. The step's other filters still run on every joined row.
- **Left.** Re-ordering joins or changing a hash join back into lookups mid-query, and showing the switch in `EXPLAIN ANALYZE`.
- **Proof.** A session test joins 9,000 orders to 3,000 customers by primary key and by a non-unique index, beyond the switch point, and checks counts and sums against arithmetic.
