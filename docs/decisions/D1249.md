## D1249 Row filters in publications — Decided by the code-only session (2026-11-18, D355); roadmap M14 change streams (D1245, D1248)

- **What users get.** `CREATE PUBLICATION p FOR TABLE orders WHERE (total > 10)`, and the same in `ALTER PUBLICATION ... ADD` or `SET TABLE`, send only the rows the condition keeps, as PostgreSQL 15 does. An expression naming a column the table does not have is refused when the publication is made.
- **How.** The parser keeps the expression's own text, which the stored publication holds per table in a further optional section after the column lists (records written before still read). The filter a walsender builds parses each text once (PostgreSQL's dialect) with its table's definition, and evaluates it as a CHECK constraint is evaluated, against the change's new row for an insert or update and its old row for a delete; a row whose condition is false or NULL is not sent. A change goes out when any publication the subscriber named covers its table without a filter, or with one that keeps the row. Creating the publication evaluates the expression once over a row of NULLs, which reports an unknown column with the evaluator's own error.
- **Differences kept.** PostgreSQL evaluates an update's filter on both rows and turns it into an insert or a delete when only one passes; EggDB sends the update when its new row passes. It also refuses filters using non-immutable functions or columns outside the replica identity for publications sending updates and deletes; EggDB does not yet.
- **Left.** Those refusals, the update transformation, and `pg_publication_rel.prqual`.
- **Proof.** The publications test makes a filtered publication, sees a bad column refused, and checks that a row above the threshold is sent and one below is not.
