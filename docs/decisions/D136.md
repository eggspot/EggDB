## D136 Bulk loads from `bcp in` and `SqlBulkCopy`: `INSERT BULK` waits in the session for rows a server streams from the bulk load message, loaded in one statement through the `INSERT` path; `SET FMTONLY` describes declared types; bcp's character format read in the engine — Decided by the build loop (by research, 2026-10-29); roadmap item 46, applies D1, D5, D9, D12, D117, D122, D123, D132

Item 46 makes `SqlBulkCopy` (Microsoft.Data.SqlClient) and `bcp in` load rows into EggDB over
TDS, and `eggdb import` load the files `bcp ... out -c` writes. Everything is written from
Microsoft's public [MS-TDS] specification (2.2.6.1 bulk load, 2.2.7.4 COLMETADATA, 2.2.7.19 ROW,
2.2.7.14 NBCROW) and the Transact-SQL and bcp reference pages; Microsoft.Data.SqlClient's sources
(MIT) were read only to see which statements and bytes `SqlBulkCopy` sends, never copied. `bcp`
itself is not run in CI: its license does not allow it there, so the check loads committed
character-format files.

**What a client sends.** `SqlBulkCopy` first sends one batch: `select @@trancount; SET FMTONLY ON
select * from <table> SET FMTONLY OFF exec ..sp_tablecollations_100 N'<table>'`, builds
`insert bulk <table> ([column] Type(size) COLLATE name, ...) [with (KEEP_NULLS, TABLOCK,
CHECK_CONSTRAINTS, FIRE_TRIGGERS, ORDER(...))]` from the columns and collations it read, runs it
as a batch, then sends one bulk load message (packet type 0x07): a COLMETADATA token echoing the
types it was given, one ROW token per row and a DONE token. Every `BatchSize` rows repeat the
`insert bulk` and the message. `bcp in` sends the same statement and message.

**`SET FMTONLY ON` is a session setting of the Transact-SQL dialect.** While it is on, a query
returns its columns and no rows (the engine's describe path, which reads no rows), and every
statement other than `SET`, `USE`, transaction control and `EXEC` returns without running.
`BatchStep` gains `format_only`, and the TDS server describes such a result's columns by their
declared types: unbounded text as `nvarchar(max)` and `bytea` as `varbinary(max)` rather than by
the longest value, since `SqlBulkCopy` refuses values longer than the size it was told. Decimal
columns are now described with TYPE_INFO length 17 in every result, as SQL Server does, because
`SqlBulkCopy` writes each decimal value with the length it was told and 17 bytes of data.
`sp_tablecollations_100` joins the catalog procedures (D133): one row per column with its id,
name, TDS collation bytes and collation name (Latin1_General_100_BIN2 for character columns,
NULL for the others). `EXEC ..name` (an empty database and schema) names a procedure as
`EXEC name` does.

**`INSERT BULK` waits in the session, and the rows come through a trait.** The statement parses
in the Transact-SQL dialect; run without rows it checks the table and its columns (208, 207) and
the session keeps its text as the pending bulk load (`Session::bulk_load_pending`). The column
types are read and ignored, since the values' types come with the data. The next batch,
connection reset or load ends the wait. `Session::execute_bulk_load(rows, on_step)` runs the
pending statement again with `rows: &mut dyn BulkRows` attached, through the ordinary batch
runner, so it gets every statement's context (the dialect's conversions and errors, identity,
sequences, implicit transactions, `@@ROWCOUNT`) and reports one `BatchStep` as a statement does.
`BulkRows::next_row(columns, row)` hands one row at a time. The alternative, a server-side
loader in `eggdb-tdswire`, was rejected: the engine core must not depend on a protocol, and the
command-line import needs the same load.

**The rows load through the `INSERT` path in one statement, as `COPY` does (D117).** Each row
goes through `StoredRows` with the table's checks, defaults and identity, foreign keys checked
in batches of 4,096 as `COPY` checks them, all in the statement's write transaction: every row
or none. A NULL takes its column's default unless `KEEP_NULLS`; columns the statement leaves
out take their defaults; a value converts to its column as SQL Server's `INSERT` converts it, so
text from a file loads into any column. An identity column the statement names keeps the values
sent (as `KeepIdentity` asks; NULL there is 339), one it leaves out is numbered; without a
column list the data holds every column and non-NULL identity values are kept, as `bcp -E`
does. Constraints are always checked (SQL Server skips `CHECK` and foreign keys without
`CHECK_CONSTRAINTS` and marks them untrusted, which EggDB has no notion of); there are no
triggers yet, so `FIRE_TRIGGERS` changes nothing.

**The TDS server streams the bulk load message.** A bulk load may be far larger than the 64 MiB
batch limit, so the connection reads the first packet of each message and, for packet type
0x07, hands the rest to `eggdb_tdswire::bulk::BulkReader` through a `BulkInput` that reads one
packet at a time. The reader parses COLMETADATA (TYPE_INFO as RPC parameters read it, D132, plus
`text`, `ntext` and `image` with their table name and text pointers), then ROW and NBCROW tokens
up to DONE, re-parsing a row that is cut by a packet boundary after reading at least as many
bytes again as it already holds, so a row of any size costs linear time and the memory held is
about twice the largest row (at most 64 MiB, error 4815 beyond). The rows go straight into
`execute_bulk_load`; its step is collected and written after the rest of the message has been
read and dropped, so the answer (a DONE with the row count, or the error) never interleaves with
reading. Bad data (4804), an unread type (4816), another number of columns than `INSERT BULK`
named (4815) and Always Encrypted columns (40517) fail the load but keep the connection; bulk
data with no `INSERT BULK` waiting is 4002, also without closing the connection, since the
message was read whole.

**bcp's character format is read in the engine.** `eggdb_sql::BcpCharacterReader` implements
`BulkRows` over any `Read`: fields end with the field terminator and the last field of a row
with the row terminator (`BcpTerminators::written` takes bcp's `-t` and `-r` text with its
escapes), no quoting; an empty field is NULL, a field of one NUL byte the empty string, a
carriage return before the default newline is dropped, `skipping(n)` is bcp's `-F`, the text is
UTF-8, rows up to 1 GiB. `eggdb import --dialect sqlserver --csv <file> --table <name>`
(`--delimiter`, `--row-terminator`, `--header`, `--keep-nulls`) runs `INSERT BULK` and loads
the file through it, so the command line and the TDS server share one load. It lives in
`eggdb-sql` next to `COPY`'s formats (D117) rather than in the command line so embedders and
the fuzzers reach it.

Not decided here: bcp's native (`-n`) and Unicode (`-w`) formats and format files, `BULK INSERT`
and `OPENROWSET(BULK ...)` reading server files (refused as `COPY` refuses them), and minimal
logging for `TABLOCK`.
