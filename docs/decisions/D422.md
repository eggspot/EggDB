## D422 MySQL's named locks (`GET_LOCK` and its family) — Decided by the code-only session (2026-11-11, D355); roadmap M10

- `GET_LOCK(name, timeout)`, `RELEASE_LOCK(name)`, `IS_FREE_LOCK(name)`, `IS_USED_LOCK(name)` and
  `RELEASE_ALL_LOCKS()` run on the application locks that SQL Server's `sp_getapplock` already
  uses (`advisory_locks.rs`), which wait with a deadline, detect waits that close a cycle and are
  released when the session ends. MySQL's locks get resources of their own (the prefix `mysql user
  lock ` and the lower-cased name, MySQL comparing names without case), so they never meet SQL
  Server's.
- `GET_LOCK` takes the lock exclusively for the session and returns 1, or 0 after the timeout; a
  negative timeout waits for good. A session may take a lock it holds again, and must release it
  as many times, as in MySQL 5.7 and later. A wait that would close a cycle is MySQL's error 3058
  (SQLSTATE `40001`); an empty name, `NULL` or a name over 64 characters is error 3057.
- `RELEASE_LOCK` returns 1 when it released one hold, 0 when another session holds the lock and
  `NULL` when nobody does; `IS_FREE_LOCK` returns 1 or 0; `IS_USED_LOCK` returns the holder's
  session number as the lock registry knows it, which may differ from `CONNECTION_ID()`: a known
  difference; `RELEASE_ALL_LOCKS` returns the number of holds released.
- `information_schema` and `SHOW` completeness stays open: it is a list without an end, worked as
  clients show what they miss.
