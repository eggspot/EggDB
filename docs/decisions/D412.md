## D412 MongoDB's `OP_COMPRESSED` with snappy and zlib — Decided by the code-only session (2026-11-10, D355); roadmap M9

- `hello` (and `isMaster`) answer a client's `compression` list with the ones this server takes,
  in the client's order: `snappy` and `zlib`. `zstd` is left out until EggDB has its own zstd
  codec (no third-party crates); a driver then simply doesn't pick it.
- An `OP_COMPRESSED` request (op code 2012) is unwrapped before it is read: its original op code,
  uncompressed size (held to the message limit and to the memory budget like any message) and
  compressor (`noop` 0, `snappy` 1, `zlib` 2). A size that doesn't match, an unknown compressor or a
  compressed message inside another closes the connection, as a damaged message does. The reply
  goes back compressed with the same compressor, as the wire protocol asks.
- Snappy uses `eggdb-columnar`'s codec and zlib decoding `eggdb-content`'s, so the wire crate gains
  those two dependency-free crates. Replies in zlib are written as stored (uncompressed) DEFLATE
  blocks with the zlib header and Adler-32: a valid zlib stream every driver reads, with no
  compressor of our own yet; snappy replies are really compressed, so drivers that offer snappy
  first get smaller replies.

**Status:** code written, unbuilt (code-only mode, D355).
