## D337 Explicit partition selection (`t PARTITION (p1, p2)` in MySQL, `PARTITION (p)` / `PARTITION FOR (key)` in Oracle) and identity and `AUTO_INCREMENT` columns in partitioned tables, numbered by the parent in statement order — Decided by the build loop (batch 6, 2026-11-10); roadmap M2, extends D169 and D316, no format change

D169 left two gaps that MySQL and Oracle applications hit at once: a query or a write could not
name the partitions it touches, and a partitioned table could not have an `AUTO_INCREMENT` or
identity column, the most common primary key there is. Both now work as the MySQL 8.4 Reference
Manual ("Partition Selection", `SELECT`, `INSERT`, `REPLACE`, `UPDATE`, `DELETE`) and Oracle's
SQL Language Reference (the `partition_extension_clause` of `query_table_expression` and
`dml_table_expression_clause`) describe them.

- **Syntax.** In the MySQL dialect, `tbl_name PARTITION (p1, p2, ...)` after a table name in
  `FROM` and joins (before the alias), and as the target of `INSERT`, `REPLACE`, `UPDATE` and
  `DELETE` (in `DELETE`, after the alias too, as MySQL writes it). In the Oracle dialect,
  `PARTITION (p)`, `SUBPARTITION (p)` and `PARTITION FOR (value, ...)` in the same places. Only
  these two dialects parse it: in PostgreSQL `FROM t partition (p1)` stays an alias named
  `partition` with a column list, as PostgreSQL reads it. Names match case-insensitively, a name
  may repeat, and naming a partition selects every partition below it.
- **Reads.** Name resolution keeps only the named partitions among those pruning leaves (D169),
  so the reference becomes the one partition or a `UNION ALL` of the named ones. When the `WHERE`
  rules every named partition out, the named partitions are still read, so the query answers no
  rows instead of reading the whole table.
- **Writes.** `INSERT` and `REPLACE` route each row as before and refuse the statement when a
  row lands outside the set: MySQL `1748 Found a row not matching the given partition set`,
  Oracle `ORA-14401 inserted partition key is outside specified partition`. `UPDATE` and
  `DELETE` run only on the named partitions; a row an `UPDATE` moves (D316) is inserted through
  the same selection, so a move inside the set works and a move out of it is `1748` /
  `ORA-14401`, and the whole statement is undone.
- **Errors.** An unknown partition is MySQL `1735 Unknown partition 'p9' in table 't'` and
  Oracle `ORA-02149 Specified partition does not exist`; a table or view that is not partitioned
  is MySQL `1747 PARTITION () clause on non partitioned table` and Oracle `ORA-14501 object is
  not partitioned`; `PARTITION FOR` a key no partition takes is `ORA-14400`.
- **Identity and `AUTO_INCREMENT`.** The refusal in `CREATE TABLE ... PARTITION BY` is gone. The
  parent numbers the rows: `INSERT` into a partitioned table gives each row its id in statement
  order before routing it (so a key on the id, `HASH(id)`, routes on the generated value), and
  passes the id to the partition as a constant; partitions have no identity column of their own
  and never generate. The counter is the furthest value any partition holds (the maximum, or the
  minimum for a negative increment), read from the partition's primary key when the column leads
  it, else from a B-tree index the column leads, else by reading the partition; no counter is
  stored, so the file format does not change. A value given explicitly is kept (MySQL's `0` and
  `NULL` generate) and moves the counter past it, as for an ordinary table. `LAST_INSERT_ID()`
  is the first id the statement generated. `GENERATED ALWAYS` refuses a given value
  (`428C9`) unless `OVERRIDING SYSTEM VALUE`, `OVERRIDING USER VALUE` numbers the row anyway,
  an `UPDATE` may set a `GENERATED ALWAYS` column only to `DEFAULT` (`428C9`), and rows moved by an
  `UPDATE` keep their ids. The implicit sequence PostgreSQL clients read
  (`SELECT last_value FROM t_id_seq`) and the statement's identity counters look across the
  partitions the same way. As in every other table, the identity or `AUTO_INCREMENT` column must
  lead the primary key, so a partitioned table keys on `PRIMARY KEY (id, created_at)`;
  `PRIMARY KEY (created_at, id)` is refused as before (MySQL `1075`, PostgreSQL `42P16`). Allowing
  it anywhere in the key, as MySQL does, is a file format change: today's table definitions are
  damaged unless that column comes first, so older releases would call such a file damaged instead
  of refusing a newer version by name. It waits for table definition version 15 and its D35
  review (roadmap M2).

Update (D363, code-only mode): a partition named directly now numbers rows from its root's
identity column, and a selected subpartition admits rows routed through its partition.

Left: a partition named directly (`INSERT INTO "t#P#p0"` or a PostgreSQL partition) does not
number rows, where PostgreSQL 17 draws from the parent's sequence; MySQL's
`SUBPARTITION BY` does not exist yet, so a selection names partitions only (a subpartition
selected alone, once they exist, will not admit rows routed to its parent level); `PARTITION`
selection on a table with row-level security policies is refused (`0A000`); `INSERT IGNORE`
refuses rows outside the set instead of skipping them with a warning; `LOAD DATA ...
PARTITION` and `ALTER TABLE ... TRUNCATE PARTITION`.
