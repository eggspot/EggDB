## D787 PostgreSQL event triggers — Decided by the code-only session (2026-11-12, D355); roadmap M5, event triggers

- `CREATE EVENT TRIGGER`, `ALTER EVENT TRIGGER` and `DROP EVENT TRIGGER` are parsed in PostgreSQL's dialect and kept
  in `eggdb_internal.pg_event_triggers` (name, event, tag filter, function, `evtenabled` letter, owner), the way the
  other code-only features keep their records in an internal table rather than a new key space. Only a superuser
  manages them (42501 otherwise, as PostgreSQL). Unknown events fail with 42601, tags of commands that never fire
  (databases, roles, tablespaces, event triggers themselves) with 0A000, unknown tags with 42601.
- Functions may now be declared `RETURNS event_trigger` (pseudo-type OID 3838). Such a function takes no arguments,
  must be PL/pgSQL, ends like a `void` function, sees `TG_EVENT` and `TG_TAG`, and fails with "trigger functions can
  only be called as triggers" when called directly.
- Firing: `Session::run` wraps each statement. When the outermost statement on the thread is a DDL command with a
  PostgreSQL tag and enabled triggers exist, the session runs `ddl_command_start` triggers, the command, then
  `sql_drop` (for drops) and `ddl_command_end` triggers, inside one transaction (`atomically`), so a failing trigger
  undoes the command, as PostgreSQL's do. Statements EggDB runs for itself (internal tables, `BEGIN`/`COMMIT`) and
  statements inside functions are not outermost and fire nothing, which keeps trigger bodies from re-firing. Triggers
  run in name order; `ENABLE REPLICA` triggers do not fire (no replication role sessions yet).
- `pg_event_trigger_ddl_commands()` returns one row for the command's own object at `ddl_command_end`, and
  `pg_event_trigger_dropped_objects()` one row per object the statement named at `sql_drop`; both fail with 39P03
  elsewhere. Object OIDs are 0 and `command` is NULL (PostgreSQL's `pg_ddl_command` is opaque). Objects a `CASCADE`
  drops along the way are not listed.
- pg_restore no longer skips `CREATE EVENT TRIGGER`.
- Left: firing `table_rewrite` (accepted, never fires), `login`, sub-commands of `ALTER TABLE` as separate rows, and
  SQL Server's and Oracle's DDL triggers.
