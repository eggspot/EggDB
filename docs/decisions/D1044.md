## D1044 Latency-aware placement for multi-region clusters — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D4, D212)

- `eggdb_cluster::regions` plans where data and voters go when a cluster spans regions, from round-trip times between
  regions (`Latencies`; a pair never measured counts as the slowest measured one, so an unknown path is never
  preferred) and the requests per region each shard received (`Traffic`).
- **Shard owners** (`place_by_latency`): each unpinned shard with traffic belongs in the region that serves its
  requests with the least total latency (requests weighted by their region's round trip to the candidate). The plan
  moves its owner there, to the node of that region owning the fewest shards, and leaves pinned shards (geo pinning,
  D212) and quiet shards where they are. The moves are carried out as D1040's online moves.
- **Voters** (`choose_voters`): a replication group of n voters led from a home region takes one node in each of the
  n regions nearest home before it takes a second node anywhere, so with n regions available losing any one region
  keeps a majority (`survives_region_loss` checks a given set). `quorum_latency` says what a commit then waits for:
  the round trip to the farthest member of the fastest majority, which for three regions is the second-nearest one.
- These are pure functions over the shard map and placement, so the rebalancing simulation (next item) runs them
  under load and failures. Left: measuring latencies and counting traffic inside `serve --cluster`, and the process
  that applies the plan.
