## D1106 Offline-first sync over HTTP, one space per signed-in application user — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D37, D228)

- **Protocol.** One request per round: `POST /sync?received=<n>`. The body is the client's changes logged after its `sent` cursor, in D228's checked binary format. The answer's body is the server's changes after `received` (at most 1,000), and `X-EggDB-Sync-Received` carries the cursor after them. The client advances `sent` and `received` only after a `200`, so a dropped connection just repeats a round, and applying a change twice is harmless because a row only takes a strictly newer stamp. `eggdb_sync::http::sync_over_http` is the client API apps call; repeat it until nothing changes to catch up.
- **Authentication per user.** Devices sign in as the application's end users with `eggdb_app_auth` (D37) and send the session token as `Authorization: Bearer`. The server checks the JWT's signature against the database's own signing keys, its issuer, audience and expiry, and that the session is neither signed out nor expired (`eggdb_app_auth.sessions`). It then takes the user id from the token. The token is checked to be JWT characters before it goes into SQL, and anything else gets `401` with `WWW-Authenticate: Bearer`.
- **One space per user.** The user's rows and change log live in the collection `sync<user id>` (`DatabaseKeyspace` with prefix `sync`). Spaces are isolated by construction, and each is one D228 replica on the server, so a user's phone and laptop converge through it.
- **Transport security.** `eggdb serve --sync-listen` uses the server's TLS settings, which are required off this machine, plus the shared memory budget and rate limiter.
- **Left** (the next roadmap lines): syncing SQL tables through change capture, log compaction, partial sync, per-field merges and CRDTs, and end-to-end encryption.
