## D298 Grouping sets (`ROLLUP`, `CUBE`, `GROUPING SETS`, MySQL's and SQL Server's `WITH ROLLUP`) are expanded into a list of sets at parse time and grouped in one pass over the rows, with `GROUPING()` read from the row's set — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory item 2, extends the grouping of roadmap item 19b

PostgreSQL ("GROUPING SETS, CUBE, and ROLLUP" in the queries chapter and the `GROUPING`
function), SQL Server (`SELECT - GROUP BY` and `GROUPING_ID`), Oracle (the `group_by_clause`,
`GROUPING`, `GROUPING_ID` and `GROUP_ID`) and MySQL ("GROUP BY Modifiers") define the same thing:
a query grouped by several sets of keys at once, each set's rows having NULL for the keys it
leaves out, and `GROUPING` telling those NULLs from NULLs in the data. SQLite has none of it.

- **Parsed into sets, once.** The parser keeps every key it reads in `Select::group_by` (so the
  name resolution, privilege and subquery passes that walk `group_by` see them unchanged) and,
  when the clause uses a construct, `Select::grouping_sets`: the expanded list of sets as indexes
  into `group_by`, and whether `DISTINCT` was written. `ROLLUP (e1, ..., en)` is the n+1
  prefixes, `CUBE` every subset in the order PostgreSQL's manual lists them, `GROUPING SETS` the
  union of its elements (which may nest), a parenthesized list one key, and the items of the
  clause are multiplied. A plain `GROUP BY` keeps `grouping_sets` empty and runs exactly as
  before. Limits as PostgreSQL's: more than 4096 sets is `54001`, a `CUBE` of more than 12 keys
  `54000`, `GROUPING` with more than 31 arguments `54023`, and nesting past the parser's 64
  levels `54001`. EggDB adds one of its own: the sets times the clause's keys may be at most
  1,048,576 (`54001`, "too many grouping set keys present"), which bounds both what the parser
  builds and the per-row work of grouping (every row is keyed once per set over every key). Each
  limit is checked from the operands' sizes before a `ROLLUP`, `CUBE`, product or set list is
  built, so a hostile clause cannot allocate its way past them. Plain keys (`GROUP BY a, b`) are
  collected once and added to every set at the end, never re-copied per comma, so a plain
  `GROUP BY` of many keys stays linear; repeated sets are numbered through a hash of the sorted
  set, each set is held as its sorted keys rather than a set-by-key table, and equal keys are
  found through a hash of their bound shape.
- **Dialects.** PostgreSQL, SQL Server and Oracle take `ROLLUP`, `CUBE`, `GROUPING SETS` and `()`;
  PostgreSQL also `GROUP BY DISTINCT` (repeated sets dropped) and `GROUP BY ALL` (the default).
  MySQL takes only `WITH ROLLUP` after a plain list, SQL Server `WITH ROLLUP` and `WITH CUBE`;
  these cannot be mixed with the other constructs. MySQL and SQLite answer a syntax error for
  `ROLLUP (...)`, `CUBE (...)` and `GROUPING SETS`. `GROUPING` is read in every dialect but
  SQLite, `GROUPING_ID` in SQL Server and Oracle and `GROUP_ID()` in Oracle; each is an internal
  function call that the grouping analysis turns into a column of the grouped row, and anywhere
  else (`WHERE`, `GROUP BY`, inside an aggregate) it is refused as an aggregate is.
- **One pass.** `Grouping::run` evaluates the keys once per row and feeds the row to one group
  per set, keyed by the set's number and its kept keys, so a duplicate set (`GROUPING SETS ((a),
  (a))`) keeps its own groups, as the standard says. Keys are compared by their bound shape, so
  `GROUP BY a, ROLLUP (a, b)` knows both `a` are one key. A set with no keys returns its row over
  no rows, as PostgreSQL's grand total does. Memory is charged per group as before.
- **Order.** When every set is the first keys of the clause's key order (any `ROLLUP`, a plain
  list with a `ROLLUP` after it, MySQL's `WITH ROLLUP`), the groups come out sorted by the keys
  with a left-out key after the kept ones, which is each subtotal after its rows and the total
  last, the order MySQL's manual and SQL Server's examples show and PostgreSQL's sorted plan
  gives. Other sets come out one set after the other. `ORDER BY` still decides when written.
- **`GROUPING` and `GROUP_ID`.** `GROUPING(a, b, ...)` is one bit per argument, the last one the
  lowest, 1 when the row's set leaves that key out; an argument that is not a key is `42803`
  "arguments to GROUPING must be grouping expressions of the associated query level".
  `GROUPING_ID` is the same bitmap. `GROUP_ID()` counts the earlier sets equal to the row's.
  SQL Server and Oracle accept only one argument for `GROUPING`; EggDB accepts more there.
- **Functional dependency.** A primary key determines its table's columns only when every set
  keeps it, as PostgreSQL's analysis does for grouping sets.

Not in this decision: SQL Server's and Oracle's own error numbers for grouping-set mistakes and
their one-argument `GROUPING`, grouping sets combined with window functions checked against
each manual, `GROUPING` whose arguments are outer references in a subquery (PostgreSQL gives it
to the outer query level; EggDB answers `42803`), and MySQL's NULL ordering (NULL first for
`ASC`, last for `DESC`), which the MySQL dialect still sorts the other way, so MySQL's `WITH
ROLLUP ... ORDER BY year DESC` example puts the super-aggregate row first (roadmap).
