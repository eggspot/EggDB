## D158 Routines: one record per name holding every overload as source, PL/pgSQL compiled to a checked statement tree at CREATE and on first use, run by an interpreter over the statement's own writer, with limits on depth, size and time — Decided by the build loop (by judgement, 2026-10-31); part 3.14, applies D9, D27, D35, D45, D157

Part 3.14 adds PostgreSQL's functions, procedures and `DO` blocks in `LANGUAGE sql` and
`LANGUAGE plpgsql`, and the trigger functions 3.13's PostgreSQL triggers were waiting for. The
plan named this decision D152, which an earlier part had taken; it is D158.

**One record per name, shared by every dialect.** A routine name's overloads are one catalog
record (prefix, `0x0C`, the internal qualified name, `public` left out as for tables), listing
for each overload its dialect, kind (function or procedure), identity (the input argument types,
typmods dropped) and the whole `CREATE` text (layout in sql.md "How SQL is stored"). Loading
re-parses the `CREATE` text; a per-session cache keyed by the store's committed version keeps
the parsed definitions, so calls read nothing while nothing changed. T-SQL (3.15) and PL/SQL
(3.16) routines go into the same records with their own dialect code, so one name space, one
`DROP ... CASCADE` and one catalog (`pg_proc`, `information_schema.routines`) cover them all.

**Stored as source, compiled to a checked tree.** A PL/pgSQL body is kept as written. At
`CREATE` (when `check_function_bodies` is on, as in PostgreSQL; `pg_dump` turns it off) it is
compiled to a statement tree (`plpgsql::Program`): declarations, blocks, loops, `RAISE`,
handlers, cursors and labels are checked with PostgreSQL's messages, and every expression is
syntax-checked by the SQL parser. Embedded SQL statements are kept as text and parsed when they
run, so a function that uses SQL EggDB cannot run yet still restores, and fails only when that
statement runs. The compiled tree is cached next to the parsed definition and rebuilt on first
use after a restart. Variables reach SQL through a parser frame that turns their names into
constants; a name that is both a variable and a column resolves to the variable (PostgreSQL's
`use_variable`), and `#variable_conflict use_column` is `0A000`.

**Run over the statement's own writer.** The interpreter works on the writer of the statement
that called it, so `CALL`, `DO`, a top-level `SELECT f(...)` of a volatile function, `PERFORM`
and trigger functions write inside the caller's transaction and commit or roll back with it.
An exception block records the previous value of every key it writes and puts them back when a
handler catches an error (PostgreSQL's subtransaction semantics). Calls inside row expressions
(`SELECT f(col) FROM t`, `WHERE`) run read-only: a function that writes there is `0A000` with a
hint to call it on its own. `LANGUAGE sql` functions run their statements in order and return
the last one's result.

**Limits (D45).** Calls nest at most 100 deep (`54001`), every loop iteration and statement
checks for cancellation, a body has at most 64 levels of nesting and 100,000 statements and
declarations, a routine's text is at most 1 MiB, a name at most 256 overloads, a routine 100
parameters, a routine 1000 open cursors, an array assignment at most 2^20 elements. Hostile
bodies are errors, never crashes or hangs (D9).

**Catalogs.** User routines get stable OIDs (hashed from their name and identity, like other
catalog objects) and show in `pg_proc`, `pg_language`, `pg_trigger.tgfoid`,
`pg_get_functiondef`, `pg_get_function_arguments`, `pg_get_function_result`,
`pg_function_is_visible`, `regproc` and `information_schema.routines`/`parameters`, so psql's
`\df` lists them.

**Restores.** `pg_dump` scripts now create their `sql` and `plpgsql` functions and procedures and
their triggers; routines in other languages (C, Python, Perl) stay in the restore report.

**Not yet:** `COMMIT`/`ROLLBACK` inside procedures, refcursors returned to the caller, transition
tables (`REFERENCING`), polymorphic argument types (`anyelement`), `regprocedure`, writes from
functions called once per row, and set-returning functions anywhere but a `FROM` item or a
`SELECT` without `FROM`.
