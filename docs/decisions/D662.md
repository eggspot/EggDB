## D662 eggdb-fuzz, a long-running fuzzer of the decoders of untrusted bytes — Decided by the code-only session (2026-11-12, D355); roadmap M2, D171, D357

D357 left "a long-running fuzzer" open for the Zstandard codec, and the same need applies to every
decoder EggDB runs on bytes a client or a file controls. Fuzzing frameworks are third-party crates,
so EggDB gets a small one of its own.

- A new binary crate, `eggdb-fuzz`, runs `eggdb-fuzz TARGET [--seconds N] [--seed S]
  [--out DIR]` (60 seconds and a fixed seed by default).
- For its target it builds a corpus of 24 valid inputs:
  - `zstd`: frames from EggDB's own encoder, over mixed text and random bytes;
  - `lz4`: LZ4 frames from a new `compress_lz4_frame`;
  - `sqlite`: files from D631's writer;
  - `arrow`: streams from the Arrow writer.
- Until the deadline it picks a corpus input and applies one to nine random edits:
  - bit flips, interesting byte values, insertions and deletions;
  - truncation, duplicated slices, and splices with another input.

  It then decodes the result inside `catch_unwind`.
- Any panic is a finding. So is, for Zstandard, a frame that decodes but does not round-trip
  through the encoder again. A finding is written to `DIR` (`fuzz-findings` by default) and the
  run exits with status 1. A clean run prints its run count.
- The generator is a seeded xorshift, so a finding replays with the same `--seed`.
- `eggdb-storage` now exports `compress_zstd` and `compress_lz4_frame` beside the decoders D641
  made public.
- The LZ4 frame writer stores each 64 KiB block compressed or as it is, whichever is smaller.
- No CI job runs it yet: wiring a nightly or manual run of hours is a CI change for a session that
  builds. `parquet` (files from the Parquet writer) and `bson` (documents with nested documents and
  arrays, whose decoding must re-encode to an equal document) were added in the same batch. The
  wire protocols' frame readers are left.

**Status:** code written, unbuilt (code-only mode, D355).
