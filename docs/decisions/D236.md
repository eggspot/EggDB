## D236 Ledger tables are an extension: append-only rows chained by SHA-256, verified in SQL — Decided by the build loop (by judgement, 2026-10-31); refines D26 and D38

Track 4.X-8 asks for tamper-evident ledger tables, an RDF store with SPARQL, XML with
XQuery, OLAP cubes with MDX and DAX (after D34's legal check) and spreadsheet-style tables.
This slice does ledger tables.

- **`CREATE EXTENSION eggdb_ledger`, then `eggdb_ledger.protect(schema, table)`**, adds a
  sequence column and two hash columns to a table and two triggers. Inserts get
  `ledger_previous`, the hash of the table's last row, and `ledger_hash`, the SHA-256 of that
  previous hash and the row's own values (as JSON). Updates and deletes are refused (SQLSTATE
  `55000`). The chain's head is kept in `eggdb_ledger.chains` in the same transaction.
- **`eggdb_ledger.verify(schema, table)`** recomputes every row's hash and checks every link in
  one window query, returning how many rows are broken: a row changed behind the triggers'
  back (for example with triggers disabled), removed, or inserted out of order shows up there.
- **`sha256()` and `sha512()`** join SQL (PostgreSQL's names, returning `bytea`), and also take
  text as its UTF-8 bytes, which the ledger needs.
- Like D231's audit chain, a chain inside the database finds edits within it but not a complete
  rewrite by someone who owns the file. Publishing the chain's head outside (a digest in the
  audit log, a signed receipt) closes that and comes with ledger digests in backups.

Left: `TRUNCATE` and `DROP` refusal, digests published outside the database and checked against
backups, SQL Server's `WITH (LEDGER = ON)` syntax onto the same mechanism, protecting a table
that already has rows, and the rest of the track: RDF with SPARQL, XML with XQuery, OLAP with
MDX and DAX, and spreadsheet tables.
