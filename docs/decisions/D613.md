## D613 AMQP x-death headers — Decided by the code-only session (2026-11-12, D355); roadmap M16, D214, D516

D516 dead-letters rejected and expired messages but republished them unchanged. RabbitMQ adds an
`x-death` header, and retry patterns depend on it: a "retry three times, then park" consumer
reads `x-death[0].count`, and MassTransit and NServiceBus read the first-death headers to report
where a message failed.

- `field_table` can now write as well as read:
  - `encode_table` writes a field table, with integers as signed 64-bit (`l`), strings as long
    strings (`S`), and nested tables, arrays, timestamps, decimals, booleans, doubles and void
    each with its own tag.
  - `with_headers` rewrites a content header's properties with a new headers table, copying
    every other property byte for byte.
- `with_death` updates the headers as RabbitMQ does:
  - the `x-death` array's entry for the same queue and reason gets its `count` raised and moves
    to the front; otherwise a new entry goes first, with `count` 1, `reason`, `queue`, `time`
    (seconds), `exchange` and `routing-keys`;
  - `x-first-death-reason`, `-queue` and `-exchange` are set once;
  - `x-last-death-*` are replaced each time.
- The broker's `dead_letter` takes the reason: `rejected` for a `basic.reject` or `basic.nack`
  without requeue, `expired` for a message past its TTL. The republished message carries the new
  headers, and the dead-letter exchange routes on them, so a headers exchange can route on
  `x-first-death-reason`.
- A unit test checks the count rising on a second rejection from the same queue, a second entry
  for another queue and reason, the first and last death headers, and a property after the
  headers (the delivery mode) surviving the rewrite.
