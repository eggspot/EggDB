## D1266 Functions the program defines, in the C API and the Python driver — Decided by the code-only session (2026-11-18, D355); roadmap M6 drivers (D16, D957)

- **What users get.** A program using the C API defines scalar SQL functions of its own on an embedded session with `eggdb_sql_create_function`, and sets each call's answer with `eggdb_function_result_null`, `_int64`, `_double`, `_text`, `_blob` or `_error`, as SQLite's `sqlite3_create_function` and `sqlite3_result_*` work. The Python driver's `Connection.create_function(name, narg, func, *, deterministic=False)` matches `sqlite3.Connection.create_function`: values arrive and return as `None`, `int`, `float`, `str` or `bytes`, an exception fails the statement with its message, and `func=None` removes the function. It is the first piece Django's backend needs (Django's SQLite backend defines its date, time and math functions this way).
- **How.** The engine already calls functions a program defines (`NativeFunctions`, D1242's `libsqlite3`): an embedded C API session now keeps its own set and runs each statement, prepared statement and `COPY` with it active. The callback gets the arguments as `eggdb_value`s with text NUL-terminated, valid during the call; the answer is copied before the call returns, so a caller's buffers (Python's among them) need not outlive it. `destroy` runs once when the definition is replaced, removed or the session closes. A server session refuses definitions with `EGGDB_ERR_INVALID_ARGUMENT`, since the server runs its own functions.
- **Left.** Aggregate functions (`create_aggregate`), collations, and the Django backend itself.
- **Proof.** The C API test defines a function that doubles numbers and text, calls it in a query and a prepared statement, sees its error fail a statement, refuses an empty name and counts one `destroy` at close; the header test checks the new declarations; the Python test defines, calls, fails and removes a function.

**Status:** code written, unbuilt (code-only mode, D355).
