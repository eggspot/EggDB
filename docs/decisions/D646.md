## D646 MySQL BIGINT UNSIGNED, YEAR, BIT, ENUM and SET columns on the nearest stored type — Decided by the code-only session (2026-11-12, D355); roadmap M10, D19

Laravel's `$table->id()` creates `BIGINT UNSIGNED AUTO_INCREMENT`, Rails and Django create
`ENUM`-like columns, Hibernate maps booleans to `BIT(1)`, and dumps of real MySQL schemas use
`YEAR`, `ENUM` and `SET` freely. EggDB refused every such `CREATE TABLE`, so those migrations
stopped at their first table.

- `BIGINT UNSIGNED` is kept as a signed 64-bit `BIGINT`, as the smaller unsigned integers already
  widen. Identifiers stay below 2^63 in practice, and a larger value is an out-of-range error
  rather than a silent wrap.
- `YEAR` and `YEAR(4)` are `SMALLINT`. `YEAR(2)` is MySQL's error 1818.
- `BIT(1)` (and `BIT`) is `BOOLEAN`, as MySQL clients treat it, and `BIT(2..64)` is `BIGINT`.
  A wider `BIT` is error 1439.
- `ENUM('a', ...)` is `VARCHAR` as long as its longest member. `SET('a', ...)` is `VARCHAR` as
  long as all its members joined by commas. Both take `CHARACTER SET` and `COLLATE` after the
  list.
- The values are stored and compared as these types. Several MySQL rules are left:
  - `ENUM` member checks and index-order sorting;
  - `SET` member checks and member order;
  - `YEAR`'s 1901–2155 range and two-digit years;
  - unsigned ranges;
  - `b'...'` bit literals.

  The spatial types stay refused.
