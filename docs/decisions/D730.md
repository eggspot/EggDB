## D730 CQL collections and tuples — Decided by the code-only session (2026-11-12, D355); roadmap M16, CQL collections, tuples, user-defined types and counters (D19, D218)

- Columns may be `list<T>`, `set<T>`, `map<K, V>` and `tuple<A, B, ...>`, nested and with `frozen<...>` accepted
  (frozen and non-frozen behave alike). Their types are kept in the table's CQL metadata in CQL's spelling.
- A collection column is stored as text holding JSON: a list or set as an array (a set sorted and without repeats),
  a map as an array of `[key, value]` pairs sorted by key, a tuple as an array with `null` for a missing item;
  items keep the text forms CQL values take. Sorting is numeric for numbers and by text otherwise.
- Values come as literals (`[1, 2]`, `{'a', 'b'}`, `{'k': 1}`, `{}`, `(1, 'x')`) or bound in CQL's binary form,
  and go back in CQL's binary form, with result and prepared metadata carrying the full type (list `0x0020`, map
  `0x0021`, set `0x0022`, tuple `0x0031` with their item types).
- `UPDATE ... SET l = l + [x]` appends to a list. Adding to sets and maps, removing items, setting a map key or a
  list index, `CONTAINS` and `CONTAINS KEY`, and bind markers inside collection literals are refused as not
  supported yet. User-defined types are still left.
- Collection types are interned once per process (at most 4,096 distinct ones) so CQL types stay plain values.
