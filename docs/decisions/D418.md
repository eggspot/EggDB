## D418 MySQL stored programs: handlers, cursors, named conditions, `RESIGNAL` and `GET DIAGNOSTICS` — Decided by the code-only session (2026-11-11, D355); roadmap M10

MySQL routines keep compiling into the routine interpreter's program (D199); the compiler
(`parser/mysql_routines.rs`, new `parser/mysql_routines/handlers.rs`) now takes:

- **Handlers.** `DECLARE CONTINUE | EXIT HANDLER FOR condition[, ...] statement`, where a
  condition is a MySQL error number, `SQLSTATE [VALUE] 'xxxxx'`, a named condition,
  `SQLEXCEPTION`, `SQLWARNING` or `NOT FOUND`. The interpreter's handlers exit their block, so a
  MySQL handler is compiled by guarding each statement: every statement of a block that has
  handlers in scope (its own block's and every enclosing block's) runs inside an internal block
  whose exception handlers are those handlers, innermost block first and, within a block, error
  numbers before SQLSTATEs before the classes (MySQL's precedence). A `CONTINUE` handler's body
  runs and execution goes on after the failed statement; an `EXIT` handler's body runs and then
  leaves the block that declared it (every block now carries a label, generated when none is
  written). Only the failed statement is undone, as MySQL does. A handler's body is compiled
  without its own block's handlers, so an error in it goes to the enclosing blocks, as in MySQL.
  `UNDO` handlers are refused (MySQL doesn't support them either), and two handlers for one
  condition in a block are error 1413.
- **Conditions.** New `ExceptionCondition` kinds match a MySQL error number or SQLSTATE through
  `mysql_errors::translate` (the error as a MySQL client would see it), and `SQLEXCEPTION`,
  `SQLWARNING` and `NOT FOUND` by class. `DECLARE name CONDITION FOR SQLSTATE '...' | number`
  names one for handlers and for `SIGNAL`/`RESIGNAL` (a condition named by number can't be
  signalled: error 1645). An unknown name is error 1319.
- **Cursors.** `DECLARE c CURSOR FOR select`, `OPEN c`, `FETCH [[NEXT] FROM] c INTO v[, ...]` and
  `CLOSE c` use the interpreter's cursors. A `FETCH` past the last row raises SQLSTATE `02000`
  ("No data - zero rows fetched, selected, or processed"), which `NOT FOUND` and error number
  1329 catch, so the usual `CONTINUE HANDLER FOR NOT FOUND SET done = TRUE` loop works.
- **`RESIGNAL`** only inside a handler (else error 1645, SQLSTATE `0K000`): bare, it re-raises the
  handled error; with `SET MESSAGE_TEXT` and no SQLSTATE it raises the handled SQLSTATE with the
  new message; with a SQLSTATE or condition name it raises that. `SIGNAL` takes a condition name.
- **`GET [CURRENT | STACKED] DIAGNOSTICS`**: `NUMBER` (1 inside a handler, else 0) and
  `ROW_COUNT`, and `CONDITION 1` with `MESSAGE_TEXT`, `RETURNED_SQLSTATE` and `MYSQL_ERRNO` (both
  as MySQL reports them), the schema, table, column and constraint names, and MySQL's constant
  items (`CLASS_ORIGIN` is `ISO 9075`, `CATALOG_NAME` `def`). Targets are local variables or user
  variables (`@x`), the latter through a hidden local and a `SET @x = ...` statement.
- Left: `SET MYSQL_ERRNO` in `SIGNAL` is still ignored, condition numbers other than 1, warnings
  (EggDB raises none in routines, so `SQLWARNING` handlers never run), and the cost of the
  guarding block per statement, which the build pass should measure on a loop-heavy procedure.
