## D920 HTTPS in the shared HTTP client — Decided by the code-only session (2026-11-12, D355); roadmap M18, follow-up of D226, D913 and D915

- `eggdb_http::parse_http_url` now reads `https://` URLs too (port 443 by default), and `HttpTarget` says whether a
  target is TLS. `eggdb_http::request` and `post` run TLS on such targets with EggDB's own TLS client (`eggdb-tls`),
  checking the server's certificate chain and name against the roots in the PEM file `SSL_CERT_FILE` names, or the
  system's bundle (`/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/cert.pem`,
  `/usr/local/etc/openssl/cert.pem`); with none, the request fails and says to set `SSL_CERT_FILE`. The `Host`
  header leaves out the scheme's default port.
- Everything built on the client gains HTTPS without changes of its own: S3-compatible archives and edge copies
  (`AWS_ENDPOINT_URL` may be `https://`), and `http(s)://` foreign sources (D915), whose allow-list entries now also
  match on the scheme, so an `http://` entry does not allow an `https://` source or the reverse.
- The CLI's own HTTPS posting for report delivery and webhooks (D747) stays as it is; folding it into the shared
  client is a later cleanup.
