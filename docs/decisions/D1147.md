## D1147 PostgreSQL's regression suite run from outside the repo — Decided by the code-only session (2026-11-14, D355); roadmap M6a (conformance suites per protocol and dialect, D10, D45)

- `scripts/pg-regress.sh <eggdb> <src/test/regress> <work dir> <rates file>` starts `eggdb serve` on its own port,
  runs every test named in `parallel_schedule` through `psql -X -a -q` (the way `pg_regress` runs them, with the
  `PG_ABS_SRCDIR`-style variables set) and compares the output with `expected/<name>.out` or any of its
  `<name>_<n>.out` alternatives. It writes `pass <name>` or `fail <name>` per test and a last summary line, and fails
  below the minimum.
- The suite is PostgreSQL's own test data, fetched in the workflow by a sparse clone of `REL_17_STABLE`'s
  `src/test/regress`; nothing of it is kept in the repository or shipped (D1). The tests run one after another
  against one database rather than in `pg_regress`'s parallel groups, so a failure in one test can only change the
  outcome of the tests that read its tables, as it does upstream.
- The minimum is the `pg_regress minimum_pass_percent` line of `benchmarks/conformance.txt` (0 until the first run),
  overridable by the workflow input or the `PG_REGRESS_MINIMUM` variable, the same way as the sqllogictest and
  MySQL test suite minimums. It is raised to the measured rate rounded down after each run that improves it.
- The `PostgreSQL regression suite` workflow runs weekly (Saturday, with the performance pass) and on demand; it
  publishes the rate in the run summary and the per-test results and outputs as an artifact for 30 days. It is not
  part of `check`, so a lower rate never blocks a PR.
