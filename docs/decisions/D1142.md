## D1142 A correlated row IN subquery looked up by key — Decided by the code-only session (2026-11-14, D355); roadmap M5 (D112, D155, D323)

- **Before.** A correlated subquery whose only links to the outer row are `inner = outer` equalities runs once and is
  looked up by those values (D112, D155), but only with a single compared value. `(a, b) IN (SELECT x, y ... WHERE
  inner.k = outer.k)`, and `= ANY` and `<> ALL` with a row on the left (D323), ran the subquery again for every
  distinct outer value.
- **Now.** A fourth lookup shape, row members, keeps the compared row's width. The key query selects the correlation
  keys followed by every item of the subquery's select list, once, with `DISTINCT`. Each group keeps its rows as
  anonymous records, the form the uncorrelated row comparison already reads (`records::anonymous`). The probe hands
  each outer row its group, so `IN`, `NOT IN`, `= ANY` and `<> ALL` compare, with SQL's NULL rules, exactly as before.
- **The same limits as the single-value lookups.** No `LIMIT`, `OFFSET`, `ORDER BY`, grouping or aggregates in the
  subquery. Its select items name no outer column and hold no subquery, and the items match the row's width (a
  mismatch keeps its `42601`-family error from the normal path). Anything else still runs per outer value.
