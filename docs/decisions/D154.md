## D154 `COPY`'s binary format on one PostgreSQL binary codec in `eggdb-sql`, `ON_ERROR ignore` for type-input errors only, `COPY FROM ... WHERE` after defaults, and client encodings converted at the channel — Decided by the build loop (by judgement and the PostgreSQL manual's COPY page, 2026-10-30); applies D1, D9, D10, D117; supersedes in part D117

D117 left four parts of PostgreSQL's `COPY` as `0A000`: the binary format, `ON_ERROR ignore`,
`COPY ... WHERE` and encodings other than UTF-8. All four are written from the PostgreSQL
manual's COPY page (its "Binary Format" section and the option list) and the protocol chapter
(D1).

**One binary codec, in the SQL core.** The binary form of each type (big-endian integers and
floats, `numeric` in base 10,000, dates and time stamps from 2000-01-01, `timetz`, `interval`,
`uuid`, `jsonb` with its version byte, one-dimensional arrays with their header) already lived
in `eggdb-pgwire` for binary parameters and results. `COPY (FORMAT binary)` needs the same forms
inside the SQL core, which never depends on a protocol (D3, D8), so the codec moved to
`eggdb_sql::encode_pg_binary` and `eggdb_sql::decode_pg_binary_text` (module `pg_binary`), and
`eggdb-pgwire` calls them; keeping a second copy in the copy module was rejected as duplicate
code that would drift. A binary field read by `COPY` becomes its text form and then goes through
its column type's text input, exactly as a text-format field does, so typmods, domains, defaults
and constraints behave the same in every format at the cost of one formatting step per value;
arrays and enums are converted directly. The file layout follows the manual: the signature, a
flags word whose bit 16 (OIDs) and other critical bits are refused, a header extension that is
skipped in pieces (never buffered whole), per row a field count that must equal the columns
and each field's length (`-1` NULL), a `-1` trailer after which more data is an error, and
data that ends at a row boundary without the trailer is accepted as PostgreSQL does; a row
that ends part way through is `22P04` (PostgreSQL ends quietly on a cut count; refusing is the
safer reading, D9). A row is at most 1 GiB, as a text line (D117). `COPY TO` sends the header
with the first row and the trailer in its own `CopyData`, as PostgreSQL does, and both copy
responses carry binary format codes. Composite and range columns and multidimensional arrays
are `0A000` until their binary forms are written. A script's inline data cannot be binary
(`0A000`): scripts are text.

**`ON_ERROR ignore` skips only type-input errors.** As in PostgreSQL 17, a row is skipped when a
value's input or its column's typmod refuses it, which in EggDB is any class `22` error of the
field conversion except bytes invalid in the encoding (`22021`, `22P05`), which PostgreSQL also
treats as hard. Format errors, constraint violations and domain checks (run with the row's
constraints in EggDB, D152) still fail the copy. `COPY n` counts the loaded rows; the notices
are PostgreSQL 17's text (`N rows were skipped due to data type incompatibility`, and per row
with `LOG_VERBOSITY verbose`), with PostgreSQL 18's `silent` accepted. The binary format refuses
`ignore`, as PostgreSQL does. `REJECT_LIMIT` (PostgreSQL 18) is left for later.

**`WHERE` is tested after the row's defaults.** As PostgreSQL does, each row is built (defaults
and `serial` values included, so a filtered row still uses a sequence value), then the condition
is evaluated with the table as its only scope, then the row is stored. The condition is checked
before any data is read: aggregates `42803`, window functions `42P20`, subqueries `0A000`,
unknown columns `42703`; `COPY TO ... WHERE` is `0A000` with PostgreSQL's message.

**Encodings are converted at the channel.** `ENCODING` describes the client's bytes. A
converting `CopyChannel` wraps the client's: on the way in it turns each piece into UTF-8
before the record reader sees it, so the reader, its limits and its line counts stay those of
D117 for every encoding; on the way out it converts each row. `LATIN1`, `LATIN9` and `WIN1252`
use their published tables; `UTF16` (with byte-order-mark detection, little-endian without one,
as Windows tools write it), `UTF16LE` and `UTF16BE` are EggDB's own additions, since PostgreSQL
has no UTF-16 encoding but spreadsheets and `bcp -w` export it. Names are matched as PostgreSQL
matches them (letters and digits only, any case); PostgreSQL's other encodings are `0A000`, an
unknown name `22023`. Data a script carries inline was decoded with the script, so `ENCODING`
does not apply to it.
