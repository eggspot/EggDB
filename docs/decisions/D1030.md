## D1030 Change capture without triggers — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D28, D210)

- `eggdb serve --cdc-capture engine` turns on capture in the engine (`Database::capture_rows`): a write
  transaction reads each SQL row key's stored bytes the first time it touches the key, and its commit writes one
  capture record (`\xffCOL\x00\x7fcapture\x00` and a sequence) holding every row it changed with the bytes before and
  after, in the same commit. Capture is therefore exactly the committed changes, in commit order, for every table,
  with no trigger, and costs nothing when off (D6).
- `eggdb_sql::cdc::deliver_captured_changes` reads the records in order, decodes each row with its table's current
  definition into Debezium-style events with full `before` and `after` rows (like PostgreSQL's `REPLICA IDENTITY
  FULL`), hands them to the same sinks as the trigger outbox (webhook, Kafka topic, queue, D210 and D527), and
  removes a record only once its every event was accepted: at least once, never out of order. `op` is `c`, `u` or
  `d` from whether the row existed before and after the commit; the `eggdb_cdc` schema's own tables are never sent.
- **Transaction metadata.** Each capture record is one transaction, so every event carries Debezium's
  `transaction` block: the record's sequence as `id`, the event's place in the transaction as `total_order`, and its
  place among the transaction's events for the same table as `data_collection_order`.
- Engine capture needs a sink (`--cdc-webhook`, `--cdc-topic` or `--cdc-queue`), else the records would only pile
  up; trigger capture (`CREATE EXTENSION eggdb_cdc`) stays the default and still works beside it.
- Left: decoding a row whose table changed shape since the commit with the definition it had then (the current one
  is used), and the retry and dead-letter handling of the outbox (D528) for captured records.
