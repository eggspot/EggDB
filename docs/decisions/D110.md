## D110 v0.2.0 scope: bring PostgreSQL, SQL Server and Oracle databases into EggDB — Decided (owner, 2026-10-27); applies D2, D10, D12, D13, D22

EggDB is one engine, its own (D2): it never runs, embeds, wraps or proxies another database
engine. A user brings a PostgreSQL, SQL Server or Oracle database over by restoring the dump or
script that database's own tools produce (D13): `pg_dump`'s plain format; SQL Server
Management Studio's Generate Scripts and `sqlpackage` scripts; Oracle `impdp ... SQLFILE=` and
SQLcl exports; and CSV from any of them. After the restore it is ordinary EggDB data that every
dialect and protocol reads. Oracle applications run their SQL unchanged through PostgreSQL or TDS
drivers with the Oracle dialect selected; there is no Oracle wire protocol (D10).

CI's test oracle is the official `postgres` container only: no SQL Server or Oracle containers.
SQL Server's and Oracle's behaviour is checked against Microsoft's and Oracle's documentation.
This release copies nothing from a live server, because EggDB has no TLS yet (D22).

The honest limits of v0.2.0: stored procedures, functions and triggers are not run; no roles or
`GRANT`; one database per file; one writer; listeners on loopback only; and no SQL Server `.bak`,
BACPAC or `.mdf` files, Oracle Data Pump files or PostgreSQL data directories. The roadmap holds
the work order and its items.
