## D1021 Instant snapshots, copy-on-write clones and branches — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D24, D28)

- `Database::clone_to` and `eggdb backup <file> <copy> --clone` clone the whole file copy-on-write where the file
  system can: APFS's `clonefile` on Apple systems and the `FICLONE` ioctl on Linux file systems with shared extents
  (Btrfs, XFS, bcachefs), declared in the platform layer (D8) from the systems' documentation. The clone takes no
  time and no space until either file changes, which makes it the instant snapshot and the branch D28 asks for: a
  database of its own from that commit on, for development, tests and trial migrations.
- The clone is taken between commits: the write transaction waits while the file is cloned, after a sync, so the
  clone holds whole commits and its log; opening it replays the log as after a stop. Readers never wait.
- On Windows the clone uses ReFS block cloning (`FSCTL_DUPLICATE_EXTENTS_TO_FILE`) over cluster-aligned ranges of at
  most 2 GiB, when the volume supports block reference counting and the file is neither sparse nor under integrity
  streams.
- Where the file system cannot clone (`EXDEV`, `ENOTSUP`, `EOPNOTSUPP`, `EINVAL`, `ENOTTY`, or a ReFS request that
  fails), on other platforms, for databases in memory and for
  encrypted files, `clone_to` writes an ordinary copy with `backup_to` and says so (`instant: false`). Encrypted
  files are never cloned block for block: the clone and the original would then encrypt different pages under the
  same file identity and key, reusing counter-mode keystream once both change.
- `--clone` also applies to copies archived into a directory, which are still verified by reading every page.
