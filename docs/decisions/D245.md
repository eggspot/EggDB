## D245 FF1 tokens, Laplace noise and k-anonymity as SQL functions — Decided by the build loop (by judgement, 2026-10-31); refines D23 and D52

Track 4.X-17 asks for Delta Sharing, zero-copy sharing with entitlements, marketplace listings,
clean-room output policies, private set intersection, differential privacy, k-anonymity,
tokenization and format-preserving encryption, blind indexes, synthetic data and masked copies.
This slice does the privacy building blocks.

- **FF1 in `eggdb-crypto`.** `Ff1` implements NIST SP 800-38G Rev. 1 over our AES and passes all
  nine NIST samples (AES-128, 192 and 256; radix 10 and 36; with and without tweaks). Halves are
  kept in `u128`, so a half is at most 120 bits (72 decimal digits in all), and the domain must
  be at least a million values, as Rev. 1 requires. FF3-1 is not implemented, since NIST is
  withdrawing FF3. This is cryptography, so it takes D35's security review.
- **`ff1_encrypt` and `ff1_decrypt` in SQL** take the value, the key and the tweak as `bytea`
  and an optional radix up to 36 over `0-9a-z`. The key comes from the caller (a parameter or
  the key management of D23), never from a table the function reads.
- **Differential privacy starts with `laplace_noise`**, drawn from the same CSPRNG as
  `gen_random_uuid()`. Floating-point Laplace sampling leaks through its rounding (Mironov,
  2012); the snapping mechanism replaces it before query-level privacy budgets are built on it.
- **`CREATE EXTENSION eggdb_privacy`** adds `k_anonymity(schema, table, columns)`, which quotes
  each column name and returns the smallest equivalence class.
