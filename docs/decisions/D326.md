## D326 PostgreSQL's privilege inquiry functions, the standard's privilege views, `FORCE ROW LEVEL SECURITY`, `pg_policy` and `pg_policies`, answered from the grant model the engine enforces — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M6b, extends D183, D186 and D285, applies D9, D12 and D20; security-critical (D35)

D183 stored roles and table grants, D186 row security and D285 column grants, but the catalog
still answered as if every user held every privilege: `has_table_privilege` and its siblings
were always true, `pg_policy` was empty, `relrowsecurity` was always false, and
`information_schema.column_privileges` listed every grant to everyone. pgAdmin, DBeaver,
DataGrip, psql's `\dp` and `\d`, Django's and Rails' multi-tenant checks and AI agents ask these
before they show a menu or run a statement, so a wrong answer either hides what a role may do or
invites statements that fail. Built from PostgreSQL's manual: "Access Privilege Inquiry
Functions" (functions-info), "Privileges" (ddl-priv), `ALTER TABLE` (sql-altertable),
`pg_policies` (view-pg-policies) and the `information_schema` chapters on `table_privileges`,
`column_privileges`, `role_table_grants`, `role_column_grants` and `usage_privileges`.

- **One set of rules.** The statement checks (`roles::check_table`, `roles::column_reach`, the
  refusal of definitions to checked roles) are now thin wrappers over
  `roles::holds_table_privilege`, `roles::column_privilege_reach` and
  `roles::may_define_objects`, which take the checked role as an argument. The catalog snapshot
  of a statement keeps a copy of the access records (key spaces `0x11` roles, `0x12` table
  grants, `0x13` policies, `0x14` row-security switches, `0x16` column grants) as
  `roles::AccessRecords`, which reads like the store, so the inquiry functions, the views and
  `pg_class` call the very functions statements are checked with, over the same records the
  statement sees (its own uncommitted grants included). There is no second copy of the rules.
- **Inquiry functions.** `has_table_privilege`, `has_column_privilege`,
  `has_any_column_privilege`, `has_sequence_privilege`, `has_schema_privilege`,
  `has_database_privilege`, `has_function_privilege` and `pg_has_role`, each with and without the
  leading role argument (`has_column_privilege` with three or four), the role by name, by OID or
  as `public`, the object by name (unquoted parts folded to lower case, as `regclass` input) or
  OID, the column by name (taken literally) or number. The privilege list is PostgreSQL's:
  names separated by commas, white space around each ignored, any case, each optionally
  followed by exactly ` WITH GRANT OPTION` (and ` WITH ADMIN OPTION` for `pg_has_role`); the
  answer is true when any listed privilege is held. Errors are PostgreSQL's and come in its
  order (role, then object name, then privilege list): `42704 role "x" does not exist`, `42P01`,
  `42703 column "c" of relation "t" does not exist`, `3F000`, `3D000`, `42883`, `42809 "t" is
  not a sequence`, `22P02 expected a left parenthesis` for a function without its argument list,
  and `22023 unrecognized privilege type: "x"`. An object named by an OID that does not exist
  gives NULL, any NULL argument gives NULL, and a role OID that names no role holds only what
  `PUBLIC` holds.
- **What each answer means.** A superuser (the session's own unchecked user, or a stored role
  with `SUPERUSER`) holds everything, grant options included. A checked role holds table and
  column privileges by its grants, the grants of the roles it belongs to and `PUBLIC`'s; `SELECT`
  on catalog relations; nothing on indexes; never `MAINTAIN` (only superusers run `ANALYZE`),
  never `RULE` (always false on PostgreSQL too) and never a grant option, since EggDB stores none
  and only superusers grant. Schemas: `USAGE` on every schema (names are not checked against
  schema privileges), `CREATE` for superusers only. Databases: `CONNECT` to the current one,
  `CREATE` and `TEMPORARY` for superusers only; another served database keeps its own roles, so
  a checked role is answered false there rather than guessed. Sequences: `SELECT` by the table
  grants, as `SELECT * FROM seq` is checked; `USAGE` and `UPDATE` for every role, since
  `nextval`, `currval` and `setval` are not checked yet. Functions: `EXECUTE` for every role, as
  routine calls are not checked (PostgreSQL grants `EXECUTE` to `PUBLIC` by default). A function
  named by text exists when `pg_proc` lists it with that many arguments. `pg_has_role` is true
  when the role is the member itself or one it belongs to, to 32 levels.
- **Privilege views.** `information_schema.table_privileges` (one row per table grant and
  privilege, `with_hierarchy` YES for `SELECT`), `role_table_grants`, `column_privileges` (now
  filtered), `role_column_grants` and `usage_privileges`. As the standard and PostgreSQL select
  them, a row is shown when its grantee is the current user, a role it belongs to, or `PUBLIC`
  (the `role_*` views leave `PUBLIC` out); a superuser session is the grantor of every grant, so
  it sees them all. A role that fails to read its memberships sees no role's grants (fail
  closed). `usage_privileges` lists `PUBLIC`'s `USAGE` on every domain and sequence, which every
  role has.
- **`FORCE ROW LEVEL SECURITY`.** `ALTER TABLE [ONLY] t FORCE ROW LEVEL SECURITY` and `NO FORCE
  ROW LEVEL SECURITY` replace the old `0A000`. The flag is bit 2 of D186's switch record
  (`[1, flags]`, bit 1 is `ENABLE`), which is kept when row security is disabled and enabled
  again, and the record is deleted only when no bit is left. `NO FORCE` is a destructive
  statement for agents (`DestructiveKind::NoForceRowSecurity`), like `DISABLE`. Only superusers
  run either. `pg_class.relrowsecurity`, `relforcerowsecurity` and `pg_tables.rowsecurity` now
  show the switches.
- **`pg_policy` and `pg_policies`.** One row per policy: `polcmd` (`*`, `r`, `a`, `w`, `d`),
  `polpermissive`, `polroles` (0 for `PUBLIC`, the session user as 10, others by their role
  OID), and `polqual` and `polwithcheck` holding the condition as `pg_get_expr` returns it, which
  is PostgreSQL's deparsed form in parentheses where the deparser of defaults and checks knows
  every construct, and the written text otherwise. `pg_policies` is PostgreSQL's view over it:
  `permissive` as `PERMISSIVE` or `RESTRICTIVE`, `roles` as `{public}` or the sorted role names,
  `cmd` as `ALL`, `SELECT` and so on. Policy OIDs are hashed in their own OID space.

Decided by research (from PostgreSQL's documentation and the repo's decisions):
- **Who owns a table.** There are no object owners yet (D183): only superusers create objects.
  The catalog keeps D183's convention that OID 10 is the session's user, so `relowner`, the first
  item of `relacl` and the grantor of every grant show the session's user. The privilege
  inquiry functions do not follow that convention: they answer from the grants, so a checked role
  is never told it holds the owner's privileges. The views filter on the grantee alone for a
  checked role (it can never be a grantor), so the displayed grantor never widens what it sees.
- **`relacl`, `attacl`, `pg_policy` and `pg_policies` stay readable by every role**, as on
  PostgreSQL, whose `pg_class`, `pg_attribute` and `pg_policy` are readable by `PUBLIC`; EggDB
  already listed every relation and its `relacl` to every role. Only the `information_schema`
  views, which the standard filters, are filtered. Hiding the catalog's ACLs would break psql's
  `\dp` and pgAdmin's privilege pages for no protection a role does not already lack on
  PostgreSQL.
- **`FORCE` takes effect with owners.** PostgreSQL's `FORCE` subjects the table's owner to its
  policies, but never a superuser or a `BYPASSRLS` role. Every owner is a superuser until object
  owners land, so forcing changes no row a statement sees today; the flag is stored, shown and
  dumped so that restoring a `pg_dump` keeps it, and applies once a non-superuser can own a
  table.
- **The flag is a new bit, not a new record version.** A release before this one reads the
  switch as `flags & ENABLE`, so it keeps applying row security to a table that is forced
  (forcing has no effect it could miss, see above); a new record version would make that release
  read the switch as absent and stop applying row security, which fails open. A damaged switch
  record now fails `ALTER TABLE ... ROW LEVEL SECURITY` instead of being overwritten.
- **`aclexplode` is left out**: it returns records, which EggDB's set-returning functions only
  produce for JSON so far; tools read `relacl` text and the `information_schema` views instead.

Security review: the inquiry functions only read; every answer for a checked role comes from
`holds_table_privilege`, `column_privilege_reach` or `may_define_objects`, the functions the
statements use, so a role is told true only where its statement would pass (and false for grant
options, `MAINTAIN` and other databases, where the engine refuses or cannot tell). Damaged grant
or role records fail the inquiry as they fail the statement. The privilege views never show a
grant to a role the viewer is not, and does not belong to; a damaged membership shows none. The
privilege-list parser works on string slices with `get` (no indexing or byte splitting that can
panic) and is checked by a randomized test over multibyte and NUL input. `FORCE` cannot weaken
row security for any role, and changing it needs a superuser.
