## D1051 Resumable large migrations: range digests and parallel ranges — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D58, D251)

- D251's `eggdb_migration` copied one table in key-order batches and compared it row by row. For tables too large for
  one worker it gains ranges:
  - `split_ranges(job, schema, table, key, pieces)` cuts the source's keys into ranges of about equal row counts
    (`ntile` over the key) in `eggdb_migration.ranges`; the first range is open below and the last open above, so keys
    the source gains outside the sampled ones still fall in a range;
  - `claim_range(job, worker)` gives the next unclaimed range to one worker through a conditional update, so any number
    of workers, in sessions on any server that reaches the job's database, never copy the same range;
  - `copy_range_batch(job, piece, ...)` copies the next rows of one range after the largest key the target already
    holds inside it: each range is resumable on its own, with the target as its checkpoint (D251's rule), and is
    marked done when a batch copies nothing.
- **Range digests.** `range_digest` is the row count and an MD5 over the range's rows (`to_jsonb`, in key order).
  `compare_ranges` computes it on both sides for every range and lists only those that differ; `compare_range` then
  compares one range row by row. Equal ranges are read once each for the digest and never compared in detail. This is
  one level of the Merkle idea D225 uses for anti-entropy; ranges are cut by key rather than by hash so a range is
  also the unit a worker copies, and a differing range can be split again with a finer `split_ranges` job over it.
- Range bounds are kept as text and compared as literals, so they take the key column's type in each query; every
  value reaches the dynamic SQL through `%L` and `%I`, and the range predicate through `%s`, never by pasting text
  into a format string.
- Digests compare like with like: both sides are tables EggDB reads (local, or through `eggdb_foreign`, D229). Pushing
  the digest down to a remote engine would need both engines to print rows identically, which differs between
  products.
- Learned from the descriptions of chunked table checksums in pt-table-checksum's documentation and of range-based
  anti-entropy; no code was read.
