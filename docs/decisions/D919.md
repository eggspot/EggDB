## D919 Immutable (WORM) backups through S3 Object Lock — Decided by the code-only session (2026-11-12, D355); roadmap M14, D53, follow-up of D226

- `eggdb backup <file> s3://bucket[/prefix] --lock-days <n>` stores the archived copy under S3 Object Lock in
  compliance mode until `n` days after it was taken (1 to 36,500): the PUT carries `x-amz-object-lock-mode:
  COMPLIANCE`, `x-amz-object-lock-retain-until-date` and the `Content-MD5` S3 requires with a lock, all signed with
  SigV4. Until that time nobody, the account's root user included, can delete or overwrite that object version, so
  ransomware holding the keys cannot destroy the backups. The bucket must have been created with Object Lock (and so
  versioning) enabled; otherwise the PUT fails and the backup reports the bucket's error.
- The manifest line records `locked_until`. The manifest itself is rewritten at every backup and is not locked; if it
  is destroyed, the locked copies remain and can be listed and restored by name.
- `--lock-days` with a local file or directory is refused: no portable file system offers a lock an administrator
  cannot lift.
- `eggdb_s3::client::Bucket::put_locked` is the client call; the S3 server EggDB serves does not enforce Object Lock
  yet (it waits for D58's legal check with the rest of the S3 API).
