## D1132 SQL's tables seen as a collection named `sql` — Decided by the code-only session (2026-11-14, D355); roadmap M4 (SQL tables kept in their own collection, D139)

- **What users get.** `collection_names()` lists `sql` once SQL has stored anything, and `collection("sql")` reads
  SQL's catalog and tables like any collection: get, scan and counts, through the C API, the drivers, the shell and
  the MCP key tools. That puts SQL beside the other collections, as D139 planned.
- **Written only by SQL.** Opening it for writing, creating, dropping it or renaming another collection to `sql`
  fails with `ReservedKey`, since a key written beside SQL's catalog could break it. A database that already has a
  collection a user named `sql` before this release keeps it: the real collection wins, and nothing about it changes.
- **Why a view rather than a move.** SQL's keys already live under their own reserved prefix
  (`RESERVED_KEY_PREFIX`, `0xff 'S' 'Q' 'L' 0x00`). Moving them under the collection prefix would rewrite every SQL
  key of every existing file. It would also change the row prefixes that LSM tables (D1119), change capture and
  replication name, and every SQL access would pay a key translation. The view gives the API D139 asked for at no
  cost. The physical move is left for when the catalog tree (M2) gives collections trees of their own, when it
  becomes a tree assignment rather than a rewrite.

**Status:** code written, unbuilt (code-only mode, D355).
