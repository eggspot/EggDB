## D1211 The text search objects in pg_catalog — Decided by the code-only session (2026-11-17, D355); roadmap M8, synonyms, stop words and text search configurations (D30, D983)

- **What users get.** `pg_ts_config`, `pg_ts_dict`, `pg_ts_parser`, `pg_ts_template` and a new `pg_ts_config_map` list the built-in configurations (`simple`, `english` and the other 17 languages), their dictionaries (`simple` and one `<language>_stem` per stemming language) and the configurations and dictionaries a database defines with `CREATE TEXT SEARCH`, so psql's `\dF`, `\dFd`, `\dFp` and `\dFt` and tools that read these catalogs show them.
- **How.** `text_search_catalog::Catalog::entries` lists the built-in and stored objects and every mapping in order; the catalog snapshot loads it beside the access records. Built-in objects sit in `pg_catalog` with fixed OIDs (configurations from 13100, dictionaries from 13200, by the order of `BUILT_IN_CONFIGURATIONS`); defined ones sit in `public` with OIDs from an FNV-1a hash of the name in their own high range, so an OID stays the same across sessions without a stored counter. The one parser is PostgreSQL's `default` (3722); the templates keep PostgreSQL's OIDs (`simple` 3727, `ispell` 3730, `synonym` 3733, `thesaurus` 3740), with `snowball` at 13000. `maptokentype` is the token type's position in `eggdb_search::TOKEN_TYPES`, counted from 1, as `ts_token_type` numbers them.
- **Left.** Dictionary options (`dictinitoption`), owners other than the session user, and a hash collision between two defined names, which gives both the same OID.
- **Proof.** A unit test in `text_search_catalog.rs` checks the built-in configurations, the `english_stem` dictionary and the `english` mapping of `asciiword`.
