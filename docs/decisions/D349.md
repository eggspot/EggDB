## D349 MongoDB positional updates (`$`, `$[]`, `$[<identifier>]` with `arrayFilters`) and pipeline-style updates in `update` and `findAndModify`, with MongoDB's error codes — Decided by the build loop (batch 6, 2026-11-10); roadmap M9, extends D197, applies D9

D197 refused every update path holding `$` or `$[`, `arrayFilters`, and an update given as an
array of stages (`238 NotImplemented`), so the update most applications send to change one
element of an array (`{$set: {"items.$.qty": 2}}`) failed. Built from MongoDB's public manual
(the `$`, `$[]` and `$[<identifier>]` update operator pages, "Updates with Aggregation
Pipeline" and the `update` and `findAndModify` command pages); the tests are those pages'
examples (`crates/eggdb-documents/src/tests.rs`, and over the commands and OP_MSG in
`crates/eggdb-mongowire/src/tests.rs`). The wire protocol has `update` and `findAndModify`;
drivers' `updateOne`, `updateMany` and `findOneAndUpdate` are those commands.

- **Where it lives.** The document model (`eggdb-documents`) does it all, so SQL over
  documents can reuse it; `eggdb-mongowire` only passes `u` (a document or an array) and
  `arrayFilters` to `parse_update_statement`. `Update::Operators` carries its `ArrayFilter`s and
  `Update` gains `Pipeline(Vec<Stage>)`; `apply_update` takes the query filter that matched the
  document.
- **`$`.** `matched_array_index(filter, document)` returns the position of the array element
  through which the filter matched: the first condition that matches through an array gives
  it (MongoDB calls more than one such condition undefined), an `$elemMatch` gives the element
  it matched, `$or` the first branch that matched, and negations (`$ne`, `$nin`, `$not`,
  `$exists`, `$size`) give none. Only an update path with `$` computes it. No position (the
  query did not go through an array, or the update is an upsert's insert) is MongoDB's
  `2 BadValue` "The positional operator did not find the match needed from the query.".
- **`$[]` and `$[<identifier>]`.** Each positional path is turned into concrete paths against
  the document as it stands when that operator runs (`grades.$[t].questions.$[s]` becomes
  `grades.0.questions.1` and so on), and the operator applies to each. An element matches
  `$[x]` when its array filter matches `{x: <element>}`. Two operators reaching the same
  concrete path, or one inside the other, are `40 ConflictingUpdateOperators`, found with a
  sorted set of changed paths (one lookup per path, so `$[]` over a large array stays linear).
  The array a positional part reads must exist (`2` "The path '…' must exist in the document in
  order to apply array updates.") and be an array (`2` "Cannot apply array updates to
  non-array element …").
- **`arrayFilters` checks**, as MongoDB answers them: each filter has exactly one top-level
  name across `$and`/`$or`/`$nor` (`9 FailedToParse` for none or two), that name is an
  alphanumeric string starting with a lowercase letter (`2 BadValue`), names are unique (`9`),
  a path's `$[x]` without a filter is `2` "No array filter found for identifier 'x' in path
  '…'", a filter no path uses is `9` "The array filter for identifier 'x' was not used in the
  update …" (so a replacement document with filters fails too), `$` or `$[…]` first in a path
  and two `$` in one path are `2`, and `$rename` with a positional source or target is `2`.
- **`28 PathNotViable`.** Creating a field inside a value that is neither a document nor an
  array, or a non-numeric field of an array, is now `28 PathNotViable` "Cannot create field
  'x' in element {…}" (before: `2 BadValue`), for every update, since `$[].x` over an array of
  numbers reaches it most often.
- **Pipeline-style updates.** `u` (or `findAndModify`'s `update`) given as an array runs the
  stages MongoDB allows there, `$addFields`/`$set`, `$project`, `$unset` and
  `$replaceRoot`/`$replaceWith`, with the aggregation code that `aggregate` uses; any other
  stage is `72 InvalidOptions` "… is not allowed to be used within an update", and
  `arrayFilters` with a pipeline is `72` "arrayFilters may not be specified for pipeline-style
  updates". The result keeps the document's `_id` (a missing one is put back first, a
  different one is `66 ImmutableField`). An upsert starts from the query's equalities and runs
  the pipeline over them, as the manual describes. `$$NOW` is bound to the statement's time,
  the same for every document it changes (it is replaced by a `$literal` before the stages
  run, so `aggregate` does not have it yet). `$concatArrays` and `$mergeObjects` join the
  expression operators, since the manual's pipeline-update examples use them.
- **Size bound while applying.** `$[]` and `$[<identifier>]` copy the operator's argument
  to every element they reach, so `{$set: {"a.$[]": <15 MB string>}}` over a large array
  would build terabytes before the 16 MiB check on the result. Once an operator reaches more
  than one path, the update counts the document's BSON size (without encoding it) and, after
  each path, swaps the old value's size for the new one's; passing `MAX_DOCUMENT_BYTES` stops
  the update with the error a too-large stored document already gives (`2 BadValue` "object to
  insert too large. size in bytes: …, max size: 16777216"; MongoDB answers `17419` there). The
  count is the real growth, so `$push`/`$addToSet` with `$each`, `$slice` and duplicates are
  counted as they come out, and an update whose result fits is never refused. Expressions do
  the same: the arguments of an operator (`$concat`, `$concatArrays`, `$mergeObjects`, `$sum`
  and the rest), an array or object literal, and the fields one `$addFields`/`$set` or
  `$project` stage computes each stop at 16 MiB, in `aggregate` too.
- **Unchanged.** Each statement is one transaction, as D197 says: a failure in the middle of a
  `multi` update leaves no document of that statement changed.

Left: `$$NOW` and `$$CLUSTER_TIME` in `aggregate`, and `$$CLUSTER_TIME` in pipeline-style
