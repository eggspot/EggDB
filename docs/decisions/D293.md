## D293 The C API steps through rows, streams `COPY` both ways through an `eggdb_copy` handle, and takes prepared statements, cancelling and `COPY` on `eggdb_sql_connect` sessions — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); refines D268, D142 and D17

D268 left out row-by-row results, `COPY ... TO STDOUT`, a copy-in fed piece by piece, and
prepared statements, cancelling and `COPY` on a session from `eggdb_sql_connect`. Drivers need
all of them: a data reader steps through rows, an export tool reads a table out, an import tool
reads a file in buffers, and the same driver code must work against a file and a server.

- **Names.** Stepping belongs to the statement: `eggdb_stmt_step(stmt, &has_row)`, the current
  row as an array with `eggdb_stmt_row`, and typed getters `eggdb_stmt_value_kind`, `_int64`,
  `_double`, `_text` and `_blob`. *Why:* `eggdb_stmt_column_*` already names the columns known
  before a run; `value` says these read the current row's values, and `step` is the word every
  SQLite-style driver expects. A copy is a handle of its own, `eggdb_copy`, made by
  `eggdb_sql_copy_in_begin` and `eggdb_sql_copy_out_begin` (session-level, `eggdb_sql_` prefix)
  and used by `eggdb_copy_put`, `eggdb_copy_read`, `eggdb_copy_end` and `eggdb_copy_free`
  (void, as `eggdb_scan_free`). *Why:* D268's rule that each handle's functions carry its name;
  one handle for both directions keeps one end and one free.
- **Crossings stay batched (D17).** `eggdb_stmt_row` lends a whole row in one call; the getters
  exist for drivers whose language reads one value at a time. A copy's pieces are up to 64 KiB.
- **The session is held.** From a statement's first step to its end or reset, and while a copy
  is open, other calls that run statements on the session fail with `EGGDB_ERR_IN_USE`, in the
  process and on a server alike. *Why:* on a server the connection is in the middle of an
  answer and cannot carry another query; refusing in the process too keeps one behavior, so a
  driver tested on a file works on a server (as ADO.NET's one open reader per connection).
- **End and reset.** After its last row a statement keeps reporting no row until
  `eggdb_stmt_reset` or `eggdb_stmt_execute` (no automatic rerun, so a loop cannot run a query
  twice by mistake). Reset, execute and finalize end a run part way; on a server they read and
  drop the rows still coming.
- **Getters convert only losslessly.** `int64` reads integers, booleans, reals with no fraction
  and decimal text (a `numeric`); `double` reads reals, integers and numeric text; `text` reads
  any value but binary data; `blob` reads binary data and any value's text. NULL and everything
  else fail with `EGGDB_ERR_INVALID_ARGUMENT`, never a silent 0. *Why:* a driver checks the kind
  first anyway, and a wrong guess is a bug worth a message.
- **Where streaming is real.** On a server each step reads one `DataRow`, each put sends
  `CopyData`, and each read takes the next `CopyData` messages. In the process the engine runs a
  statement, and reads a `COPY`'s data, inside one call (`Session::execute_*`), and its writer
  slot, temporary tables and PL/SQL state belong to the calling thread, so it cannot be moved to
  a helper thread to be fed from outside. So in the process a step converts one row from the
  engine's result (the printed text of all values is never held at once), a copy-in keeps its
  pieces until `eggdb_copy_end` runs the `COPY`, and a copy-out runs at begin and lends its data
  in pieces. The API is the same, so a resumable engine later changes nothing for callers.
- **Not the expected `COPY`.** A statement given to a copy call that is not the `COPY` it
  expects runs (as PostgreSQL would run it) and then fails with SQLSTATE `0A000`, on both kinds
  of session; the connection stays usable.
- **Server sessions.** `eggdb_sql_prepare` sends Parse and Describe for a named statement
  (`eggdb_capi_<n>`), so the parameter count and columns come from the server; finalize queues
  a Close sent before the session's next exchange (never in the middle of one). Values are bound
  as text and typed by their place, since the types are bound after prepare. `eggdb_sql_cancel`
  sends PostgreSQL's `CancelRequest` with the `BackendKeyData` the connection received, over a
  new connection with the same TLS mode, and waits for the server to close it. A connection
  that breaks in the middle of an exchange marks the session broken: every later call fails
  with `EGGDB_ERR_IO` until it is closed, instead of misreading the stream.
- **The client.** `eggdb_pgwire::client::PgClient` gains `prepare_named`, `close_statement`,
  `start_prepared` with `next_answer` (one message of the answer at a time) and
  `collect_answers`, `start_copy_in`, `finish_copy_in`, `fail_copy_in`, `next_copy_out_piece`
  and `cancel_request`; `start_copy_out` now leaves the connection ready when the statement is
  not a copy. `execute_with_parameters` shares the Bind and answer code.

**Not yet:** rows streamed out of the engine itself in the process (a resumable executor), a
local copy-in loaded as its pieces arrive, parameter types declared to a server at prepare time
(typed `Parse`), binary result formats on server sessions, asynchronous calls, and the drivers'
use of the new calls (D16).
