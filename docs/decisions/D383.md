## D383 SQLite's temporary triggers — Decided by the code-only session (2026-11-10, D355); roadmap M5

SQLite's `CREATE TEMP TRIGGER` (or `TEMPORARY`) puts the trigger in the session's `temp` schema:
it fires for that session's statements only, may sit on a main table, and is gone when the
connection closes. EggDB's temporary objects (D151) already live under keys that only the
session's own reads and writes reach, and vanish with the session.

- **Where it is kept.** A temporary trigger is stored in the trigger record of a temporary owner
  named after its table (`triggers::temporary_owner`: the `pg_temp` schema and `\u{1}` before the
  table's name, so it can never be a real table's name), so the trigger key is temporary and
  every other session sees nothing.
- **Firing.** `triggers::of_table` adds the temporary owner's triggers after the table's own,
  only when the session holds temporary objects (`temporary::active`), so other sessions and
  sessions without temporary objects pay nothing.
- **Dropping.** `DROP TRIGGER` finds it by name through the session's view of the trigger records,
  as for any other trigger.
- Other dialects keep refusing `CREATE TEMP TRIGGER`. `sqlite_temp_schema` does not list it yet.
