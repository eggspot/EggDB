## D368 Triggers of a row moved to another partition — Decided by the code-only session (2026-11-10, D355); closes one of D316's leftovers

PostgreSQL moves a row whose new key belongs to another partition by deleting it from the
source and inserting it into the target, and fires the source's `DELETE` row triggers and the
target's `INSERT` row triggers, but only the `UPDATE` statement triggers. EggDB fired the
`BEFORE UPDATE` row triggers, no `DELETE` triggers, and the target's `INSERT` statement triggers
as well as its row triggers (D316).

- **Source.** `move_out` fires the source partition's `BEFORE DELETE` row triggers before it
  deletes a leaving row (reading the row when the update did not keep it) and its `AFTER DELETE`
  row triggers after; a `BEFORE DELETE` trigger that returns NULL keeps the row in place and it
  is not counted, as in PostgreSQL. Statement triggers are not chosen
  (`Firing::for_moved_row`).
- **Target.** While the moved rows are inserted through the partitioned table, the table and its
  partitions are marked as receiving moved rows (`triggers::moving_rows_into`, a guard that
  unmarks them when the insert ends), and `Firing::for_table` leaves out `INSERT` statement
  triggers for them; `INSERT` row triggers still fire. A trigger body that inserts into the same
  tree during the move also skips those statement triggers; that nesting is rare and documented
  here.
- **Other dialects.** MySQL and Oracle have no triggers on partitions, so only their table-level
  triggers matter; whether a moved row should fire the table's `INSERT` row triggers there (it
  should not) is checked in the build-and-fix pass.
