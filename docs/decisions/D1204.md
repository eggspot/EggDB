## D1204 Per-account statement limits: MySQL's `MAX_QUERIES_PER_HOUR` and `MAX_UPDATES_PER_HOUR` — Decided by the code-only session (2026-11-17, D355); roadmap M6c, request quotas and admission control (D25, D234)

- **What users get.** `CREATE USER ... WITH MAX_QUERIES_PER_HOUR n MAX_UPDATES_PER_HOUR m` and `ALTER USER ... WITH` (0 lifts a limit), as MySQL writes them, are stored for the role and enforced on every protocol and dialect: once a role has run `n` statements (or `m` changing ones: writes and definitions) in the hour since its first counted statement, the next is refused, with MySQL's error 1226 (`User 'x' has exceeded the 'max_questions' resource (current value: n)`) in MySQL sessions and `53400` elsewhere, until the hour has passed. This is request quotas per tenant where tenants log in as their own roles, and the admission control a SaaS operator needs against one tenant's runaway job. `MAX_CONNECTIONS_PER_HOUR` and `MAX_USER_CONNECTIONS` were accepted and not enforced (enforced since D1232).
- **How.** The limits live in their own key space (`ROLE_LIMIT_SPACE` 0x20, dropped with the role) so role records keep their format; a session reads them when its role logs in. The counts are kept in the process, per database and role, shared by every session of the role and every listener, and are not persisted: a restart starts the hour again, as MySQL's `FLUSH USER_RESOURCES` would.
- **Left.** Connection limits (`MAX_USER_CONNECTIONS`, PostgreSQL's `CONNECTION LIMIT`), which need a count of open sessions per role; concurrency limits (statements running at once per tenant), and counts shared by a cluster's nodes.
- **Proof.** A unit test of the counter (per hour, per role, changes counted apart, MySQL's and the other dialects' errors) and an end-to-end test through a MySQL `CREATE USER ... WITH MAX_QUERIES_PER_HOUR 2` and a session refused on its third statement.
