## D141 Online backup and compaction: a logical copy of one snapshot, rebuilt entry by entry into a staging file, synced, checked and renamed into place; compaction as that copy renamed over the file; `eggdb backup` and `eggdb compact` as Claude Fable designed them — Decided by the build loop (by research, 2026-10-30); roadmap item 28, applies D9, D15, D20, D24, D35, D78, D84, D86, D90, D93, D139, D140

Item 28 gives EggDB a backup that runs while the database works, and a way to give a file's
free and leaked pages back to the disk.

**A logical copy of one snapshot.** `ReadTransaction::copy_to` in `eggdb-storage` copies what a
read transaction sees: every entry of the file's one tree, in key order, into a new file with
the same page size and a new identity. The tree holds everything (the default key space,
collections and their catalog (D139), SQL tables, keys' deadline records (D140)), so nothing is
copied model by model and a new model needs no change here. The copy's first commit sets the
snapshot's feature flags (a file that had expiring keys keeps `EXPIRING_KEYS`) and a clock
high-water mark at the snapshot's stamp, so every later commit stamps above it and a key that
had expired stays expired (D140's time never goes back). A snapshot with read-only-compatible
features this release does not know is refused: copying it would write a file whose rules this
release does not follow. *Why logical, not pages:* a page copy would have to bring the free
list, the log and its recycled segments along and then renumber or reclaim them, which is the
format's most delicate code (D78, D84); a logical copy goes through the same B+tree, log and
commit code every write uses and is crash-tested already, packs the leaves, and makes backup and
compaction one procedure. *Cost:* a backup reads every value and writes every page once, and
its entries are first counted by a pass over the keys (no values read) to size its page cache
for the largest value.

**Online.** The copy reads one snapshot (D77/D86): the writer and other readers keep working,
each source read takes the store only for its own step, and commits made while the copy runs
are not in it. A writer that changes more pages than the snapshot memory holds expires the
snapshot, and the backup fails with `SnapshotTooOld` rather than holding the writer back. The
copy is written in batches of a quarter of its own page cache (16 MiB, or the largest value's
pages plus a margin), under `Normal` durability, then checkpointed and synced.

**Staging, check, rename.** The copy is built at `<path>.backing-up` (backup) or
`<path>.compacting` (compaction) beside its destination. After the checkpoint and sync it is
checked as `eggdb check` checks a file: its tree must hold exactly the snapshot's entries and
no page may be unused (`StorageError::CopyIncomplete` otherwise). Only then is it renamed and
the directory synced. A crash at any operation leaves the destination as it was or the whole
copy (fault-injection sweep in `snapshot_copy_tests.rs`: every operation of a backup and of a
compaction fails once, followed by a reopen, a power loss dropping unsynced writes, or two
torn-write power losses). `CopyFailure` tells the three outcomes apart: not copied (the staging
file was removed, unless it was there before), not renamed (the complete, verified copy is kept
at the staging path and named in the error, as import keeps its file), and renamed but the
directory not synced. A staging file that exists refuses the copy and is never removed: it is a
copy still running or one a crash left, and removing someone else's file is worse than asking.
A backup never replaces a file.

**Compaction.** `Database::compact(self)` first checks the file (a damaged file is refused and
left as it is, and the report counts its leaked pages), then copies its snapshot with the file
itself as the destination, so the rename replaces it atomically. It takes the database by value:
no commit can go to the file after it was replaced. `Database::compact_file(path)` opens the file
read-only (a shared lock, D78), so readers in other programs keep working and keep reading the
file they opened; a writer refuses it (`Locked`). Renaming over a file another program holds open
works on Unix and, with the POSIX rename semantics the standard library uses, on Windows 10 1607
and later.

**Known limit.** A writer in another program that opened the path an instant before the rename
but takes its lock after the compaction closes the file would write to the replaced file. The
window is between that program's open and its lock, two system calls; closing it is follow-up
work: the platform layer would tell whether a file it locked is still linked at its path.

**The command line** follows Claude Fable's design in `docs/ux/cli.md` section 22:
`eggdb backup <file> <copy>` and `eggdb compact <file>` (the last reserved names, so the
reserved-command message is retired), one report each in text or JSON, the copy's path checked
before the file is opened, `backup <copy>` in `eggdb shell` (the online path for a file the
shell holds for writing) and `compact` refused there with the command to type.

**Not in this release:** incremental, scheduled and remote backups, point-in-time recovery from
archived logs (the rest of D24), progress reporting, a backup through `eggdb serve`'s clients,
and compaction of a file `serve` holds.
