## D101 Benchmarks are reported on pull requests and only a slowdown of more than 2x blocks; one final `check` job is the required check and auto-merge is allowed — Decided (owner, 2026-10-27); supersedes D7's merge rule for pull requests and the failing gates of D80, D94, D99 and D100
**The performance rule (owner, 2026-10-27).** On pull requests, CI measures the benchmarks
automatically on every run and only reports the change: a slower benchmark does not block the
merge, except a slowdown of more than 2x on any benchmark, which still blocks and is fixed in that
pull request. Per-PR results are kept so a regression can be traced to the pull request that
caused it. Every other slowdown is fixed in a weekly performance pass (Saturdays), which reads the
reported changes, fixes the slow paths and lowers the baseline with `--update` where a line
improved. This replaces "a slower result blocks the PR until it is fixed" in D7 for pull requests;
the rest of D7 (the best existing database for each workload, benchmarks for every hot path,
gated against a committed baseline) stands, and so does its exception: a slowdown of more than 2x
may still be accepted when a research subagent concludes it is the unavoidable, minimised price of
correctness or security, with the reasoning recorded here and exactly the affected baseline lines
updated.

**How `eggdb-bench` and `eggdb-sqlite-compare` apply it.** Every line in
`benchmarks/baseline.txt` is compared with its measurement, and the run prints and adds to the
GitHub step summary a table with the value, the line, the change in percent and a verdict:
- `ok`: within the line's tolerance (30% for ratios, 50% for the SQLite ratios, 15% for the SQL
  ones of D99 and D100, 1% for the binary's size, 10% for peak memory);
- `SLOWER`: above the tolerance and at most twice the line. Reported, never failing;
- `BLOCKED`: more than twice the line. Fails the run, after one more measurement for ratios, so
  one noisy sample does not block a pull request. A count above a line of zero (an allocation on
  a path that made none, a leaked page) is more than twice and blocks;
- `improved`: below the line. Reported; counts that fell used to fail until the baseline was
  lowered, and no longer do;
- a count without a baseline line still fails, since the new benchmark has to be added to the
  baseline with `--update` in the same pull request.

The size, peak memory and start time of the `eggdb` binary (D6, D14) follow the same rule: growth
is reported and the weekly pass looks at it, and doubling blocks. D99's condition (the SQL ratios
at most 1.0 before v0.3.0) is unchanged and is checked by the weekly pass and at the release. Each
run writes one line per metric (`<os> <benchmark> <metric> <value> <baseline> <change>
<verdict>`) with `--results`, and CI uploads those files as artifacts, named
`benchmarks-pr-<number>-<head sha>` and `sqlite-compare-pr-<number>-<head sha>` (`push` in place
of `pr-<number>` on `main`), kept 90 days.

**One final required check, and auto-merge.** CI's last job is named `check`: it runs after every
other job (`needs:` all of them, `if: always()`) and fails when any of them failed or was
cancelled. The `main` ruleset requires only the status check named `check`, so the job that used
to carry that name (format, lint, test, smoke test and docs) is now `lint-and-test`, and new jobs
only have to be added to the `needs:` list of `check`. A pull request that changes the job
names provides the new `check` from its own run. Once `check` exists, auto-merge
(`gh pr merge <number> --auto --squash --delete-branch`) is allowed in this repository: it waits
for `check`, which waits for everything else.

**Flaky tests.** A test that fails on one platform and passes when run again is quarantined for
that platform with `#[cfg_attr(target_os = "<os>", ignore = "flaky on <platform>: see issue #N")]`
and an issue labelled `flaky` that names it, so it stops blocking pull requests and stays
visible. The history of CI on 2026-10-27 shows none today: every sporadic failure of the
`platforms` job was a real bug that was fixed (a file lock inherited by a starting child process,
D95), and the benchmark lines that failed at random (`page_cache.hit`, `large_value.get`,
`btree.scan`) are covered by the rule above, not quarantined.
