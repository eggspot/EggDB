## D797 SQL Server's hierarchyid — Decided by the code-only session (2026-11-12, D355); roadmap M10, SQL Server's types

- A `hierarchyid` value is a tree position written `/1/3/2.1/`. EggDB stores it as bytes of its own order-preserving
  encoding (`crates/eggdb-sql/src/sqlserver_hierarchy.rs`): for each level, each dot-separated number as a marker and
  a sign-flipped big-endian 64-bit integer, an end-of-level byte, and an end-of-path byte, chosen so plain byte order
  is SQL Server's depth-first order (a node before its children, `/2/` before `/10/`, `/1/1/` before `/1/1.1/` before
  `/1/2/`). SQL Server's own ORDPATH bits are not reproduced; nothing outside EggDB reads them.
- A column declared `hierarchyid` in the SQL Server dialect is `varbinary(892)` (SQL Server's maximum size for the
  type), so it keys, sorts and indexes by that order; the catalogs show `varbinary(892)`, since EggDB keeps no
  declared SQL Server type beyond the engine's (an open item of its own).
- The static methods `hierarchyid::GetRoot()` and `hierarchyid::Parse(s)` (the SQL Server lexer now gives `::` as a
  token instead of refusing it) and the instance methods `ToString()`, `GetLevel()` (smallint), `GetAncestor(n)`,
  `GetDescendant(c1, c2)`, `IsDescendantOf(p)` (bit) and `GetReparentedValue(old, new)` work on columns and qualified
  columns as `node.Method(...)`, like the `xml` methods (D695). `GetDescendant` picks the next integer after `c1`,
  before `c2`, or between them, falling back to a dotted step (`/1/2.1/`) when the two are adjacent; SQL Server's
  exact choice of new numbers differs in some gaps but keeps the same order. Bad text fails with SQL Server's 6522.
- Left: casting and implicitly converting strings to `hierarchyid` (an explicit `Parse` is needed), the type's own
  catalog entry and TDS UDT form, `rowversion` and `sql_variant`.
