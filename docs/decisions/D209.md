## D209 Replication ships numbered key-value change batches; the protocol first, engine capture next — Decided by the build loop (by judgement, 2026-10-31); refines D18

Part 4.M14-3 asks for synchronous, asynchronous and cascading replicas, failover, and
consistency chosen per request, checked with simulated network partitions.

- **Replicate below the data models.** Every model (SQL, documents, graphs, key-value servers)
  writes through EggDB's key-value transactions, so a replica that receives each commit's
  key-value changes holds every model at once and applies them with the same code. `eggdb-
  replication` defines the protocol: a batch per commit, numbered within the primary's term;
  replicas apply strictly in order (gaps are reported with the sequence they need, stale terms
  refused), acknowledge prefixes, can feed cascading replicas from their own retained batches,
  and serve a read only when they hold the client's `ReadToken`. Synchronous mode reports a
  commit durable once enough replicas acknowledged it; failover promotes the candidate with the
  newest term and then the most applied, which starts a new term.
- **Tested by deterministic simulation**: forty seeded runs drop deliveries at random and then
  fail over; every commit reported durable must survive on the new primary.
- **Capture is the engine's next step.** Producing each commit's changes needs a hook in the
  write transaction (opt-in, so a database without replicas pays nothing, D6) and a network
  transport in `eggdb serve`; both are a slice of their own with the storage review, shared with
  change streams (4.M14-5).

Left: the commit hook and its change log, the transport (TLS, authentication) and `eggdb serve
--replica-of`, initial copy by snapshot (D208's archive), automatic failure detection, fencing
of an old primary, and Jepsen-style checks against real processes.
