## D1309 Changes written back into SQLite files through the rollback journal — Decided by the code-only session (2026-11-25, D355); roadmap M5, D180, D631

- **What users get.** `eggdb sql app.sqlite`, `eggdb shell app.sqlite` and the other commands that open an SQLite file for writing now write the changes back into it when the command ends, so an SQLite application sees them; before, the file was only read into memory (D180). The write is crash-safe as SQLite's own is in rollback journal mode: the file's old pages go to `<file>-journal` and are synced, the new pages are written and synced, and deleting the journal commits. A journal a crash left beside a file is rolled back before the file is read, as SQLite's next connection would. The file's change counter and schema cookie move on, so open SQLite connections reread it. Nothing is written when nothing changed or with `--read-only`.
- **How.** `eggdb-sqlite-format` gains `replace_database`, `roll_back_hot_journal` and `change_counter`, written from SQLite's published file format description (the journal header, page records and their checksums of every 200th byte). The session's new `sqlite_file_bytes` builds the whole file as `VACUUM INTO` does (D631), and the CLI's SQLite copy writes it back at close, or when it is dropped. Rewriting the whole file keeps the writer simple and the journal correct at the cost of time proportional to the file's size; the file comes out in rollback journal mode with 4,096-byte pages.
- **Safety.** The change counter read at open must still be in the file, otherwise another program wrote meanwhile and the changes are refused rather than overwrite its work; a `-wal` file holding frames or an existing journal also refuse, since writing beside them could lose committed data.
- **Left.** Page-level edits of only the changed pages, writing through the WAL, and taking SQLite's byte-range file locks so EggDB and SQLite can write the same file at the same time.
- **Proof.** Format tests replace a file and read the new rows, see the counter move on and no journal left, refuse a stale counter, roll back a torn write from its journal byte for byte, and check the checksum's bytes; a CLI test inserts a row into an SQLite file, reads both rows back from the file in a new process, and sees the counter moved on exactly once.
