## D1096 The container image's download size and pull time, measured at every release and budgeted — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D14, D224, D354)

- **What is measured.** For each platform of a release's image (amd64, arm64), the bytes a pull downloads: the config plus the compressed layers, read from the registry's own manifests with `docker buildx imagetools inspect --raw`. That is exact and needs no pull. On the runner's platform it also measures how long a cold `docker pull` takes. `scripts/footprint-image.sh` prints them as `container <platform> image_compressed_bytes` and `container <platform> pull_ms`, with the change from the previous release's image.
- **Where it shows.** The release workflow's `image` job runs it after pushing and adds a "Container image" table to the GitHub Release notes, replacing an earlier one when a release is re-run. D14 asks for every release's sizes in public, and this extends the binary sizes table to the image.
- **Kept from growing.** The budgets are the `container` lines of `benchmarks/footprint.txt` (32 MiB per platform, 15 s for a pull on a hosted runner, as first ceilings). Following D354, the weekly performance pass checks them and lowers them to the measured values. A release over a budget gets a workflow warning, not a failed release, because the release is already public when the image is measured and D353 treats a failed release as an emergency.
- **Why nothing else changes.** The image is already `FROM scratch` with only the static musl binary, so its size is the binary's size; shrinking it is the binary's work (D6).

**Status:** code written, unbuilt (code-only mode, D355).
