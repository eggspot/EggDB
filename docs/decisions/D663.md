## D663 key_length in MySQL's EXPLAIN FORMAT=JSON — Decided by the code-only session (2026-11-12, D355); roadmap M6c, D345

MySQL tools and DBAs read `key_length` to see how much of a composite index a query uses. D345's
JSON plans named the key and its used parts but not their length.

- A plan entry that uses a key now carries `"key_length"`: the sum of MySQL's index byte widths of
  the key parts it uses (as a string, as MySQL prints it), plus one byte for each nullable part.
  The widths are:
  - integers by size (`SMALLINT` 2, `INT` 4, `BIGINT` 8), `FLOAT` 4, `DOUBLE` 8;
  - `DATE` 3, `TIME` 3, `DATETIME` 5 and `TIMESTAMP` 4, each with the bytes of its fractional
    seconds;
  - `DECIMAL(p, s)` with MySQL's packed nine-digit words;
  - `CHAR(n)`/`VARCHAR(n)` as `n × 4` (`utf8mb4`) plus the two-byte length, capped at 3,072;
  - other types (`TEXT`, `BLOB`) as the 3,072-byte prefix limit plus the length.
- The key parts are the same ones `used_key_parts` lists, now computed once as column positions
  (`key_columns`) for both.
- Left from the item: `used_columns`, `data_read_per_join`, attached subqueries, MySQL's `` `db`.`t`.`c` ``
  spelling, format version 2, and `INSERT`/`REPLACE` plans.
- Test: the primary-key plan of `EXPLAIN FORMAT = JSON` shows `"key_length": "4"` for an `INT`
  key.
