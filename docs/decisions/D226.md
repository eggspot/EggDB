## D226 Separated storage starts as archives in object storage that a new node restores from — Decided by the build loop (by judgement, 2026-10-31); refines D18, D24 and D208

Part 4.M18-2 asks for pages on object storage with stateless compute nodes that scale to zero.

- **The archive is the durable copy; the node's disk is a cache of it.** `eggdb backup <file>
  s3://bucket/prefix` archives the same verified copy as a directory archive (D208), with the
  same `manifest.jsonl`, into any S3-compatible bucket. `eggdb restore <new> s3://... [--at]`
  restores it. `eggdb serve --restore-from s3://...` restores the newest copy when its file is
  missing, so a node started on an empty disk (a container, a serverless instance woken from
  zero) comes up with the archived state. Scaling to zero is then a matter of archiving before
  stopping. A node can lose at most what changed since the last archive, which the schedule of
  `backup` decides (D200).
- **One small S3 client, ours**, in `eggdb_s3::client`: put, get, delete and list, signed with
  the shared SigV4 code (D219), over a general request function added to `eggdb-http`'s client
  (chunked responses, bounded bodies, the caller's `Host`). Settings come from the environment
  variables every S3 tool reads (`AWS_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`,
  `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`). Only `http://` endpoints for now, which covers EggDB's
  own S3 endpoint, MinIO and in-cluster gateways. AWS itself needs `https://`: the TLS client in
  `eggdb-tls` with certificate checks is its own slice.
- **A copy is checked twice**: before upload (opened and checked as in D208) and after download
  (its SHA-256 against the manifest), and it is written under a staging name and renamed, so a
  torn download never becomes the database.

Left: page-level storage (the page cache reading missing pages from object storage, and the log
shipped segment by segment, so archives are continuous and nodes start without a full
download), `https://` endpoints, multipart uploads for copies over the server's single-request
limit, uploading without a staging file, retention, and a simulator test of restoring under
failures.
