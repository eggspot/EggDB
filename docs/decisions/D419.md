## D419 Variables set inside MySQL stored programs and `SIGNAL ... SET MYSQL_ERRNO` — Decided by the code-only session (2026-11-11, D355); roadmap M10

- `SET @x = expr` and `SET [SESSION] name = expr` inside a MySQL procedure or function are run by
  the routine interpreter itself (`plpgsql/run.rs` `mysql_assignments`): the value is evaluated
  with the routine's variables in reach and recorded in a per-thread journal
  (`mysql_variables::record_routine_assignment`). While the routine runs, the MySQL parser reads
  `@x` and `@@name` from the journal first, so later statements of the body see the new values.
- After a `CALL`, the session applies the journal through the same code as a top-level `SET`
  (`session/mysql.rs` `assign_value`), whether the call succeeded or not, since MySQL's variables
  are not transactional: a variable set before a failing statement keeps its value. A system
  variable the session refuses (read-only, wrong value) fails the `CALL` with MySQL's error 1238
  or 1231 after the body ran, where MySQL fails the `SET` statement itself: a known difference.
  The `OUT` parameters written to user variables are applied after the journal, so they win, as
  in MySQL where they are assigned when the procedure returns.
- A stored function that sets a variable while called from a top-level `SELECT` records it in the
  journal, but only a `CALL` applies the journal; such an assignment is dropped at the next `CALL`.
  Left for later.
- `SIGNAL`/`RESIGNAL ... SET MYSQL_ERRNO = n` now sets the raised error's MySQL error number
  (`RaiseItem::MySqlErrno`, `RaisedFields::vendor_code`), which clients see and handlers for that
  number catch; a value that is not a number from 1 to 65535 is error 1231.
