## D1008 Graph algorithms over SQL/PGQ property graphs — Decided by the code-only session (2026-11-13, D355); roadmap M13 (D55, D206, D248, D1007)

- `GRAPH_TABLE (graph CALL procedure(arguments))` runs one of D248's graph algorithms over a property graph defined
  on tables (D1007), and stands for a relation in the `FROM` clause like any `GRAPH_TABLE`. The procedure is named
  with or without its `eggdb.` prefix, case-insensitively, and takes the same arguments as the Cypher `CALL`.
  `CALL` inside `GRAPH_TABLE` is EggDB's own form; SQL:2023 part 16 defines no algorithms, and a table-valued form
  keeps the result joinable with the tables it came from.
- The algorithms no longer read the key-value graph directly: `eggdb-graph` gains a `Topology` trait (node ids and
  each node's neighbours), implemented by its own store and by an in-memory `EdgeList`, and every algorithm except
  `weightedShortestPath` (which reads relationship properties) runs over either through `call_procedure`. One copy
  of each algorithm serves both graph models.
- The session reads each vertex table's key and each edge table's source and destination keys as text (at most a
  million rows per table), numbers the vertices, runs the algorithm and writes its records back as an inline
  `VALUES` relation. A vertex is named `table alias:key` (key columns joined with commas), in the columns `node`,
  `node1`, `node2`, `component` and `community`; a path is a JSON array of names in `nodes`; scores are `double
  precision` and counts `bigint`. `shortestPath` names its start and end vertices the same way.
- A vertex table without a `KEY` uses the columns its edges reference; an edge that references other columns than
  its vertex's key is refused for algorithms.
