## D325 HTTP/1.1 persistent connections, pipelining, chunked request bodies and streamed chunked responses in `eggdb-http`, for every HTTP listener, under the memory budget — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M6a, extends D188 and D307, applies D9 and D34

`eggdb-http` (D188) served one request per connection and refused `Transfer-Encoding`, so every
REST, Elasticsearch, S3, DynamoDB, SQS, observability, metrics and MCP client paid a TCP
handshake per request, and clients that send chunked bodies (Elasticsearch bulk loaders, S3 and
HTTP libraries streaming an upload of unknown length) were refused. Built from RFC 9112
(sections 6, 7 and 9) and RFC 9110.

- **Persistent connections.** An HTTP/1.1 connection persists by default; an HTTP/1.0 one only
  when it sends `Connection: keep-alive`, and its answers then carry `Connection: keep-alive`. A
  `close` option in any `Connection` field ends the connection after its answer. The server
  closes it after `Limits::keep_alive_idle_timeout` without a request (default
  `KEEP_ALIVE_IDLE_TIMEOUT`, 5 s, as Apache httpd's `KeepAliveTimeout`) and after
  `Limits::max_requests_per_connection` requests (default `MAX_REQUESTS_PER_CONNECTION`, 100, as
  `MaxKeepAliveRequests`), the last answer saying `Connection: close`; `Limits::with_keep_alive`
  sets both. Once twelve of a listener's sixteen connection threads are busy, every answer closes
  its connection, so idle persistent clients cannot keep new ones out, and a stopping server
  closes idle connections within 200 ms. A connection closes after a refused or unreadable
  request, after a response whose own `Content-Length` header disagrees with its body (except
  `HEAD`), and after a streamed response to an HTTP/1.0 client. Closing is gentle (RFC 9112
  9.6): the server half-closes and reads for up to 1 s or 1 MiB, so a client still sending a
  refused body reads the refusal instead of a reset.
- **Pipelining.** Bytes past a request's end stay buffered for the next one, so requests sent
  without waiting are answered in order on the same thread; empty lines before a request line
  are skipped.
- **Timeouts.** A new connection's first request must start within 5 s, a request head must
  arrive within 10 s of its first byte, and a body read may wait 5 s for each piece, replacing
  the old 5 s per read, which let a client hold a thread for hours by sending a head byte by byte.
- **Chunked request bodies.** `Transfer-Encoding: chunked` (any case) is decoded: chunk
  extensions are ignored, trailer fields are read, checked as field lines and discarded (at most
  16 KiB and 100 of them), and the body handed to the handler has no framing. A chunk-size line
  is at most 1 KiB; the sizes, extensions and line ends together may exceed the body by at most
  64 KiB, so a body of one-byte chunks with long extensions is refused instead of costing the
  server unbounded reading. `100 Continue` is sent for a chunked body too.
- **Smuggling defences** (RFC 9112 6.1, 6.3 and 11.2). Refused with `400` and a closed
  connection: `Transfer-Encoding` together with `Content-Length`; `Transfer-Encoding` in an
  HTTP/1.0 request; codings where `chunked` is not last, appears twice, or is missing (`gzip`
  alone, an empty field); more than one `Content-Length` field, or one that is not all digits
  (`+5`, `5, 5`, ` `); header names that are not tokens (space before the colon, folded
  continuation lines); bare LF or CR, or NUL, inside a header line; a chunk-size line ended by a
  bare LF, with no hex digits, or with anything but `;` after its digits; chunk data not followed
  by CRLF; versions other than `HTTP/1.x`. `gzip, chunked` and other codings before `chunked`
  get `501 Not Implemented`. A `Content-Length` or chunk size past the listener's limit (or past
  what fits in a machine word) gets `413`.
- **Streamed responses.** A handler served by `serve_replies_with_limits` answers a `Reply`:
  `Reply::Whole(Response)`, sent as before with `Content-Length`, or
  `Reply::Streamed(StreamedResponse)`, whose `BodyProducer` writes into a `BodyWriter` that
  sends a chunk each time `STREAM_CHUNK_BYTES` (16 KiB) gather. HTTP/1.1 clients get
  `Transfer-Encoding: chunked` and keep the connection; HTTP/1.0 clients get the plain body
  ended by closing the connection. A `HEAD` request gets the head without calling the producer.
  A producer that fails after the head is sent leaves the chunked body without its last chunk
  and closes the connection, so the client sees an incomplete response rather than a short
  complete one. `StreamedResponse::collected` and `Reply::into_response` build the whole body
  in memory for callers that need it. `serve_with_limits` keeps its signature and wraps its
  handler's `Response` in `Reply::Whole`, so every existing listener gets persistent
  connections, pipelining and chunked uploads unchanged.
- **REST rows streamed.** `eggdb_api::Endpoint::reply` answers a `GET` of a table with a
  streamed JSON array written row by row, and `eggdb serve --rest-listen` serves it through
  `serve_replies_with_limits`; `Endpoint::answer` returns the same bytes collected.
- **Memory budget (D307).** A chunked body is held against the budget as it arrives: each chunk's
  size is added and held before its bytes are read, and a chunk the budget cannot take gets the
  listener's own refusal (`429` for Elasticsearch, `503 SlowDown` for S3, and so on) and a closed
  connection. A streamed response holds one 16 KiB chunk, under the 64 KiB that is not counted,
  instead of its whole body. The connection's reservation is given back after each answer.
- **Fixes on the way.** Status lines now carry the right reason phrase for `201`, `204`, `206`,
  `304`, `409`, `411`, `412`, `416` and `501` (they said `Internal Server Error`); a `204` carries
  no `Content-Length` and no `1xx`, `204` or `304` answer carries a body; `Connection`,
  `Transfer-Encoding` and `Keep-Alive` set by a handler are dropped, since the server owns them;
  the server sets `TCP_NODELAY` and sends a head with a body under 64 KiB in one write, so a
  persistent connection never waits on delayed acknowledgements. The webhook and S3 client's
  chunked decoder no longer panics on a chunk cut short at the end of the response or on a
  chunk size near `usize::MAX`.

Decided by research: an unknown coding alone (`Transfer-Encoding: gzip`) gets `400`, not `501`,
because RFC 9112 6.3 requires `400` whenever `chunked` is not the final coding of a request,
while `501` (RFC 9112 6.1) is kept for a coding before a final `chunked`. Duplicate identical
`Content-Length` values are refused rather than merged, which RFC 9112 6.3 allows and which
leaves no reading that a proxy in front could take differently. A missing `Host` header is not
refused: RFC 9112 3.2 asks for `400`, but EggDB's listeners are loopback or TLS-only and health
probes and older tools send none; this is in "Left". Streamed responses never carry a
`Content-Length` even when the producer knows it, so the server never has to check a producer's
count against its promise.

Left: HTTP/2 and HTTP/3 (D34); request bodies with `gzip` or `deflate` content or transfer coding;
refusing an HTTP/1.1 request without `Host` (RFC 9112 3.2); streaming the Elasticsearch scroll
and search hits, S3 `GetObject` of large objects piece by piece, and Prometheus query results
through `StreamedResponse` the way the REST API does; handing a large request body to its
handler as it arrives instead of whole; connections served from the shared event loop rather
than a thread each (D103, D165), which would lift the sixteen-connection limit.
