## D285 Column privileges as PostgreSQL grants them, checked where names are resolved, and row-security `WITH CHECK` evaluated on every new row — Decided by the build loop (EggAgentCode task 20261103-0137, 2026-11-03); roadmap item 18 (M6b), refines D183 and D186, applies D9, D20 and D22; security-critical (D35)

D183 stored table privileges and D186 row policies, but left column privileges out and refused
`INSERT` and `UPDATE` under row security unless every policy said `WITH CHECK (true)`. Tools that
manage access (pgAdmin, DBeaver, Django's and Rails' multi-tenant setups) grant single columns
and write real `WITH CHECK` conditions, and expect PostgreSQL's answers.

- **Statements.** `GRANT SELECT (a, b), INSERT (a), UPDATE (a), REFERENCES (a) ON t TO r` and
  `REVOKE` of the same, `ALL [PRIVILEGES] (a)` for all four, in PostgreSQL's and MySQL's form
  (`GRANT SELECT (a) ON t TO r`; the same parser serves both, and Oracle's `GRANT UPDATE (a)`).
  `DELETE`, `TRUNCATE` and `TRIGGER` on a column fail with `0LP01 invalid privilege type ... for
  column`, an unknown column with `42703`. Revoking a privilege on the table also revokes it on
  every column, as PostgreSQL does. Column privileges work on tables and views.
- **Storage.** Column grants have their own space `0x16`: key `u32 big-endian length of the
  table's internal name, the name, grantee \0 column`, value `[2, privilege bits]`. The length
  prefix keeps a table of schema `s` and a table named `s` apart (an internal name is
  `schema \0 table`, so `table \0 grantee \0 column` in the grants space could not tell
  table `s`, role `t`, column `x` from table `s.t`, role `x`). A table grant stays
  `table \0 grantee` with `[1, bits]` in space `0x12`; every reader of a table's grants and
  policies now takes only the keys whose rest after `table \0` holds no further `\0`, so
  renaming or dropping table `s` leaves the grants and policies of `s.t` where they are. A
  release before this one never reads space `0x16`, so it neither shows nor applies column
  grants, and it does not delete them with a dropped table. So that such leftovers never reach a
  later relation of that name, every way a relation name comes into existence first deletes the
  table grants, column grants, policies and row-security switch stored under it: `CREATE TABLE`
  (which SQL Server's `SELECT INTO`, temporary tables, materialized views, every dialect's table
  creation and restores go through, as will `CREATE TABLE ... AS` once it is built), a new `CREATE VIEW`, and the target of a table or view
  rename, `SET SCHEMA` or schema rename; `ADD COLUMN` and the target of `RENAME COLUMN` first
  delete the column grants stored under that column name. `DROP VIEW` deletes the view's table
  and column grants as `DROP TABLE` does, and a view rename or schema move takes them along.
  Files written before this release have no column grants and open unchanged. Any other value or key in the column space is damage:
every check that reads it fails, so damage denies rather than allows. Column grants follow
  `ALTER TABLE ... RENAME COLUMN` and go with `DROP COLUMN`; table and column grants, policies and
  the row-security switch now follow `ALTER TABLE ... RENAME TO` (before, they stayed under the
  old name and applied to a later table of that name).
- **Reading.** A role reads a column when it holds `SELECT` on the table or on that column. The
  resolver keeps, for every `FROM` list in reach, each entry's label, columns and the columns the
  role may not read, and checks each column reference against the entry it binds to, innermost
  first, as PostgreSQL binds it: select lists, `*` and `t.*`, whole rows (`row_to_json(t)`, a bare
  `t`), `WHERE`, `GROUP BY`, `HAVING`, window definitions, `ORDER BY` (the select's and the
  query's), `LIMIT`, `JOIN ... ON` and `USING`, `LATERAL` items, subqueries correlated at any
  depth, common tables and set operations. A reference to a hidden column fails with `42501
  permission denied for table t`. An entry whose columns are unknown (a derived table, a function,
  a common table) never ends the search for an unqualified name, so an ambiguous case denies. A
  role with no privilege on the table and none on any column is refused as before; with some
  column, `SELECT count(*)` passes, as on PostgreSQL. Views run with their owner's rights as
  before (only superusers create them), so a view's own text is not checked against the reader.
- **Writing.** `INSERT` needs `INSERT` on each column it writes: the listed columns, the first
  *n* for `VALUES` of width *n* or a select list without `*`, every column otherwise, none for
  `DEFAULT VALUES`. `UPDATE` needs `UPDATE` on each `SET` column, `ON CONFLICT DO UPDATE` on each
  of its `SET` columns. Every column a write reads (`WHERE`, `SET` expressions, `RETURNING`,
  `RETURNING *`, the conflict target) needs `SELECT`, which a role with only `INSERT`, `UPDATE`
  or `DELETE` on the table does not have: before this release such a role could read through
  `WHERE` and `RETURNING`. `excluded.*` is the proposed row and is not checked, as on PostgreSQL.
  `MERGE` needs `SELECT` on every column of its target. `COPY t TO` needs `SELECT` and `COPY t
  FROM` needs `INSERT` on the copied columns.
- **Catalog.** `pg_attribute.attacl` lists column grants as `aclitem[]` (psql's `\dp` shows them
  under "Column privileges"), and `information_schema.column_privileges` lists each column grant
  and each table grant of `SELECT`, `INSERT`, `UPDATE` and `REFERENCES` expanded to its columns
  (not the owner's implicit privileges).
- **`WITH CHECK`.** `INSERT` and `UPDATE` under row security evaluate, on each new row after
  `BEFORE` triggers ran, the `OR` of the role's permissive policies for the command and the `AND`
  of its restrictive ones, each policy's `WITH CHECK` or, when it has none, its `USING`, as
  PostgreSQL's `CREATE POLICY` defines it. With no permissive policy the check is `false`. A row
  for which it is not true fails the statement with `42501 new row violates row-level security
  policy for table "t"` and nothing the statement wrote stays. With `RETURNING`, the new row must
  also pass the role's `SELECT` policies. `UPDATE` and `DELETE` that read rows (`WHERE`,
  `RETURNING`, `SET` expressions with columns) also see only rows the `SELECT` policies allow. The
  check rides as a labelled last `RETURNING` item that `execute::insert` and `execute::update`
  verify and remove on every path (top level, `WITH`, PL/pgSQL, triggers, `INSERT ... SELECT`,
  partitions), so the client never sees it. A checked role's `INSERT ... VALUES` of literals
  now goes through the binder instead of the literal fast path, which checks neither; superuser
  and embedded sessions keep the fast path.

Security review: the checks fail closed. A role is refused whenever a reference could bind to a
hidden column (unknown entries never end the search, unqualified names deny on any entry in the
nearest list that hides them, labels match also by their last name part). Policy conditions are
resolved with the scopes set aside, so the user's column privileges never block a policy and a
policy never widens them. The new-row check is evaluated by the executor on the stored row, so a
`BEFORE` trigger, `INSERT ... SELECT`, a data-modifying `WITH` or a `DO` block cannot skip it; a
user `RETURNING` item named like the label sits before the check and cannot replace it. Grants
are only written by superusers (D183). Damaged grant records deny. Describe (`Parse`/`Describe`)
binds without the check, so the row description never shows it. Round-1 security review fixes:
the column-grant key moved to its own length-prefixed space (above), so a column grant can no
longer be read as a table grant on a schema's table of the same name; `ALTER TABLE s RENAME`,
`DROP TABLE s`, `REVOKE` and `DROP COLUMN` touch only table `s`'s own grants and policies, never
those of the tables in schema `s`; a policy name holding `\0` is refused (`42602`); and when the
binder appended the new-row check, a result without its column is refused (`42501`) instead of
passing. Test: `a_table_named_like_a_schema_keeps_only_its_own_grants_and_policies`.

Test vectors (`crates/eggdb-sql/src/roles/columns/tests.rs`,
`crates/eggdb-sql/src/column_privileges/tests.rs`, `crates/eggdb-sql/src/row_security/tests.rs`,
`crates/eggdb-pgwire/tests/column_privileges.rs`): granted columns through joins, subqueries,
`RETURNING` and `count(*)`; 42 ways to reach an ungranted column (`*`, `t.*`, whole rows, `WHERE`,
`ORDER BY`, `HAVING`, aggregates, functions, `CASE`, windows, correlated and uncorrelated
subqueries, derived tables, `WITH`, `UNION`, `USING`, `ON`, `LIMIT`, `INSERT` without a column
list, `INSERT ... SELECT *`, `RETURNING`, `RETURNING *`, `ON CONFLICT DO UPDATE` set and read,
`UPDATE` set, `WHERE` and `RETURNING`, a view, `COPY TO`, `MERGE`); writes without `SELECT`;
revoke, `PUBLIC`, renames and drops; refused `GRANT` forms; `attacl` and `column_privileges`;
files without column grants and older readers; four damaged records; scope binding rules; for
`WITH CHECK`: `USING` as the check, `NULL` owners, multi-row and `INSERT ... SELECT` with one bad
row, `UPDATE` moving a row out, `WITH`, `DO` blocks, label spoofing, per-command and restrictive
policies, a `BEFORE` trigger rewriting the owner, `RETURNING` needing visibility, and the
extended protocol's row description.

Not yet: SQL Server's `DENY` beyond tables (its `GRANT` and `REVOKE` are parsed since D586, `DENY` on tables
since D621),
`WITH GRANT OPTION` on columns, column privileges on sequences, `MERGE` with column-only
privileges or evaluated checks (still refused unless `WITH CHECK (true)`), `ON CONFLICT DO
UPDATE` under row security, row security through an updatable view onto a table that has it,
grants following MySQL's `CHANGE COLUMN`, and dynamic data masking (SQL Server's `MASKED WITH`,
Oracle's redaction), which needs its own decision.
