## D1065 rsyslog and syslog-ng in CI — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D315, D783)

- New script `scripts/syslog-senders/check.sh <eggdb binary> <work directory>`, run by a new CI job,
  `syslog-senders` (in `check`'s `needs`). It starts two databases:
  - a plain one with `--syslog-listen 127.0.0.1:5514`, taking UDP and TCP;
  - one with `--syslog-listen 127.0.0.1:6514 --tls-self-signed`, taking syslog over TLS (RFC 5425).
- It then runs the two daemons people forward logs with, each fed one message by util-linux `logger`:
  - **rsyslog** (`rsyslogd` from the runner, installed with apt when missing) takes the message on `imtcp`.
    It forwards it with `omfwd` over TCP, octet-counted, as RFC 5424 (`RSYSLOG_SyslogProtocol23Format`), and
    over UDP in the traditional RFC 3164 format.
  - **syslog-ng** (the `balabit/syslog-ng:4.7.1` image, on the host network) takes it on a `network()`
    source. It forwards it with `syslog()` over TCP (RFC 5424, octet counting), over TLS (with
    `peer-verify(optional-untrusted)` for the self-signed certificate), and with `network()` over UDP (RFC
    3164).
- The check reads the `syslog` table back with psql 17 (from the `postgres:17` image, as `tls-clients` does).
  It waits up to 30 seconds for:
  - two rows per daemon on the plain server, the sender's tag as `app_name` in both formats;
  - one row on the TLS server.
- The configuration files and the logs of every process are kept as the job's artifact.
- The test senders are never shipped (D1). Every line of the script is ours, written from rsyslog's and
  syslog-ng's public configuration documentation.
