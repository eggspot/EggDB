## D823 MySQL logins for stored roles — Decided by the code-only session (2026-11-12, D355); roadmap M6b, D183

- A MySQL client that logs in as any user other than the served one (`--user`) is checked against the stored role of
  that name in the database it asks for (or the default one): the role must have `LOGIN` and a SCRAM-SHA-256
  verifier (D183). Stored roles keep only that verifier, which no MySQL scramble can be checked against, so the
  listener asks for the password itself: `caching_sha2_password`'s "perform full authentication" when the client
  uses that plugin, otherwise an authentication switch to `mysql_clear_password`. Both need TLS, the local socket or
  loopback, as MySQL's own full authentication does without RSA keys.
- `ScramVerifier::matches_password` (new, in `eggdb-auth`) derives the key with the stored salt and iterations and
  compares it without an early exit. `eggdb-mysqlwire` now depends on `eggdb-auth`.
- The session is opened with `identify_role`, so the role's grants and row security apply, also after
  `COM_RESET_CONNECTION`; a role that can no longer log in is refused there. Logins are recorded in the audit (D816).
- Left: TDS logins for stored roles, and MySQL's RSA key exchange for full authentication without TLS.
