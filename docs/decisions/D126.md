## D126 Oracle's types and semantics in the Oracle dialect: exact NUMBER values, datetime and number format models, NLS session settings, Oracle's implicit conversions and date arithmetic, and MERGE, with no file-format change — Decided by the build loop (by plan review, by judgement and by research, 2026-10-29); roadmap item 42, applies D1, D9, D10, D19, D108, D111, D114, D116, D119

Item 42 completes what D108 began: the Oracle dialect now computes, converts and prints values
the way Oracle's SQL Language Reference documents. Everything lives in Oracle modules of
`eggdb-sql` (`oracle_datetime`, `oracle_nls`, `oracle_conversion`, `oracle_functions`) and in
`merge.rs` / `parser/merge.rs`, reached from the engine through the hooks item 39 added for SQL
Server, each now choosing by dialect. Nothing new is stored: no type tag, catalog entry, view or
check record changes, so no format version and no D35 review.

**Exact numbers.** Decimal constants are `numeric` in Oracle SQL (D111's "Oracle's constants stay
doubles" no longer holds). `/` divides exactly (`0.3/0.1` is `3`; a quotient that does not end
is cut at `numeric`'s division scale, about 20 digits, where Oracle keeps 38 — a known
difference). `ROUND`, `TRUNC`, `CEIL`, `FLOOR`, `MOD`, `ABS`, `SIGN`, `GREATEST` and `LEAST`
compute in decimal, `TO_CHAR(number, fmt)` formats from the decimal digits, and numbers print as
Oracle prints them (`.5`, `24000`). `TO_NUMBER` reads integers and decimals exactly (`NaN` and
other words are `ORA-01722`, a number past `numeric`'s range `ORA-01426`) and, given a model,
reads by it with the elements `TO_CHAR` writes: `9 0 . D , G $ S MI FM`; text the model does not
describe is `ORA-01722`. The NLS parameter of `TO_NUMBER` and `TO_CHAR` accepts
`NLS_NUMERIC_CHARACTERS = '.,'` only (other characters `ORA-03001`, a malformed string
`ORA-12702`).

**Datetime format models.** `TO_DATE`, `TO_TIMESTAMP` and `TO_CHAR(datetime)` read and write
`DD MM MON MONTH Y YY YYY YYYY RR RRRR HH HH12 HH24 MI SS FF FF1-9 AM PM A.M. P.M. X`,
punctuation, quoted text, `FM` and `FX` (each toggling where it appears); `TO_CHAR` also writes
`D DAY DY DDD J SSSSS`, which `TO_DATE` refuses with `ORA-03001` until item 42b. Names follow the
element's capitalisation, `MONTH` and `DAY` are padded to nine characters unless `FM`. Reading
follows the String-to-Date Conversion Rules: blanks ignored, punctuation left out or replaced by
one other punctuation character, trailing time fields left out, the alternatives `MM`→`MON`→
`MONTH`, `MON`↔`MONTH`, `YY`→`YYYY`, `RR`→`RRRR`, and with `FX` an exact match (the page's FX
table is tested whole). `RR` follows the century rule on the statement clock's year; `YY` takes
the current century. Left-out fields default to the first day of the current month at midnight.
Years are 1 to 9999 (`ORA-01841`): the engine counts a year 0 and Oracle has none, so years before
1 wait for AD/BC in 42b. Elements Oracle writes but never reads (`CC`, `IW`, `Q`, `WW`, `YEAR`
and the like) are `ORA-01820` in a reading model; the remaining elements (`DS`, `DL`, `TS`,
`TZH`/`TZM`/`TZR`/`TZD`, `RM`, `E`, `SP`, `TH`, AD/BC) are `ORA-01821` until 42b. By judgement,
the Format Models page's 22-character limit is not applied (Oracle's own default
`NLS_TIMESTAMP_FORMAT` is longer); a model over 1,000 bytes is `ORA-01801`. Parsed models are
cached per thread, up to eight, and the cache is emptied when a statement starts, so a constant
model is parsed once per statement (D7). `TO_CHAR` checks the largest text a model can produce
against the session's value limit before it builds it (D119).

**Declared types choose the format.** `TO_CHAR(d)` without a model, `||` and `CONCAT` write a
datetime by the NLS format its declared type selects: `NLS_DATE_FORMAT` for a `DATE` (and an
unknown type), `NLS_TIMESTAMP_FORMAT` for a `TIMESTAMP(p)` with `FF` printing `p` digits, and
`NLS_TIMESTAMP_TZ_FORMAT` in the session's time zone for a time zone column. Other string
functions given a date use the `DATE` rule (a known difference).

**NLS settings are session state.** `ALTER SESSION SET name = value [...]` applies left to
right. `NLS_DATE_FORMAT`, `NLS_TIMESTAMP_FORMAT` and `NLS_TIMESTAMP_TZ_FORMAT` are checked when
set (`FF` in the date format is `ORA-01821`); `NLS_LANGUAGE`/`NLS_DATE_LANGUAGE` accept American
and `NLS_TERRITORY` America (another one is `ORA-12705`); `NLS_NUMERIC_CHARACTERS='.,'`,
`NLS_SORT=BINARY` and `NLS_COMP=BINARY` are what EggDB does. Setting the territory resets the
formats and numeric characters it implies, and the language resets the date language and sort
(the Globalization Support Guide's lists, confirmed by research). Names Oracle has not are
`ORA-02248`; Oracle parameters EggDB does not support (`TIME_ZONE`, `NLS_LENGTH_SEMANTICS`,
`EDITION`, `EVENTS`, `NLS_CURRENCY`, ...) are `ORA-03001`, which item 43 skips by number.
`CURRENT_SCHEMA = x` sets `search_path` to the folded name (`ORA-01435` when the schema does not
exist), and the Oracle dialect now resolves unqualified names through `search_path` as
PostgreSQL's does. The parameters live on the session (`Session::oracle_nls`), next to SQL
Server's status, not in `Settings`: `RESET` and `DISCARD` do not touch them. Each statement of an
Oracle session, `COPY` included, runs with them installed for the thread (`oracle_nls::enter`
beside `constraints::enter` in `run_tokens`), which is what item 43's CSV route relies on.

**Text meeting a date or a number.** A text constant compared with or assigned to a `DATE` or
`TIMESTAMP`, and `CAST(text AS DATE|TIMESTAMP)`, is read by the NLS format the target type
selects (a value of unknown precision tries the date format, then the timestamp format), then as
strict ISO 8601 (`YYYY-MM-DD[ HH24:MI:SS[.FF]]`) and nothing else, so `'now'` is refused. The
ANSI literals `DATE '...'` and `TIMESTAMP '...'` are strict ISO only, never NLS, and a
`TIMESTAMP` literal with an offset is a time zone value. A text constant meeting a number is
read by `TO_NUMBER`'s rules only after the engine's own reading failed, so `WHERE id = '5'` keeps
its path in every dialect. Assignment converts text into date and number columns the same way,
and writes numbers and dates into character columns as Oracle writes them (`.5`, NLS date text;
a time stamp with a fractional second takes the timestamp format). In comparisons and
arithmetic, text meets a number as a number and a date by the NLS format (`'5.5' + 1` is 6.5,
`'x' = 1` is `ORA-01722`).

**Date arithmetic.** `date ± n` and `n + date` cut the date to whole seconds (a `TIMESTAMP`
becomes a `DATE`, as in Oracle), add `n` days and round to the second, so `1/24`, `1/1440` and
`1/86400` are exact; `date - date` is the difference in days, exact when it ends. A
`TIMESTAMP - TIMESTAMP` gives days too, where Oracle gives an `INTERVAL` (a known difference
until 42b). `ADD_MONTHS` keeps the last day of a month on the last day, `LAST_DAY` keeps the time
of day, and `TRUNC(date[, fmt])` takes the year, month, day, hour and minute units.

**MERGE.** The parser builds `ast::MergeStatement` (`parser/merge.rs`, with `MergeRules::oracle()`
allowing `DELETE WHERE`), and `merge.rs` runs it. Deviation from the plan, by judgement: the
plan rewrote MERGE into `UPDATE ... SET c = (subquery)` and `INSERT ... SELECT`, but the engine
has no `INSERT ... SELECT`, so `merge.rs` joins directly. The source (a table or a subquery) is
read once, before anything is written, so a source that reads the target sees it unchanged.
Each target row is matched with the source rows its `ON` condition accepts; when `ON` equates a
target column with a source column of the same kind, the source rows are hashed once by those
columns and only candidates are checked, otherwise every pair is. A target row with more than
one source row passing `ON` and the update's `WHERE` is `ORA-30926` (with or without a primary
key), before anything is written. Matched rows are updated through the update's own row writer
(indexes, keys, foreign keys and checks), then the updated rows whose new values satisfy
`DELETE WHERE` are deleted, then the source rows that matched no target row and pass the
insert's `WHERE` are inserted through the `INSERT` path. An updated `ON` column is `ORA-38104`,
an ambiguous unqualified name `ORA-00918`, `DEFAULT` in `VALUES` and subqueries in `MERGE`'s
clauses `ORA-03001`. The result is `MERGE n`, rows updated plus rows inserted. The source, the
hashed keys and the updated rows are charged to work memory (D100). `NEXTVAL` in `VALUES` draws
for inserted rows only, where Oracle draws per source row (a known difference). A failing MERGE
rolls back as any failing Oracle statement that wrote (D108). In the MCP classifier a MERGE with
`DELETE WHERE` whose `ON` names no target column is destructive (shown as a delete without a
filter); any other MERGE is a write.

**Cross-dialect.** The conversion hooks read the session's dialect, as item 39's do: an Oracle
view queried from PostgreSQL computes its Oracle functions with Oracle's defaults, but its
implicit conversions follow PostgreSQL's rules (listed for 42b).

**Engine changes.** `constraints::current_dialect()` copies the enum instead of cloning the
statement context, which every hook benefits from; `eval::string_constant` asks
`read_by_dialect`; `execute::assignment_rule` takes the dialect; `update()`'s row writing and
`delete()`'s row removal became `write_updated_rows` and `delete_rows`, which MERGE shares.

**42b**, after item 43: `MONTHS_BETWEEN`, `NEXT_DAY`, `ROUND(date)`, `TO_TIMESTAMP_TZ` and the
zone elements, AD/BC, `J`/`DDD`/`SSSSS`/`D`/`DAY`/`DY` as input with their conflict errors,
`DS`/`DL`/`TS` and the other remaining elements, `EEEE`/`V`/`B`/`C`/`L`/`U`/`PR`/`RN`/`X` in number
models and `NLS_CURRENCY`, `TIME_ZONE`, other languages and territories, `INTERVAL` types and
`TIMESTAMP - TIMESTAMP` as an interval, `TO_DATE(... DEFAULT ... ON CONVERSION ERROR)`, LISTAGG,
`FETCH ... PERCENT`/`WITH TIES`, `||` precedence, division at 38 digits, `NUMBER(p)` range checks
by `p`, `VARCHAR2` byte semantics, dates shown by `NLS_DATE_FORMAT` in `eggdb sql` and the shell,
Oracle conversions in Oracle views read from another dialect, and `NEXTVAL` per source row in
MERGE. The binary's growth from the new modules is measured by CI's footprint lines (D6).
