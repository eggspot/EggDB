## D234 Tenancy by row is an extension of row security keyed on the session's tenant — Decided by the build loop (by judgement, 2026-10-31); refines D20, D22 and D32

Track 4.X-6 asks for tenants isolated by row, schema or database, per-tenant quotas and keys, and
tenants moved online.

- **By row, on the security the engine already has.** `CREATE EXTENSION eggdb_tenancy` installs
  `eggdb_tenancy.isolate(schema, table, tenant_column)`. It turns on and forces row security on
  the table and adds one policy: rows are visible and writable only where the tenant column
  equals the session's `eggdb.tenant` setting (`SET eggdb.tenant = 'acme'`). A connection pool
  sets it per request, and the application's queries stay unchanged.
- **Fails closed.** A session that has not chosen a tenant gets an error, not every tenant's
  rows, because `current_setting` of an unset name errors. Isolation applies to roles without
  the right to bypass row security: the application connects as such a role, never as the
  superuser.
- **Quotas per tenant** in `eggdb_tenancy.tenants (tenant, max_rows)`, enforced on every insert
  by a trigger with SQLSTATE `53400` (configuration limit exceeded), counted per isolated table.
- **By schema or database** needs nothing new: a schema per tenant with its own role (D22), or a
  database file per tenant, which EggDB makes cheap by being one small file (D3).

Left: quotas by bytes and requests per tenant (D25), per-tenant encryption keys with crypto-
shredding (D23, D231), the tenant prefix in the key layout for moving a tenant online between
shards (D20, D212), and tenant-aware `eggdb backup` and restore.
