## D305 SQLite's dynamic typing for `TEXT`, `NUMERIC`, `REAL` and untyped columns, and a class-ordered key encoding for every dynamic column — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); inventory item 48 (brief 3.09), applies D1, D9, D19, D20, D35, D107, finishes D153's "Not yet"

D153 gave SQLite `BLOB` columns the engine's `Dynamic` type and left two things out: columns of
the other affinities kept one engine type each (`TEXT` and untyped columns `text`, `REAL` and
`NUMERIC` columns `double precision`), and keys and indexes on dynamic columns were refused
(`0A000`) because no key encoding ordered the storage classes. SQLite's datatype page
(datatype3.html) is the source for what follows; no SQLite source was read.

**One type with an affinity.** `SqlType::Dynamic` becomes `SqlType::Dynamic(TypeAffinity)`,
where the public `eggdb_sql::TypeAffinity` is `Text`, `Numeric`, `Real` or `Blob`. The SQLite
dialect's column definitions map `CHAR`/`CLOB`/`TEXT` names to `Text`, `BLOB` and no type to
`Blob`, `REAL`/`FLOA`/`DOUB` to `Real`, and the rest (including `BOOLEAN`, `DECIMAL`, `DATE` and
`DATETIME`, which D107 mapped by hand) to `Numeric`. Storing a value first reduces it to its
storage class (D153's rule) and then applies the affinity: `Text` writes a number as SQLite
prints it, `Numeric` turns text that is a well-formed integer or real literal (optional sign and
surrounding ASCII spaces; hexadecimal is not well-formed) into an integer when it fits and a real
otherwise, and a real that is a whole number into an integer, and `Real` does the same and then
makes every number a real. `Blob` keeps the value. A string constant read against such a column
goes through the same affinity, which gives SQLite's comparison rule for a column of `NUMERIC` or
`REAL` affinity and a string (`amount = '12'`); a decimal constant against a dynamic column in
the SQLite dialect is a real, as SQLite's literals are. In the SQLite dialect an integer and a
real now compare by their exact values (SQLite does; PostgreSQL's rounding to `float8` stays in
the other dialects), so a 64-bit integer beyond 2^53 never equals a nearby real.

`INTEGER` columns keep `bigint`: `INTEGER PRIMARY KEY` row ids, `AUTOINCREMENT`, the SQLite file
importer's row-id alias and every integer key rely on it, and text in an `INTEGER` column is the
next step. `CAST` keeps the static mapping it had (`CAST(x AS TEXT)` is `text`, `AS REAL`
`double precision`), so casts are unchanged. Tables that files already hold keep their column
types: nothing is migrated, and only tables created from now on get the new types.

**The file format (security-critical, D35).** A `Blob` dynamic column keeps type tag `24` in
table-definition version 10, byte for byte as v0.2.0 writes it. Any other affinity is type tag
`25` followed by the affinity's code (`1` text, `2` numeric, `3` real), allowed only in the new
table-definition version 13 (`AFFINITY_FORMAT_VERSION`; 12 stays a view version), which is the
version 11 layout plus that tag and is written only for a table holding such a column. An older
release refuses a version 13 table by name; a version 13 table without such a column, tag `25`
in an older version or with another code, and tag `25` in a view or a user-defined type are
damage. View records store no type for a dynamic column (their column types only guard against
a changed source), so views never need tag `25`. Rows are unchanged: a dynamic column of any
affinity holds the four storage-class tags, and the reader accepts all four whatever the
affinity, so a write path that misses an affinity can never make a row unreadable.

**The key encoding.** Keys and index entries of dynamic columns use their own encoding, chosen by
the column's type at every place a key is built (row keys, index entries, unique checks, point
lookups, index ranges and join lookups go through `encode_column_key`): NULL is `0x02` as in
every column (after every value), and a value is `0x01`, a class byte and its body. Numbers
(`0x01`) are the nearest 64-bit float in the existing order-preserving form, then a 16-bit
offset, the integer's exact distance from that float, which is nonzero only beyond 2^53 and at
most 1024; rounding is monotonic, so integers and reals order by exact value, and equal numbers
(`3` and `3.0`) have equal keys, as SQLite's unique indexes treat them. Text (`0x02`) and blobs
(`0x03`) are their bytes escaped as `text` keys are. The classes therefore sort as SQLite's
comparison orders them, so an index range (`k > 2.5`) and an index-ordered `ORDER BY` give what
the SQLite dialect's comparison gives. The planner uses these keys for predicates only in the
SQLite dialect, whose comparison they match. The reader accepts only canonical keys (an offset
that does not round to its float, a negative zero, a non-canonical NaN, an unknown class or text
that is not UTF-8 is damage), so every accepted key re-encodes to the same bytes, which the
decoder robustness test checks over random and truncated bytes.

**Tested by** test vectors for every class and the integer edges (`i64::MIN`, `i64::MAX`,
2^53 + 1), a 50,000-pair ordering property against an independent statement of SQLite's order,
a 200,000-case hostile-bytes test (never a panic, skip and decode agree, only canonical keys),
format tests (version 13 round trip, every truncation damaged, older readers refusing it by
name, `BLOB` tables staying version 10 with tag 24), the committed v0.2.0 sample files (D96),
session tests in the SQLite dialect and the SQLite correctness suite, where D153's
`NUMERIC`-keeps-the-integer difference now matches.

Left out, with roadmap "Next" lines: `INTEGER` columns as dynamic, the `TEXT` affinity applied
to an integer compared with a `TEXT` column, `CAST(x AS NUMERIC)` giving integers, affinities of
view columns, `PRAGMA table_info` showing the declared text, and per-value classes in the C
API's column kinds for SQLite columns.
