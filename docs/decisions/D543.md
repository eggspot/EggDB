## D543 `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY` and B-tree storage parameters — Decided by the code-only session (2026-11-11, D355); roadmap M5

Migration tools (Rails, Django, Alembic, Prisma, Flyway scripts) write PostgreSQL index changes
with `CONCURRENTLY` and with `WITH (fillfactor = ...)`; the PostgreSQL dialect now runs them
instead of refusing them.

- **`CONCURRENTLY`:** `CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY` build or drop the
  index as the plain statements do. EggDB's build holds the writer while it runs, so other writes
  wait instead of carrying on beside it, which is the difference `CONCURRENTLY` exists to avoid
  on PostgreSQL; the result is the same index. PostgreSQL's refusal inside a transaction block
  (`25001`) is not reproduced. Other dialects still refuse the word.
- **Storage parameters:** `WITH (fillfactor = n, deduplicate_items = on|off)` on an index is
  read and ignored (EggDB's B-tree pages have no fill factor), and `TABLESPACE pg_default` is
  accepted; other parameters and tablespaces are refused by name.
- **Left out:** partial, expression and covering (`INCLUDE`) indexes and `NULLS NOT DISTINCT`,
  which need the index definition's stored form to grow (a file format change with its review).

**Status:** code written, unbuilt (code-only mode, D355).
