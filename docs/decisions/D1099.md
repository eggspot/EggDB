## D1099 Page-level remote storage: the database file as versioned 1 MiB chunks in object storage, with a local cache — Decided by the code-only session (2026-11-13, D355); roadmap M18 (D18, D226)

- **Below the engine, not inside it.** The page store is a `File` (`eggdb::page_store::PageStoreFile`), plugged in through a new `DatabaseFile::Custom` variant, so the page cache, the log, checkpoints, crash recovery and checksums work unchanged. A missing page is a cache miss in the page cache, which reads the file, and the file fetches the chunk from object storage. The format stays the same at every size (D4).
- **Chunks and a manifest.** The file is cut into 1 MiB chunks, each stored as `chunks/<index>-<version>`. The `manifest` object lists every chunk's version, the file's size and a generation. A sync uploads each chunk written since the last one under the next generation, then the manifest, which switches the remote state to the new chunks in one object write, then removes superseded versions. A crash between uploads leaves the previous manifest, which names only complete chunks, so the remote copy is always a state the file had at a sync. The engine syncs at every durable commit, and its log lives inside the file, so each commit ships the log chunks it filled, segment by segment, and each checkpoint ships the data chunks it wrote.
- **Local cache.** A local file holds the chunks fetched or written. A `.chunks` sidecar records which chunk versions it holds, so a restart refetches only chunks the manifest has moved on. A new node with an empty cache opens at once and fetches only what it reads (D226's "start without a full download").
- **Where.** `Database::open_page_store(objects, cache, options)` takes any `ObjectStore` (`get`, `put`, `delete`), with `MemoryObjects` for tests. `eggdb serve --page-store s3://bucket/prefix` uses the S3 client of D226 with its usual environment settings, and the served file as the cache.
- **One writer.** Object storage has no lock this code relies on, so one server writes a page store at a time (stated in the guide). Fencing with conditional writes, and readers following a writer's manifest, are left for later.
- **Cost.** Each durable commit costs at least two object writes (a chunk and the manifest). Workloads that need lower latency use `Durability::Normal`, whose group commit (D59) batches syncs, or archives instead (D226).
