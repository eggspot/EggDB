## D1085 A memory floor and size budgets per microcontroller profile — Decided by the code-only session (2026-11-13, D355); roadmap M17 (D41, D230, D354, D1084)

- **The profile.** `cortex-m3 engine` is EggDB's storage engine on a Cortex-M3: the QEMU run of D1084.
- **What is measured** (`scripts/footprint-cortex-m.sh`):
  - `code_bytes`: the vector table, `.text`, `.rodata` and `.data`'s image in flash, read from the release
    ELF by `llvm-size` (rustup's `llvm-tools`). The emulated flash array is now zeroed `.bss`, erased at
    start, so it no longer counts as code.
  - `heap_peak_bytes`: the bump allocator's high-water mark when the run ends. The allocator never frees,
    so this is the most the engine took.
  - `frame_bytes`: the page cache's frames, which the caller gives.
  - `static_bytes`: `.data` and `.bss` from the linker's symbols, less the test's own flash array, frame
    buffer and heap reserve.
  - `ram_floor_bytes`: heap peak, frames and statics together. That is the memory floor `docs/embedded.md`
    publishes.
- **Budgets.** They sit in `benchmarks/footprint.txt` as `cortex-m3 engine` lines, in that file's layout.
  The script fails when a value is over its budget. As with every footprint target (D354), it runs in the
  Saturday performance pass, not in CI. CI's `cortex-m` job only runs the program.
  - The first budgets are generous: 512 KiB of code, 512 KiB of heap, 768 KiB of floor. The first measured
    run tightens them, and the values are published with each release.
