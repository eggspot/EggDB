## D948 The page cache placed on a NUMA node — Decided by the code-only session (2026-11-13, D355); roadmap M1, follow-up of D356's `MemoryRegion::place_on_numa_node`

- `PageCache::place_on_numa_node(node)` moves the cache's frames, its one region allocated at open (D77), to the node
  through the platform layer (`mbind` with `MPOL_BIND` and `MPOL_MF_MOVE` on Linux and Android) and keeps them there.
- `eggdb::Options::cache_numa_node(Some(n))` asks for it at open, with the operating system's node number; the
  default `None` leaves placement to the system. It runs before `lock_cache`, so locked pages are already where they
  belong. A node the machine does not have, or a system that cannot place memory, fails the open with
  `ErrorKind::Io` and the system's reason, so a deployment that asked for placement never runs silently without it.
- The roadmap's "shards using it" waits for sharding (D18): today one database has one cache, and a server that wants
  one database per node opens each with its node.
