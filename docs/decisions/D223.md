## D223 The file format's building blocks become a no_std crate, with pages on raw flash — Decided by the build loop (by judgement, 2026-10-31); refines D4, D8, D20 and D41

Part 4.M17-3 asks for the core on a microcontroller with a fixed memory budget over a flash
driver trait, checked under QEMU.

- **The same format at every size starts with the same code.** CRC-32C, the superblock and its
  two header slots, page headers, `PageChecksum` and `FormatError` moved from `eggdb-storage`
  into `eggdb-format`, which builds with `#![no_std]` and `alloc` when its default `std`
  feature is off. `eggdb-storage` depends on it with `std` and re-exports everything under the
  old names, so no caller changed. With `std`, CRC-32C still uses SSE4.2 or the ARM CRC
  instructions after runtime detection; without it, the table-driven code runs. `FileId::random`
  needs the operating system's randomness and stays behind `std`.
- **`Flash` is the driver interface** a board implements: read, erase a sector, program erased
  bytes. `FlashPages` stores page `n` at `n` × the page size, erasing the page's sectors before
  programming it, with the same header and checksum as a file's page. It allocates nothing: every
  call works in the caller's page buffer, which is the fixed memory budget.
- **The format code moved unchanged**: same bytes, same checks, same tests, so the compatibility
  sample files (D96) are unaffected. The crate's tests carry their own copy of the 35-line test
  random generator, because a test-only helper cannot be shared between crates without
  publishing it.

Left: the B-tree, page cache, log and transactions without `std` (they need the platform layer's
embedded backend and a fixed-frame cache), wear levelling and power-loss tests on flash, the
header slots on flash, a QEMU Cortex-M run in CI (a start-up routine and linker script of our
own), and the size and memory budgets per microcontroller profile (D34).
