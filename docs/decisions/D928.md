## D928 Byte quotas per tenant — Decided by the code-only session (2026-11-12, D355); roadmap M6c, follow-up of D234

- `eggdb_tenancy.tenants` gains `max_bytes`. On every insert, and every update that makes a row bigger, of an
  isolated table, the tenant's rows in that table (as their JSON text, `octet_length(to_jsonb(row)::text)`, the same
  measure for every type) plus the change must stay within it, else the write fails with `53400` (configuration
  limit exceeded), as `max_rows` does. Shrinking a row or deleting one is always allowed.
- Like `max_rows` (D234), the quota counts per isolated table, by reading the tenant's rows in it, so it needs nothing
  the application role cannot already read: a running total would need a table every tenant can write, which a
  tenant could reset, since trigger bodies run with the caller's privileges.
- Request quotas and admission control (concurrent statements per tenant) need the server to count statements per
  tenant outside SQL and are left.
