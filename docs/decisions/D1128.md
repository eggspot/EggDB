## D1128 Waiting on predicate locks instead of failing at commit — Decided by the code-only session (2026-11-14, D355); roadmap M3 (D172)

- **What changes.** Before this, a serializable transaction beside the writer (D1123) learned only at commit that
  another one had inserted into a range it scanned, and failed with `40001`. Now its reads take *predicate locks* and
  writers wait for them, as PostgreSQL's and SQL Server's locking serializable levels make writers wait.
- **The locks.** Each scan of table rows takes a shared lock on its key range in the shared lock table (D1126), held
  until the transaction ends; each point read of a row takes one on that key alone. Scans of the catalog take none.
  Only serializable transactions take them (`ConcurrentWrite::holds_predicate_locks`); snapshot ones keep
  first-committer-wins.
- **Who waits.** An exclusive row lock, which every row write in a concurrent block takes, now also waits for any
  other transaction's predicate lock whose range contains the row. `NOWAIT` fails with `55P03` and `SKIP LOCKED`
  passes over the row. Shared row locks (`FOR SHARE`) do not wait for predicate locks, since readers never conflict.
- **Deadlocks.** Range holders count as blockers in the wait graph, so two serializable transactions that each
  write into a range the other read form a cycle. The one that closed it fails with `40P01`, where PostgreSQL's
  SSI would fail one with `40001`; both mean "retry".
- **The commit check stays** as the backstop for writers that take no row locks (blocks on the one writer, key-value
  writes outside SQL), so serializability never depends on every writer taking locks.
- **Left:** predicate locks on index ranges (today a scan through an index locks the index-key range, which row
  writes never test), and lock escalation when one transaction holds very many ranges.
