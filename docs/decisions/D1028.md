## D1028 Replica freshness chosen per request — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D18, D209, D1024)

- A session chooses, with ordinary custom settings so every driver can set them, how fresh a replica's reads must
  be: `eggdb.read_freshness` = `eventual`, `bounded_staleness` (with `eggdb.max_staleness_ms`), `read_your_writes`,
  `causal` or `linearizable`, and `eggdb.read_after` = a replication token `term:sequence`. Setting only the token
  means read-your-writes. Each statement checks before it runs and waits up to `eggdb.freshness_timeout_ms`
  (5,000 ms by default); past that it fails with SQLSTATE 55000 and says what the replica lacks.
- **Tokens.** `SHOW eggdb.replication_token` gives the primary's last batch after a write, and on a replica what it
  applied after a read. Read-your-writes waits for the token of the session's own write; causal consistency is the
  same wait with a token carried across sessions and clients, so anything that read or wrote something passes on
  "at least this much" (the token order is the batch order, a total order consistent with causality).
- **Bounded staleness** needs the replica caught up with the primary's last sequence as last heard (heartbeats carry
  it now, every second while idle) and that hearing to be no older than the bound. **Linearizable** asks the
  primary for its last sequence when the statement begins and waits to apply it, which costs a round trip.
- The checks reach the server's replication state through hooks (`eggdb_sql::set_replication_hooks`) that only a
  replicating server installs; elsewhere every read is fresh and nothing waits.
