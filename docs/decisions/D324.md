## D324 `ON CONFLICT ON CONSTRAINT`, an index predicate on `ON CONFLICT (...) WHERE` inferring a full unique index, and `COPY`'s `REJECT_LIMIT` — Decided by the build loop (EggAgentCode task 20261104-1214, 2026-11-04); roadmap M6a, extends D154 and D32, applies D10 and D9

PostgreSQL's upsert had two spellings EggDB refused with `0A000`: naming the arbiter by its
constraint (`ON CONFLICT ON CONSTRAINT name`) and the index predicate after the conflict columns
(`ON CONFLICT (cols) WHERE predicate`), which SQLite's upsert also has. `COPY`'s `ON_ERROR
ignore` (D154) skipped any number of rows; PostgreSQL 18 bounds it with `REJECT_LIMIT`. Each is
built from the manuals: PostgreSQL's `INSERT` ("ON CONFLICT Clause" and its examples) and `COPY`
pages, PostgreSQL 18's regression expectations for the messages, and SQLite's "UPSERT" page.

- **One conflict target.** `Insert.conflict_target` is now `ConflictTarget`: `Inferred` (the
  plain columns, the expressions and the predicate) or `Constraint(name)`. The parser takes
  `ON CONSTRAINT name` in PostgreSQL, a column list whose elements may be expressions, SQLite's
  `ASC`/`DESC` on an element (PostgreSQL's `42P10` `ASC/DESC is not allowed in ON CONFLICT
  clause` at the list's opening parenthesis, and `NULLS FIRST/LAST`, as `parse_clause.c` raises
  them), and `WHERE predicate` after the list in both dialects. A parenthesized bare column,
  `ON CONFLICT ((a))`, is the column `a`. A
  constraint name counts as a target for `DO UPDATE`.
- **The arbiter by name.** `ConflictArbiter::named` finds the primary key by its constraint name
  (`<table>_pkey` unless named) or a unique index that backs a unique constraint. PostgreSQL
  looks the name up in `pg_constraint`, so a unique index made by `CREATE UNIQUE INDEX` is not
  found: `42704` `constraint "x" for table "t" does not exist`, as is any unknown name; a
  `CHECK` or foreign key of that name is `42809` `constraint in ON CONFLICT clause has no
  associated index`. The arbiter is then the same `PrimaryKey` or `UniqueIndex` the inferred
  target gives, so a conflict on another unique key still fails with `23505`.
- **Partitioned tables.** Each partition's indexes have their own names, so before the rows are
  routed `execute::routed_conflict_target` turns a constraint target into the inferred columns
  of the parent's constraint.
- **Index predicate.** PostgreSQL infers a full unique index whatever the predicate, which only
  narrows the partial ones. EggDB has no partial indexes yet, so the predicate's columns are
  checked against the table (`42703`), a qualifier other than the table's name or alias is
  `42P01` `missing FROM-clause entry for table "zz"` (`excluded` included), a subquery is
  `0A000` `cannot use subquery in index predicate`, and the full unique index on the columns is
  the arbiter; no matching index is `42P10` (in SQLite `ON CONFLICT clause does not match any
  PRIMARY KEY or UNIQUE constraint`). An expression in the target is `42P10` too, as no index is
  on an expression yet.
- **`REJECT_LIMIT n`.** A new `CopyOptions.reject_limit`. It needs `ON_ERROR ignore` (`22023`
  `COPY REJECT_LIMIT requires ON_ERROR to be set to IGNORE`), a count above zero (`22023`
  `REJECT_LIMIT (n) must be greater than zero`), a value (`42601`) and a number (`22P02`). The
  loader checks the count after each skipped row, as PostgreSQL's `CopyFrom` does: the row that
  makes it exceed `n` fails the copy with `22P02` `skipped more than REJECT_LIMIT (n) rows due to
  data type incompatibility` and the context of the field that failed (`COPY t, line L, column
  c: "value"`), and the copy's single transaction loads nothing.

Decided by research: PostgreSQL 18's source raises the limit error with
`ERRCODE_INVALID_TEXT_REPRESENTATION` (`22P02`, `copyfrom.c`, REL_18_STABLE), not `22P04` or
`22000`, so EggDB uses `22P02`. (An earlier version of this entry said `ERRCODE_DATA_EXCEPTION`;
review round 1 checked the source and corrected it.) PostgreSQL rejects an
ON CONSTRAINT name that is only a unique index (`get_relation_constraint_oid` reads
`pg_constraint`), so EggDB does too, while `ON CONFLICT (cols)` keeps inferring such an index.

Left: partial unique indexes (`CREATE UNIQUE INDEX ... WHERE`) and their inference by implication
of the given predicate, indexes on expressions and their inference (`ON CONFLICT
(lower(email))`), `COLLATE` and operator classes on a target column, exclusion constraints as
arbiters, `DO UPDATE ... WHERE`, and the per-row `LOG_VERBOSITY verbose` notices before a
`REJECT_LIMIT` error (they are dropped with the failed copy's result). Also left (review round 2): a
column-level `CONSTRAINT name PRIMARY KEY` or `UNIQUE` keeps the generated name (`t_pkey`), so `ON
CONFLICT ON CONSTRAINT name` finds only the table-level form; and `DO UPDATE` that moves a row to
another partition fails with `23514` instead of PostgreSQL's own refusal of the move.
