## D642 SQLite's own table text after RENAME COLUMN and DROP COLUMN — Decided by the code-only session (2026-11-12, D355); roadmap M5, D273, D294

Migration tools for SQLite (Alembic's batch mode, Django's and Rails' schema checks, Prisma's
diff) read `sqlite_schema.sql` back after an `ALTER TABLE`. EggDB kept the text as written
across `ADD COLUMN` and `RENAME TO` (D273). After `RENAME COLUMN` or `DROP COLUMN` it fell back to
generated text, which loses the user's formatting, constraints written as text, and comments.

- `AlteredTexts::save` now edits the kept text for both, as SQLite does.
- `RENAME COLUMN a TO b` writes `"b"` (quoted, as SQLite writes a renamed identifier) wherever
  the old name stands as a column, matched case-insensitively and skipping strings:
  - the column definition's first word;
  - names inside parentheses: table constraints' column lists, `CHECK` and generated-column
    expressions.

  Column lists after `REFERENCES other_table` name the other table's columns and are left alone,
  unless the reference is to the table itself. The table's indexes get the same rename inside
  their column list and `WHERE`.
- `DROP COLUMN c` cuts the column's definition with the comma before it, or the one after it when
  it is the first column. SQLite refuses to drop an indexed column, so index texts don't change.
- When an edit cannot find what it needs, the text falls back to the generated one, as before.
- Not done: renamed column references in views' and triggers' text.
- Test: the existing kept-text test now follows two renames (a plain column, and one named by
  a `UNIQUE` constraint and an index) and a drop through `sqlite_schema`.
