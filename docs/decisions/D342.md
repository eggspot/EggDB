## D342 PostgreSQL's and MySQL's `TABLE t` as a query, PostgreSQL's SQL `PREPARE`/`EXECUTE` and `CREATE TABLE ... AS EXECUTE`, the storage options of `CREATE TABLE ... AS`, MySQL's `CREATE TABLE ... LIKE`, and SQL Server's `SELECT ... INTO` keeping `NOT NULL` — Decided by the build loop (batch 6, part P7, 2026-11-10); roadmap M5, finishes the leftovers of D323, extends D303, applies D9, D10 and D307

D323 built `CREATE TABLE ... AS` and left its neighbours, which answered `0A000` or a syntax
error. Each is built from the dialects' manuals: PostgreSQL's `CREATE TABLE AS`, `PREPARE`,
`EXECUTE`, `SELECT` ("TABLE Command") and "Storage Parameters" under `CREATE TABLE`; MySQL 8's
"TABLE Statement" and "CREATE TABLE ... LIKE Statement"; SQL Server's "SELECT - INTO Clause".

- **`TABLE name` is `SELECT * FROM name`.** The parser builds that `Select` wherever a query may
  stand (`Parser::table_query`), so `TABLE t` works as a statement, a set operand, a `WITH`
  query, a derived table, a subquery, an `INSERT` source and the query of `CREATE TABLE ... AS`
  in PostgreSQL (`TABLE ONLY t`, `TABLE t *`) and MySQL (with `ORDER BY` and `LIMIT`, which the
  ordinary query tail takes). `TABLE` starts a query only when a name follows it, so nothing that
  reads `table` as a word (`LOCK TABLE`, `GRANT ... ON TABLE`) changes. `EXPLAIN TABLE t` keeps
  its refusal; MySQL's `EXPLAIN ANALYZE TABLE t` is P10's (D345).
- **Storage options are checked, not kept.** EggDB has one table format, so `USING heap`,
  `WITH (...)`, `WITHOUT OIDS` and `TABLESPACE pg_default` change nothing, but everything
  PostgreSQL refuses is refused with its code, in PostgreSQL's clause order: another access
  method `42704` "access method ... does not exist" (`42809` "is not of type TABLE" for the
  index methods), another tablespace `42704` (`pg_global` `22023` "only shared relations ..."),
  an unknown parameter or namespace, a value of the wrong kind or out of PostgreSQL's range
  (with its "Valid values are between ..." detail) and a parameter given twice `22023`, and
  `oids = true` `0A000`. The parameters and ranges are PostgreSQL 16's heap and `toast.`
  options. They are parsed only before `AS`; a plain `CREATE TABLE` keeps refusing them.
- **SQL `PREPARE` and `EXECUTE` live in the session.** `CREATE TABLE ... AS EXECUTE` needs the
  statement it names, and SQL-level `PREPARE` did not exist, so the session now keeps prepared
  statements (`session/prepared.rs`): the text of the statement after `AS` (checked by parsing
  it with untyped `$n`), its declared types and its parameter count. `EXECUTE` evaluates its
  arguments with one scalar `SELECT`, binds them to `$n` as text typed by the declared type (the
  same `Parameters::Values` path the extended protocol uses), parses the text again and runs it
  as the statement, so privileges, read-only transactions, triggers and the MCP filters apply
  to it as to any statement. `CREATE TABLE ... AS EXECUTE` takes the parsed `SELECT` as its
  query (`42809` "prepared statement is not a SELECT" otherwise). `DEALLOCATE` and `DISCARD ALL`
  forget them; a session keeps at most 4096 and 64 MiB of their text (`54000`), the limits the
  PostgreSQL listener uses for its protocol-level statements. An agent's `EXECUTE` is
  classified as running code, so the MCP server asks before it, as for `CALL`.
- **`CREATE TABLE ... LIKE` copies the stored definition.** MySQL copies "the definition of
  another table, including any column attributes and indexes", generated columns and
  partitioning, but no foreign keys. Rebuilding a `CREATE TABLE` from the stored definition would
  repeat every rule of the table's dialect, so `create_table_like` creates the new name through
  the ordinary `CREATE TABLE` path (name resolution, `1050` for an existing name, `IF NOT EXISTS`,
  `TEMPORARY`, the relation and column comments, a new table identifier) and then stores a copy of
  the source's `TableDefinition` under that identifier and name: columns, defaults, identity,
  generated columns, the primary key, every index with its identifier (each table's index entries
  are keyed by its own identifier, so the copy starts empty) and the checks, whose generated names
  `old_..._check` become `new_..._check`. Foreign keys and their constraint states are dropped.
  A partitioned source gets its partition key record and one copy per partition, named
  `new#P#partition` and attached with the same bound and index links, recursively. Nothing on
  disk changes shape: the copies are the records `CREATE TABLE` and partitioning already write.
  A view is `1347` "is not BASE TABLE", a missing table `1146`, and a `TEMPORARY` copy of a
  partitioned table `1562`, as MySQL answers.
- **SQL Server's `SELECT ... INTO` keeps `NOT NULL`.** SQL Server gives each new column "the
  same name, data type, nullability, and value as the corresponding expression", so the rule
  MySQL and Oracle already use (a column copied directly, by name or `*`, from the only table
  of a query without joins or grouping sets keeps its `NOT NULL`) now applies to SQL Server too;
  an identity column, always `NOT NULL`, stays `NOT NULL`.

Not built, on purpose: SQL Server also transfers the identity property, but EggDB's identity and
`AUTO_INCREMENT` counter is read from the furthest row of the primary key, which must start
with that column, and `SELECT ... INTO` makes no key; carrying the identity needs a counter
record of its own, which is a file format change (D35) and so stays on the roadmap, with
`NOT NULL` through inner joins and of non-null expressions (constants, `ISNULL(x, 0)`).

Left: `EXECUTE` of the extended protocol's named statements (kept apart from SQL `PREPARE`),
the storage options in a plain `CREATE TABLE`, `EXPLAIN TABLE t`, the identity property and the
rest of SQL Server's nullability rules in `SELECT ... INTO`.
