## D307 Secrets stay out of `Debug` output, and Kafka, MQTT, AMQP 0-9-1 and 1.0, NATS, STOMP, Bolt, the HTTP listeners and RESP pub/sub hold their memory against the one server budget — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); finishes D284's listeners, refines D254

Two gaps were left open (inventory items 56 and 61). Several structs that hold a password or a
key derived `Debug`, so a `{:?}` in a log line or a panic message printed the secret. And D284's
"Not yet" listed the listeners that kept only their own per-message caps: a logged-in client of
Kafka, MQTT, AMQP, NATS, STOMP, Bolt or one of the HTTP listeners could still grow the server
without bound by sending messages up to those caps on many connections, and a RESP publisher
could fill the queue of a subscriber that does not read with 10,000 messages of up to 512 MiB.

- **Secrets in `Debug`.** Every struct that holds a secret writes its own `Debug`, showing `***`
  (or whether a password is set) in place of the value: `eggdb_pgwire::ConnectOptions` and
  `CancelRequest`, `eggdb_tdswire::TdsConnectOptions`, `eggdb_resp::ServerConfig`
  (`requires_password`), the client's `ServerUrl`, and `eggdb_sql`'s `RoleOptions` and
  `StoredRole`. The message listeners' configs already left their password hashes out. The
  client's own `RedactedConnectOptions` wrapper is gone, since the options redact themselves.
  Each has a test that formats it with `{:?}` and checks the secret is absent.
- **One budget, every listener.** `eggdb serve` gives the same `Arc<MemoryBudget>` of
  `--max-connection-memory` to every listener. As in D284, what a connection holds at or under
  `UNCOUNTED_BUFFER_BYTES` (64 KiB) is not counted, a declared length is held before the buffer
  for it grows, and every hold is a `Reservation` given back when dropped.
  - *HTTP* (REST, Elasticsearch, S3, DynamoDB, SQS, metrics, observability, MCP):
    `eggdb_http::Limits` and `serve_with_limits` hold a body over 64 KiB before it is read (and
    before `100 Continue`) and the response's body before it is sent. A request the budget
    cannot take gets the listener's own refusal: `429 circuit_breaking_exception` for
    Elasticsearch, `503 SlowDown` for S3, `ThrottlingException` for DynamoDB, and `503` with
    `Retry-After` for the rest.
  - *Kafka*: a request's declared length before it is read and its response before it is
    written; one that does not fit ends the connection, as a broker does with a request past its
    limits.
  - *NATS*: what a `PUB` or `HPUB` declares before its payload; `-ERR 'Server Memory Budget
    Exceeded'` ends the connection. A message fanned out to many subscribers is built per
    delivery as it is written, each copy held while it is sent.
  - *STOMP*: a frame's `content-length`, a transaction's staged `SEND` bodies while it stays
    open, and a queue batch while it is delivered (released back to the queue when it does not
    fit); an `ERROR` frame ends the connection.
  - *MQTT*: a packet's remaining length and a retained-message replay; `DISCONNECT` with `0x97`
    Quota exceeded for MQTT 5 (a plain close for 3.1.1) ends the connection.
  - *AMQP 0-9-1*: a content header's declared body size, the read buffer, and a batch of
    deliveries until it is written (released back to its queue when it does not fit);
    `506 RESOURCE_ERROR` closes the connection.
  - *AMQP 1.0*: the bytes of a message sent over many transfer frames, with every other
    unfinished delivery of the connection; `amqp:resource-limit-exceeded` closes the
    connection. Deliveries to a receiving link are held until written, and the ones that do not
    fit go back to their queue for the next round.
  - *Bolt*: twice a message's chunks as they arrive (the message and its parsed fields);
    `Neo.TransientError.General.MemoryPoolOutOfMemoryError` ends the connection, since the rest
    of the message is never read. A `PULL` whose records do not fit fails with the same code and
    the connection goes on after `RESET`, as Neo4j's own memory errors do.
  - *RESP pub/sub*: every message queued for a subscriber holds its bytes, counted from the
    first byte, until the connection's push thread writes it or the connection ends; a
    subscription the budget has no room for does not receive the message, as one past the
    10,000-message queue does not. The hold travels with the message to that thread as an
    `OwnedReservation` (`MemoryBudget::reserve_owned`), which keeps an `Arc` of the budget.
- **The refusal is each protocol's own**, so clients and their retry logic treat it as the
  original's out-of-memory, quota or overload answer.

Tests: per listener, a client past a small budget is refused (or disconnected) and the budget
returns to zero: `crates/eggdb-esrest`, `eggdb-s3`, `eggdb-dynamodb` and `eggdb-http`'s tests for
the HTTP refusals; `a_request_past_the_memory_budget_ends_its_connection_before_it_is_read`
(Kafka); `a_message_past_the_memory_budget_ends_its_connection_and_others_go_on` (NATS);
`frames_and_transactions_past_the_memory_budget_are_refused_and_others_go_on` (STOMP);
`packets_and_retained_replays_past_the_memory_budget_are_refused` (MQTT);
`a_message_body_past_the_memory_budget_closes_its_connection_and_others_go_on` (AMQP 0-9-1);
`a_message_past_the_memory_budget_closes_its_connection_with_resource_limit_exceeded` and
`deliveries_past_the_memory_budget_wait_until_the_ones_before_them_are_written` (AMQP 1.0);
`a_message_past_the_memory_budget_ends_its_connection_before_it_is_read` and
`records_past_the_memory_budget_fail_their_pull_and_the_connection_goes_on_after_reset` (Bolt);
`queued_messages_hold_the_memory_budget_until_they_are_written` (RESP pub/sub) and
`an_owned_reservation_gives_its_bytes_back_on_the_thread_that_drops_it` (`connection_limits`).

### Security review

- *Threat.* The same as D284's: a logged-in client of any listener makes the server allocate
  until the operating system kills it. Every listener of `eggdb serve` now turns that into a
  refusal for the client that asks for too much.
- *Before allocation.* Every listener holds a declared length (HTTP `Content-Length`, Kafka's
  size, NATS's `PUB` count, STOMP's `content-length`, MQTT's remaining length, AMQP 0-9-1's
  body size) before its buffer grows. AMQP 1.0 and Bolt have no declared message length, so they
  hold each frame or chunk (at most 64 KiB) as it arrives.
- *Release on every path.* Holds are `Reservation`s or `OwnedReservation`s, given back when
  dropped, so a connection that ends mid-message, a dropped queued message or a push thread
  that stops on a write error cannot leak budget; the tests check `used_bytes()` returns to zero.
- *Fairness.* A refused request never takes bytes from another connection. A RESP subscriber
  that never reads holds at most its 10,000 queued messages, and its publishers' messages to it
  stop once the budget is full, so it cannot keep other connections' requests out for longer
  than it keeps its subscription.
- *Secrets.* Redacting `Debug` covers `{:?}` in logs, panics and test failures; none of these
  structs implements `Display`.

Not yet: replies built whole before they are measured (RESP's `EXEC`, single large values, a
Bolt record, an HTTP response body) still cost their size for a moment when refused; a Bolt
result's rows waiting for the next `PULL` and Kafka's and the queues' stored messages are
storage, not counted; AMQP 1.0 and AMQP 0-9-1 deliveries that never fit are released and
received again each round until room appears.
