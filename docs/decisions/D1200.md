## D1200 Data-quality checks at scale in `eggdb_catalog` — Decided by the code-only session (2026-11-17, D355); roadmap M6c, data-quality rules at scale (D42, D51, D244)

- **What users get.** Beside the row conditions of `quality_rules` (D244), `eggdb_catalog.quality_checks` declares the checks data teams run in tools like Great Expectations and dbt tests: `rule` (a row condition), `unique` (the listed columns together), `null_ratio` (a column's nulls), `references` (a column's values present in `schema.table:column`), `row_count` (`min..max`, either end open) and `freshness` (the newest value of a time column within an interval, a day by default). Each has an allowed failure ratio, a severity (`error` or `warning`) and, for the row checks, a sample percentage for large tables. `eggdb_catalog.run_quality_checks([table] [, examples])` runs them (all, or one table's), returns each check's name, severity, verdict, rows checked and failed and a sentence, records the counts in `quality_results`, and keeps up to `examples` failing rows per check as JSON in `quality_failures` for the people who fix them.
- **At scale.** Every check is one aggregate pass over its table (two for `unique`), sampled rows when asked, and nothing is held in memory but the counts; jobs (D27) schedule it like any function.
- **Left.** Incremental checks over only new rows (a watermark column), distribution and drift checks against stored profiles, and alerts on a failed `error` check.
- **Proof.** A unit test declares four kinds against a small table and reads the verdicts and a failing row's example.

**Status:** code written, unbuilt (code-only mode, D355). The catalog script changes reach databases that create the extension after this change.
