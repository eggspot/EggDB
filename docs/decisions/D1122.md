## D1122 Index builds that block neither reads nor writes — Decided by the code-only session (2026-11-13, D355); roadmap M2 (online schema changes and reindexing, D20)

- **Why a long build blocks writers today.** EggDB has one writer at a time, and `CREATE INDEX` backfills every row
  inside one write transaction, so other writers wait for the whole build. Readers never wait, since they read
  snapshots.
- **`CREATE INDEX CONCURRENTLY`** (PostgreSQL's spelling) outside a transaction block builds in many short commits,
  as PostgreSQL's three phases do:
  1. One commit defines the index as *building*. Every write from then on maintains it (inserts, updates and deletes
     go through the same index code), but the planner and join lookups skip it, so no query reads a half-built index.
  2. Commits of 4,096 rows each backfill the existing rows in primary-key order. Other writers take the writer
     between them. A row a writer touched already has its entry, which the backfill puts again unchanged; a unique
     index checks each row against the entries already there.
  3. One commit marks the index ready.
- **Failure drops the index.** A failure in any step, such as a duplicate key (`23505`) or the index being dropped
  under it, drops the half-built index and its entries in one more commit and returns the error. PostgreSQL would
  leave an invalid index for the user to drop instead. Inside a transaction block, `CONCURRENTLY` is refused with
  `25001`, as PostgreSQL refuses it. On a partitioned table the build happens in one commit, as before.
- **The catalog records it.** The building state is bit 2 of an index's flag byte in the table definition's options
  section (beside "unique without a constraint"). A release that does not know the bit refuses the table definition
  as damaged rather than reading through a half-built index. Only a build interrupted by a crash leaves the bit set:
  writes keep maintaining the index, queries never use it, and `DROP INDEX` removes it.
- **Left:** `REINDEX ... CONCURRENTLY` (EggDB's indexes are kept exact in each commit, so a rebuild only matters
  after damage), MySQL's `ALGORITHM=INPLACE, LOCK=NONE`, SQL Server's `ONLINE = ON` and Oracle's `ONLINE` mapped
  onto the same build, `indisvalid`/`indisready` in `pg_index` following the bit, and `ALTER TABLE` changes that
  rewrite rows done in steps the same way.
