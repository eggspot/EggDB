## D146 Index methods and sort order, unique indexes that are not constraints and identity columns in the table definition: format version 9 only for tables that use them, entries still stored ascending, `GENERATED ALWAYS` enforced in PostgreSQL's dialect — Decided by the build loop (by research, 2026-10-30); roadmap item 37 part c (37c, batch part 3.01), applies D9, D10, D20, D35, D109, D118, D129; supersedes in part D118 (`OVERRIDING`) and D129 (what the catalog shows of indexes and identities)

psql's `\d` showed every index as an ascending `btree`, every unique index as a `UNIQUE`
constraint and every identity column as `generated by default as identity`, because the table
definition did not record more (D129). Item 37c records it.

**What the table definition keeps.** Each index keeps its access method (`btree`, or `hash` from
PostgreSQL's `USING hash`; MySQL's `USING HASH` stays a `btree`, as InnoDB keeps it), each
column's order as written (`DESC`, and `NULLS FIRST` or `NULLS LAST` with PostgreSQL's default:
NULLs first exactly when the column is `DESC`), and whether a unique index backs a `UNIQUE`
constraint or was made by `CREATE UNIQUE INDEX` (in MySQL's dialect every unique index backs a
constraint, as there). A table keeps the identity kind of a column when it differs from what
the column already says: `GENERATED ALWAYS` on an auto-increment column made by `CREATE TABLE`,
and `ALWAYS` or `BY DEFAULT` on a column that `ALTER TABLE ... ADD GENERATED` (as `pg_dump`
writes identity columns) gave an owned sequence and a `nextval(...)` default. An auto-increment
column needs no entry to be `BY DEFAULT`; an entry on a column that has neither auto increment
nor a default means nothing and is not written.

**Format version 9 (security-relevant, D35).** Only a table that uses one of these is written in
table-definition version 9: the version 7 layout (constraints part always present, schema
qualified or not), then the identity entries (count, then per entry its column number as a
varint and `1` `ALWAYS` or `2` `BY DEFAULT`, strictly in column order), then for every index in
order its method byte (`0` `btree`, `1` `hash`), a byte `1` for a unique index without a
constraint (`0` otherwise) and two 32-bit little-endian masks over its key positions, `DESC` and
`NULLS FIRST`. Every other table keeps its version and bytes, so files that do not use these stay
readable by older releases, and an older release refuses a version 9 table by name (`0A000`).
Decoding is strict: an unknown method or kind, a mask bit past the index's width, the
"without constraint" byte on a non-unique index, a `hash` index that is unique, has more than one
column or carries an order, identity entries out of order, repeated, past the last column or not
in their canonical form, and a version 9 definition that needs none of it are all damage
(`XX001`), never a panic. Tests pin the bytes, cut every encoding at every length, damage each
marker, feed 20,000 seeded mutations to the decoder and refuse version 10; the D96 sample files
are untouched.

**Entries stay ascending (decided by research).** An index's entries are stored as before:
ascending, NULLs after every value, whatever its method or order. Storing a `DESC` column
inverted would add a second key encoding to every reader of entries (row lookups, unique checks,
the consistency check, the range planner) for a gain only in `ORDER BY` lists that mix
directions; reading backward already serves a `DESC` order (D109), and results never depend on
the entries' order. A `hash` index is one more ordered index here, used for ranges and order
too; PostgreSQL's limits on it (one column, not unique, no `ASC`, `DESC` or `NULLS`) are kept
with PostgreSQL's `0A000` messages, and its column shows as `integer` in `pg_attribute`, as
PostgreSQL's hash codes do.

**What the catalogs show.** `pg_class.relam` is the method's access method, `pg_index.indoption`
the order bits (`1` `DESC`, `2` `NULLS FIRST`), `pg_get_indexdef` writes `USING <method>` and each
column's order as PostgreSQL does, `pg_constraint` holds only unique indexes that back a
constraint, `pg_attribute.attidentity` is `a` or `d` with `atthasdef` false and no `pg_attrdef`
row for a restored identity column, `pg_depend.deptype` is `i` for an identity column's sequence,
and `information_schema.columns` gives the generation and the sequence's start, increment and
bounds. MySQL's `SHOW INDEX` (collation `D`), `SHOW CREATE TABLE`, Oracle's `*_IND_COLUMNS.DESCEND`,
SQL Server's `sys.index_columns.is_descending_key` and `.schema`'s `CREATE INDEX` statements show
the order; the public `IndexSchema` gains `method` and `orders`. In PostgreSQL's dialect
`ALTER TABLE ... DROP CONSTRAINT` finds only constraints, and `ALTER COLUMN ... SET DEFAULT` or
`DROP DEFAULT` on a recorded identity column is `42601`, as there.

**`GENERATED ALWAYS` is enforced (decided by research).** Recording `ALWAYS` without its rule
would show one thing and do another (D10). An `INSERT` that gives an `ALWAYS` column a value is
`428C9 cannot insert a non-DEFAULT value into column "id"` with PostgreSQL's detail and hint,
unless it says `OVERRIDING SYSTEM VALUE`; `OVERRIDING USER VALUE` (refused before, D118) ignores
the values given for identity columns; an `UPDATE` may set an `ALWAYS` column only to `DEFAULT`.
`COPY`, bulk loads and restores keep the values they bring, as `COPY` does in PostgreSQL, and
`pg_dump --inserts` writes `OVERRIDING SYSTEM VALUE`. Oracle's `GENERATED ALWAYS AS IDENTITY` is
not recorded yet, so Oracle restores and scripts that give identity values keep working; its
`ORA-32795` waits for the Oracle follow-ups. An auto-increment column made by `serial` still
looks like an identity column, as D129 decided, since the table definition does not tell the two
apart.
