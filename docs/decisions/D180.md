## D180 Reading SQLite's file format with our own reader; SQLite files open as copies in memory — Decided by the build loop (by judgement, 2026-10-31); refines D5, D13 and D35

Part 4.M5-3 asks to open, query and write `.sqlite` files directly. Reading comes first:

- **`eggdb-sqlite-format`** is a crate of our own, with no dependencies, written from SQLite's
  published file format description. It reads the 100-byte header (page size, reserved bytes,
  UTF-8 only), table b-trees with interior and leaf pages, the record format and its serial
  types, overflow chains, and `sqlite_schema`. With a `-wal` file beside the database, it lays
  over the pages of every frame up to the last commit whose salts and cumulative checksums hold,
  as a reader opening after a crash would. Every offset, length, page number and chain is
  checked, b-tree walks are bounded in depth and refuse loops, and a fuzz test of 5,000 mutated
  files gives errors, never panics. `WITHOUT ROWID` tables and UTF-16 databases are refused by
  name.
- **The command line** opens a file in SQLite's format as a database in memory (D175). It
  creates the tables, inserts the rows (filling an `INTEGER PRIMARY KEY` from the rowid, as
  SQLite stores it), then creates the indexes, views and triggers, and says on stderr that
  changes are not written back. A test in `eggdb-sqlite-compare` writes files with SQLite itself,
  in rollback and WAL mode, with overflow pages, and checks every row.

Left: writing the format back (the B-tree writer, the rollback journal and the WAL), so that
files we write pass `PRAGMA integrity_check`; `WITHOUT ROWID` tables; UTF-16; and
`eggdb restore` from an SQLite file into an EggDB file.
