## D866 `client_encoding` on the PostgreSQL wire — Decided by the code-only session (2026-11-12, D355); follow-up of D830

- `client_encoding` (in the startup packet, `SET`, or `PGCLIENTENCODING` through libpq) now takes PostgreSQL's
  single-byte encodings — `LATIN1`, `LATIN9`, `WIN1252` and the D830 tables (`WIN1251`, `KOI8R`, `LATIN2`...) under
  their names and aliases — as well as `UTF8` and `SQL_ASCII`. The multi-byte ones (`SJIS`, `EUC_JP`, `GBK`, `BIG5`...)
  stay 0A000 until their tables exist.
- `eggdb_sql::ClientEncoding` is the public form of those encodings: `decode` (a NUL or an undefined byte is an
  error), `encode` (a character with no byte is 22P05, as in PostgreSQL) and `encode_lossy` (`?` for such a
  character).
- The PostgreSQL listener reads the session's encoding before each message. Query and statement text, portal and
  statement names and text-format parameters are decoded from it; text-format result values are encoded to it, and a
  value it cannot hold fails the statement with 22P05; row descriptions, command tags, parameter statuses,
  notifications and error and notice fields are encoded with `?` for what it cannot hold, so an error always reaches
  the client. Binary-format values and parameters are never touched.
- `COPY` without `ENCODING` now uses the client encoding, as PostgreSQL's does, so `\copy` from a LATIN1 client reads
  and writes LATIN1 data.
- A `SET client_encoding` inside a multi-statement query string takes effect from the next message. The startup
  packet's authentication fields and SASL messages stay UTF-8.
- Left: the multi-byte encodings, and the MySQL, SQL Server and Oracle character set lists.
