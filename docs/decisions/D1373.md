## D1373 Oracle's ROWID, UROWID, XMLTYPE, VECTOR, SDO_GEOMETRY and LONG RAW columns — Decided by the code-only session (2026-11-25, D355); roadmap M10 "Oracle's types" (D19), the types EggDB already has a home for

- **What users get.** Oracle DDL with these column types now creates the table instead of failing: `ROWID` and `UROWID(n)` keep the row id text an application stored (EggDB's own `ROWID` pseudo-column stays as it is), `XMLTYPE` keeps the document's text as SQL Server's `xml` does, `VECTOR(dimensions, format)` is EggDB's vector type (D2, the one `<->` and the vector indexes use), `SDO_GEOMETRY` is EggDB's geometry type, and `LONG RAW` is bytes.
- **Why these mappings.** Each matches what applications do with the column: store and read back the value, compare it, pass it to the dialect's own functions where EggDB has them. The arguments Oracle takes (`UROWID`'s length, `VECTOR`'s dimension count and number format, an `XMLTYPE` schema) are read and set aside, as for a `VARCHAR2` length in byte or char semantics; a value of another dimension count is the vector type's own error.
- **Still refused.** `BFILE`, a locator to a file outside the database, which a single-file engine (D3) has nowhere to point; it stays `not supported` with its name. The `XMLTYPE` storage clauses and object and collection types are left.
- **Proof.** An Oracle test creates a table with each type, stores a row id and an XML document and reads them back, and refuses `BFILE` by name.

**Status:** code written, unbuilt (code-only mode, D355).
