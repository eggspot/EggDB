## D370 A failing MySQL `CALL` keeps the procedure's statements before the failing one — Decided by the code-only session (2026-11-10, D355); roadmap M3, closes one of D317's leftovers

MySQL runs each statement of a procedure as a statement of its own: when one fails, its changes
are undone and the statements before it keep theirs (committed at once under autocommit, kept
in the open transaction otherwise). D317 undid the whole `CALL`.

- **Where the failing statement starts.** The statement-level undo log (`UndoWrite`, D317)
  publishes its length to a thread-local (`undo_marks::note_undo_length`) when it opens and
  after every entry. The routine interpreter, before each statement of a MySQL routine
  (`plpgsql::statements::run_statement`), copies that length as the latest statement start
  (`mark_procedure_statement`). The session clears both before each statement.
- **Undo.** When a MySQL `CALL` fails, the session undoes back to the latest statement start
  instead of the statement's own start, in a transaction (with or without savepoints). Under
  autocommit, a MySQL `CALL` now writes through an undo log too; on failure it undoes back to the
  failing statement and commits the rest, then reports the error.
- **Cost.** Only MySQL `CALL` under autocommit gains an undo log, bounded by the work-memory limit
  like every statement in a transaction; a procedure that overwrites more than that fails where
  it ran before, with the undo log's own error.

**Left:** a statement inside a trigger or stored function that a procedure's statement runs also
marks a start, so a failure there keeps the partial work of the statement that fired it; MySQL
undoes that statement whole.

**Status:** code written, unbuilt (code-only mode, D355).
