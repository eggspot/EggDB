## D1337 Concurrent transactions spill their changes to sorted scratch runs, instead of row versions in the engine — Decided by the code-only session (2026-11-25, D355); roadmap M2 "Row versions in the storage engine (MVCC), so changes larger than memory spill" (D172)

- **The question.** D172 put concurrency above the single-writer engine: a concurrent transaction reads a snapshot, keeps its writes in a map, and checks and applies them at commit. Its one limit was that the map lives in memory, so a transaction's changes had to fit in it; the roadmap names engine-level row versions (MVCC) as the way to lift that.
- **Decided.** The limit is lifted where it sits, in the write set, without versioning rows in the B-tree. Engine-level MVCC (version chains in leaves, visibility per transaction, garbage collection of old versions) would rebuild the storage engine D86 and D172 chose to keep, for a goal a spilling write set reaches with the existing commit path: reads already come from snapshots (D86), commits already apply in one write transaction, and that transaction may now outgrow the cache (D1333). Row versions stay a candidate for a later decision if many writers on the same rows need more than optimistic validation.
- **What users get.** A concurrent transaction may change more than memory holds: past 32 MiB of changes, they are written as a sorted run to a scratch file beside the database (`<name>-txn-<process>-<n>.spill`, removed when the transaction ends) and memory starts over. A get looks at memory, then the runs from the newest; scans, the snapshot-isolation check and the commit walk all of them merged in key order, the newest change of each key winning, one entry at a time. Each run keeps a sparse index of its 64 KiB blocks, so a get reads one block. An in-memory database keeps its changes in memory as before.
- **Left.** Two-phase commit's prepared record still holds all changes in one value (`PREPARE TRANSACTION` of a transaction larger than a value fails as before); serializable read sets and collection changes stay in memory.
- **Proof.** Write-set tests: five rounds of overlapping puts and deletes with a 4 KB budget spill several runs; every key reads back its newest change, a full walk and a range walk equal a model, and dropping the set removes its scratch files; an in-memory database never spills. The existing concurrent-transaction tests run unchanged on the new write set.

**Status:** code written, unbuilt (code-only mode, D355).
