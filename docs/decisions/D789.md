## D789 Writing WITHOUT ROWID tables into SQLite files — Decided by the code-only session (2026-11-12, D355); roadmap M5, SQLite files

- `eggdb-sqlite-format` gets `SqliteObject::WithoutRowidTable { name, sql, rows, primary_key, orders }`. Its rows,
  given in column order, are stored as SQLite stores them: one index b-tree record per row holding the primary key
  columns in key order, then the other columns in table order, sorted with the same comparison as indexes (D631), and
  `sqlite_schema` lists it as a `table` whose root is that index b-tree. Rows of unequal length, a key that does not
  fit the columns, and two rows with the same key are refused rather than written into a file SQLite would call
  corrupt.
- `VACUUM INTO` (D631) writes `WITHOUT ROWID` tables instead of refusing them. Their primary key makes no
  `sqlite_autoindex` (the table is that index); their `UNIQUE` constraints and explicit indexes hold the key columns
  followed by the primary key columns not already among them, which is what SQLite keeps in place of the rowid.
  Tables with virtual generated columns are still refused, since leaving those columns out would shift the key.
  Primary key columns are written ascending: EggDB's table definition does not keep a key column's `DESC`.
- Left: `DESC` primary key columns, writing UTF-16 files (only editing a UTF-16 file in place would need it), and
  editing files in place.
