## D1195 SQL Server's column `DENY` — Decided by the code-only session (2026-11-17, D355); roadmap M6b (D285); security-critical (D35)

- **What users get.** `DENY SELECT (secret) ON items TO reader` (and `ON OBJECT::items (secret)`, for `SELECT`, `INSERT`, `UPDATE` and `REFERENCES`) refuses those columns to the role and the roles that belong to it, whatever else they hold on the table or the column, as SQL Server's denial wins over every grant: a statement that uses the column fails with `42501`, `SELECT *` loses it as for any column not granted, and `has_column_privilege` says false. A later `GRANT` or `REVOKE` of the same column privilege clears the denial, as in SQL Server, and a `DENY` removes the same column grant.
- **Storage.** Its own key space (`COLUMN_DENY_SPACE` 0x1F) keyed like the column grants. A table's drop forgets them, and renaming the table or a column moves them, dropping a column forgets its own; the access snapshot loads them. The column reach a statement is checked with gains `EveryBut`, for a role that holds the privilege on the table but is denied some columns.
- **Proof.** A unit test denies one column after a table grant, reads the two columns' privileges, grants the column again and reads it back.
- **Security review.** As a D35 change it needs a security-only review pass once built.
