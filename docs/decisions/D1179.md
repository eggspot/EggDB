## D1179 Objects transformed on the way out: resize, crop and convert with our own codecs, or a WebAssembly function — Decided by the code-only session (2026-11-15, D355); roadmap M6a (generated APIs, D37), builds on D1078

- **Images.** D1078's renditions (PNG and baseline JPEG codecs of our own, Exif orientation, area-averaging scaling) gain `eggdb_content::transform`: crop a rectangle first, then fit the box as `contain` (inside it, keeping the shape), `cover` (over it, keeping the shape, centred, overflow cut off) or `fill` (stretched to it), and write PNG or JPEG at a quality. A box side given alone takes the other from the picture's shape. Pictures are not enlarged unless asked (`enlarge`), so a thumbnail request never inflates a small original; a box over 65 535 pixels a side or 64 megapixels is refused. The resampling already handled enlargement, so it was only split out of `fit` (`resampled`).
- **On object storage.** An S3 `GET` (or `HEAD`) with `x-eggdb-transform=<options>` answers the transformed object instead of the stored one, in the style of image proxies (imgproxy, Supabase's image transformations), so an `<img>` URL (a presigned one included, since the parameter is signed with the rest of the query) can ask for `w:400,h:300,fit:cover,format:jpeg,q:80` or `crop:10_20_300_200`. Options are comma-separated `key:value`: `w`, `h`, `fit`, `crop` (`x_y_width_height`), `format` (`png`, `jpeg`), `q` (1 to 100), `enlarge` and `wasm`. The response has an ETag of its own (the object's ETag and the options, hashed), so caches keep one per variant; `Range` is refused with a transform, objects over 64 MiB are not transformed, a bad option is `400` `InvalidArgument`, and a picture that cannot be decoded is `422`.
- **WebAssembly extensions.** `wasm:<name>` runs a named transform before any image options, through the `eggdb_s3::ObjectTransform` hook. `eggdb serve` supplies it as a call of the SQL function `storage_transforms.<name>(bytea, text) returns bytea` with the object's bytes and content type, in the server user's session: a function written in WebAssembly (`CREATE FUNCTION ... LANGUAGE wasm`, D27) with EggDB's sandbox and limits (D45) becomes an object transform, a watermark or a format EggDB has no codec for. Only names of letters, digits and `_` are accepted, and only that schema is searched, so a URL cannot call any other function. A transform that fails or returns NULL is `422`; a server without the hook answers `501`.
- Not yet: caching transformed variants in the store, WebP and AVIF codecs of our own, and transforms on the other object APIs (WebDAV, Couch attachments).
- Tests: `transforms_crop_then_contain_cover_or_fill_the_box` in `eggdb-content`, `transform_parameters_read_as_their_options` and `objects_are_transformed_on_the_way_out` in `eggdb-s3`.
