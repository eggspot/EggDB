## D153 Named time zones from the embedded IANA source compiled per region, infinite intervals, MySQL's full `TIME` range and SQLite `BLOB` columns as a dynamic type — Decided by the build loop (by judgement and the public documentation of PostgreSQL, MySQL, Oracle, SQLite and the IANA time zone database, 2026-10-30); roadmap item 31b (batch part 3.09), applies D1, D3, D6, D8, D9, D19, D20, D30, D35, D111, D113, D130, D149, D152

Item 31 (D113) left named time zones, infinite intervals, MySQL's `TIME` outside a day and
SQLite `BLOB` columns to later; items 36 (D130) and 42b (D149) refused region names (`22023`,
`ORA-01882`) until a time zone database existed. They are built here.

**The time zone database is IANA's public-domain source, embedded.** EggDB ships the release's
one-file source, `tzdata.zi` (the rearguard form, whose daylight saving flags are the ones
PostgreSQL shows: Dublin's summer is daylight time), as data in `eggdb-sql`
(`src/time_zones/tzdata.zi`, release 2026e). The engine never reads the operating system's
zone files (D8, D3): one binary gives the same answers on every platform, in the browser and on
an embedded device. The file costs about 105 KiB of binary size, a stated growth under D6; it is
text, so a release's change is reviewable as a diff. Nothing is parsed until a region is first
named: the first lookup indexes the file's zones, rules and links (an alias resolves to its
target's lines under its own name, as PostgreSQL shows `US/Eastern`), and each region is
compiled once by our own compiler (`time_zones/compile.rs`, written from the format zic(8)
documents) into the UTC instants of its offset changes through 2037 and, for a region whose
rules continue, those rules, applied per year after that. Compiled regions are kept for the
process's life (a few hundred at most). Updating the database is replacing `tzdata.zi` with a
new release's file and the version its unit test names; nothing else changes.

**One `TimeZone` type for every dialect.** `eggdb_sql::TimeZone` is a fixed offset or a
compiled region. The session's `TimeZone` setting, the statement clock, `AT TIME ZONE`,
`make_timestamptz`, `timestamptz` input and output, `to_char`'s `TZ` (the region's
abbreviation), `to_timestamp`'s `TZ`, Oracle's `TIME_ZONE`, `TZR`, `FROM_TZ`, `TZ_OFFSET` and
`SESSIONTIMEZONE`, MySQL's `time_zone` and the PostgreSQL protocol's text results all use it.
`TimeZone` names are read as PostgreSQL reads them: `UTC` and its spellings, POSIX-style offsets
(`+03` is west), a plain number of hours east for the setting, then a region in any letter case;
anything else is `22023` (it was accepted and ignored before). A local time is resolved as
PostgreSQL documents for invalid or ambiguous time stamps: a time a spring-forward change skips
takes the offset from before the change, a time a fall-back change repeats the offset from after
it. `timestamptz ± interval` adds months and days on the local calendar and the time part as
elapsed time, as PostgreSQL does, which only differs from the earlier fixed-offset arithmetic
across a region's change. `pg_timezone_names` lists the regions. Left out: time zone
abbreviations in input, `pg_timezone_abbrevs`, POSIX rule strings as `TimeZone`, SQL Server's
Windows zone names, and the rest of IANA's history before 1970 that the `backzone` file holds
(PostgreSQL leaves it out too).

**Infinite intervals as PostgreSQL 17 represents them.** `infinity` is the interval whose months,
days and microseconds are all at their maximum and `-infinity` all at their minimum, so they
need no new storage: they compare above and below every finite interval by the existing length
order, and the file format is unchanged. Arithmetic follows PostgreSQL 17 (`infinity -
infinity`, a zero factor and a NaN are `22008`), and a finite result that would equal a
sentinel is out of range. A time stamp plus an infinite interval stays `22008` until infinite
time stamps exist.

**MySQL's `TIME` range in the same `time` type.** A stored `time` may hold `-838:59:59` to
`838:59:59`; text is read with MySQL's forms when the statement's dialect is MySQL, and
PostgreSQL's dialect still reads `00:00:00` to `24:00:00`. The decoder's validity check widens to
that range: old files decode as before, and a file holding a wider value is refused by an older
binary as damaged, never misread (D35's compatibility tests keep passing). The MySQL protocol's
binary `TIME` sends the sign and days.

**SQLite `BLOB` columns as `SqlType::Dynamic`.** A column declared `BLOB` gets the engine's
`Dynamic` type, which keeps each value in its storage class (integer, real, text, blob; other
values as their text). Its type tag (24) is written only in table-definition version 10, which
D152 introduced in the same unreleased batch, so no new version number is needed. Static typing
treats such a column as untyped, values compare across classes in SQLite's order in the SQLite
dialect, and keys and indexes on it are refused (`0A000`) until a class-ordered key encoding
exists. Columns of SQLite's other affinities keep their engine types (D107), and untyped columns
stay `text`, because changing them would change the types of tables existing files already hold.
