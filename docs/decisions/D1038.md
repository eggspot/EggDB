## D1038 The cluster transport and `eggdb serve --cluster` — Decided by the code-only session (2026-11-13, D355); roadmap M15 (D211, D212)

- `eggdb serve --cluster 1=host:port,2=host:port,3=host:port --cluster-node <id>` runs the server as one voter of a
  Raft group. Each server listens on its own address for the cluster's traffic, separate from the client protocols.
- **Transport.** Frames are the replication protocol's (length, kind, payload) with the same login: the listener sends
  a fresh challenge, the peer answers with the server user's HMAC proof and its node id. Raft messages travel in
  `RAFT` frames as `eggdb_consensus::wire` encodes them (fixed big-endian numbers, length-prefixed entries and data,
  every length checked against the bytes left). Each server keeps one outgoing connection per peer, opened on demand
  and at most once a second, and drops messages while a peer is unreachable, which Raft tolerates; incoming
  connections feed one queue. Off this machine the traffic needs TLS, as replication does (`--cluster-ca` checks the
  peers).
- **One driver thread** owns the `Node`: it steps queued messages, ticks every 100 ms, proposes new batches while it
  leads, stores `take_changes` with `Database::save_consensus` before sending anything, applies committed entries, and
  compacts the log above 20,000 entries (keeping 10,000).
- **What the log carries** is D209's replication batches, as D211 said. The leader is a replication primary in
  synchronous mode with one acknowledgement: a client's commit is made locally, captured as a batch, proposed, and the
  commit returns once the cluster committed that entry (the driver acknowledges it then). Followers apply committed
  batches in sequence; their database is fenced with the leader's id, so writes there are refused with where to send
  them. A server leads (`promote`, unfenced) only once it has committed an entry of its term and applied everything
  committed, so it never takes writes on an incomplete database.
- **Divergence is detected, not repaired in place.** A leader can commit a write locally that the cluster loses if it
  fails before the entry commits. Batches carry their predecessor's term, so a server whose database holds a batch the
  cluster did not commit sees the mismatch (or a gap) when the cluster's batch at that sequence arrives, and stops with
  a message to start again with `--cluster-seed`. The same flag serves a server that fell behind the compacted log
  (its node reports an installed snapshot). `--cluster-seed` asks the voters for the leader, which backs up its
  database, reads the batch the copy ends at, waits until the cluster has committed it, and sends the Raft index,
  term and configuration of that batch before the file; the new server resets its Raft state to that snapshot
  (`Database::reset_consensus`) and joins from there.
- Left for later items: adding and removing voters from the command line (the node supports joint consensus, D1037),
  streaming snapshots inside the Raft protocol instead of a restart with `--cluster-seed`, leases for follower-free
  reads at the SQL layer, and the shard map on top (D212).
