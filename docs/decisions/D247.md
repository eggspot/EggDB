## D247 Leases with fencing tokens and OpenFeature flags in the `eggdb_coordination` extension — Decided by the build loop (by judgement, 2026-10-31); refines D54

Track 4.X-19 asks for locks and leases with fencing tokens, leader election, watches and service
discovery, the etcd v3 and ZooKeeper protocols, a configuration store with OpenFeature flags,
a secrets store with dynamic credentials, an LDAP v3 server and SCIM, the Active Directory
specifications, and WebAuthn. This slice does leases, leader election and flags in SQL.

- **Leases are rows, tokens a sequence.** `acquire` locks the lease's row (`FOR UPDATE`), so two
  candidates in one database cannot both win, and takes a new fencing token from one sequence
  for every change of holder, so tokens only grow (Kleppmann's fencing). A renewal keeps the
  token. Expiry is by the database clock, so clients need no synchronised clocks.
- **Flags follow the OpenFeature evaluation API's vocabulary** (flag key, variants, default
  variant, targeting, evaluation context, resolution reason, `FLAG_NOT_FOUND`), so an OpenFeature
  provider for EggDB is a thin call to `evaluate_flag`. Targeting starts with "attribute in
  list"; flagd's full JsonLogic comes later.
- **Same engine, same guarantees.** Leases and flags are ordinary tables, so they replicate and
  back up with the data; on a cluster they rely on the consensus of M15 for one holder across
  nodes.

Left: watches and service discovery (on change streams, D28), the etcd v3 gRPC API, the
ZooKeeper protocol, JsonLogic targeting and fractional rollouts, the secrets store, LDAP v3 and
SCIM, MS-ADTS, and WebAuthn.
