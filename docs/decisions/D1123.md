## D1123 SQL sessions on concurrent transactions — Decided by the code-only session (2026-11-13, D355); roadmap M3 (SQL sessions on concurrent transactions with each dialect's isolation levels and errors, D172, D173)

- **Which blocks run concurrently.** An explicit transaction block whose isolation is `REPEATABLE READ` (or SQL
  Server's `SNAPSHOT`) runs on a snapshot-isolation `ConcurrentTransaction` (D172); `SERIALIZABLE` runs on a
  serializable one. The isolation comes from `BEGIN ISOLATION LEVEL ...`, `START TRANSACTION ISOLATION LEVEL ...` or
  `SET TRANSACTION ...`. These blocks no longer hold the database's one writer while they run: their writes stay
  in the transaction until `COMMIT`, which takes the writer for one short check-and-apply.
- **What stays on the one writer.** Autocommit statements and `READ COMMITTED` and `READ UNCOMMITTED` blocks keep it.
  Those levels never fail a write for a concurrent change in PostgreSQL, MySQL, SQL Server or Oracle; they wait on
  row locks instead. Running them optimistically would surprise applications with serialization failures they were
  never written to retry. Row locks that make them concurrent too are M3's row-lock item.
- **The errors.** A failed check is SQLSTATE `40001` ("could not serialize access due to a concurrent commit", with
  PostgreSQL's retry hint), MySQL error 1213 and Oracle `ORA-08177`. SQL Server's 1205 comes from its own error
  mapping of `40001`.
- **The plumbing.** `KeyValueStore::begin_concurrent_write(ConcurrentIsolation)` (default: none) returns a
  `ConcurrentWrite`. The session wraps it as its block writer, so savepoints, triggers and the statement undo log work
  unchanged over it. `eggdb::sql::SqlConcurrentWriter` adapts `ConcurrentTransaction`: reads record what serializable
  validation needs, scans materialise their range, and `put_if_absent` is a read then a write inside the transaction.
- **Left:** collections, keys with a time to live and counters inside these blocks (the next M3 item), scans that
  stream instead of materialising, a per-database default isolation (`default_transaction_isolation`), and Flyway's
  two-connection check in the compatibility job.
