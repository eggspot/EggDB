## D341 Top-N sort for `ORDER BY ... LIMIT n [OFFSET m]` and a nullable index read in two ranges in place of the sort — Decided by the build loop (batch 6, 2026-11-10); roadmap M5, extends D100, D146, D321 and D340, applies D7 and D9

`ORDER BY ... LIMIT 10` held every matching row and sorted them all before taking ten (D100's
"no top-N for `LIMIT` yet"), and since D321 (MySQL) and D340 (SQLite, SQL Server) sort NULLs
first for `ASC` and last for `DESC`, an index on a nullable column, whose entries are stored
ascending with NULLs last (D146), stopped replacing the sort in those dialects: `SELECT id FROM
events ORDER BY created_at DESC LIMIT 10` read and sorted the whole table. MySQL's "LIMIT Query
Optimization" (a sort with `LIMIT` keeps only the rows it needs; an index gives the order when
it can), PostgreSQL's top-N heapsort for `Sort` under `Limit`, and SQLite's, MySQL's and
Microsoft's statements that NULL sorts lowest describe the behaviour EggDB now has.

- **Top-N heap.** When a query that no key orders has `LIMIT n` (or `FETCH FIRST n ROWS ONLY`,
  `TOP n`, `OFFSET m ROWS FETCH NEXT n ROWS ONLY`) with an `OFFSET m`, the sort keeps the
  n + m smallest rows in a bounded max-heap (`top_n::TopRows`) while it reads, ordered by the
  sort keys and then by arrival, so tied rows keep the order they arrived in: the result is the
  same rows in the same order as the full stable sort's. A row that does not beat the heap's
  largest is dropped before it is charged; an evicted row's bytes are released, so the
  statement's work memory (D100, D307) holds at most n + m rows. A heap whose rows pass the
  1 GiB work memory fails with the same `53200` the full sort would, since the full sort holds
  every row the heap holds and more. `SELECT DISTINCT` keeps its first-seen filter in front of
  the heap, so it uses the heap too.
- **What still sorts every row.** `WITH TIES` (the rows tied with the last one are unbounded),
  `PERCENT` (it needs the row count first), `DISTINCT ON` (the first row of each group is
  chosen after sorting) and an n + m that overflows the platform's `usize` take the full sort.
  `LIMIT 0` reads and checks every row as the full sort does, and returns none.
- **Same errors.** An expression in a sort key that fails on some row fails the same way. The
  check that sort keys can be compared with one another (D100's `check_sortable`) runs on each
  row as it arrives against the first non-NULL key of its column (`top_n::SortabilityCheck`),
  and the first failure, per column in `ORDER BY` order, is returned after the scan, as the
  full sort returns it.
- **Two-range index read.** When an `ORDER BY` column wants its NULLs at the other end from the
  index (NULLs first for `ASC`, last for `DESC`: the default in MySQL's, SQLite's and SQL
  Server's dialects, or an explicit `NULLS FIRST` on `ASC` or `NULLS LAST` on `DESC` in any
  dialect) and the column may hold NULLs, the planner reads the key in two ranges: its NULL
  entries (the `NULL_IN_KEY` byte after the fixed prefix) and then the values for `ASC`, the
  values backward and then the NULL entries backward for `DESC`. Within the NULL range the rows
  come in the order of the key's later columns, as they do among equal values. It does this only
  when that column is the first `ORDER BY` column after the columns fixed by `=` (`WHERE kind =
  1 ORDER BY created_at DESC` on an index on `(kind, created_at)` splits after the `kind`
  prefix) and every later `ORDER BY` column is `NOT NULL` (the primary key that ends every index
  key is); otherwise the query sorts. With a `LIMIT` the read stops after the rows it returns,
  as it does for a `NOT NULL` column.
- **No split when the filter excludes NULL.** A `WHERE` with a conjunct that is never true for a
  NULL column (`=`, `<>`, `<`, `<=`, `>`, `>=` naming the column, `IS NOT NULL`, `BETWEEN`,
  `IN (...)` or `LIKE`) keeps one range: the NULL entries it reads at the end are filtered out.
  A range on the column already stops before the NULL entries.
- `EXPLAIN` shows the index read with no `Sort` node (`-> Index scan on events using
  events_created_at (reverse)` in MySQL's tree, `SCAN events USING INDEX events_created_at` in
  SQLite's query plan, `Index Scan using events_created_at on events` in PostgreSQL's).

Speed (D7): `sql_mysql.order_by_nullable_index_limit` (D321's line, now over 20,000 rows of
which every tenth `created_at` is NULL) and the new `sql_sqlite.order_by_nullable_index_limit`
time `ORDER BY created_at DESC LIMIT 10` against `ORDER BY id DESC LIMIT 10` on the primary key,
and `sql.order_by_limit_topn` times `ORDER BY created_at LIMIT 10` with no index against a scan
of the same rows that returns none (`WHERE created_at < 0`); their baseline lines come from the
next `--update` run.

Decided: the two-range read also serves PostgreSQL's and Oracle's explicit `NULLS FIRST` on
`ASC` (and `NULLS LAST` on `DESC`), which sorted before, since the rule is the same; a later
nullable `ORDER BY` column whose NULL order happens to match the index is still sorted, the
simpler rule the plan review chose; ties keep arrival order in the heap so `LIMIT` never changes
which tied rows a query returns compared with the same query without it (an index read in
place of the sort may still order tied rows differently, as before).

Tests: `top_n_tests.rs` (seeded random tables in PostgreSQL's, MySQL's, SQLite's and SQL
Server's dialects, each limited query's rows equal to the matching slice of the same query
without `LIMIT`, with ties, NULLs, `DESC`, expressions, `DISTINCT` and `GROUP BY`; a failing
sort key; `LIMIT 0` and the largest `bigint` limits and offsets; `TOP ... WITH TIES` and
`PERCENT`; indexed and unindexed copies of a random table answering the same in every dialect,
with equality prefixes, filters that exclude NULL and a later nullable column; `EXPLAIN` in
MySQL's, SQLite's and PostgreSQL's forms with no sort; entries read by `ORDER BY created_at
[DESC] LIMIT n` over 2,000 rows, bounded, and a short NULL range followed by the smallest
values); new cases in the MySQL, SQLite and SQL Server correctness suites (NULLs first and last
with `LIMIT`, `OFFSET`, an equality on the index's first column and a `WHERE` that excludes
NULL).

Left: a top-N for `WITH TIES`, `PERCENT` and `DISTINCT ON`; the two-range read for a later
nullable `ORDER BY` column or a nullable column that is not the first after the fixed ones;
spilling sorts to disk (D100).
