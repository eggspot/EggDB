## D147 Transact-SQL defaults kept as written and IDENTITY seeds and increments: two new default tags in table-definition version 9, the next identity number from the furthest stored one — Decided by the build loop (by research and judgement, 2026-10-30); roadmap item 40b (batch part 3.03), applies D9, D10, D20, D35, D96, D123, D124, D125, D146; supersedes in part D123 (defaults) and D125 (the restore's identity reset and "default not kept")

D123 kept a Transact-SQL `DEFAULT` only when it folded to a constant, `GETDATE()` and its kin or
`NEWID()`, and D124 cut item 40a before the rest; `IDENTITY` took only (1, 1), and the restore
of an SSMS script rewrote any other seed and increment to (1, 1) and listed every other default as
"default not kept" (D125). SSMS scripts are full of both (`DEFAULT (dateadd(day,(30),getdate()))`,
`IDENTITY(1000,10)`), so item 40b keeps them.

**What the table definition keeps.** A column's default byte gains two tags, allowed only in
table-definition version 9 (D146), which v0.2.0, the first release with SQL records, has not
shipped yet; the tags `0` (no default), `1` (a PostgreSQL default's text) and `2` (an
auto-increment column counting from 1 by 1) keep their meaning:
- `3`: a default written in another dialect: the dialect code as a `CHECK`'s (D124), then the
  text. Only SQL Server (`4`) is written; `0` is damage (tag `1` is the canonical form), as is a
  blank text.
- `4`: an auto-increment column with its seed and increment, two 64-bit little-endian signed
  numbers. An increment of 0, the pair (1, 1) (tag `2` is the canonical form) and a second one
  in a table are damage.

A table is written in version 9 when it has one of these, as for D146's options, and keeps its
older version and bytes otherwise; a version 9 definition that needs none of D146's or D147's
options is damage. In memory the table definition holds the seed (`identity_seed`, for its one
auto-increment column) and the dialect of each column default that is not PostgreSQL's
(`default_dialects`), next to D146's identity entries, so the 30-odd places that build a column
did not change. Dropping a column renumbers the entries; `SET DEFAULT`, `ADD DEFAULT ... FOR`,
`ALTER TABLE ... ADD GENERATED` and MySQL's `MODIFY` set them.

**Which defaults are kept as written (decided by judgement).** A default D123 already folds stays
PostgreSQL text, so tables that only use those keep their bytes and every dialect reads them as
before. Any other expression is kept as written in Transact-SQL, without its enclosing
parentheses (SSMS writes the stored definition, `(dateadd(day,(30),getdate()))`, inside one more
pair; the catalog's `sys.default_constraints.definition` puts one pair back, so a script restored
and scripted again matches). Before it is kept, the text must parse again on its own as one
Transact-SQL expression and name no local variable, so a stored text never depends on the batch
around it (D137 parses statements with the batch's variables as constants); otherwise it is
40517, which the restore lists as "default not kept". Column references and subqueries stay
refused as for every dialect (`0A000`), as SQL Server refuses them (its 128 and 1046 are not
given yet).

**How a kept default runs.** It is parsed in Transact-SQL and its value is assigned with SQL
Server's rule, whichever dialect inserts the row (a PostgreSQL `INSERT` into a restored SQL
Server table gets the same values as a TDS client). Its implicit conversions inside the
expression follow the inserting statement's dialect, D124's known difference for views and
`CHECK`s. A stored text that no longer parses is damage (`XX001`), never a panic. PostgreSQL's
catalogs and `information_schema` show the text as written; `.schema`'s PostgreSQL `CREATE TABLE`
leaves it out rather than write a statement that would not load; the public `ColumnSchema` gains
`default_dialect`.

**Identity numbers (decided by judgement).** The first row gets the seed; after that, the next
number is the furthest stored value plus the increment: the largest for a positive increment,
the smallest for a negative one, read from the primary key's first or last entry as before, and
never before the seed (`max(furthest, seed - increment) + increment`). For (1, 1) this is
exactly the old rule (`max(largest, 0) + 1`). An explicit value under `IDENTITY_INSERT` that
lies beyond moves the next number, as SQL Server documents ("If the value inserted is larger
than the current identity value for the table, SQL Server automatically uses the new inserted
value as the current identity value"). Without a stored counter, a deleted furthest value is used
again and an emptied table starts at its seed again (SQL Server keeps counting); keeping a
counter is a write per insert and a format change of its own, left for later with
`DBCC CHECKIDENT`, `IDENT_SEED`, `IDENT_INCR` and `IDENT_CURRENT`. `sys.identity_columns` shows
the seed and increment, and so do `sp_help` and PostgreSQL's
`information_schema.columns.identity_start` and `identity_increment`.

**Validation (decided by research).** Microsoft's IDENTITY page asks for both arguments or
neither; forum quotations of Books Online add that the increment must be a whole number other
than zero within the column type's bounds, and the same is required of the seed. SQL Server's
own error numbers and wording for a zero increment or an out-of-range seed could not be confirmed
from public sources, so they are the generic Msg 50000 (SQLSTATE `22023`) with EggDB's own
wording ("The IDENTITY seed of column 'id' must be a whole number within the range of int."), as
D124 did for an unconfirmed number. `tinyint` identities take `smallint`'s range, as D123 keeps
`tinyint` as `smallint`.

**The restore.** The reader no longer rewrites `IDENTITY(s, i)` to (1, 1) when it cuts computed
and `rowversion` columns, and no longer lists seeds as known differences; defaults are listed only
when they cannot be kept.

**Tests.** Pinned bytes for a table with both tags (written by hand from the layout), every cut,
each tag in an older version, every bad dialect code, a zero increment, (1, 1), a blank text and
20,000 seeded mutations, all errors and never panics; the next-number rule at the edges of `i64`;
a corpus of stored Transact-SQL defaults with their texts and values; session, correctness-chapter
and restore tests, and the SSMS fixture's `eggdb restore`, reopened, giving 1020 for
`IDENTITY(1000,10)` after 1010 and today plus 30 days for `dateadd(day,(30),getdate())`. The D96
sample files are untouched. As a file-format change it needs the second, security-only review of
D35.
