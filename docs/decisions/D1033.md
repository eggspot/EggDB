## D1033 Materialized views kept up to date at commit, and continuous queries — Decided by the code-only session (2026-11-13, D355); roadmap M14 (D28)

- `CREATE INCREMENTAL MATERIALIZED VIEW name AS query` (EggDB's own form, as pg_ivm's `create_immv` is an
  extension's) creates the materialized view as `CREATE MATERIALIZED VIEW` does, then keeps it up to date inside
  every transaction that changes its base table, so it is current at commit and never needs `REFRESH`.
- **Recompute what changed, not everything.** A row trigger on the base table, generated from the query, deletes and
  recomputes only the view rows the changed base rows touch: for a projection (`SELECT` of columns and expressions
  from one table with an optional `WHERE`, its primary key among the selected columns), the view row of the same
  key; for a `GROUP BY` with any aggregates (`count`, `sum`, `avg`, `min`, `max` and the rest, since the group is
  recomputed from its rows rather than adjusted), the view row of the old group and of the new one. Group values are
  compared with `IS NOT DISTINCT FROM`, so a `NULL` group stays one group.
- **What is refused.** Joins, subqueries, `DISTINCT`, `HAVING`, `ORDER BY`, `LIMIT`, set operations, window functions,
  `*`, and a projection without the base table's primary key are refused with the reason, instead of maintained
  wrongly; such views stay ordinary materialized views.
- **Continuous queries.** The trigger notifies the channel `<view>_changes` with the operation after each change, so a
  client that `LISTEN`s is told when the view's result changed and reads it again: a continuous query over any
  incremental view, through PostgreSQL's own notification protocol.
- `DROP MATERIALIZED VIEW` drops the trigger and its function first; the view's triggers, functions and base table are
  recorded in `eggdb_internal.incremental_views`.
- Left: joins of several tables (deltas per joined table) and maintenance deferred to commit for many changes to one
  group.
