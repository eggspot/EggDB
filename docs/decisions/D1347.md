## D1347 Asynchronous C API calls, one callback per batch — Decided by the code-only session (2026-11-25, D355); roadmap M6 "Asynchronous C API calls, completed by one callback per batch" (D17, D293)

- **What users get.** `eggdb_sql_execute_async(sql, text, callback, user_data)` and `eggdb_sql_execute_with_parameters_async(...)` run a batch of statements as their synchronous twins do, on a thread of their own, and return at once. One `eggdb_completion` callback reports the whole batch: the status, and the results, valid until the next call on the session as for a synchronous call. An event loop (libuv, Tokio, Node's N-API, .NET's thread pool) drives the database without blocking.
- **Contract.** The session belongs to the call until its callback: every other call on it, `eggdb_sql_close` included, fails with `EGGDB_ERR_IN_USE` (a flag the call sets atomically, so two calls cannot both start), except `eggdb_sql_cancel`, which stops the running statement as it does for a synchronous call. The callback runs on the call's thread, where `eggdb_last_error` and `eggdb_last_sqlstate` describe a failure exactly as after a synchronous call, and the session is free again when it runs, so it may start the next call. Bad arguments and a busy session fail at once, without a callback. Parameters and the text are copied before the call returns.
- **How.** One thread per call, started with the standard library; the session's state is reached through the same cell as every call, guarded by the flag instead of the caller's promise. User-defined functions registered on the session work in asynchronous calls, since they are made active for each call on the thread that runs it.
- **Left.** A shared pool of threads instead of one per call, asynchronous prepared-statement execution and stepping, and the language drivers' use of these calls (the item "every language driver using the new C API calls").
- **Proof.** A C API test runs a three-statement batch asynchronously and gets one callback with three results, runs a failing query and reads `42P01` inside the callback, and runs a synchronous call and closes the session afterwards.

**Status:** code written, unbuilt (code-only mode, D355).
