## D313 The browser card answers the pointer and the async clipboard through the same model the desktop uses, X11 moves large selections with `INCR`, and drops show the drag-over ring on Windows (OLE `IDropTarget`) and X11 (XDND v5) — Decided by the build loop (EggAgentCode task 20261103-1926, 2026-11-03); roadmap M6e, extends D274 and D279, applies D8, D9 and D16

D279 left four platform gaps: the browser card took keys but no pointer and used only the
browser's `copy` and `paste` events; X11 refused clipboard text larger than one request in both
directions; Windows took drops through `WM_DROPFILES`, which says nothing until the drop, so the
connect card's drag-over ring (`docs/ux/first-screen.md`, D274) never showed; and X11 took no
drops at all. Each is built from its public specification: the W3C Pointer Events, UI Events and
Clipboard API specifications, the ICCCM's section 2.7.2 "INCR Properties", Microsoft's COM and
OLE documentation of `IDropTarget`, `IDataObject` and `RegisterDragDrop`, and freedesktop.org's
"Drag-and-Drop Protocol for the X Window System" (version 5) with RFC 2483's `text/uri-list`.

- **Browser pointer.** `web/card.js` sends `pointerdown`, `pointermove`, `pointerup`,
  `pointercancel`, `pointerleave` and `dblclick`, in CSS pixels from the canvas, with the DOM
  button number and the modifier bits of `eggdb_wasm_card_key`, to new exports
  `eggdb_wasm_card_pointer_down`, `_move`, `_up`, `_leave` and `eggdb_wasm_card_double_click`.
  They drive `eggdb_gui::browser::CardPointer`, which does for the card what `Workspace` does on
  the desktop (D279): hit testing through the accessibility tree, the caret at a press in an
  input, a drag extending its selection, multi-clicks counted by the GUI (500 ms, 4 px), and
  buttons, links, checkboxes and tabs acting on a release on the same node. The browser's own
  `dblclick` only fills in a word selection when the GUI's count missed it (a user whose
  double-click interval is longer than 500 ms). A press the card uses is `preventDefault`-ed and
  captured, and the focus follows the card; the secondary button, the back and forward buttons,
  a busy card and the layout picker stay the browser's, so its context menu still opens. A real
  click (`detail` above 0) no longer acts a second time through the ARIA mirror's `click`, which
  stays for screen readers' activations. The card has nothing that scrolls, so the wheel stays
  the page's; `browser::wheel_notches` turns DOM deltas (pixels, lines, pages) into the platform
  layer's notches for the screens that will.
- **Async clipboard.** `Ctrl/Cmd+C` and `V` keep using the browser's synchronous `copy` and
  `paste` events, which need no permission; when the browser fires neither after the key (as some
  do with nothing selected natively), the loader falls back to `navigator.clipboard.writeText`
  or `readText` within the same user gesture. The host can call `card.copy()` and `card.paste()`
  from its own menus; both answer `false` when the browser refuses or has no async clipboard (an
  insecure origin). Paste keeps the 1 MB limit.
- **X11 `INCR`.** A selection larger than one request (the server's maximum request length less
  `ChangeProperty`'s header) is answered with an `INCR` property holding its size, after
  selecting `PropertyChange` on the requestor's window; each deletion of that property writes
  the next chunk (at most 256 KB), then an empty one, and the requestor's events are deselected
  when it is read. At most 8 transfers run at once, one per requestor and property, and one the
  requestor stops deleting for 10 s is given up by the event loop, which wakes for it even when
  nothing else happens. Reading, the window selects `PropertyChange` on
  itself and, for an `INCR` answer, reads each new value with a deleting `GetProperty` until the
  empty one, waiting 2 s per chunk and 30 s for the whole selection, giving up an owner that
  removes the property before it is read more than 8 times, and refusing more than the 8 MB clipboard
  limit, so a slow or hostile owner never hangs the window. Errors from a
  requestor's window gone meanwhile stay ignored, now including `ChangeWindowAttributes`. Both
  sides are `x11_incr::OutgoingIncr` and `IncomingIncr`, state machines without I/O.
- **Windows drop target.** After `OleInitialize`, the window registers an `IDropTarget` of our
  own COM declarations (`QueryInterface`, `AddRef`, `Release`, `DragEnter`, `DragOver`,
  `DragLeave`, `Drop`) with `RegisterDragDrop`, reading `CF_HDROP` from the `IDataObject` with
  `GetData` and `DragQueryFileW` and freeing it with `ReleaseStgMedium`. `DragEnter` with files
  sends `FileDragEntered` (the ring shows) and answers `DROPEFFECT_COPY` when the source allows
  it, `DragLeave` sends `FileDragLeft`, and `Drop` sends `FilesDropped`. When OLE cannot start on
  the thread (another apartment model) or refuses the registration, the window keeps
  `DragAcceptFiles` and `WM_DROPFILES` as before. The window revokes the target before it is
  destroyed. The effects and the drag state are `win32::FileDragTarget`, tested on every system.
- **X11 XDND.** The window sets `XdndAware` to 5. A source from version 3 on is followed:
  `XdndEnter` (reading `XdndTypeList` when it offers more than three types, an error from a gone
  source window answering no types), `XdndPosition` answered with `XdndStatus` (accepting with
  `XdndActionCopy` only when `text/uri-list` is offered, with an empty rectangle so every move is
  sent), the paths asked for from `XdndSelection` at the first position's time so the ring can
  show before the drop, `XdndLeave`, and `XdndDrop` answered with `XdndFinished` once the paths
  are read (accepted only when there are any). The `text/uri-list` keeps `file:` URIs on this
  host (an empty host or `localhost`), percent-decoded, at most 1,024, and leaves out other URIs,
  other hosts and paths that are not UTF-8 or hold a NUL; a list sent with `INCR` is read too.
  The protocol is `xdnd::XdndTarget`, which turns each message into the reactions the window
  performs. The window queues each XDND message and each `XdndSelection` answer (at most 256
  waiting; a full queue drops its oldest `XdndPosition`, else its oldest `XdndEnter`, and never
  drops a `XdndLeave`, a `XdndDrop` or an answer for those, `xdnd::queue_bounded`) and handles
  them one at a time from its event loop, at most 16 before giving back a waiting key or pointer
  event (`xdnd::handles_drag_input`), so a flood of positions neither loses a drop nor holds the
  user's input back, and the round
  trips they need (the type list, the paths, an `INCR` read) never nest inside another read. An
  answer is read only when the current drag asked for its paths and has had no answer yet, at
  the time of its request or `CurrentTime`, so a late answer to an earlier drag is ignored.
- **Review round 1.** The `INCR` read's overall limit and the gone-property count, the queued
  XDND handling, the stalled transfers given up from the event loop, the answer matched to its
  drag, and the OLE target's helpers that take OLE's pointers made `unsafe fn` came from the
  batch's first review.

Not done: the browser's drag and drop of files (opened in memory, D274), its
`prefers-reduced-motion` (D311) and touch gestures beyond a tap and a drag; the wheel on a
browser screen that scrolls (the main window is not in the browser yet); `INCR` for selections
other than `CLIPBOARD` (`PRIMARY` is not served); XDND as a drag source, other actions than copy
and the `XdndProxy` property; a landing property per XDND drag (two sources answering at once
into the one landing property, the second writing before the first's answer is read, give the
first's paths to the second); Windows' drop target as a source (`DoDragDrop`) and drop
descriptions; Wayland's data device for both the clipboard and drops; and a hand check of the
three on real desktops (CI checks the protocol logic, and the browser test checks the pointer and
the clipboard events in headless Chrome).
