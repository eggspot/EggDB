## D150 Oracle restore follow-ups: a key takes over an index named in `USING INDEX`, constraints disabled inside a column move to the table level, Oracle's identities recorded and enforced with their options, and SQL*Plus scripts in `eggdb sql` through one public step reader — Decided by the build loop (by judgement, Oracle's public SQL Language Reference and SQL*Plus documentation, and Claude Fable's design, 2026-10-30); roadmap item 43b (batch part 3.06), applies D9, D10, D13, D15, D127, D146, D147; supersedes in part D127 and D146

D127 left three Oracle restore items for later (an index named differently in `USING INDEX`, a
constraint disabled inside a column, SQL*Plus commands in `eggdb sql`), and D146 left Oracle's
`GENERATED ALWAYS` unrecorded. They are built here. No file-format change: identities use D146's
identity kinds and D147's seed and increment in table-definition version 9.

**`USING INDEX name` (engine, Oracle's dialect).** `ADD CONSTRAINT ... PRIMARY KEY | UNIQUE (...)
USING INDEX [schema.]name` looks the index up on the table: a missing one is `ORA-01418`, one
whose leading columns are not the constraint's columns (in any order) is `ORA-14196`. An index on
exactly the constraint's columns that backs no other constraint is dropped and the key or unique
constraint makes its own, named after the constraint, as D127 already does for an index of the
same name (EggDB keeps one index per key; the index's own name is not kept, a known limit). An
index with more columns stays, and the constraint gets its own index beside it. `USING INDEX`
followed by index properties (`NOSORT`, `INDEXING PARTIAL`, storage) names no index.

**Constraints disabled inside a column (restore).** A `CHECK`, `REFERENCES`, `UNIQUE` or `PRIMARY
KEY` written `DISABLE` inside a column of `CREATE TABLE` or of `ALTER TABLE ... ADD (...)` is cut
out of the column and remembered as a table-level clause (`CONSTRAINT n FOREIGN KEY (c)
REFERENCES ...`, `UNIQUE (c)`), exactly as D127 remembers a disabled table-level one: the matching
`ENABLE` adds it over the loaded rows, and one still disabled at the end is listed. `ALTER TABLE
... ADD (...)` with disabled table-level constraints, skipped before, now runs the rest. The
engine still refuses `DISABLE` outside the restore (0A000): a session cannot keep a constraint it
does not enforce.

**Oracle's identities (engine).** `GENERATED ALWAYS AS IDENTITY` is recorded as `ALWAYS` (D146)
and enforced: a value given in an `INSERT` is `ORA-32795`, an `UPDATE` of the column `ORA-32796`
(both without PostgreSQL's hint). `BY DEFAULT [ON NULL [FOR INSERT ONLY | FOR INSERT AND
UPDATE]]` is recorded as `BY DEFAULT`. Identity options, in parentheses or bare as `DBMS_METADATA`
writes them, are read with the sequence-option parser: `START WITH` and `INCREMENT BY` become
D147's seed and increment (`START WITH` defaults to `MINVALUE`, or `MAXVALUE` when descending, as
Oracle's does); `CACHE`, `ORDER`, `KEEP`, `SCALE` and their `NO` forms, `NOCYCLE`, and a
`MINVALUE`/`MAXVALUE` that does not end the identity inside its type's range are accepted with no
effect. `INCREMENT BY 0` is `ORA-04002`, `MINVALUE >= MAXVALUE` `ORA-04004`, a start outside them
`ORA-04006`/`ORA-04008`. A limit inside the type's range, `CYCLE` and `START WITH LIMIT VALUE` are
0A000: EggDB's identity runs to the end of its type and takes the next value after the furthest
stored one (D147), so it cannot stop or wrap where Oracle's sequence would. `user_tab_identity_cols`
and its `all_`/`dba_` forms list identity columns, with `ISEQ$$_<table id>` as the sequence name
and Oracle's `IDENTITY_OPTIONS` text.

**Identities in restores.** The restore no longer cuts identities with options out of `CREATE
TABLE` before running it: the engine keeps what it can. A `CREATE TABLE` the engine refuses with
0A000 or 42P16 (options EggDB cannot keep, or an identity that is not the first column of the
primary key) runs again without the identity clause, listed as before (`identity not kept`), as
SQL Server's restore does (D148). The Oracle restore session keeps the identity values its
`INSERT`s give, `ALWAYS` included (Oracle's exports carry them), through a session flag the
statement context reads; `COPY` and bulk loads keep them already (D146).

**SQL*Plus scripts in `eggdb sql` (D15 design, docs/ux/cli.md section 26).** `eggdb-sql` gains
`SqlPlusScript`, a public step reader over the restore's SQL*Plus reader: it hands its caller
statements (with `EXECUTE p` as `BEGIN p; END;`), `PROMPT` text, `CONNECT` as an `ALTER SESSION
SET CURRENT_SCHEMA` statement, `EXIT` with `ROLLBACK` and its status, and every other command as
it is, with its place (`line 4`, `hr_populate.sql line 61`). `eggdb sql --dialect oracle` reads a
script (a file or stdin; `-c` stays plain SQL) through it, with the restore's include opener and a
new `--define`: commands that did their job are silent, `SPOOL`, `HOST`, `WHENEVER SQLERROR
CONTINUE`, `EXIT` status words, unrun and unknown lines get one `NOTICE:` each, and the rest are
counted in one closing notice. The reader's messages now name EggDB rather than `eggdb restore`,
so one message serves both commands. A UTF-16 script is still refused by `eggdb sql` (it reads
UTF-8 only); `eggdb restore` reads both.

**Left for later.** Keeping the name of an index taken over by a key; identity limits and `CYCLE`;
`BY DEFAULT` refusing an explicit `NULL` (EggDB generates a value, as `ON NULL` does); SQL*Plus
commands in `eggdb shell`; `DESCRIBE`, `VARIABLE`/`PRINT`, `SPOOL` and `COLUMN` formatting.
