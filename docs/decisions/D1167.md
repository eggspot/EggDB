## D1167 `json(b)_populate_record` in a select list and in expressions — Decided by the code-only session (2026-11-14, D355); roadmap M6a (D289, D302)

- **What changed.** `json_populate_record(base, document)` and `jsonb_populate_record` (the one-row forms) were
  table functions only. They are now values in any expression, a select list included, as in PostgreSQL:
  - `SELECT json_populate_record(null::pt, '{...}')` gives one composite column, printed `(3,4)`;
  - `(json_populate_record(...)).field` reads one field;
  - a non-NULL base row (`ROW(1, 2)::pt`) keeps the fields the document does not name.
- **How.** `sql_json::populate_scalar` takes its row shape the way hstore's `populate_record` does
  (`hstore_functions::record_shape`, now shared): from a composite type's attributes or the record value given.
  It fills each named field through the same `json_to_record::field` conversion `json_to_record` uses, with the
  last of repeated keys winning. A NULL document returns the base row. Typing gives the call the base row's type.
- **Still sets.** The select-list set-returning machinery no longer treats these two names as sets
  (`returns_a_set_in_expressions`); in FROM they are still table functions. The `...recordset` forms remain
  set-returning.
- **Not yet.** A table's own row type (`null::t` for a table `t`) is still FROM-only: in an expression it is
  refused with `0A000` and a hint, since a table's row type has no composite type entry to build the value
  from. A column alias list on the FROM form is left too.
- **Tests.** A composite value from a select list, a field selection, a non-NULL base row, and the refused table
  row type.

**Status:** code written, unbuilt (code-only mode, D355).
