## D1079 CalDAV invitations sent as iMIP mail — Decided by the code-only session (2026-11-13, D355); roadmap M16 (D56, D1073, D1077)

- `eggdb serve` with `--dav-listen` (and not `--read-only`) runs an iMIP sender beside the DAV listener. It
  joins CalDAV scheduling's outbox queue (D1077) to the mail store's delivery (D1073).
- Every 10 seconds it takes each waiting invitation from the user's outbox
  (`eggdb_dav::waiting_invitations`). It writes the invitation as an RFC 6047 message:
  - from `<user>@<mail domain>`, to the recipients;
  - the subject `Invitation:`, `Cancelled:` or `Reply:` with the event's summary;
  - an RFC 5322 date and a message id from the UID;
  - one `text/calendar; method=…` part holding the iTIP object as queued.
- Recipients in the mail domain (or `localhost`) get it in the INBOX (`eggdb_mail::deliver_local`). Others
  get it through `--smtp-relay` (`eggdb_mail::relay_message`, the client of D1073), with each refusal
  logged.
- An invitation leaves the outbox once it went out: always, when it has only local recipients; and when
  the relay took the message, if it has remote ones. Without a relay, invitations to other domains wait,
  with one log line saying why, and nothing is delivered twice.
- Header values are stripped of control characters, so an event's summary cannot inject header lines.
- Left: replies that come back by mail. These are iMIP messages the mail store receives; turning them into
  inbox iTIP items is a small step left for the DAV-and-mail bridge.
- Learned from: RFC 6047, RFC 5546 and RFC 5322.

**Status:** code written, unbuilt (code-only mode, D355).
