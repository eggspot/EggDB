## D155 A per-session plan cache keyed by statement shape, conditions pushed into views and derived tables, and `IN` and scalar-aggregate subqueries decorrelated by key — Decided by the build loop (by judgement, 2026-10-30); item 19e, applies D7, D99, D100, D112

Item 19e's remaining fixes (D99, D100, D112): point `SELECT`s still parsed every statement,
a lookup through a view read the whole view, and a correlated `IN` or aggregate subquery ran once
per distinct outer value.

**A plan cache for statements that differ only in their constants.** Each session keeps up to 64
parsed `SELECT`s. The key is the statement's tokens with the text of every number and string
constant left out (its kind, byte offsets and length kept), plus the dialect and the session's
settings object (held by the entry, so a changed setting, which replaces the object, never
matches an old entry). A statement of a cached shape skips the parser: the template is cloned and
each literal is replaced by the literal of the constant at the same byte offset, computed exactly
as the parser computes it. Because offsets are part of the key, every position in the cached
statement, and so every error position, is the one a fresh parse gives. What is cached is the
parsed statement before names are bound, so `CREATE`, `DROP` and `ALTER` of tables and views
(by this session or another) need no invalidation: binding reads the catalog every time.

A template is kept only when it is provably the parse of any statement of its shape: every
literal in it is the literal of exactly one constant token at its own offset, with an equal value,
and every constant token is used. A constant the parser folds (`-5`), turns into another value or keeps outside the
expressions the cache walks (in a subquery or a type modifier) fails that check, and the shape is remembered as never cached so the check does not run
again. Only the PostgreSQL, MySQL and SQLite dialects are cached: Oracle's and SQL Server's
parsers read constants through dialect hooks first. Statements with parameters, variables,
binary constants, setting changes, user-defined types loaded for the parse, SQL Server batches,
or over 4 KiB of text are not cached.

*Instead of an AST that borrows the SQL text*, which D99 listed first: the cache removes the
parse of a repeated shape entirely, where borrowing would only make each parse cheaper, and it
does not change the lifetime of every AST type across the crate. Borrowing stays possible later
for statements that are never repeated.

**Conditions pushed into views and derived tables.** A view is still expanded into a derived
table (D116). Before a `SELECT` runs its derived tables, each `AND` part of its `WHERE` that names
only one derived table's columns is copied, rewritten over the columns those outputs read, into
that table's own `WHERE`; it also stays where it was, so the result cannot change. A part moves
only when it is built from columns, constants, operators, casts and `CASE` (no function calls, so
nothing volatile is evaluated more often), only into a derived table whose outputs are plain
columns (or `*` over one stored table) and which has no grouping, aggregates, `DISTINCT`, limits,
windows or set-returning functions, and only when the outer `FROM` has no outer join, which could
turn a row removed inside into one extended with NULLs. A view defined with `*` is expanded in
two layers (D116), and the condition moves through both, so `SELECT ... FROM v WHERE id = 5`
reads `people` by its primary key. As in PostgreSQL, the order in which `AND` parts are evaluated
is not promised, so a part that fails on a row another part excludes (`1/0`) may fail earlier.

**`IN`, `= ANY`, `<> ALL` and scalar aggregates decorrelated.** D112's key lookup for `EXISTS` now
serves three shapes. For `IN` (and `= ANY`, `<> ALL`), a subquery whose outer references are
only `inner = outer_column` parts of its `WHERE` runs once as `SELECT DISTINCT keys, item`, and
its values are grouped by the keys' equality bytes: an outer row gets its group's values and the
ordinary membership test, so NULLs on either side answer exactly as before; a missing group is
the empty set (`IN` false, `NOT IN` true). A scalar subquery whose single item is an aggregate
expression with every column inside an aggregate (`count(*)`, `coalesce(sum(x), 0)`) runs once
as the same item `GROUP BY` the keys (plain columns), and a missing group takes the item over no
rows, computed once by running it with `WHERE false`, so `count` gives 0 and `sum` NULL as the
per-row run does. Outer values of another family of types than the keys, and a NULL key, fall
back to or answer like the per-row run. A subquery with a limit, `OFFSET`, `ORDER BY`, `HAVING`,
`GROUP BY`, windows or a subquery in its item keeps the per-row run. The `EXISTS` lookup now also
refuses a `LIMIT 0`, which it used to ignore.

`IN` against an uncorrelated subquery hashes integer values (`smallint`, `integer`, `bigint`) as
64-bit integers with the seeded hash of D100's integer maps instead of encoding each probe into
bytes; any other value, a `numeric` probe among integers included, takes the byte keys or the
comparison loop as before.

**Measured by** `sqlite_compare.sql_view_point_select`, `sql_correlated_in` and
`sql_scalar_aggregate` beside the existing lines; their baselines are taken in the build step,
gated at 15% as D99's SQL lines.

**CI's `compare` job on macOS too.** D94 ran the comparison on Linux only, so the macOS
`ratio_to_sqlite` lines were enforced only by hand. Item 19e's check is the 1.0 ratio on both
systems, so the job now runs on `ubuntu-latest` and `macos-latest` (standard runners, free for
this public repository), each against its own system's lines, with one results artifact per
system. The two legs run in parallel, so the time to a green run grows only by the macOS leg's
queue.
