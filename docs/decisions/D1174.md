## D1174 Temporary tables move with `USE`, and session locks stay held where they were taken — Decided by the code-only session (2026-11-15, D355); roadmap M6a; supersedes the refusal in D294

- D294 refused a `USE` (and `COM_INIT_DB`) while the session held a temporary table or a session-level lock, because the switch closes the session that held them. SQL Server and MySQL keep both across `USE`, so applications that build a `#temp` table and then switch failed on EggDB.
- **Temporary tables.** They live in the session's own overlay (`TemporaryObjects`), not in the database's store, with session-local ids, so they do not belong to either database. `Session::switch_to` copies the overlay's committed entries into the `DatabaseSwitch` (a switch inside a transaction is already refused, `25001`), and `DatabaseSwitch::into_session` gives them to the new session, where the same names keep resolving, as `#temp` tables in SQL Server's `tempdb` do.
- **Still refused**, with D294's codes (`0A000`, SQL Server's `40508`, MySQL's `1235`) and the objects named: a temporary view, whose text names the old database's relations, and a temporary table whose columns use the old database's own types or domains (enums, composites, user ranges, domains), whose OIDs mean nothing in the other database. Built-in base types and built-in ranges move.
- **Session locks.** Advisory locks and `sp_getapplock` locks are kept per database (D294's `AdvisoryLocks`, keyed by the store). The session's lock owner is now shared (`Arc`): a switch hands the old owner to the new session, which keeps it alive, so its session locks stay held on the database they were taken in, as SQL Server's application locks belong to the database they were requested in. When the client returns to that database with `USE`, the owner becomes the session's own again, so `sp_releaseapplock` and `pg_advisory_unlock` release them; otherwise they are released when the client disconnects. MySQL's `GET_LOCK` names are server-wide in MySQL but per database in EggDB (unchanged here), so `RELEASE_LOCK` after `USE` finds a lock only in the database that took it.
- Test: `temp_tables_move_with_use_and_session_locks_stay_held_where_they_were_taken` in `eggdb-tdswire`'s `databases` tests (replacing D294's refusal test).

**Status:** code written, unbuilt (code-only mode, D355).
