## D753 A schema registry and data contracts in eggdb_catalog — Decided by the code-only session (2026-11-12, D355); roadmap M6c, a schema registry and data contracts (D51)

- `eggdb_catalog.register_schema(subject, definition)` keeps versioned schemas per subject in
  `schema_versions`, in the shape `{"fields": [{"name", "type", "required", "default"}]}`, and returns the version:
  an identical schema returns its existing version, a new one gets the next number. Each subject has a compatibility
  mode in `schema_subjects`, with Confluent Schema Registry's names: `NONE`, `BACKWARD` (the default), `FORWARD`,
  `FULL` and their `_TRANSITIVE` forms, which check against every version instead of the latest. A schema that breaks
  its mode is refused with SQLSTATE 42804 and the list of problems.
- `schema_differences(reader, writer)` lists what stops a reader schema from reading data written with a writer
  schema: a required field without a default that the writer lacks, a field whose type differs, and a required field
  the writer may leave null. Fields only the writer has are ignored. Types are compared by name, so schemas that
  describe tables use `information_schema`'s `data_type` names, which `describe_table(schema, table)` returns.
- A data contract in `contracts` binds a table to a subject, an owner, a freshness column and limit (one day by
  default) and a minimum row count. `check_contract(name)` returns one row per clause (`schema`, `freshness`,
  `volume` and each quality rule on the table from `quality_rules`), each with `passed` and a detail, and appends them
  to `contract_results`, so a pg_cron job can alert on a broken contract.
- Avro and Protobuf schema texts, Confluent's REST API and schema references are left.
