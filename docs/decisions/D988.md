## D988 `eggdb follow mongodb://` — Decided by the code-only session (2026-11-13, D355); roadmap M9, following a live MongoDB (D13, D162, D197)

- `eggdb follow <file> mongodb://user@host:port/...` copies a MongoDB replica set or sharded cluster into the file's
  MongoDB-compatible store and keeps it in step through the cluster's change stream, as the PostgreSQL and SQL
  Server follows do (D162, D263). A standalone server is refused with how to make it a one-member replica set.
- The client is EggDB's own (`eggdb_mongowire::client`): `OP_MSG` over TCP or TLS (EggDB's TLS, with `tlsCAFile` or
  the system's roots) and SCRAM-SHA-256, written from MongoDB's published specifications. The client checks the
  server's SCRAM signature too. `mongodb+srv://` needs DNS SRV lookups and is refused for now; of several seed hosts
  the first is used.
- Order: the change stream is opened first (`allChangesForCluster`, `fullDocument: updateLookup`) and its first resume
  token kept; then every collection is copied with its indexes; then the stream is read from that token. Inserts,
  updates and replaces write the document as the source holds it, by `_id` with upsert, and a change whose document
  is already gone deletes it, so changes made during the copy converge instead of being applied twice.
- Each batch of changes and the batch's resume token commit in one transaction through a staged overlay of the
  store (the multi-document transaction path, D566); the position is the document `mongodb` of
  `eggdb_follow.state`, so it lives in the same store as the documents. A second run resumes from it and refuses a
  different source or replica set.
- `--schema` chooses databases; `admin`, `config`, `local` and `eggdb_follow` are never followed. `--until
  caught-up`, `--reconnect-for` and Ctrl-C behave as for the other sources. An invalidate event stops the follow.
- Left: `mongodb+srv://`, other seeds when the first is down, X.509 and LDAP sign-in, and collection options changed
  after the copy (`collMod`).
