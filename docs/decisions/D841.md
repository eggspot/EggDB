## D841 OAuth for MCP over HTTP — Decided by the code-only session (2026-11-12, D355); roadmap M6c, D189

- With `EGGDB_MCP_OAUTH_ISSUER`, `EGGDB_MCP_OAUTH_JWKS` (a JSON Web Key Set file) and `EGGDB_MCP_OAUTH_RESOURCE` (the
  endpoint's own URL), `eggdb serve`'s MCP listener accepts OAuth access tokens beside the token file's static
  tokens, as the MCP authorization specification describes for remote servers: a Bearer JWT signed by one of the
  keys (`eggdb_auth::jwt`, D301's verifier), issued by that issuer, whose audience holds the resource URL (RFC 8707),
  within 60 s of clock leeway. Its `sub` is the role the agent runs as.
- It serves the protected-resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource` (`resource`,
  `authorization_servers`, `bearer_methods_supported`), and a 401 names it in `WWW-Authenticate: Bearer
  resource_metadata="..."`, so MCP clients find the authorization server on their own. The three variables go
  together, or serve refuses to start.
- An OAuth caller gets the time limit and writes setting of a token-file line for the same role, else the defaults
  (read-only, the default time limit); per-token quotas apply to static tokens only. The admin API (D840) takes the
  same tokens.
- Left: TLS on the MCP listener (D189), and token introspection for opaque tokens.
