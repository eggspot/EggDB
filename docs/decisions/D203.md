## D203 Vectors: pgvector's text, operators and functions now, an HNSW graph in eggdb-vector, the stored type next — Decided by the build loop (by judgement, 2026-10-31); refines D2 and D19

Part 4.M12-1 asks for `vector(n)`, HNSW and IVF indexes, and pgvector's operators.

- **`eggdb-vector`**, from pgvector's public documentation (its text form and the definition of
  each distance) and Malkov and Yashunin's HNSW paper: parsing and writing vectors, the four
  distances, normalization, and an HNSW graph with pgvector's defaults (`m` 16,
  `ef_construction` 64) whose recall the tests check against exact search.
- **SQL first through text.** The operators `<->`, `<=>`, `<#>`, `<+>` and the functions take
  vectors as their text or as numeric arrays, so applications using pgvector's SQL work today,
  with exact search. `vector(n)` is accepted as a column type and stored as text: adding a
  stored type touches every type switch in the engine (encoding, casts, catalogs, wire
  formats) and is its own slice, made together with the index so the index can read
  binary vectors.
- **pgvector is MIT-licensed**; only its documented behaviour was used, as for every other
  system (D1).

Left: a stored `vector(n)` type with its dimension checked, binary send and receive and a
catalog entry clients find by name; `CREATE INDEX ... USING hnsw` (and `ivfflat`) backed by the
graph and kept in the file, used by `ORDER BY ... LIMIT`; `halfvec`, `sparsevec` and bit
vectors; vector arithmetic; and an ANN benchmark (recall and queries per second) against
pgvector.
