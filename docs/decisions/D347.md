## D347 RESP blocking commands (`BLPOP`, `BRPOP`, `BLMOVE`, `BRPOPLPUSH`, `BLMPOP`, `BZPOPMIN`, `BZPOPMAX`, `BZMPOP`, `XREAD BLOCK`) and their non-blocking forms (`LMOVE`, `RPOPLPUSH`, `LMPOP`, `ZPOPMIN`, `ZPOPMAX`, `ZMPOP`), with first-come first-served wake-ups — Decided by the build loop (batch 6, part P12, 2026-11-10); roadmap M7, extends D193, applies D9 and D307

D193 left blocking commands out, and `XREAD BLOCK` answered an error, so job queues built on
`BLPOP`/`BRPOPLPUSH` (Sidekiq, Resque, Bull's older releases, Celery's Redis broker) and stream
consumers that wait with `XREAD BLOCK` could not run against EggDB. Built from the Redis command
reference pages of each command (arguments, reply shapes in RESP2 and RESP3, errors, the
"blocking behaviour", "what key is served first" and "behaviour inside MULTI" sections); no Redis
code is used or read. Consumer groups are not part of this decision: they need group state stored
with the stream, a new stored value kind, so they come as their own security-critical format part
(D35).

- **Non-blocking commands first.** `LMOVE source destination LEFT|RIGHT LEFT|RIGHT` and
  `RPOPLPUSH` (as `LMOVE ... RIGHT LEFT`) move one element, rotating when both keys are the same;
  a missing source answers nil without looking at the destination, a destination of another type
  answers `WRONGTYPE` and moves nothing. `ZPOPMIN`/`ZPOPMAX key [count]` answer a flat
  member-score array, except with a count in RESP3, where each member is a two-element array (the
  new `Reply::Pairs`); a missing key or a count of 0 is an empty array, a negative count
  `ERR value is out of range, must be positive`, more arguments `ERR syntax error`.
  `LMPOP numkeys key ... LEFT|RIGHT [COUNT n]` and `ZMPOP ... MIN|MAX [COUNT n]` pop from the
  first key that has elements and answer `[key, elements]` (`ZMPOP`'s elements are member-score
  pairs in both protocols), the null array when every key is empty, `ERR numkeys should be
  greater than 0`, `ERR count should be greater than 0` and `ERR syntax error` as Redis does.
  Multi-element replies are held against the reply room (D307) inside the transaction, so a pop
  that would pass it answers `-OOM` and pops nothing; so are `XREAD` replies, entry by entry,
  since `COUNT 0` and `XREAD BLOCK` can return a whole stream.
- **Timeouts.** The list and sorted-set commands take seconds as a float (`0.5` waits 500 ms,
  rounded up to a millisecond; `0` waits forever): `ERR timeout is not a float or out of range`,
  `ERR timeout is negative`, `ERR timeout is out of range` (infinite). `XREAD BLOCK` takes whole
  milliseconds: `ERR timeout is not an integer or out of range`, `ERR timeout is negative`. A
  timeout answers the null array, `*-1` in RESP2 and `_` in RESP3, for every blocking command,
  `BLMOVE` and `BRPOPLPUSH` too, as Redis's reference says.
- **Would block.** Each blocking command first runs once like its non-blocking form. When there
  is nothing to take, only the connection's own loop (`serve_connection`) waits; everywhere else
  the command answers at once with what Redis answers inside `MULTI`: the null array, or the null
  bulk string for `BLMOVE` and `BRPOPLPUSH`. So `EXEC` and an append-only-file replay
  (`eggdb restore` of an AOF) never wait. Replies queued for a pipelined client go out before it
  starts waiting.
- **Waiting and wake-ups.** Every connection's commands write through a wrapper keyspace that
  records the keys a committed write stored a value under; after the command, the connection
  hands them to the server's waiter registry. The registry keeps one first-in first-out queue
  per `(database, key)`, and each waiter a generation number. A blocked client registers on its
  keys, tries again (so a write between its first try and its registration is not lost), then
  waits on a condition variable until its generation changes. A write wakes only the head of the
  key's queue (plus any `XREAD` waiters before it, which take nothing); the woken client takes
  its element, and its own write wakes the next one if elements are left, so `RPUSH k a b c`
  with three clients blocked on `k` serves them in the order they blocked, one element each. A
  woken client that takes nothing (another client took the element, or the key now holds another
  type) passes the wake to the next in line, and so does one that gives up (timeout, disconnect)
  after being woken. `XREAD BLOCK` waiters do not consume, so every one of them is woken by a
  write to its stream.
- **Waits are slices.** A waiting client sleeps at most `READ_POLL` (200 ms) at a time; after
  each slice it checks that the server is not stopping and that its client is still connected,
  before every retry too, so a client that disconnects while blocked takes no element and a
  server shutdown is not held up by `BLPOP k 0`. The connection check reads, without waiting,
  whatever the client has sent since it blocked into the connection's request buffer, up to
  64 KiB (the uncounted buffer every connection may hold, D307), and a read of 0 bytes means the
  client closed: a peek would only see the first pipelined byte and never the close behind it.
  Past 64 KiB the connection counts as open and TCP backpressure holds the rest of the pipeline
  in the client, so a client that closes behind more than 64 KiB is seen only when it is next
  answered; nothing read ahead is left uncounted once the blocking command answers. The request
  buffer gives its capacity back to 64 KiB once a larger request has been read, and drops the
  bytes it has parsed before it reads more. The buffered commands run after the blocking command
  answers, in order, as Redis runs a pipeline. The client at the head of a
  key's queue (and every `XREAD` waiter) also tries again after each slice, which covers writes
  made without the RESP listener (another front end writing the same keyspace).
  The registration is removed on every way out.
- **`INFO` counts blocked clients.** `INFO` answers a `# Clients` section with
  `blocked_clients:<n>`, the number of clients waiting in a blocking command now, as Redis
  reports it there. The count is the waiter registry's: a client counts from the moment it is on
  its keys' queues (it is added under the registry's lock after its queue entries) until its
  registration is removed, on every way out and before its reply is sent. So once `INFO` reports
  `n`, a write from any connection wakes those `n` clients, and a client that has received its
  reply no longer counts. Each command reads the count as it starts; everywhere nothing can block
  (an append-only-file replay, an embedded caller) it is 0, and `INFO` inside `MULTI` reports the
  count as `EXEC` starts. The tests use it to order clients instead of sleeping: a test sends the
  blocking command, then polls `INFO` from another connection until `blocked_clients` reaches the
  expected count (for at most 10 s), and only then writes, so a slow machine cannot run the write
  first (macOS CI after #101 ran a `ZADD` before the `BLPOP` it was meant to wake, after a fixed
  150 ms sleep, and got `WRONGTYPE`). Sleeps remain only where nothing can be observed: the time a
  woken client has to retry before the test changes the key again, and the time the server has
  to read pipelined commands behind a blocked one, and neither decides whether a test passes.
- **A look before a write.** Every try, the first one and each retry, first reads the waited
  keys in a read-only snapshot and opens a write transaction only when one of them holds a
  non-empty list or sorted set (a stream read never writes), so a client blocked on empty keys
  commits no transactions however long it waits.
- **Edge cases as Redis documents them.** A key that becomes another type while waited on keeps
  the client blocked (`BLPOP` on a key turned into a sorted set waits on); `BLMOVE` whose source
  gets an element while its destination holds another type answers `WRONGTYPE` and moves nothing.
  `XREAD BLOCK ... $` reads from the stream's last ID at the moment the client blocks (0-0 for a
  missing stream), and `XREAD COUNT 0` or a negative count means no limit, as Redis does.
- **Known differences.** A client that is not blocked (a plain `LPOP`) can take an element between
  the write and the woken client's retry; Redis serves blocked clients before it runs the next
  command, so there the blocked client would always win. A client blocked on several keys is
  served in first-come order per key, but a slice retry of the head of one of its keys may take
  from another key whose queue had an older waiter, when a write and the slice end coincide. A
  write from another front end reaches a non-head waiter only through the head (at its next
  slice), so a waiter queued behind a client whose key changed type waits for that head's turn.

The tests are in `crates/eggdb-resp/src/tests_blocking.rs`: the reference pages' replies for each
command in RESP2 and RESP3 and their errors; over the real listener, three clients blocked on one
list served first-come first-served by one `RPUSH`, a blocked client that disconnects taking no
element, one that closes behind a pipelined command taking none either and freeing its
connection, a blocked client pipelining far past 64 KiB holding nothing against the budget while
blocked and still getting every reply in order, `PING` and `QUIT` pipelined behind `BLPOP`
answered after its reply and before the close, a client blocked on empty keys opening no write transaction, a server stop ending `BLPOP k 0`, timeouts in both protocols, wake-ups of `BLMOVE`,
`BZPOPMAX`, `XREAD BLOCK $` and `BRPOP` on two keys, a retyped key keeping its client blocked and
`BLMOVE` to a wrong-type destination, blocking commands inside `MULTI`, `INFO`'s
`blocked_clients` counting `BLPOP` and `XREAD BLOCK` waiters up and down (inside `MULTI` too); and an append-only file
with `BLPOP`, `BZPOPMIN`, `BLMOVE` and `XREAD BLOCK` replaying without waiting.

Left: stream consumer groups (`XGROUP`, `XREADGROUP` with `BLOCK`, `XACK`, `XPENDING`, `XCLAIM`,
`XAUTOCLAIM`, `XINFO`), as their own format part (value kind 6, D35), and `WAIT`/`WAITAOF`,
`CLIENT UNBLOCK` and `CLIENT PAUSE`, with the rest of `CLIENT` (D193).
