## D1171 Composite types get their pg_class row, and tables their row type — Decided by the code-only session (2026-11-14, D355); roadmap M6a (the catalog)

- In PostgreSQL a composite type made by `CREATE TYPE ... AS (...)` has a `pg_class` row of `relkind` `c` that its `pg_type.typrelid` points to, with its fields in `pg_attribute`; every table and view has a row type in `pg_type` (`typtype` `c`, `typrelid` the relation) that `pg_class.reltype` points to. EggDB showed `typrelid` 0 and `reltype` 0, so Npgsql's type loading, which keeps only composites whose class has `relkind = 'c'`, never loaded a user composite, and psql's `\d <composite>` found nothing.
- Each user composite now gets a class OID from the same `Space::Relation` batch as the relations, keyed on the type's OID (which a rename keeps, as in D1169). Its `pg_class` row and `pg_attribute` rows are built next to the relations' rows from the type's stored attributes; it is kept out of the relation list itself, so the other catalogs (`information_schema.tables`, SQL Server's and Oracle's views, privileges) do not start listing it, as PostgreSQL's do not.
- Every table and view gets a row type OID in the user type range (16384 and up), from a hash of its relation OID, stepping past user types and other row types. `pg_type` lists them after the user types, `pg_class.reltype` names them. psql's `\dT` and Npgsql already filter them out by `typrelid`/`relkind`, as against PostgreSQL.
- Not yet: `regclass` and `regtype` input of a composite's class or a table's row type by name, and arrays of row types (`typarray` 0).
- Test: `composite_types_and_tables_link_their_pg_type_and_pg_class_rows` in `pg_catalog/tests.rs`.
