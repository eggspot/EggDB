## D546 Kafka idempotent producers — Decided by the code-only session (2026-11-11, D355); roadmap M16

Java's Kafka producer turns `enable.idempotence` on by default since 3.0, and librdkafka's
exactly-once settings need it, so the broker now hands out producer ids and checks sequence
numbers instead of storing a retried batch twice.

- **InitProducerId** (versions 0 and 1) without a transactional id returns the next producer id
  with epoch 0. The id counter is kept in the file (key `4` in the Kafka collection), so ids are
  never reused after a restart. A transactional id is refused with `INVALID_REQUEST` (42) until
  transactions are built.
- **Produce** reads each batch's producer id, epoch and base sequence. A batch without a producer
  (`-1`) is stored as before. For a producer, the partition keeps one state row (key `5`, topic,
  partition, producer id): epoch, last sequence, and the last batch's first sequence, offset and
  record count. A batch is appended when it is the producer's first on the partition with sequence
  0, a new epoch starting at 0, or the next sequence of the same epoch (wrapping after the largest
  int32 as Kafka does); a retry of the last batch answers with that batch's first offset and
  stores nothing; an older epoch is `INVALID_PRODUCER_EPOCH` (47), a gap or reorder
  `OUT_OF_ORDER_SEQUENCE_NUMBER` (45), an id never handed out `UNKNOWN_PRODUCER_ID` (59), and a
  transactional batch `INVALID_TXN_STATE` (48). Every batch of a request is checked before any is
  written, and the states are written in the same transaction as the batches.
- Deleting a topic deletes its producer states. Retention does not remove a state row; it is 22
  bytes per producer and partition.
- Only the last batch per producer is remembered, where Kafka remembers five; a client with more
  than one batch in flight per partition that retries an older one gets 45 and resends from there.
