## D350 One square root for every dialect, MySQL's date-part functions rewritten onto `EXTRACT`, and `ADD INDEX`, `RENAME INDEX` and `DROP INDEX` in MySQL's `ALTER TABLE` — Decided by the build loop (batch 6, 2026-11-10); roadmap M10, extends D316, applies D9 and D10

Only Oracle's dialect had a square root (`oracle_sqrt`): `sqrt(2)` answered `42883` in
PostgreSQL, `SQRT(16)` 1305 in MySQL, `no such function` in SQLite and 195 in SQL Server.
MySQL's `YEAR(d)`, `MONTH(d)`, `DAYOFWEEK(d)` and the other date-part functions were missing,
so D316's and D322's tests wrote `EXTRACT(YEAR FROM d)`, and MySQL's `ALTER TABLE ... ADD INDEX`
answered 1235. Built from PostgreSQL's "Mathematical Functions and Operators", MySQL 8.0's
"Mathematical Functions", "Date and Time Functions" and "ALTER TABLE Statement", SQLite's
"Built-In Mathematical SQL Functions" and Microsoft's "SQRT (Transact-SQL)"; the tests use the
manuals' examples.

- **One square root.** `square_root::square_root(value, dialect)` answers for every dialect; each
  parser names its own internal call (`sqrt` in PostgreSQL, `mysql_sqrt`, SQLite's
  `sqlite_sqrt`, `sqlserver_sqrt`; Oracle keeps `oracle_sqrt`, whose behaviour is unchanged) and
  the internal names cannot be written by users. A negative argument is PostgreSQL's `2201F`
  `cannot take square root of a negative number`, NULL in MySQL and SQLite, and SQL Server's
  error 3623 `An invalid floating point operation occurred.`. PostgreSQL's `sqrt(numeric)` is a
  `numeric` rounded to at least 16 significant digits, keeping the argument's scale when it is
  larger, as PostgreSQL gives it (`sqrt(2::numeric)` is `1.414213562373095`;
  `Numeric::square_root_to_significant_digits`, on the exact decimal square root); every other
  argument is a `double precision` (`float` in SQL Server, `DOUBLE` in MySQL). Text is read as
  each dialect reads it: PostgreSQL parses it as `double precision` (`22P02` otherwise), MySQL
  takes its numeric prefix (`'9abc'` is 9), SQLite gives NULL for text that is no number, SQL
  Server answers 8114 and 206 for a type it cannot convert to `float`.
- **MySQL's date parts on `EXTRACT`.** `YEAR`, `QUARTER`, `MONTH`, `DAY`/`DAYOFMONTH`, `HOUR`,
  `MINUTE`, `SECOND`, `MICROSECOND`, `DAYOFWEEK` (1 = Sunday), `DAYOFYEAR` and `WEEKDAY`
  (0 = Monday) are rewritten by the MySQL parser onto the internal `mysql_extract(unit, value)`
  that `EXTRACT` already uses, with three units `EXTRACT`'s own syntax still refuses
  (`dayofweek`, `dayofyear`, `weekday`). `mysql_date_parts::extract` now reads, for `EXTRACT`
  too: dates, datetimes and timestamps; a `TIME` (its hours unbounded for `HOUR`, the current
  date for a date part, as MySQL converts a `TIME` to a `DATETIME`); strings in date, datetime
  and time forms; and numbers in MySQL's `YYMMDD`, `YYYYMMDD`, `YYMMDDhhmmss` and
  `YYYYMMDDhhmmss` forms. NULL, an invalid date and a string that is no date give NULL; the zero
  date `'0000-00-00'` (with or without a time) gives 0 for the year, quarter, month and day,
  its clock for the time parts and NULL for the day of the week and of the year, as MySQL
  documents. A partition key written `YEAR(d)` works, since key expressions are stored as text
  and parsed again in their dialect. One argument only: another count is 1582.
- **`ALTER TABLE` indexes in MySQL.** `ADD INDEX|KEY [name] [USING ...] (columns)` goes through
  `CREATE INDEX`'s path (`indexes::create_index`), so on a partitioned table it reaches every
  partition (D316) and an unnamed key is named after its first column; `ADD UNIQUE [INDEX|KEY]`
  already made a unique index. `RENAME INDEX|KEY a TO b` renames the index, its comment and,
  on a partitioned table, the partitions' indexes linked to it that carry the same name
  (`partition_indexes::rename_linked`). `DROP INDEX|KEY` already dropped through
  `DROP INDEX`. Errors: 1061 `Duplicate key name` for a name the table has, 1176 `Key 'a'
  doesn't exist in table 't'` for renaming a missing key, 1280 `Incorrect index name` for a
  rename to `PRIMARY`, 1091 `Can't DROP` for dropping a missing one. `ADD FULLTEXT` and `ADD
  SPATIAL` answer 1235 (`FULLTEXT and SPATIAL indexes`), as in `CREATE TABLE`.

Decided: no file format change. A column prefix in a key (`(name(10))`) keeps `CREATE INDEX`'s
behaviour in `ADD INDEX` too: the whole value is indexed, and a `UNIQUE` prefix key is refused
with 1235, because the index definition has no place for the prefix length. The date-part
functions give NULL without MySQL's warning 1292 for a string that is no date. Index names are
compared as written (folded to lower case like every MySQL identifier), as `CREATE INDEX`
compares them.

Tests: `square_root.rs` (PostgreSQL's numeric scale and its error, MySQL's and SQLite's NULLs,
MySQL's numeric prefix, SQL Server's 3623 and 8114), `mysql_date_parts.rs` (the MySQL manual's
examples, zero dates, invalid dates, numbers, stored dates and times), `partition_tests.rs`
(`ADD INDEX`, `RENAME INDEX` and `DROP INDEX` on a table partitioned by `YEAR(d)` reach every
partition; 1061 and 1091), and new cases in the MySQL suite (`SQRT`, every date-part function on
literals and on stored `DATE`, `DATETIME(6)` and `TIME` columns, zero dates, 1582, the
`ALTER TABLE` index forms with `SHOW INDEX`, 1061, 1176, 1091 and 1235), the PostgreSQL suite
(`sqrt` of `double precision` and `numeric`, `2201F`), the SQLite suite and the SQL Server
suite (3623).

Left: MySQL's `WEEK()` with its modes and `DATE_FORMAT()`, warning 1292 from the date-part
functions, dates with a zero month or day other than `'0000-00-00'`, and prefix indexes (an
index-definition format change).
